# Карта данных `Claude-Memory/Gaming/` — кто пишет, что читать, чего не делать

Читать перед любым режимом, который трогает библиотеку, список «присматриваюсь» или профиль вкуса.
Правило раздела: **один файл — один писатель, слияние при чтении.** Файлы не сводятся в один и не
«синхронизируются» переносом записей.

## Файлы

| Файл | Писатель | Что хранит | Скилл |
|---|---|---|---|
| `taste-profile.yaml` | **скилл** | модельные поля: `mood_clusters` (веса), `anti_patterns`, `wishlist_hints`, `library` с вердиктами калибровки, история рекомендаций | читает и пишет |
| `library_full.yaml` | **скилл** (режим ОБНОВЛЕНИЕ ПРОФИЛЯ: Exophase, Steam) | полный список купленного: название, платформа, часы | читает и пишет |
| `watchlist.yaml` | **скилл** (режим ПРИСМАТРИВАЮСЬ) | игры «хочу / на-карандаш / не-интересно»: `condition`, `note`, пороги числом, `nsuid_us`, `source` | читает и пишет |
| `recommendations/*.md` | **скилл** | выдачи и их `итог` | читает и пишет |
| `user-state.json` (`gaming-user@1`) | **сайт** (карточка игры, `/api/gm/save`) | поля владельца по игре: `state`, `demo`, `progress`, `rating`, `note`, `hours`, `platform`, `price_target_usd`, `discount_target_pct`, `nsuid_us`, `steam_appid`, `eshop_url`, `cover_url`, `store_title`, `cover_tried`, `deleted`, `added`, `updated` | **только читает** |
| `eshop-prices.json` | **сайт** (задача цен, 08:30 МСК и кнопка) | цены US eShop игр списка | только читает (годен 24 ч) |

Платформы — коды `switch2`, `switch`, `steam_deck`, `steam`, `pc`, `xbox`. Игра описана **тремя осями**; в YAML скилла писать те же коды:

| Ось | Поле | Коды | Когда |
|---|---|---|---|
| Статус | `state` | `хочу`, `на-карандаш`, `не-интересно` (подпись «не хочу»), `куплена` | всегда |
| Демо | `demo` | `true` (нет поля или `false` — нет) | только при некупленном `state`; у `куплена` флага нет |
| Прохождение | `progress` | `не-начата` (по умолчанию, = null), `играю`, `отложена`, `пройдена`, `брошена` | только у `куплена` и у игр с `demo: true`, у остальных null |
| Оценка | `rating` | `восторг`, `понравилось`, `нормально`, `не понравилось` или null | всегда |

`demo: true` (оверлей) — играл в демо, игру не купил: новинкой не предлагать; оценку такой игры учитывать при
калибровке как слабое наблюдение с пометкой «демо»; вес кластера по одной демо-оценке не менять.

**Старые значения** (в файлах владельца могут встретиться до миграции) читаются одним правилом: `state` `демо` → `demo: true` + статус `не-интересно`, если `rating` «не понравилось», иначе `на-карандаш`; `state` `играю` / `пройдена` / `брошена` →
статус `куплена` + `progress` с тем же словом; `rating` `брошено` → оценки нет и, если `progress` пуст, `progress: брошена`.
Вердикт `брошено` в `library` советника читается так же: прохождение «брошена», оценки нет; остальные нестандартные вердикты (например «смешанно») — как есть.

## Как читать

1. Ключ игры во всех файлах — название без регистра и пунктуации. Название в YAML скилла не менять
   без причины: по нему запись сайта находит свою игру.
2. Собрать игру = запись YAML скилла + поверх неё непустые поля записи `user-state.json` с тем же ключом.
   Поля сайта главнее: `rating` вместо вердикта `library`, `hours` вместо часов `library_full`, `state`
   вместо `status` watchlist, пороги и `note` — тоже.
3. `state` куплена у игры из watchlist → она уже в библиотеке, новинкой не предлагать.
   `не-интересно` → жёсткий фильтр. `deleted: true` → игры нет.
4. Запись есть только в `user-state.json` (владелец добавил игру на сайте) → это полноценная игра
   библиотеки или списка; в YAML её не переносить.
5. Расхождение файлов — не ошибка и не повод для правки: его разрешает чтение.

## Чего не делать

- Не писать и не править `user-state.json` и `eshop-prices.json` ни при каких запросах (миграцию оверлея на три оси выполняет владелец скриптом сайта `tools/gaming_migrate.py`, не скилл).
- Не переносить записи между слоями: ни `library` → `user-state.json`, ни оценки и часы сайта → YAML.
  Просят «перенеси всё в один файл» → объяснить устройство и отказаться.
- Не удалять игру из YAML из-за того, что на сайте она `deleted` или куплена: достаточно учесть при чтении.
  Исключение — штатный шаг КАЛИБРОВКИ «купил и играл → убрать из `watchlist.yaml`».
- Не дублировать оценку владельца в `library.verdict` и не «исправлять» её.

## Как обновлять вкусы

Источник наблюдений — оценки и часы владельца в `user-state.json`; место результата — только
`taste-profile.yaml`. Шаг 0 КАЛИБРОВКИ: взять записи с `rating`, у которых `updated` новее
`taste-profile.yaml: updated`; по каждой решить вслух, меняет ли она вес кластера (типичная для кластера
игра, оценка расходится с ожиданием → шаг ±0.05–0.1) или нет (единичное наблюдение, оценка совпала).
После калибровки обновить `taste-profile.yaml: updated` — это и есть отметка «оценки сайта учтены до этой даты».
