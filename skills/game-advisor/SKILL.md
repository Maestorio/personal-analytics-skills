# game-advisor

Целевая модель: Sonnet (РЕКОМЕНДАЦИЯ/КАЛИБРОВКА), Haiku допустим для ПРОВЕРКИ ЦЕН.

## Контекст пользователя (постоянный)

- Платформы: **Nintendo Switch 2** (приоритет по умолчанию) + Steam Deck. Игры Switch 1
  рассматривать как совместимые, с проверкой наличия Switch 2 Edition / бесплатного обновления.
- US eShop: доступ готов (аккаунт + оплата) — цены US-региона всегда включать в выдачу.
- Физические копии: интерес есть (распродажи; зарождающаяся традиция покупать в поездках).
- Язык: русская локализация — плюс-фактор; её отсутствие — трение для текстонасыщенных
  JRPG (прецедент: Chained Echoes отложена частично из-за английского). Для каждой
  рекомендации указывать наличие русского языка (интерфейс/субтитры).
- Язык вывода: русский. Названия игр — оригинальные (не переводить).

## Карта данных (читать первой)

`Gaming/` — два слоя с разными писателями: YAML скилла (`taste-profile.yaml`, `library_full.yaml`,
`watchlist.yaml`, `recommendations/`) и файл сайта `user-state.json` с полями владельца (состояние,
оценка, часы, заметка, пороги), который скилл **только читает** и считает главнее своих YAML. Записи
между слоями не переносятся. Полная карта, порядок чтения и запреты — `references/data-layout.md`:
прочитай её до первого чтения или записи файлов `Gaming/`.

## Режимы

Определи режим по запросу. Если неоднозначно — уточни одним вопросом.

### 1. РЕКОМЕНДАЦИЯ (режим по умолчанию)

Вход: настроение/запрос («хочу большой сюжет на 40+ часов», «потупить вечером»,
«кооп с партнёром»).

Алгоритм:
1. Загрузи `Gaming/taste-profile.yaml` (транспортный протокол — ниже). Если хранилище
   недоступно — используй встроенную копию `references/taste-profile.yaml` и предупреди
   об устаревании.
2. Сопоставь запрос с одним из **кластеров настроения** профиля (yaml: `mood_clusters`).
3. Загрузи `Gaming/watchlist.yaml` и учти его ДО поиска: записи `хочу` и
   `на-карандаш`, подходящие под кластер, — готовые кандидаты (пометить «это уже
   обсуждалось, <дата>»); `не-интересно` — жёсткий фильтр, в выдачу не попадают.
   Затем `Gaming/user-state.json` (оверлей правок владельца с сайта, `gaming-user@1`): его
   `state`, `rating`, `note` и пороги **главнее** записей watchlist и library с тем же названием;
   `state` куплена — игра уже в библиотеке, новинкой не предлагать (прохождение `progress` — отдельная ось, не состояние);
   `не-интересно` — тот же жёсткий фильтр; `deleted: true` — игры нет. Оверлей скилл только читает.
4. web_search по каталогу: новинки Switch 2 + проверенная классика Switch 1, подходящая
   под кластер и **отсутствующая** в `library`. Фильтр отрицательных сигналов
   (`anti_patterns`) обязателен — особенно «стена гринда» и MMO-структуры.
5. Для каждого кандидата собери: жанр/теги, длительность HLTB, оценку OpenCritic,
   объём и тон пользовательских отзывов (источники с доверием ≥ СРЕДНЕЕ,
   см. `references/source-trust.md`), наличие русской локализации.
6. Цены: US eShop (+ активные скидки, DekuDeals как агрегатор) и 2–3 московских магазина
   из `references/stores-moscow.md` + самостоятельный поиск других точек
   (список пользователя — проверенные, но не исчерпывающие). Цены только из
   загруженных страниц; цены по памяти запрещены.
7. Выдача: список 3–7 позиций (с учётом методологии отбора ниже: 70/30 разведка,
   diversity-чек, техно-гейт). Для каждой позиции — карточка из блоков:
   - **Почему именно эта** — явный мостик к конкретной игре из истории («понравится,
     если зашла X»); для discovery-пика — мостик по латентной оси, а не по жанру.
   - **Отзывы (суть, не только цифра)** — оценка критиков (OpenCritic) + краткая
     выжимка: что хвалят и на что жалуются критики И игроки (сентимент, а не балл).
   - **Отзывы на техсостояние** — отдельно: как игра идёт (Digital Foundry / перф-жалобы
     в свежих отзывах именно Switch 2-версии). 30fps — не минус; дёрганье/фрейм-пейсинг/
     баги — красный флаг с понижением в списке.
   - **Длительность** HLTB (Main / Main+Extra).
   - **Русский язык** (интерфейс/субтитры: да/нет; для текстонасыщенных — вес к приоритету).
   - **Цены** — цифра US eShop + физика Москва/поездка (только из fetched-страниц).
   - **Ссылки на источники** для самостоятельной проверки (обязательно).
8. Предложи сохранить выдачу в `Gaming/recommendations/YYYY-MM-DD-<slug>.md`.
9. Реакцию пользователя на каждого кандидата занеси в `Gaming/watchlist.yaml`
   (режим 1a ниже) — иначе обсуждённое теряется между сессиями.

**Pre-emit checklist `taste-profile.yaml` (при любой правке профиля —
КАЛИБРОВКА, ОБНОВЛЕНИЕ ПРОФИЛЯ).** Файл читают внешние потребители
(индексы, дашборды) как строгий YAML — перед выдачей сверь:
- ключи верхнего уровня не переименовывать: `updated`, `platforms`,
  `mood_clusters`, `latent_axes`, `anti_patterns`, `library`;
- у каждого кластера в `mood_clusters`: `title` (человекочитаемое имя),
  `weight` (0..1), `evidence` (список строк), опц. `notes`;
- формат evidence-строки: `Название [NN.Nч] [(вердикт|stated)]` — часы
  с суффиксом `ч`, пометка в круглых скобках; ничего другого в скобках
  названия не писать;
- `verdict` в `library` — строго из enum: `восторг` / `понравилось` /
  `нормально` / `не понравилось` (+ опц. `progress`: `не-начата` / `играю` /
  `отложена` / `пройдена` / `брошена`; опц. `причина` из реестра тегов дропа);
  `verdict: брошено` — прежний формат: читать как `progress: брошена` без оценки;
- `anti_patterns` — список `{pattern, evidence}`;
- `updated` — дата `YYYY-MM-DD`.

**Машиночитаемость выдачи (обязательные маркеры).** Файл рекомендации читают
внешние потребители (индексы, дашборды) — сохраняй в нём стабильные якоря:
- шапка-список с полями `- **Дата:** YYYY-MM-DD`, `- **Кластер:** <slug>`,
  опц. `- **Склоняется к:** …`;
- секция `## Кандидаты` с таблицей, где есть колонки **«Игра»** и **«Роль»**
  (роль = краткое «почему именно эта», мостик);
- секция `## Итоги` со строками вида `- Название — \`итог:\` _(…)_` —
  заполняется в КАЛИБРОВКЕ.
Переименование этих секций/колонок ломает внешние парсеры — не менять без нужды.

Правила:
- НЕ рекомендовать игры из library (кроме «переиграть/DLC» по явному запросу).
- Массовые хиты, которые пользователь очевидно знает (Mario Kart, основные Zelda),
  не предлагать без причины — ценность в неочевидных находках.
- Отмечать наличие демоверсии в eShop — пользователь активно пробует демо.
- Для JRPG обязательная проверка на «стену гринда» (отзывы уровня Main story:
  жалобы на принудительный фарм опыта → флаг).
- **Анти-выгорание / жанровое разнообразие (обязательно).** Не замыкаться на топ-кластерах.
  В каждой выдаче — минимум 1 позиция из смежного или непривычного жанра (за пределами 2–3
  доминирующих кластеров), помеченная как «смена ритма / свежий вкус». Баланс: большинство
  под текущее настроение, но 1–2 «вбок». Причина — засиживание на одном типе игр ведёт к
  игровому выгоранию; задача скилла — мягко расширять, а не только подтверждать привычку.
  Стретч-пик подбирать не случайно, а через мостик от того, что зашло (напр. от roguelike
  к тактике/иммёрсив-симу), и указывать этот мостик явно.

### Методология отбора (гибрид + разведка)

Скилл — не чистый content-based матчер по жанрам (у него врождённая over-specialization).
Отбор строится как гибрид с явной квотой разведки:

- **Content-слой** — mood_clusters + `latent_axes` профиля («зайдёт, если зашла X»).
- **Collaborative-слой (через веб)** — co-occurrence: «тем, кому зашли ELDEN RING + BG3 +
  Xenoblade, часто заходит Y». Аппроксимация без базы игроков: Steam «More like this»,
  кураторские списки «if you liked…», подборки. Даёт кандидатов ВНЕ явных жанров.
- **Квота разведки 70/30** — в каждой выдаче ~70% «в точку» (сильные кластеры) + ~30%
  discovery. Из discovery ≥1 — серендипный пик: неожиданный жанр, но лежащий на
  «любит»-оси из `latent_axes` (мостик обязателен, не рандом).
- **Diversity-чек** — не более 2 позиций одного кластера в списке из 5–7.
- **Техно-гейт (flag-but-show)** — пост-фильтр независимо от вкуса. 30fps не штрафуется;
  дёрганье / плохой фрейм-пейсинг / низкая оценка за техсостояние порта (Digital Foundry
  или свежие отзывы именно Switch 2-версии) → красный флаг + понижение в списке, но
  позиция остаётся (решение за пользователем).
- **Петля-бандит** — verdict'ы по explore-пикам в `recommendations/*.md` тюнят долю
  разведки и набор осей при ретроспективе скилла.

### 1a. ПРИСМАТРИВАЮСЬ (обсуждено, но не куплено)

После каждой выдачи РЕКОМЕНДАЦИИ реакция пользователя на КАЖДОГО кандидата
попадает в `Gaming/watchlist.yaml` — список «обсудили, но не куплено». Это
делает скилл, страница `games.html` только читает (экран «Присматриваюсь»).

Отображение реакции в `status` (строго из enum):

| Реакция пользователя | status |
|---|---|
| «интересно», «хочу», «возьму потом» | `хочу` |
| промолчал / «по желанию» / «подумаю» / «пока не хочу» | `на-карандаш` |
| «не интересно», «не предлагать», явный отказ | `не-интересно` |

Правила ведения:
- **Купил — запись уходит из watchlist** в `taste-profile.yaml: library`
  (вердикт появится в КАЛИБРОВКЕ). Дублировать игру в обоих файлах нельзя.
- Игра уже в watchlist и обсуждается снова → **обновить существующую запись**
  (status/condition/note + `added` не трогать), а не добавлять вторую.
- Не предлагать в новой выдаче то, что лежит со `status: не-интересно`;
  `хочу` и `на-карандаш` предлагать можно — напомнив, что это уже обсуждалось,
  и проверив, не выполнилось ли `condition` (скидка, порт, формат).
- **Правила отбора (исключения по издателю, традиции покупок) — НЕ здесь.**
  Их место — `wishlist_hints` в профиле: watchlist хранит игры, а не политику.
- **Оверлей `user-state.json` скилл не пишет и не переносит.** Поля, которые владелец задал на сайте
  (состояние, оценка, заметка, пороги цены, `nsuid_us`), живут там и при чтении перекрывают watchlist и
  library; расхождение между файлами — не ошибка, его разрешает чтение, а не правка YAML. Статус (4: `хочу` / `на-карандаш` / `не-интересно` / `куплена`; «играл в демо, не купил» — флаг `demo: true` при некупленном статусе: игра с флагом — не новинка, не предлагать),
  прохождение и платформы — кодлисты `game_state` / `game_progress` / `game_platform` (`codelists.json`; правило чтения — `references/data-layout.md`); watchlist знает только `хочу` / `на-карандаш` / `не-интересно`.

**Pre-emit checklist `watchlist.yaml`** (файл читает страница как строгий YAML):
- верхний уровень: `schema_version`, `updated` (`YYYY-MM-DD`), `items`;
- запись: обязательные `title` + `status` из enum выше; опц. `platform`,
  `condition` (при каком условии вернуться), `note`, `added` (`YYYY-MM-DD`,
  ставится один раз);
- `source` — имя файла подборки; **обязателен, если игра пришла из выдачи**:
  карточка на странице ссылается по нему на отчёт (`recommendations/<source>`),
  и несуществующее имя открывает пустой слайдовер. Игра из разговора без
  сохранённой подборки — `source` **не ставить** (не «чат …»: это не файл;
  контекст — в `note`);
- `updated` — на дату правки; сортировку страница делает сама (по `added`).
- цены US eShop (опц., с 2026-10-21): `eshop_url` — ссылка на страницу игры в US eShop
  (находит скилл; издание Switch 2 — отдельная страница на `-switch-2`), `nsuid_us` —
  строка цифр, `store_title` — название из магазина. **Ценовой порог — числом, обязательно,**
  если `condition` его задаёт: «≤ $10» → `price_target_usd: 10`, «скидка ≥ −50%» →
  `discount_target_pct: 50` (оба сразу — выполнен любой). «Просто скидка» или условие без
  цены — порогов не ставить: о любой новой скидке сайт и так пришлёт push. Текст в
  `condition` сайт не читает. `nsuid_us`/`store_title` по ссылке заполняет
  `tools/eshop_lookup.py`, без них сайт цену игры не загружает.

### 2. КАЛИБРОВКА (петля обратной связи)

Вход: «зашла/не зашла [игра]», «прошёл X, вот впечатления», оценка прошлой рекомендации, а также
**оценки с сайта**: «сверь оценки с сайта», «учти мои оценки в профиле» — и всегда шагом 0 любой калибровки.

0. **Оценки с сайта.** Загрузи `Gaming/user-state.json`; возьми записи с `rating`, у которых `updated`
   новее `taste-profile.yaml: updated` (это оценки, поставленные владельцем в карточке игры после
   последней калибровки). По каждой реши отдельно и скажи вслух: меняет ли она веса кластеров
   (игра типична для кластера и оценка расходится с ожиданием → шаг ±0.05–0.1) или нет (единичное
   наблюдение, нетипичная игра, оценка совпала с ожиданием → веса не трогать, только отметить). Саму
   оценку в `library` не копировать — она живёт в оверлее. Нечего учитывать → так и сказать.
1. Загрузи `taste-profile.yaml` и последние файлы из `recommendations/`.
2. Обнови: `library` (новая запись с оценкой), веса `mood_clusters.<slug>.weight` (малый шаг
   ±0.05–0.1, не перекалибровывать по одному наблюдению), при необходимости `anti_patterns`.
   Оценка, поставленная владельцем на сайте (`rating` в `user-state.json`), — данность: в `library`
   вердикт не дублировать и не переписывать, веса калибровать по ней.
3. Если игра лежала в `watchlist.yaml` — **убери запись оттуда** (купил и играл →
   её место в `library`) либо поменяй статус, если передумал, не купив.
4. Если игра была из прошлой рекомендации — обнови её `итог` в файле выдачи
   (попадание / промах / частично) — данные для ретроспективы самого скилла.
4. Обнови поле `updated` на сегодняшнюю дату. Если оно уже равно сегодняшней — оставь
   след калибровки (строка в `data_sources` или комментарий), чтобы правка была
   прослеживаема даже при совпадении дат. Сохрани профиль (транспортный протокол ниже),
   покажи изменения (diff).

Шкала оценок в library: `восторг / понравилось / нормально / не понравилось`; прохождение — необязательное поле `progress`.
Сила сигнала: брошенная игра (`progress: брошена`) без оценки — отрицательный сигнал прежней силы; с оценкой действует оценка;
оценка игры с флагом `demo: true` — слабое наблюдение с пометкой «демо»; вес кластера по одной демо-оценке не менять. Для брошенных фиксировать причину одним тегом: `стена-гринда / язык / жанр-мимо /
сложность / темп / не-время` (последний = «может вернусь», не отрицательный сигнал).

**«Синхронизируй профиль с сайтом»** — разовый перевод своих YAML на три оси и перекалибровка: в `taste-profile.yaml`
каждый `library.verdict: брошено` → `progress: брошена`, `verdict` снять, `причина` сохранить; затем веса кластеров — по всем
оценкам `user-state.json` (шаг 0, без отсечки по `updated`). Файл сайта скилл не трогает.

### 3. ОБНОВЛЕНИЕ ПРОФИЛЯ (массовая загрузка)

Вход: новый webarchive/HTML Exophase, CSV/скриншоты Steam, ручной список.

1. Распарси источник (Exophase webarchive: plistlib → WebMainResource →
   `ul.overview > li`: `h3` — название, `span.hours` — часы, `div.lastplayed` — дата).
2. Слияние в `library` по названию (нормализация: обрезка пробелов, без ™/®).
   Новые часы = max(старое, новое).
3. **Известное ограничение данных:** Exophase занижает часы (прецедент: Animal Well
   показан как 6 минут, фактически пройдена). Часы — индикатор, не истина; при
   противоречии с явным утверждением пользователя приоритет у пользователя.
4. Пересчитай агрегаты кластеров, покажи изменения, сохрани.

### 4. ПРОВЕРКА ЦЕН

Вход: конкретная игра (или список).

1. Цена US eShop: сначала `Gaming/eshop-prices.json` (загрузка сайта, 08:30 МСК) — если
   `fetched_at` моложе 24 ч и игра там есть, цена оттуда с пометкой «US eShop API, загрузка
   сайта <время>»; старше, `status: unavailable` или игры нет — со страницы магазина, как
   раньше. История скидок — DekuDeals: `dekudeals.com/items/<slug>`.
2. Московские магазины из `references/stores-moscow.md` — по лестнице источников
   (WebSearch → Chrome MCP для JS-каталогов → web_fetch для статики), поиск по названию.
   Плюс самостоятельный поиск: другие магазины с наличием картриджей.
3. Наличие + цена + формат (полноценный картридж / Game-Key Card / Switch 2 Edition).
4. Таблица: магазин | цена | формат | ссылка. Вывод: где выгоднее и на сколько.

### 4a. СКИДОЧНЫЙ ПРОГОН (без названия игры)

Вход: «что есть интересного по скидке», «посмотри распродажу eShop», «стоит ли
что-то брать сейчас» — игра НЕ названа.

**Начинать с `watchlist.yaml`, а не с поиска новинок.** Список уже отобран
вкусом пользователя; искать новое, не проверив его, — предлагать чужое вместо
своего же отложенного.

1. Прочитай `Gaming/watchlist.yaml`. Проверь цены по **`status: хочу`**
   (приоритет) и **`status: на-карандаш`** (вторым эшелоном); `не-интересно`
   не проверять вовсе. Цены — по правилу шага 1 режима 4 (`eshop-prices.json` моложе 24 ч,
   там же `target_met` для `price_target_usd` / `discount_target_pct`).
2. Для записи с `condition`, где задан ценовой порог («ждёт скидку ≤ $24.99»),
   **явно скажи, выполнен он или нет** — это и есть повод к покупке; выполненный
   порог выносится наверх выдачи. Для `condition` о формате/порте (картридж,
   релиз на Switch 2) проверь, не изменилось ли положение дел.
3. Только после этого — обычный поиск скидок среди новых кандидатов
   (методология отбора 70/30, diversity-чек, техно-гейт).
4. Выдача делится на два блока: **«Из твоего списка»** (с отметкой, что это
   уже обсуждалось и когда) и **«Новое»**. Скидки в обоих блоках — только из
   фактически прочитанных страниц.
5. Реакция на кандидатов из блока «Новое» заносится в watchlist (режим 1a);
   купленное — переносится в `library`.

### 5. МАГАЗИНЫ В ПОЕЗДКЕ

Вход: «где купить игры в [городе/стране]» (часто в связке с travel-planning).

0. Сначала проверь `references/stores-travel.md` — проверенные пользователем точки
   по городу (якоря). Не отменяет самостоятельный поиск и перепроверку свежести.
1. По лестнице источников: WebSearch по локальным игровым магазинам (ретро/новые) и
   крупным сетям региона (примеры: GEO/Book-Off/TSUTAYA — Япония; GAME —
   Великобритания/Испания; Media Markt — Германия/Нидерланды); каталог/витрину на
   JS-сайтах (Авито и пр.) дочитывать через Chrome MCP, если подключён.
2. Для 3–5 точек: адрес, специализация (новое/ретро/б-у), ориентир цен, отзывы.
3. Обязательно перепроверь актуальность (не закрылся ли магазин) — источник свежее 12 мес.
4. Если параллельно идёт работа travel-planning: предложи добавить точку в маршрут.
5. Region-lock: физические картриджи Switch region-free; но обновления Switch 2 Edition
   и DLC привязаны к региону аккаунта — предупреждать при покупке за рубежом.

## Лестница источников (web-retrieval)

Порядок каналов при чтении каталогов, цен, оценок и магазинов. Использовать первый
сработавший; при пустом результате спускаться ниже:

1. **WebSearch** — основной канал. Новинки Switch 2, оценки OpenCritic/HLTB, порядок цен,
   поиск магазинов по городу. Без настройки, работает всегда.
2. **Chrome MCP (opt-in)** — для JS-тяжёлых и закрытых для `web_fetch` сайтов
   (Авито, DekuDeals, каталоги магазинов). `navigate` + `get_page_text` читают
   отрендеренную страницу в браузере пользователя (его регион/сессия). Включается, если
   подключено расширение Claude for Chrome — проверка `list_connected_browsers` непуста.
   Если браузер не подключён — ступень пропустить, не падать. Подтверждено на живом Авито
   (2026-07-06): бренд-страница магазина с полным каталогом читается напрямую.
3. **web_fetch** — статические каталожные страницы (большинство магазинов Москвы).
4. **webarchive / HTML от пользователя** — только если сайт закрыт для всех каналов выше
   и пользователь сам приложил файл. Парсинг офлайн через `plistlib` → `WebMainResource`
   (schema.org-разметка или Exophase-структура). Аварийный костыль, не штатный режим.

Провенанс-гейты и блокировки скриптами, прокси или альтернативным сетевым доступом
**не обходить**. Если ни один канал не достаёт — честно сообщить «источник недоступен»,
данные не выдумывать. Цены — всегда только из фактически прочитанной страницы.

## Транспортный слой (Claude-Memory/Gaming/)

Следует общему протоколу `transport-layer.md` библиотеки Claude-Memory.
Транспорт один — Synology mount.

**Шаг 0.** Перед первой записью в Claude-Memory прочитать `_hub/settings.json`; `ai_mode: off` → в Claude-Memory не писать, сообщить владельцу, что сайт в режиме без ИИ и правки идут с сайта.

Пути (дополнение к общему списку):
```
GAMING_DIR             = {MEMORY_ROOT}/Gaming
GAMING_PROFILE         = {GAMING_DIR}/taste-profile.yaml
GAMING_LIBRARY_FULL    = {GAMING_DIR}/library_full.yaml
GAMING_WATCHLIST       = {GAMING_DIR}/watchlist.yaml
GAMING_ESHOP_PRICES    = {GAMING_DIR}/eshop-prices.json   # пишет сайт (hub-notify), скилл только читает
GAMING_RECS_DIR        = {GAMING_DIR}/recommendations
GAMING_INDEX           = {GAMING_DIR}/INDEX.md
```

Инструменты: `Read`, `Write`, `Edit`, `Glob`, `request_cowork_directory`.
Bash-пути не использовать.

Проверка доступности (первый шаг сессии) — рабочий корень (`SCOPE_ROOT`) этого
скилла `GAMING_DIR`, **корень `MEMORY_ROOT` не запрашивать и не листать:**
1. `Glob("*", path=GAMING_DIR)` — если пусто или ошибка →
   `request_cowork_directory(path=GAMING_DIR)`.
2. Объяснить: «Нужен доступ к Synology Drive — в каждой новой сессии Cowork доступ
   даётся заново.»
3. Повторить Glob. Если снова ошибка → **остановиться и сообщить пользователю**;
   при необходимости выдать файл в чат для ручного сохранения. Никуда больше не писать.

**NAS первичен, Mac-зеркало — кэш.** Файлы `recommendations/*.md` пишет только
скилл (веб их не правит). Штатно записи доезжают до зеркала за секунды
(File Station-гибрид server.py, 2026-08-13), но при отказе гибрида
(DSM недоступен) сайдкар молча пишет локально — тогда зеркало отдаёт
устаревшую версию до перезапуска Drive Server. Если свежий вердикт
критичен для калибровки/ретроспективы, а его не видно — предупредить
пользователя; эталон — файл на NAS (виден через страницу games).

Типовые операции:
```python
# Читать профиль
profile = Read(f"{GAMING_DIR}/taste-profile.yaml")

# Обновить профиль: читать → merge → писать (никогда не перезаписывать без merge)
Write(f"{GAMING_DIR}/taste-profile.yaml", content=updated_yaml)

# Сохранить выдачу рекомендаций
Write(f"{GAMING_RECS_DIR}/{today}-{slug}.md", content=markdown)

# Последние выдачи для калибровки
recs = sorted(Glob("*.md", path=GAMING_RECS_DIR))
```

## Ретроспектива скилла (раз в квартал или по запросу)

По файлам recommendations/ с заполненными итогами: доля попаданий, систематические
промахи (по кластерам), корректировка методологии. Формат — упрощённый
retrospective-forecast-audit: одна шкала «купил и зашло / купил и не зашло / не купил».
