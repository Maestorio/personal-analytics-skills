# Шаг 4-plan — Генерация markdown-плана (emit-plan mode)

> Вынесено из SKILL.md дословно при дроблении 2026-08-12 (этап 3, подготовка Max → Pro).

## Шаг 4-plan — Генерация markdown-плана (вместо Шага 5)

**Активируется** при `emit_plan: true` в Шаге 4 или при явном `--emit-plan`.

### Цель шага

Вместо запуска FCA в текущей сессии — выдать пользователю markdown-документ,
описывающий **в каком порядке, с какими промптами, на какой модели запустить
каждый FCA в отдельном чате**. Это:
- Дешевле (Sonnet на FCA в свежей сессии вместо Opus на оркестрации в
  длинной).
- Можно паузить, распараллеливать, выполнять с разных устройств.
- HST → отдельный чат (Opus).

### Формат

Использовать шаблон `references/rebuild-plan-template.md`. Базовая структура:

1. **Шапка** — режим, дата, scenario matrix, список факторов
2. **Сводка факторов** — таблица из Шага 4 (factor / current_state / dependencies)
3. **Порядок выполнения** — нумерованный список по DAG
4. **Шаги 1..N** — для каждого фактора: тип (Type 1/2), модель (Sonnet),
   готовый промпт `/forecast-confidence-applier ...`, expected output
5. **(Опц.) HST блок** — для каких прогнозов рекомендуется HST + промпт
   `/hypothesis-stress-tester ...` на Opus
6. **Финал** — промпт `/macro-forecast-chain --mode ASSEMBLE-ONLY` (или
   эквивалентное «assemble-only» в свободной форме)

### Перед формированием промпта — Glob существующих forecast по теме

Для каждого фактора в плане **обязательно** прогнать `Glob("{topic}*.yaml", path="forecasts/")`. Если найдены файлы с `status: active`:

1. В expected output шага плана добавить **явное указание**:
   > Если по этой теме уже есть active forecast (`{old_basename}.yaml`), новый FCA должен включить в output поле `replaces: {old_basename}.yaml` на верхнем уровне forecast YAML. Это сигнал для save-to-library workflow B5: вариант (a) — новая версия + старый получает `status: superseded` + `superseded_by:`.

2. Если найдено несколько active на одну тему (data hygiene-проблема — должна была быть один) — перечислить все и попросить пользователя выбрать canonical, который замещается.

3. **Не передавать в промпт** `forecast.central_estimate` или per-scenario значения из старого файла — это нарушение принципа «не делать работу FCA» (см. anti-patterns ниже). Только имя файла как target для `replaces:`.

### Anti-patterns при генерации промптов

**Принцип: orchestrator не делает работу FCA.** Промпт каждого FCA должен быть **минимальным** — тема, горизонт, домен, тип, путь к scenario YAML. Никаких:

- ❌ **Интерпретаций неосевых факторов через сценарии.** Например, для Brent нельзя писать «Sc-A → нормализация Ормуза, иранский экспорт восстанавливается». Это работа Шага 1.5B самого FCA: он прочитает scenario YAML, оценит влияние на фактор, проатрибутирует источники. Если orchestrator пропишет интерпретацию — FCA получит anchor и потеряет независимость.
- ❌ **«Базовые данные из текущего прогноза как отправная точка».** Никаких `L1 weighted median: $68/bbl`, `working modal Sc-D $107/$93`. Каждый FCA-запуск стартует чисто.
- ❌ **Копирования описаний сценариев из scenario YAML в промпт.** FCA откроет файл по `source_matrix:` сам.

**Допустимо:**
- ✓ Пометка `axis_dependent: true` для факторов, которые **сами являются осью** сценарной матрицы (например, sanctions в geopolitics-матрице). Это by construction, не интерпретация.
- ✓ Upstream factor dependencies из DAG (если фактор зависит от другого фактора, который пересчитывается на предыдущем шаге плана) — указать **порядок выполнения**, но не передавать значения upstream forecast в промпт.
- ✓ Указание Type 2 conditional vs Type 1 isolated.

Это правило — для всего шаблона. См. `references/rebuild-plan-template.md` секция «Anti-patterns при составлении промпта».

### После выдачи плана

Сохранить артефакт через save-to-library в `Claude-Memory/_audits/rebuild-plan-{date}.md`
(опц., по запросу пользователя). Сессия завершается без запуска FCA. Скилл явно
напоминает: «План выдан. Когда выполнишь все FCA по списку — запусти
`/macro-forecast-chain --mode ASSEMBLE-ONLY` для финальной сборки bundle».
