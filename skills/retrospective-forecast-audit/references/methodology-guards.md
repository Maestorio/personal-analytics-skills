# Methodology Guards: операционные правила защиты от срыва аудита

Этот файл объединяет операционные правила, без которых скилл срывается на длинных задачах: sequential guard, pre-output checkpoint, fail-fast, правила Deep Research, шаблон Refusal.

Применять перед каждой публикацией финального отчёта (Full ИЛИ Light) и при каждом сбое инструмента.

---

## 1. Sequential Guard

**Запрещено публиковать любой ответ, в котором отсутствует основная таблица вердиктов**, кроме случаев:
- Шаг 0 явно вернул отказ (горизонт не наступил, нет даты прогноза, нечего аудитировать)
- Активирован Refusal-режим (см. §5)
- Пользователь прервал аудит в середине

**Reference Set (§0) сам по себе — НЕ финальный отчёт.** Это промежуточный артефакт, всегда часть полного отчёта вместе с таблицей вердиктов и итоговым выводом.

**Если в разговоре есть DR-досье, собранное по workflow B до активации скилла** — это сырьё для §0/§3/§4, а не финал. Всегда нужно довести до §0–§8 + docx по полной процедуре. Структура «Часть A / B / C» из DR-досье НЕ переносится в финальный аудит — финал имеет структуру §0–§8.

**Если web_search/web_fetch вернул только фрагменты для §0** — это сигнал перейти к декомпозиции тезисов и Шагам 4–7, а НЕ повод опубликовать.

**Если контекст начинает заканчиваться, а таблицы вердиктов ещё нет** — приоритет на её создание. Не пиши длинные §3 shape-of-error блоки до того, как готова §2.

## 2. Pre-Output Checkpoint

Перед публикацией финального ответа **обязательно** пройди этот чек-лист в порядке. Если хоть один пункт не выполнен — НЕ публикуй финал, а: (a) дозаполни недостающее, либо (b) явно сообщи о неполноте.

### Для Full Audit
- [ ] Шапка отчёта содержит «**Тип анализа:** Full Audit · **Модель:** [текущая]»?
- [ ] **Summary Box** между шапкой и §0: N тезисов · Hit rate · Альфа · Ср. ценность · Дов. вес + 1 строка вердикта?
- [ ] §0 Reference set заполнен (10–20 фактов с URL)?
- [ ] §1 декомпозиция A/B/C построена для всех композитных тезисов?
- [ ] §2 таблица вердиктов содержит все тезисы × три шкалы × маркеры × ценность?
- [ ] **Цитаты иноязычных тезисов в §2 даны как «перевод» (en/de/zh: "оригинал ≤15 слов")** в КАЖДОЙ ячейке «Тезис»?
- [ ] §3 shape-of-error написан для всех тезисов с ценностью ≤−2?
- [ ] §3.M мета-аудит вторичного источника (если применимо)?
- [ ] §4 агрегаты: Hit rate, альфа-генерация, средняя ценность и др. посчитаны?
- [ ] §5 семь качественных осей с обоснованием?
- [ ] §6 ограничения честно перечислены?
- [ ] §7 итоговый вердикт + дифференцированный доверительный вес по темам?
- [ ] §8 предложение режимов Memory/Export/A+B (обязательный финальный блок)?
- [ ] **Весь отчёт на русском** (включая шапку, таблицы, обоснования)?
- [ ] **Структура — настоящий аудит, а не «досье в формате Часть A/B/C»** (anti-pattern Opus+DR)?
- [ ] При тезисах ≥10 — **создан docx в ТОМ ЖЕ ходе** (не «по запросу позже»; явное сообщение об исчерпании контекста — единственное допустимое исключение)?

### Для Light Audit
- [ ] Шапка отчёта содержит «**Тип анализа:** Light Audit · **Модель:** Sonnet»?
- [ ] Под шапкой — плашка о сокращениях?
- [ ] **Summary Box** между плашкой и §0?
- [ ] §0 Reference set (короткий, 5–7 фактов с URL)?
- [ ] §2 Light-таблица вердиктов: все тезисы × три шкалы × маркеры × ценность + inline колонки A/B/C для композитов?
- [ ] **Цитаты иноязычных тезисов даны как «перевод» (en/de/zh: "оригинал ≤15 слов")** в КАЖДОЙ ячейке «Тезис»?
- [ ] §4-light: 3 метрики (Hit rate, Альфа-генерация, Средняя ценность)?
- [ ] §5-light: 3 оси (Фактическая точность, Добавленная стоимость vs консенсус, Честность калибровки)?
- [ ] §6 ограничения (2–3 пункта)?
- [ ] §7 итоговый вердикт + дифференцированный доверительный вес — ПОЛНЫЙ?
- [ ] §8 предложение режимов A/B/A+B (обязательный финальный блок)?
- [ ] **Весь отчёт на русском**?

### Если хоть один раздел отсутствует
Явно зафиксируй: «Аудит частичный, не хватает раздела X. Причина: [исчерпан контекст / сбой инструмента / пользователь прервал]. Готов продолжить со следующего раздела при повторном запросе».

**Никогда не симулируй полный отчёт частичными данными.**

## 3. Fail-Fast при сбое инструмента

Если вызов инструмента вернул:
- пустой результат (пустой массив, "no results", "0 results found")
- task_id без последующих данных
- HTTP ошибку
- результат, который явно не относится к запросу

— остановись. **НЕ заполняй пробел знанием из training data.**

Сообщи пользователю одной из формулировок:

### Если сорвался Шаг 3 (сбор консенсуса)
> Не удалось получить snapshot консенсуса по [тезис X] на дату [дата прогноза]. Опции:
> (a) Дай альтернативный источник или ручной snapshot
> (b) Пропустим этот тезис со Шкалой 2 = ❓
> (c) Продолжим без верификации (НЕ рекомендую — методологически некорректно, выводы будут смещёнными)
>
> Что выбираешь?

### Если сорвался Шаг 4 (верификация факта)
> Не удалось проверить фактический результат по [тезис Y] на дату оценки. Опции:
> (a) Дай источник вручную
> (b) Тезис идёт со Шкалой 1 = ❓ и в агрегаты не входит
> (c) Прерываем аудит до восстановления данных
>
> Что выбираешь?

### Если в разговоре до активации скилла был запущен DR и он завершился без данных
DR внутри скилла не запускается (см. §4). Если пользователь предварительно запустил DR в отдельном сообщении и получил task_id без данных — это НЕ блокирует скилл. Аудит ведётся пошаговым web_search + web_fetch на Шагах 3 и 4 как обычно.

**Никогда не продолжай аудит молча после сбоя поиска.**

## 4. Использование Deep Research (launch_extended_search_task)

### Глобальный запрет

**DR ЗАПРЕЩЁН на любой модели внутри активной сессии скилла** (Opus, Sonnet, любая будущая). Эмпирическое основание: 2/2 наблюдаемых запусков скилла с DR внутри дали паттерн срыва E «Dossier instead of audit» — модель публиковала research-пакет как финал без второго прохода по Шагам 1–7.

Запрет действует независимо от того, активирован ли скилл с самого начала разговора или включился позже. Если в разговоре уже есть результат DR (DR был запущен ДО активации скилла — это допустимо), он используется как **сырьё для §0/§3/§4**, не как готовый артефакт для публикации.

### Двухэтапный workflow B (рекомендуемый)

Полезен на длинных горизонтах (≥10 лет), больших архивах (≥30 тезисов), восстановлении snapshot консенсуса далёких годов (1995, 2000, 2005, 2010), где богатство первоисточников критично.

**Этап 1 (БЕЗ скилла):** пользователь запрашивает DR-досье отдельным сообщением. Заголовок ответа — например, «Research-досье: [материал]». Структура «Часть A / Часть B / Часть C» здесь легитимна — это досье, не аудит.

**Этап 2 (СО скиллом):** пользователь следующим сообщением просит провести аудит, ссылаясь на досье выше. Скилл активируется, использует досье как input, проходит все 7 шагов и выдаёт §0–§8 с docx.

Между этапами пользователь явно подтверждает переход — это checkpoint на уровне workflow, а не на уровне модели, что надёжнее.

Почему двухэтапность работает (перенесено из SKILL.md 2026-08-12):
- На Этапе 1 нет претензии на аудит → нет соблазна выдать досье как финал.
- На Этапе 2 контекст начинается чистым: модель видит «у меня есть готовое сырьё,
  моя задача — построить аудит», а не «я только что прочитала кучу источников,
  надо что-то выдать».

### Если пользователь просит DR внутри активной сессии скилла

> На скилле retrospective-forecast-audit Deep Research отключён по методологическим причинам — на 2/2 наблюдаемых запусках DR внутри скилла давал срыв в формате «досье вместо аудита». Опции:
>
> (a) Запустить DR отдельным сообщением БЕЗ скилла («собери досье по [материал]»), затем вернуться сюда: «используя досье выше как input, проведи Full Audit». Это рекомендуемый workflow для длинных горизонтов и больших архивов.
>
> (b) Продолжить здесь без DR — пошаговый web_search + web_fetch на Шагах 3 и 4. Дольше по turn'ам, но без риска срыва.
>
> Что выбираешь?

Не запускай DR молча, даже если кажется, что «контекст уже большой и web_search будет долгим». Долгий web_search — это правильный режим работы скилла. DR — это режим pre-research до активации скилла.

### Что делать, если DR уже отработал ранее в разговоре (до активации скилла)

Это допустимая ситуация (пользователь следует workflow B). Действия:

1. Используй DR-результат как сырьё для §0 (Reference Set), §3 (snapshot консенсуса), §4 (верификация фактов).
2. Веди полный 7-шаговый аудит со всеми разделами §0–§8 и docx — не сокращай шаги «потому что много данных уже собрано».
3. В §6 «Методологические ограничения» отметь источник Reference Set: «Snapshot консенсуса собран Deep Research-сессией [дата] перед активацией скилла».
4. Pre-output checkpoint проходится в полном объёме перед публикацией.

## 5. Refusal-режим: текст для пользователя

Применяется на Sonnet при тезисах ≥16, или транскрипте ≥2 ч, или одновременно нескольких доменах с большим объёмом.

### Шаблон ответа

```
# Аудит не запускается на текущей модели

⚠️ На Sonnet качественный аудит этого материала не получится.

**Оценка объёма:**
- Тезисов ориентировочно: [N]
- Длина транскрипта: [M минут / часов]
- Доменов: [список]
- Композитных тезисов: [K]

**Опции на выбор:**

1. **Ограничить покрытие.** Выбираем вместе топ-15 приоритетных тезисов
   (по влиянию на портфель / по новизне / по контрарности — ты решаешь
   критерий). Делаю Light Audit только по ним. Остальные тезисы явно
   помечаются как «не разбирались в этой сессии».

2. **Переключить на Opus.** В селекторе модели наверху чата.
   Повторяешь запрос (можно той же фразой). Получаешь полный Full Audit
   без потерь. Это рекомендуемый вариант для материалов такого объёма.

Что выбираешь?
```

**Не пытайся сделать Light тихо при тезисах ≥16** — потеря покрытия слишком большая, пользователь должен явно решить.

## 6. Противодействие специфическим паттернам срыва Sonnet

Эти паттерны наблюдались на реальных запусках. Если замечаешь у себя — остановись.

### Паттерн A: «Reference Set published as final»
**Симптом:** написал §0 Reference set, далее переход к финальной формулировке без §2 таблицы вердиктов.
**Контрмера:** перед написанием любого ответа после §0 проверь — была ли §2 таблица в этом turn'е? Если нет — ты НЕ закончил аудит.

### Паттерн B: «Optimistic completion»
**Симптом:** длинная цепочка шагов (≥10), модель «срезает» промежуточные и переходит сразу к финалу.
**Контрмера:** при количестве тезисов ≥9 на Sonnet — Refusal или явная эскалация на Opus. Не пытайся «справиться» сокращением шагов.

### Паттерн C: «Phantom search»
**Симптом:** инструмент вернул пустой результат или ошибку, модель «вспомнила» данные из training data.
**Контрмера:** инвариант №7 (числа только с URL из текущей сессии) — операционное правило, не принцип. Перед каждым числом в таблице — проверка «есть ли URL из этой сессии?».

### Паттерн D: «Tool hallucination»
**Симптом:** модель вызывает инструмент, который не существует в текущем контексте (например, на Opus без Deep Research пытается вызвать launch_extended_search_task).
**Контрмера:** при первом сбое инструмента — НЕ ретрай в надежде, что в этот раз сработает. Переключайся на доступные инструменты и сообщай пользователю.

### Паттерн E: «Dossier instead of audit» (Opus + Deep Research)
**Симптом:** Deep Research вернул богатый research-пакет (snapshot консенсуса, фактические исходы, L-R sweep). Модель публикует его как финал в формате «Часть A — снимок консенсуса / Часть B — фактические исходы / Часть C — L-R / Часть D — track record / Часть E — методология». Структура читается как академический research paper, а не как аудит.

**Признаки** (любой из них = НЕ финальный аудит):
- Нет колонки «Ценность» (−3..+3) ни у одного тезиса
- Нет маркеров 🌍/👤/⚠️/⭐
- Нет агрегата Hit rate / Альфа-генерация / Средняя ценность
- Нет балльной оценки качественных осей (0–10)
- Вердикты словесные («подтверждено / опровергнуто»), а не числовые
- Структура «Часть A/B/C» вместо «§0/§1/§2/§3/§4/§5/§6/§7/§8»
- docx упомянут как «будет создан» или «сейчас сделаю», но по факту не создан

**Контрмера:** после возврата DR-результата явно скажи себе «это сырьё, не финал». Веди второй проход по Шагам 1–7 + §8 с DR-пакетом как input. Если контекст исчерпан — следуй стандартной процедуре «контекст исчерпан перед docx», но НЕ маскируй сырое досье под финал.

### Паттерн F: «English creep» (язык вывода)
**Симптом:** иноязычные цитаты в таблице остаются на оригинальном языке без перевода; обоснования местами сливаются в английский («Hit rate 41% reflects systematic miss…»); первый черновик целиком на английском.
**Контрмера:** перед выдачей любого черновика — проверка «весь ли отчёт на русском?». Цитаты — формат `«перевод» (en: "оригинал")`. Если первый черновик на английском — переписывай, не предлагай пользователю «сделать перевод по запросу». Это методологический брак, не приемлемое промежуточное состояние.

---

## 7. Когда читать этот файл

- Перед публикацией каждого финального ответа (pre-output checkpoint, §2)
- При первом сбое любого инструмента (fail-fast, §3)
- Перед использованием Deep Research (§4)
- При активации Refusal-режима (§5)
- Если замечаешь у себя один из паттернов срыва (§6)

Не читать впустую — но в этих случаях обязательно.
