# portfolio-scenario-stress

Мост между прогнозным слоем и портфелем. Показывает, **что произошло бы с текущими позициями** при реализации каждого сценария. Чистый аналитический слой: никаких «продать / купить» — только последствия.

**Дисклеймер по точности:** sensitivity matrix даёт ориентиры ±5–15 п.п., не precision. Это decision support, не Bloomberg-grade модель. Каждый выход сопровождается явным confidence note.

---

## Inputs / Outputs

**Inputs:**
- Portfolio snapshot `portfolio-{date}.json` ← `Portfolio/snapshots/` через transport-layer (или приложен пользователем)
- Forecast/scenario ← любой из: Shell-сценарии (scenario-builder), filtered consensus (FCA), stress-tested forecast (HST), macro-chain YAML, inline-описание в сообщении

**Outputs (черновик в `_drafts/` + выжимка в чат, Шаг 6):**
- `stress-{date}-{slug}.md` → `Claude-Memory/_drafts/` → save-to-library (Workflow E1.0) переносит в `Portfolio/stress/`
- `stress-{date}-{slug}.yaml` → то же самое (парный файл)
- в чат — выжимка: ΔP&L портфеля по горизонтам × сценариям, топ-5 позиций по вкладу, tail-флаги, строка «черновик: …»

**Upstream скиллы:** portfolio-data-loader (snapshot), scenario-builder / forecast-confidence-applier / hypothesis-stress-tester / macro-forecast-chain (forecast)
**Downstream скиллы:** portfolio-integrated-view (читает stress YAML), save-to-library
**Shared refs:** transport-layer, yaml-schemas, claude-memory-layout

## Модель и масштаб

**Sonnet — всегда.** Числа считает `scripts/stress_build.py` (Шаг 3.6): модель назначает чувствительности бумаг и пишет текст. Блок `per_position` руками не пишется — на крупном портфеле ручной блок выходит неполным и ломает `portfolio-integrated-view`. Нет Python в окружении — прогон невозможен: остановиться и сообщить.

## Глобальные принципы

1. **Никаких рекомендаций.** Если возникает соблазн написать «рекомендуется сократить» — это в `ru-portfolio-advisor`, не сюда. Скилл показывает картину, решение принимает пользователь.

2. **Explicit confidence.** Каждая оценка идёт с честной пометкой точности. Ячейки матрицы с `confidence: low` помечаются отдельно в выходе.

3. **Чувствительность — у каждой бумаги портфеля.** Позиция без секторального маппинга не исключается: чувствительность назначается по процедуре `references/idiosyncratic-tickers.md` с указанием метода в `factor_betas_method`; обосновать не получается — спросить владельца, а не угадывать. Бумага без чувствительности выпадает из расчёта вместе со своим весом, поэтому артефакт с непустым `unmapped_tickers` сборщик и валидатор сохранения отклоняют.

4. **Идемпотентность.** Повторный запуск на тех же входах → идентичный выход.

5. **Equal-weighted ≠ probability-weighted.** Сценарии Shell по методологии равновероятны (0.25 × 4). Это допущение метода, не реальная вероятность. В выходе явно указывать тип весов.

5a. **Никаких ⭐/«рабочий»/«базовый» маркеров под `modal_flag: no_modal`.** Если входной `scenarios` YAML содержит `modal_flag: no_modal` (Pure Shell D1), то в выводе пользователю **запрещено**:
   - Помечать любой сценарий ⭐ или «base / working / dominant».
   - Указывать «Sc-X используется для нелинейных факторов» (под D1 нелинейные факторы потребляются через `conditional_on_scenarios.by_scenario` — все 4 сценария параллельно, не один).
   - Заполнять `robustness.modal_scenario` чем-либо кроме `none`.
   Если у нелинейного фактора **нет** блока `by_scenario` (deprecated входы) — использовать fallback на медианный сценарий и пометить caveat `MISSING_BY_SCENARIO_FALLBACK_TO_MEDIAN` (severity: medium); это не «working scenario», а явная деградация.

6. **Не пересчитывать портфельные данные.** Скилл читает снапшот от portfolio-data-loader — не парсит xlsx заново.

7. **Не строить сценарии.** Скилл применяет сценарии от scenario-builder — не строит оси неопределённости.

8. **Combined factors — не всегда аддитивны.** Нефть −20% + слабый рубль (типичная корреляция) частично компенсируют друг друга для нефтяников. Детали — в `references/sector-sensitivities.md`.

Прочитать `references/transport-layer.md` (Synology mount). Если снапшот не указан явно — попытаться найти последний `portfolio-*.json` в `PORTFOLIO_SNAPSHOTS`.

### Шаг 1. Приём и валидация входов

**Обязательный вход:**
- Снапшот портфеля `portfolio-{date}.json` (от portfolio-data-loader)
  - Из сообщения пользователя (прикреплён JSON)
  - Или из `Portfolio/snapshots/` через активный транспорт (взять свежайший)

**Порядок обнаружения снапшота:**
1. `Glob("{MEMORY_ROOT}/Portfolio/snapshots/portfolio-*.json")` — единственный канонический паттерн; взять файл с наибольшей датой в имени.
2. Запрещено: искать в корне `Claude-Memory/`, в произвольных директориях, перебирать имена по частям.
3. Если Glob вернул ошибку (транспорт не подключён) → сначала `request_cowork_directory` → повторить Glob → только после этого диагностировать отсутствие файла.

**Прогнозный вход** — типы:

| Тип | Источник | Что содержит | Приоритет |
|-----|----------|-------------|-----------|
| **D** | macro-forecast-chain | macro-scenarios-*.yaml: by_scenario блоки, prob-weighted сценарии, caveats | Наивысший |
| **C** | hypothesis-stress-tester | Main case (P) + уязвимости с P | Высший |
| **B** | forecast-confidence-applier | Modal оценка + confidence band | Средний |
| **A** | scenario-builder | 4 Shell-сценария, равные веса 0.25 | Базовый |
| **Hybrid** | Комбинация | Тип C/B для одного фактора + A для остальных | По контексту |

**Совместимость с типами forecast YAML (events-yaml-spec.md §5):**
- Stress-test работает с **Type 2 conditional** (per-scenario значения) — это его основной случай.
- **Type 1 isolated forecast YAML** напрямую в stress-test НЕ участвуют. Если у фактора есть только Type 1 forecast — его Layer 1 marginal используется как **baseline** (одинаковое значение во всех 4 сценариях), без condition refinement. Это работа `macro-forecast-chain`, а не stress-test.
- **Forecasts без attribution** (ни Type 1, ни Type 2) — auto-discovery их не читает, в bundle не попадают.

При auto-discovery (`forecasts/*.yaml`) фильтруйте только Type 2 — Type 1 для stress нерелевантны (одно значение во всех сценариях не даёт стресс-сигнала).

#### Логика получения прогнозного входа

**Если пользователь передал хоть что-то** (сценарий, прогноз, stress-tested результат — в сообщении или в контексте разговора) → использовать только это. Claude-Memory не просматривается вообще. Если передан только сценарий — прогнозы из памяти не добавляются и наоборот.

**Если ничего не передано** → авто-discovery из `Claude-Memory/`:

1. Прочитать `references/transport-layer.md`, выбрать транспорт
2. **Сначала проверить** `Claude-Memory/macro-chain/macro-scenarios-*.yaml` (Тип D):
   - Если найден → это приоритетный вход. Показать дату и coverage_score, спросить «использовать?»
3. **Если нет Типа D** → Glob `scenarios/*.yaml` и `forecasts/*.yaml`
3. **Фильтрация по факторам** (не по теме):
   - Скилл работает с финансовыми факторами: brent, ставка ЦБ, usdrub, cnyrub, санкции, геополитика
   - Из найденных файлов брать только те, что выражены непосредственно через эти факторы
   - Пример: есть прогноз «США-Иран» и прогноз «нефть при эскалации» — брать второй; первый — транзитивная связь, которая уже снята в нефтяном прогнозе
   - Правило: **наиболее проксимальный к портфельным факторам файл имеет приоритет**
4. **Если найдены и прогноз, и сценарий** по схожим факторам:
   - Предпочесть **прогноз (Тип C > B)** — он даёт реальные вероятности, Expected P&L считается честно
   - Сценарии (Тип A) брать только если прогноз покрывает лишь один фактор, а сценарии — несколько одновременно → тогда **гибрид**: прогноз для своего фактора, сценарии для остальных
5. Показать пользователю, что найдено и что будет использовано:
   > «Нашёл в Claude-Memory: (a) stress-tested прогноз ставки ЦБ от 2026-05-01, (b) Shell-сценарии нефть/рубль от 2026-04-15. Использую (a) как основной, (b) как гибридное дополнение для нефтяного фактора. Продолжить?»
6. Дождаться подтверждения, затем перейти к Шагу 2

**Если авто-discovery ничего не нашло** → запросить у пользователя:
> «Не нашёл подходящих сценариев или прогнозов в Claude-Memory. Передай прогнозный вход: (a) сценарии от scenario-builder, (b) filtered consensus от forecast-confidence-applier, (c) stress-tested forecast от hypothesis-stress-tester, или (d) ключевые факторы вручную (Brent ±%, ставка ±б.п., USD/RUB ±%)»

**Валидация снапшота:**
- Проверить `data_quality_flags` на `severity: error` — если есть, предупредить перед расчётом
- Собрать список позиций из `holdings` (только `is_blocked: false`)
- Для каждой позиции проверить наличие секторального маппинга (см. `references/sector-sensitivities.md` таблицу тикеров)
- Позиции без маппинга → список `UNMAPPED_POSITIONS`, флаг в выходе

**Pre-flight: dual-shock check**

Проверить прогнозный вход на двойной счёт через pass-through:
- Если в `by_scenario` присутствуют одновременно `shock_brent` И `shock_inflation_via_brent`
  → выдать ошибку: «⚠️ Двойной счёт: brent→inflation pass-through уже встроен
  в conditional CPI. Удали один из шоков перед расчётом».
- Правило: никогда не добавлять первичный шок и его производный через pass-through
  в одном bundle.

### Шаг 2. Нормализация входа

Прочитать `references/input-adapters.md` (раздел «Канонические имена факторов» — критично, скрипт молча игнорирует не-canonical имена).

Конвертировать все прогнозные входы в единый internal format с **canonical** именами факторов (`brent`, `cbr_rate`, `usdrub`, `cnyrub`, `sanctions`, `geopol`, `xauusd` — точно как `CANONICAL_FACTORS` в `scripts/input_contract.py`):

```json
[
  {
    "label": "Название сценария/кейса",
    "probability": 0.25,
    "factors": {
      "brent": -20.0,
      "cbr_rate": 200,
      "usdrub": 15.0,
      "cnyrub": 12.0,
      "sanctions": {"h6": 0.4, "h12": 0.7, "h24": 0.7},
      "geopol": {"h6": 0.5, "h12": 0.8, "h24": 0.8}
    },
    "confidence": "medium",
    "source": "scenario-builder",
    "weight_type": "equal"
  }
]
```

Единицы: `brent/usdrub/cnyrub/xauusd` — % изменение; `cbr_rate` — п.п. (>0 рост ставки); `sanctions/geopol` — интенсивность `[-1..+1]` (`+1` = ужесточение, `−1` = смягчение, `0` = статус-кво). При чтении `macro-input-{date}.yaml` — переименовать поля по mapping-таблице из `references/input-adapters.md` (internal `_pct_change`/`_bps_change`/`_escalation` → canonical).

**Политические дилы задавать путём по горизонтам** (`{h6: …, h12: …, h24: …}` или `{level_l1_<год>: …, unit: intensity}`), а не одним числом: скаляр означает «разрядка через полгода = разрядка через два года» и почти всегда неверен. `compute_horizon_factors.py` на скаляр выдаст warning (P0-2).

`weight_type`: `"equal"` для Тип A, `"probability"` для Типов B/C.

Для гибридного входа: фактор из более специфического источника (Тип C) имеет приоритет над общим (Тип A).

### Шаг 3. Чувствительности по позициям

Шаг нужен для бумаг, которых нет в прошлом стрессе, и для бумаг на пересмотр; остальным чувствительности переносит скрипт (Шаг 3.6). Для таких бумаг прочитать:
- `references/sector-sensitivities.md` — всегда
- `references/bonds-sensitivity.md` — если в портфеле есть `asset_type: "bond"`
- `references/fund-decomposition.md` — если есть TGLD, SBMX, РЕНТАЛ ПРО или другие фонды

**Для каждой позиции** назначить чувствительность β к каждому из 7 факторов:

1. Определить сектор через таблицу маппинга в `sector-sensitivities.md`
2. Взять β сектора по каждому фактору из sensitivity matrix
3. Учесть нелинейности (нефть + рубль для нефтяников, ставка + резервы для банков)

**Для облигаций (из `bonds-sensitivity.md`):**
- `Δцена% ≈ −duration_years × rate_bps_change / 100`
- FX-облигации: добавить валютную переоценку
- Корпоративный кредитный спред: через rating tier (упрощённо)

**Для фондов (из `fund-decomposition.md`):**
- Разложить на underlying перед применением матрицы

**Результат этого шага:** чувствительности по бумагам — вход `betas-priors.json` (Шаг 3.6). Перемножение на факторы сценариев и ΔP&L в рублях считает скрипт; матрицу `position × scenario` руками не считать.

### Шаг 3.5. Idiosyncratic-reasoning pass

Макро-стресс-тест отвечает на вопрос «как изменится цена при движении нефти,
ставки, курса и т.д.». Для части позиций это полная картина — облигации,
индексные фонды, сырьевые компании первого ряда. Для других позиций главный
driver доходности лежит вне макрофакторов: дивидендная политика, корпоративные
действия (M&A, buyback, выпуск/гашение), регуляторные решения по конкретной
индустрии или эмитенту. Стресс-тест без учёта этого даёт недооцененную оценку
неопределённости — формально число посчитано, но половина риска не видна.

Этот шаг — короткое рассуждение скилла по каждой позиции с заметным вкладом
в портфель (≥1% по стоимости, или входит в Top-5 уязвимых из Шага 4). Цель —
не назвать конкретные тикеры с готовыми ответами, а пройтись по позициям и
ответить на три вопроса:

1. **Какая доля cash flow / valuation определяется макро?** Высокая (нефтяники,
   облигации, банки в части net interest income) / Средняя (потребсектор,
   электроэнергетика — частично макро через инфляцию, частично регуляторика) /
   Низкая (девелопмент с льготной ипотекой — определяется регуляторным
   решением; growth-имена — sentiment-driven; компании с высокой долей дивидендов
   — driven дивполитикой акционеров).

2. **Какие идиосинкратические факторы НЕ попали в матрицу?** Типовые категории:
   - Дивидендная политика (особенно для позиций, где дивдоходность >5% годовых)
   - Регуляторные решения по индустрии (банки — нормативы ЦБ, девелопмент —
     ипотечные программы, нефтегаз — НДПИ/демпфер, IT — секторальные льготы)
   - Корпоративные действия (M&A, выкупы, доп.эмиссии, smartlab-style
     разделения)
   - Специфические санкционные риски (отдельные эмитенты под угрозой блокирующих
     санкций, не покрытых общим уровнем интенсивности `sanctions`)
   - ESG / sustainability рейтинги (для позиций с зарубежным фондированием)

3. **Насколько идиосинкратика может перекрыть макро-результат?** Качественная
   оценка по шкале:
   - `MACRO_DOMINATES` — идиосинкратика на ±10–20% максимум, макро задаёт основной диапазон.
   - `MIXED` — идиосинкратика и макро сопоставимы; стресс-тест даёт половину картины.
   - `IDIOSYNCRATIC_DOMINATES` — макро вторично, основной риск/возврат вне матрицы.

Реализация — без отдельного файла с тикерами и без захардкоженных эмитентов.
Скилл рассуждает по типу позиции (sector + asset_type из снапшота) и отвечает
на три вопроса по типовому профилю. Если у пользователя есть конкретный override
(например, override на конкретный эмитент), он передаётся через `corp-events` блок
в снапшоте — но базовая логика работает по sector-level паттернам.

**Типовые шаблоны рассуждения (sector-level, БЕЗ конкретных имён):**

| Sector / Asset type | Macro share | Идиосинкратика — что не в матрице | Verdict |
|---------------------|-------------|-----------------------------------|---------|
| oil_gas (крупные) | High | Дивполитика, НДПИ/демпфер, отдельные санкции | MIXED |
| oil_gas (средние) | High | + buyback, + специфические санкционные риски | MIXED |
| banks (крупные) | High | Дивидендная политика, нормативы ЦБ, M&A | MIXED |
| banks (нишевые) | Medium | + регуляторика по сегменту, + клиентская концентрация | MIXED |
| metals / mining | High | Дивполитика (квартальные/полугодовые), переработка, экспортные пошлины | MIXED |
| real_estate (девелопмент) | Medium | Льготная ипотека, региональные программы, банкротства | IDIOSYNCRATIC_DOMINATES при изменении ипотечных программ |
| consumer | Medium | Регуляторика цен, конкуренция, M&A | MIXED |

| bonds_fx | High | + санкции на конкретного эмитента, FX-risk на купоны | MIXED |
| funds (gold) | High | Структурные риски фонда, replication mechanism | MACRO_DOMINATES |
| funds (broad equity) | High | Состав корзины (если меняется), tracking error | MACRO_DOMINATES |
| funds (real-estate-style) | Medium | Качество underlying assets, структурные риски ЗПИФ | MIXED |

Шаблоны — стартовая точка, а не закрытый список. Если позиция не попадает ни
в одну категорию, рассуждать на основе того, что известно из sector + asset_type +
доли в портфеле. Если совсем нет данных — пометить `IDIOSYNCRATIC_UNKNOWN` и
вынести в отдельную секцию вывода.

Этот шаг текстовый: PSS не пытается посчитать идиосинкратический ΔP&L
(для этого нужны данные, которых в макро-матрице нет). Цель — проявить
ограничения стресс-теста и дать пользователю явный список «слепых пятен»
для отдельной оценки.

### Шаг 3.6. Числа одной командой — stress_build.py

Блок `per_position` и все портфельные числа считает `scripts/stress_build.py`; модель готовит ему чувствительности (`betas-priors.json`) и факторы сценариев. Скрипт вызывает тот же расчёт, которым числа стресса пересчитывает сайт, поэтому файл скилла и пересчёт сайта на одном снапшоте совпадают. **Все файлы `scripts/` обязаны лежать рядом.**

**Включаются в per_position:**
- Все unblocked stocks/bonds/funds с `value_rub > 0`
- Money-market funds (TPAY, TMON, LQDT, SBMM): включаются автоматически с `factor_betas: {sanctions: 0, geopol: 0, cbr_rate: 0, usdrub: 0, cnyrub: 0, brent: 0, xauusd: 0}`, `factor_betas_method: "money-market — нечувствителен к рассматриваемым факторам"`, нулевые дельты во всех горизонтах `by_horizon`

**Schema v2 (Phase 4):** `factor_betas` — **плоские** (месячные беты SS-1, горизонт-независимы, D4-2). Всё горизонт-зависимое — в блоке `by_horizon.{hNN}: {delta_pct_by_scenario, expected_pct_pweighted, tail_var_pct, tail_var_scenario_id}`. Горизонты берутся из `factors_by_horizon` сценариев (v2) или из `--horizons` (v1-вход → обёртка `by_horizon.{h20}`).

**Исключаются:**
- RUB cash на брокерском счёте
- Blocked positions (FXIT, FXUS, frozen US stocks)

**Scenario IDs** в `per_position` совпадают с ключами блока `scenarios:` (абстрактные `A`/`B`/`C`/`D` или `A_<label>` если задан в SSOT scenarios YAML). Скилл не привязан к конкретной семантике сценариев — скрипт читает ID-ы напрямую из переданного scenarios-фрагмента.

```json
{
  "SBER": {
    "factor_betas": {
      "sanctions": -35, "geopol": -20, "cbr_rate": 0.30,
      "usdrub": -0.10, "cnyrub": 0, "brent": 0.05, "xauusd": 0
    },
    "sanctions_position": 0.9,
    "factor_betas_method": "sector prior from sector-sensitivities.md (banks, elevated-rate context)",

    "asset_type": "stock"
  },
  "RU000A107RH8": {
    "factor_betas": {
      "sanctions": -0.30, "geopol": -0.15, "cbr_rate": 0,
      "usdrub": 0.95, "cnyrub": 0, "brent": 0, "xauusd": 0
    },
    "factor_betas_method": "USD-замещайка Tier 2, FX-pass-through",
    "factor_betas_r2": null,
    "asset_type": "bond_fx"
  }
}
```

**Важно:**
- **Позиция на санкционной шкале (P1-3):** `sanctions_position ∈ [0,1]` — где бумага стоит СЕГОДНЯ (0 — санкциями не тронута, 1 — максимально заблокирована). Движение фактора `sanctions` клампится доступным ходом: `effective = clamp(position + intensity, 0, 1) − position`. Отсюда берётся асимметрия «ужесточение слабее, снятие сильнее» — из позиции, а не из двух бет. Поле опционально (нет → полная интенсивность, прежнее поведение), но скрипт предупреждает по бумагам с |β_sanctions| ≥ 20, а значение вне [0,1] или нечисловое останавливает расчёт. `geopol` не клампится. Шкала позиций и класс экспозиции — `references/sector-sensitivities.md` → «Позиция на санкционной шкале».
- **У облигаций политическая бета законно мала** и в примере выше это не опечатка: `β = −duration × Δspread_бп / 100` (Tier 2, дюрация 3 → `−3 × 10/100 = −0.30`). Акции считаются десятками п.п., облигации — долями, и обе записи в ОДНИХ единицах. Бету облигации на 100 не умножать. Таблица Δspread — `references/bonds-sensitivity.md` §4.
- **Контракт единиц (P0-1):** β — п.п. цены на ОДНУ единицу фактора. Для `sanctions`/`geopol` единица — интенсивность 1.0, поэтому бета банков = **−35**, а не −0.35; у облигаций она законно мала (`−duration × Δspread_бп / 100`). Долевая запись отличается ×100 и молча зануляет политический канал — скрипт откажется считать (гард шкалы, Шаг 3.6.4). Детали и калибровка — `references/sector-sensitivities.md` → «Контракт единиц».
- **`asset_type` проставлять всегда, и точнее, чем в снапшоте.** По нему гард решает, применим ли нижний порог шкалы. В снапшоте класс грубый (`stock` / `bond` / `fund`), а под `fund` лежат и золотой, и ОБЛИГАЦИОННЫЕ фонды — у последних беты законно дробные. Пиши в priors `fund_equity` / `bond_fund` / `fund_gold`: значение из priors приоритетнее снапшота. Голый `fund` → проверка по бумаге пропускается с warning.
- Все 7 канонических факторов прописываются **явно** (отсутствующий → 0). См. `output-template.md`.
- `factor_betas_method` использовать канонические шаблоны из `bonds-sensitivity.md` для облигаций.
- `factor_betas_r2: null` в priors-only режиме (Phase 4.1). В Phase 4.2 сюда придёт реальный R² от MOEX-регрессии.
- ⚠️ **Беты из артефактов ДО 2026-08-03 переиспользовать нельзя без проверки шкалы.** Прогоны `stress-2026-07-15` и `-07-23` записали политические беты в долевой шкале (SBER −0.35 вместо −35) — канал в них занулён, порядок сценариев перевёрнут. Берёшь беты из старого артефакта — сверь политические с `sector-sensitivities.md` и домножь на 100, если они в долях (скрипт всё равно не пропустит).
- **Перенос из прошлого стресса** делает скрипт (`--priors-from`): пометку `reused from <файл>` в `factor_betas_method` он ставит сам. В `caveats` добавить запись `severity: LOW` «factor_betas перенесены из прошлого прогона без пересмотра». Пересматриваешь бумагу — дай её запись в `betas-priors.json` целиком, по `sector-sensitivities.md`.

#### Веса сценариев: по умолчанию 0.25, опционально — по горизонтам

Pure Shell D1: если ничего не задано, у всех четырёх `p: 0.25`, `modal_flag: no_modal`.
Равные веса — это «метод не претендует знать вероятности геополитики», а не «все
четыре равновероятны». **Основной результат — четыре колонки сценариев**, среднее
по ним сопровождается явной пометкой, что это арифметическое среднее, а не ожидание.

Убеждение о том, какой мир реализуется, зависит от срока: на полгода вперёд может
быть модальным один сценарий, на два года — другой. Для этого есть блок весов по
горизонтам:

```yaml
scenarios:
  A: {p: 0.25, p_by_horizon: {h6: 0.45, h12: 0.35, h24: 0.20}, ...}
  D: {p: 0.25, p_by_horizon: {h6: 0.05, h12: 0.15, h24: 0.30}, ...}
```

Сами горизонтные веса (PSS-9, 2026-08-05) доходят до **всех** потребителей
total-return: ценовой слой, bond carry (облигации, money-market, кэш),
`portfolio-integrated-view` (carry, идио-слой, `total_return_by_horizon`, Monte
Carlo), вьюер и подписи ячеек `joint_tail` в coherence-audit. Ноги считаются на
одном убеждении.

Скаляр `p` рядом **обязателен** и после этого: по нему считается диагностика
нормировки (сумма весов и её severity), и он же — деградация на горизонтах,
которых в блоке нет. Скрипт откажется считать без него. Блок, заданный части
сценариев, тоже останавливает расчёт. Не поддерживает горизонтные веса только
`macro-forecast-chain --mode RECALIBRATE` — он на таких матрицах отказывается
работать явно (MFC-5).

Полярность матрицы должна быть объявлена в `matrix.polarity` — умолчания нет.

Задавать его руками по четырём сценариям трудно, поэтому веса выводятся из
убеждений **по осям** (два вопроса на горизонт вместо четырёх) —
`scripts/scenario_axis_weights.py`, функция `weights_by_horizon`. Источник
осевых убеждений — матрица сценариев:
`downstream_sensitivity_hints.axes_meta.<ось>.quantitative_anchor.
modal_expected_value` (скаляр, уже есть в живых матрицах) и опциональное
`modal_expected_value_by_horizon: {h6: …, h12: …, h24: …}`.

⚠️ **Полярность.** Маппинг квадрантов на id — канон §17 F4: `stress_pole: A`
(обе оси в HIGH), `detente_pole: D` (обе в LOW). Перепутанная полярность не
падает, а зеркалит веса — вес войны уезжает на разрядку. До 2026-08-04 такая
ошибка жила в `joint_from_axes`.

Блок необязателен. Если он есть, он должен быть задан **у всех** сценариев и
суммироваться в 1 на **каждом** горизонте — иначе `compute_per_position.py`
откажется считать. Частично заполненный блок смешал бы веса разных убеждений.

**3.6.3.** Сохранить в рабочую папку `betas-priors.json`. Факторы сценариев на сроки стресса руками не считаются:
- **числовые** (brent, usdrub, cnyrub, cbr_rate, xauusd) скрипт берёт из `--macro-scenarios`: уровни по датам сетки интерполирует линейно по дням на конец каждого срока; срок позже последней точки сетки — уровень последней точки, срок помечается `extrapolated`, CI расширяется. Покрытие прогнозом (`horizon_coverage`) и оговорку о сроках за пределами прогноза (`HORIZON_EXTRAPOLATED`) пишет скрипт; свою запись об экстраполяции в `caveats` не клади — скрипт её отбросит. Сроки задаёт стресс: приписка в файле макро-сценариев о том, на каких датах считать, сроки стресса не меняет;
- **политические** (sanctions, geopol) — ровно один источник: `--political-from {прошлый stress-*.yaml}` переносит пути как есть (матрица сценариев не пересматривалась) либо `--political-paths /tmp/political.json` — `{X: {sanctions: {h6: …, h12: …, h24: …}, geopol: {…}}}`, когда пути пересмотрены; значения — интенсивность в [-1, 1].

Вход не из макро-цепочки (inline-сценарий, консенсус без файла макро-сценариев) — вместо этого `--horizon-factors-input /tmp/horizon-factors-input.json`: `{scenarios: {X: {factors: {f: {level_l1_<год>, unit} | {h6: …} | число}}}}`.

**3.6.4.** Посчитать числа — режим «только числа», без `--fill`:

```bash
python3 scripts/stress_build.py \
  --snapshot {portfolio-{date}.json} \
  --scenarios {scenarios/{slug}-{date}.yaml} \
  --macro-scenarios {macro-chain/macro-scenarios-{date}.yaml} \
  --priors-from {последний stress-*.yaml} \
  --political-from {последний stress-*.yaml} \
  --horizons-from {последний stress-*.yaml} \
  --library-root {LOCAL_LIBRARY_ROOT} \
  --weight-type probability --include-ev \
  --slug {scenario_slug} \
  --tables /tmp/stress-tables.md \
  --output /tmp/stress-numbers.yaml
```

- Запускать из папки скилла; пути к файлам библиотеки — полные.
- `--tables` — готовые таблицы отчёта (итоги по срокам, позиция × сценарий, секторы, Top-5, концентрация, метрики, покрытие сроков, купонный слой, вклад факторов с пробами «рубль = 0» и «золото = 0»), собранные из того же расчёта.
- `--scenarios` — SSOT-матрица со `scenario_triggers`; `--macro-scenarios` — при входе из macro-forecast-chain всегда.
- `--priors /tmp/betas-priors.json` — добавить, только если есть новые или пересмотренные бумаги (3.6.2).
- `--political-paths /tmp/political.json` вместо `--political-from` — когда политические пути пересмотрены (3.6.3).
- Веса матрицы вероятностные (Тип B/C/D) — `--weight-type probability --include-ev`; равные веса Pure Shell — `--weight-type equal` без `--include-ev`: ожидание тогда не публикуется.
- Уточнения купонного слоя — `--carry-overrides`, `--sanctions-haircut`, `--mm-spread-pp`, `--fx-reinvest-rate-pct` (Шаг 3.7).

Скрипт печатает сводку (таблица «сценарий × срок» по обеим базам, ожидание, худший сценарий основного срока, топ-5 бумаг по вкладу в его убыток, предупреждения) и пишет рабочий файл с пометкой `numbers_only: true`. Из него берутся числа для текста отчёта; это не артефакт, в `_drafts/` его не класть.

**Сроки.** Цифры вида «6-12-24» в запросе — метки сроков (`h6`/`h12`/`h24`), а не просьба пересчитать даты. Сроки — из файла сайта `scenarios/horizons.json` (скрипт читает его сам при `--library-root`; другие сроки в `--horizons` / `--anchor-dates` он отвергает). Файла нет — `--horizons-from` на последний `stress-*.yaml` в `Portfolio/stress/` (та же логика поиска, что для снапшота на Шаге 0): метки, даты и основной срок переносятся как есть, а при остатке до ближайшего срока меньше трёх месяцев скрипт сдвигает все сроки на шесть месяцев и печатает предупреждение — вынести его в выжимку. Сообщить в выводе, откуда взяты сроки, вопросом не задерживать. Скилл не изобретает даты и файл сроков не пишет (его меняет только сайт: «Стресс» → «Настройки стресса»). Сроки отличаются от прошлого стресса — санкционный и геополитический пути задать заново под новые сроки, а не переносить через `--political-from`. Файла сроков нет, а владелец сам назвал даты — `--horizons 6,12,24` (от сегодня) или `--anchor-dates …` с `--primary-horizon`. Нет ни файла сроков, ни прошлого стресса, ни дат в запросе — спросить.

**Веса с сайта.** С `--library-root` скрипт берёт веса, заданные владельцем на странице «Стресс» (`scenarios/stress-weights-<матрица>.json`), если они заданы на те же сроки. Весов на сайте нет или они заданы на другие сроки — считает на весах матрицы (они заданы на даты матрицы, а не на сроки стресса) и печатает предупреждение: передать его владельцу в выжимке и попросить задать веса на странице «Стресс» на новые сроки — сайт пересчитает стресс сам, скилл повторно запускать не нужно.

**Отказ (код 1) — исправить вход и перезапустить:**
- перечень строк про файл макро-сценариев (нет фактора, сценария, числового `value` по датам, спота) — файл макро-цепочки не годится для расчёта: числа руками не подставлять, вернуть файл на пересборку `macro-forecast-chain` с этим перечнем;
- `у бумаг снапшота нет чувствительностей` — назначить β перечисленным бумагам в `betas-priors.json`. Чувствительность обязана быть у каждой бумаги: бумага без неё выпадает из всех портфельных чисел;
- `ШКАЛА ПОЛИТИЧЕСКИХ БЕТ` — гард контракта единиц: перечисленные беты записаны в долевой шкале, домножить ИХ (не все подряд) на 100. Гард называет конкретные записи и к облигациям нижний порог не применяет;
- остальные ошибки контракта priors (форма, нечисловые беты, `sanctions_position`) предъявляются одним списком за прогон.

Значения `sanctions_position` скрипт подставляет из `references/sanctions-positions.yaml` (SSOT) сам, какое бы значение ни пришло на вход; расхождение печатается предупреждением. Пересмотр значений — `/sanctions-positions` по рубрике.

Скрипт детерминистически на **каждом горизонте** считает: `delta_pct = sum(beta[f] * factors_by_horizon[hNN][f])`, CI через `ci_from_delta(...)` (×`ci_inflation` при экстраполяции года FCA), `expected_pct_pweighted` через probability-weighting, `tail_var_pct` через min — и кладёт в `by_horizon.{hNN}`. `macro_blindspot` (через r2/beta/idiosyncratic-list) — плоский, горизонт-независим.

> ⚠ **Флаг ≠ таблица `macro_blindspots`.** Скрипт ставит булев флаг механически и узко
> (низкий R², все |β| < 0.1, список идиосинкратических тикеров); таблицу Шага 3.5 пишет
> модель по вердиктам и она шире (прогон 08-15: 4 флага против 27 строк таблицы,
> ≈39,5% портфеля). Синхронизировать их НЕ надо — это разные вопросы («беты ненадёжны»
> против «какую долю дисперсии описывает макро»). Но вердикт в таблице заполнять
> обязательно: `portfolio-integrated-view` с 2026-08-16 ставит метку 👁 по обоим
> источникам сразу, и строка без вердикта из разметки выпадает.

#### Maturity guard (автоматически внутри скрипта)

Облигации с погашением/офертой ДО конца срока получают `price_delta = 0` на
этом сроке (`price_delta_zeroed` + `t_live_months` в срезе `by_horizon`) —
их лайфцикл (купоны + par + реинвест) считает купонный слой (Шаг 3.7) в той же команде.

### Шаг 3.7. Купонный слой (bond carry) — в той же команде

Купоны (факт. расписание, НЕ YTM×t), pull-to-par и реинвест тела по сценарной
траектории КС + FX на купоны/тело + MM/кэш `stress_build.py` считает сам и кладёт
блоком `bond_carry` (спека — `yaml-schemas.md` §11.2). От модели — только уточнения
по бумагам: `--carry-overrides` (`{тикер: {bond_type: floater, ytm_pct: …}}` из
weekly-bonds-review) и, при необходимости, параметры слоя (`--sanctions-haircut`,
`--mm-spread-pp`, `--fx-reinvest-rate-pct`). Distressed-бумаги (`credit_review_required`; порог ytm не применяется, если оферта или погашение ближе 30 дней — `--distressed-ytm-min-days`, метка `ytm_threshold_skipped_near_event`)
и HIGH-caveats блока поднять в общий `caveats` артефакта. Guard двойного счёта:
валидатор блокирует `matures_within` × живой `price_delta`.

#### Контроль качества

- **Покрытие:** `Σ weight_pct(per_position) ≈ 100% (±2%)` — веса бумаг и секторов считаются от позиций без кэша; `cash_rub_pct` и `blocked_pct` — отдельные поля от портфеля с кэшем, в эту сумму не входят. Если расхождение >2% — найти пропущенные тикеры в priors и перезапустить скрипт. Допуск ±2% — сеть от округлений, потерю одной ноги расщеплённой позиции он не ловит: это работа `coverage_pct` скрипта, который считает по РЕАЛЬНО опубликованной стоимости.
- **Бумага на нескольких счетах** (main + iis_3) — одна запись: скрипт схлопывает ноги, `weight_pct` считается от ПОЛНОЙ стоимости позиции, `on_iis: true` если хотя бы одна нога на ИИС-3. Руками не разделять. Разные бумаги под одним тикером (омонимы) не схлопываются — меньшая уходит в `unmapped_tickers` с причиной `ticker collision`.
- **Скрипт сам логирует warnings** — внимательно прочитать (`coverage_pct`, пропущенные тикеры).
- **Blindspot-проверка:** для каждого `macro_blindspot: true` проверить, что reason разумный (не ложный positive из-за случайного `|beta| < 0.1`).

### Шаг 4. Агрегация и риск-метрики

Портфельные P&L-числа (1–3 ниже) и списки п. 5 считает `stress_build.py`
из `per_position` + `bond_carry` — не вручную. Контракт баз (обе базы, по
каждому горизонту) — `references/yaml-schemas.md` §11.2a; полная
спека — `docs/investment/task-stress-basis-contract.md`.

**Секторальная агрегация:** `sector_breakdown_pct` скрипт собирает из `per_position`
(sum ΔRUB по позициям сектора; секторы и подписи — закрытый список `references/sector-groups.yaml`) — всегда **ценовая база (price)**, т.к.
`per_position_basis` — инвариант. Отмечать это явно: `sector_breakdown_basis: price`.

**Портфельные метрики (`portfolio_aggregates`,
`scenarios.<X>.portfolio_level_by_horizon`):**

1. **Total P&L per scenario, обе базы** — `price_delta_rub` (Layer 1, сумма ΔRUB
   по позициям) и `total_return_rub` (Layer 1 + Layer 2 carry) — оба явно, не
   один скаляр под общим именем.

2. **Expected P&L, обе базы** — только если входные данные содержат probability
   weights (Тип B/C/D) И передан флаг `--include-ev`:
   `E[P&L] = sum(p_by_horizon[h][X] × pl_rub[X][h])` на каждой базе отдельно.
   Для Типа A (equal-weighted) — `null` в `portfolio_aggregates.*` (см. D2:
   EV сознательно не публикуется для Pure Shell).

3. **P&L distribution, обе базы:** min / max / argmin / argmax по сценариям на
   каждом горизонте — `portfolio_aggregates.{price,total_return}.pl_range_rub_by_horizon`.

4. **Tail risk (только Тип C):**
   - Worst-case probability-weighted P&L
   - Какой vulnerability scenario даёт наибольший убыток

5. **Risk concentration** (из `per_position` — всегда price, п. 5 ниже отдельно не двоится по базе):
   - Top-5 позиций по абсолютному убытку в worst scenario
   - Top-5 позиций по абсолютной прибыли в best scenario
   - Concentration ratio: доля портфеля (по стоимости), движущаяся в одном направлении при доминирующем факторе; фактор называет модель (`concentration.dominant_factor` в `fill.yaml`), долю считает скрипт

6. **Hedge candidates:**
   - Позиции с противоположной чувствительностью к доминирующему фактору портфеля
   - Примеры: при нефтяном риске — розница, банки, телеком (слабая или отрицательная корреляция с нефтью)

7. **Vulnerability mapping (только Тип C):**
   - Какие позиции страдают специфически от vulnerability scenarios, а не от main case
   - Это самые ценные данные для tail risk hedging

### Шаг 5. Генерация выхода

Прочитать `references/output-template.md`. Блоки ниже — полный отчёт, тело файла 1 черновика (Шаг 6); в чат идёт выжимка («Черновик и выжимка в чат»).

**Таблицы чисел — из файла `--tables` итогового запуска (Шаг 6.0), вставлять как есть.** Числа руками не переписывать, не округлять заново и не пересчитывать: расхождение текста отчёта с YAML — дефект. В прозе ссылаться на числа из этих таблиц. Строка «Итого» таблицы позиций может отличаться от портфельного итога на единицы рублей — это округление по бумагам.

**Обязательные блоки выхода:**

1. **TL;DR (3–5 строк):** главный риск, главная возможность, что скрыто в структуре

2. **Confidence note** — в начале, до таблиц:
   > `Оценки ориентировочные (±5–15 п.п. на позицию). Sensitivity matrix — исторические средние, а не precision tool. Факторы с low confidence помечены ⚠️.`
   > `Тип весов: [equal-weighted / probability-weighted]. [При equal-weighted добавить: «Не интерпретировать как реальные вероятности»]`

3. **Таблица позиция × сценарий → ΔP&L** (RUB и %)
   — Отсортировать по абсолютному убытку в worst scenario
   — UNMAPPED позиции — отдельной строкой внизу с пометкой

4. **Секторальная сводка** — по секторам × сценарий

5. **Top-5 уязвимых позиций** — в worst scenario

6. **Top-5 устойчивых / выигрывающих позиций** — в best scenario

7. **Hedge кандидаты** (если есть)

8. **Vulnerability map** (только Тип C) — позиции, чувствительные к tail scenarios

9. **Метрики портфеля:** `portfolio_aggregates.{price,total_return}` — P&L range по горизонту, Expected P&L (только если вход probability-weighted И флаг `--include-ev`, иначе `null`), Concentration ratio (из `per_position`, price)

10.1. **Robustness verdict** (обязательная секция, обе базы — §11.2a, заполняет `compute_portfolio_aggregates.py`):

```yaml
robustness:
  price:
    basis: price
    by_horizon:
      h12:
        positive_or_neutral_scenarios: <int из 4>
        worst_case: { id: "<scenario_id>", pl_pct: <float> }
        best_case: { id: "<scenario_id>", pl_pct: <float> }
        spread_pct: <best_pl_pct - worst_pl_pct>

  total_return:
    basis: total_return
    by_horizon: { ... }   # та же форма, числа с учётом bond_carry
  hedge_target: "<сценарий, требующий хеджирования>"   # от базы не зависит
  modal_scenario: "<id или none>"        # dominant если probability-weighted вход
                                          # ОБЯЗАТЕЛЬНО "none" если входной
                                          # scenarios YAML содержит
                                          # modal_flag: no_modal (Pure Shell D1)
```

10. **Macro-only blindspots** (новая секция, всегда):
    Список позиций со статусом `MIXED` или `IDIOSYNCRATIC_DOMINATES` из Шага 3.5
    с краткой характеристикой идиосинкратических факторов, которые макро-стресс
    не покрывает. Формат:

    ```
    ━━━ Macro-only blindspots ━━━
    Стресс-тест построен только на макрофакторах. Для следующих позиций
    значимая часть риска/возврата лежит вне матрицы:

        • Регуляторика по сегменту
      Verdict: MIXED — макро задаёт ~60% дисперсии, остальное идиосинкратика.

    {ticker}  ...

    Для таких позиций рекомендуется отдельная оценка через ru-portfolio-advisor

    ```

    Это **не рекомендация купить/продать** — это разметка ограничений
    стресс-теста.

## Anti-patterns

❌ **Давать рекомендации.**
Плохо: «Рекомендуется сократить долю нефтяников». Только: «В worst scenario нефтяники дают −380k RUB (-18%)».

❌ **Угадывать сектор бумаги без маппинга.**
Плохо: «Предположительно ритейл». Хорошо: назначить чувствительность по `references/idiosyncratic-tickers.md` с методом в `factor_betas_method` либо спросить владельца; оставить бумагу в `unmapped_tickers` нельзя.

❌ **Представлять equal-weighted как вероятностный.**
Всегда явно: «Это методологическое допущение Shell (0.25 × 4), не реальные вероятности».

❌ **Считать макро-стресс полной оценкой риска.**
Шаг 3.5 (idiosyncratic reasoning) и блок «Macro-only blindspots» в выходе —
обязательны. Без них пользователь видит только половину риска для позиций со
смешанным или преимущественно идиосинкратическим профилем (банки, девелопмент,
утилиты, недосекторальные ЗПИФ). Стресс-тест без этого блока — неполный.

❌ **Претендовать на точность.**
Плохо: «Портфель потеряет 12.7%». Хорошо: «Ориентировочно −10–15% (±5–8 п.п. доверительный диапазон)».

❌ **Пересчитывать XIRR или менять данные снапшота.**
Скилл только читает снапшот, не модифицирует.

❌ **Моделировать поведенческие факторы.**
Gap'ы открытия, паника, halts, margin calls — вне scope этого скилла.

❌ **Двойной счёт через pass-through.**
`shock_brent` и `shock_inflation_via_brent` вместе в одном bundle — это двойной счёт.
brent→inflation pass-through уже встроен в conditional CPI. Pre-flight check в Шаге 1 ловит это.

❌ **Править собранный YAML руками.**
Числа и имена полей пишет `stress_build.py`; ручная правка разводит файл с пересчётом сайта
и ломает контракт схемы, который проверяет `save-to-library`. Нужна правка — изменить вход
(`betas-priors.json`, `fill.yaml`) и пересобрать.

❌ **Эмитировать портфельное число, не назвав базу.**
Любой `*_rub`/`*_pct` на уровне `portfolio_level_by_horizon`/`portfolio_aggregates`/
`robustness` обязан жить под именем, которое само называет базу
(`price_delta_rub` vs `total_return_rub`), либо внутри блока с явным
`basis: price|total_return` — контракт §11.2a `yaml-schemas.md`.
`validate_stress_output.py` блокирует и голое имя, и неверный `basis` в блоке.

❌ **Сравнивать два прогона, не сверив `basis_contract`.**
17 прогонов 2026-05-11…2026-09-18 меняли базу расчёта под одними и теми же
именами полей 4 раза — сравнение «доходность ушла в минус» оказывалось
сравнением ценового слоя с полной доходностью. Перед любым сравнением двух
stress-YAML — свериться, что оба несут одинаковый `basis_contract`, и
сравнивать `price_delta_*` с `price_delta_*`, `total_return_*` с
`total_return_*`, никогда вперемешку. Архивные файлы без `basis_contract` —
через `scripts/normalize_stress.py`, не на глаз.

❌ **Опускать `caveats` или ставить туда только LOW/MEDIUM записи.**
Минимум одна запись `severity: HIGH` обязательна. В Phase 4.1 (priors-only,
`factor_betas_r2: null`) канонический HIGH-caveat: «factor_betas — секторальные
priors из учебника, не регрессия на реальных данных. Все CI — placeholder
±max(\|Δ\|×0.4, 5%). Точность оценки на позицию: ±5–15 п.п.».
