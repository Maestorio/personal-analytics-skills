# Чтение stress-файла — режимы 3 и 8

> Заменил `mode-8-stress.md` 20.08.2026 (RPA-20). Прежний файл назывался «Режим 8» и
> заканчивался строкой «в остальных режимах (1-7) stress-файл не нужен» — при том, что
> SKILL.md с 19.08 требует его и в Mode 3. Модель, запуская Mode 3, открывала инструкцию,
> сообщавшую ей, что инструкция не про неё.

## 0. Числа берутся из скрипта, не из чтения YAML

Первое действие в обоих режимах — прогон:

```
python3 scripts/stress_digest.py \
    --snapshot Portfolio/snapshots/portfolio-<date>.json \
    --mode 3            # или 8
    [--as-of YYYY-MM-DD] [--tr-stocks X --tr-bonds Y] [--json]
```

Без `--stress` берётся самый свежий `Portfolio/stress/stress-*.yaml` (по полю `date`
внутри файла, не по имени и не по mtime). Если рядом лежит пересчёт сайта `auto/recalc-<этот стресс>.yaml`, дайджест сам берёт числа из него, а возраст и вердикт свежести считает по дате стресса скилла (дате суждений); при `narrative_stale` тексты стресса (оговорки, слепые зоны) относятся к числам дня прогона. С явным `--stress <путь>` пересчёт не подставляется. Скрипт выдаёт: возраст и вердикт свежести по
режиму, сверку поколения со снапшотом, таблицу горизонтов с множителями, EV и tail по
акциям (поштучно и взвешенно), bond carry по держимым выпускам, список непокрытых бумаг,
пропорцию L1-redirect (если заданы обе стороны TR) и готовый блок для отчёта.

Перед эмиссией — второй режим того же скрипта, линт черновика:

```
python3 scripts/stress_digest.py --lint-draft <файл с черновиком ответа>
```

Две проверки, обе про то, на чём молча спотыкается ответ: числа стресса без названного
файла и даты (устаревший срез становится неотличим от свежего) и литеральный множитель
горизонта (`× 24/12`, `× 12/12`) вместо реального — см. §3. Exit 1 = черновик нельзя
эмитить.

**Правило.** Любое число из стресса, попадающее в ответ, приходит из этого прогона.
Стресс — YAML на сотни килобайт: `per_position` содержит десятки записей по 3 горизонта
× 4 сценария, соседние ключи выглядят одинаково, и выборка фрагментами регулярно даёт
не тот срез. Ручное взвешивание 20+ позиций по долям — второй источник той же ошибки.

Читать сам YAML имеет смысл ради качественного контекста: `top_risks`, `hedge_candidates`,
`macro_blindspots`, `caveats`, `notes`, разбор сценариев. Числа — из скрипта.

## 1. Кому что нужно

| Режим | Зачем стресс | Срез | Если стресса нет |
|---|---|---|---|
| **3** Rebalance Opinion | строка «Stress macro EV» и bond-сторона TR-таблицы `rebalance-framework.md` §6.2 — обоснование L1-redirect | primary **h12**, вторая колонка **h24** | L1-redirect **defer** (§6.3), остальной режим идёт полностью |
| **8** Stock Quality Forward Review | макро-фильтр к forward-тезисам, горизонт 1–2 года | **h12** и **h24** | режим продолжается, в ответе явно: macro ΔP&L недоступен |

В режимах 1, 2, 4–7 stress-файл не нужен. Отдельная лестница «свежесть стресса →
глубина вердикта» для Mode 4 живёт в `stocks-methodology.md` § «Три режима глубины»
(4 / 12 недель) — она про право называть числовой таргет в разборе одной бумаги и к
режимам 3 и 8 отношения не имеет.

## 2. Свежесть: у режимов разные лестницы

Возраст считает скрипт (`freshness.code`), и лестницы намеренно не совпадают.

**Mode 8** — стресс есть суть режима, работать без него нельзя:

| Возраст | Поведение |
|---|---|
| ≤ 30 дней | обычный прогон |
| 30–60 дней | в шапке: «⚠️ Stress-тест устарел (`<date>`, +`<N>` дней). Для актуального макро-фильтра рекомендую: запусти `macro-forecast-chain` → `portfolio-scenario-stress`, потом повтори Mode 8. Продолжить с устаревшим? (y/N)» — и **жди явного ответа**. При «да» / `--allow-stale-stress`: «⚠️ Stress устарел на `<N>` дней. Макро-overlay может не отражать текущую ставку ЦБ. Verdict по macro-фактору — pending refresh.» |
| > 60 дней | отказ без запроса: «❌ Stress-тест устарел более чем на 60 дней (`<date>`). Mode 8 без актуального макро-фильтра даёт ненадёжный verdict. Запусти `macro-forecast-chain` → `portfolio-scenario-stress` и обратись снова.» |
| файла нет | продолжай без него, в ответе явно: macro ΔP&L недоступен |

**Mode 3** — стресс нужен одной ветке из семи, поэтому деградирует она, а не режим:

| Возраст | Поведение |
|---|---|
| ≤ 30 дней | полный §6.2 |
| 30–60 дней | предупреждение в шапке; TR-таблица считается, пропорция redirect помечается «проверить после refresh стресса» |
| > 60 дней или файла нет | **L1-redirect defer** по §6.3: buffer остаётся внутри акций с минимальными движениями по priority queue, в отчёте — строка «L1 redirect отложен: стресс от `<date>`, +`<N>` дней». Диф IE, тайминг продаж, база докупки, макро-матрица считаются полностью |

Отказывать в Mode 3 целиком нельзя: разбор изменений IE, тайминг продаж и база докупки
акций стресса не касаются, и блокировать их из-за устаревшего макро-среза — потеря
работы без выигрыша в точности.

## 3. Горизонты якорные — hNN не равен числу месяцев

Стрессы идут в режиме `horizon_mode: anchored`: ключи `h6`/`h12`/`h24` — конвенция
цепочки, а длина горизонта задаётся `horizon_ends` (единственный SSOT). Для прогона от
15.08.2026 якоря 31.12.2026 / 30.06.2027 / 30.06.2028 отстоят на **4,5 / 10,5 / 22,5
месяца**. Отсюда:

- дивиденды и купоны в TR-таблице масштабируются множителем **`месяцы/12`**
  (h12 → 0,87; h24 → 1,88), а не литеральными `12/12` и `24/12`;
- множители печатает `stress_digest.py` (колонка «множитель»), из головы не берутся;
- `bond_carry` уже учитывает реальную длину окна (`t_live_months`, обрезанный погашением
  или офертой) — купоны по держимым бумагам второй раз не масштабируются.

**Primary в Mode 3 — h12** (совпадает с `primary_horizon` файла); h24 идёт второй
колонкой, когда решение обсуждается на двухлетнем горизонте. Пороги пропорции redirect
(§6.2) применяются к спреду **на том срезе, который назван основным в таблице** — спред
на 10,5 месяца и на 22,5 месяца не взаимозаменяемы.

## 4. Что берётся из файла

| Поле | Куда идёт |
|---|---|
| `per_position[<тикер>].by_horizon.<hNN>.expected_pct_pweighted.value` | строка «Stress macro EV» stocks-стороны §6.2; макро-фильтр forward-тезиса в Mode 8 |
| `…expected_pct_pweighted.ci_pct` | ширина интервала, когда вердикт опирается на близкие числа |
| `…tail_var_pct` + `tail_var_scenario_id` | риск сдвига доли: какая бумага и в каком сценарии режет сильнее всего |
| `bond_carry.per_position[<ISIN>].by_horizon.<hNN>.expected_carry_pct` | bonds-сторона §6.2 по **держимым** выпускам: купоны + pull-to-par + fx + reinvest, взвешено по сценариям, с CI |
| `horizon_ends`, `horizon_mode`, `primary_horizon` | длина горизонта и множители (§3) |
| `scenarios[*].p` / `p_by_horizon` | веса сценариев, применённые в этом прогоне; SSOT весов — `scenarios/{name}.yaml`, стресс их только отражает |
| `top_risks`, `hedge_candidates`, `macro_blindspots`, `caveats` | качественный контекст к вердикту |

Чего в стрессе **нет** и брать оттуда нельзя: количеств, стоимости позиций, счетов,
`on_iis` в полном виде — состав портфеля реконструируется только из снапшота
(правило №17 SKILL.md).

Bond carry покрывает лишь то, что в портфеле. Для выпусков-кандидатов, которых нет в
книге (длинные ОФЗ под rate-cut и т.п.), carry считается отдельно — котировки, YTM и
дюрация через `scripts/moex_quotes.py`, допущение о траектории ставки называется явно.
В отчёте эти две группы не смешиваются.

## 5. Сверка поколения

Стресс собран на конкретный снапшот (`portfolio_snapshot_id`). Если анализ идёт на более
свежем — веса позиций разошлись, и скрипт выдаёт `generation_mismatch`. Это не блокировка:
EV по бумаге остаётся валидным (он про бумагу, не про вес), а взвешенные суммы становятся
приближением. В отчёте это называется одной строкой, а не умалчивается.

Сроки стресса сверяются с файлом сроков сайта (`scenarios/horizons.json`). Не совпали — скрипт выдаёт
`stress_terms_mismatch`: обзор называет это в оговорках и не подаёт числа стресса как относящиеся к действующим срокам.

## 6. Куда числа попадают в отчёте

- **Mode 3** — раздел «Buffer distribution» → «Если L1-redirect — Total return table»

- **Mode 8** — макро-колонка forward-тезисов шаблона 8 и sizing-модификатор вердикта.
