# Обязательный процесс анализа

Для КАЖДОГО режима, если делаешь глубокий анализ (не просто flagging), проходи этот чек-лист.
Это не бюрократия, а способ не забыть важное.

---

**Шаг 0. Проверь входные данные.** Если для запрошенного режима требуется snapshot — убедись, что он доступен (приложен или читается из `Portfolio/snapshots/`). Если нет — попроси и **остановись**, не переходи к шагам 1+. Правило №0 и правило №17 действуют полностью.

**Шаг 1. Загрузи snapshot.** Читай `Portfolio/snapshots/portfolio-<latest>.json` через transport-layer (если не был передан явно). Проверь `schema_version >= "2.0"`. Если ниже — сообщи пользователю, что нужна перегенерация через `portfolio-data-loader`.

**Шаг 2. Если режим Returns Analysis** (режим 6) или пользователь хочет доходность: используй блок `snapshot.returns` — уже посчитано data-loader'ом. Смотри в первую очередь `returns.by_type` — в нём сразу видна структура доходности.

**Шаг 2а. Если вопрос про качество или эффективность ЦЕЛОЙ КОРЗИНЫ** (режимы 6 и 8, а также любой вопрос «какие мои бумаги неэффективны»): используй `snapshot.per_instrument_xirr` по всем активным тикерам корзины и отсортируй по xirr. Без этого шага разбор скатывается в абстракцию. Per-instrument xirr даёт количественную базу: какие тикеры тянут вниз, какие дают альфу.

**Шаг 3. Подгрузи свежие котировки и YTM** (для режимов 1, 2, 3, 8):
```bash
python3 scripts/moex_quotes.py --from-portfolio /tmp/portfolio.json --json > /tmp/quotes.json
```
Сначала `python3 scripts/moex_quotes.py --health` — если ISS недоступен, переходи на fallback-каналы (`references/data-sources-priority.md`) и укажи в шапке отчёта. Матрица «какой профиль для какого режима» — там же.

**Шаг 3а. Недельные изменения и метка среза — только скриптом (RPA-28, режимы 1 и 2).**
```bash
python3 scripts/weekly_changes.py --snapshot /tmp/portfolio.json \
  --from <дата данных прошлого обзора> --to <последний торговый день с закрытием> > /tmp/weekly.json
```
Все «Δ за неделю» по бумагам, изменение книги акций, сравнение с IMOEX (`book_stocks.vs_imoex_pp`),
движение RGBI и доходностей облигаций (`yield_change_bp`) берутся из этого вывода, подпись среза —
из `window.label` («закрытие 07.10 → закрытие 15.10»). Цены снапшота — это утро дня загрузки, их
**нельзя** подписывать как «закрытие прошлого дня» и сравнивать с индексом по закрытиям (аудит
20.10.2026: YDEX «−4,1%» вместо −7,2%, в обзоре 08.10 знак сравнения с IMOEX перевёрнут, цены ОФЗ
«16.10 ~12:15» — на деле закрытие 15.10). Утверждения «впервые с …» — только по `window_max`/
`window_min` истории за всё заявленное окно (`--from` раньше). Бумага в `errors` — так и написать в
отчёте («нет закрытия ISS»), не подставлять число из другого источника молча.

**Шаг 4. Проверь `data_quality_flags`** в snapshot — если есть severity `error`, начни ответ с предупреждения. Флаг `ie_changes_detected` означает, что в файле изменились веса IE New/Old — это важно для режимов 3 и 8.

**Шаг 5. Посмотри `ie_actual.per_ticker`** и `ie_summary`. Это **один из трёх сигналов** target frame:

1. `planned_share_pct` — твой target (колонка «Доля Планируемая» из Numbers, primary)
2. `ie_new_pct` — IE-сигнал (secondary, может оспаривать planned)
3. `real_share_pct` — текущее положение

Иерархия — `docs/investment/portfolio/new_met.md` §2.1: fundamental gate → macro → target frame. IE и planned — это **координаты тактики**, они применяются ПОСЛЕ fundamental gate (Шаг 7.5), не вместо. Когда `planned_share_pct=null` — fallback на `ie_new_pct` с пометкой в reasoning.

**Парные колонки (обязательно, retro §E).** Любая таблица долей выводит `planned_share_pct`
и `ie_new_pct` **всегда парой** — даже если вопрос сессии касается только одной из них.
Таблица долей ровно с одной из этих двух колонок запрещена: в разборе 19.08.2026
`planned_share_pct` был в данных, но выпал из выбранного представления на раннем шаге, и все
дальнейшие расчёты пошли в координатах IE.

**Шаг 5.5. Gate Review Inheritance (METH-2).** Гейт акции вычисляется из её последнего решения
(`Portfolio/decisions/`): статус — проекция вердикта, срок — `review_by`. Берётся из выборки — `prior_digest.py
--decisions` (режимы 1–2), `security_digest.py --key` (разбор бумаги, блок `decisions.latest.gate`) или
`decision_write.py digest --key`; файлы решений целиком не читаются. Для каждого тикера в текущем анализе:

1. Решения нет → fundamental gate `unknown` (Mode 3 действует с консервативным cap; Mode 4/8 его ставят решением).
2. Есть → статус как inherited gate:
   - `new_position` (≤4 нед) — мягко, REDUCE OK, ADD ≤0.5 п.п.
   - `review_needed` — Mode 3 skip, Mode 1 не пытается решить, Mode 4 = priority deep dive
   - `reviewed_keep` / `reviewed_buy_more` — gate alive, обычная тактика
   - `reviewed_under_review` / `review_aging` — HOLD, без adds
   - `reviewed_reduce` — REDUCE/EXIT по плану
   - `divested` — игнорировать

Mode 1 **наследует** gate, не пересчитывает. Mode 4/8 — updater'ы: новый гейт = новое решение в блоке
`decisions:` шапки отчёта (`references/adhoc-save.md`).

**Шаг 5.7. База весов — двухуровневая модель (ИНВАРИАНТ, обязательно).**

Все «доли» / «веса» / «% позиции» — это **либо** уровень 1, **либо** уровень 2. Никогда не смешивать в одном тезисе, recommendation или сравнении.

| Уровень | Что это | База | Где использовать |
|---|---|---|---|
| **L1 — класс актива в портфеле** | Доля типа (Акции / Облигации / Кэш / Другое) от NAV | `balance_summary.total_current_rub_excl_iis` | Решения о asset allocation: «40% акций vs 35% акций», «облигации перегружены на 2 п.п.» |
| **L2 — бумага внутри своего класса** | Доля акции среди всех акций; доля облигации среди всех облигаций (или внутри подкорзины USD/EUR/CNY/ОФЗ/КОРП) | `holdings_value_for_class_excl_iis` (сумма по типу актива) | Решения per-security: target / IE / planned / real. Caps в Mode 3. Recommendation в Mode 8 |

**Источники полей (всегда L2 для per-security):**
- `ie_actual.per_ticker[T].real_share_pct` → L2 (доля среди акций)
- `ie_actual.per_ticker[T].planned_share_pct` → L2
- `ie_actual.per_ticker[T].ie_new_pct` / `ie_old_pct` → L2
- `weight_real_pct` / `weight_user_planned_pct` (PRIMARY) / `weight_ie_target_pct` (secondary) в weekly-review YAML → L2
- Бонды: «доля выпуска от облигационной части» — L2 (база = сумма облигаций)

**Источники полей (всегда L1):**
- `balance_summary.goals_matrix` — Валюта × Тип от NAV → L1 (ИИС-3 отдельно в `goals_matrix_iis`)
- «Целевая доля класса "Акции" 40%» → L1
- «Кэш 4.9%» → L1

**Правила эмиссии:**

1. **Каждый процент в выводе помечается базой явно**, если из контекста не очевидно. Шаблоны:
   - «Доля PLZL **6.6% (среди акций)**» — L2, явно
   - «Доля акций **38.2% от NAV**» — L1, явно
   - В таблицах per-security достаточно одного header'а: «Доля, % (среди акций)» или «Доля, % (среди облигаций)».

2. **Сравнения только в одной базе.** Если real_share_pct = 6.63% (L2) и IE-таргет 8% (L2) — сравниваем напрямую. Если хочется сказать «довести до 5%» — это **либо** L2 (5% среди акций), **либо** L1 (5% от NAV); явно указать какую.

3. **Конвертация L1 ↔ L2:**
   ```
   L1_pct = L2_pct × stock_share_of_nav    (для акции)
   L2_pct = L1_pct / stock_share_of_nav
   ```
   где `stock_share_of_nav = sum_stocks_value / total_current_rub_excl_iis`. Аналогично для облигаций.

4. **Recommendation per-security** (Mode 1 per-issuer, Mode 3 ребаланс, Mode 4 single, Mode 8 forward) → **всегда L2**, чтобы быть в одной системе координат с IE/planned/real. Если есть веская причина дать NAV-base число — рядом обязательно эквивалент в L2.

5. **Сложение sanity-check.** Сумма всех L2 акций ≈ 100%. Сумма всех L1 ≈ 100%. Никогда не суммировать L1 и L2.

6. **Нарратив «overweight / underweight»** строится в **той же базе**, что и target. PLZL real=6.63% L2 < IE=8% L2 → **underweight** на 1.37 п.п. (L2). Текст «выше IE-таргета» при L2 < target — фактическая ошибка.

См. также Шаг 6 (NAV-база для класс-аллокации) и rebalance-framework.md §"Иерархия target".

**Шаг 6. Вычисли реальные доли класса актива (L1)** от `balance_summary.total_current_rub_excl_iis` (основные счета без ИИС-3). Для анализа облигационной части используй `balance_summary.bonds_value_by_type_excl_iis`. НЕ от плановой суммы, НЕ от «Итого» с пополнениями. Per-security доли (L2) уже посчитаны в `ie_actual.per_ticker` — не пересчитывать.

**Шаг 6.1. Gate-aware sizing — база докупки для открытых тикеров акций.** Слова плана владельца (`user_plan`) в автоматическом режиме: «держать» — ничего, «привести к плану» — докупка и срез до плана, «докупать» — только докупка, «ждать» — блокировка, «продать» — срез до нуля без коридора и запрет покупки (таблица — `references/gate-aware-sizing.md` §«Слова плана владельца»). Бумага плана «докупать»/«привести к плану» без позиции — кандидат на первую покупку: гейт должен разрешать (нет записи = «новая», покупка закрыта до разбора), цена — котировка или цена IE (там же). Если среди
акций текущего цикла есть хотя бы один тикер со статусом `review_needed`/`reviewed_under_review`/
`review_aging` или активным `no_buy`-constraint (Шаг 5.5) с недостигнутым таргетом
(`real_weight < target_weight`) — сумма докупки Open-тикеров считается от **базы докупки**
(то, во что акционная книга может вырасти сейчас, пока часть бумаг стоит под гейтами), не от
полного плана класса и **никогда** от `balance_summary.goals_matrix` → `Изменение` (это разрыв
до полного плана, не сумма докупки — на этом поле построена ошибка ×14 от 19.08.2026).
Обоснование и таблица вариантов — `references/gate-aware-sizing.md` §«Сайзинг при частичной
заморозке акционной книги». Если таких тикеров нет — база докупки равна полному плану класса,
гейт не применяется.

**Срез до плановой доли — `--trim`, не `--selling`.** Если решение по тикеру — сократить
позицию ИМЕННО до определённой плановой доли (не полный выход и не транш без известной
цели), передавай его в `--trim TICKER[=weight_pct]`, а не в `--selling`: `--selling`
полностью выбрасывает тикер из расчёта (и из базы, и из веса открытых), занижая базу
докупки — реальный кейс 21.08.2026, ошибка ×1,8. `--trim` держит остаток позиции в базе
(это её неподвижная часть) и считает цель среза от той же базы, что и докупки. Дискриминатор
— «определён ли целевой вес после сокращения, и равен ли он плановой доле» —
`references/gate-aware-sizing.md` §«Из чего состоит `F`».

**Правило только для класса акций.** Для облигаций и фондов база докупки — плановая (полный
план корзины); гейт-aware база здесь не применяется — `references/bonds-methodology.md`,
`references/funds-methodology.md`.

**Правило неразворота — `--acted`/`--cycles`.** Если по бумаге в этом горизонте (обычно
3–6 месяцев) уже была сделка, передай её направление явно: `--acted TICKER=buy` или
`--acted TICKER=trim` (направление обязательно — голый `--acted TICKER` без направления
даёт понятную ошибку). Движение в ту же сторону разрешено без ограничений; арифметика,
требующая развернуться, — подавляется, тикер уходит в Dormant с warning'ом, база
пересчитывается. Перед сделкой, где риск разворота на горизонте не очевиден, прогони с
`--cycles FILE.json` (список обозримых состояний цикла) — скрипт покажет диапазон цели по
всем состояниям и явный `reversal_risk`, если какое-то из них требует движения в обратную
сторону сверх гистерезиса (`--hysteresis-pp`, по умолчанию 1,0 — Rule 3). `reversal_risk` —
предупреждение, не блокировка: решение исполнять сейчас или отложить — за владельцем. Срочная
продажа (`--selling`) правилу не подчиняется — исполняется всегда. Обоснование и три уровня
защиты — `references/gate-aware-sizing.md` §«Правило неразворота».

**Лимиты концентрации — `--concentration-limits`/`--sector`.** По умолчанию скрипт сам
подхватывает `references/concentration-limits.yaml` (как и `constraint_engine.py` —
флаг только переопределяет путь). Знаменатель — фактическая книга (`L2_cur`), НЕ база
докупки: это ДРУГОЙ вопрос, не путать с сайзингом. Нарушение лимита блокирует `Open`
(даже вопреки ручному `--open`) и не даёт срезу (`Rebalancing`) развернуться в докупку —
но не блокирует сам срез, им нарушение и лечится; также снимает признак «сделка уже была
в горизонте» для среза (риск-лимит старше правила неразворота). Секторный лимит —
отдельный флаг `--sector`, выключен по умолчанию (гейт на качество поля `sector` в
снапшоте). Отказ загрузки конфига деградирует с warning'ом, сайзинг не прерывает.
Обоснование и разграничение с «Concentration cost» Шага 7.5 ниже —
`references/gate-aware-sizing.md` §«Лимиты концентрации».

**Автоматический режим `--auto` — не для отчёта.** Его зовёт не аналитик: это расчёт
колонки «Сейчас» в «Долях и целях» вьюера (Open = недобор к плану владельца **больше
гистерезиса** (1 п.п.) без автоблокировки; срез = перевес > гистерезиса у `user_plan: BALANCE`;
pending-условие с продажей (`sell_condition`) или «держать» (`condition_hold`) в своём окне
закрывает докупку — 2026-10-26; лоты по цене и лоту снапшота, цели IE не участвуют). Во вьюере тот же расчёт идёт в JS
(`tools/assets/rebalance-engine.js`); совпадение держит `tools/tests/test_rebalance_parity.py`.
Меняешь классификацию, базу, лоты или лимиты здесь — меняй и там (тест упадёт). В отчёте
по-прежнему — решение аналитика через `--open`/`--trim`/`--acted`: автоматика не знает
правила неразворота, сроков из отчётов и «резервов».
С `--quotes FILE` в режиме `--auto` файл — **`quotes@1`** (`python3 scripts/moex_quotes.py --emit
quotes@1 --boards TQBR`; с валютными облигациями — `--boards TQBR,TQOB,TQCB --fx <валюты номинала держимых облигаций, кроме RUB/SUR, через запятую>`, иначе блока курсов нет и такие облигации остаются по снапшоту): живые цены применяются поверх снапшота ДО расчёта (`apply_quotes`:
стоимость = кол-во × цена, доли от активной книги, строка класса «Сейчас»/«Планы»), как во вьюере
(`RebalanceEngine.applyQuotes`). Без `--quotes` — цены снапшота, старые прогоны воспроизводятся.
Вне режима `--auto` `--quotes` по-прежнему принимает выход `moex_quotes.py --json` (только лоты).

Ни сбор входов, ни арифметику не делай вручную — вызывай скрипт:

```bash
python3 scripts/gate_aware_sizing.py \
  --snapshot <путь к portfolio-<date>.json>            # обязателен
  [--decisions <Portfolio/decisions>]                  # опц., гейт из решений (автоклассификация Blocked)
  [--security-attrs <Portfolio/security-attrs.json>]   # опц., IPO-пауза по справочнику бумаг
  [--conditions <Portfolio/conditions.yaml> --conditions-state <Portfolio/conditions-state.json>]
  [--open TICKER[=weight_pct][,...]]                   # тикеры цикла, открытые к докупке
  [--selling TICKER[,...]]                             # полный выход/срез без цели (вне F и S)
  [--trim TICKER[=weight_pct][,...]]                   # срез до плановой доли (вне F, но в S)
  [--blocked TICKER[,...]]                             # ручное дополнение автоклассификации
  [--acted TICKER=buy|trim[,...]]                      # правило неразворота: направление уже
                                                        # исполненной в этом горизонте сделки
  [--cycles FILE.json]                                 # обозримые состояния цикла (диапазон цели)
  [--hysteresis-pp N]                                  # гистерезис флага разворота (default 1.0)
  [--concentration-limits FILE.yaml]                   # лимиты концентрации, дефолт — шипованный конфиг
  [--sector]                                           # секторный лимит (выключен по умолчанию)
  [--concentration-today YYYY-MM-DD]                   # дата для проверки истечения исключений
  [--quotes /tmp/quotes.json]                          # выход moex_quotes.py → лоты (опц.)
  [--extra-cash-from-sales N]
  [--json | --text]                                    # по умолчанию — оба блока
```

Разбери `base_source` из JSON-выхода:
- `fixed_point` — обычный случай, база докупки посчитана по неподвижной точке;
- `fixed_point_capped` — неподвижная точка выше плана класса, база ограничена планом;
- `t_full_no_gates` — в F ничего нет (все бумаги двигаются к плану), база докупки равна полному плану класса;
  без блокировок, но со спящими бумагами база — та же неподвижная точка (`fixed_point`);
- `manual_check_required` — расчёт вырожден (`near_degenerate`), числа не досчитаны —
  доложи пользователю и не выдумывай сумму.

Проверь `warnings[]` — каждый (`weight_fallback_ie:<TICKER>`, `manual_unblock:<TICKER>`,
`lots_unavailable:<TICKER>`, `yaml_unavailable`, `trim_overridden_by_selling:<TICKER>` —
тикер передан и в `--trim`, и в `--selling`, побеждает полный выход,
`trim_direction_flipped:<TICKER>` — база докупки выросла настолько, что цель среза
превысила текущую позицию, срез формально развернулся в докупку,
`extra_cash_from_sales_double_count_risk` — одновременно `--trim` и ненулевой
`--extra-cash-from-sales`, риск посчитать выручку от среза дважды,
`acted_reversal_suppressed:<TICKER>` — правило неразворота подавило разворот по тикеру с
`--acted`, тикер переведён в Dormant, база пересчитана,
`acted_reversal_iteration_limit_exceeded:<N>` — предохранитель итерации не сошёлся за
отведённое число проходов (не должно срабатывать при корректном входе — если сработал,
числа под `--acted` требуют ручной проверки),
`recent_trade_hint:<TICKER>` — по тикеру есть недавняя сделка (`recent_direction` в
снапшоте), а `--acted` по нему не передан: реши, было ли это решением о ребалансе, и
если да — передай `--acted` явно, признак автоматически не выставляется,
`trim_candidate_hint:<TICKER>` — тикер помечен `user_plan: BALANCE` и стоит выше плановой
доли, а `--trim` по нему не передан: если это срез до плана — передай `--trim <TICKER>`,
иначе база докупки выйдет заниженной (позиция целиком считается неподвижной). Порог здесь
не гистерезис: флаг решает не размер среза, а попадёт ли ВСЯ позиция в базу — кейс
21.08.2026, перевес SBERP 0,61 пп при занижении базы на 1 339 122 ₽. Классификация
автоматически НЕ меняется,
`concentration_breach:<группа>` — эмитент/сектор превысил лимит концентрации,
`exception_expired:<id>` — именованное исключение из лимита истекло, применён лимит по
умолчанию, `sector_limit_disabled` — секторный лимит не считается (грязные данные
`sector`), `open_override_blocked_by_concentration:<TICKER>` — запрошенная докупка
отклонена лимитом концентрации (ручной `--open` риск-лимит не отменяет),
`concentration_blocks_rebalancing_buy:<TICKER>` — срез, требуемый лимитом, не может
развернуться в докупку той же бумаги, цель капнута на текущую позицию,
`concentration_check_unavailable:<причина>` — конфиг лимитов концентрации недоступен
(файл/PyYAML/данные), проверка пропущена, сайзинг не прерван) отражается в
тексте ответа рядом с тикером.

Готовый текстовый блок скрипт формирует сам (`report_block`) — по контракту
`references/output-templates.md` §«Как называть базу докупки». В ответ идут база докупки,
остаток, закрытый для покупок гейтами, доли к базе и суммы по бумагам (включая срез, если
он есть в цикле — со своей формулировкой, не докупкой) — **без** формулы, `T*`, `F`, `S`,
«неподвижной точки» и имён функций; развёрнутый вывод расчёта — только по прямому вопросу
«откуда число».

> Если в тексте ответа применительно к бумагам одного класса **дважды и более**
> встречается формулировка о блокировке покупки («гейт», «условие», «IPO-гейт»,
> «under_review», «заблокирован», «очередь заблокирована») и в том же ответе называется
> сумма докупки по этому классу — прогон `gate_aware_sizing.py` **обязателен**.
> Словесное описание блокировки без числа закрытой гейтами части — незавершённый анализ.

**Шаг 7.5. Fundamental Gate Pushback (METH-2).** Перед формированием verdict — оцени fundamental gate для каждого тикера через 4 forward-чека (`docs/investment/portfolio/new_met.md` §2.1):

- **Concentration cost**: >7% портфеля в одной thin-margin бумаге → gate под сомнение.
  **Не путать с лимитами концентрации Шага 6.1** (`--concentration-limits`): здесь
  знаменатель — весь портфель (NAV), там — акционная книга (`L2_cur`); здесь роль —
  эвристический триггер усомниться в gate конкретного тикера, там — количественный
  риск-лимит с конфигом и исключениями, блокирующий докупку. Разные вопросы, разные числа
  — совпадение порядка величины (7% vs 15%/20%) ничего не значит
- **Fundamentals delta**: ухудшение forward-метрик (маржа, NIM, ROE, FCF, долг) на последних 2–4 отчётах → gate=under_review
- **Trust IE по domain**: consumer/tech/financial = MEDIUM → IE × 0.7-0.8
- **Catalyst EV**: catalyst tree E[return] ниже portfolio benchmark → gate=under_review

**XIRR — НЕ gate-чек.** Realised XIRR (`per_instrument_xirr`) — backward-looking диагностика и audit-контекст. Длинная просадка (>18 мес) — это **триггер для проверки** forward-тезиса, а не основание дисконтировать target. Различай:

- **Циклический убыток** (тезис жив, цикл против): фундаментал в норме, catalyst EV положительный, просадка от внешнего цикла (rate, FX, сырьё) → НЕ дисконтировать target, ждать разворота цикла
- **Сломанный тезис** (тезис мёртв): фундаментал ухудшается 2+ отчёта подряд И/ИЛИ catalyst delivery отрицательная И/ИЛИ структурный regulatory headwind → gate=broken/reduce, target → 0 через Mode 4

XIRR-колонка в выходе — комментарий «история и forward согласованы / диверг», не самостоятельный аргумент для INCREASE/DECREASE.

**Логика комбинации gate × macro:**

| Fundamental gate | Macro modal scenario | Verdict |
|------------------|---------------------|---------|
| alive | tailwind | BUY/HOLD к target |
| alive | neutral | HOLD, small adds |
| alive | headwind | HOLD без adds |
| alive | severe headwind | TRIM до safe-size |
| under_review | любой | HOLD, ждать clarification |
| broken | любой | REDUCE/EXIT поэтапно |

Если **Mode 1** обнаружил hard trigger по бумаге с inherited `reviewed_keep` → `flags.gate_review_required: true`
у бумаги в обзоре: гейт становится «Нужен разбор», пока обзор новее решения. Mode 1 **не** пишет решений.

Если **Mode 4** делает deep dive → запись в блоке `decisions:` шапки отчёта: `verdict` (гейт — его проекция),
`review_by` (срок гейта, 7–180 дней; null — 60 дней), `target_pct`, `note`.

Critical events — см. `references/critical-events-list.md` (двухуровневая модель closed_enum / open_trigger).

**Шаг 9.5. Ограничения и условия бумаг — срез (Mode 1, 2, 7, 8).** Выполняется до Шага 10. Обзор условий не пишет
и ограничений не заводит: ограничение бумаги существует только как условие (модуль (а): определения
`conditions@2` + состояние) или как слово плана владельца на сайте. `user_constraints[]` в обзоре — **производный
срез** на дату обзора, его строит скрипт; из прошлого обзора он не переносится (`carry_over_weekly.py` его не несёт).

1. Срез и итоговые вердикты — одним вызовом по аналитическим вердиктам ВСЕХ бумаг обзора:
   ```bash
   echo '{"analytical_verdicts": {"DOMRF": {"verdict": "BUY", "confidence": 0.72}, …}}' |
     python3 scripts/reconcile_constraints.py --root {root} --snapshot {снапшот} --today {review_date} --pretty
   ```
   По каждой бумаге выход даёт `advisor_verdict`, `unconstrained_verdict` (+`_confidence`, только если вердикт
   изменило условие), `advisor_verdict_constraints` (объединить с ИИС-3-локами, не перезатирать),
   `user_constraints[]` (срез: `derived: true`, `as_of`, `condition_id` или `plan_field`, `reason` из кодлиста
   `block_reason`, `until`, `summary`), `waits_owner[]`, `markdown_block`. Поля кладутся в YAML как есть (delta
   `per_item.set`), `markdown_block` — в отчёт. Правила среза — докстринг скрипта: ждущее условие с `verdict_now`
   фиксирует вердикт; сработавшее и ждущее владельца — запись `status: fired`, вердикт не меняется; слово плана
   KEEP/WAIT/SELL при вердикте вверх — запись `plan_field: user_plan`, вердикт не меняется.
2. Сработало (`waits_owner`) → резолюция в MD-отчёте (применён / уже исполнено / отклонено / перенесено — SKILL.md,
   Pre-emit checklist); «перенесено» — фраза владельцу «перенеси условие `<id>` на …» (Режим 9).
3. **Сверка с условиями ближайшей недели (Mode 1 и Mode 2).** После финальных вердиктов —
   `echo '{"verdicts": {тикер|ISIN: advisor_verdict, …по ВСЕМ бумагам обзора}, "horizon_days": 7}' |
   python3 {save-to-library}/scripts/apply_condition.py crosscheck --root {root} --today {review_date}`. Ловит бумагу,
   упомянутую в тексте действия ЧУЖОГО условия (своп «продать X → купить Y» заведён на Y), с вердиктом против
   намерения. Каждый `conflicts[]` — правка вердикта или фраза владельцу о правке условия, и одна строка резолюции
   в отчёте.
4. Владелец в сессии говорит «не покупать до …», «входить ниже …», «сними/продли ограничение» — это условие или
   план, не поле обзора: готовая фраза на «Действиях» («добавь условие …», «перенеси условие X на …») → Режим 9
   (`apply_condition.py add|edit|withdraw`) либо правка плана на сайте. В YAML обзора ограничение не пишется никогда.
5. Форма (TRIPLET RULE): `unconstrained_verdict` ≠ `advisor_verdict` ⇒ срез непуст. save-to-library (F2.6) блокирует
   обзор, где это нарушено или запись среза без `derived` / `as_of` / `condition_id | plan_field` / `summary`.

**Шаг 9.7. `verification_priority` ставит штамп, не модель.** В YAML обзора поле остаётся `null` (так его
пишет стаб). После записи файла save-to-library запускает `assemble_artifact.py stamp-report --root … --doc
Portfolio/weekly-reviews/<файл>.yaml`: скрипт считает приоритет каждой бумаги
`constraint_engine.compute_verification_priority` (вердикт, уверенность, действующие условия модуля (а), статус гейта
модуля (б)) и перезаписывает поле; валидатор с `--root` блокирует расхождение. Правило движка (расширенное C5,
`catalyst-tree-rules.md §6`): HIGH — вердикт со сделкой сейчас или нужен разбор (гейт «нужен разбор», «новая, без
разбора», «срок решения вышел»); MEDIUM — отложенное действие (условие с вердиктом-сделкой, сделка под ограничением),
уверенность < 0,6; LOW — иначе. «Наблюдать» — не «нужен разбор»: такая бумага ждёт своего условия. Статус гейта
модель берёт только из выборки `security_digest`, копию в обзор не пишет.

**Шаг 9.8. Финальная самопроверка перед эмиссией (retro §5).** Проверка «сходится ли» не
ловит «то ли посчитано» — тождество «сумма недоборов = избыток кэша» сходится до рубля и при

```bash

```

Чистый выход (exit 0) обязателен для любого ответа, где названа сумма или доля докупки акции;
нарушения — устранить до эмиссии, не отправлять черновик как есть.

Суммы, количества и целевые доли любых сделок (акции, облигации, фонды) в строках с действием проверяет
второй линт — по выводу скриптов прогона; выводы сохраняй в файлы (`fanout-news.md`, «Результаты — в файлы»):


`sizing_to_target.py` считает «довести долю до N %» от базы `--base nav` (по умолчанию, NAV без ИИС-3),

в базе класса: `--base class`. Числа, которых нет в выводе скриптов, в ответ не идут: посчитай скриптом или убери.

## Mode 3 — Stability constraints (METH-2)

См. `references/rebalance-framework.md`. Краткая сводка:

1. **Cap per position per cycle** — таблица caps по статусу (от 0.5 п.п. для new_position до 40% для reviewed_reduce)
2. **Cap per cycle** — ≤4 позиции за один rebalance (priority broken → under_review → drift ≥2 п.п.)
3. **Hysteresis** — не двигать если `|real - target| < 1 п.п.` И нет триггера
4. **Continuity check** — прочитать предыдущий weekly-review, не разворачивать verdict без gate-flip объяснения
