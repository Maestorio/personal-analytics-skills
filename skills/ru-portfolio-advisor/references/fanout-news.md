# Fan-out субагентам: сбор новостей/событий (Mode 1 / Mode 2)

> Вынесено из SKILL.md дословно при дроблении 2026-08-12 (этап 3, подготовка Max → Pro).

### Fan-out субагентам: сбор новостей/событий (ОБЯЗАТЕЛЕН: Mode 1 — при ≥5 акциях, Mode 2 — при ≥5 корп-эмитентах)

**Mode 1 без sweep — тоже дефект прогона (RPA-34, с 2026-10-27).** До этого fan-out в Mode 1 был
«рекомендован», и 26.10.2026 обзор акций на Sonnet (High effort) выбрал сбор сам: ~45 страниц
(21 лента investmint + cbr, tbank, smart-lab, IR-сайты) прошли через основной контекст, прогон
дал 3 компакции, после второй новости пришлось искать в журнале сессии — ровно инцидент 16.10,
от которого RPA-25 защищает только при запущенных агентах.

**Проверяемо:** `sweep_collect.py` пишет в блок `coverage` поле `method: sweep_collect`; валидатор
save-to-library блокирует обзор с ≥5 акциями / корп-эмитентами без него (`review_date` ≥ 2026-10-27).
**Субагентов в среде нет** (инструмент Agent/Task недоступен) — остановись ДО сбора и скажи владельцу:
«субагентов нет; собрать новости в основном контексте (это 2–3 компакции) или перенести обзор?».
Согласие → `coverage.method: inline_owner_approved` и `coverage.method_note` (причина + дата согласия);
валидатор пропустит с предупреждением.

**Mode 2 без sweep — дефект прогона, а не экономия (RPA-26).** Обзор облигаций 16.10.2026 пропустил
fan-out («по 22 выпускам эмитентов отдельно не проверял») в неделю кредитного стресса у девелоперов;
независимый аудит нашёл пропущенный статус «под наблюдением» Эксперт РА по ЛаймЗайму (08.10) и
рейтинг Автобана, отозванный НКР ещё 24.09 (inc-2026-10-20-7, -8, -12). Если бюджет/лимит не
позволяет sweep — остановиться и сказать владельцу ДО сборки YAML, а не выпускать обзор с переносом.

Сырые выдачи web_search по 20+ тикерам — главный пожиратель контекстного окна
advisor'а и корень R-COV-провала 23.07 (покрытие молча срезалось, потому что
честный per-тикер поиск инлайн слишком дорог). При ≥5 тикеров/эмитентов к
проверке — **не выполняй поиски сам**: делегируй добычу субагентам по образцу
`forecast-monitor` §4.0. Разделение труда жёсткое: агенты только ИЗВЛЕКАЮТ
факты; вердикты, скоринг, catalyst tree и reconcile — только у тебя.

**Результаты — в файлы, не в контекст (RPA-25, жёстко).** 16.10.2026 результаты четырёх
sweep-агентов жили только в контексте; после 3–4 компакций их пришлось восстанавливать из журнала
сессии (inc-2026-10-20-13). Порядок:
1. До отправки батчей запиши отправленные строки в `{workdir}/sweep/rows.json`
   (`[{"key", "name", "query"}]`) — это эталон для сверки `searched_as`.
2. В промт каждого агента: «запиши JSON-массив в `{workdir}/sweep/sweep-<N>.json`; в ответ —
   ОДНА строка: `OK sweep-<N>.json: строк X, с событиями Y, budget_exhausted Z`». Если среда агенту
   писать файлы не даёт и он вернул JSON текстом — **первым же действием** запиши его в этот файл
   (Write), и только потом читай.
3. Сводку собирает скрипт, а не ты:
   ```bash
   python3 scripts/sweep_collect.py --rows {workdir}/sweep/rows.json --dir {workdir}/sweep \
     --mode 1|2 --today {review_date} --md {workdir}/sweep/summary.md > {workdir}/sweep/collect.json
   ```
   Он проверяет `searched_as` против отправленного `name` (чужая компания → строка отброшена),
   формат событий (kind, ISO `event_date`, url), `accessed` не в будущем; отдаёт события, «тихих»,
   недопроверенных (`budget_exhausted` + не вернувшиеся + отброшенные), кандидатов на ярус 2,
   рейтинги (Mode 2) и готовый блок `coverage` (`checked_this_run` / `not_checked`).
4. Читай `summary.md` (короткий), а не сырые ответы. После компакции — перечитай его же.
   `accessed_date` источников бумаги = `accessed_by_key` из `collect.json`, а не дата обзора.
5. Обязанности родителя ниже (сверка, переподтверждение критичных фактов, spot-audit «тихих»)
   остаются за тобой — скрипт снимает только механику.

**Расшифровка стрима / вебинара IE — тоже агентом и в файл.** Расшифровку целиком не читать.
Агент (sonnet) получает список тикеров и эмитентов портфеля и пишет `{workdir}/sweep/ie-stream.json`:
`[{"key", "statement": "<=40 слов, близко к тексту", "timecode", "stance": "buy|hold|sell|avoid|neutral|mention"}]`
плюс `{"key": "_macro", ...}` для макро-тезисов (ставка, курс, нефть). Правила: только то, что
сказано в расшифровке; без оценок; тикер, который не упоминался, не выдумывать. Родитель читает этот
файл и применяет к нему профиль доверия IE (`references/invest-era-profile.md`) как обычно.

**Ярус 1 — sweep (model: haiku; батчи 5–8 строк; все батчи одним сообщением — параллельно).**

**Резерв поиска родителю (жёстко, до отправки батчей).** Общий бюджет `web_search`
сессии конечен и общий с субагентами. Перед fan-out отложи **≥25 вызовов** себе —
переподтверждение критичных фактов (правило 16), spot-audit «тихих» и добор причин
аномалий делегировать нельзя, а сделать их нечем, если ярус 1 выбрал всё.
Инцидент 15.08.2026: 5 sweep-агентов израсходовали 200/200 до начала переповерки —
причина секторного провала золотодобытчиков и календарь ЦБ остались невыясненными,
хотя это ровно те задачи, что закреплены за родителем.

**Бюджет яруса 1 — в промт каждого агента:** ≤2 `web_search` на строку, ≤2 открытых
страницы на строку, потолок батча — `2 × число строк`. Лимит исчерпан → вернуть
собранное, недостающие строки пометить `status: "budget_exhausted"` (не `quiet` —
иначе непроверенное выглядит как проверенное).

**Окно поиска — без «слепого окна».** `window_start` = дата ДАННЫХ прошлого обзора
(дата снапшота / последнего закрытия, на котором он строился) минус 2 дня, а не дата его выхода
и не «последние 14 дней» от сегодня. Кейс 16.10: обзор 08.10 строился на данных утра 08.10,
обзор 16.10 смотрел релизы Эксперт РА с 09.10 — действие 08.10 выпало у обоих.

Список строк:
- **Mode 1:** активные акции (`holdings` where `asset_type == "stock"`) +
  `ie_summary.list_in_ie_not_in_portfolio`.
- **Mode 2 (фильтр из снапшота — НЕ все облигации):** только корп-эмитенты
  (ОФЗ исключить — эмитентского риска нет, макро покрыто watcher/monitor);
  приоритет `credit_quality MEDIUM/LOW`, бумаги с офертой ≤ 6 мес, замещайки
  (санкционный риск). Бумаги одного эмитента группировать в одну строку.
  **Обязательно в строки:** эмитенты из блока «Рейтинг пора перепроверить» выжимки прошлого обзора
  (`credit_rating_checked_at` пуст или старше 28 дней) и бумаги с действующим условием
  (выборка `apply_condition.py digest`), где триггер — рейтинговое действие.

Промт субагенту (самодостаточный — агент НЕ читает SKILL.md и не может спросить):

```
Для каждой строки выполни web_search новостей С {window_start} ПО {today} и верни
СТРОГО JSON-массив, по объекту на строку:
{"key": "<ticker|issuer>", "searched_as": "<название компании, по которому искал>",
 "status": "quiet"|"events"|"budget_exhausted",
 "events": [{"kind": "report|dividend|rating|offer|default|court|sanction|guidance|other",
             "event_date": "YYYY-MM-DD", "fact": "<=20 слов", "url": "..."}],
 "ratings": [{"agency": "АКРА|Эксперт РА|НКР|НРА", "rating": "...", "outlook_or_status": "...",
              "action_date": "YYYY-MM-DD", "action": "присвоение|подтверждение|понижение|повышение|под наблюдением|отзыв", "url": "..."}],
 "accessed": "YYYY-MM-DD"}
("ratings" — только для строк облигаций: ДЕЙСТВУЮЩИЙ рейтинг эмитента/выпуска по каждому агентству
 с датой ПОСЛЕДНЕГО действия, включая отзыв и статус «под наблюдением»; не нашёл — пустой список.)
Правила (нарушение = мусор):
- ИМЯ ЭМИТЕНТА БЕРЁТСЯ ТОЛЬКО ИЗ ПОЛЯ name ВХОДНОЙ СТРОКИ. Расшифровывать тикер
  самостоятельно ЗАПРЕЩЕНО: тикеры неоднозначны, и своя догадка уводит поиск в
  другую компанию. В searched_as вернуть ровно то название, по которому искал.
- Бюджет: ≤2 web_search и ≤2 открытых страницы на строку. Исчерпан — вернуть
  {"key": "...", "status": "budget_exhausted", "accessed": "..."}, НЕ "quiet".
- event_date — дата САМОГО СОБЫТИЯ, не дата публикации страницы.
- fact — только из результатов поиска ЭТОЙ сессии; ничего из своих знаний.
- Ничего релевантного → {"key": "...", "searched_as": "...", "status": "quiet",
  "accessed": "..."} — честное «тихо» лучше догадки.
- Предпочтительные источники: для эмитентов облигаций — АКРА / Эксперт РА / НКР /
  НРА, e-disclosure.ru, moex.com; для акций — раскрытия, IR-сайты, деловые СМИ.
- Никаких вердиктов, оценок и интерпретаций — только извлечение.
Строки: [{key, name, подсказка-запрос}, ...]
```

**`name` во входной строке обязателен** — источники по приоритету: предыдущий
weekly-review (для облигаций — `per_bond[].issuer`, шапка `fundamental_score_basis`,
Шаг 3.5 чек-листа) → `snapshot.holdings[].name`. В снапшоте поля `issuer` нет —
юридическое имя эмитента приходит только из weekly-review-bond YAML. Строку без
установленного имени в fan-out **не отправлять** — проверить самому.

**Ярус 2 — targeted deep-dive (model: sonnet; ТОЛЬКО по эскалации, один агент на строку).**

Триггеры эскалации из ответов яруса 1:
- Mode 2: `kind ∈ {rating, offer, default, court, sanction}` или ≥2 событий по
  одному эмитенту;
- Mode 1: `kind ∈ {sanction, court}` или отчёт/guidance с явным расхождением
  против ожиданий.

Задание агенту яруса 2 — собрать **досье фактов** по одной строке: история
рейтинговых действий, лента раскрытий e-disclosure, график купонов/оферт,
суды/санкции. Тот же формат: факты + даты + URL, серьёзность — только
enum-классификацией. **Запрещено:** рассуждения, аналогии «похожих кейсов»,
вердикты — маленькая модель «вспоминает» кейсы из своих знаний вместо поиска,
а провенанс-правило на рассуждения не натягивается.

**Бюджет яруса 2 — жёстко в промт агента** (калибровка 31.07: свободный deep-dive
по Борцу сделал 137 обращений и стоил ~20% всей сессии; его вывод достигался
5 источниками). В задании формулируй **конкретный вопрос** («подтвердить/опровергнуть
факт X», «хронология события Y»), а не «разберись с эмитентом», и ставь лимит:
**≤ 12 web_search-запросов и ≤ 10 открытых страниц; приоритет — рейтинговые
агентства → e-disclosure/moex → IR → деловые СМИ; лимит исчерпан — вернуть
собранное с пометкой budget_exhausted**, решение о продолжении за родителем.

**Обязанности родителя (не делегируются):**
- **Сверка `searched_as` — до чтения фактов.** Не совпало с `name`, которое ты
  отправил (иное юрлицо, иная отрасль, транслитерация в другую компанию) → весь
  ответ по строке **отбрасывается**, строка проверяется самостоятельно, инцидент
  идёт в Caveats. Два боевых случая 15.08.2026: BTBR искали как «BitRiver» вместо
  B2B-Center (при `name: 'iВ2В-РТС'` прямо в снапшоте) и RU000A107AW3 как
  «Аэрофьючерс» вместо АО «АЭРОФЬЮЭЛЗ» — оба ответа выглядели валидным JSON'ом
  и прошли бы без этой сверки.
- **`status: budget_exhausted` — не покрытие.** Такая строка идёт в R-COV как
  непроверенная (`carried_over: true` или собственная проверка), никогда не как
  `quiet`.
- **Критичные факты — переподтвердить самому по URL агента**: дефолт, даунгрейд,
  дата оферты, дивидендная отсечка. Правило 16 в полной силе: агентский факт без
  первички (e-disclosure / moex.com / IR / рейтинговое агентство) — повестка для
  проверки, не источник даты.
- `accessed` агентских ответов → таблица покрытия R-COV (`accessed_date`
  источников). `quiet` со свежим `accessed` = тикер ПРОВЕРЕН в этом прогоне
  (не carried_over).
- Битый формат / вердикты вместо фактов → ответ отбрасывается, батч выполняется
  самостоятельно (fallback, как в monitor §4.0).
- **Spot-audit «тихих»**: false-quiet ничем не ловится (в отличие от ложного
  события, которое режет переподтверждение). Поэтому 1–2 случайных строки со
  статусом `quiet` за прогон переповерь сам одним web_search; расхождение
  (событие было, агент промолчал) — фиксируй в Caveats как инцидент яруса 1
  и в этом прогоне не доверяй прочим quiet без переповерки.
- Правило 18 не нарушается: агенты не формируют ответ и не читают SKILL.md —
  они только добывают факты; агрегация и все выводы остаются у центральной модели.
