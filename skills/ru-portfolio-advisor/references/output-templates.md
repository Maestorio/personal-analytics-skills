См. `analysis-process.md` Шаг 5.7. Кратко:

## Как называть базу докупки (контракт формулировок)

SSOT — `docs/investment/portfolio/gate-aware-sizing-rollout-plan.md` §1 (решение владельца
20.08.2026), цитируется дословно. Правило распространяется на **все** шаблоны ниже, где
называется сумма покупки акции, и **не зависит** от источника денег (пополнение, выручка от
продажи, купоны). Владелец: формулу в отчёте видеть не нужно. Нужны — база и то, что в неё
не влезло. Числа при этом обязательны: убираем нотацию, а не цифры.

### 1.1 Глоссарий: внутреннее ↔ отчётное

| Внутри (спека, референсы, код) | В тексте отчёта |
|---|---|
| `T*`, «неподвижная точка» | **база докупки** — сумма ₽ + % NAV (термин утверждён владельцем 20.08.2026) |
| `T_full` | **полный план класса** / «плановые 40%» — сумма ₽ |
| `T_full − T*` (`blocked_gap_rub`) | **не размещается сейчас** — сумма ₽ + пп NAV; из неё: |
| `gap_gated_rub` | **остаток, закрытый для покупок гейтами** — сумма ₽ (термин утверждён владельцем) |
| `gap_in_corridor_rub`, `gap_unallocated_rub` | «недобор бумаг в коридоре и „держать“», «доля плана, не распределённая по бумагам» |
| `F`, `S`, `T* = F/(1−S)`, `1/(1−Σw)` | **не выводятся никогда** |
| Open / Blocked / Dormant / Rebalancing / Selling | «открыты к докупке» / «под гейтом» / «без сигнала» / «на срез до плана» / «на полное сокращение» |
| `compute_fixed_point_target`, имена скриптов | не выводятся |

### 1.2 Обязательный состав (не форма — состав)

Любой ответ, где названа сумма или доля докупки **акции**, обязан содержать:

1. **База докупки одной фразой:** сколько ₽ (и % NAV), и почему именно столько — какие
   бумаги стоят и потому не растут.
2. **Остаток, закрытый для покупок гейтами:** сколько ₽ (только `gap_gated_rub`, не весь разрыв до плана класса:
   недобор бумаг в коридоре и нераспределённая доля плана называются отдельно) и что его открывает —
   поимённо, с датой/триггером. Гейт без даты называется бессрочным явно (это проблема
   конкретного тикера, а не «недостижимость 40%»).
3. **Доли к базе** — отдельной строкой, в процентах: владелец вводит их вместе с базой
   в IntelInvest, который сам считает лоты. Формат: `RENI 11% · MBNK 4% · X5 5,5%`.
   Без базы эти проценты бесполезны — поэтому база и доли всегда рядом, в одном блоке.
4. **По каждой открытой бумаге:** факт ₽ → цель ₽ → докупить ₽, и — если есть котировки —
   приблизительное число лотов («≈ N лотов по <цена> ₽ на <дата>», округление вниз).
   Лоты справочные: точное количество считает IntelInvest, скилл лишь даёт порядок.
   **Если в цикле есть срез до плана (Rebalancing, не полная продажа):** та же строка,
   но «срезать ₽» вместо «докупить ₽», округление лотов вверх (дорезать лучше, чем
   недорезать). Срез — это ЧАСТЬ той же базы докупки, не отдельная сумма с другим
   знаменателем; сумму среза не выводить без суммы докупки рядом (правило-минимум п.5.3
   применяется к обеим сторонам).
5. **Проверка на разворот (правило неразворота, `gate-aware-sizing.md` §«Правило
   неразворота») — если прогон делался с `--cycles`:** одной строкой диапазон цели по
   обозримым циклам (`target_min ₽ … target_max ₽`), не только цель текущего цикла — план
   должен явно показывать, что цель может уехать в этом направлении дальше. Если
   `reversal_risk` непуст — отдельная строка-предупреждение с тикером и величиной
   отклонения; это предупреждение, не блокировка, решение исполнять сейчас или отложить —
   за владельцем. Прогона без `--cycles` эта строка не касается — диапазон просто не
   считался, домысливать его не нужно.
6. Ни формулы, ни `T*`/`F`/`S`, ни «1/(1−…)», ни имён функций.
7. Развёрнутый вывод расчёта — только если пользователь спросил «откуда число»,
   и тогда один раз, отдельным блоком в конце.

**Правило-минимум:** если в ответе сказано, что что-то докупается, база докупки названа.
Без неё ответ не отдаётся — владелец не сможет применить доли в IntelInvest.

### 1.4 Термины закреплены, синонимы вторичны

**«База докупки»** и **«остаток, закрытый для покупок гейтами»** — канонические названия
(решение владельца 20.08.2026), в заголовке блока и в первом упоминании используются
дословно. Дальше по тексту допустимо «база», «достижимая база», «то, во что книга может
вырасти сейчас». Запрещены как замена: «целевая сумма» (путается с планом), «доступная
сумма» (путается с кэшем), «недобор класса» (это про полный план, а не про базу).

## Общие правила

- Заголовок — что за анализ + дата (сегодняшняя или диапазон).
- **Имя файла отчёта (если отчёт сохраняется как отдельный файл) обязательно содержит дату** в формате ISO `YYYY-MM-DD` (для одиночной даты) или `YYYY-MM-DD_YYYY-MM-DD` (для диапазона). Примеры корректных имён:
  - `weekly-stocks-review_2026-04-18.md`
  - `weekly-bonds-review_2026-04-12_2026-04-18.md`
  - `rebalance-opinion_2026-04-18.md`
  - `single-stock_SBER_2026-04-18.md`
  - `fund-selection_stocks-replacement_2026-04-18.md`
  Без даты сохранять нельзя — пользователь копит отчёты и должен по имени видеть период.
- Executive summary / Главный вывод — **всегда** структурированный по буллет-категориям, не один плотный абзац.
- Action items — всегда в конце, нумерованы по приоритету.
- Источники — в самом конце со ссылками и датами.
- Никаких "надеюсь, это помогло" и прочего мусора.

## Статусы гейтов и вопросы владельцу в тексте для человека

Статус гейта — **подписью в кавычках и смыслом для сделок**, не кодом: «YDEX — решение «наблюдать»:
докупать нельзя, при перевесе над планом больше 1 п.п. — сокращать», а не «YDEX reviewed_under_review». Подписи и смыслы —
`references/gate-status-labels.md` (те же, что во вьюере). Коды остаются в машинных полях (выборка
`security_digest`, решения).

Разбор бумаги сделан после прошлого обзора (раздел выжимки `prior_digest.py` «Разборы бумаг после прошлого
обзора») — писать вывод разбора и записанное решение («Разбор YDEX от 23.10: держать без докупки, гейт «На
пересмотре»»), а не «нужен разбор».

Любой вопрос, требующий решения владельца (гейты, условия, отказ из журнала), — **первым блоком ответа**,
с ответом «да / нет», только реальные изменения. Не последним пунктом списка «Что нужно решить».

### Pre-emit checklist для режимов 3 и 8 (realised vs forward; пункты «Mode 3/1» и про докупку — и для режима 1)

Перед эмиссией — для **каждой строки** с вердиктом `replace` / `trim` / `weak-keep` / `buy_more` или предлагаемым `Δ planned ≠ 0`:

- [ ] Forward-тезис строки содержит **минимум один** из: catalyst EV (probability × upside), fundamentals delta (направление за 2–4 отчёта), stress-чувствительность (по 4 сценариям), valuation gap (к IE-target / peer-multiples), дивполитика на 12м вперёд?
- [ ] XIRR упомянут **только** в audit-блоке/колонке, **не** в обосновании вердикта или Δ?
- [ ] Нет фраз вида «XIRR +X% → поднять planned», «XIRR −X% → дисконтировать target», «best XIRR + buy_more gate» (XIRR здесь висит как мнимый аргумент)?
- [ ] Если строка `weak-XIRR-keep` — явно проговорено, что прошлая просадка циклическая, а forward жив (с указанием forward-сигнала, удерживающего тезис)?
- [ ] Если строка `replace-by-fund` — обоснование строится на forward EV-spread (catalyst EV корзины vs IMOEX − TER), а не на backward XIRR-spread? Backward XIRR — audit-подтверждение, не достаточное условие.
- [ ] Mode 3: gate-статусы взяты as-is из выборки решений (`security_digest.py` / `decision_write.py digest`) без перекраски на основании XIRR drag?
- [ ] Mode 3: если в ответе есть числа из стресса — прогнан `stress_digest.py --mode 3`, и в тексте стоят файл, дата и возраст стресса, а множитель горизонта взят из его таблицы (не `hNN/12`)?
- [ ] Mode 3: стресс старше 60 дней или отсутствует → L1-redirect отложен с указанием причины, а остальной режим выдан полностью (не отказ от режима)?
- [ ] Mode 3: если в отчёте есть **buffer redirect через L1-границу** (stocks → bonds/fund/cash), приведена ли total-return таблица **per-instrument** (divs+catalysts+stress для stocks, carry из `bond_carry` для держимых облигаций и coupons+capital gain для конкретных ISIN-кандидатов)? Stress-EV cluster spread (`EV_stocks_cluster − EV_bonds_cluster`) — **недостаточное основание** (пропускает дивиденды, idio catalysts, instrument-specific YTM). ## Шаг 9.5 — срез ограничений бумаги: схема и блоки вывода

### YAML-схема среза `user_constraints` (per-ticker / per-bond, необязательный блок)

Срез ПРОИЗВОДНЫЙ (schema.md §4.2): его строит `scripts/reconcile_constraints.py` на дату обзора из действующих
условий (модуль (а)) и плана владельца; поля кладутся в YAML как есть, руками не пишутся и из прошлого обзора не
переносятся. Нет ограничений — блока нет.

```yaml
unconstrained_verdict: BUY              # только если условие изменило вердикт: аналитический до него
unconstrained_verdict_confidence: 0.78
advisor_verdict: HOLD                   # итоговый — из выхода скрипта
advisor_verdict_constraints:            # summary записей среза + ИИС-3-локи (объединять)
  - "условие domrf-px-2200: покупать ниже 6 600 ₽"
user_constraints:
  - derived: true                       # всегда true — запись построена скриптом
    as_of: "2026-11-06"                 # дата обзора, на которую собран срез
    condition_id: domrf-px-2200         # источник: id условия ИЛИ (взаимоисключающе) —
    # plan_field: user_plan             #   поле плана владельца (user_plan | user_status)
    # plan_value: WAIT                  #   слово плана (кодлист user_plan)
    reason: pending_buy_condition       # код кодлиста block_reason
    status: pending                     # pending | fired (сработало, ждёт владельца)
    until: "2026-12-31"                 # дата триггера или срок условия; null — без срока
    summary: "условие domrf-px-2200: покупать ниже 6 600 ₽"
```

Перечни — кодлисты (`codelists.json` в scripts/ скилла): `reason` — `block_reason`, тип триггера условия —
`condition_trigger_type`, слово плана — `user_plan`. Собственных перечней у среза нет.

**TRIPLET RULE (форма):** `unconstrained_verdict` ≠ `advisor_verdict` ⇒ срез непуст — вердикт может изменить
только условие из среза. save-to-library блокирует нарушение и запись среза без `derived` / `as_of` /
`condition_id | plan_field` / `summary` (в обзорах с 31.10.2026); запись прежней формы (`type`/`expires`/`active`) —
предупреждение «устаревшая форма», она игнорируется.

**Новое ограничение в YAML не пишется никогда.** «Не покупать до …», «входить ниже …», «сними/продли» —
условие через Режим 9 (`apply_condition.py add|edit|withdraw`) или слово плана владельца на сайте; в отчёте —
готовая фраза на «Действиях».

### Блоки вывода в markdown (после per-ticker блока)

`markdown_block` выхода `reconcile_constraints.py` — как есть: перечень записей среза с «до …» и пометкой
«сработало, ждёт владельца», при изменённом вердикте — «аналитический X, итоговый Y». Резолюция сработавших
условий — по Pre-emit checklist SKILL.md.

### Отражение в Executive summary

Если у бумаг есть срез — одна строка:

```
**Ограничения бумаг:** {TICKER1} (условие {id}, до {дата}), {TICKER2} (план владельца: {слово}), …
```

## Решение по бумаге — блок `decisions:` в шапке отчёта (режимы 3 / 4 / 5a / 8)

Вывод разбора по бумаге — один блок `decisions:` в YAML-шапке отчёта (`report@1`), по записи на бумагу; директив
гейта нет (файл гейтов упразднён, статус гейта считается из решения). Модель заполняет только эти поля; `id`,
время, источник, сработавшие условия и автора ставит скрипт `save-to-library` `decision_write.py from-report`
после сохранения отчёта (Workflow N). Схема — `docs/investment/_cross-cutting/data-structures/schema.md` §3.1.

```yaml
decisions:
  - key: GMKN                 # тикер или ISIN; должен быть в tickers[] шапки
    verdict: HOLD             # BUY | ADD | HOLD | HOLD_TO_MAT | WATCH | TRIM | SELL — один словарь для всех классов
    target_pct: null          # целевая доля плана, % портфеля; null = «как в плане»
    review_by: "2026-12-15"   # срок пересмотра (он же срок гейта), 7–180 дней; null = 60 дней от записи
    note: "отчёт 3К подтвердил тезис, докупка — после дивидендной политики"   # одна фраза «почему», ≤ 200 знаков
    confidence: 0.7           # необязательно, 0..1
    keep_open: []             # необязательно: id сработавших условий бумаги, которые это решение НЕ закрывает
```

- Нужен полный разбор Mode 4 (Mode 8 не хватает данных, противоречивые сигналы) — запись в `decisions:` с
  `verdict: WATCH` (статус «наблюдать», докупка закрыта до следующего решения после разбора), `review_by` — срок
  разбора, в `note` — что проверить.
- Проверка шапки — `assemble_artifact.py validate-report --file <отчёт>.md` (блокирующая).

### Статус гейта в weekly-review YAML — не пишется

Копии статуса гейта (`gate_status_snapshot`) в обзоре нет: статус считает модуль (б) из последнего решения по бумаге
(`Portfolio/decisions/`, schema.md §3.5), модель берёт его из выборки `security_digest`. Если обзор нашёл повод для
разбора — `flags.gate_review_required: true` у бумаги, это единственный сигнал гейту из обзора. Валидатор
save-to-library у старых обзоров с копией даёт предупреждение «устаревшая копия, не читается».

## Общие подсказки по форматированию

- Используй таблицы для сравнений (финансы поквартально, кривая ОФЗ, peer-comparison).
- Никогда не вставляй дисклеймеры в середину — только явные предупреждения об ограничениях данных (например, "данные по Q1 ещё не раскрыты").
- Для тикеров всегда в upper case: SBER, не sber.
- Для ISIN — как есть (чувствительны к регистру).
- Процентные пункты обозначай "п.п." (3 п.п.), проценты — "%".
- Валюты: ₽, $, €, ¥. Для CNY допустимо "¥" или "CNY".
