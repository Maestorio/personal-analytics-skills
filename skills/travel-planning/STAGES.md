### Сквозные правила

- **Haiku — категорически нет на Stage 2/3/4** (Tier-1/2/3 баг). SKILL.md model self-check блокирует.
- **Sonnet без thinking — нет на Stage 2/3/4/5** (срезает углы). Допустим только на P / 1A / E.
- **Safety filter Sonnet** в Claude.ai обычном чате может валиться → кнопка «Continue» запускает Haiku (не Sonnet!) с тем же визуальным лейблом. Workaround: новый чат на Opus.
- **Retrospective dates** — если сезон в прошлом, Stage 0 спрашивает (либо `retrospective: true`, либо опечатка). Opus делает осмысленный inference с явным флагом, не silent shift.

## P — Profile management

**Зачем.** Создать / обновить / объединить / показать / удалить профиль
группы путешественников. Профиль читают все Stage 0–6.

**Входы.** Для CREATE — ничего. Для остальных — `profiles/{profile_id}.md`.

**Запуск.** Под-режим (`create` / `update` / `merge` / `show` / `delete`)
и `profile_id` (кроме CREATE). При CREATE и MERGE — обязательный `[ASK]`
поля `группа_архетип` (выбор из 4 значений, дефолта нет).

**Выход.** `profiles/{profile_id}.md` с обязательными секциями (состав
группы, базовый город, стиль, ядро интересов, физформа, переносимость,
исключения, бюджет) и YAML-полем `группа_архетип`.

**Переносимость ≠ физформа.** Физформа — выносливость (шаги, перепад,
высокогорье). Переносимость — внешние условия, при которых день
перестаёт работать: жара с влажностью, мокрая тропа с уклоном,
укачивание на серпантине, езда пассажиром на байке в дождь. Пороги
персональные, не усредняются; планирование идёт по самому низкому
порогу группы.

**Исключения — два тира.** «Никогда» (вето) и «не как основа, но
эпизодически допустимо» (пляж на полдня; попсовая точка рядом с базой,
когда день сорвался). Один список превращает «не интересно» в вето и
выбрасывает точку из артефакта — а на месте в неё всё равно идут.

**Модель.** Sonnet без thinking.

**Детали** — `references/profile-management.md` (§2 CREATE, §3 UPDATE,
§4 MERGE, §7.5 архетипы и веса).

---

## Архетипы группы — кратко

4 значения поля `группа_архетип`:

- `самостоятельные` — соло или пара, планируют сами, без гида; активный темп, mid-range (дефолтный аналог; legacy-имя `независимые_соло_пара` продолжает работать)
- `семья_с_детьми` — с детьми до 16, длительные базы, кид-friendly POI
- `взрослые_50_плюс` — основной возраст 50+, комфорт, без ночных переездов
- `люкс` — премиум, resort-based, fewer locations

Архетип определяет калибровку **Stage 1** (seed source-set DR) и
**Stage 2** (веса similarity 6 компонентов). Перекрывается опц. блоком
`similarity_weights_override` в YAML профиля.

**Полные таблицы весов и seed-наборов** — `references/profile-management.md` §7.5.

## 0 — Региональное сужение

**Зачем.** Превратить размытый запрос в конкретный скоуп 3–5 логических
регионов с распределением ночей.

**Входы.** Профиль.

**Запуск.** Направление, длительность (ночей), сезон, `profile_id`.
Опц.: `trip_start_city`, `pre_committed_places`, `trip_wishes`.

**Выход.** `{trip_id}/0_scope.md`:
- YAML-шапка (`home_city`, `trip_start_city`, `home_eq_start`,
  `trip_wishes`, опц. `content_density_overrides`).
- Анализ 8–12 регионов по 8 параметрам.
- 3 пакета: компактный / сбалансированный / расширенный.
- Honest assessment.
- Блок `## Решение` — заполняет человек.

Плюс `{trip_id}/trip.yaml` — мета-карточка поездки (`trip-meta@1`:
title/status/travelers/season, необязательные точные даты start/end;
спека — §2.3 storage-and-naming). Создаётся здесь со `status: planning`;
дальше статус ведут режимы, меняющие состояние поездки (план принят Stage 5
→ `ready` + `start`/`end`, если у дней есть даты; состоялась → `done`;
вытеснена → `superseded`). Даты для старых планов:
`python3 scripts/trip_dates.py trips/{trip_id}` — печатает строки для вставки.

**Модель.** **Opus + adaptive thinking** (приоритет) — особенно
при ≥3 страны или ≥6 регионов в anchor. Sonnet + adaptive thinking
— допустимый минимум для одностраничных поездок с очевидным скелетом
(но canonical bias: пропускает hidden-gem регионы за пределами стандартного
туристического скелета страны).

**Детали** — `references/stage0/stage0-scope.md`.

## 1 — DR-промт (Mode A) или довыборка (Mode B)

**Зачем.**
- **Mode A:** сгенерировать промт для запуска Deep Research в отдельной
  сессии. Скилл сам DR не запускает.
- **Mode B:** добавить отчёты к существующей DR-базе через discovery
  (B1) или по URL (B2).

**Входы.** Mode A: `0_scope.md` с заполненным `## Решение`, профиль.
Mode B: `1_dr_reports.md`, профиль.

**Запуск.** `trip_id`. Для Mode B1 — темы discovery; Mode B2 — список URL.

**Выход.**
- Mode A: готовый промт + шаблон YAML-шапки для `1_dr_reports.md`.
  Промт автоматически параметризован под архетип профиля (seed source-set)
  и содержит блок активного поиска критических отзывов на регионе.
- Mode B: обновлённый `1_dr_reports.md`.

**Модель.** Mode A — Sonnet без thinking (подстановка плейсхолдеров).
Mode B — Sonnet + adaptive thinking (discovery + парсинг 20-field).

**Детали** — `references/stage1/stage1-dr-prompt.md`.

## 2 — Similarity filter

**Зачем.** Каждому автору DR-базы поставить similarity-score 0–10 по 6
компонентам и категорию (в теле — ВЫСОКАЯ / СРЕДНЯЯ / НИЗКАЯ / ОСОБЫЙ СИГНАЛ /
БЕЗ ОЦЕНКИ; в YAML — `HIGH / MEDIUM / LOW / OUTLIER / UNSCORED`).
Сформировать reading list для Stage 3.

**Входы.** `1_dr_reports.md`, `0_scope.md`, профиль.

**Запуск.** `trip_id`. Веса 6 компонентов резолвятся автоматически из
`группа_архетип` профиля (опц. перекрытие через `similarity_weights_override`).

**Выход.** `{trip_id}/2_similarity.md`:
- YAML со счётчиками категорий.
- Reading list для Stage 3.
- 20-field карточки на каждого автора с обоснованием.

**Модель.** **Opus** (приоритет) — сложная multi-step задача с
парсингом + категоризацией. Sonnet+thinking — допустимый fallback с
двойной строгостью. Haiku не поддерживается.

**Детали** — `references/stage2/stage2-similarity.md`.

## 3 — POI aggregation

**Зачем.** Извлечь места из reading list, нормализовать имена, посчитать
упоминания по тональности, категоризировать в 6 категорий (в теле — СИЛЬНОЕ /
СЛАБОЕ ПОДТВЕРЖДЕНИЕ / СКРЫТАЯ ЖЕМЧУЖИНА / СПОРНЫЙ / КРАСНЫЙ ФЛАГ / СЛАБЫЙ
СИГНАЛ; в YAML — `strong_confirmed` … `low_signal`).
Пометить synergy-пары и iconic exceptions.

**Входы.** `1_dr_reports.md`, `2_similarity.md`, профиль.

**Запуск.** `trip_id`. Опц. принудительный режим `--mode abundant|scarce`.

**Выход.** `{trip_id}/3_poi_pool.md` (legacy-имя `3_poi_aggregation.md`
тоже принимается на чтение; внутренний YAML-идентификатор `stage:` —
`3_poi_aggregation`):
- YAML со счётчиками, `aggregation_mode`, `synergy_pairs`,
  `iconic_exceptions`.
- Per-POI блок: счётчики, тональность, выдержки, характеристики, опц.
  Combined-with / Iconic-exception, пустое поле «Комментарий пользователя».
- Non-mainstream highlights.

**Что делает пользователь после.** Перед Stage 4 заполняет руками
«Комментарий пользователя» под интересующими POI — это явный приоритетный
сигнал для Stage 4. Опц. — «Комментарий к региону» (строка
`**Комментарий к региону:**` под заголовком региона): что ещё хочется
посмотреть в регионе; Stage 4 учитывает как пожелания.

**Модель.** **Opus base без thinking** (приоритет — валидировано
на Корее: ~10% 5-часового лимита, лучший контекст для Stage 4,
spec-compliant с полезным превышением).

- **Opus + adaptive thinking** — тратит до 50% 5-часового лимита
  без качественного прироста; использовать только при базе >60 POI
  или >10 регионов, либо когда Opus base явно деградирует на
  нормализации спорных кейсов. Adaptive thinking превращает каждое
  локальное решение (тональность, synergy O(N²), cluster, iconic
  exception, нормализация) в reasoning-pass — накопительно ×3-5
  стоимости.
- **Sonnet + adaptive thinking** — допустимый fallback (Корея:
  ~16% лимита, +1 cluster, +5 synergy pairs относительно Opus base,
  но −8 POI Сеул, −1 POI Чеджу, более сжатые quotes). Риск spec
  violations: region-first ordering, пропуск «Комментарий
  пользователя» под POI, слияние разных POI.
- **Haiku и Sonnet без thinking — не поддерживаются** (Tier-1/2/3 баг).

**Детали** — `references/stage3/stage3-poi.md` (в т.ч. правила
категоризации, RED FLAG двух веток для abundant / scarce режимов).

## 4 — Route variants

**Зачем.** Построить 2–3 структурно различных варианта маршрута с явными
тредофами. Стадия не выбирает «лучший» — даёт варианты, человек выбирает
в `## Решение`.

**Входы.** `3_poi_pool.md` с заполненными комментариями
пользователя, профиль. Опц. предыдущий план.

**Запуск.** Только `trip_id`.

**Выход.** `{trip_id}/4_variants.md`:
- YAML с бюджетом, `home_eq_start`, warnings.
- Priority pool до вариантов (MUST / HIGH / MEDIUM / CONDITIONAL / EXCLUDE).
- 2–3 варианта (A / B / C) с маршрутом по дням, отброшенным контентом,
  логистикой, swap-стратегиями.
- Сравнительная таблица.
- Honest assessment с рекомендацией.
- Блок `## Решение` — заполняет человек.
- Опц. `## Комментарии к вариантам` — тоже человек (`**Вариант A:** …`,
  `**Общий комментарий:** …`; в HTML — поля под каждым вариантом). Stage 5
  читает их вместе с `## Решение`.

**Модель.**
- Желательно: **Opus** (с adaptive thinking или без).
- На больших поездках (≥18 ночей, ≥5 регионов) — **Opus + thinking**.
- Sonnet+thinking — допустимый fallback с двойной строгостью Pre-emit
  checklist'а.
- Sonnet без thinking не работает; Haiku не поддерживается.

**Детали** — `references/stage4/stage4-variants.md`.

## 5 — Final consolidation

**Зачем.** Развернуть выбранный вариант Stage 4 в финальный план с
дневной разбивкой, конкретными отелями, ценами, бюджетом. Режим
определяется автоматически:
- **surgical** — структура совпадает с `previous_plan`, точечные правки.
- **reconstructive** — план с нуля или существенная пересборка.

**Входы.** `4_variants.md` с заполненным `## Решение`, профиль, опц.
предыдущий план.

**Запуск.** `trip_id`. Режим определяется автоматически на первом шаге.

**Выход.** `{trip_id}/5_final_plan.md`:
- Расписание по часам / полудням.
- Конкретные отели с верификацией цен на агрегаторах.
- Транспортные сегменты с временем и стоимостью.
- Итоговый бюджет.
- `todo_verification_items` — список TODO к проверке.
- Опц. конвенции Этапа-2 (backward-compatible, на экспорте → визуал):
  тезис `**Замысел маршрута:**` (на обложку), статус-маркеры
  `[[бронь: план|забронировано]]` / `[[погода: …]]` (цветные чипы),
  `*Источник: …*` для якорных POI; дневной `⚠️` — короткий указатель,
  полный swap — в риск-таблице. Детали — `references/stage5/stage5-final.md`
  §6.3.1.

**Риск-таблица — шесть правил (R1–R6, `stage5-final.md`, §8).** Понижать
вероятность можно только внутри горизонта цитируемого прогноза (R1);
риски от одного фактора — одна ставка, и «перетасуем блоки» хеджем не
считается, на каждую базу нужен `[[дождевой блок]]` на полный день (R2);
митигация, которая не убирает причину, вероятность не снижает (R3);
плечо без объезда несёт путь отхода в обе стороны, а не только буфер (R4);
исключённые пользователем точки в ≤30 мин от базы идут в скамейку
запасных, а не в мусор (R5); стыковки считаются для обоих международных
плеч (R6).

**Модель.** Thinking обязателен в обоих режимах:
- Surgical: Sonnet + adaptive thinking.
- Reconstructive: **Opus + adaptive thinking**.

**Детали** — `references/stage5/stage5-final.md`.

## 6 — Финиш (доводка)

**Зачем.** Довести **устаканенный** план 5_vX до trip-ready идеала
добавками, которые **не влияют на выбор маршрута**: координаты маршрута
для обзорной карты, дорожное досье (визы / медицина / прививки / страховка
/ этикет / упаковка / экстренные контакты / связь), инкорпорация
косметической брони. Правило границы: *нужно, чтобы ВЫБРАТЬ маршрут или
ЗАБРОНИРОВАТЬ → Stage 5; пост-решение, один раз → Stage 6.*

**Не делает.** Не переисследует POI, не строит варианты, не меняет дни.
**Не редактирует `5_final_plan.md`** (он immutable) — пишет отдельный
`6_final.md`. Структурная бронь (ломает логистику) — назад в Stage 5.
Enrichment (история / рестораны) — только по явному запросу.

**Входы.** Устаканенный `5_final_plan_v{N}.md` + профиль (из его YAML).
Опц.: `0_scope.md` (визы/сезон), факты косметической брони, запросы
enrichment.

**Запуск.** `trip_id`. Координаты резолвятся двухтиерно: Tier-1 —
детерминированный газетир (`scripts/geocode.py`), Tier-2 — модель для
ненайденных (деревни). Активный web search для досье.

**Выход.** `{trip_id}/6_final_v{N}.md`:
- `## Координаты маршрута` — таблица точек (`lat`/`lon`/источник) + порядок
  маршрута + рёбра (спека обзорной карты).
- `## Дорожное досье` — H3 под-секции.
- опц. `## Бронирования`, `## Углубления`.

**Экспорт.** Финальный PDF собирается **механически**: рендер 5_vX
(билдеры Stage 5) + обзорная карта + досье/бронь/углубления приложениями.
Контент 5_vX повторно через модель не прогоняется (ноль дрейфа).
`6_{trip_id}_финал_v{N}.pdf`.

**Модель.** Sonnet + adaptive thinking (retrieval/компиляция, не
Opus-интеграция).

**Детали** — `references/stage6/stage6-final.md`.

## E — Export

**Зачем.** Адаптировать артефакт под получателя (партнёр / семья /
друзья / архив). Дефолт-формат — **HTML** (self-contained дизайн-система)
для всех стадий 0–6; PDF/DOCX — по явному `--format` (DOCX — Stage 3
operative-документ + round-trip).

**Stage 3 и Stage 4 HTML — редактируемые.** Если страница открыта с хостинга,
где доступен generic write-API (`/api/health` + `/api/file` + `/api/save`),
на Stage 3 правятся теги регионов, комментарии к регионам и комментарии POI,
на Stage 4 — комментарии к вариантам и общий («Сохранить» пишет в исходный
`3_*.md` / `4_*.md` рядом; конфликт версий по hash). Без API —
обычная статичная витрина; DOCX остаётся офлайн-вариантом заполнения.
Экспортируй Stage 3 **в директорию поездки** `trips/{trip_id}/`: имя md
берётся оттуда (каноничное `3_*.md`), а не из имени polished-черновика —
`polished_*` write-API не пропускает, и правки молча не работают.

**Входы.** Артефакт исходной стадии.

**Запуск.** `trip_id`, стадия, формат, опц. получатель.

**Выход.** `{trip_id}/{stage_short}_{краткое_имя}_{YYYY-MM-DD}.{ext}`
рядом с исходным артефактом.

**Русификация.** Правило одно на весь пайплайн: **ключ — в YAML, ярлык — в
теле**. YAML-шапки и JSON-контракты скриптов остаются английскими (машинный
слой: `category: HIGH`, `strong_confirmed: 4`, `role: core`, `tempo: balanced`),
тело `.md` пишется русскими ярлыками (ВЫСОКАЯ, СКРЫТАЯ ЖЕМЧУЖИНА, Ядро,
сбалансированный). Ярлык модель **не переводит сама** — копирует вербатим из
`category_label` / `severity_label` output'а скриптов.

Экспорт добивает остаток детерминированно: старые артефакты с английскими
ярлыками в теле печатаются по-русски (парсеры двуязычны), плюс словарь
англицизмов (all-in → всё включено). SSOT переводов —
`scripts/data/taxonomy.json`, одинаково в HTML и reportlab/DOCX.

Английскими в теле остаются: имена компонентов similarity (`C1 style 8→2.0`),
машинные трейлеры карточек Stage 1 (`tonality: critical`), якоря парсинга
(`#### Cluster:`, `**Combined with:**`, `SIGNAL:`, заголовки секций
`## Longlist` / `## Honest assessment` и т.п.). `POI` и `Deep Research` не
переводятся никогда.

**Модель.** Sonnet без thinking. HTML — свой рендер-слой (без внешних
зависимостей); PDF — HTML→PDF (локальный chromium или core `pdf`); DOCX —
reportlab-ветка (Stage 3).

## Общие правила (все стадии 0–6)

**Transport gate.** Если требуемый входной файл не приложен к чату И
Synology mount недоступен — скилл останавливается и просит приложить
файлы (или починить доступ). Альтернативных транспортов нет.

**Gate-проверки.** Каждая стадия проверяет наличие входных артефактов
до запуска. Не угадывать — если чего-то нет, отказ одной строкой.

**Manual save.** Скилл не пишет в `{travel_root}` автоматически (выдаёт
markdown в чат, сохраняет пользователь). Исключение — Cowork + Synology
mount: скилл пишет через Write + present_files.

**«Сохранить как» — НЕ в теле файла.** Блок сохранения выдаётся
отдельным сообщением в чате после артефакта, не внутри markdown.

**Profile drift.** Если профиль обновлялся после создания стадии —
скилл предупреждает одной строкой, старые артефакты автоматически не
пересчитывает.

**Цены и фактоиды.** Любая денежная цифра — диапазон + TODO для
верификации на Stage 5. Сезонные утверждения без явного источника —
TODO. Не маскировать TODO под факт.
