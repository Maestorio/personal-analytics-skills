# travel-planning

Пайплайн структурированного планирования путешествий. Распределяет работу между
ИИ (сбор источников, similarity-фильтр, POI-агрегация, построение вариантов) и
человеком (финальные решения о scope и выборе варианта). Делает скрытые
ИИ-решения явными и проверяемыми, лечит «ореол достоверности от структуры».

Пользователь — биостатистик. Коммуникация на русском, структурно, без воды.

Философия пайплайна и обоснование стадий — в `references/methodology.md`.
Загружай при вопросах «как это работает», «зачем similarity-фильтр»,
«почему такое разделение».

---

## Inputs / Outputs

**Inputs:** запрос пользователя, профили из `{travel_root}/profiles/`,
артефакты предыдущих стадий из `{travel_root}/trips/{trip_id}/`. Резолв
`{travel_root}` — `references/storage-and-naming.md`.

**Outputs (как artefact в чат):** markdown с YAML frontmatter, готовый к сохранению
пользователем по предложенному пути. Скилл **не пишет** в файловую систему
автоматически.

**Downstream:** дефолт-экспорт — self-contained HTML (свой рендер-слой, без
внешних зависимостей); core `pdf` / `docx` — только при `--format pdf/docx` в
Export mode (PDF также локальным HTML→PDF-движком).

## Хранилище

**Шаг 0.** Перед первой записью в Claude-Memory прочитать `_hub/settings.json`; `ai_mode: off` → в Claude-Memory не писать, сообщить владельцу, что сайт в режиме без ИИ и правки идут с сайта.

Корень — `{travel_root}/`. Логика резолва (Synology mount; fallback —
только файлы, приложенные к чату), конвенции путей, имена файлов, YAML-шапки —
всё в **`references/storage-and-naming.md`**. Загружай этот файл при любой
операции чтения/записи артефакта.

**`{travel_root}` = `~/Library/CloudStorage/SynologyDrive-home/Claude-Memory/travel-planner/`**
(папки `profiles/`, `trips/`). Это единственное место планов. Папка «Путешествия»
(на Synology, в «Документах», в подключённых проектах) — НЕ `{travel_root}`: там
бывают старые копии и сырые билеты/ваучеры. Нет доступа к пути выше (облачная
среда, Cowork) — запроси его по `storage-and-naming.md` §1.2, а не ищи в других
папках; планов поездки не нашёл — стоп по §1.4.

Базовая структура корня (для ориентира — детали в reference):

```
{travel_root}/
├── profiles/{profile_id}.md
└── trips/{trip_id}/
    ├── trip.yaml
    ├── 0_scope.md
    ├── 1_dr_reports.md
    ├── 2_similarity.md
    ├── 3_poi_pool.md
    ├── 4_variants.md
    ├── 5_final_plan.md
    └── {stage_short}_{краткое_русское_имя}_{YYYY-MM-DD}.{ext}   # экспорты
```

Экспорты лежат рядом с md-файлами, отдельной папки `exports/` нет.

`trip.yaml` — машиночитаемая карточка поездки (контракт `trip-meta@1`,
спека — §2.3 storage-and-naming): Stage 0 создаёт её (`status: planning`),
дальше статус обновляется по жизненному циклу (план принят → `ready`
и точные даты `start`/`end`, если у дней плана есть даты; поездка
состоялась → `done`; проработка вытеснена → `superseded`). Без точных дат
карточка держит только `season` — это штатное состояние. Даты для уже
принятых планов — `scripts/trip_dates.py`.
Поддерживать карточку актуальной — обязанность каждого режима, который
меняет состояние поездки.

Конвенция `trip_id`: `{назначение}[_{детализация}]_{YYYY-MM}` русскими буквами
(пример: `аргентина_2025-03`, `вьетнам_север_2023-09`, `узбекистан_родители_2027-04`).

## Маршрутизация режимов

Скилл запускается через `/travel-planning`. После запуска по сути
запроса определи один из 9 режимов. Если из запроса режим не очевиден —
задать ОДИН уточняющий вопрос (перечислить P/0..6/E с короткими описаниями)
и остановиться. Не угадывать `trip_id`, не угадывать `profile_id`.

| # | Режим | Когда применять | Reference |
|---|-------|-----------------|-----------|
| **P** | Profile management | пользователь хочет создать / обновить / объединить / показать / удалить профиль путешественника. **Доп. под-режимы EXPORT_FORM / IMPORT_FORM / MERGE_FORM** — анкета через DOCX в Word (пустая для CREATE, предзаполненная для UPDATE, объединение 2+ анкет для MERGE), парсится скриптом `scripts/profile/anketa.py`. См. `references/profile-management.md` §10. **DOCX-анкета профиля ≠ Export артефакта стадии (E)** — если пользователь прикладывает `.docx` со словами «Вопрос:» / «Ответ:» / «[x]» в первых 5 строках, это P-IMPORT_FORM, а не E. | `references/profile-management.md` |
| **0** | Региональное сужение | новая поездка: нужно разбить страну/регион на логические единицы и распределить ночи | `references/stage0/stage0-scope.md` |
| **1** | DR-база | (A) scope зафиксирован — генерация промта для Deep Research в отдельной сессии; (B) есть готовый DR-файл и нужно расширить — два опц. под-режима: B1 = discovery на forum.awd.ru по тематике (DR не открывает из-за BPC-challenge), B2 = пользовательские URL. Под-режимы могут идти вместе или порознь | `references/stage1/stage1-dr-prompt.md` |
| **2** | Similarity filter | есть выгрузка DR-отчётов: применить профиль и посчитать similarity-score каждому автору | `references/stage2/stage2-similarity.md` |
| **3** | POI aggregation | есть Stage 2: агрегировать упоминания мест из reading-list авторов (HIGH + OUTLIER + расширенный MEDIUM) по 6 категориям; LOW-авторы читаются только для RED FLAG-сигнала | `references/stage3/stage3-poi.md` |
| **4** | Route variants | есть Stage 3: построить 2–3 структурно различных варианта маршрута с тредофами; user_comments из Stage 3 — явный приоритет, перекрывает priority rule категорий (включая RED FLAG); inline бюджет-warning при ≥10% over лимита из профиля; iconic_exception действует только через user comment | `references/stage4/stage4-variants.md` |
| **5** | Final consolidation | заполнен блок `## Решение` Stage 4: детализировать выбранный вариант до полного дневного плана (9 секций — шапка, подготовка, маршрут, сводные таблицы, план реагирования на риски, чеклист, diff, TODO). Два режима: surgical (структура совпадает с previous_plan) / reconstructive (с нуля). Правки пользователя из `## Решение` встраиваются естественно в маршрут. Активный web search для расписаний/операторов/имён отелей; цены отелей — TODO. Опц. MCP-расширения (Booking/Expedia) — opt-in | `references/stage5/stage5-final.md` |
| **6** | Финиш (доводка) | есть **устаканенный** `5_final_plan_v{N}.md` (маршрут уже не итерируется): довести план до trip-ready идеала добавками, **не влияющими на выбор маршрута**. Ядро (всегда): координаты маршрута (Tier-1 газетир `scripts/geocode.py` + Tier-2 модель, персист в `6_final.md`) для обзорной карты; дорожное досье (визы/медицина/прививки/страховка/этикет/упаковка/экстренное/связь, активный web search); инкорпорация **косметической** брони. Enrichment (история/рестораны/онсэны) — **скилл СПРАШИВАЕТ сам** (§6.5, шаг 9): во время планирования углубления мешают, при финализации нужны, а помнить о них пользователь не обязан. Вопрос несёт границы: по одному блоку на страну и регион, **≤5 предложений + строка источника** (гейт в `polish_check.py`). Шире бюджета — отдельным файлом в `внешние_справки/`, не в дорожный документ. **НЕ редактирует 5_vX** (immutable), пишет отдельный `6_final.md`; финальный PDF собирается механически на экспорте. **Структурная** бронь (ломает логистику) — НАЗАД в Stage 5, не сюда | `references/stage6/stage6-final.md` |
| **E** | Export | подготовить артефакт стадии под конкретного получателя. **Дефолт-формат — HTML для всех стадий 0–6** (self-contained дизайн-система); PDF/DOCX — только по явному `--format`. **Двухслойный flow:** polish (модель переименовывает pipeline-фразы по `references/stage{N}/stage{N}-polish-prompt.md`) → sanity-check (Python diff source ↔ polished по счёту секций/чисел) → render (`export.py`, движок `html` по умолчанию; `--format pdf` через HTML→PDF — КРОМЕ `--stage 6 --format pdf`, там дефолт нативный `reportlab` (дорожный документ печатают: номера страниц, колонтитул с провенансом, независимость от установленного конвертера); `reportlab` также обслуживает DOCX Stage 3). Запускать в **новой Sonnet-сессии** через `/travel-planning export` + приложенный артефакт (по месту, пакет НЕ копировать). **Реализовано (все стадии 0–6):** Stage 0 (витрина «вселенной» регионов для DR, self), Stage 1 (reference-витрина DR-отчётов — карточки списком, регион строкой покрытия), Stage 2 (HTML — интерактивный lookup похожих авторов; PDF — статичная scoring-витрина), Stage 3 (HTML-витрина POI — на хостинге с generic write-API (`GET /api/health`+`GET /api/file?path=`+`POST /api/save {path,content,base_hash}`) сама становится operative: теги регионов, комментарии к регионам (`**Комментарий к региону:**`) и комментарии POI правятся на странице и сохраняются в исходный `3_*.md` рядом со страницей, конфликт по hash → «обнови страницу»; без API — обычная статика. **Имя md в странице — каноничное `3_*.md` из директории вывода, а не имя polished-черновика** (`polished_*` не проходит whitelist write-API → тихий 403 и мёртвая правка), поэтому выход Stage 3 пиши в `trips/{trip_id}/`; приёмка — `grep '"mdFile"' {файл}.html`. **DOCX по запросу** — офлайн operative-документ + round-trip; PDF read-only), Stage 4 (витрина сравнения вариантов, self; на хостинге с тем же write-API — поля комментария под каждым вариантом и общее, пишутся в секцию `## Комментарии к вариантам` исходного `4_*.md` — имя так же каноничное из директории вывода, поэтому выход Stage 4 тоже пиши в `trips/{trip_id}/`), Stage 5 (финальный план, self+parents), Stage 6 (финал: механический рендер 5_vX + обзорная карта маршрута + дорожное досье, self+parents). **Stage 3 export** обогащается из соседних `1_dr_reports.md`/`0_scope.md`, если приложены (иначе self-contained реестр внутри). **Round-trip import** (только Stage 3): заполненный `{trip_id}_места.docx` → `export.py --import` → обновляет `3_poi_pool.md` inplace. | `references/export/export-modes.md` |

Применяй ДО загрузки соответствующего reference и ДО запуска работы.

Передавай **только `3_poi_pool.md`**; никаких upstream-файлов и поиска по папке. Legacy: если у старого файла нет секции `## Источники` — экспортёр fallback'ом ищет соседний `1_dr_reports.md`; не найдёт → атрибуция `cXX Имя` без ссылок (не ошибка, лечится пересохранением Stage 3 с реестром). |

Если gate не выполнен — **первая и единственная строка ответа**: список того,
чего не хватает, и предложение действий («запусти Stage N» / «выбери профиль
из списка» / «начни с Stage 0 для новой поездки»). И стоп.

**Transport gate.** Если хотя бы один требуемый входной файл одновременно
(а) не приложен к чату и (б) не читается из Synology mount — остановиться,
вывести список недостающих файлов и попросить пользователя приложить их к
чату (или починить доступ к Synology). Никаких альтернативных транспортов
нет. Полная формулировка — `references/storage-and-naming.md` §1.4 и §8.0.

Дополнительные правила:
- **Возврат к существующей поездке (re-entry detection v2).** Если
  пользователь упомянул `trip_id` существующей поездки — Glob
  `trips/{trip_id}/` для всех артефактов; прочитать YAML каждого для
  определения `schema_version` и `iteration`. Зафиксировать текущее
  состояние одной строкой:

  > Состояние `{trip_id}`: Stage 0-3 завершены ✓ (schema v2); Stage 4
  > итерации v1, v2; Stage 5 v2 финален.

  Если есть `5_final_plan_v{N}.md` и пользователь не указал явно «новая
  итерация» — **спросить одной строкой**:

  > Что делать?
  > 1. Новая итерация Stage 4 (вернуться к POI pool, перетегировать) ← default при «план не подошёл»
  > 2. Продолжить с v{N} (Stage 5 другая корректировка)
  > 3. Пересобрать Stage 3 (потерять POI комментарии)
  > 4. Вернуться раньше Stage 3 (требует переделки DR, дорого)
  > 5. Сбросить все теги в Stage 3 md и начать tagging заново

  Default = 1 (новая итерация Stage 4). При выборе 1: пользователь
  правит `**тег:** ...` строки (и опц. `**Комментарий к региону:**`)
  в `3_poi_pool.md`, опц. пишет `## Комментарии к вариантам` в
  текущем `4_variants_v{N}.md`, запускает Stage 4
  заново → создаётся `4_variants_v{N+1}.md` (DR не пересобирается —
  Stage 1, 2, 3 stable).

  Если артефакты только v1 (legacy schema) — предложить миграцию или
  продолжение в v1 совместимости.
- **Profile drift.** Если профиль обновлялся после старта поездки — предупредить
  явно, не пересчитывать старые артефакты автоматически.
- **Новый профиль на старте Stage 0.** Если `profile_path` отсутствует и
  пользователь хочет планировать — предложить запустить Profile mode сначала.
- **Quality-enhancing optional inputs.** Перед стартом любой стадии
  >0 — Glob `trips/{trip_id}/` на наличие **опциональных, но повышающих
  качество** артефактов, которые **не приложены к чату**. Если найден
  такой файл в travel_root, но не приложен → **STOP**, **одна** строка
  «найден `{filename}` в travel_root — приложить? [Y/N]», ждать ответ.
  НЕ работать с дефолтами / representative dates / placeholders, если
  файл существует в хранилище и пользователь не подтвердил его
  игнорирование.

  Список optional quality-enhancing inputs:
  | Стадия | Optional input | Что улучшает |
  |---|---|---|
  | 4 | `0_scope.md` | точные даты, `home_city`, `trip_start_city`, `pre_committed_places`, `trip_wishes` |
  | 5 | `0_scope.md` | то же + предотвращает silent representative dates |
  | 4 / 5 (новая итерация) | предыдущий `4_variants.md` / `5_final_plan.md` | контекст для surgical-режима, diff |
  | 6 | `0_scope.md` | направление/сезон/country quota → визы и сезонные риски в досье |
  | 6 (новый перегон) | предыдущий `6_final_v{N}.md` | переиспользование собранного досье/координат при мёрже новой брони/enrichment |

  Если файл не найден в Glob — продолжать без него (это нормально для
  первой итерации). Правило срабатывает **только** при «найден + не

## Выбор модели

**Тир, а не версия.** Имена в таблице и в self-check'ах стадий — тир модели
(Opus / Sonnet / Haiku). Режимы калибровались на Opus 4.7 / Sonnet 4.6 /
Haiku 4.5; текущая версия того же тира проходит проверку без warning
(«Я модель: Opus + adaptive thinking» удовлетворяет «рассчитан на Opus +
adaptive thinking»). Понижение тира (Opus-требование → Sonnet;
Sonnet-требование → Haiku) идёт по явным веткам fallback/стоп. Если новая
версия на конкретной стадии даёт признаки деградации (переименованные
компоненты, чужие шкалы, пропуск скриптов) — остановиться и сообщить
пользователю, как при несоответствии модели.

| Режим | Модель (приоритет 1) | Fallback | Обоснование |
|-------|----------------------|----------|-------------|
| P | Sonnet без thinking | — | заполнение полей |
| **0** | **Opus + adaptive thinking** | Sonnet + adaptive thinking | штучный тредофф depth vs coverage + анализ 8–12 регионов. У Sonnet+thinking — **canonical bias**: пропускает non-mainstream регионы, соответствующие профилю. Opus устойчивее. Sonnet+thinking — допустимый fallback для одностраничных поездок с очевидным скелетом. |
| 1A | Sonnet без thinking | — | подстановка плейсхолдеров в готовый шаблон |
| 1B | Sonnet + adaptive thinking | — | discovery-фильтр (B1) + разбор контента в 20-field; чувствителен к выбору релевантного |
| **2** | **Opus без thinking** | Sonnet + adaptive thinking | объёмная multi-step задача с обязательным `Read` reference + парсинг 20-field × N авторов + запуск скрипта + сборка markdown. Sonnet без thinking не справляется (срезает углы, выдумывает категории). Opus — стабильно по spec. |
| **3** | **Opus + adaptive thinking** | Sonnet + adaptive thinking | агрегация POI с кросс-авторской нормализацией имён + 6-категорийная категоризация. Sonnet+thinking рискует нарушить region-first ordering, пропустить «Комментарий пользователя» под POI или слить разные POI в один (потеря RED FLAG). Opus spec-compliant и консолидирует POI, не over-decomposes. |
| **4** | **Opus** | Sonnet + adaptive thinking | перебор структурных альтернатив + тредофф-анализ. Opus устойчивее к типовым failure modes тредофф-анализа: додумывание точки вылета пользователя, схлопывание формата POI в один броский подсигнал, однотонная загрузка региона, структурно близкие варианты, неучтённая физнагрузка против профиля. Sonnet+thinking как fallback — допустим с двойной строгостью Pre-emit checklist'а (`references/stage4/stage4-variants.md` §6.9). |
| **5 surgical** | **Sonnet + adaptive thinking** | Opus + adaptive thinking | точечные правки в существующем плане; структура наследуется из previous_plan, меняются только POI/активности внутри дней. Sonnet+thinking достаточен для семантической интерпретации правок + детализации новых POI. Opus — fallback при больших поездках (≥18 ночей) с активным web search. Скрипта нет — pure LLM с Pre-emit checklist (`references/stage5/stage5-final.md` §6.7). |
| **5 reconstructive** | **Opus + adaptive thinking** | Sonnet + adaptive thinking | интеграция многих переменных под штучные ограничения: дневные блоки, расписания транспорта, отели, бюджет, реагирование на риски. Opus устойчивее к типовым failure modes: пропуски часов работы, обрезанные swap-стратегии, забытые TODO-категории, пересмотр решений предыдущих стадий. Sonnet+thinking как fallback — допустим для коротких поездок (≤7 ночей). |
| **6** | **Sonnet + adaptive thinking** | Opus (overkill) | retrieval / компиляция / web-search + синтез досье + мёрж косметической брони — НЕ Opus-интеграция (как reconstructive Stage 5). Координаты резолвятся детерминированно (`scripts/geocode.py` Tier-1) + модель добивает ненайденные (Tier-2). Карту рисует детерминированный рендерер. Opus допустим, но избыточен. Sonnet без thinking — остановиться (досье деградирует — пропускаются прививки/этикет/экстренные контакты). |
| E | Sonnet без thinking | — | адаптация тона под аудиторию |

Stage 5 сам определяет режим (surgical vs reconstructive) на первом шаге.
Если reconstructive — явно предложить пользователю поднять модель до Opus
перед началом работы.

### Stage 0: model self-check (обязательный первый шаг)

Stage 0 рассчитан на **Opus + adaptive thinking**. У Sonnet+thinking
— canonical bias: модель пропускает non-mainstream регионы, соответствующие
профилю (видит только «канонический туристический скелет» направления).

**Первая операция Stage 0 — назвать модель одной строкой:**

```
Я модель: <name>. Stage 0 рассчитан на Opus + adaptive thinking.
```

Логика реакции:
- **Opus + adaptive thinking** → продолжать.
- **Opus без thinking** → продолжать с warning «thinking рекомендуется».
- **Sonnet + adaptive thinking** → продолжать с warning: «canonical

- **Sonnet без thinking** → остановиться, предложить переключение

### Stage 0: content_density_override (mini-spec)

Профильное окно `## Частота смены локаций` — **soft constraint**, не
жёсткий потолок. Для каждого региона **обязательно** проверить, не
противоречит ли content-density региона профильному ограничению. Если
регион содержит ≥5 ночей самодостаточного контента, а профиль сужает
до 4 ночей — подсветить override в reasoning региона и предложить
пользователю в `## Решение`.

Конкретные правила и формулировка — `references/stage0/stage0-scope.md`
§6 «Для каждого региона укажи» → блок «Content-density override».
Применённые override фиксируются в YAML-шапке поле
`content_density_overrides[]`.

Без этой проверки Stage 0 рискует молча сузить регион с реальными
5+ ночами контента до профильного максимума 3–4 ночи — потеря материала.

### Stage 1: critic-фразы + seed source-set (mini-spec)

DR-промт Stage 1 параметризуется по `группа_архетип` профиля:
- **Seed source-set** для DR-выборки берётся из лукапа архетипа
  (`references/profile-management.md` §7.5 — канон архетипов и весов).
  Seed — рекомендация, не жёсткий ограничитель; DR может включать
  источники вне seed.
- **Активный поиск критических отзывов** — обязательный блок промта.
  Для каждого региона DR должен найти 1–2 отчёта с обоснованной
  критикой («переполнено», «переоценено», «развод», «вылизано»);
  тональность критики проставляется к POI в поле 14 карточки, откуда её
  читает Stage 3. Без этих отчётов scarce-ветка RED FLAG не сработает.

В META-DIAGNOSTICS DR обязан отметить:
- источники «вне seed-списка»;
- число critical-отчётов **по каждому региону**;
- если critical=0 хотя бы для одного региона → WARNING.

Подробности — `references/stage1/stage1-dr-prompt.md` §6.

### Stage 3: scarce-ветка RED FLAG (mini-spec)

RED FLAG-генератор Stage 3 имеет **две ветки**:

1. **Ветка 1 (abundant + scarce):** `high_neg ≥ 1 И high_recommend = 0
   И low_recommend ≥ 1` — HIGH-критика + LOW-recommend.
2. **Ветка 2 (только scarce, HIGH-доля <30%):** `high_recommend = 0`
   И `non_high_negative ≥ 3` → RED_FLAG; `non_high_negative ≥ 2` →
   CONTESTED. Закрывает математическую невозможность ветки 1 при узкой
   HIGH-когорте.

`non_high_negative` — обоснованная критика (criticize / regret_visited)
от OUTLIER/MEDIUM/LOW. **Обоснованная** = с указанием причины
(«переполнено», «развод», «вылизано», и т.п.). При экстракции упоминаний
LLM проставляет тональность `criticize` ТОЛЬКО при наличии причины в
карточке.

**Язык таксона (Stage 3):** ключ (`STRONG_CONFIRMED` … `LOW_SIGNAL`) — в
YAML-счётчиках и в payload; ярлык (**СИЛЬНОЕ ПОДТВЕРЖДЕНИЕ** / **СЛАБОЕ
ПОДТВЕРЖДЕНИЕ** / **СКРЫТАЯ ЖЕМЧУЖИНА** / **СПОРНЫЙ** / **КРАСНЫЙ ФЛАГ** /
**СЛАБЫЙ СИГНАЛ**) — в теле `.md`, вербатим из `category_label` /
`cluster_category_label` output'а скрипта. Категории авторов в теле —
ВЫСОКАЯ / ОСОБЫЙ СИГНАЛ / СРЕДНЯЯ / НИЗКАЯ (включая якорь выдержек
`- {Автор} #{N} (ВЫСОКАЯ): {текст}`). Английскими остаются якоря
парсинга: `#### Cluster:`, `**Combined with:**`, `**Iconic exception:**`,
`**⚠ Tourist-trap archetype:**`, заголовки секций.

**Из non-HIGH авторов в payload передавать:** для OUTLIER/MEDIUM — все
упоминания (включая criticize/regret_visited); для LOW — recommend (для
ветки 1) **и** criticize/regret_visited (для ветки 2). Neutral от LOW
не нужен.

Скрипт `aggregate_pois.py` применяет обе ветки детерминированно. LLM не
руками категоризирует.

### Safety filter awareness

В Claude.ai чате на Sonnet 4.6 safety filter иногда валит Stage 2 (триггер
не воспроизводим). Пользователь видит «Chat paused» и кнопку «Continue».

**Эта кнопка не возвращает Sonnet** — она запускает Haiku 4.5, оставляя
визуальный лейбл «Sonnet» в шапке. Качество вывода резко падает.

Рекомендованный workflow:
- При safety pause — **открыть новый чат на Opus** (не нажимать Continue).
- Opus в Claude.ai на этой задаче safety filter не валит.
- Альтернатива — Cowork: Sonnet+thinking в Cowork пока safety pause не
  встречал, но без гарантий.

### Stage 2: mini-spec (защита от срезания углов)

Эти параметры — **mandatory** и не могут быть переписаны моделью под свои
«удобные» аналоги. Если модель решит сократить или переименовать —
это нарушение spec, валидируется на выходе.

**6 компонентов similarity (имена строго):**
1. `style` — стиль путешествий
2. `focus` — фокус автора
3. `pace` — темп
4. `independence` — независимость планирования
5. `depth` — non-touristy depth
6. `demo` — возраст и состав группы

Запрещены замены: `season` вместо `pace`, `group` вместо `independence`,
`experience` вместо `depth`, `photo` вместо `demo` и т.п. — типовая
ошибка деградировавшей модели.

**Веса зависят от `группа_архетип` профиля** (канон архетипов и весов —
`references/profile-management.md` §7.5). Дефолт
для `самостоятельные` (legacy: `независимые_соло_пара`) = 25/25/15/10/15/10. Другие архетипы дают
другие веса (например, `взрослые_50_плюс` сильно поднимает demo до 35,
снижает depth до 5). Скрипт `similarity_score.py` резолвит веса
автоматически из payload-поля `группа_архетип` — LLM **не** должна
руками подставлять веса.

**5 категорий (имена строго):** `HIGH`, `MEDIUM`, `LOW`, `OUTLIER`,
`UNSCORED`. Запрещены «Tier-1/2/3», «MISMATCH», «EXCELLENT/GOOD/FAIR», звёзды.

**Язык таксона:** ключ (`HIGH`) — в YAML и в JSON-payload; ярлык
(**ВЫСОКАЯ** / **СРЕДНЯЯ** / **НИЗКАЯ** / **ОСОБЫЙ СИГНАЛ** / **БЕЗ ОЦЕНКИ**)
— в теле `.md`. Ярлык **копируется вербатим** из `category_label` output'а
скрипта, не переводится моделью. Severity предупреждений так же:
`critical/borderline/info` в YAML → **критично/погранично/инфо** в теле
(`severity_label`). Английский ярлык в теле или русский в YAML = нарушение
spec. Компонентные строки `C1 style 8→2.0` остаются английскими.

**Шкала: 0–10**, не 0–100.

**Обязательные шаги (diagnostic-only parser flow):**
1. `Read` references/stage2/stage2-similarity.md.
2. `Read` 1_dr_reports.md (или принять inline из чата). **LLM читает
   markdown напрямую** для семантической интерпретации карточек.
3. `Read` профиль — извлечь `группа_архетип` из YAML.
   - Если есть и валидное (одно из 4 значений или legacy-алиас —
     `независимые_соло_пара` резолвится в `самостоятельные`) — использовать.
   - Если отсутствует (legacy-профиль) — fallback `самостоятельные`
     с warning пользователю одной строкой («профиль без `группа_архетип`,
     используется дефолт; запусти Profile mode UPDATE для калибровки»).
   - Опц. `similarity_weights_override` — если есть, перекрывает архетип.
4. `bash` запуск `scripts/parse_dr_cards.py < 1_dr_reports.md` для
   **диагностики** (status + card_summaries). Скрипт **не строит payload**;
   диагностика — сигнал, deformed ли формат.
5. Read `diagnostic.status`:
   - `ok`/`warning` — продолжать на шаг 6.
   - `error` — opt-in fallback диалог (§9.12 reference).
6. LLM строит payload, читая markdown карточки **напрямую**: для каждой
   из card_summaries проставить components 0–10 и outlier_signal по
   rubric'ам. id/url/name/user_added — из card_summaries (антигаллюцинационная
   сверка).
7. В итоговый payload добавить top-level поле `группа_архетип` из YAML
   профиля (и опц. `similarity_weights_override`).
8. `bash` запуск `scripts/similarity_score.py < filled_payload.json`.
9. Сборка markdown по §8 reference на основе JSON-output скрипта.
   В `## Контекст` отобразить `archetype_used` и `weights_source` из
   output скрипта.

Без обоих скриптов (parse_dr_cards.py и similarity_score.py) Stage 2 не
принимается. Если модель «посчитала вручную» — это значит, что она НЕ
прочитала reference и mini-spec, и результат недоверен.

**Opt-in LLM-fallback при ошибках парсера.** Если
`parse_dr_cards.py` вернул `diagnostic.status=error` (URL пропуски,
mismatch с reports_count, нестандартный формат) — **скилл не парсит
руками самостоятельно**. Выдать пользователю ОДИН batch с тремя
вариантами: (1) LLM-fallback для проблемных карточек, (2) пропустить
их, (3) стоп. Только после явного выбора пользователя продолжать.
Подробности — `references/stage2/stage2-similarity.md` §9.12.

### Stage 4: mini-spec (защита от срезания углов)

Stage 4 — pure LLM (без скрипта), что повышает риск срезания углов
особенно у Sonnet без thinking. Параметры ниже — **mandatory**, любые
отклонения = нарушение spec.

**Priority pool (порядок убывания приоритета, строго):**

Уровни (MUST … EXCLUDE) — внутренняя шкала Stage 4; категории Stage 3
названы так, как стоят **в теле** `3_poi_pool.md` (русский ярлык; в
легаси-артефактах — английский, принимать обе формы).

1. **MUST** — POI с явным положительным комментарием пользователя
   («надо обязательно», «КРАСОТА», «На попасть туда»). Перекрывает
   любую категорию Stage 3, включая КРАСНЫЙ ФЛАГ.
2. **HIGH** — СИЛЬНОЕ ПОДТВЕРЖДЕНИЕ, СКРЫТАЯ ЖЕМЧУЖИНА (без user comment).
3. **MEDIUM** — СЛАБОЕ ПОДТВЕРЖДЕНИЕ. В `aggregation_mode: scarce` категория
   слабее (1 рекомендация автора ВЫСОКАЯ + подтверждение), чем в `abundant`
   (2). Не сравнивать категории через режимы.
4. **CONDITIONAL** — СПОРНЫЙ (только при явной поддержке профиля)
   + КРАСНЫЙ ФЛАГ с положительным user comment (обязательная строка
   «Включён по явному выбору пользователя» в варианте).
5. **EXCLUDE** — КРАСНЫЙ ФЛАГ без user comment; iconic_exception без
   user comment; POI с явно негативным комментарием.

**Комментарий к региону** (`**Комментарий к региону:** …` в шапке региона
Stage 3, опц.) — пожелания пользователя к региону целиком («что ещё хочется
посмотреть»). Названное место, которого нет среди POI, — кандидат в вариант
с TODO на проверку (не выдавать за подтверждённый POI); негатив («не хочу X»)
— как негативный комментарий POI. Невыполненные пожелания — в honest
assessment с причиной. **Не путать с тегом:** комментарий не меняет
обязательность региона.

**Итерация `v{N+1}`** — прочитать `## Комментарии к вариантам` предыдущей
версии (`**Вариант X:** …`, `**Общий комментарий:** …`): прямой сигнал «что
поправить»; отразить в «что изменилось». Саму секцию Stage 4 **не эмитит** —
её пишет пользователь (руками или полями HTML).

**Iconic_exception** — читать `reason` для контекста, **включать только
через user comment**. Без коммента — упомянуть в honest assessment
(«не включён, обнови комментарий в Stage 3»). Страховка от silent
over-promote.

**Бюджет (обязательное правило):**

- `budget_target_rub` = бюджет/неделю из секции «## Бюджет» профиля
  × `duration_nights / 7`.
- Каждый вариант получает **относительный cost rank** `$ / $$ / $$$`
  относительно `budget_target_rub` (НЕ рублёвые суммы — точный бюджет
  считает Stage 5).
- Если все варианты `$$$` (на верхней границе бюджета или выше) →
  info-строка в honest assessment «ни один вариант не уложился в
  комфортный бюджет; расширить бюджет или пересмотреть scope».

**Структурное различие вариантов (sanity-check):** минимум один из
тредофов (глубина/покрытие, плотность, набор регионов, буферы, темп)
различается между любыми двумя вариантами. Если все варианты
косметически разные — это провал, перестроить.

**Сколько вариантов:** дефолт 3; 2 обоснованно при узком scope
(1–2 региона / ≤7 ночей); >3 не делать.

**Обязательные секции выхода:**
1. `## Контекст для следующих стадий`
2. `## Сравнение с предыдущим планом` *(только если `previous_plan` != null)*
3. `## Вариант A` / B / (C)
4. `## Сравнительная таблица` — 6 обязательных осей методологии
   (культурное / физ. / погода / логистика / профиль / сезон) + 2
   фикс. (бюджет / уникальный риск) + до 2 опц. релевантных. Лимит — 10.
5. `## Honest assessment`
6. `## Решение`

**Format-запреты:** имя файла строго `4_variants.md` (без пробелов);
YAML строго `---` (три дефиса) и сверху, и снизу.

**Pre-emit checklist (обязательный self-check ДО сохранения файла).**
Stage 4 обязан прогнать checklist'и из
`references/stage4/stage4-variants.md` §6.10 ДО emit. Чеклист закрывает
типовые failure modes тредофф-анализа, сгруппированные в 7 классов:

- **Класс A — факты:** Stage 0 резолвит `home_city` (из профиля) и
  `trip_start_city` (из запроса; дефолт = `home_city`); Stage 4
  формулирует крайние дни маршрута по `home_eq_start` (старт и конец
  в доме vs в другом городе — разные слова: «Старт/Завершение
  маршрута» vs «Прилёт/Вылет»); международный перелёт не в midpoint
  и только если `home_eq_start == false`; цены = диапазон +
  TODO/«оценочно»; сезонность = источник или TODO.
- **Класс B — Stage 3 сигнал:** HIGH-формат POI разнесён между
  вариантами; условные user_comments отработаны явно; LOW SIGNAL
  регион с 3+ ночами имеет либо общее знание с TODO, либо мягкую
  активность; **POI synergy через `commonly_combined_with` field** —
  Stage 3 размечает кандидатов на объединение в одну экскурсию,
  Stage 4 формулирует помеченные пары как «X + Y единой экскурсией»
  (либо явно расцепляет в «осознанно отбрасывает» с обоснованием);
  fallback для legacy Stage 3 без поля — попарная проверка по
  characteristics; **`trip_wishes` из Stage 0** — backstop-сигнал:
  каждое пожелание пользователя закрыто POI в priority pool варианта
  (поднимает POI в MUST даже без user_comment'а); непокрытые пожелания
  — TODO в Warnings.
- **Класс C — структура:** структурное различие пар вариантов (НЕ
  «один POI vs другой» на одной геометрии); priority pool вынесен в
  отдельный блок ДО Вариантов; внутрирегиональный баланс соблюдён;
  физнагрузка отслежена против профиля; каждый Ключевой риск имеет
  swap.
- **Класс D — логистика:** хрупкий узел во всех вариантах → альтернатива
  хотя бы в одном; один день = одна траектория, не «или…или».
- **Класс I — монотонность маршрута (F-57):** `region_order` геогр.
  монотонен (немонотонность = zigzag, только с обоснованием в
  `red_flags`); open-jaw exit достижим без backtrack; известный прямой
  рейс между core-регионами есть хотя бы в одном варианте; длинный
  транзит (>3 ч) в день вылета → буфер-ночь или вылет после 14:00.
- **Класс E — формат:** `$N` → `\$N`/`USD N`/backtick; YAML `---`;
  имя файла; `## Решение` пустой. **Auto-check:**
  `python3 scripts/check_format.py --stage 4 < 4_variants.md` —
  заменяет хрупкую bash-grep самопроверку (chat-tool ломается на
  regex-escape c `\\$`).
- **Класс F — Warnings:** «бюджетные ярлыки оценочные», TODO
  международного перелёта, LOW SIGNAL caveat.

Нарушение любого пункта = НЕ сохранять, исправить и перепрогнать.

### Stage 5: mini-spec (защита от срезания углов)

Stage 5 — pure LLM (без скрипта), что повышает риск срезания углов на
длинных детализированных планах. Параметры ниже — **mandatory**, любые
отклонения = нарушение spec.

**Mode detection (детерминированно):**

1. `previous_plan == null` → **reconstructive**.
2. `previous_plan != null` + структура совпадает (тот же набор регионов
   + та же аллокация ночей ±0) → **surgical**.
3. Иначе → **reconstructive** с переиспользованием payment-инфры и
   логики реагирования на риски из previous_plan.

Объявляется одной строкой в начале Turn 2. Mode НЕ выбирается
пользователем, не угадывается, не «оптимизируется».

**Парсинг `## Решение` Stage 4:**

- `**Выбран вариант:**` → нормализация (A/B/C/кастомный →
  вариант_а/б/в/кастомный); raw label фиксируется.
- `**Состав:**` + `**Почему этот выбор:**` (опц.) — семантическая
  интерпретация правок (замена формата активности / добавление /
  удаление / уточнение).
- Правки **встраиваются в маршрут естественно**, БЕЗ маркеров в днях.
  ОДНА summary-строка в `## Контекст и ключевые параметры`:
  «Применены правки пользователя из `## Решение` Stage 4: …».
- Кастомный вариант с пустым `**Состав:**` → отказ, требовать
  заполнить.
- **`## Комментарии к вариантам`** (опц., перед `## Решение`): комментарий к
  выбранному варианту и `**Общий комментарий:**` — правки того же рода, что
  `**Состав:**`; к невыбранным — контекст (правка, только если пользователь
  явно «забирает» оттуда что-то в выбранный). Противоречие с `## Решение` →
  приоритет у `## Решение` + clarification. Детали — `stage5-final.md` §6.2.

**Уровень детализации дня (по шаблону `stage5-final.md` §6.3):**

Каждый день — компактный блок с фиксированными иконками-секциями:

- 📍 локация-откуда → локация-куда + переезд (расстояние, способ, время)
- 🏨 отель (имя + район + рейтинг + диапазон-ориентир + TODO); строка **опускается** при повторе того же отеля в последовательных днях — никаких «Та же гостиница»
- 🎯 программа (часовая разбивка с часами работы, ценами входов,
  временем на посещение, опц. операторами synergy-пар); **для key POI
  — MUST через user_comment и HIGH из Stage 3 — 2–4 предложения
  культурного/архитектурного контекста, не только адрес+цена+часы**
  (см. `stage5-final.md` §7 «Сенсорная плотность для key POI»). Для
  проходных POI (LOW SIGNAL без user_comment) — короткое перечисление.
- 💰 бюджет дня (диапазон); согласован с подытогом сводной таблицы
  (±15%) ИЛИ явно оговорено, что показывает только часть статей
- ⚠️ риски / нюансы / swap-стратегии

**Web search policy:**

- **Активно:** расписания транспорта, часы работы и стоимость входа
  достопримечательностей, конкретные операторы synergy-пар Stage 3,
  имена/районы/рейтинги отелей, сезонные ограничения.
- **НЕ web search (всегда TODO):** цены отелей (даже найденные —
  диапазон с TODO), цены ресторанов (кроме общих диапазонов), цены
  такси.
- **Лимит ~10-20 поисков на план.** Никаких систематических «на каждый
  ресторан».

**Опц. MCP-расширения (Booking / Expedia):**

- **По умолчанию** — не используется, цены отелей TODO.
- **Активировать** только при явном запросе пользователя или при
  активных MCP-коннекторах в среде.
- MCP-цены подставляются с пометкой «через {Booking|Expedia} MCP,
  YYYY-MM-DD» и **не заменяют TODO**.
- В YAML фиксировать `mcp_extensions_used`.

**Бюджетная консолидация:**

- `total_budget_rub` = сумма дневных диапазонов midpoint + ночёвки
  midpoint + внутренний транспорт.
- Международный перелёт включается **только** при `home_eq_start ==
  false`, отдельной строкой в `## Шапка`.
- `budget_status` рассчитывается vs `budget_target_rub` из Stage 4
  (under_target / on_target / over_10_20 / over_20+).

**9 обязательных секций output (строгий порядок):**

1. `## Контекст и ключевые параметры`
2. `## Шапка`
3. `## Критические подготовительные пункты`
4. `## Маршрут по дням`
5. `## Сводные таблицы` (транспорт / бюджет / гастрономия)
6. `## План реагирования на риски`
7. `## Чеклист за 2 недели до поездки`
8. `## Diff с предыдущим планом` *(только если `previous_plan` != null)*
9. `## TODO для верификации` (категоризовано: before-booking /
   2-weeks-before / in-trip)

**Opt-in clarification для конфликтующих правок:**

Если правка пользователя структурно противоречит варианту (например,
«добавить день в {регион}» при выделенных в этот регион ночах без
резерва) — ОДИН batch с 3 вариантами (перераспределить ночи /
реализовать урезанно / отказаться от правки). Stop, дождаться ответа.
НЕ угадывать. В YAML устанавливается `clarification_used: true`.

**Format-запреты:** имя файла строго `5_final_plan.md` (без пробелов);
YAML строго `---` (три дефиса) и сверху, и снизу; цены в долларах
только как `\$NN` / `USD NN` / backtick (никакого чистого `$NN`).

**Pre-emit checklist (обязательный self-check ДО сохранения файла).**
Stage 5 обязан прогнать checklist'и из `references/stage5/stage5-final.md`
§6.7 ДО emit. 8 классов:

- **Класс A — Stage 4 consistency + Stage 0 чтение:** все дни выбранного
  варианта присутствуют; правки применены; формулировка крайних дней
  по `home_eq_start`; mode объявлен; решения Stage 0/3/4 не пересмотрены;
  **`0_scope.md` прочитан если файл существует** (точные даты,
  `home_city`, `trip_start_city`, `pre_committed_places`, `trip_wishes`
  — взяты как факт); молчаливая подстановка «представительных дат» при
  наличии 0_scope.md — нарушение.
- **Класс B — TODO discipline + budget heuristic:** каждая цена отеля

  или web search ссылка; международный перелёт только при
  `home_eq_start == false`; `todo_verification_items` в YAML совпадает;

  расписания транспорта со ссылкой или TODO; MCP-цены с датой запроса;
  **рейтинг для каждого отеля, в первую очередь для основного
  именованного кандидата** (web search для рейтинга основного → потом
  для альтернатив; «нашёл для альтернатив, основной TODO» — нарушение,
  перепрогнать); **time-of-day sanity для активностей** (старт
  скорректирован под время в пути и достижимое окно работы); **TODO
  операторов с платформой поиска** (Klook / GetYourGuide / Viator /
  vexere / 12go / etc.), голое «TODO выбрать оператора» без направления

- **Класс D — логистика и риски:** каждый переезд имеет транспорт +
  время + способ бронирования + диапазон стоимости; узкие звенья из
  Stage 4 сохраняют swap-стратегию; synergy-пары как «комбо у оператора

- **Класс E — формат и YAML:** долларовые цены escape'нуты; YAML три
  дефиса; имя файла `5_final_plan.md`; нет «опущено for brevity»; нет

- **Класс F — Diff, TODO summary, чеклист:** Diff заполнен если
  `previous_plan != null`; секция TODO содержит все TODO из тела;

  источники проверки** (JTWC / Windy / cbr.ru / met-service страны /
  ...).
- **Класс G — дисциплина заполнения дня + хореография прилёта/вылета
  (F-49/F-61):** каждый день имеет POI на утро И на день (пустой полудень

  явно (прямой / технический / с ночёвкой).
- **Класс P — enforcement пользовательских комментариев (F-54):**

## Что НЕ делает этот скилл

- Не пишет в `{travel_root}` автоматически — на каждом выходе markdown в чат,
  пользователь сохраняет руками.
- Не оркестрирует Deep Research — Stage 1 выдаёт промт, пользователь запускает
  DR сам в отдельной сессии.
- Не ищет авиабилеты, не бронирует отели, не выдумывает цены. Любые цифры
  по отелям и местам, не проверенные на Booking/Trip.com или локальных
  агрегаторах — помечаются как TODO.
- Не пересчитывает старые поездки при обновлении профиля. Если профиль
  изменился — предупреждает, но автоматически не перегенерирует.
- Не помогает на месте во время поездки.
- Не выбирает «лучший вариант» за пользователя — показывает тредофы,
  финальный выбор идёт в блок `## Решение` выходного файла.
