# storage-and-naming.md

Полная спецификация хранилища, путей, имён и YAML-шапок для скилла
`travel-planning`. Этот файл — **единственная точка**, в которой
описаны транспорт, конвенции и операции чтения/записи. SKILL.md и
stage-references обращаются к хранилищу абстрактно (`{travel_root}/...`),
любые правки инфраструктуры выполняются только здесь.

## 1. Резолв `{travel_root}`

`{travel_root}` — корневая папка travel-planner внутри хранилища. Резолвится
в момент первой файловой операции в сессии. Транспорт один — Synology mount;
если он недоступен, единственный источник входных данных — файлы,
приложенные пользователем к чату.

**Только этот путь.** Артефакты поездок ищутся и пишутся исключительно в
`{travel_root}`. Коннекторы облачных дисков (Google Drive и др.), папки
«Документы» и подключённые рабочие папки как источник плана не используются —
даже если папки `trips/{trip_id}/` не нашлось по ожидаемому имени: сначала
`Glob("{travel_root}/trips/*")` и сверка с названием поездки; не нашлось —
сообщить пользователю и попросить путь, а не искать по другим хранилищам.

### 1.1 Synology mount

Путь: `~/Library/CloudStorage/SynologyDrive-home/Claude-Memory/travel-planner/`

Доступ — через стандартные файл-тулзы (`Read`, `Write`, `Edit`, `Glob`).
Дерево живёт на NAS (`/volume1/homes/hubuser/Claude-Memory`), вне облачных
синков; Mac-зеркало — его локальная проекция.

Проверка доступности:

```
Glob("~/Library/CloudStorage/SynologyDrive-home/Claude-Memory/travel-planner/**/*.md")
```

Если возвращает результат (даже пустой список без ошибки) — Synology
доступен.

### 1.2 Запрос Cowork-доступа

Если `Glob` к Synology возвращает ошибку доступа — это означает, что
в Cowork-режиме пользователь не предоставил доступ к этой папке.
Запросить доступ ОДИН раз:

```
mcp__cowork__request_cowork_directory
  с просьбой выбрать папку
  ~/Library/CloudStorage/SynologyDrive-home/Claude-Memory/travel-planner/
  (или родительскую Claude-Memory/)
```

После предоставления доступа повторить `Glob` — должно работать.

Признак песочницы: пути вида `/mnt/...`, папки подключены под именами вроде
`SynologyDrive-home--Путешествия`, а `~/Library/CloudStorage/...` отсутствует.
Подключённая папка «Путешествия» — не `{travel_root}` (там билеты, ваучеры и
устаревшие копии `trips/`, в которых нет свежих поездок). В этом случае сразу
запросить доступ к `Claude-Memory/travel-planner/` (шаг выше); не нашёл папку
поездки по имени — НЕ делать вывод «плана нет» по чужим папкам, а перейти к
§1.4 и попросить приложить файлы либо выдать доступ.

### 1.4 Transport gate

**Когда срабатывает.** Если хотя бы один из требуемых входных файлов
(см. SKILL.md «Активационные gate'ы» для конкретной стадии):

- **не приложен** к чату пользователем, И
- **не читается из Synology** (mount отсутствует, или возвращает ошибку
  доступа, или Cowork-доступ к папке не выдан) —

то скилл **обязан остановиться** и вывести сообщение пользователю.

**Шаблон сообщения:**

```
Не могу получить входные файлы.

Не приложено к чату:
- {file_a} ({что_это})
- {file_b} ({что_это})

Synology mount недоступен (или Cowork-доступ к папке не выдан).

Варианты — выбери один:

1. **Приложить файлы.** Ответь следующим сообщением, приложив
   {file_a} и {file_b} напрямую к чату.

2. **Починить доступ к Synology** (выдать Cowork-доступ / проверить mount)
   и сказать «повтори».

Стоп.
```

**Если пользователь приложил файлы** — повторно проверить gate-список;
если всё на месте, продолжить. Если приложено частично — повторить
сообщение с обновлённым списком недостающего.

### 1.5 Кэширование выбора в рамках сессии

После первого успешного резолва источника входа (Synology / приложенные
файлы) зафиксировать его на всю сессию — это исключает рассинхрон при
параллельных правках.

### 1.6 NAS первичен, Mac-зеркало — кэш (web-правки)

Артефакты Stage 3–6 правятся с веба (теги/комментарии POI, варианты,
отметки подготовки). Штатно web-правки доезжают до зеркала за секунды
(File Station-гибрид сайдкара, 2026-08-13), но при отказе гибрида
(DSM недоступен) запись ложится на NAS локально — тогда зеркало отдаёт
версию БЕЗ последних web-правок до перезапуска Drive Server. Перед
перезаписью артефакта, который пользователь недавно трогал с веба,
при сомнении предупредить о возможной несвежести зеркала; эталон —
файл на NAS (виден через страницу travel).

## 2. Структура и базовые конвенции

```
{travel_root}/
├── README.md                                        # короткий гайд по структуре
├── profiles/
│   ├── {profile_id}.md
│   └── ...
└── trips/
    ├── {trip_id}/
    │   ├── trip.yaml                                # мета-карточка поездки (§2.3)
    │   ├── 0_scope.md                               # stable
    │   ├── 1_dr_reports.md                          # stable
    │   ├── 2_similarity.md                          # stable
    │   ├── 3_poi_pool.md                            # stable (mutable: теги под регионами)
    │   ├── 4_variants_v1.md                         # versioned mutable
    │   ├── 5_final_plan_v1.md                       # versioned mutable
    │   ├── 4_variants_v2.md                         # последующая итерация
    │   ├── 5_final_plan_v2.md
    │   ├── _archive/                                # автоархив старых итераций при N ≥ 4
    │   │   ├── 4_variants_v1.md
    │   │   └── 5_final_plan_v1.md
    │   ├── 5_{trip_id}_финальный_план_v2_для_родителей.pdf   # экспорт (§4.2)
    │   ├── 4_{trip_id}_варианты_v2.pdf
    │   ├── 2_{trip_id}_похожие_авторы.html
    │   └── ...
    ├── {trip_id_2}/
    └── ...
```

**Общие правила:**

- Имена md-файлов стадий — **фиксированные английские**. Stage 0-3 без
  суффикса (один файл per trip). Stage 4 / Stage 5 — с суффиксом
  `_v{N}` (versioned itterations). Это даёт детерминированный `Glob`
  для любой стадии и любой итерации.
- Имена `profile_id` и `trip_id` — **lowercase русскими буквами**,
  словоразделитель `_` (underscore).
- Имена экспортов — **русские**, описательные, lowercase.
- Все даты — ISO `YYYY-MM-DD` или `YYYY-MM` без точек и слэшей.
- Кодировка — UTF-8, перевод строк — LF.
- Дефис используется только внутри ISO-даты. Внутри имён — только `_`.

### 2.1 Stable / mutable / versioned разрез

Артефакты в `trips/{trip_id}/` делятся на три класса:

| Класс | Файлы | Кто правит |
|---|---|---|
| **Stable** (не правится между итерациями) | `0_scope.md`, `1_dr_reports.md`, `2_similarity.md` | Только при полном перепрогоне с нуля. Не правится при iteration loop. |
| **Stable с user-mutable частью** | `3_poi_pool.md` | Скилл генерирует, пользователь дописывает `**тег:** ...` под региональными заголовками, опц. `**Комментарий к региону:** ...` в шапке региона и `Комментарий пользователя:` под POI. Между итерациями теги/комментарии можно менять. |
| **Versioned mutable** | `4_variants_v{N}.md`, `5_final_plan_v{N}.md` | Новый файл при каждой итерации. В `4_variants_v{N}.md` пользователь заполняет `## Решение` и опц. `## Комментарии к вариантам`. Latest `v{max(N)}` — актуальный; старые сохраняются как история. При `N ≥ 4` — автоархив в `_archive/`. |

### 2.1b `внешние_справки/` — материал для чтения, не артефакт стадии

Подпапка поездки под длинные справки: исторические сводки, тематические обзоры,
всё, что читают **до** поездки дома, а не с телефона в пути. Файлы там ничем не
ограничены по объёму, но обязаны нести источники — жанр (история, «первый /
старейший») даёт наибольшую долю уверенных ошибок.

Два жёстких правила:

- **Не класть в корень поездки с цифрой стадии.** Вьюер и экспортёр разбирают
  корень по маске `^[0-6][_ ]`, и такой файл станет конкурирующим артефактом
  стадии: попадёт в `buildStages`, может вытеснить настоящий экспорт и уехать
  в документ. Подпапка обходит это целиком — листинги пропускают директории.
- **Не путать с `## Углубления` Stage 6.** Там — короткая выжимка (≤5
  предложений на блок, гейт в `polish_check.py`), здесь — полный текст.
  Связь односторонняя: выжимка может ссылаться на файл справки, не наоборот.

Имя — свободное, с датой сбора: `внешние_справки/история_ханоя_2026-09-03.md`.
Версионирования нет: справка либо актуальна, либо переписывается целиком.

Iteration loop работает так: пользователь правит `**тег:** ...` в `3_poi_pool.md`,
запускает Stage 4 → создаётся `4_variants_v{N+1}.md`. DR (Stage 1) и similarity
(Stage 2) не пересобираются — дорогие шаги изолированы от iteration.

### 2.2 Schema version

YAML-шапка каждого артефакта содержит поле `schema_version: N` для
совместимости. При несовпадении версии при чтении — скилл предлагает
миграцию или полный перепрогон с нуля.

### 2.3 `trip.yaml` — машиночитаемая карточка поездки

Каждая директория `trips/{trip_id}/` содержит `trip.yaml` — компактную
мета-карточку поездки. Её читают внешние потребители (индексы, дашборды),
которым не нужно парсить артефакты стадий. Только **плоские** ключи —
без вложенных структур:

```yaml
schema: trip-meta@1
title: Северный Вьетнам        # человекочитаемое название поездки
status: planning               # см. таблицу ниже
travelers: [мария, алексей]    # имена участников, lowercase
season: "2026-09"              # YYYY-MM или YYYY (кавычки обязательны)
start: 2026-09-14              # необязательно: первый день поездки (YYYY-MM-DD)
end: 2026-09-27                # необязательно: последний день поездки (YYYY-MM-DD)
updated: 2026-07-10            # дата последнего изменения карточки
```

**Точные даты `start` / `end`.** Необязательные, только парой; `end` не раньше
`start`; формат `YYYY-MM-DD` без кавычек. Ставятся, когда даты дней известны
точно — при принятии финального плана (Stage 5): `start` — дата первого дня,
`end` — последнего. Пока дат нет, ключей нет вовсе (не пустые значения, не
`TODO`): поездка без точных дат — нормальное состояние, о ней известен только
`season`. Для поездок, принятых раньше, даты достаёт
`python3 scripts/trip_dates.py trips/{trip_id}` из файла Stage 5 и печатает
строки для вставки.

| `status` | Когда |
|---|---|
| `planning` | поездка прорабатывается (дефолт с момента Stage 0) |
| `ready` | финальный план устаканен, к поездке готовы |
| `done` | поездка состоялась |
| `superseded` | проработка вытеснена другой директорией (`{trip_id}` пересоздан) |

**Жизненный цикл:** Stage 0 создаёт `trip.yaml` (`status: planning`,
`title` — из формулировки пользователя, `travelers` — из профиля,
`season` — из scope). Дальше карточка **обновляется при смене статуса**:
финальный план принят → `ready` (и `start`/`end`, если у дней есть даты);
после поездки → `done`; при пересоздании
поездки в новой директории у старой → `superseded`. При любом обновлении —
освежить `updated`.

Как и все артефакты — manual save: скилл выдаёт содержимое, сохраняет
пользователь. При работе с существующей поездкой без `trip.yaml` —
предложить создать его по данным `0_scope.md`.

**Pre-emit проверка.** Перед выдачей `trip.yaml` прогони содержимое через
`check_format.check_trip_meta` (обязательные поля, enum `status`, `season`
строго в кавычках `"YYYY-MM"`/`"YYYY"`, `travelers` flow-списком, `start`/`end`
парой в формате `YYYY-MM-DD` и по порядку) и `check_format.trip_meta_warnings`
(`ready` без месяца в `season`; месяц `start` не совпадает с `season`) — либо
сверь глазами по этому же списку. Незакавыченный `season` YAML-парсеры
читают как число/дату — это молча ломает потребителей.

## 3. `profile_id` и `trip_id`

### 3.1 `profile_id`

Идентификатор профиля путешественника или группы. Формат: lowercase русскими
буквами, словоразделитель `_`.

| Случай | Шаблон | Пример |
|---|---|---|
| Один человек | `имя` | `иван`, `анна` |
| Пара | `имя_имя` | `иван_анна` |
| Семейная группа | `имя_группа` | `иван_родители`, `анна_сестра` |
| Друзья | `имя_группа` | `иван_друзья_2026`, `иван_альпинисты` |

Имя файла: `profiles/{profile_id}.md`.

### 3.2 `trip_id`

Идентификатор поездки. Базовый шаблон:

```
{назначение}[_{детализация}]_{YYYY-MM}
```

Где:

- **`назначение`** — страна или крупный регион, одно слово.
- **`детализация`** *(опционально)* — гибкий слот, добавляется при
  необходимости. Может быть:
  - географический скоуп: `север`, `юг`, `столичный`, `горный`, `полный`
  - идентификатор спутников (если состав отличается от дефолтного):
    `родители`, `соло`, `с_детьми`
  - комбинация: `север_соло`, `столичный_родители`
- **`YYYY-MM`** — год и месяц начала поездки.

Примеры формата:

| trip_id | Расшифровка |
|---|---|
| `<назначение>_<YYYY-MM>` | минимальная форма |
| `<назначение>_<деталь>_<YYYY-MM>` | с уточнением скоупа или состава |
| `<назначение>_<деталь>_<деталь>_<YYYY-MM>` | составная детализация |

**Когда добавлять `детализацию`:**

- Поездка покрывает только часть страны и важно это зафиксировать в имени.
- Состав спутников отличается от дефолтного (`иван_анна`) — добавить
  `родители` / `соло` / другое.
- Иначе — опускать. Лишний слот = шум.

Если возникает коллизия (две поездки в одно направление в один месяц с
одинаковой детализацией) — добавить дискриминатор после года:
`грузия_соло_2026-05_а`, `грузия_соло_2026-05_б`.

### 3.3 Транслит

Конвенция — русские буквы. Транслит латиницей не используется ни в
`profile_id`, ни в `trip_id`, ни в экспортах. macOS Finder и Synology Drive
корректно обрабатывают кириллицу в путях.

Для составных географических имён — соединять `_`: `центральная_азия`,
`шёлковый_путь`, `средиземноморье`.

## 4. Имена файлов стадий и экспортов

### 4.1 Стадии — фиксированные английские имена

| Стадия | Имя файла | Класс |
|---|---|---|
| Stage 0 | `0_scope.md` | stable |
| Stage 1 | `1_dr_reports.md` | stable |
| Stage 2 | `2_similarity.md` | stable |
| Stage 3 | `3_poi_pool.md` | stable + user-mutable теги/комментарии |
| Stage 4 | `4_variants_v{N}.md` | versioned mutable |
| Stage 5 | `5_final_plan_v{N}.md` | versioned mutable |
| Stage 6 | `6_final_v{N}.md` | versioned mutable |

Имена фиксированы и одинаковы для всех поездок. Это позволяет любой стадии
найти артефакты предыдущих по детерминированному пути:
- Stage 0-3: `Glob("trips/{trip_id}/{N-1}_*.md")` — один файл per trip.
- Stage 4/5/6: `Glob("trips/{trip_id}/{N-1}_*_v*.md")` → latest версия
  определяется по `max(N)` в имени.

**Stage 6 ≠ Stage 5 (важно).** `6_final.md` — ОТДЕЛЬНЫЙ файл; Stage 6 **не
редактирует** `5_final_plan.md` (тот immutable SSOT маршрута). `6_final.md`
хранит ТОЛЬКО добавки Stage 6 (координаты маршрута + дорожное досье + дельты
брони + углубления), а не повторяет день-за-днём контент Stage 5. Финальный
PDF собирается механически на экспорте = рендер 5_vX (билдеры stage5.py) +
карта + досье/бронь/углубления. См. `references/stage6/stage6-final.md`.

При первой итерации создаются `4_variants_v1.md` и `5_final_plan_v1.md`.
При следующих — `v2`, `v3`, ... `_archive/` подпапка появляется
автоматически при `N ≥ 4` (старые версии перемещаются туда).

**Legacy compat:** артефакты v0.22 и ранее использовали `3_poi_aggregation.md`,
`4_variants.md`, `5_final_plan.md` (без `_v{N}`). При чтении такого
артефакта скилл интерпретирует как v1 + предлагает миграцию. Текущее имя
файла Stage 3 — `3_poi_pool.md`; внутренний YAML-идентификатор `stage:`
остаётся `3_poi_aggregation` (на нём завязан export-слой) — это норма,
не рассинхрон.

### 4.2 Экспорты — единая trip-ориентированная схема

Лежат **в той же папке** `trips/{trip_id}/`, рядом с md-файлами. Отдельной
подпапки `exports/` нет.

**Единый шаблон для всех стадий** (2026-06-01):

```
{stage}_{trip_id}_{описание}[_v{N}][_получатель].{ext}
```

| Слот | Значение |
|---|---|
| `stage` | `0` / `1` / `2` / `3` / `4` / `5` — номер стадии (первым сегментом) |
| `trip_id` | `{страна(ы)}_{YYYY-MM}` (например `камбоджа_лаос_2026-02`) — несёт регион и дату/месяц поездки |
| `описание` | lowercase русскими буквами через `_` (см. таблицу ниже) |
| `_v{N}` | только для версионируемых стадий (4/5); 0/1/2/3 — без версии |
| `_получатель` | опц. суффикс (`_для_родителей`); для self — опускается |
| `ext` | `pdf` / `docx` / `html` / `pptx` / `xlsx` |

Дата генерации **в имя не выносится** — она в футере документа; дата/месяц
*поездки* уже внутри `trip_id`. `trip_id` берётся из YAML-шапки артефакта.

Дефолтные описания по стадиям:

| Stage | Описание | Пример имени |
|---|---|---|
| 0 | `регионы` | `0_камбоджа_лаос_2026-02_регионы.pdf` |
| 1 | `dr_отчёты` | `1_камбоджа_лаос_2026-02_dr_отчёты.pdf` |
| 2 | `похожие_авторы` | `2_камбоджа_лаос_2026-02_похожие_авторы.pdf` / `.html` |
| 3 | `места` | `3_камбоджа_лаос_2026-02_места.docx` |
| 4 | `варианты` | `4_камбоджа_лаос_2026-02_варианты_v1.pdf` |
| 5 | `финальный_план` | `5_камбоджа_лаос_2026-02_финальный_план_v1.pdf` |
| 6 | `финал` | `6_камбоджа_лаос_2026-02_финал_v1.pdf` |

Получатель — часть описательного имени, не структурный слот:
`5_корея_2024-03_финальный_план_v1_для_родителей.pdf`.

**Все форматы одной стадии делят ОДНУ основу имени, различаясь только `{ext}`**
(`2_{trip_id}_похожие_авторы.pdf` = `….docx` = `….html`). HTML — НЕ исключение:
ведущая цифра стадии обязательна во всех форматах. Именно по префиксу `{stage}_`
травел-окно Personal Hub (`tools/travel.html`, `stageOf` = `/^([0-6])[_ ]/`)
распознаёт стадию файла; имя без цифры (напр. `{trip_id}_регионы.html`) не
распознаётся и файл не показывается. Контракт «имя экспорта ↔ `stageOf`»
закреплён `tools/tests/test_pages_contracts.py`.

Stage 6 экспорт-описание — `финал` (короче «финального_плана» Stage 5; это
ideal-сборка план + карта + досье, не дубль). Versioned `_v{N}` как 4/5.

Реализация — `scripts/export/file_naming.py`: общий `build_trip_doc_filename`
(параметр `stage` префиксует номер) + per-stage обёртки
(`build_scope_filename` … `build_final_plan_filename` … `build_final_filename`
для Stage 6). Round-trip import
(`export.py:_identify_import`) определяет стадию по префиксу `{stage}_` и
описанию-суффиксу; совместим со старым форматом без префикса.

**Legacy generic** (`build_export_filename`, с датой
`{stage}_{имя}_{YYYY-MM-DD}.{ext}`) сохранён как fallback для стадий вне
основного набора, но per-stage экспорты используют trip-схему выше.

### 4.3 Стадии без артефакта

`1_dr_reports.md` для конкретной поездки может отсутствовать, если
пользователь решил не сохранять сырой DR-выход. Тогда Stage 2 работает на
временно приложенном файле в чате. Но в большинстве кейсов рекомендуется
сохранять — переиспользуется при перезапусках Stage 2 с другими весами.

## 5. YAML frontmatter — общая спецификация

Каждый markdown-файл (профили, артефакты стадий) начинается с YAML-шапки.
Назначение: следующая стадия должна понять контекст, прочитав только шапку,
без парсинга тела документа.

**Разделитель блока — строго ровно три дефиса `---`**, и сверху, и снизу.
Не `-----` (пять дефисов) и не любое другое число. На разделителе
`-----` markdown-рендеры могут отрисовать поля шапки как продолжение
списка предыдущего поля (поля «уезжают» под `input_files:`), и downstream-
стадии не парсят такую шапку. Будь аккуратен на любом артефакте.

### 5.1 Поля для всех артефактов поездки

Имена полей — английские (технические ключи). Значения — русские, где
применимо. Это даёт читаемый YAML и предсказуемый парсинг.

| Поле | Тип | Описание |
|---|---|---|
| `trip_id` | string | Идентификатор поездки (русскими) |
| `stage` | string | `0_scope` / `1_dr_reports` / `2_similarity` / `3_poi_aggregation` / `4_variants` / `5_final_plan` |
| `travelers_profile` | string | Относительный путь от `{travel_root}`: `profiles/{profile_id}.md` |
| `created` | YYYY-MM-DD | Дата создания файла |
| `updated` | YYYY-MM-DD | Дата последнего обновления (если ≠ created) |

### 5.2 Поля для профилей

| Поле | Тип | Описание |
|---|---|---|
| `profile_id` | string | Идентификатор (русскими) |
| `created` | YYYY-MM-DD | — |
| `updated` | YYYY-MM-DD | — |

Полная спека профиля — в `references/profile-management.md`.

### 5.3 Stage-специфичные поля

Каждая стадия добавляет свои поля. См. §6.

## 6. YAML frontmatter — по стадиям

Примеры приведены на двух поездках пары `иван_анна` —
`перу_2027-09` (Север Вьетнама) и `непал_2027-10`
(Огненная Земля + Лос-Гласьярес). Значения полей — русские, где это
естественно.

### 6.1 Stage 0 — scope

```yaml
---
trip_id: непал_2027-10
stage: 0_scope
schema_version: 2
iteration: 1
travelers_profile: profiles/иван_анна.md
created: 2027-01-15
duration_nights: 13
season: осенний_трекинговый_сезон_2027
trip_format: multi_region_tour          # multi_region_tour | single_base | explicit_list
home_city: <город>
trip_start_city: <город>                 # дефолт = home_city
home_eq_start: true
tempo: balanced
longlist:                                # 6–8 регионов с reserve (НЕ финальный выбор)
  - { region: <регион_1>, role: core, nights_optimum: 3, reserve_for: null }
  - { region: <регион_2>, role: supporting, nights_optimum: 3, reserve_for: null }
pre_committed_places: [<город_въезда>, <обязательное_место_1>]
trip_wishes: ["<пожелание вербатим из запроса>"]
total_regions_analyzed: 9
---
```

Это сводка ключевых полей. **Каноническая полная v2-схема** (все поля
`longlist`, `universe_summary`, `excluded_regions`, `country_quota`,
`content_density_overrides`, `non_canonical_regions`) — §8 в
`stage0/stage0-scope.md`. Поля `selected_regions` (v1) больше нет:
финальный выбор регионов делается тегами после Stage 3, не в Stage 0.

### 6.2 Stage 1 — DR reports

```yaml
---
trip_id: перу_2027-09
stage: 1_dr_reports
travelers_profile: profiles/иван_анна.md
regions:
  - <регион_1>
  - <регион_2>
  - <регион_3>
  - <регион_4>
season: сухой_сезон_2027
dr_run_date: 2027-07-15
reports_count: 23
meta_diagnostics_warnings:
  - "60% отчётов от само-организованных туров (sample bias)"
# опц. — только если запускался Mode B (довыборка). Провенанс решений,
# чтобы база воспроизводилась с диска (какие источники добавлены/отброшены и почему):
mode_b_decisions:
  submodes: [b1_awd, b2_lists]        # какие под-режимы запускались
  scope_filter: "<решение по off-scope: B1/B2/B3 или прозой>"
  added: {dr_agent: 20, b1_awd: 3, b2_lists: 0}   # карточек по происхождению
  awd_themes: [<id>, ...]             # ID тем forum.awd.ru (если был b1)
  dropped:                            # что отброшено и почему
    - "<например: 12 off-scope (Ха-Зянг loop); 2 дубля по URL>"
created: 2027-07-15
---
```

`mode_b_decisions` отсутствует/null, если был только Mode A (чистый DR без
довыборки). Поле LLM-заполняемое (решения — судебная зона LLM); счётчики
карточек и `reports_count` остаются за `merge_dr_additions.py`. Скрипт merge
сохраняет блок дословно при повторном merge (неизвестные top-level ключи
проходят насквозь).

### 6.3 Stage 2 — similarity

```yaml
---
trip_id: перу_2027-09
stage: 2_similarity
travelers_profile: profiles/иван_анна.md
input_file: 1_dr_reports.md
high_similarity_count: 6
medium_count: 9
low_count: 5
outlier_count: 3
unscored_count: 1
total_authors: 24
weights_used: [25, 25, 15, 10, 15, 10]

  high: 7.0

  - "HIGH = 6 (< 8): выборка пограничная, рассмотри расширение источников"

---
```

Поля `unscored_count`, `total_authors`, `weights_used`, `thresholds_used`
— опциональные при чтении: старые Stage 2 файлы без них остаются
валидными.

**Opt-in LLM-fallback при ошибках парсера.** Если
`parse_dr_cards.py` диагностика выдала `status=error` и пользователь
выбрал вариант 1 или 2 (см. `stage2/stage2-similarity.md` §9.12), YAML
дополняется соответственно:

```yaml
# Вариант 1: LLM-fallback
partial_parse: true
llm_fallback_authors: ["peru-2027-09-017", "peru-2027-09-023"]
parse_diagnostic_at_run:
  status: error
  issues_summary: "3/39 без URL; формат поля 1 не распознан"

# Вариант 2: пропущенные
skipped_authors_count: 3
skipped_authors: ["peru-2027-09-017", ...]
parse_diagnostic_at_run:
  status: error
  issues_summary: "..."
```

Эти поля — опциональные, появляются только при наличии проблем парсера.
При `status=ok` или `warning` без user-action они не добавляются.

### 6.4 Stage 3 — POI aggregation

```yaml
---
trip_id: перу_2027-09
stage: 3_poi_aggregation
travelers_profile: profiles/иван_анна.md
input_files:
  - 1_dr_reports.md
  - 2_similarity.md
created: 2027-07-20
total_pois: 87
strong_confirmed: 14
weak_confirmed: 22
hidden_gems: 9
contested: 6
red_flags: 4
low_signal: 32
aggregation_mode: abundant
chosen_similarity_run: 2_similarity.md
previous_plan: null
warnings:
  - "RED FLAG 31% — структурный конфликт профиля с выборкой"
---
```

Счётчики категорий (`strong_confirmed` … `low_signal`) и `total_pois`
возвращает `aggregate_pois.py` одним JSON — они должны совпадать с
таблицей распределения в теле файла. Сумма шести счётчиков == `total_pois`.

`aggregation_mode` — режим категоризации Stage 3 (`abundant` / `scarce`),
берётся из `aggregates.mode` скрипта. См. `stage3/stage3-poi.md` §6.5.

Опциональные поля:

- `chosen_similarity_run` — какой Stage 2 файл использован
  (`2_similarity.md` по умолчанию; `2_similarity_alt.md` при повторном
  прогоне Stage 2 с другими весами — см. §10.5).
- `previous_plan` — путь к предыдущему плану поездки, если он есть; при
  наличии Stage 3 добавляет раздел сравнения. `null` — раздела нет.
- `details_file` — если выход разбит на два файла (большая выборка) —
  ссылка на `3_poi_pool_details.md`.
- `skipped_pois_count` — добавляется только если при
  `diagnostic.status=error` пользователь выбрал пропуск проблемных POI
  (см. `stage3/stage3-poi.md` §9.9).
- `iconic_exceptions` — число POI с флагом `iconic_exception.present=true`
  (`aggregates.iconic_exceptions` из скрипта). См.
  `stage3/stage3-poi.md` §6.8.
- `synergy_pairs` — число POI с непустым `commonly_combined_with`
  (`aggregates.synergy_pairs` из скрипта). См.
  `stage3/stage3-poi.md` §6.9.
- `trip_id_warning: mixed_script` — при смешанном trip_id (§10.8).

### 6.5 Stage 4 — variants

```yaml
---
trip_id: непал_2027-10
stage: 4_variants
schema_version: 2
iteration: 1
travelers_profile: profiles/иван_анна.md
input_files: [3_poi_pool.md, profiles/иван_анна.md]
created: 2025-01-22
duration_nights: 13
aggregation_mode_inherited: scarce       # из YAML Stage 3
budget_target_rub: 400000                # «## Бюджет» × длительность
home_eq_start: true
international_flight_context: { direct_to_entry: false, expected_hubs: [<хаб>], approx_one_way_hours: 14 }
variants:                                # SSOT shape-данных для Stage 5
  - { name: A, chosen_regions: [{region: <регион>, nights: 3}], region_order: [<регион>], transport_segments: [{from: <X>, to: <Y>, type: bus}], cost_rank: "$$", red_flags: [] }
warnings: ["..."]
---
```

Выбор варианта — в теле, блок `## Решение` (`**Выбран вариант:**`,
заполняет человек руками); поля `chosen_variant` в YAML Stage 4 нет.

Расширенная схема Stage 4 — все поля **опциональные при чтении
downstream** (старые файлы без новых полей остаются валидными).
Детальное описание каждого поля — §8 в `stage4/stage4-variants.md`;
ключевые:

- `variants[]` — SSOT shape для Stage 5: `chosen_regions`, `region_order`,
  `transport_segments`, `cost_rank` (`$ / $$ / $$$`), `red_flags`.
- `aggregation_mode_inherited` — режим Stage 3 (`abundant` / `scarce`);
  Stage 5 не трактует WEAK-категории как сильные при `scarce`.
- `budget_target_rub` — из секции `## Бюджет` профиля (RUB/неделю ×
  `duration_nights / 7`); опц. `budget_target_rub_with_flex` при вилке ±N%.
- `international_flight_context` — `direct_to_entry` / `expected_hubs` /
  `approx_one_way_hours` для arrival/departure choreography Stage 5.
- `previous_iteration` (или legacy `previous_plan`) — путь к предыдущему
  `4_variants_v{N-1}.md` для diff-секции.

Бюджет Stage 4 — относительный `cost_rank`, не рублёвый статус; поля
`budget_status_overall` / `over_budget_variants` / `recommended_balanced`
(v1) убраны — точный бюджет считает Stage 5.

Опциональные поля:

- `details_file` — если выход разбит на два файла (большая поездка,
  3 варианта × 18+ ночей не помещается) — ссылка на
  `4_variants_part_b.md` (`stage4/stage4-variants.md` §9.11).
- `trip_id_warning: mixed_script` — при смешанном trip_id (§10.8).

### 6.6 Stage 5 — final plan

```yaml
---
trip_id: непал_2027-10
stage: 5_final_plan
travelers_profile: profiles/иван_анна.md
mode: reconstructive                     # или surgical — детектируется скиллом
input_files:
  - 4_variants.md
  - profiles/иван_анна.md
previous_plan: null                       # путь к предыдущему плану или null
chosen_variant: вариант_б                 # нормализованный (вариант_а/б/в/кастомный)
chosen_variant_raw: "B"                   # raw label из ## Решение Stage 4
duration_nights: 13
total_budget_rub: 400000                  # сумма дневных диапазонов midpoint
budget_target_rub: 186000                 # унаследовано из Stage 4
budget_status: on_target                  # under_target | on_target | over_10_20 | over_20+
todo_verification_items: 9                # счёт TODO в секции ## TODO
home_eq_start: true                       # унаследовано из Stage 0
aggregation_mode_inherited: scarce        # унаследовано из Stage 3/4
web_search_used: true                     # был ли активный поиск
mcp_extensions_used: []                   # ["booking"], ["expedia"], ["booking","expedia"], или []
clarification_used: false                 # был ли opt-in clarification round
created: 2025-01-28
warnings: []
---
```

Расширенная схема Stage 5 — все поля ниже **опциональные при чтении
downstream** (Export mode), но фиксируются при создании файла.

Поля схемы:

- `mode` — `surgical` / `reconstructive`, детектируется детерминированно
  в `references/stage5/stage5-final.md` §6.1. `surgical` — структура
  совпадает с `previous_plan` (тот же набор регионов + ±0 ночей);
  `reconstructive` — иначе.
- `previous_plan` — путь к предыдущему плану поездки, если есть.
  Используется для mode detection и опционально для секции
  `## Diff с предыдущим планом`.
- `chosen_variant` — нормализованный (`вариант_а`/`вариант_б`/
  `вариант_в`/`кастомный`); парсится из блока `## Решение` Stage 4.
- `chosen_variant_raw` — raw label из `**Выбран вариант:**` блока
  `## Решение` (`A`/`B`/`C`/`кастомный`). Для traceability.
- `total_budget_rub` — расчёт LLM из дневных диапазонов midpoint +
  ночёвки midpoint + внутренний транспорт. Международный перелёт
  включается только при `home_eq_start == false`.
- `budget_target_rub` — унаследовано из YAML Stage 4.
- `budget_status` — `total_budget_rub` vs `budget_target_rub`:
  - `under_target`: total ≤ 0.9 × target;
  - `on_target`: 0.9 × target < total < 1.1 × target;
  - `over_10_20`: 1.1 × target ≤ total < 1.2 × target;
  - `over_20+`: total ≥ 1.2 × target.
- `todo_verification_items` — счёт всех TODO в секции `## TODO для
  верификации` (3 категории: before-booking, 2-weeks-before, in-trip).
- `home_eq_start` — унаследовано из YAML Stage 0; влияет на формулировку
  крайних дней маршрута и включение международного перелёта в total.
- `aggregation_mode_inherited` — унаследовано из YAML Stage 3/4; для
  downstream consistency check (Export mode не должен делать выводов о
  «силе» категорий без учёта режима).
- `web_search_used` — bool. Был ли активный web search на стадии (для
  расписаний/операторов/отелей/часов работы).
- `mcp_extensions_used` — список использованных MCP-коннекторов для
  цен отелей. Пустой список `[]` — стандартный режим без MCP. Допустимые
  значения: `booking`, `expedia` (другие имена при появлении). См.
  `references/stage5/stage5-final.md` §6.4 «Опц. MCP-расширения».
- `clarification_used` — bool. Был ли opt-in clarification round
  (§9.4 stage5-final.md) для конфликтующих со структурой правок.

Опциональные поля:

- `details_file` — при split на два файла (большие планы, ≥18 ночей,
  не помещается в один ответ) — ссылка на
  `5_final_plan_part_b.md`. См. stage5-final.md §9.10.
- `trip_id_warning: mixed_script` — при смешанном trip_id (§10.8).
- `incomplete_sections` — список секций профиля, которых не хватает
  (например, `["payment_infrastructure"]` если `## Платёжная
  инфраструктура` пустая в профиле — Stage 5 продолжает с TODO-меткой).

**Парсинг блока `## Решение` Stage 4.**

Stage 5 на старте семантически парсит `## Решение` блок из
`4_variants.md`:

1. **`**Выбран вариант:**`** — обязательно. Допустимые значения
   (lowercase): `a`, `b`, `c`, `кастомный`. Нормализуется в
   `chosen_variant` (`вариант_а`/`вариант_б`/`вариант_в`/`кастомный`);
   raw label сохраняется в `chosen_variant_raw`.
2. **`**Состав:**`** (опц.) — текстовое описание состава; может
   содержать правки (замена формата активности, добавление,
   удаление, уточнение).
3. **`**Почему этот выбор:**`** (опц.) — обоснование; может содержать
   дополнительные правки.

Правки **встраиваются в финальный план естественно**, без маркеров в
днях. ОДНА summary-строка в `## Контекст и ключевые параметры` фиксирует
факт правок. Текст правок **НЕ хранится в YAML** отдельным полем —
информация уже в `## Решение` Stage 4 и в самом теле финального плана.

**Замечание про токены.** Русские значения в YAML стоят чуть больше токенов,
чем латинские (BPE-токенизатор менее эффективен для кириллицы). Разница
небольшая — на стадии это +5–15% к размеру frontmatter. Для длинных списков
(сотни POI, авторов) — можно перейти на латиницу в значениях полей
конкретной стадии, явно отметив это в шапке: `language: en`. По умолчанию —
русский.

### 6.7 Stage 6 — финал (доводка)

```yaml
---
trip_id: вьетнам_север_2026-09
stage: 6_final
travelers_profile: profiles/алексей.md
created: 2026-06-05
source_plan: 5_final_plan_v2.md          # устаканенный 5_vX, на котором построен финал
coords_source_summary: "gazetteer: 4, model: 2"   # сколько координат из газетира / модели
booking_incorporated: false              # опц.: инкорпорирована ли косметическая бронь
enrichment_requested: []                 # опц.: список явных запросов углублений
warnings: []
---
```

Поля схемы:

- `source_plan` — имя устаканенного `5_final_plan_v{N}.md`, на чём построен
  финал. Рендерер по нему находит и читает 5_vX (immutable) для механической
  сборки. Если файл рядом не найден — fallback на latest `5_*_v*.md` в папке.
- `coords_source_summary` — человекочитаемая сводка происхождения координат
  (`gazetteer: N, model: M`); ревьюабельность Tier-1/Tier-2 (см.
  `references/stage6/stage6-final.md` §6). Детальный `source` — в колонке
  таблицы `## Координаты маршрута`.
- `booking_incorporated` — опц. bool: была ли вмёржена косметическая бронь
  (секция `## Бронирования`). Структурная бронь идёт НАЗАД в Stage 5, не сюда.
- `enrichment_requested` — опц. список тем явно запрошенных углублений
  (история региона, рестораны, онсэны…). Пустой — углублений нет.

**Stage 6 — versioned** (`6_final_v{N}.md`): перегон после новой брони /
enrichment даёт v2, v3. **Backward-compat:** старый/менее подробный 5_vX на
входе НЕ ломает Stage 6 — новые поля/маркеры опциональны, отсутствие ≠ ошибка.

Тело `6_final.md` (по `references/stage6/stage6-final.md` §8): `## Координаты
маршрута` (таблица точек `№ | Точка | lat | lon | Источник | Дни` + строка
`**Маршрут:**` + список `**Рёбра:**`), `## Дорожное досье` (H3: визы/медицина/
страховка/этикет/упаковка/экстренное/связь), опц. `## Бронирования`, опц.
`## Углубления`. День-за-днём контент 5_vX в `6_final.md` НЕ дублируется.

## 7. Блок «Контекст для следующих стадий»

Первый markdown-блок в теле каждого файла стадии (после YAML-шапки и
заголовка). Назначение — саморепрезентация файла на случай, когда он
читается изолированно, без чтения всех 5+ предыдущих артефактов.

Длина: 5–8 строк. Содержание (минимум):

- кто едет (профиль одной фразой). О группе — «самостоятельная пара» /
  «путешествуют самостоятельно» (не «независимая пара» / «независимые
  путешественники» — это pipeline-жаргон архетипа)
- длительность и сезон
- выбранный географический скоуп
- 1–2 ключевых ограничения или решения

Шаблон:

```markdown
## Контекст для следующих стадий

Поездка `{trip_id}`: {профиль одной фразой — состав, физформа, темп; для архетипа `самостоятельные` — «самостоятельная пара» / «путешествуют самостоятельно»}.
{N} ночей в {сезон} ({сезонная характеристика — погода, doминируящие
события). Скоуп: {регион_1 (n) → регион_2 (n) → …}. {Ключевая
логистическая особенность — обязательные перелёты, паромы, открытая
дуга, etc.}. {Размещение, бюджетная категория}. Предыдущего плана нет
(или ссылка).
```

## 8. Операции чтения и записи

### 8.0 Приоритет источника входного артефакта

Стадии 2+ читают артефакты предыдущих стадий. Источник выбирается по
приоритету — первый доступный:

1. **Файл приложен к чату** — пользователь приложил `1_dr_reports.md` /
   `2_similarity.md` / `3_poi_pool.md` / `4_variants.md` напрямую
   к сообщению. Чистый текст, без кодирования. **Дефолт** — явная воля
   пользователя «работать с этой версией»; ничего не угадывать.
2. **Synology mount** — `Read` по локальному пути (§1.1). Чистый текст,
   без кодирования. Использовать, когда файл не приложен, но mount
   доступен.
3. **STOP → Transport gate (§1.4).** Если файл не приложен И Synology
   недоступен — вывести сообщение со списком недостающих файлов
   (приложить / починить доступ). Дождаться ответа пользователя.
   Альтернативных транспортов нет.

**Запрет: сниппеты и превью — не данные.** Никогда не реконструировать
`reading_list`, карточки авторов, таблицы или любые списки из обрезков —
только из полного файла (приложение / Synology). Типовая ошибка
«срезать угол» — брать превью вместо файла.

### 8.1 Поиск профиля по `profile_id`

```
profile_path = "{travel_root}/profiles/{profile_id}.md"
Read(profile_path)
```

Если `Read` возвращает ошибку «файл не найден» — пользователь сослался
на несуществующий профиль. Реакция: перечислить существующие профили
(см. §8.2) и спросить.

### 8.2 Перечисление существующих профилей

```
Glob("{travel_root}/profiles/*.md")
```

Для каждого найденного файла прочитать только первые 30 строк (YAML +
заголовок) — этого достаточно для краткой сводки в чат.

### 8.3 Перечисление существующих поездок

```
Glob("{travel_root}/trips/*/0_scope.md")
```

Поездки без Stage 0 не считаются полноценными. Для каждой — прочитать
YAML-шапку `0_scope.md` для извлечения метаданных (trip_id,
travelers_profile, duration_nights, season, selected_regions).

### 8.4 Определение «последней завершённой стадии» поездки

```
Glob("{travel_root}/trips/{trip_id}/[0-5]_*.md")
```

Сортировать по префиксу `0..5`, последняя стадия = последний файл по
сортировке. Дополнительно проверить YAML-поле `chosen_variant` в
`4_variants.md`: если `null` — Stage 4 «в процессе», ещё нет решения.

### 8.5 Чтение артефакта предыдущей стадии

Стандартный шаблон для любой стадии N (где N ≥ 2):

```
prev = N - 1
prev_glob = "{travel_root}/trips/{trip_id}/{prev}_*.md"
Glob(prev_glob)         # вернёт ровно один файл
Read(полученный_путь)
```

Если файл отсутствует — gate не выполнен. См. SKILL.md «Активационные gate'ы».

### 8.6 Запись артефакта — зависит от environment

Правила записи зависят от того, в каком клиенте работает скилл:

| Environment | Synology mount | Что делает скилл |
|---|---|---|
| **Cowork** | доступен | пишет через `Write` в `{travel_root}/trips/{trip_id}/{filename}` + `mcp__cowork__present_files` |
| **Cowork** | недоступен | выдаёт markdown в чат |
| **Claude.ai (обычный чат)** | n/a | выдаёт markdown в чат |

Запись — только через локальный Write в Synology mount.

Полная процедура для каждого случая — в §9.

Исключение: экспорты pdf/docx/pptx/xlsx генерируются делегатами
(core anthropic-скиллы) — они сами решают, куда писать (обычно — в
outputs/workspace Cowork-сессии). После генерации скилл предлагает
пользователю переместить экспорт в `{travel_root}/trips/{trip_id}/`.

## 9. Environment-aware save: процедура

После любой стадии (кроме экспорта) скилл определяет environment и
действует по соответствующей ветке. Сам markdown с YAML-шапкой остаётся
в чате во всех случаях — это страховка на случай, если запись через
Write не сработает или пользователь захочет перепроверить.

### 9.1 Cowork + Synology доступен (основной путь)

1. **Проверка доступа.** Если в текущей сессии ещё не делалось чтение
   из Synology — `Glob("{travel_root}/**/*.md")`. Если возвращает результат
   (даже пустой список без ошибки) — mount доступен.
2. **Создание директории, если её нет.** `{travel_root}/trips/{trip_id}/` —
   проверить, и при отсутствии создать через bash или Write (Write создаст
   автоматически с любой глубиной).
3. **Запись.** `Write({travel_root}/trips/{trip_id}/{stage_filename},
   content)`. Имя файла строго по §4 (для Stage 2 — `2_similarity.md`,
   без вариаций).
4. **Презентация пользователю.** В чат — короткое сообщение:
   ```
   Файл сохранён: [2_similarity.md](computer://{travel_root}/trips/{trip_id}/2_similarity.md)
   ```
   Плюс `mcp__cowork__present_files` для рендера карточки. Дублировать
   полный markdown в чат **не нужно** — он уже в файле.

**Запрет: НЕ писать в `/home/claude/`, `/tmp/`, sandbox-пути.** Если
Synology доступен — пишем туда, не в sandbox.

### 9.2 Cowork без Synology mount

1. Скилл попытался `Glob` к Synology — ошибка доступа или пустой результат
   с ошибкой permission.
2. **Запрос cowork-директории — ОДИН раз за сессию.**
   `mcp__cowork__request_cowork_directory` с просьбой выбрать папку
   `~/Library/CloudStorage/SynologyDrive-home/Claude-Memory/travel-planner/`
   (или родительскую Claude-Memory/).
3. **Если пользователь дал доступ** — повторить процедуру §9.1.
4. **Если пользователь отказал или у него нет Synology Drive** — выдать
   полный markdown в чат и сообщение:
   ```
   Synology mount недоступен. Скопируй markdown выше и сохрани руками как
   `{travel_root}/trips/{trip_id}/2_similarity.md`.
   ```

### 9.3 Claude.ai (обычный чат)

В обычном чате без Cowork нет ни Synology mount, ни `mcp__cowork__*`
тулз. Скилл выдаёт полный markdown в чат + сообщение:

```
Скопируй markdown выше и сохрани руками как
`{travel_root}/trips/{trip_id}/2_similarity.md` через Synology Drive.
Папку `trips/{trip_id}/` создай, если её ещё нет.
```

### 9.4 Что НЕ должно быть в теле файла

Блок «Сохранить как» / computer://-ссылка / напоминание про создание
папки — всё это **только в чате после файла**, не в теле markdown
артефакта. Файл должен быть чистым markdown-документом с YAML-шапкой и
секциями стадии (см. §6 + stage-references), без meta-инструкций по
сохранению.

## 10. Edge cases

### 10.1 Коллизия `trip_id`

Две поездки в одно направление в один месяц с одинаковой детализацией
(редко, но возможно — например, поехали в Тбилиси в начале и в конце мая
разными группами):

- Дискриминатор после месяца: `грузия_соло_2026-05_а`, `грузия_соло_2026-05_б`.
- Не использовать день в `trip_id` — `2026-05-03` ломает консистентность
  с остальными.

### 10.2 Profile drift

Пользователь обновил профиль после старта поездки (например, дополнил список
ограничений или сменил бюджет):

- В YAML-шапке профиля поле `updated` отражает дату последнего изменения.
- При работе со стадиями поездки скилл сравнивает `created` стадии с
  `updated` профиля. Если профиль обновлён ПОСЛЕ создания текущей стадии —
  предупредить одной строкой: «профиль обновлён `YYYY-MM-DD`, текущая стадия
  создана `YYYY-MM-DD` — некоторые рекомендации могут устареть. Перегенерировать?»
- Не пересчитывать автоматически.

### 10.3 Пропущенная промежуточная стадия

Пользователь хочет Stage 4, но в папке нет Stage 3 (например, удалил
случайно или работал в другой сессии и не сохранил):

- Реакция: «Stage 3 артефакт `3_poi_pool.md` отсутствует в
  `trips/{trip_id}/`. Запусти Stage 3 сначала. Если данные уже собирались —
  приложи файл в чат, я учту».
- Не пытаться восстановить Stage 3 из Stage 1 и Stage 2 на лету.

### 10.4 Stage 1 без сохранения

Пользователь прогнал DR в отдельной сессии и просто скопировал результат
в чат, не сохранив `1_dr_reports.md`:

- Допустимо для разового прогона Stage 2.
- Перед Stage 3 настоятельно рекомендовать сохранить — иначе придётся
  каждый раз вставлять заново.

### 10.5 Несколько артефактов одной стадии (повторный прогон)

Пользователь перезапустил Stage 2 с другими весами similarity — теперь у
него два варианта `2_similarity.md`:

- Один файл = одна стадия. Второй вариант сохранять как
  `2_similarity_alt.md` (или с суффиксом даты).
- Поле `chosen_similarity_run` в YAML Stage 3 — указывать, какой из них
  использовался.

### 10.6 Файл виден, но не читается (не докачан)

Synology Drive умеет держать файл заглушкой: в дереве он виден и размер
известен, а содержимого на диске нет. Листинг заглушку от загруженного файла
не отличает.

- Доступ к службе синхронизации есть → `Read` докачает файл сам, но медленно:
  ~0,6–2 с на файл. Много файлов — читать пачкой (несколько `Read` одним
  сообщением), а не по очереди.
- Доступа нет → `Read` вернёт пустоту или ошибку, и файл останется
  нечитаемым. **Ожидание не поможет:** в режиме «по требованию» файл сам не
  докачается, его загружают на самом устройстве.

**Не путать с «файла нет»:** листинг файл показал, а `Read` по нему упал — это
незагруженное содержимое, а не отсутствующий файл. Сообщать именно так.

Реакция — остановиться, ничего не записав, и спросить пользователя, приведя
дословный текст ошибки (он называет причину):

> Файл `{path}` не читается: `{ошибка}`. Похоже, содержимое не загружено на
> устройство — скачать его отсюда я не могу, это делается на устройстве.
> · Я загрузил — проверь ещё раз · Работаем без него · Стоп

Содержимое не угадывать. «Работаем без него» уместно для необязательного
входа (например, профиля попутчика); если не читается артефакт предыдущей
стадии — только «загрузил» или «стоп».

### 10.7 Латиница в `trip_id` или `profile_id`

Если пользователь по привычке создаёт идентификатор латиницей
(`<country>_<detail>_<YYYY-MM>`) — это допустимо для legacy-поездок, не
блокирующая ошибка. Скилл работает с любым форматом. Но при создании новых
поездок и профилей рекомендуется русский — для консистентности с экспортами
и читаемости в файл-менеджере.

### 10.8 Смешанная система письма в `trip_id` (mixed script)

Если идентификатор содержит **и латиницу, и кириллицу**
(пример формы: `<latin>_<кириллица>_<YYYY-MM>`) — это нежелательно:

- Glob-поиск работает, но `trip_id` сложнее читать и копировать.
- При экспорте имена файлов будут содержать обе системы письма.
- Это часто результат опечатки или неполного переименования.

Действия скилла при детекции mixed-script:

- Gate-предупреждение ОДНОЙ строкой при первом упоминании trip_id:
  «trip_id `{trip_id}` смешанный (латиница + кириллица). Рекомендую
  переименовать в `{кириллический_вариант}` либо `{латинский_вариант}`».
- Не блокировать — работа продолжается.
- В YAML каждого нового артефакта добавлять `trip_id_warning: mixed_script`
  — следующие стадии повторят предупреждение.
- Старые поездки с mixed-script — терпеть, не выбрасывать
  предупреждение каждый раз; добавить `trip_id_warning` только при
  создании нового артефакта на этой поездке.

Детекция: trip_id содержит хотя бы один латинский символ И хотя бы один
кириллический. Дефисы, цифры, подчёркивания — нейтральные.
