# stage3-polish-prompt.md

Инструкция для модели в **export-mode Stage 3**. Применяется ДО рендера
DOCX/PDF: модель читает оригинальный `3_poi_pool.md`, выдаёт
«отполированную» версию, которую затем рендерит детерминированный
Python-скрипт (`stages/stage3.py`).

Stage 3 — **operative-документ**: пользователь заполняет в DOCX теги
регионов (`обязательно` / `можно` / `не интересно`) и комментарии на
каждый POI. PDF — read-only витрина того же контента после заполнения.

**Принцип:** polish = минимальная косметика. Stage 3 уже структурирован
жёстко (regional-блоки, нумерация POI, 6 полей внутри карточки). НЕ
переписывать факты, НЕ переименовывать POI, НЕ менять счётчики, НЕ
трогать выдержки. Удаляется только pipeline-жаргон в заголовке и
служебных секциях.

**Когда применять:** для всех получателей (Stage 3 пока имеет только
`recipient = self` — DOCX/PDF идентичны).

---

## Что на входе и что на выходе

**Вход:** полный markdown `3_poi_pool.md` — YAML frontmatter + body
(контекст, распределение, warnings, полная агрегация POI по регионам,
non-mainstream highlights).

**Выход:** markdown того же формата (YAML + body), с применёнными ниже
трансформациями. Никаких пояснений — только сам markdown.

---

## Трансформации

Применять **все** по порядку. Если какая-то не применима — пропустить,
не упоминать.

### T1. Cover title — человеко-читаемый

H1 заголовок переписать без pipeline-жаргона (`Stage 3 v2 — ...`,
`Stage 3 — Агрегация POI: камбоджа_лаос_2026-02`):

**Стало:** `# {Регионы человекочитаемо} · агрегация POI`

Примеры:
- `# Камбоджа и Лаос · агрегация POI`
- `# Северный Вьетнам · агрегация POI`

Регионы брать из YAML (`trip_id` → split по `_` без последнего «YYYY-MM»
сегмента) или из `regions` Stage 1, если он рядом.

### T2. Маркер параметров поездки (для cover-таблицы)

Первой строкой body (СРАЗУ после `---` frontmatter, ПЕРЕД секцией
«Контекст для следующих стадий») вставить маркер `[[поездка: …]]`:

```
[[поездка: группа: Алексей | регионы: Камбоджа → Лаос | сезон: февраль 2026 | темп: размеренный]]
```

Те же поля что в Stage 1 polish (`../stage1/stage1-polish-prompt.md` T2) — единый
формат маркера во всём pipeline. Скрипт сам соберёт cover-таблицу.

### T3. Убрать pipeline-жаргон из заголовков H2

Заголовки секций оставить как есть **кроме**:
- если есть `## Следующий шаг` или `## Что дальше` — **удалить** секцию
  целиком (это служебный pipeline-жаргон, не нужен пользователю).
- `## Контекст для следующих стадий` оставить (читатель видит на
  cover-блоке коротко, в body тоже полезно).

Формулировка про группу (в т.ч. в `## Контекст для следующих стадий`):
«независимая пара» / «независимые путешественники» → «самостоятельная
пара» / «путешествуют самостоятельно» (каноническая формулировка архетипа
`самостоятельные`). Компонент похожести `independence` («независимость
планирования») не трогать — это другое понятие.

### T3b. Нормализация тегов регионов

В заголовках регионов `### {Регион} — N POI · **тег:** {значение}` поле
`тег` пользователь заполняет вольно: «надо», «нет», «да», «точно»,
«может быть» и т.п. Builder выводит тег в DOCX как pre-checked чекбокс
из трёх канонических значений — **обязательно / можно / не интересно**.

**Что делает polish:** привести каждый непустой тег к одному из трёх
канонических значений по смыслу:
- утвердительное («надо», «да», «точно», «обязательно», «must») →
  `обязательно`
- условное («можно», «возможно», «может быть», «опционально») → `можно`
- отрицательное («нет», «не надо», «не интересно», «skip») → `не интересно`

```
### Сием-Рип и Ангкор — 19 POI · **тег:** _____            ← пусто, оставить
### Луангпрабанг — 8 POI · **тег:** надо                    ← заменить на «обязательно»
### Центральный Меконг — 2 POI · **тег:** нет               ← заменить на «не интересно»
```

Пустой тег (`_____`, пробел) оставить как есть — пользователь заполнит
в DOCX.

**Это единственный механизм нормализации тега.** Builder НЕ угадывает
синонимы программно — он принимает только три канонических значения и
сравнивает точно. Любую вольную формулировку («надо подумать», «если
успеем», «зависит») обязан привести к канону именно polish. Если тег не
приводится к канону — оставь `можно` (нейтральный дефолт) и не выдумывай
четвёртое значение.

### T4. Не трогать структуру POI

**Дословно сохранить:**
- Все `### {Регион} — N POI · **тег:** ...` заголовки (включая placeholder
  `_____` если тег не заполнен; скрипт сам решит показывать ли).
- Blockquote `> **Режим категоризации региона:** ...` под каждым регионом.
- Параграф `— из Stage 0: ...` (passthrough описания региона).
- Строку `**Комментарий к региону:** ...` под заголовком региона (если есть) —
  это текст пользователя, не править и не переносить.
- Все `#N **Название** (Local) — КАТЕГОРИЯ` POI headers.
- 6 нумерованных полей каждого POI (Регион / счётчики / OUTLIER … / Выдержки /
  Характеристики / Комментарий пользователя).
- Все `**Combined with:** ...`, `**Cluster:** ...`, `**Iconic status:** ...`,
  `**Trap archetype:** ...`, `**Iconic exception:** ...` маркеры —
  они контракт парсера.
- **Секцию `## Источники (реестр авторов)` в конце файла — ДОСЛОВНО,
  целиком.** Это не pipeline-жаргон: экспорт берёт отсюда URL/год авторов
  (self-contained, без `1_dr_reports.md`). Строки `- cNN | имя | год |
  <url-поле>` не переписывать, не сокращать URL, не убирать секцию.

**Не переписывать:**
- ID авторов в выдержках (`c01`, `c02`, ... — экспортёр сопоставляет их с
  реестром `## Источники` в конце файла для ссылок/года).
- Цифры счётчиков по категориям авторов (поля 2–3 POI).
- Категорию POI — её решает `aggregate_pois.py` детерминированно.

**Язык ярлыков — не трогать ни в одну сторону.** Тело нового артефакта
рождается с русскими ярлыками (СИЛЬНОЕ ПОДТВЕРЖДЕНИЕ, ВЫСОКАЯ, …), старые
файлы — с английскими (STRONG CONFIRMED, HIGH). Polish **не переводит**
ярлыки: ни EN→RU («помогу русификации»), ни RU→EN («верну канон»). Обе формы
валидны, экспорт печатает их по-русски сам. Перевод ярлыка = правка данных,
а не языка изложения.

### T5. Cluster header — не трогать формат

`#### Cluster: {имя} ({N} POI) — {категория}` оставить как есть, включая
блок «Логическая единица: ...» и «Aggregated counts: ...» под ним.
Скрипт парсит это как cluster-блок и рендерит отдельный header.

### T6a. Региональные саммари (presentation-grade)

**Зачем:** Stage 3 md содержит только raw counts/выдержки. Для presentation
DOCX/PDF под каждым region header выводится короткое описание региона
(«что это и чем интересно») и саммари по авторам («кто покрывал, тон,
акценты»). Без них pdf/docx выглядит как сухой dump карточек.

**Когда применять:** ВСЕГДА. Polish читает Stage 3 (и опционально
приложенные Stage 0 + Stage 1) и генерирует на их основе оба маркера.

**Что вставить per регион** (в любом месте body, обычно прямо после
`### {Регион} — N POI` headline региона, до его POI):

```
[[регион: Сием-Рип и Ангкор | описание: Главное в регионе — крупнейший ансамбль кхмерской храмовой архитектуры IX–XIII вв.; outlying-храмы дают руинную малолюдную фактуру против парадного ядра.]]

[[регион: Сием-Рип и Ангкор | авторы: 3 HIGH-автора покрывают регион плотно — Алекс делает акцент на маршрутах малого/большого круга, Дария — на фотографии и логистике рассвета, annamfoto — на outlying-храмах (Бенг-Меалеа, Кох-Кер). Также 1 OUTLIER (Tripadvisor) критикует основные храмы как переоценённые из-за толп.]]
```

**Правила содержания:**

- **описание:** 1-2 предложения. ЧТО это за регион и ЧЕМ он уникален
  ДЛЯ ПУТЕШЕСТВЕННИКА (не «состав:» — список POI и так в карточках
  ниже). Если Stage 0 приложен — переписать «Принципиально:» строку
  своими словами + добавить сезонный/логистический штрих. Если Stage 0
  не приложен — экстрагировать смысл из POI выдержек региона.
- **авторы:** 1-3 предложения. КТО покрывает (similarity-тиры с
  числами авторов) + КАКОЙ АКЦЕНТ каждый делает (по содержанию их
  выдержек). Полезно отметить **расхождения тона** (HIGH-рекомендуют
  vs OUTLIER-критикуют). Имена авторов брать как они идут в выдержках
  (короткое имя из Stage 3, без префикса `cXX`).

**Что НЕ вставлять:**
- Не повторять `Режим категоризации` (уже выведет скрипт)
- Не выводить отдельный POI count (уже в `— N POI` в headline)
- Не давать рекомендации «куда поехать» (это работа Stage 4, не Stage 3)

### T6b. Региональное English-имя для поиска Google Images

**Зачем:** в DOCX название POI кликабельно → открывает Google Images.
Pages при сохранении DOCX ломает unicode-URL (двойное %-encoding), поэтому
search query идёт на латинице. Для дизамбигуации общих английских названий
(«Pub Street» — есть везде; «Small Circuit» — outside Ангкора абстракция)
к query добавляется English-имя региона.

**Что вставить per регион** (одна строка, можно рядом с T6a-маркерами):

```
[[регион: Сием-Рип и Ангкор | english: Siem Reap, Cambodia]]
[[регион: Пномпень | english: Phnom Penh, Cambodia]]
[[регион: Луангпрабанг | english: Luang Prabang, Laos]]
```

Формат: `Город, Страна` (английский, ASCII). Без артиклей «the», без
лишних слов. Если регион — целая провинция/плато, давай главный город +
страну: «Champasak, Laos» (плато Боловен), «Nong Khiaw, Laos»
(долина Нам-Оу).

Без этого маркера builder fallback'нется на список стран trip_id
(«Pub Street in Cambodia or Laos») — менее точный, но рабочий.

### T6. Distribution table — не переименовывать колонки

Таблица `## Распределение по категориям` — оставить headers `Категория /
Кол-во / Доля` и категории дословно, в том языке, в котором они пришли.
Скрипт ожидает именно эти 6 категорий (канон тела — русский ярлык, легаси —
английский; принимаются обе формы):

| Ярлык в теле | Легаси-форма |
|---|---|
| СИЛЬНОЕ ПОДТВЕРЖДЕНИЕ | STRONG CONFIRMED |
| СЛАБОЕ ПОДТВЕРЖДЕНИЕ | WEAK CONFIRMED |
| СКРЫТАЯ ЖЕМЧУЖИНА | HIDDEN GEM |
| СПОРНЫЙ | CONTESTED |
| КРАСНЫЙ ФЛАГ | RED FLAG |
| СЛАБЫЙ СИГНАЛ | LOW SIGNAL |

Не добавлять, не убирать, не переводить строки — только сохранить.

### T7. Author URL coverage — все авторы должны иметь ссылку на отчёт

**Зачем:** в presentation-PDF и DOCX каждая выдержка автора подписана
ссылкой на оригинальный отчёт (через lookup `cXX` → Stage 1). Если у
автора нет URL — читатель не может проверить первоисточник.

**Что делает polish:**
1. После применения T1–T6a — пройтись по всем `cXX` упомянутым в выдержках
   и убедиться что каждый из них есть в приложенном Stage 1
   (`1_dr_reports.md`) как `### Карточка NN` (где `NN` совпадает с
   числом в `cNN`).
2. Если какой-то `cXX` не находится в Stage 1 → это сигнал что либо
   `cXX` неверный (опечатка в Stage 3), либо Stage 1 не приложен. В
   обоих случаях — НЕ молча оставляй; добавь в конец body новый блок
   `## Warnings` (или append к существующему):
   ```
   - ⚠️ автор `cXX <имя>` не найден в Stage 1; ссылка на отчёт в PDF/DOCX отсутствует
   ```
3. **Не выдумывай URL** — если автор не в Stage 1, ссылка ДОЛЖНА
   отсутствовать. Лучше явное warning чем ложный URL.

**После build builder сам печатает stderr-warning** если у каких-то
авторов URL не нашёлся (даже после polish). Это последняя страховка —
polish может ошибиться, builder ловит.

**Контракт пользователю:** при экспорте Stage 3 *обязательно* прикладывай
`1_dr_reports.md` рядом с `3_poi_pool.md`. Без него все ссылки
на отчёты в DOCX/PDF будут отсутствовать (плюс описания регионов
обеднеют — но это второстепенно).
