# stage3-poi.md

Полная спецификация Stage 3 — агрегация POI. На входе — reading list
от Stage 2 (HIGH + OUTLIER + расширенный MEDIUM) и полная база DR-карточек
от Stage 1. На выходе — каждое упомянутое место с категорией STRONG
CONFIRMED / WEAK CONFIRMED / HIDDEN GEM / CONTESTED / RED FLAG / LOW SIGNAL
и характеристиками из отчётов.

Философия и место в пайплайне — `../methodology.md` §3 «Stage 3».

## 1. Назначение

Свести упоминания мест из отчётов отфильтрованных авторов в одну
структурированную картину: какие POI **подтверждены** похожими
путешественниками, какие — **hidden gems**, какие — **туристические
ловушки** для этого профиля.

Зачем категоризация, а не плоский «список мест»:

- Плоский «топ-N мест в стране» — то, что выдаёт любой гайд. Ценность
  Stage 3 — различить место, которое хвалят **похожие на пользователя**
  авторы, от места, которое хвалят стандартные туристы.
- **RED FLAG** — ключевая категория: место хвалят LOW-similarity авторы,
  но HIGH-similarity критикуют как переоценённое. Без двухслойной выборки
  (широкий Stage 1 + фильтр Stage 2) такие места не видны.
- **HIDDEN GEM** — место, которое нашли 1–2 HIGH-автора и больше никто.
  Плата за широкую выборку Stage 1 окупается именно здесь.

Stage 3 — **агрегация, не приоритизация**. Решение «что брать в маршрут»
принимается на Stage 4. Stage 3 не строит маршрут, не сортирует места
по «обязательности», не рекомендует.

## 2. Inputs / Outputs

**Inputs:**

- Stage 2 артефакт: `{travel_root}/trips/{trip_id}/2_similarity.md` ← Read
  (reading list, расширенный список, полная таблица авторов с категориями)
- Stage 1 база: `{travel_root}/trips/{trip_id}/1_dr_reports.md` ← Read
  (20-field карточки; Stage 3 читает поля 14 «POI с тональностью» и
  15 «hidden gems»)
- **Stage 0 артефакт** (F-58, обязателен):
  `{travel_root}/trips/{trip_id}/0_scope.md` ← Read. Stage 3 использует
  YAML-шапку для `country_quota` (атрибуция POI к стране при cross-region
  кейсах), а body — для passthrough описаний регионов под `### {Регион}`
  заголовками в §8 (Stage 3 → Stage 4 touchpoint удобнее, если описание
  региона из Stage 0 доступно прямо в Stage 3 md). При отсутствии — Stage 3
  продолжает с warning «региональные описания недоступны», но это
  pipeline gap, не штатный режим.
- Профиль: `{travel_root}/profiles/{profile_id}.md` ← Read
  (для раздела Non-mainstream highlights и оценки релевантности)
- Опц.: предыдущий план поездки (если есть) — для раздела сравнения

**Outputs (в чат + manual save пользователем):**

- `{travel_root}/trips/{trip_id}/3_poi_pool.md` — Stage 3 артефакт
  с YAML-шапкой, полной агрегацией POI (8 полей на место), разделом
  Non-mainstream highlights и опц. сравнением с предыдущим планом.

**Downstream:** Stage 4 (route variants) читает категории POI как основу
для построения структурно различных вариантов маршрута.

## 3. Поток

Один режим, 2 turn'а.

### Turn 1 — пользователь

«агрегировать POI для {trip_id}», «Stage 3 для {trip_id}», «собрать
места из отчётов», «третий шаг».

### Turn 2 — скилл

**0. Model self-check (обязательный первый шаг).** Назвать модель одной
строкой: «Я модель: <name>. Stage 3 рассчитан на Opus base без
thinking (fallback — Sonnet + adaptive thinking).»

- **Opus base (без thinking)** — продолжать без warning. Primary.
- **Opus + adaptive thinking** — предупредить одной строкой: «Opus+T
  тратит до 50% 5-часового лимита без качественного прироста
  относительно Opus base. Рекомендую переключиться на Opus base.
  Продолжить на Opus+T только при базе >60 POI или >10 регионов».
  Дождаться решения пользователя.
- **Sonnet + adaptive thinking** — продолжать без stop, предупредить
  одной строкой: «Допустимый fallback. Риски: spec violations
  (region-first ordering, пропуск «Комментарий пользователя» под POI,
  слияние разных POI), недопокрытие niche-регионов».
- **Sonnet без thinking** — **остановиться**: «Stage 3 без thinking
  не работает (Tier-1/2/3 баг нормализации). Открой новый чат на Opus
  base или на Sonnet + adaptive thinking».
- **Haiku** — **остановиться**: «Stage 3 не поддерживается на
  Haiku. Открой новый чат на Opus base или Sonnet + adaptive
  thinking. Не нажимай «Continue» после safety pause — это переводит
  на Haiku». Логика — `../../SKILL.md` блок про safety filter.

1. Gate-проверки (§4).
2. Получить `2_similarity.md` — источник по приоритету
   `../storage-and-naming.md` §8.0 (приложенный файл → Synology mount;
   сниппеты и превью данными не считать). Извлечь: `reading_list` (HIGH + OUTLIER),
   `reading_list_extended` (MEDIUM ≥ 6.5), `unscored_with_signal`,
   и **полную таблицу всех авторов** — из неё взять id авторов
   категории LOW (нужны для RED FLAG, см. §6.4). Из YAML Stage 2 также
   взять `total_authors` (размер DR-базы) — он идёт в payload и
   определяет режим категоризации (§6.5, §6.6).
3. Получить `1_dr_reports.md` (тот же приоритет источника — §8.0).
4. Read профиля.
5. **Опц.** Если есть предыдущий план поездки — Read его (для §8
   раздела сравнения). Если нет — раздел сравнения опускается.
6. **Profile drift check.** Сравнить `updated` профиля с `created`
   Stage 2. Если профиль обновлён позже — одной строкой предупредить,
   продолжить (см. §9.6).
7. **Извлечение POI (LLM).** По §6.1–§6.4: для каждого reading-list
   автора (HIGH + OUTLIER + расширенный MEDIUM) — все упомянутые места
   из полей 14/15 с тональностью; для каждого LOW-автора — **только**
   recommend-упоминания (для RED FLAG-сигнала). Нормализовать имена
   мест (§6.2): одно место под разными написаниями — одна запись POI.
   Опционально — проставить `iconic_exception` для топ-1 эталонов
   категорий, которые профиль явно исключает (§6.8).
7.5. **Synergy detection (LLM).** После извлечения всех POI прогнать
   попарный чек на synergy по §6.9: для каждой пары POI в одном
   регионе проверить признаки (общий оператор в characteristics /
   общий транспорт и стартовая точка / явное упоминание совместности
   автором). Если хотя бы один признак выполнен — заполнить
   `commonly_combined_with` обоим POI пары (симметрично). Высокий
   порог — если все признаки слабые, поле остаётся пустым.
8. **Сформировать JSON-payload** по §6.6 — список нормализованных POI
   с упоминаниями, цитатами, характеристиками и опц. полями
   `iconic_exception` / `commonly_combined_with`.
9. **bash: запуск `scripts/aggregate_pois.py`** через stdin:
   ```
   echo '<payload>' | python3 .../aggregate_pois.py
   ```
   Скрипт детерминированно считает упоминания по тональности,
   категоризирует по 6 правилам, формирует агрегаты и warnings.
10. **Read `diagnostic.status` из output:**
    - `"ok"` — продолжать на шаг 11.
    - `"warning"` — одной строкой пользователю («скрипт: {N} POI,
      мелкие замечания — {issue codes}. Продолжаю»), продолжать.
    - `"error"` — **не чинить payload молча.** См. §9.9 «Opt-in
      исправление при error».
    Если exit 1 (zero POI) или exit 2 (пустой/невалидный stdin) —
    сообщить пользователю, не угадывать.
11. Собрать markdown по §8 на основе JSON-output скрипта.
12. **Output — environment-aware** (тот же паттерн, что Stage 2 §3 шаг 10):

    - **Write/Bash доступен:** СРАЗУ сохранить файл через `Write` как
      `{travel_root}/trips/{trip_id}/3_poi_pool.md`. В чат — короткий
      summary + `computer://`-ссылка. Не говорить «спека не пишет файл
      сам».
    - **Write недоступен** (claude.ai chat): per Class G — Message 1
      = готовый `3_poi_pool.md` целиком одним блоком (включая `**тег:** _____`
      строки под каждым региональным заголовком per §11); Message 2 =
      save instruction + сообщение про tagging (см. §11) + summary.

**Стоп.** Пользователь сохраняет файл (или скилл сохранил автоматически),
заполняет `**тег:** ...` под региональными заголовками + опц. комментарии
под POI, готов к Stage 4.

### Размер выборки

**Дефолт — небольшая база.** Stage 1 даёт 20–30 отчётов, и по умолчанию
исходить надо из худшего случая: найден минимум (~20, иногда < 15 —
см. `../stage1/stage1-dr-prompt.md` §9.6), и пользователь ничего не добавлял
руками через Stage 1 Mode B. После фильтра Stage 2 reading list ещё
меньше, HIGH-авторов — единицы. Это **нормальный режим работы Stage 3**,
не повод для тревоги — следствия для категоризации описаны в §9.12.

**Большая база — редкое исключение.** Если reading list + LOW-авторы
суммарно дают > 40 авторов к разбору (обычно — только когда выборка
расширена через Stage 1 Mode B) — перед работой предупредить: «База
большая ({N} авторов к разбору, включая LOW для RED FLAG). На
Sonnet+thinking возможно срезание углов при извлечении. Варианты:
(1) одним проходом; (2) разбить извлечение на батчи по регионам,
собрать единый payload, прогнать скрипт один раз; (3) поднять модель
до Opus». Решает пользователь, скилл не делает chunking сам.

Применяй ДО запуска работы. Если хоть одна не выполнена — отказ ОДНОЙ

| Что | Обязательно | Если не задано |
|---|---|---|
| `trip_id` | да | спросить или предложить из существующих (Glob) |

```

**Отказ при отсутствии Stage 1:** аналогично — Stage 3 читает поля 14/15

### 6.1 Из каких авторов и каких полей извлекать

Stage 2 даёт три группы авторов. Stage 3 работает со всеми, но
по-разному:

| Группа Stage 2 | Что извлекать | `author_category` в payload |
|---|---|---|
| `reading_list` — HIGH | **все** POI из полей 14/15 с тональностью | `HIGH` |
| `reading_list` — OUTLIER | **все** POI из полей 14/15 с тональностью | `OUTLIER` |
| `reading_list_extended` — MEDIUM ≥ 6.5 | **все** POI из полей 14/15 с тональностью | `MEDIUM` |
| LOW-авторы (из полной таблицы Stage 2) | **только** recommend-упоминания (§6.4) | `LOW` |

`unscored_with_signal` — опционально: если у автора есть сигнал и
пользователь хочет его учесть, извлекать как `OUTLIER`. По умолчанию
пропускать.

Источник POI в карточке:

- **Поле 14** — «Полный список упомянутых POI с тональностью каждого».
  Основной источник: места + тональность напрямую.
- **Поле 15** — «нетуристические / hidden gems места». Их тоже включать;
  они кандидаты в HIDDEN GEM.
- Поле 8 выхода (характеристики места) — собирать из полей 14, 16
  (логистика), 18 (проблемы) и прозы карточки.

### 6.2 Нормализация имён POI

Одно место под разными написаниями = **одна** запись POI. Это главная
семантическая работа Stage 3. Объединять:

- транслит ↔ латиница: «Лагуна-де-лос-Трес» = «Laguna de los Tres»;
- разговорные / маркетинговые имена: «горы Аватар» = «Чжанцзяцзе»
  (Zhangjiajie);
- частичные написания: «Лома-дель-Плиегуэ-Тумбадо» = «Loma del Pliegue
  Tumbado» = «Loma Pliegue»;
- одно место с разной детализацией: «Перито-Морено» = «ледник
  Перито-Морено» = «Glaciar Perito Moreno».

НЕ объединять разные места, даже похоже названные (две разные лагуны,
два храма с близкими именами в разных городах). При сомнении —
оставлять раздельно и в чате одной строкой отметить.

Каждый POI в payload получает `name_ru` (русская транслитерация —
канон) и `name_local` (латинский / местный вариант, если есть).
Если из карточек место упоминается только латиницей — `name_ru` =
транслитерация, `name_local` = оригинал.

### 6.3 Тональность упоминания

Для каждого упоминания POI в карточке проставить **одну** тональность:

| Тональность | Значение |
|---|---|
| `recommend` | автор рекомендует, хвалит, советует |
| `neutral` | упомянуто без явной оценки |
| `criticize` | автор критикует, предупреждает, считает переоценённым |
| `regret_visited` | автор жалеет, что посетил |
| `regret_missed` | автор жалеет, что **пропустил** (не был, но хотел бы) |

Тональность — семантика, её определяет LLM из прозы карточки.
`regret_missed` ≠ `recommend`: это сигнал интереса без личного опыта;
скрипт учитывает его отдельно (см. §6.5).

**Особое правило для `criticize`.** Тональность `criticize` ставится
**только при наличии причины** в тексте карточки. Примеры
обоснованных причин: «переполнено», «переоценено», «вылизано под
западного туриста», «развод на деньги», «нет того, ради чего я ехал»,
«туристическая ловушка». Просто «не понравилось» без указания причины
— ставить `neutral`, не `criticize`. Это правило важно для scarce-
ветки RED FLAG-генератора Stage 3 (см. §6.4): scarce-ветка
срабатывает по обоснованной критике от не-HIGH авторов, и пустые
жалобы создавали бы шум.

`regret_visited` ставится при явном сожалении автора о том, что
посетил место (с причиной или без — само по себе явное сожаление
сильнее, чем безаргументная criticize).

### 6.4 LOW-авторы для RED FLAG (вариант B)

RED FLAG имеет **две ветки** срабатывания:

**Ветка 1 (классическая, abundant + scarce):** место **хвалят
LOW-similarity** авторы, но **критикуют HIGH-similarity**. Скрипту нужны
positive-упоминания LOW-авторов И critic-упоминания HIGH.

**Ветка 2 (только scarce-режим):** место **никто из HIGH не
рекомендует**, а ≥3 OUTLIER/MEDIUM/LOW-автора **обоснованно критикуют**
(тональность `criticize` или `regret_visited`). Срабатывает когда
HIGH-когорта узкая и ветка 1 математически невозможна (например,
Vietnam: 4 HIGH из 43 → шанс что 2 HIGH-критика сойдутся на одном
месте близок к нулю). Порог: nhn≥3 → RED_FLAG, nhn=2 → CONTESTED.

#### Из каких авторов какие упоминания извлекать

- **HIGH-авторы:** все упоминания всех тональностей (как обычно).
- **OUTLIER / MEDIUM-авторы:** все упоминания, включая **`criticize`** и
  **`regret_visited`** — нужны для scarce-ветки 2.
- **LOW-авторы:** упоминания с тональностью **`recommend`** (для ветки 1)
  И **`criticize` / `regret_visited`** (для ветки 2). Neutral от LOW
  не нужен — не участвует ни в одном правиле.
- `author_category` для каждого упоминания — `HIGH` / `OUTLIER` /
  `MEDIUM` / `LOW` точно как у автора в Stage 2.

#### «Обоснованная» критика — что это значит

Критика считается обоснованной, если автор указывает **причину**: «слишком
туристически», «переполнено», «переоценено», «развод на деньги»,
«вылизано под западного туриста», «нет того, ради чего я ехал», и т.п.
Просто «не понравилось» без причины — не считается. LLM при экстракции
проставляет тональность `criticize` ТОЛЬКО при наличии причины в тексте
карточки (см. §6.3); скрипт доверяет тональности без перепроверки.

Это единственная роль non-HIGH авторов в Stage 3 в части RED FLAG-сигнала.
Их места не попадают в основные positive-категории (STRONG / WEAK /
HIDDEN GEM) сами по себе — только усиливают CONTESTED / RED FLAG.

### 6.5 Шесть категорий — правила (категоризирует скрипт)

LLM **не** категоризирует. Скрипт `aggregate_pois.py` применяет правила
ниже детерминированно. Здесь — для понимания, что LLM подаёт на вход.

#### Язык категорий: ярлык в теле — русский, ключ в YAML — английский

Одна категория живёт в двух формах, и **путать их нельзя**:

| Ярлык в теле `.md` (пишешь его) | Ключ в YAML / JSON (машинный) | Поле счётчика в YAML |
|---|---|---|
| **СИЛЬНОЕ ПОДТВЕРЖДЕНИЕ** | `STRONG_CONFIRMED` | `strong_confirmed` |
| **СЛАБОЕ ПОДТВЕРЖДЕНИЕ** | `WEAK_CONFIRMED` | `weak_confirmed` |
| **СКРЫТАЯ ЖЕМЧУЖИНА** | `HIDDEN_GEM` | `hidden_gems` |
| **СПОРНЫЙ** | `CONTESTED` | `contested` |
| **КРАСНЫЙ ФЛАГ** | `RED_FLAG` | `red_flags` |
| **СЛАБЫЙ СИГНАЛ** | `LOW_SIGNAL` | `low_signal` |

Категории авторов — так же: `HIGH` → **ВЫСОКАЯ**, `OUTLIER` → **ОСОБЫЙ
СИГНАЛ**, `MEDIUM` → **СРЕДНЯЯ**, `LOW` → **НИЗКАЯ**.

**Правило (анти-дрейф):** русский ярлык **не переводи сам** — копируй
**вербатим** поле `category_label` из output скрипта (у кластеров —
`cluster_category_label`). Английский ключ (`category`) идёт **только** в
YAML-счётчики; в JSON-payload на вход скрипта категории авторов —
тоже английские (`author_category: "HIGH"`).

В правилах ниже категории названы **английскими ключами** — это описание
логики скрипта, а не текст для тела файла.

Скрипт считает на каждый POI:
- `high_recommend` — число HIGH с тональностью recommend;
- `high_neg` = HIGH `criticize` + HIGH `regret_visited`;
- `high_regret_missed` — HIGH, жалеющие что пропустили (контекст);
- `low_recommend` — LOW с recommend;
- `non_high_negative` — обоснованная критика (criticize или regret_visited)
  от OUTLIER + MEDIUM + LOW авторов;
- `non_high_total` — сумма упоминаний OUTLIER + MEDIUM + LOW.

| Категория | Правило (скрипт, по приоритету сверху вниз) |
|---|---|
| **CONTESTED** | `high_recommend ≥ 1` И `high_neg ≥ 1` (HIGH расколоты) |
| **RED FLAG (ветка 1)** | `high_neg ≥ 1` И `high_recommend = 0` И `low_recommend ≥ 1` |
| **RED FLAG (ветка 2, scarce)** | scarce-режим И `high_recommend = 0` И `non_high_negative ≥ 3` |
| **CONTESTED (ветка 2, scarce)** | scarce-режим И `high_recommend = 0` И `non_high_negative ≥ 2` (если ветка 2 RED_FLAG не сработала) |
| **STRONG CONFIRMED** | `high_recommend ≥ 3` И `high_neg = 0` |
| **WEAK CONFIRMED** | `high_neg = 0`, `non_high_total > 0`, и `high_recommend = 2` (режим **abundant**) либо `high_recommend ∈ {1,2}` (режим **scarce**) |
| **HIDDEN GEM** | `high_recommend ∈ {1,2}` И `high_neg = 0` И `non_high_total = 0` |
| **LOW SIGNAL** | всё остальное (мало данных; критика HIGH без LOW-противосигнала; только regret_missed) |

Ветка 2 (scarce) срабатывает ТОЛЬКО при `high_recommend = 0` — если есть
хоть одна HIGH-рекомендация, проверка идёт по веткам STRONG / WEAK /
HIDDEN GEM как обычно. Цель ветки 2 — закрыть случай, когда HIGH-авторы
**не доезжают** до места (selection bias DR-выборки), а non-HIGH
авторы единогласно критикуют — это сигнал, что место в маршрут не нужно.

`regret_missed` в правила не входит — это контекст, виден в поле 4
выхода. POI с преобладанием HIGH `regret_missed` попадёт в LOW SIGNAL
по счёту, но §8 Non-mainstream highlights его подсветит (§9.7).

#### Полный порядок приоритета правил (скрипт, сверху вниз)

Таблица выше — базовые 8 правил. С учётом слоёв F-55 (§6.10), F-56
(ниже) и ветки 3 (§6.11) скрипт применяет правила в таком порядке —
первое сработавшее даёт финальную категорию, кроме F-56-tiebreaker,
который применяется последним перед return:

1. **F-55 trap_archetype** (§6.10): `trap != null` → `hr = 0` → RED FLAG;
   `hr = 1` И `non_high_negative ≥ 1` → CONTESTED; `hr ≥ 2` → пропустить.
2. **CONTESTED (ветка 1):** `hr ≥ 1` И `high_neg ≥ 1`.
3. **RED FLAG (ветка 1):** `high_neg ≥ 1` И `hr = 0` И `low_recommend ≥ 1`.
4. **CONTESTED (ветка 3, lone OUTLIER, §6.11):** `hr ≥ 1` И `high_neg = 0`
   И `outlier_negative ≥ 1`.
5. **Ветка 2 (только scarce И `hr = 0`):** `non_high_negative ≥ 3` → RED FLAG;
   иначе `≥ 2` → CONTESTED.
6. **Стандарт:** STRONG / WEAK CONFIRMED / HIDDEN GEM / LOW SIGNAL (таблица выше).
7. **F-56 iconic tiebreaker** (последним): WEAK/HIDDEN GEM + `iconic_status != null`
   + `hr ≥ 1` + `high_neg = 0` → STRONG CONFIRMED.

Ветка 3 (шаг 4) идёт **до** F-56 (шаг 7): lone-OUTLIER-критика
перекрывает iconic-elevate. Ветки 3 и 2 взаимоисключающи по
`high_recommend`, поэтому их относительный порядок на результат не влияет.

#### UNESCO/iconic tiebreaker (F-56 v2)

**Проблема:** в текущей шкале известные UNESCO World Heritage / National
Treasure / iconic destinations с тонкой DR-выборкой получают абсурдные
ярлыки — «Ангкор-Ват = WEAK CONFIRMED», «Байон = HIDDEN GEM», «Та-Прохм
= LOW SIGNAL». Категории sample-relative, не reality-relative.

**Решение — tiebreaker, не auto-elevate:**

LLM при экстракции помечает POI флагом `iconic_status` если POI имеет
**высокий уровень узнаваемости / mandatory-for-region статус** по
general knowledge. Не каждый UNESCO obligatorily iconic — нужна реальная
высокая канониcal recognition.

| Условие | Действие скрипта |
|---|---|
| `iconic_status != null` И `high_recommend ≥ 1` И `high_neg == 0` И итоговая категория WEAK CONFIRMED или HIDDEN GEM | Auto-elevate до **STRONG CONFIRMED** |
| `iconic_status != null` И `high_recommend == 0` | НЕТ override. Без хотя бы одной HIGH-рекомендации tiebreaker не работает — это **не auto-include UNESCO**, а решение на границе |
| `iconic_status != null` И `high_neg ≥ 1` | НЕТ override (place is HIGH-contested — нормальная категория CONTESTED) |
| `iconic_status != null` И уже STRONG CONFIRMED | passthrough (без изменения) |

**Принцип:** tiebreaker применяется **только** когда:
1. Хотя бы один HIGH-автор подтвердил место (свежий evidence)
2. Нет HIGH-критики (нет conflict signal)
3. Стандартная категория получилась бы ниже STRONG из-за тонкости выборки

В этих условиях iconic status — **обоснованный signal**, что место
заслуживает STRONG, даже если статистически не набралось 3 HIGH-голосов.

**Что LLM помечает как iconic_status:**

| Уровень | Критерии | Примеры |
|---|---|---|
| `world_iconic` | Top-10 globally recognized по своей категории (architectural, natural, cultural) | Ангкор-Ват, Тадж-Махал, Мачу-Пикчу, Великая китайская стена, Парфенон, Колизей, Стоунхендж, пирамиды Гизы |
| `national_iconic` | Top symbol страны / её mandatory-for-region representation | Кёнбоккун (Сеул), Гранд-каньон (US), Уффици (Флоренция), Ангкор-Том в составе Ангкор-комплекса |
| `regional_iconic` | Иконичный для региона страны, но не общенациональный | Байон (Ангкор-комплекс), Та-Прохм (Ангкор-комплекс), Ват-Пху (Лаос), Кёнджу Бульгукса |

LLM использует general knowledge — не нужен external lookup. Порог
консервативности: когда сомневаешься — **не помечать**.

**Что НЕ iconic_status:**
- POI просто популярный — не iconic
- POI с UNESCO статусом, но не топ-attractor в категории — не iconic
  (пример: некоторые культурные ландшафты UNESCO без mass recognition)
- POI с локальной фактурой (street market, local viewpoint) — не iconic

**Формат в payload (опционально):**

```json
"iconic_status": "world_iconic" | "national_iconic" | "regional_iconic" | null
```

Tiebreaker — простой override; нет `reasoning` field (как у trap_archetype
или iconic_exception) — статус достаточно из общего знания.

#### Два режима категоризации

WEAK CONFIRMED — единственное правило, зависящее от **режима**. Режим
выбирает скрипт по **доле HIGH** = `high_authors_total / total_authors`
(`total_authors` — размер всей DR-базы, из YAML Stage 2, см. §6.6):

- **abundant** (доля ≥ порога, дефолт 30%) — консервативно: WEAK требует
  `high_recommend = 2`. Профиль хорошо представлен в выборке — строгие
  правила оправданы.
- **scarce** (доля < порога) — гибко: WEAK допускает `high_recommend = 1`
  (при `non_high_total > 0`). Место с одной HIGH-рекомендацией +
  подтверждением от OUTLIER/MEDIUM/LOW не падает в LOW SIGNAL. Нужно,
  когда HIGH-когорта узкая (минимальная DR-выборка, профиль конфликтует
  с источниками).

Порог — **доля**, не абсолют: редкий регион с маленькой, но профильной
выборкой (высокая доля HIGH) остаётся в abundant и не «деградирует» из-за
малого размера. STRONG CONFIRMED от режима **не зависит** — всегда
`high_recommend ≥ 3` (честно: 0 STRONG, если нет 3-консенсуса).

Режим определяет скрипт автоматически. Принудительно — флаг
`--mode abundant|scarce`. Если `total_authors` не передан — fallback на
абсолют (`high_authors_total ≥ 8` → abundant). Выбранный режим и доля —
в output (`aggregates.mode`, `aggregates.high_share`).

#### Per-region режим категоризации

Скрипт считает режим **на каждый регион отдельно** (`aggregates.mode_per_region`).
Это нужно когда поездка покрывает регионы разной туристической плотности:
часть регионов центральные («каноническое ядро» страны) — там много
HIGH-авторов; часть второстепенные — там 0-1 HIGH. Глобальный режим
терял эту разницу.

Правило per-region:
- Для каждого региона: `high_authors_per_region` = число различных HIGH-авторов,
  упомянувших хотя бы один POI этого региона.
- Если `high_authors_per_region >= --per-region-floor` (дефолт 3) → регион
  получает режим **abundant** для своих POI.
- Иначе → **scarce** (и в этом регионе работает scarce-ветка 2
  RED_FLAG/CONTESTED — генерируется по обоснованной non-HIGH критике, даже
  если глобально HIGH-доля высокая).
- POI без региона использует **глобальный** режим (`aggregates.mode`).

При `--mode abundant|scarce` (ручной форс) — все регионы получают
одинаковый режим (для тестов и совместимости).

В output каждый POI имеет `mode_used` (для диагностики), `aggregates.mode_per_region`
— карта регион → режим.

#### Cluster units (группировка POI)

POI могут быть помечены `cluster_id` в payload — это означает, что
LLM считает несколько POI **одной логической единицей**. Примеры:
храмовый комплекс с несколькими monuments объезжаемый одной экскурсией;
группа водопадов в одном национальном парке; археологический круг с
несколькими постройками одной эпохи.

Что делает скрипт:
- Группирует POI с одинаковым `cluster_id`.
- Считает **aggregated counts** (sum по всем members): `high_recommend`,
  `non_high_negative`, etc.
- Применяет `categorize()` на aggregated counts — получает `cluster_category`.
- Region cluster'а определяется по members (warning при cross-region —
  кластеризация **внутри одного региона**).
- В output отдельный массив `clusters[]` с cluster-level данными.

Индивидуальные POI **сохраняют свою личную категорию** (на основе своих
counts) — для display в полном списке. Cluster category — параллельный
сигнал для Stage 4, который видит cluster как **один selectable unit**:
если кластер STRONG_CONFIRMED, Stage 4 включает либо весь кластер, либо
ни одного member.

Когда LLM маркирует cluster:
- **Геогеографическая близость** + **общая логистика** (один base, общая
  экскурсия) + **тематическое единство** (один период истории, один
  caves system, один waterfalls system).
- Не маркировать как cluster обычные «по соседству» POI, у которых
  логика посещения независимая.
- Cluster содержит **2-5 POI** обычно; при ≥6 — это уже регион, не кластер.

Cluster naming: один член кластера несёт `cluster_name_ru` (для display
header'а); остальные — только `cluster_id`.

Поля POI для кластеризации (см. §6.6):
- `cluster_id: string | null` — идентификатор кластера, общий для members
- `cluster_name_ru: string | null` — display name (только у одного из членов)

### 6.6 Формат JSON-payload для скрипта

LLM формирует payload и передаёт в `aggregate_pois.py` через stdin:

```json
{
  "trip_slug": "аргентина_юг_2025-03",
  "total_authors": 43,
  "pois": [
    {
      "name_ru": "Лагуна-де-лос-Трес",
      "name_local": "Laguna de los Tres",
      "region": "лос_гласьярес_чальтен",
      "mentions": [
        {"author_id": "arg-helvhrav-001", "author_category": "HIGH", "tonality": "recommend"},
        {"author_id": "arg-mar-004", "author_category": "HIGH", "tonality": "recommend"},
        {"author_id": "arg-kuk-009", "author_category": "OUTLIER", "tonality": "neutral"}
      ],
      "quotes": [
        "helvhrav (HIGH): «подъём 4 часа, последний км — курумник, виды того стоят»"
      ],
      "characteristics": "Трек 8–10 ч туда-обратно. Выходить до рассвета. Март — холодно и ветрено наверху. Толпы на смотровой к полудню."
    }
  ]
}
```

Top-level поля payload:

- `trip_slug` — slug поездки.
- `total_authors` — **размер всей DR-базы** (число авторов), из YAML
  Stage 2 (поле `total_authors`). Нужен скрипту для выбора режима
  категоризации (§6.5). Передавать всегда, когда Stage 2 YAML доступен;
  без него скрипт уходит в fallback по абсолютному числу HIGH.
- `pois` — список POI (поля ниже).

Поля POI:

| Поле | Тип | Описание |
|---|---|---|
| `name_ru` | string | русская транслитерация, канон. **Обязательно.** |
| `name_local` | string \| null | латинский / местный вариант |
| `region` | string \| null | регион/кластер из scope поездки |
| `mentions` | list | упоминания, см. ниже |
| `quotes` | list[string] | 1 фраза от 2–3 авторов с указанием similarity-категории. Скрипт **не трогает**, пробрасывает в выход. |
| `characteristics` | string | сезон, время на посещение, логистика, толпы, риски, лучшее время дня. Скрипт пробрасывает в выход. |
| `iconic_exception` | object \| null | `{present: bool, reason: string}` — флаг «топ-1 эталон категории, исключённой из профиля» (§6.8). Опционально. Скрипт пробрасывает в выход + считает агрегат. |
| `commonly_combined_with` | list \| null | кандидаты на синергию: POI в том же регионе, которые типично комбинируются с этим POI в одну экскурсию. См. §6.9. Опционально. Скрипт пробрасывает в выход + считает агрегат. |
| `cluster_id` | string \| null | идентификатор кластера. Если POI — член логической единицы (храмовый комплекс, группа водопадов, археологический круг), все members имеют один `cluster_id`. Скрипт группирует и считает cluster-level aggregates. Опционально. |
| `cluster_name_ru` | string \| null | display name кластера (один из членов несёт, остальные опускают). Опционально. |
| `trap_archetype` | object \| null | `{archetype: string, reasoning: string}` — флаг туристической ловушки по архетипу (§6.10). Опционально. Скрипт пробрасывает + применяет сдвиг категоризации (если `archetype != null` И `high_recommend == 0` → RED FLAG; И `high_recommend == 1` И `non_high_negative ≥ 1` → CONTESTED). |
| `iconic_status` | string \| null | `world_iconic` / `national_iconic` / `regional_iconic` / `null` — F-56 v2 tiebreaker для известных UNESCO/iconic POI (§6.5). При наличии И `hr >= 1` И `hneg == 0` И стандартная категория ниже STRONG → auto-elevate до STRONG_CONFIRMED. |

Поля `mention`:

| Поле | Значения |
|---|---|
| `author_id` | id автора (из reading list Stage 2 или из таблицы для LOW) |
| `author_category` | `HIGH` / `OUTLIER` / `MEDIUM` / `LOW` |
| `tonality` | `recommend` / `neutral` / `criticize` / `regret_visited` / `regret_missed` |

Для `LOW` ожидается только `tonality: recommend` (§6.4).

Один автор упоминает один POI **максимум один раз** — одно упоминание
на пару (автор, POI). Правила STRONG / WEAK CONFIRMED считают
рекомендации от **разных** HIGH-авторов, поэтому дублировать автора в
`mentions` одного POI нельзя.

Запуск:
```bash
echo '<payload>' | python3 \
  ~/Library/CloudStorage/SynologyDrive-home/Claude-Memory/.../scripts/aggregate_pois.py
```
(или `{repo_root}/skills/travel-planning/scripts/aggregate_pois.py`,
если скилл установлен из репозитория).

### 6.7 Выходной JSON скрипта (что использовать в §8)

Скрипт возвращает на каждый POI в `pois[]`:

- `name_ru`, `name_local`, `region` — как на входе;
- `high_recommend`, `high_neutral`, `high_criticize`,
  `high_regret_visited`, `high_regret_missed`, `high_count`;
- `outlier_count`, `medium_count`, `low_recommend`, `low_count`,
  `non_high_total`, `non_high_negative`, `outlier_negative`;
- `category` — `STRONG_CONFIRMED` / `WEAK_CONFIRMED` / `HIDDEN_GEM` /
  `CONTESTED` / `RED_FLAG` / `LOW_SIGNAL` (машинный ключ — в YAML);
- **`category_label`** — русский ярлык той же категории («СИЛЬНОЕ
  ПОДТВЕРЖДЕНИЕ»). **Копируется в тело вербатим** (§6.5): переводить
  ключ самому запрещено — ярлык приходит из словаря скрипта;
- `mode_used` — режим, применённый к этому POI (per-region режим);
- `total_mentions`;
- `cluster_id`, `cluster_name_ru` — passthrough из payload (cluster);
- `quotes`, `characteristics`, `iconic_exception`,
  `commonly_combined_with` — проброшены без изменений;
  `iconic_exception` = `{present, reason}` (§6.8);
  `commonly_combined_with` = список `{poi_name, why}` или null (§6.9).

`pois[]` отсортирован для **region-grouped вывода** (§8): сначала по
региону (регионы — по убыванию числа POI), внутри региона — по приоритету
категории (STRONG → WEAK → HIDDEN GEM → CONTESTED → RED FLAG →
LOW SIGNAL), затем по убыванию `high_recommend`, `high_count`,
`total_mentions`. POI без региона — в конце.

Top-level:

- `region_order` — список регионов в порядке вывода (по убыванию числа
  POI; `без_региона` последним). По нему LLM расставляет заголовки
  регионов в §8, **не пересортировывая** `pois[]` руками;
- `aggregates`:
  - категории: `total_pois`, `strong_confirmed`, `weak_confirmed`,
    `hidden_gems`, `contested`, `red_flags`, `low_signal`,
    `iconic_exceptions`, `synergy_pairs`;
  - режим: `high_authors_total`, `total_authors`, `high_share`, `mode`
    (глобальный); **per-region режим:** `high_authors_per_region` (карта), `mode_per_region`
    (карта регион → режим);
  - **cluster clusters:** `total_clusters` (число cluster units), `pois_in_clusters`,
    `pois_standalone`;
  - regions: `by_region` (POI counts);
- `clusters[]` — список cluster-level записей. Поля:
  `cluster_id`, `cluster_name_ru`, `region`, `member_poi_names`,
  `member_count`, aggregated counts (`high_recommend`, `non_high_negative`, …),
  `cluster_category` (машинный ключ), **`cluster_category_label`** (русский
  ярлык — в cluster-header тела копируется вербатим), `mode_used`. Stage 4
  читает `clusters[]` как единицы выбора (включить кластер целиком или не
  включать).
- `warnings` — список аналитических предупреждений (anti-bloat и пр.);
- `diagnostic` — `{status, issues}`, статус `ok` / `warning` / `error`
  (качество входного payload).

### 6.8 Iconic exception — флаг исключения из профиля (опционально)

Опциональный per-POI флаг для случаев, когда место **явно конфликтует
с исключением в профиле**, но является **топ-1 эталоном своей категории
в регионе** — пропустить такое нелогично, даже если профиль формально
говорит «не люблю».

Примеры:
- профиль «не люблю наблюдение за животными» + Isla Martillo (пингвины
  Ушуаи) — топ-1 пингвинья колония региона;
- профиль «не люблю древнюю архитектуру» + Angkor Wat в Камбодже;
- профиль «не люблю крупные музеи» + Лувр в трёхдневном Париже.

**Высокий порог.** Ставить ТОЛЬКО когда выполнены все три условия:
1. Профиль **явно исключает** категорию места (раздел «Явные исключения»
   профиля).
2. POI — **топ-1 эталон** именно этой категории в этом регионе/стране
   (general knowledge + положение в выборке).
3. Если сомневаешься — **не ставь**. Лучше пропустить флаг, чем поставить
   на каждое лёгкое расхождение (флаг быстро обесценится).

Формат в payload (опционально, в объекте POI):

```json
"iconic_exception": {
  "present": true,
  "reason": "профиль исключает зоонаблюдение, но Isla Martillo —
             топ-1 пингвинья колония региона"
}
```

Если не применимо — поле опускается или `{"present": false, "reason": ""}`.
Если `present=true`, `reason` обязателен (скрипт выдаст info-issue
`iconic_no_reason`, если пустой).

**Флаг НЕ меняет категорию POI** — она считается скриптом по §6.5
независимо от iconic_exception. Это ортогональная аннотация.

**Чейн использования (важно):**
1. LLM проставляет `iconic_exception` при экстракции.
2. В §8 место выводится с дополнительной строкой
   `**Iconic exception:** {reason}` — пользователь видит флаг.
3. Если пользователь заинтересовался — он сам отмечает это в
   «Комментарии пользователя» (§8 поле 6).
4. Stage 4 при построении вариантов **приоритизирует места с
   пользовательским комментарием** — комментарий = явный сигнал
   «я этого хочу». Сам iconic-флаг без комментария Stage 4 не двигает —
   страховка от silent over-promote (модель не пропихивает
   профильное исключение в маршрут без согласия пользователя).

### 6.9 POI synergy — кандидаты на объединение в одну экскурсию (опц.)

Опциональный per-POI флаг для случаев, когда **два или более POI в
одном регионе типично комбинируются местными операторами в одну
экскурсию** (один билет, один отплыв/выезд, общий маршрут). LLM
проставляет этот флаг при экстракции; Stage 4 использует его как
**data-якорь** при сборке дней — пара с непустым `commonly_combined_with`
формулируется как «X + Y единой экскурсией», не два дня подряд.

**Принципы, не справочник.** Раздел НЕ содержит исчерпывающий список
известных комбо-туров. Конкретные синергии в каждом регионе LLM
выявляет **из характеристик и упоминаний** Stage 3, а не из памяти
модели как заученный реестр. Скилл не нужно править, если в новой
поездке найдётся новая пара комбинируемых POI — детекция работает по
общим признакам ниже.

**Признаки synergy (хотя бы один — достаточно для кандидата):**

1. **Общий оператор в characteristics.** Если в `characteristics` обоих
   POI назван один и тот же оператор / компания / тур-провайдер
   (явная строка в тексте, не догадка) — кандидат.
2a. **Общая стартовая локация ИЛИ общий природный объект.** Оба POI
   либо стартуют из одной точки (один порт, один шаттл, один трансфер,
   одна тропа-голова), либо ссылаются на **один и тот же физический
   объект** (один ледник, одна гора, одна тропа, один залив, один
   пляж, одна река). Маршрут и операторы не обязаны совпадать —
   достаточно общей физической привязки. Кандидат.
2b. **Общий тип транспорта от одной точки.** Оба POI — катерные выходы
   из одного порта; автобусные дневные туры по одной дороге; выезды
   одного шаттла; пешие хайки от одного trailhead. Полное совпадение
   маршрута не требуется — достаточно общего «как добираться». Кандидат.
3. **Явное упоминание совместности в reading list.** Хотя бы один автор
   reading list упомянул посещение обоих POI как часть одной экскурсии
   («делали X и Y одним туром», «в этот же выход зашли в...»). Это
   **дополнительное подтверждение**, не самостоятельное условие —
   усиливает кандидат, найденный по 1/2a/2b. Кандидат сам по себе тоже
   может быть отмечен по этому признаку, даже если 1/2a/2b слабы.

**«Один объект, разные грани» — паттерн особого внимания.**

Если два POI описывают **один и тот же физический объект** с разных
сторон или с разной активностью — это **сильный сигнал synergy**.
Типовые паттерны:

- мостки/смотровая на одном леднике + прогулка по льду этого же ледника
  (один поход / выезд закрывает оба POI);
- катерный осмотр залива + высадка на острове в этом же заливе;
- хайк к точке обзора горы + альтернативная боковая лагуна с той же
  тропы;
- старый город снаружи (прогулка) + знаковое здание внутри него (вход).

Это **принципы**, не справочник. Конкретные комбо в новой поездке
модель выявляет из characteristics и упоминаний, без правки скилла.

**Что НЕ является признаком synergy:**

- Просто «оба POI в одном регионе» — недостаточно (тогда synergy
  была бы у любых пар, что бессмысленно).
- Догадка LLM про комбо без явных следов в characteristics или
  упоминаниях.
- Туристическая близость без операторской или физической связи
  (например, две городские смотровые в разных кварталах — каждая
  самостоятельная активность).

**Порог применения.** Если хотя бы один из признаков 1 / 2a / 2b явно
выполнен — кандидат. Признак 3 усиливает уверенность, но **не обязателен**.
Если ни 1, ни 2a, ни 2b не выполнены — поле `commonly_combined_with`
оставляется пустым. Лучше пропустить synergy, чем выдумать комбо без
физического или операторского основания.

**Формат в payload (опционально, в объекте POI):**

```json
"commonly_combined_with": [
  {
    "poi_name": "Имя второго POI как name_ru",
    "why": "Краткое обоснование на основе характеристик / упоминаний"
  }
]
```

Если не применимо — поле опускается или `null` / `[]`. Поле
**симметричное**: если POI #X отмечен как комбинируемый с #Y, то #Y
**рекомендуется** также отметить с #X (для надёжности — Stage 4
проверяет любую сторону). Скрипт симметрию **не достраивает
автоматически** — это семантика LLM.

**Формат в §8 markdown** (выводится только при непустом
`commonly_combined_with`, как дополнительная строка после
характеристик):

```
**Combined with:** {Имя POI} — {why}
```

**Чейн использования (важно):**
1. LLM при экстракции по §6 проставляет `commonly_combined_with`
   кандидатов, если выполнен хотя бы один признак выше.
2. Скрипт `aggregate_pois.py` пробрасывает поле в output без
   изменений + считает `aggregates.synergy_pairs`.
3. В §8 пары выводятся строкой `**Combined with:**` под характеристиками.
4. Пользователь видит флаг и **может прокомментировать**: согласиться
   («ок, объединить»), уточнить («нет, хочу отдельно»), или ничего не
   писать (по умолчанию = согласие).
5. Stage 4 при сборке priority pool — пары с непустым
   `commonly_combined_with` (без отрицательного комментария пользователя
   на одном из POI) формулируются как **единая экскурсия в одном дне**.

**Флаг НЕ меняет категорию POI** — категория считается скриптом по
§6.5 для каждого POI независимо. Synergy — ортогональная аннотация
для Stage 4.

### 6.10 Known tourist-trap priors (F-55)

**Проблема.** Текущий RED FLAG-механизм чисто evidence-gated: срабатывает
только на фактическую критику HIGH/non-HIGH авторов в DR-выборке. При
тонкой выборке (0% местноязычных источников, ≥60% старых отчётов,
самосэмплированные блогеры избегают критики, чтобы не портить отношения с
PR-агентами) классические туристические ловушки **никогда не зажигаются**,
даже когда их репутация ловушки — широко известна.

Примеры провалов (зафиксированы в retro-валидациях):
- Tonle Sap floating villages (Chong Khneas) — классический развод на
  «сиротские деревни»; в КЛТ-выборке нейтральные упоминания → LOW SIGNAL.
- Pub Street, Сием-Рип — прозападная пьянка вне профильного интереса;
  упомянуто нейтрально → LOW SIGNAL.
- Phnom Bakheng sunset — переполненный hill с лимитом и плохим закатом;
  слабо критикован → LOW SIGNAL.

Senior travel agent **знает** эти архетипы без любой DR-выборки. Скилл
обязан давать аналогичный сигнал — это базовая компетенция, не fancy
feature.

**Решение: layer «known trap archetype priors».**

LLM при экстракции POI помечает каждый POI флагом `trap_archetype`, если
POI попадает под один из перечисленных архетипов туристических ловушек.
Флаг ортогонален категории; **не блокирует** включение в план, но **сдвигает
категоризацию**:

- Если у POI есть `trap_archetype` И `high_recommend == 0` → авто-RED FLAG
  (любой режим).
- Если у POI есть `trap_archetype` И `high_recommend == 1` И `non_high_negative ≥ 1`
  → авто-CONTESTED.
- Если у POI есть `trap_archetype` И `high_recommend ≥ 2` → категория остаётся
  по §6.5 правилам, но в `quotes` обязателен явный caveat: «Архетип
  туристической ловушки {имя_архетипа} — при включении планировать с
  осторожностью».

**Архетипы — справочник.** Базовый список (расширяемый); LLM сопоставляет
POI с архетипом по general knowledge:

| Архетип | Признаки POI | Примеры |
|---|---|---|
| `floating_village_orphan_scam` | Лодочная экскурсия к плавучей деревне с обязательным посещением «сиротского приюта» / школы (донация ожидается); цена непрозрачна, обязательная переплата гида | Chong Khneas (Tonle Sap), Cai Be (Mekong delta), некоторые Halong Bay tours |
| `pub_street_westernized_drinking` | Туристическая улица в азиатской стране, заполненная barами для бэкпэкеров, западной едой; противоречит локальной культуре | Pub Street (Siem Reap), Khao San Road (Bangkok), Bui Vien (HCM City) |
| `sunset_hill_overcrowded_with_limit` | Закатная точка с лимитом посетителей (300-500 чел/закат) и обязательной очередью; реальный закат посредственный из-за обзорной геометрии или дымки | Phnom Bakheng, частично Mount Phousi (Луангпрабанг) |
| `staged_ethnic_village` | «Этническая деревня» с расписанием «представлений» местной культуры (танцы, традиционные ремёсла), где жители одеваются в костюмы только во время туристических часов | Многие horeb-горные деревни в Северном Таиланде/Лаосе, Long Neck Karen villages |
| `floating_market_for_tourists` | Плавучий рынок, который существует **только** благодаря туристам; местные покупают на сухопутных рынках | Damnoen Saduak vs Amphawa, Cai Rang в late hours |
| `tuktuk_scam_route_with_gem_stops` | Тур-маршрут с обязательными остановками в «семейных мастерских» / магазинах драгоценностей где гид получает % | «Однодневный тур Бангкока» от частного тук-тук-водителя, частично «Grand Tour Vientiane» |
| `inflated_tourist_market` | Рынок, продающий имитацию ремесла по 3-10× ценам, со штатом «торговцев-актёров» | Russian Market PP частично, Night Market в туристических зонах LP |
| `crowded_temple_no_atmosphere` | Знаковый храм / монастырь в high-season настолько переполнен, что атмосферного опыта получить невозможно (фото только над толпой); требует dawn arrival для содержательного визита | Часть Angkor Wat в peak hours, Wat Pho в midday, частично Bayon |
| `tourist_train_artificial` | Аттракцион, заменивший аутентичный объект ради туристов | New Bamboo Train Battambang (vs original), частично Eastern & Oriental Express |

**Эвристика «подходит ли POI под архетип?»** LLM использует:
1. **Имя POI** + **регион** (если POI в типичной туристической зоне).
2. **Характеристики** (`characteristics` в payload): если в тексте упомянуты
   признаки архетипа (например, «сиротский приют», «обязательная донация»,
   «350 человек лимит», «работают только в туристические часы») —
   совпадение.
3. **General knowledge** LLM. Это **не** работа Stage 1 DR — LLM напрямую
   из своих знаний помечает архетип.

**Порог консервативности.** Когда сомневаешься — **не помечать**. Лучше
пропустить флаг, чем поставить ложноположительно. Архетип помечается, когда
есть **высокая уверенность** (3+ признака архетипа или прямое попадание в
типовое имя).

**Формат в payload (опционально, в объекте POI):**

```json
"trap_archetype": {
  "archetype": "floating_village_orphan_scam",
  "reasoning": "Chong Khneas — типичный пример: лодочная экскурсия с обязательным «сиротским приютом» и непрозрачной донацией, многократно описано в общедоступных гайдах как развод"
}
```

Если не применимо — поле опускается или `null`. Если `archetype` задан,
`reasoning` обязателен.

**Чейн использования:**
1. LLM при экстракции (§6.1-6.4) помечает `trap_archetype` для POI,
   попадающих под архетипы.
2. Скрипт `aggregate_pois.py` пробрасывает поле + применяет правило
   сдвига категоризации (см. выше).
3. В §8 markdown — POI с `trap_archetype` получает явную строку
   `**⚠ Tourist-trap archetype:** {archetype} — {reasoning}` под
   характеристиками.
4. Stage 4 priority pool — POI с `trap_archetype` помещается в
   `red_flags` варианта по умолчанию; user может перебить через
   user_comment («это всё равно интересно»).
5. Stage 5 — при включении POI с `trap_archetype` в day-by-day,
   обязательная mitigation-нота в описании дня («рассвет до толп; не
   брать "донационный" тур»).

**Что НЕ архетип** (распространённые false positives):
- POI **просто популярный** ≠ trap. Эйфелева башня — не trap, хоть и
  многолюдная.
- POI с **сезонными толпами** ≠ trap. Это weather/timing issue.
- POI с **высокой ценой** ≠ trap. Цена ≠ развод.
- POI **переоценённый медиа** ≠ trap, если не имеет признаков из таблицы
  выше. Это subject of taste.

Архетип — это **структурный механизм** обмана / искажения опыта, не
популярность.

### 6.11 OUTLIER overrated может сдвигать до CONTESTED (F-55, часть 2)

Сейчас одиночная OUTLIER-критика «overrated» структурно подавляется
HIGH-gate (CONTESTED ветка 1 требует HIGH-критика; ветка 2 scarce
требует ≥3 non-HIGH negative). Это слишком жёсткое: иногда единственный
голос против — правильный (Fabio Nodari про Муангнгой, Samantha про
Халласан).

**Правка правил §6.5:** добавляется **ветка 3** для CONTESTED:

> **CONTESTED (ветка 3, lone OUTLIER):** есть **≥1 OUTLIER-автор с
> обоснованной критикой** (`criticize` ИЛИ `regret_visited`) И
> `high_recommend ≥ 1` И `high_neg == 0`. POI остаётся в плане, но с
> явным флагом «есть профильно-релевантный одиночный негативный голос —
> рассмотри before commit».

OUTLIER — это автор с похожим профилем, но не вошедший в HIGH из-за
малого размера статистики. Его обоснованная критика — сильный сигнал,
не шум.

Скрипт `aggregate_pois.py` добавляет проверку ветки 3 после веток 1 и 2;
priority: ветка 1 > ветка 2 > ветка 3.

## 7. Правила работы

### Граница LLM vs скрипт

**LLM делает:**
- Извлекает POI из полей 14/15 карточек reading-list авторов.
- **Нормализует имена** POI (§6.2) — главная семантическая работа.
- Проставляет тональность каждому упоминанию (§6.3).
- Извлекает positive-упоминания LOW-авторов (§6.4).
- Назначает регион каждому POI.
- Пишет `quotes` (выдержки) и `characteristics` (характеристики места).
- Формирует JSON-payload.
- Собирает итоговый markdown по §8.
- Пишет раздел сравнения с предыдущим планом (§8) — чистая семантика.

**Скрипт `aggregate_pois.py` делает:**
- Считает упоминания на POI по тональности и категории автора.
- Применяет 6 правил категоризации (§6.5) детерминированно.
- Считает агрегаты (`total_pois`, счётчики категорий, `by_region`).
- Генерирует `warnings` (anti-bloat: STRONG CONFIRMED > 50%,
  RED FLAG > 30%).
- Возвращает `diagnostic` (валидность payload).
- Сортирует `pois[]` region-first (для region-grouped вывода §8),
  отдаёт `region_order`.
- Пробрасывает `quotes` и `characteristics` без изменений.

**LLM НЕ делает:**
- Не категоризирует POI руками — это скрипт.
- Не считает упоминания руками.
- Не приоритизирует места (это Stage 4).
- Не «улучшает» категорию из соображений «логичнее так» — категория
  только из скрипта.

### Web search

Для Stage 3 web search **не нужен** — все данные в карточках и профиле.
Допустима разовая сверка спорной нормализации имени места (одно ли это
место), но не для каждого POI.

### Что подсвечивать в выходе

- **RED FLAG** — выносить заметно: это главная находка Stage 3.
- **HIDDEN GEM** — в отдельный раздел Non-mainstream highlights (§8).
- **CONTESTED** — показывать обе стороны (цитаты «за» и «против»).
- **Anti-bloat warnings** скрипта — в начало markdown, после контекста.

### Запреты и обязательства по выводу

- **НЕ опускать данные «for brevity».** Все POI из payload — в выходном
  файле. Если контекст не вмещает — выдать файл в две части (§9.8),
  но не сокращать.
- **Имя файла строго `3_poi_pool.md`.** Без суффиксов, без
  trip_id и даты в имени.
- **«Сохранить как» — не в теле файла**, отдельным сообщением в чат
  (см. §8 и `../storage-and-naming.md` §9).
- **trip_id одной системой письма** — при mixed-script одной строкой
  предупредить, добавить `trip_id_warning: mixed_script` в YAML
  (см. `../storage-and-naming.md` §10.8).
- **REGION-FIRST ordering — НЕ category-first.** Структура `##
  Полная агрегация POI` обязана быть сгруппирована **по регионам**
  (`### {Регион} — {N} POI`), внутри региона — по категории. **Запрет**
  на category-first структуру (`## STRONG CONFIRMED` → `## WEAK
  CONFIRMED` → ... — это нарушение spec, не вариант). При сомнении —
  читать `region_order` из output скрипта и буквально следовать ему.
  Sonnet+thinking иногда срывается в category-first; Opus stable.
- **«Комментарий пользователя:» ПОД КАЖДЫМ POI.** Это поле — не
  optional. Под каждым POI **обязательно** строка `6. Комментарий
  пользователя:` (пустая, для ручной калибровки). Спецификация в §8 ниже.
  Пропуск этого поля под хотя бы одним POI — нарушение spec.

### Pre-emit checklist для Stage 3 (обязательный self-check)

Перед сохранением файла прогнать **обе** проверки. Счётчик POI
автоматизирован — прогнать:

```bash
python3 skills/travel-planning/scripts/check_format.py --stage 3 < 3_poi_pool.md
```

Exit 0 = OK; exit 1 = нарушения в stderr. Покрывает `yaml_delimiters` и
`poi_count` (`total_pois` == числу «Комментарий пользователя»). Остальные
пункты ниже — вручную.

1. **Region-first ordering:** `## Полная агрегация POI` содержит
   секции `### {Регион} — {N} POI` в порядке `region_order`. Нет
   секций-категорий (`## СИЛЬНОЕ ПОДТВЕРЖДЕНИЕ` и т.п.) на верхнем уровне.
2. **POI comment placeholders:** под **каждым** POI есть строка
   `6. Комментарий пользователя:` (пустая или с уже заполненным
   текстом). Считать: число POI в файле = число строк
   «Комментарий пользователя:».
   → `check_format.py --stage 3` проверяет автоматически (`poi_count`).
3. **Формат выдержек (контракт с экспортом):** каждая строка поля 4 —
   `- {Автор} #{N} (ВЫСОКАЯ|ОСОБЫЙ СИГНАЛ|СРЕДНЯЯ|НИЗКАЯ): {текст}`. Без ярлыка
   категории в круглых скобках + двоеточия экспорт вытащит ноль авторов под POI.
   Проверка: число строк-выдержек по всем POI ≥ суммы счётчиков с
   содержательной цитатой (полного равенства нет — counts включают
   упоминания без цитаты, §6; но ноль выдержек при ненулевых counts —
   сигнал, что формат поехал).
4. **Язык категорий (§6.5):** в теле — русские ярлыки, скопированные
   вербатим из `category_label` / `cluster_category_label`; в YAML-счётчиках
   и в payload — английские ключи. Английский ярлык в теле (`— LOW SIGNAL`,
   `(HIGH):`) или русский в YAML = нарушение. Проверить: заголовки POI,
   cluster-header, таблица распределения, поля 2–4 каждого POI.

Нарушение любой проверки = НЕ сохранять, исправить, перепрогнать.

### Стиль

- Без эмодзи в теле файла (в чате допустимы для severity).
- Категории — каноническими ярлыками (§6.5): в теле русские, в YAML английские.
- Выдержки (поле 4) — короткие, строго в формате
  `- {Автор} #{N} ({КАТЕГОРИЯ АВТОРА}): {текст}` (см. §8 — контракт с экспортом).
- **Тело — по-русски.** `warnings` формулируй русским текстом: severity —
  словом из канона (`критично:` / `погранично:` / `инфо:`, поле
  `severity_label` скрипта), категории — русскими ярлыками.
- **Никаких ссылок на внутренние файлы скилла в теле артефакта**
  («см. stage3-poi.md §6.5», «по §6.10 спеки»). Пользователь этих файлов не
  видит. Нужен смысл — сформулируй его словами: не «RED FLAG по §6.4 ветка 2»,
  а «ни один автор категории ВЫСОКАЯ не рекомендует, трое из остальных
  обоснованно критикуют».

## Полная агрегация POI

Сгруппировано **по регионам** — так удобнее планировать маршрут.
Регионы идут в порядке `region_order` из output скрипта (по убыванию
числа POI). Внутри региона POI — ровно в порядке `pois[]` из скрипта:
приоритет категории (STRONG CONFIRMED → … → LOW SIGNAL), затем по
убыванию `high_recommend`. Категория каждого POI видна в его заголовке,
отдельные секции по категориям не нужны — сводка в таблице
«Распределение по категориям».

LLM **не пересортировывает** `pois[]` — идёт по списку и вставляет
заголовок региона при смене региона. Нумерация `#{N}` — сквозная по
всему файлу.

### {Регион} — {N} POI · **тег:** _____

**Stage 3 → Stage 4 touchpoint (теги регионов).** Сразу после заголовка
региона — поле `**тег:** _____` для пользовательской калибровки. Скилл
оставляет поле **пустым** при генерации; пользователь дописывает руками
одно из значений:

- `обязательно` — регион обязателен в финальном плане. Stage 4
  включает во **все** варианты.
- `можно` — на усмотрение Stage 4 (default; пустое поле трактуется как
  `можно`).
- `не интересно` — не включать ни в один вариант.

Поддерживаются короткие синонимы: `must` / `да` / `ok` / `skip` / `нет`.
Регистр и пробелы вокруг игнорируются. Произвольный freeform-комментарий
после значения допустим: `**тег:** обязательно — ради этого вся поездка` —
Stage 4 сохранит comment в свой YAML.

**Описание региона из Stage 0** (passthrough для удобства пользователя):
после строки тега — 2-3 предложения о регионе, скопированные из
`0_scope.md` секции `## Region universe`. Это избавляет от
переключения между файлами при тегировании.

```markdown
### {Регион} — {N} POI · **тег:** _____

— из Stage 0: {2-3 предложения о регионе с density tag и сезонной
  пометкой}
```

**Комментарий к региону (опц., заполняет пользователь).** Свободный текст —
что ещё хочется посмотреть в регионе, чего нет среди POI, и прочие пожелания
по региону целиком. Одна строка в шапке региона (до первого кластера/POI),
обычно сразу под заголовком:

```markdown
### {Регион} — {N} POI · **тег:** обязательно

**Комментарий к региону:** ещё храм Кирымса, рассвет на Тохамсане
```

Скилл при генерации эту строку **не эмитит** — её создаёт пользователь (руками
или полем «Комментарий к региону» в HTML-экспорте). Метка фиксированная:
`**Комментарий к региону:**`; «Комментарий пользователя» в ней недопустим —
по числу таких строк сверяется `total_pois`. Потребитель — Stage 4 (§2 Inputs
`stage4-variants.md`).

**Per-region режим:** после описания —
**одна строка** с указанием режима, выбранного скриптом:

> **Режим категоризации региона:** abundant (HIGH-авторов: 5) — стандартные
> правила
>
> или
>
> **Режим категоризации региона:** scarce (HIGH-авторов: 1) — СЛАБОЕ
> ПОДТВЕРЖДЕНИЕ допускает 1 рекомендацию автора ВЫСОКАЯ; ветка 2
> КРАСНОГО ФЛАГА / СПОРНОГО активна при критике от не-ВЫСОКИХ

Берётся из `aggregates.mode_per_region` и `aggregates.high_authors_per_region`.

**Исключение из правила языка:** `abundant` / `scarce` и подстрока
`(HIGH-авторов: N)` в этой строке — **якорь парсера, пиши дословно**.
Русифицируется только пояснение после тире.

**Cluster units:** если в регионе есть кластеры (`clusters[]` из
output скрипта с `region == {текущий регион}`), они выводятся **перед**
индивидуальными POI в отдельном блоке:

```markdown
#### Cluster: {cluster_name_ru} ({member_count} POI) — {cluster_category_label}

Логическая единица: {member_poi_names через запятую}. Кластер выбирается
**целиком** в Stage 4 (включить все members или ни одного).

Aggregated counts: ВЫСОКАЯ рекоменд. {high_recommend} / ВЫСОКАЯ критика
{high_criticize+high_regret_visited} / не-ВЫСОКАЯ критика {non_high_negative}.

— затем members кластера ниже в общем списке POI региона, каждый со своей
   индивидуальной категорией (не cluster_category).
```

Для **каждого** POI региона:

```
#{N} **{name_ru}** ({name_local}) — {category_label}
1. Регион: {region}
2. ВЫСОКАЯ: {high_count} (рекоменд. {high_recommend} ·
   нейтр. {high_neutral} · критик. {high_criticize} ·
   жалеют о посещении {high_regret_visited} ·
   жалеют что пропустили {high_regret_missed})
3. ОСОБЫЙ СИГНАЛ / СРЕДНЯЯ / НИЗКАЯ: {outlier_count} / {medium_count} / {low_count}
4. Выдержки:
   - {Автор} #{N} ({КАТЕГОРИЯ АВТОРА}): {выдержка}
   - {Автор} #{N} ({КАТЕГОРИЯ АВТОРА}): {выдержка}
5. Характеристики: {characteristics}
**Iconic exception:** {reason}      ← ТОЛЬКО если iconic_exception.present=true
**Combined with:** {Имя POI} — {why}   ← ТОЛЬКО если непусто commonly_combined_with
**Cluster:** {cluster_name_ru}      ← ТОЛЬКО если POI имеет cluster_id
6. Комментарий пользователя:
```

(Поля 1–3 — числа из скрипта; выдержки и характеристики — `quotes` и
`characteristics` из output; ярлык категории — `category_label` из
скрипта вербатим, английский `category` идёт только в YAML (§6.5).

**Формат строки выдержки — строгий (контракт с экспортом):**
`- {Автор} #{N} ({КАТЕГОРИЯ АВТОРА}): {выдержка}`, где `{Автор}` — имя/ник как
в карточке Stage 1, `#{N}` — номер карточки DR (= `author_id` Stage 2,
даёт ссылку на отчёт), `{КАТЕГОРИЯ АВТОРА}` — русский ярлык категории автора
из Stage 2: `ВЫСОКАЯ` | `ОСОБЫЙ СИГНАЛ` | `СРЕДНЯЯ` | `НИЗКАЯ`,
`{выдержка}` — короткая содержательная цитата/пересказ. Экспортный
парсер достаёт автора и категорию по этому шаблону; отклонишься — он
вытащит ноль выдержек и в PDF/DOCX не будет авторов под POI. Якорь
парсера — `({КАТЕГОРИЯ АВТОРА}):`, поэтому ярлык + двоеточие обязательны.

Строка `**Iconic exception:**` — без номера, рендерится **только** когда
`iconic_exception.present=true` в output скрипта; для большинства POI
её нет. См. §6.8. Строка `**Combined with:**` — без номера, рендерится
для каждого элемента непустого `commonly_combined_with` (отдельная
строка на каждую пару). См. §6.9.)

**Поле 6 «Комментарий пользователя» — оставляется пустым.** Это место
для ручной калибровки: пользователь сам отмечает, что ему интересно или
не интересно. Если у POI есть `Iconic exception` (строка выше) и
пользователь решил его включить — он отмечает это здесь; Stage 4
приоритизирует POI с пользовательским комментарием явно. Скилл поле
сам не заполняет и при перезапуске Stage 3 не восстанавливает (как и
весь файл — manual save).

Регионы — все из `region_order`. POI без региона — секция
«### Без региона — {N} POI» в конце, если такие есть.

## Источники (реестр авторов)

- c{NN} | {имя автора} | {год} | {url-поле из поля 1 Stage 1, дословно}
- c{NN} | {имя автора} | {год} | {url-поле}
```

**Реестр авторов — ОБЯЗАТЕЛЬНАЯ хвостовая секция** (контракт с экспортом,
см. `stage3-output-spec.md`). По строке на **каждый `cNN`, упомянутый в
выдержках** (`#{N}`). Делает `3_poi_pool.md` самодостаточным: экспорт одним
файлом получает URL/год авторов отсюда, **не открывая `1_dr_reports.md`**.

- Формат строки строгий: `- cNN | имя | год | url-поле` (4 поля через `|`).
- **`url-поле` копируется ДОСЛОВНО из поля 1 карточки Stage 1 `#N`** — со
  всеми ссылками и метками: `<url1> (Пекин) + <url2> (Сучжоу) — «Название»`.
  Не переписывать, не сокращать — экспортёр разберёт сам (метки → текст
  ссылок; без меток → название→url1 + «часть 2»).
- `год` — поле 4 Stage 1 (можно пусто). `имя` — как в выдержках.
- У тебя уже открыт `1_dr_reports.md` (шаг §7 п.3) — бери значения оттуда.

### SSOT и роль YAML

YAML-шапка дублирует счётчики категорий из таблицы распределения. Они
**должны совпадать** — скрипт возвращает их одним JSON. Рассинхрон
возможен только при ручном пересчёте (запрещено, §10).

### «Сохранить как» — НЕ в файле

Отдельным сообщением в чат после файла, содержание зависит от
environment — см. `../storage-and-naming.md` §9.

## 9. Граничные случаи

### 9.1 POI без региона

Карточка упоминает место, но регион не определяется (общая фраза,
место вне scope-регионов). В payload `region: null`. Скрипт относит
такие POI в bucket `без_региона` в `by_region` и поднимает diagnostic
issue `poi_without_region` (severity warning). В §8 такие POI — в своих
категориях, поле «Регион: не определён».

### 9.2 Дубль POI после нормализации

Если в payload два POI-объекта с одинаковым `name_ru` (нормализация
не свела) — скрипт поднимает diagnostic `duplicate_poi` (warning) и
обрабатывает оба как есть. При warning — пересмотреть нормализацию
(§6.2), пересобрать payload, перезапустить скрипт. Скрипт сам дубли
**не сливает** — это семантика.

### 9.3 POI без упоминаний

POI-объект с пустым `mentions` — diagnostic `poi_no_mentions` (warning),
скрипт ставит LOW SIGNAL. Обычно — ошибка сборки payload.

### 9.4 reading_list пуст (HIGH + OUTLIER = 0)

Stage 2 не дал HIGH/OUTLIER авторов. Stage 3 не имеет основы — POI
агрегировать не из чего.

- Отказать ОДНОЙ строкой: «Stage 2 reading list пуст (HIGH + OUTLIER =
  0). Stage 3 без HIGH-авторов не имеет статистической основы. Расширь
  источники через Stage 1 Mode B и перезапусти Stage 2».
- НЕ запускать Stage 3 на одних MEDIUM/LOW.

### 9.5 Stage 2 был с partial_parse / skipped_authors

Если YAML Stage 2 содержит `partial_parse: true` или
`skipped_authors_count > 0`:

- Авторы из `llm_fallback_authors` — их URL/имена разбирались
  семантически; данные карточек надёжны, но в `## Контекст` одной
  строкой отметить: «{N} авторов Stage 2 разобраны llm-fallback».
- `skipped_authors` — эти авторы не попали в reading list вообще,
  Stage 3 их не видит. Отметить в контексте, если их много.

### 9.6 Profile drift

Профиль обновлён после создания Stage 2 (`updated` профиля > `created`
Stage 2) — одной строкой предупредить: «профиль обновлён {date}, Stage 2
создан {date}; категоризация POI наследует фильтр Stage 2. При
существенных изменениях — перезапусти Stage 2». Не блокировать.

### 9.7 POI только с regret_missed

Место, которое несколько HIGH-авторов упомянули как «жалею, что
пропустил», но никто не посетил. По счёту (§6.5) — LOW SIGNAL
(`high_recommend = 0`). Это корректно: подтверждённого опыта нет. Но
сигнал ценный — обязательно вынести в Non-mainstream highlights с
явной пометкой «N HIGH-авторов жалеют, что пропустили».

### 9.8 Большой выход не помещается в один ответ

Если POI много и детальный §8 не вмещается в один ответ — разбить:
- `3_poi_pool.md` — YAML + распределение + warnings + STRONG/
  WEAK/HIDDEN GEM + Non-mainstream highlights + сравнение с планом;
- `3_poi_pool_details.md` — CONTESTED + RED FLAG + LOW SIGNAL.

В YAML основного файла — `details_file: 3_poi_pool_details.md`.
«Опущено for brevity» — запрещено (§10).

### 9.9 Opt-in исправление при `diagnostic.status = error`

Скрипт ставит `error` при структурных проблемах payload (POI без
`name_ru`, невалидные `author_category`/`tonality`, пустой `pois`).
Скилл **не чинит payload молча**. Выдать ОДИН batch с диагностикой и
вариантами:

```
Скрипт aggregate_pois.py: {N} POI, статус error:

- {issue 1: severity, code, message, affected_pois}
- ...

Как действовать:
1. Я исправлю проблемные POI (перепроверю извлечение и нормализацию,
   пересоберу payload, перезапущу скрипт).
2. Пропустить проблемные POI — они не попадут в агрегацию.
3. Стоп — посмотрю сам.
```

Только после явного выбора продолжать. Вариант 1 — это пересборка
payload самим скиллом (исправление своей же ошибки извлечения), не
«выдумывание» — поэтому, в отличие от Stage 2 §9.12, он не требует
маркировки в YAML. Но если пользователь выбрал вариант 2 — добавить
в YAML `skipped_pois_count: N`.

### 9.10 Все POI одной категории

Если скрипт выдал, например, 80% STRONG CONFIRMED — сработает anti-bloat
warning. Это сигнал, что либо нормализация слишком агрессивно слила
места, либо reading list однородный. Показать warning, не блокировать;
в `## Контекст` отметить.

### 9.11 trip_id со смешанной системой письма

См. `../storage-and-naming.md` §10.8. Одной строкой предупредить,
добавить `trip_id_warning: mixed_script` в YAML, продолжить.

### 9.12 Узкая HIGH-когорта (мало HIGH-авторов)

Дефолтный случай при минимальной DR-выборке (Stage 1 = 20–30 отчётов,
худший случай ~20): после фильтра Stage 2 HIGH-авторов мало — единицы.
Последствие для категоризации:

- STRONG CONFIRMED требует ≥ 3 рекомендаций от **разных** HIGH-авторов.
  Если HIGH-авторов всего 0–2 — STRONG CONFIRMED **недостижима** по
  построению; скрипт выдаёт critical warning.
- Если HIGH-авторов 3–5 — STRONG строг (нужно согласие большей части
  когорты); скрипт выдаёт info warning.

Это **ожидаемое** поведение, не дефект Stage 3. При узкой когорте
большинство POI окажутся в WEAK CONFIRMED / HIDDEN GEM / LOW SIGNAL —
категории честно отражают, сколько похожих путешественников подтвердили
место. Не пытаться «накрутить» STRONG, переписывая категории руками
(они приходят только из скрипта, §10).

Если пользователю нужно больше STRONG-сигнала, правильный шаг — **не**
смягчать порог, а расширить источники через Stage 1 Mode B и
перезапустить Stage 2. Порог `strong_min` менять только осознанно
(флаг `--strong-min`), зафиксировав причину в `## Контекст`.

При узкой когорте скрипт обычно сам уходит в режим **scarce** (§6.5):
WEAK CONFIRMED тогда принимает места с 1 HIGH-рекомендацией (+ внешнее
подтверждение), и распределение не схлопывается полностью в LOW SIGNAL.
STRONG при этом не трогается. Режим виден в `aggregates.mode` и в
`## Контекст`.

## 10. Что НЕ делать

- НЕ категоризировать POI руками — категория только из скрипта.
- НЕ считать упоминания руками.
- НЕ приоритизировать места по «обязательно / желательно» — это Stage 4.
- НЕ строить маршрут, не предлагать конкретные изменения плана.
- НЕ рекомендовать отели и рестораны (Stage 5), не называть цены.
- НЕ сливать дубли POI скриптом — нормализация имён это работа LLM (§6.2).
- НЕ объединять разные места с похожими именами.
- НЕ опускать POI «for brevity» — все из payload в выходе (§7, §9.8).
- НЕ изобретать категории. Канон строго (§6.5): в теле — **СИЛЬНОЕ
  ПОДТВЕРЖДЕНИЕ**, **СЛАБОЕ ПОДТВЕРЖДЕНИЕ**, **СКРЫТАЯ ЖЕМЧУЖИНА**,
  **СПОРНЫЙ**, **КРАСНЫЙ ФЛАГ**, **СЛАБЫЙ СИГНАЛ**; в YAML —
  `strong_confirmed` … `low_signal`. Запрещены «must-see», «Tier-1/2/3»,
  звёзды, проценты «важности».
- НЕ переводить ярлык категории самостоятельно и НЕ подбирать синоним
  («ПОДТВЕРЖДЁН», «СИЛЬНОЕ СОВПАДЕНИЕ») — только вербатим-копия
  `category_label` / `cluster_category_label` из output скрипта (§6.5).
- НЕ оставлять английский ярлык в теле (`— LOW SIGNAL`, `(HIGH):`) и НЕ
  класть русский ярлык в YAML — это две разные формы одной категории.
- НЕ ссылаться в теле артефакта на внутренние файлы скилла («см.
  stage3-poi.md §6.5») — пользователь их не видит, формулируй смысл словами.
- НЕ изобретать тональности. Канон строго: `recommend`, `neutral`,
  `criticize`, `regret_visited`, `regret_missed`.
- НЕ запускать Stage 3 на одних MEDIUM/LOW при пустом reading_list (§9.4).
- НЕ чинить payload молча при `diagnostic.status = error` — диалог
  по §9.9.
- НЕ писать «Сохранить как» в тело файла (§8).
- НЕ использовать sandbox-пути (`/home/claude/`, `/tmp/`) для файла-
  результата (см. `../storage-and-naming.md` §9).
- НЕ изобретать имя файла. Строго `3_poi_pool.md` — через
  подчёркивания `_`, без пробелов («3 poi aggregation.md» —
  наблюдаемая ошибка модели).
- НЕ использовать `-----` (пять дефисов) или иное число — YAML
  frontmatter строго ровно `---` (три дефиса) и сверху, и снизу. Иначе
  поля шапки «уезжают» под предыдущий list-item, downstream Stage 4
  не парсит. См. `../storage-and-naming.md` §5.
- НЕ продолжать на Haiku (model self-check, шаг 0).
- НЕ реконструировать reading_list, таблицу авторов или POI из сниппетов
  и превью — работать только с полным файлом (Synology / приложение,
  см. `../storage-and-naming.md` §8.0).
- НЕ выставлять `--mode` руками без причины — режим (abundant / scarce)
  скрипт выбирает сам по доле HIGH. Ручной форс — только осознанно,
  с пометкой причины в `## Контекст`.
- НЕ забывать `total_authors` в payload — без него режим уходит в
  fallback по абсолюту (§6.5, §6.6).

## 11. Следующий шаг

После того как скилл сгенерировал `3_poi_pool.md`, в чат выводится
**одно сообщение** с инструкцией для пользователя:

> Stage 3 готов. POI pool в `3_poi_pool.md`. Прежде чем строить
> варианты — заполни **теги** регионов прямо в md:
>
> - под каждым `### {Регион} — {N} POI` есть поле `**тег:** _____`;
> - впиши руками одно из: `обязательно` / `можно` / `не интересно`
>   (или короткие синонимы: `must` / `да` / `skip` / `нет`);
> - пустое поле трактуется как `можно` (default).
>
> Опционально под каждым POI можно дописать `Комментарий пользователя:`.
>
> Когда готов — скажи «строй варианты» (или «Stage 4 для {trip_id}»).
> Stage 4 прочитает теги из файла и предложит 2-3 варианта маршрута.

**Никакого `user_region_tags.yaml` или другого отдельного файла для
тегов нет** — теги живут в `3_poi_pool.md` под региональными
заголовками. Это и есть user-facing touchpoint между Stage 3 и Stage 4
(см. `../methodology.md` §2 «3-tag система»).

Если выборка дала много RED FLAG (anti-bloat warning) или мало STRONG/
WEAK CONFIRMED — рассмотреть возврат к Stage 1 Mode B для расширения
источников перед Stage 4.

При следующих итерациях (re-run Stage 4 после v1 / v2 / ...) пользователь
просто меняет теги в этом же `3_poi_pool.md` и запускает Stage 4 заново —
создаётся `4_variants_v{N+1}.md`. Stage 3 не пересобирается, DR не
пересобирается.
