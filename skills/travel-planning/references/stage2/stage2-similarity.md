# stage2-similarity.md

Полная спецификация Stage 2 — фильтр авторов по similarity с профилем
путешественников. На входе — база DR-карточек от Stage 1 (20-field).
На выходе — каждый автор с разбивкой score 0–10 по 6 компонентам и
категорией HIGH / MEDIUM / LOW / OUTLIER / UNSCORED.

Философия и место в пайплайне — `../methodology.md` §3 «Stage 2».

## 1. Назначение

Применить **профиль путешественников** к каждому автору из Stage 1
и отделить отчёты от **похожих** путешественников (HIGH) от стандартных
туристов (LOW). Дополнительно выделить **OUTLIER** — авторов с низким
общим score, но конкретным сильным сигналом, релевантным какому-то
аспекту профиля (например, фотограф для фото-профиля, food-blogger для
гастро-профиля, китайско-говорящий для Китая).

Зачем фильтр **после** DR, а не до:

- Если профиль применить до сбора, DR будет искать в узком сегменте и
  пропустит OUTLIER-отчёты. А именно они ценны как контр-индикаторы
  на Stage 3 (RED FLAG места — хвалят стандартные туристы, критикуют
  HIGH-similarity).
- Discrete фильтр на готовой выборке прозрачнее: видно распределение
  по категориям, можно проверить, что HIGH не пуст и не доминирует
  одним стилем.

Зачем нужны 6 компонентов с весами, а не один общий «похож/не похож»:

- Делает scoring проверяемым: пользователь видит, *почему* автор HIGH.
- Позволяет калибровать веса под профиль (фото-ориентированному
  пользователю focus важнее demo).
- Различает «похожий стиль + другой фокус» от «другой стиль +
  одинаковый фокус» — оба могут быть HIGH, но по разным причинам.

## 2. Inputs / Outputs

**Inputs:**

- Профиль: `{travel_root}/profiles/{profile_id}.md` ← Read
- DR-база: `{travel_root}/trips/{trip_id}/1_dr_reports.md` ← Read
  (или, если файл не сохранён, контент DR в чате — см. §3 Случай B)
- Опц.: `{travel_root}/trips/{trip_id}/0_scope.md` — для шапки YAML

**Outputs (в чат + manual save пользователем):**

- `{travel_root}/trips/{trip_id}/2_similarity.md` — Stage 2 артефакт
  с YAML-шапкой, распределением, списком для детального чтения и
  per-author разбивкой по 6 компонентам.

**Downstream:** Stage 3 (POI aggregation) читает `reading_list`
(HIGH + OUTLIER) и пробегает по их полям 14–15 в исходных DR-карточках.

## 3. Поток

### Случай A: `1_dr_reports.md` сохранён в `{travel_root}` — 2 turn'а

#### Turn 1 — пользователь
«нужна фильтрация авторов для {trip_id}», «Stage 2 для {trip_id}»,
«применить similarity».

#### Turn 2 — скилл

**0. Model self-check (обязательный первый шаг).** Назвать модель
одной строкой: «Я модель: <name>. Stage 2 рассчитан на Opus.»
Логика реакции — см. `../../SKILL.md` блок «Stage 2: model self-check».
Если Haiku — остановиться. Если Sonnet+thinking — продолжать с warning.
Если Opus — без warning.

1. Gate-проверки (§4).
2. Read профиля (`profile_path`).
3. Получить DR-базу `1_dr_reports.md` — источник по приоритету
   `../storage-and-naming.md` §8.0 (приложенный файл → Synology mount;
   сниппеты и превью данными не считать).
4. Опц. Read `0_scope.md` для подтверждения метаданных (duration,
   season, regions).
5. **Profile drift check.** Сравнить `updated` профиля с `dr_run_date`
   из YAML Stage 1. Если профиль обновлён ПОСЛЕ DR — одной строкой
   предупредить, продолжить (см. §9.6).
6. **bash: запуск `scripts/parse_dr_cards.py`** (**diagnostic-only**
   режим, не парсер payload'а):
   ```
   python3 .../parse_dr_cards.py --trip-slug <trip_id> < 1_dr_reports.md
   ```
   Скрипт **не строит JSON-template** с авторами и components. Возвращает
   только **diagnostic** (status, issues, cards_without_url) + **card_summaries**
   (id, url, name, user_added) — для антигаллюцинационной сверки.

   **Read `diagnostic.status` из output:**
   - `"ok"` — все карточки распознаны чисто (count match, URLs present).
     Продолжать на шаг 7.
   - `"warning"` — мелкие пропуски (имена, расхождение count в пределах
     20%). Одной строкой пользователю: «парсер: {N} карточек, мелкие
     пропуски ({issue codes}). Продолжаю.» Продолжать.
   - `"error"` — формат deformed (>20% без URL ИЛИ большое расхождение
     count). **Остановиться, не парсить руками самостоятельно.**
     См. §9.12 «Opt-in LLM-fallback при error».

   Если скрипт вернул exit 1 (zero cards) или exit 2 (пустой stdin) —
   сообщить пользователю и спросить, что приложено в чате. Не угадывать.
7. **LLM строит полный payload, читая `1_dr_reports.md` напрямую.**
   Граница LLM/script: script — диагностика, **LLM — семантическая
   интерпретация**. Для каждой карточки:
   - **id, url, name, user_added** — взять из `card_summaries` (антигаллюцинационная
     сверка с output скрипта). Если LLM видит в markdown больше карточек
     чем в card_summaries — это сигнал, что diagnostic пропустил deformed
     карточки; вернуться к шагу 6 с диалогом §9.12.
   - **components 0–10** — заполнить по rubric'ам §6.2 на основе **текста
     карточки в markdown**, не из script output.
   - **outlier_signal** — определить по §6.4. `present=false` для большинства;
     `present=true` только для действительно уникального сильного сигнала,
     релевантного профилю. **Доля OUTLIER ≤ 30%** (см. §10), скрипт
     similarity_score выдаст critical warning при превышении.
8. **bash: запуск `scripts/similarity_score.py`** через stdin:
   ```
   echo '<filled JSON-payload>' | python3 .../similarity_score.py
   ```
9. Распарсить выход скрипта → собрать markdown по §8 (распределение,
   reading list с тремя группами, per-author breakdown с
   weighted_contributions, warnings).
10. **Output — environment-aware.** Тот же паттерн, что Stage 1
    Mode B (см. `../stage1/stage1-dr-prompt.md` §7.2.5):

    **Случай A: Write tool / Bash доступен** (Cowork / Claude Code):
    - **Перед сохранением (если Bash доступен): детерминированная сверка** —
      `python3 scripts/check_format.py --stage 2 < 2_similarity.md` (проверяет
      делиметр `-----`→`---`). Любой issue → исправить ДО сохранения.
    - **СРАЗУ** использовать `Write` tool для сохранения файла как
      `{travel_root}/trips/{trip_id}/2_similarity.md`. Не спрашивать
      «нужен ли файл», не объяснять «спека не пишет файл сам».
    - В чат — короткий summary (1-3 строки): что в reading_list, какие
      WARN-флаги, `computer://`-ссылка на сохранённый файл.
    - Никаких полных YAML / per-author breakdown / reading_list
      в чате — всё уже в файле.

    **Случай B: Write tool недоступен** (claude.ai chat):
    - Per Class G discipline (см. `../stage0/stage0-scope.md` §6.7 Class G):
      раздельные сообщения.
    - **Message 1: готовый `2_similarity.md` целиком в чат** одним
      markdown-блоком (YAML + body). Не отдельный YAML-блок «вставь
      руками», не summary с просьбой склеить — **полный артефакт**.
    - **Message 2:** save instruction + summary:

      ```
      Сохрани как `{travel_root}/trips/{trip_id}/2_similarity.md`.

      Ключевые сигналы Stage 2:
      - reading_list: {N HIGH + M OUTLIER}
      - reading_list_extended (MEDIUM ≥6.5): {K}
      - {1-2 WARN-флага, если есть}

      Готов к Stage 3: `/travel-planning stage 3 для {trip_id}` —
      приложи 2_similarity.md, 1_dr_reports.md, {profile_id}.md.
      ```

**Запрет:** НЕ говорить пользователю «Stage 2 по спецификации скилла
не пишет файл сам — он выдаёт markdown в чат». Это устаревшая v0.21
формулировка. В v2 spec **Write используется автоматически** когда
доступен; в claude.ai chat — эмитится готовый артефакт целиком.

**Стоп.** Пользователь сохраняет файл (или скилл сохранил автоматически
в Случае A), обсуждает HIGH-список, готов к Stage 3.

### Случай B: пользователь скопировал DR в чат, файл не сохранён

#### Turn 1 — пользователь
«вот DR-выход, прогони Stage 2: [простыня карточек]».

#### Turn 2 — скилл

1. Gate-проверки (§4). DR-контент в чате считается за вход, но:
   **предупредить** одной строкой: «`1_dr_reports.md` в файловой системе
   отсутствует; одноразовый прогон возможен, но Stage 3 без сохранения
   потребует повторного вставления».
2. Если профиль не задан явно — спросить (ОДИН batch уточнений).
   Иначе как Случай A с шагов 6–10.

### Большая выборка (≥ 60 карточек)

Если в DR-базе ≥ 60 карточек — перед запуском работы предупредить
пользователя:

> «База из {N} карточек. Sonnet без thinking сможет обработать,
> но риск пропуска компонентов выше. Варианты:
>   1. Прогнать единым проходом — быстрее, но качество per-author может
>      просесть.
>   2. Разбить на батчи по 25–30 карточек, собрать JSON-payload по
>      батчам, прогнать `similarity_score.py` один раз на объединённом
>      payload.»

Решение принимает пользователь. Скилл не делает chunking автоматически.

## 4. Gate-проверки на входе

Применяй ДО запуска работы. Если хоть одна не выполнена — отказ с
конкретным указанием, чего не хватает.

| Что | Обязательно | Если не задано |
|---|---|---|
| `trip_id` | да | спросить или предложить из существующих (Glob) |
| `profile_path` или `profile_id` | да | предложить из существующих профилей |
| `1_dr_reports.md` в `trips/{trip_id}/` ИЛИ контент в чате | да | отказать: «запусти Stage 1 или приложи DR-выгрузку» |
| Stage 0 артефакт | нет (рекомендуется) | продолжить, в YAML Stage 2 не ссылаться на `selected_regions` |

**Отказ при отсутствии Stage 1:**

```
Stage 2 требует базу отчётов из Stage 1.

не вижу DR-контента в этом сообщении.

Варианты:
1. Запусти Stage 1: «дай промт DR для {trip_id}»
2. Прогон Deep Research в отдельной сессии, потом приложи результат
   сюда или сохрани как `1_dr_reports.md`

Стоп.
```

И ОДНА строка ответа — ничего больше.

## 6. Промт — методика scoring + JSON-payload

LLM получает профиль (Read), DR-базу (Read) и инструкцию ниже как
системный контекст. Промт состоит из четырёх частей:

- §6.0 — язык таксонов (ключ в YAML, ярлык в теле)
- §6.1 — формула и веса
- §6.2 — rubric для каждого из 6 компонентов
- §6.3 — политика «не указано»
- §6.4 — OUTLIER универсальное правило
- §6.5 — формат JSON-payload для скрипта

### 6.0 Язык таксонов: ключ — в YAML, ярлык — в теле

Одна категория живёт в двух формах, и **путать их нельзя**:

| Ярлык в теле `.md` (пишешь его) | Ключ (YAML / JSON) | Счётчик в YAML |
|---|---|---|
| **ВЫСОКАЯ** | `HIGH` | `high_similarity_count` |
| **СРЕДНЯЯ** | `MEDIUM` | `medium_count` |
| **НИЗКАЯ** | `LOW` | `low_count` |
| **ОСОБЫЙ СИГНАЛ** | `OUTLIER` | `outlier_count` |
| **БЕЗ ОЦЕНКИ** | `UNSCORED` | `unscored_count` |

Severity предупреждений: `critical` → **критично**, `borderline` →
**погранично**, `info` → **инфо**.

**Правило (анти-дрейф):** русский ярлык **не переводи сам** — копируй
**вербатим** поле `category_label` (автор) / `severity_label` (warning) из
output скрипта. Английский ключ (`category`) идёт **только** в YAML-счётчики.

**Что в теле остаётся английским** (решение Р5 — машинный слой):
компонентные строки `C1 style 8→2.0` (имена компонентов канонические, §6.2),
строка `SIGNAL:`, суффиксы `[user_added]` / `[low_confidence: N/6]`,
заголовки секций (`## Warnings`, `## Reading list для Stage 3`) — это якоря
парсинга, экспорт русифицирует их сам.

В §6.1–§6.5 ниже категории названы **английскими ключами** — это описание
логики скрипта и payload'а, а не текст для тела файла.

### 6.1 Формула и веса

Каждый автор получает score 0–10 по 6 компонентам. Финальный
total_score считает **скрипт**, LLM только проставляет компоненты.

**Веса резолвятся скриптом** из `группа_архетип` профиля (см.
`references/profile-management.md` §7.5). LLM в payload передаёт
`группа_архетип` из YAML профиля — скрипт ищет соответствующие веса в
`ARCHETYPE_WEIGHTS`. Если у профиля есть `similarity_weights_override`
блок — он перекрывает архетипные веса.

#### Таблица весов по архетипам

| # | Компонент | `самостоятельные` | `семья_с_детьми` | `взрослые_50_плюс` | `люкс` |
|---|---|---|---|---|---|
| 1 | `style` | 25 | 20 | 15 | 30 |
| 2 | `focus` | 25 | 20 | 15 | 20 |
| 3 | `pace` | 15 | 25 | 25 | 15 |
| 4 | `independence` | 10 | 5 | 5 | 5 |
| 5 | `depth` | 15 | 5 | 5 | 10 |
| 6 | `demo` | 10 | 25 | 35 | 20 |

Логика:
- Для семьи / родителей вес `demo` резко растёт — нужны авторы похожего
  демографического состава (с детьми / в возрасте).
- Для них же `depth` падает: стандартный маршрут с предсказуемой
  инфраструктурой важнее, чем off-the-beaten-path.
- Для люкса акцент на `style` и `demo` — премиум-авторы похожего профиля.

#### Что измеряет каждый компонент

| # | Компонент | Что измеряет |
|---|---|---|
| 1 | `style` | стиль путешествий: independent mid-range vs alternative |
| 2 | `focus` | совпадение фокуса автора с ядром интересов профиля |
| 3 | `pace` | темп: количество локаций, дней на локацию |
| 4 | `independence` | независимое планирование vs организованный тур |
| 5 | `depth` | non-touristy depth vs стандартный туристический маршрут |
| 6 | `demo` | возрастной диапазон и состав группы |

#### Приоритет резолва весов

В коде `similarity_score.py` — следующий порядок (выше перебивает ниже):

1. CLI `--weights` (raw 6 чисел) — для ad-hoc экспериментов
2. CLI `--archetype` (лукап ARCHETYPE_WEIGHTS) — для ручного override
3. `payload.similarity_weights_override` — индивидуальная калибровка
4. `payload.weights` — legacy raw веса
5. `payload.группа_архетип` — основной канал (типично)
6. `DEFAULT_WEIGHTS = 25/25/15/10/15/10` — backward-compat
   (эквивалент `самостоятельные`)

В выход скрипта добавлены поля `archetype_used` и `weights_source` для
traceability — отображаются в `## Контекст` Stage 2 файла.

### 6.2 Rubric для каждого компонента (0–10)

**1. `style` — стиль путешествий (вес по архетипу; дефолт 25%)**

Извлекаем из карточек: поле 9 (Стиль), поле 12 (Тип размещения).
Сверяем с разделами «Стиль путешествий» профиля.

- **10/10** — полное совпадение стиля и размещения: independent mid-range
  + private rooms 3+, multi-modal без машины (если у профиля так).
- **8/10** — стиль совпадает (independent), размещение чуть выше/ниже
  (homestay вместо отеля 3+, или 4+ вместо 3+).
- **5/10** — частичное: independent, но размещение luxury или хостел с
  общими спальнями.
- **3/10** — organized tour, но в формате small group active.
- **0/10** — luxury all-inclusive или party-tour, противоположность профилю.

**2. `focus` — фокус автора (вес по архетипу; дефолт 25%)**

Извлекаем: поле 13 (Главный фокус автора), поле 14 (тональность POI),
поле 20 (фотографические интересы). Сверяем с разделом «Ядро интересов»
профиля.

- **10/10** — фокус автора (один или mix) попадает в ≥3 пункта ядра
  интересов профиля.
- **8/10** — попадает в 2 пункта.
- **5/10** — попадает в 1 пункт.
- **3/10** — фокус смежный (например, «культура» при ядре «архитектура»),
  но не прямое совпадение.
- **0/10** — фокус прямо противоречит профилю (beach-relax при культурном
  ядре, food-extreme при ограничениях профиля).

**3. `pace` — темп (вес по архетипу; дефолт 15%)**

Извлекаем: поле 10 (Темп). Сверяем с «Стиль путешествий» → темп профиля
(rapid / активный / standard / slow).

- **10/10** — точное совпадение количества дней на локацию (±0.5 дня).
- **8/10** — близкое (±1 день).
- **5/10** — разница ±2 дня.
- **3/10** — заметно медленнее/быстрее (×2).
- **0/10** — крайности: автор за день в каждом городе при slow-профиле,
  или 14 дней в одном городе при активном.

**4. `independence` — независимость планирования (вес по архетипу; дефолт 10%)**

Извлекаем: поле 9 (тег независимости), поле 11 (Транспорт). Сверяем с
«Стиль путешествий» → independent vs tour preference.

- **10/10** — полностью самостоятельная организация, общественный
  транспорт / multi-modal (если профиль такой).
- **7/10** — самостоятельная, но с частными водителями на сложных
  участках.
- **5/10** — mix: часть тур, часть самостоятельно.
- **3/10** — package tour с отдельными свободными днями.
- **0/10** — fully escorted tour.

**5. `depth` — non-touristy depth (вес по архетипу; дефолт 15%)**

Извлекаем: поле 15 (hidden gems), общая тональность поля 14 (упоминания
нетуристических мест), часть поля 16 (лайфхаки).

- **10/10** — автор активно ищет нетуристическое, есть ≥3 hidden gems,
  явная критика mainstream-точек.
- **7/10** — баланс mainstream + нетуристическое, ≥1 hidden gem.
- **5/10** — только mainstream, но с попыткой найти нестандартный угол.
- **3/10** — стандартный туристический круг без отклонений.
- **0/10** — только Top-10 from Lonely Planet.

**6. `demo` — возраст и состав группы (вес по архетипу; дефолт 10%)**

Извлекаем: поле 7 (Состав группы), поле 8 (Возрастной диапазон).
Сверяем с разделом «Состав группы» профиля.

- **10/10** — полное совпадение возраста и формата (пара 30+ ↔ пара 30+,
  семья с детьми 5–10 ↔ семья с детьми 5–10).
- **7/10** — близкий возраст (±10 лет), такой же формат.
- **5/10** — другой возраст (±20 лет), такой же формат (пара ↔ пара).
- **3/10** — другой формат (соло-путешественник при паре, группа друзей
  при семье).
- **0/10** — полная противоположность (тур пожилых при паре 25+, или
  party-backpackers при семье с пожилыми).

### 6.3 Политика «не указано»

Если в карточке поле = «не указано» (или невозможно вывести компонент
из имеющихся данных):

- В JSON-payload передавай этот компонент как **`null`**.
- Скрипт перераспределит вес на остальные компоненты пропорционально
  (например, при 4 известных из 6 — веса нормируются от 60 до 100,
  каждый умножается на 100/60).
- Скрипт пометит `confidence` автоматически:
  - `full` — все 6 компонентов известны
  - `partial` — 4–5 известны
  - `low` — 3 известны
  - `unscored` — < 3 известны → category=UNSCORED независимо от score

**Не угадывай компонент** при отсутствии данных. Если в карточке нет
указания на темп — pace=null, не «5 по умолчанию». Иначе теряется
сигнал, что данных мало.

### 6.4 OUTLIER — универсальное правило

Для каждого автора: после проставления компонентов отдельно реши, есть
ли у автора **уникальный сильный сигнал, релевантный какому-то аспекту
профиля**, даже если общий стиль/темп не совпадает.

«Релевантный профилю» — открытый список, конкретизируется ПОД ПРОФИЛЬ:

- Фото-профиль → автор с упоминанием конкретного оборудования, света,
  time-lapse, postprocessing — релевантный сигнал.
- Гастро-профиль → food-blogger с deep dive в локальную кухню,
  специализированный кофе, рынки.
- Профиль с языковыми навыками страны (живёт там / знает язык) →
  автор-носитель / эксперт по региону.
- Архитектурный профиль → автор с искусствоведческим бэкграундом,
  упоминания периодов/стилей.
- Профиль с физическими ограничениями → автор с теми же ограничениями
  (например, «путешествие с пожилыми родителями», «без машины», «вегетарианец»).
- Профиль с трек-интересом → автор-турист с упоминанием конкретных
  маршрутов, времени, сезонов.
- Контр-индикатор (любой профиль) → автор с **обоснованной резкой
  критикой** массово хвалимого места (вес для будущего RED FLAG в Stage 3).

«Уникальный сигнал не релевантный профилю» — НЕ считается OUTLIER:

- Дайвер при non-beach профиле — не OUTLIER.
- Cycling-tour при не-cycling профиле — не OUTLIER.
- Party-blogger при семейном профиле — не OUTLIER.

В JSON-payload передавай:
```json
"outlier_signal": {"present": true, "description": "фотограф, упоминает Capture One, рассветная съёмка Шапы"}
```

или
```json
"outlier_signal": {"present": false, "description": ""}
```

LLM **обязательно** даёт описание в `description`, даже если коротко
(оно идёт в выходной markdown для пользователя).

### 6.5 user_added — независимый scoring

Карточки с пометкой `(user_added)` в DR-базе обрабатывай ТОЧНО ТАК ЖЕ
как остальные. Не давай им преимущество в score.

В JSON-payload передавай `"user_added": true` — скрипт сохранит флаг
для визуализации (отдельная пометка в выходе) и для информативного
warning, если они системно попадают в LOW.

### 6.6 Формат JSON-payload для скрипта

**payload строит LLM**, читая `1_dr_reports.md` markdown напрямую.
Скрипт `parse_dr_cards.py` выдаёт **только diagnostic + card_summaries**
(id, url, name, user_added) для антигаллюцинационной сверки — никаких
raw_card_text / components / outlier_signal в его output.

LLM формирует payload:
- **Анти-галлюцинационная сверка:** id, url, name, user_added берутся
  из `card_summaries` (output `parse_dr_cards.py`). Если LLM видит в
  markdown карточку, которой нет в card_summaries — это сигнал deformed
  карточки, которую парсер пропустил; вернуться к шагу 6 с диалогом §9.12.
- **Семантическое заполнение** — на основе **текста карточки в markdown**:
  - `components.{style,focus,pace,independence,depth,demo}` 0–10 (или
    null если в карточке поля нет, §6.3) по rubric'ам §6.2.
  - `outlier_signal.present` (true/false) и `outlier_signal.description`
    по правилу §6.4 (универсальный сигнал, релевантный профилю).
    **Доля present=true не должна превышать 30% от выборки** — иначе
    категория OUTLIER размывается (anti-bloat).

После заполнения сформируй итоговый JSON и передай в
`similarity_score.py` через stdin.

**В payload обязательно добавь `группа_архетип`** — поле из YAML
профиля. Скрипт зарезолвит веса по архетипу автоматически. Если у
профиля есть `similarity_weights_override` блок — передай его тоже
(он перекрывает архетипные веса). Поле `weights` (raw 6 чисел)
поддерживается для backward-compat, но новые payload должны идти
через `группа_архетип`.

### 6.7 Выходной JSON скрипта (что использовать в §8)

Скрипт возвращает на каждого автора в `scored_authors[]`:

- `total_score` (float, 0–10) — итог.
- `category` — HIGH / MEDIUM / LOW / OUTLIER / UNSCORED (машинный ключ — в YAML).
- **`category_label`** — русский ярлык той же категории («ВЫСОКАЯ»).
  **Копируется в тело вербатим** (§6.0): переводить ключ самому запрещено.
- `confidence` — full / partial / low / unscored.
- `low_confidence_flag` (bool) — true если HIGH/OUTLIER с components_known < 4.
- `components_known` (int 0–6).
- `effective_weights` (dict) — нормализованные веса в %.
- **`weighted_contributions` (dict)** — `{component: value × eff_weight / 100}`.
  Сумма по всем 6 компонентам == `total_score`. Используется для формата
  `C1 9→2.25 · C2 7→1.75 · ...` в §8.
- `in_reading_list` (bool) — true для HIGH и OUTLIER.
- **`in_extended_reading_list` (bool)** — true для MEDIUM с total ≥ 6.5
  (borderline-high). Стоит прочитать сверх HIGH/OUTLIER, если HIGH-выборка
  узкая.

Top-level поля (включая поля архетипа для traceability):

- `archetype_used` (str | null) — какой архетип был использован для резолва
  весов; всегда каноническое имя (legacy-алиас `независимые_соло_пара`
  отдаётся как `самостоятельные`). Отображается в `## Контекст` Stage 2 файла.
- `weights_source` — откуда взялись веса:
  `default` / `archetype` / `override` / `cli_weights` / `cli_archetype` /
  `payload_weights`. При нормальном Stage 2 запуске значение обычно
  `archetype` (типичное) или `override` (если профиль с
  `similarity_weights_override`).

Остальные top-level поля:

- `reading_list` — список id для основного reading list.
- **`reading_list_extended`** — список id MEDIUM-borderline.
- `unscored_with_signal` — UNSCORED авторы с outlier_signal=true.
- `distribution`, `confidence_breakdown`, `warnings`, `weights_used`,
  `thresholds_used` (с `medium_high_borderline`). У каждого warning есть
  `severity` (ключ) и **`severity_label`** (русское слово — в тело вербатим).

## 7. Правила работы

### Граница LLM vs скрипт (diagnostic-only parser)

**LLM делает:**
- Читает `1_dr_reports.md` markdown **напрямую** для извлечения семантики
  (текст карточек, тональность, стиль автора).
- Строит **полный payload** для similarity_score.py: id/url/name/user_added
  сверяет с `card_summaries` (output parse_dr_cards), components/outlier_signal
  проставляет на основе markdown по rubric'ам §6.2 и §6.4.
- Контролирует, чтобы доля `outlier_signal.present=true` не превышала 30% —
  иначе similarity_score выдаст critical warning.
- Получает JSON-ответ от `similarity_score.py`.
- Формирует markdown для пользователя по §8.

**`parse_dr_cards.py` делает (только диагностика):**
- Парсит markdown 1_dr_reports.md на карточки **для диагностики структуры**.
- Извлекает `url`, `name`, `user_added` для card_summaries — антигаллюцинационная
  справка для LLM.
- Возвращает `diagnostic.status` (ok / warning / error) — сигнал LLM,
  можно ли продолжать без opt-in fallback диалога (§9.12).
- **НЕ строит JSON-template для similarity_score.py.** Это работа LLM.

**Скрипт делает:**
- Нормализует веса при null-компонентах (политика «не указано», §6.3).
- Считает total_score.
- **Считает `weighted_contributions`** — вклад каждого компонента в
  итоговый score (`value × eff_weight / 100`). Сумма == total_score.
- Определяет confidence (full / partial / low / unscored).
- Категоризирует HIGH / MEDIUM / LOW / OUTLIER / UNSCORED.
- Подсчитывает распределения.
- Генерирует warnings (HIGH < 5 → critical, HIGH < 8 → borderline,
  low_confidence в HIGH, UNSCORED с signal, user_added в LOW).
- Формирует `reading_list` (HIGH + OUTLIER), `reading_list_extended`
  (MEDIUM с total ≥ 6.5) и `unscored_with_signal`.

**LLM НЕ делает:**
- Не считает total_score руками.
- Не считает weighted_contributions руками — берёт из output скрипта.
- Не категоризирует HIGH/MEDIUM/LOW самостоятельно.
- Не решает, кого включить в reading_list — скрипт это делает по правилу.
- Не пересчитывает веса при null-компонентах.

### Web search

Для Stage 2 web search **не нужен**. Все данные уже в DR-карточках и
профиле. Если LLM хочет сверить, что какой-то автор — известный
фото-блогер с правильным жанром, — это допустимо (например, поиск
имени автора), но не делай это для каждого автора.

### Что подсвечивать в выходе

- **HIGH < 8** — явный сигнал «выборка узкая», вынеси в начало markdown
  (после контекста).
- **OUTLIER** — отдельной подсекцией в reading list, обязательно с
  `description` сигнала (это ключевой сигнал, теряется в сводных таблицах).
- **MEDIUM borderline (`reading_list_extended`)** — отдельной подсекцией
  «Расширенный список» в reading list (formatting как HIGH, без сокращений).
- **low_confidence_flag в reading list** — суффикс `[low_confidence: N/6]`
  у author entry.
- **user_added в reading list** — суффикс `[user_added]`.
- **unscored_with_signal** — отдельной секцией после reading list:
  «не вошли автоматически (components_known < 3), но имеют сигнал —
  прочитать опционально».

### Запреты и обязательства по выводу

- **НЕ опускать данные «for brevity».** Все авторы из исходной выборки
  должны быть в выходном файле — либо в детальной форме (если в
  reading list/extended), либо одной компактной строкой в полной таблице
  (если MEDIUM/LOW не в extended). Пропуски «опущено для brevity»,
  «остальные аналогично», «см. JSON» — запрещены. Если контекст не
  помещается, выдай две части файла, но не сокращай контент.

- **Формат имени файла строго фиксирован:** `2_similarity.md`. Запрещены
  суффиксы типа `_stage2_`, `_v2_`, имя trip_id в имени файла, дата
  в имени файла. Полный путь — `{travel_root}/trips/{trip_id}/2_similarity.md`.

- **trip_id одной системой письма.** Если пользователь передал
  `argentina_юг_2025-03` (смесь латиницы и кириллицы) — gate-предупреждение
  ОДНОЙ строкой: «trip_id смешанный (латиница + кириллица). Рекомендую
  переименовать в `аргентина_юг_2025-03` либо `argentina_south_2025-03`».
  Работу продолжить, но в YAML добавить `trip_id_warning: mixed_script`.

- **«Сохранить как» — НЕ в файле.** Этот блок выдаётся в чат отдельным
  сообщением после файла (см. §8). В самом файле его не должно быть.

### Стиль

- **Тело — по-русски** (§6.0): ярлыки категорий — вербатим из
  `category_label`, severity — из `severity_label`, проза — русская.
  Термины пайплайна в прозе — по-русски: «балл», не `score`; «список для
  чтения», не `reading list`; «компоненты», не `components`.
- **Никаких ссылок на внутренние файлы скилла в теле артефакта**
  («см. stage3-poi.md §6.5», «по §6.4 спеки»). Пользователь их не видит —
  формулируй смысл словами.
- Без эмодзи в самом файле (в чате допустимы для подсветки severity).
- Per-author breakdown в reading list — формат как в §8 (weighted
  contributions + Тянет вверх / Тянет вниз + URL отдельной строкой).
- Reasoning «Тянет вверх / Тянет вниз» у HIGH/OUTLIER/extended — 1–2
  строки каждая, без воды.
- Цитаты из карточек разрешены, если иллюстрируют scoring (например,
  «автор пишет: "за две недели объехали 12 локаций" → pace=3/10»).

```
Этот блок — кандидаты к прочтению, если выборка ВЫСОКАЯ узкая (< 8). Не

## БЕЗ ОЦЕНКИ с outlier-сигналом
```

```
## Per-author scoring для СРЕДНИХ и НИЗКИХ (компактный формат)

Для всех авторов, которые НЕ в списке для чтения (т.е. СРЕДНЯЯ не в
расширенном, НИЗКАЯ, БЕЗ ОЦЕНКИ без сигнала) — одна строка каждому:

```
#{N} **{name}** — {total}/10 ({category_label}) {[low_confidence: M/6]} {[user_added]}
C1 {value}→{contribution} · C2 {value}→{contribution} · C3 {value}→{contribution} ·
C4 {value}→{contribution} · C5 {value}→{contribution} · C6 {value}→{contribution}
{один тег-маркер по-русски: «стандартный туристический сценарий»,
«организованный тур», «пляжный фокус», «не подходит по фокусу», «нет данных»
— 5-10 слов}
{url}
```

Без «Тянет вверх / Тянет вниз» (это для reading list). Цель — показать,
**почему** автор не в reading list, в одну строчку. Если пользователь
хочет глубже — он попросит.
```

### SSOT и роль YAML

YAML-шапка дублирует ключевые числа из таблицы распределения. Они
**должны совпадать** — скрипт возвращает их одним JSON, рассинхрон
возможен только если LLM руками пересчитала числа (что запрещено).

Поле `weights_used` и `thresholds_used` сохраняется для воспроизводимости:
если в будущем веса будут меняться, можно сверить старые stage 2 с
новыми по этим полям.

### «Сохранить как» — НЕ в файле

Этот блок — **отдельным сообщением в чате после файла**, не в теле
markdown. Содержание зависит от environment (см. `../storage-and-naming.md`
§9):

- **Cowork + Synology доступен:** скилл сам пишет через Write +
  показывает computer://-ссылку и `mcp__cowork__present_files`.
- **Cowork без Synology:** «Synology mount недоступен. Скопируй markdown
  выше и сохрани руками как `{travel_root}/trips/{trip_id}/2_similarity.md`.»
- **Claude.ai (обычный чат):** «Скопируй markdown выше и сохрани руками
  как `{travel_root}/trips/{trip_id}/2_similarity.md`.»

## 9. Граничные случаи

### 9.1 Stage 1 файл не сохранён в `{travel_root}`

Пользователь прогнал DR в отдельной сессии и вставил карточки в чат
без сохранения `1_dr_reports.md`:

- Допустимо для одноразового прогона Stage 2.
- В YAML Stage 2 поле `input_file` указать как `<inline>` или
  `1_dr_reports.md (не сохранён)`.
- Предупредить пользователя: перед Stage 3 настоятельно рекомендовать
  сохранить `1_dr_reports.md`, иначе придётся вставлять заново.

### 9.2 Слишком большая база (≥ 60 карточек)

См. §3 «Большая выборка». Скилл предлагает на выбор:
- одним проходом (риск качества per-author);
- разбить на батчи 25–30, потом один прогон скрипта на объединённом
  payload.

В обоих случаях payload скрипта итоговый — единый. Скрипт не
поддерживает инкрементальное добавление.

### 9.3 Все компоненты у автора null

Возможно при крайне пустой DR-карточке (только URL и заголовок). LLM
честно передаёт все 6 компонентов как `null`. Скрипт ставит UNSCORED.
В warnings — отдельная строка.

Если таких авторов много (> 10% от выборки) — сигнал, что DR-промт
Stage 1 надо переработать (поля 5–13 не извлеклись). В этом случае
поднять с пользователем вопрос о ре-DR.

### 9.4 HIGH = 0 (все попали в MED/LOW/UNSCORED)

Полностью неподходящая выборка под профиль. Не блокирует Stage 3, но
делает его бессмысленным (POI агрегировать не из чего).

Действия скилла:
- Critical warning от скрипта (HIGH < 5).
- В Контексте секции явно зафиксировать: «выборка не содержит HIGH-авторов,
  Stage 3 не имеет статистической основы. Расширь источники через Stage 1
  Mode B (B1 — discovery на awd.ru, B2 — добавить URLs)».
- НЕ запускать Stage 3 автоматически.

### 9.5 user_added доминирует выборку (> 50%)

Пользователь активно дополнял базу. Скилл считает scores независимо
(§6.5), но в warnings отдельной строкой подсветить долю user_added:
«{N}/{M} карточек = user_added. Скиллы Stage 3 будут учитывать их
наравне с DR-выборкой».

Не блокирует, но отмечает в контексте.

### 9.6 Profile drift — профиль обновлён после Stage 1

Сравнить `updated` профиля с `dr_run_date` из YAML `1_dr_reports.md`:

- Если `updated` > `dr_run_date` — одной строкой:
  «Профиль обновлён {date}, DR проводился {date}. Текущая фильтрация
  использует свежий профиль. Если изменения существенные — рассмотри
  ре-DR с новым scope».
- Не блокирует, продолжает.

### 9.7 Повторный запуск с другими весами

Пользователь хочет прогнать Stage 2 с другими весами similarity
(например, поднять `focus` до 35% для фото-ориентированной поездки):

- Запустить с `--weights 25,35,10,10,10,10` (сумма 100).
- Сохранить как `2_similarity_alt.md` (или с суффиксом даты), чтобы
  не потерять основной артефакт.
- В шапке YAML обязательно `weights_used` — отражает фактически
  применённые веса.
- На Stage 3 поле YAML `chosen_similarity_run: 2_similarity_alt.md`
  (см. `../storage-and-naming.md` §10.5).

### 9.8 Дубли авторов в DR-базе

Иногда merge_dr_additions (Stage 1 Mode B) пропускает дубль (например,
два разных URL ведут на одну тему). Если LLM видит идентичные карточки:

- Сохранить ОДИН вариант, второй пометить как `(дубль)` в comment.
- Не подавать в JSON-payload дважды.
- В warnings: «{N} дубликатов отброшено».

### 9.9 LLM не уверена в компоненте

Не угадывать. Если ставить score опасно (нет данных), передать null
и в reasoning при выводе написать «не указано в карточке — компонент
исключён из scoring». Это лучше шумного среднего.

### 9.10 trip_id со смешанной системой письма

Пользователь передал `argentina_юг_2025-03` (латиница `argentina` +
кириллица `_юг`). По соглашению (см. `../storage-and-naming.md`
§3, §10.7) `trip_id` должен быть либо целиком кириллическим
(`аргентина_юг_2025-03`), либо целиком латинским (`argentina_south_2025-03`).

Действия скилла:
- Одной строкой gate-предупреждение пользователю: «trip_id смешанный
  (латиница + кириллица). Рекомендую переименовать в `аргентина_юг_2025-03`
  либо `argentina_south_2025-03` (более единообразно)».
- Работу не блокировать — продолжить с переданным trip_id.
- В YAML выхода добавить `trip_id_warning: mixed_script`, чтобы видно
  было на Stage 3+.

Эта проверка — мягкая, для предотвращения накопления legacy. Старые
поездки с mixed-script разрешены (см. §10.7 storage-and-naming).

### 9.12 Opt-in LLM-fallback при `diagnostic.status=error`

Когда `parse_dr_cards.py` вернул `diagnostic.status=error` (URL пропуски
> 20%, или expected vs found mismatch > 20%, или слишком мало карточек) —
**скилл не парсит руками самостоятельно**. Вместо этого выдаёт пользователю
ОДИН batch с диагностикой и 3 вариантами.

**Формат вопроса (одно сообщение, не задавать по очереди):**

```
Парсер `parse_dr_cards.py` распознал {N} карточек, есть проблемы:

- {issue 1: severity, code, message}
  Затронутые id: {affected_ids[:5]} (всего {len})
- {issue 2: ...}
- ...

Как действовать? Выбери один из вариантов:

1. **LLM-fallback парсинг.** Я разберу проблемные карточки семантически
   из исходного markdown `1_dr_reports.md`. В выходном Stage 2 файле в YAML появится
   `partial_parse: true` и список авторов с `parse_method: llm_fallback`.
   На результаты scoring это не влияет, только маркируется источник
   парсинга для прозрачности.
2. **Пропустить проблемные карточки.** Эти {N} авторов не попадут в
   payload и Stage 2 файл. Распределение и reading list будут считаться
   на оставшихся.
3. **Стоп — я подправлю Stage 1 файл.** Скилл остановится, ты обновишь
   формат и перезапустишь Stage 2.
```

После выбора пользователя:

- **Вариант 1 (LLM-fallback):**
  - Для каждого проблемного автора (из `cards_without_url` /
    `cards_without_name` / mismatch) LLM читает карточку напрямую из
    `1_dr_reports.md`, семантически извлекает URL и/или имя.
  - В payload поле `parse_method` меняется на `"llm_fallback"` у этих
    авторов; `script` остаётся у остальных.
  - В YAML итогового Stage 2 файла добавляется:
    ```yaml
    partial_parse: true
    llm_fallback_authors: ["{id1}", "{id2}", ...]
    parse_diagnostic_at_run:
      status: error
      issues_summary: "..."
    ```
  - В блоке `## Контекст для следующих стадий` одной строкой:
    «Парсер сообщил об ошибках, {N} авторов разобраны семантически
    (parse_method=llm_fallback). См. YAML `llm_fallback_authors`.»

- **Вариант 2 (пропустить):**
  - Проблемные авторы исключаются из payload (не передаются в
    similarity_score.py).
  - В YAML итогового Stage 2 файла:
    ```yaml
    skipped_authors_count: N
    skipped_authors: ["{id1}", "{id2}", ...]
    parse_diagnostic_at_run:
      status: error
      issues_summary: "..."
    ```
  - В контексте: «{N} карточек пропущены из-за нераспознанного формата
    (по выбору пользователя). См. YAML `skipped_authors`.»

- **Вариант 3 (стоп):**
  - Скилл ничего не делает. Сообщение: «Жду, пока обновишь Stage 1.
    Когда готов — запусти Stage 2 снова.»

**Жёсткий запрет:** скилл **не имеет права** выбрать вариант 1 без
явного согласия пользователя. Это защита от silent выдумывания полей,
которые LLM может «придумать» из текста карточки.

### 9.11 Большая выборка не помещается в один ответ

Если 50+ авторов с детальным reading list не помещаются в context budget
одного ответа: разбить выход на ДВА файла:
- `2_similarity.md` — YAML + распределение + warnings + reading list +
  unscored_with_signal + полная таблица.
- `2_similarity_details.md` — per-author scoring для MEDIUM/LOW
  (компактный формат §8).

В YAML основного файла добавить `details_file: 2_similarity_details.md`.

**Нельзя:** «остальные опущены for brevity», «см. JSON», «доступно при
запросе». Это запрещено §7.

## 10. Что НЕ делать

- НЕ считать total_score руками (это работа скрипта).
- НЕ считать weighted_contributions руками — берёт из output скрипта.
- НЕ применять веса руками.
- НЕ категоризировать HIGH/MEDIUM/LOW без скрипта.
- НЕ давать user_added преимущество в score (§6.5).
- НЕ предлагать POI на этой стадии (Stage 3).
- НЕ строить маршрут (Stage 4).
- НЕ выбирать «лучшего автора» — все HIGH идут в reading list равноценно.
- НЕ скрывать low_confidence или unscored с signal — это полезная
  информация, должна быть в выходе.
- НЕ опускать данные «for brevity» (§7). Все авторы выборки — в выходе.
- НЕ делать web search для каждого автора (отдельная сверка имени
  допустима, см. §7).
- НЕ запускать Stage 3 автоматически после Stage 2.
- НЕ писать «Сохранить как» в тело файла (§8).
- НЕ использовать sandbox-пути типа `/home/claude/` или `/tmp/` для
  файла-результата (см. `../storage-and-naming.md` §9).
- НЕ изобретать имена файла кроме `2_similarity.md` (§7 «Запреты»).
- НЕ парсить 20-field карточки руками — всегда через
  `parse_dr_cards.py`. Исключение: opt-in LLM-fallback **только после
  явного согласия пользователя** при `diagnostic.status=error` (§9.12).
- НЕ выбирать вариант LLM-fallback автоматически. При
  `diagnostic.status=error` — диалог с пользователем по §9.12, ждать
  выбор. Самовольный fallback = silent выдумывание полей.
- НЕ давать `outlier_signal.present=true` больше чем 30% авторов
  (anti-bloat). OUTLIER — категория для **уникального** сигнала,
  она не может быть у половины выборки. Скрипт выдаст critical warning
  при превышении — пересмотри маркировки, оставь только действительно
  уникальные сильные сигналы.
- НЕ переименовывать компоненты (`season` вместо `pace`, `photo` вместо
  `demo` и т.п.) — это нарушение spec, видели в Haiku-прогоне. Имена
  строго: `style/focus/pace/independence/depth/demo`.
- НЕ изобретать категории (`Tier-1/2/3`, `MISMATCH`, `EXCELLENT`).
  Канон строго (§6.0): в теле — **ВЫСОКАЯ / СРЕДНЯЯ / НИЗКАЯ / ОСОБЫЙ
  СИГНАЛ / БЕЗ ОЦЕНКИ**, в YAML и payload — `HIGH/MEDIUM/LOW/OUTLIER/
  UNSCORED`. Шкала 0–10, не 0–100.
- НЕ переводить ярлык категории самостоятельно и НЕ подбирать синоним
  («ВЫСОКОЕ», «ВЫБРОС», «НЕ ОЦЕНЁН») — только вербатим-копия
  `category_label` / `severity_label` из output скрипта (§6.0).
- НЕ оставлять английский ярлык в теле (`(HIGH)`, `| OUTLIER |`,
  `⚠️ critical:`) и НЕ класть русский ярлык в YAML — это две разные формы
  одной категории.
- НЕ ссылаться в теле артефакта на внутренние файлы скилла («см.
  stage3-poi.md §6.5») — пользователь их не видит, формулируй смысл словами.
- НЕ продолжать работу если model self-check показал Haiku
  (см. шаг 0 потока). Stage 2 на Haiku даёт мусор.
- НЕ реконструировать карточки или данные из сниппетов и превью —
  работать только с полным файлом (Synology / приложение,
  см. `../storage-and-naming.md` §8.0).

## 11. Следующий шаг

После того как пользователь сохранил `2_similarity.md`:

- Активируется Stage 3 (`/travel-planning` → «агрегируй POI
  для {trip_id}» или «Stage 3 для {trip_id}»).
- Stage 3 читает YAML Stage 2 (`reading_list`) и проходит по полям
  14–15 (POI и hidden gems) этих авторов в исходных DR-карточках.

Скилл не запускает Stage 3 автоматически — пользователь сам решает,
когда HIGH-список адекватен и можно переходить к агрегации POI.

Если HIGH = 0 или < 5 (critical warning) — рекомендованный шаг
**не Stage 3**, а возврат к Stage 1 Mode B для расширения источников.
