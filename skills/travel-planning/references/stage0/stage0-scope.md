# stage0-scope.md

Полная спецификация Stage 0 — регионального сужения. Берёт начальный
широкий запрос («хотим в [направление]») и формирует **longlist 6–8
логических регионов** для DR (Stage 1) — с 30% reserve относительно
того, сколько регионов реально войдёт в финальный план. Выбор финальных
регионов делается **после Stage 3** через тегирование, когда POI evidence
уже собран («evidence перед route» — `../methodology.md` §2).

Стадия двухактная (без промежуточного артефакта между актами):

- **Akt A** — диалог: показать region universe + tempo math + 3 вопроса
  пользователю → пользователь отвечает.
- **Akt B** — формализация longlist'а в `0_scope.md` (тот же чат, после
  ответа пользователя; промежуточный артефакт между актами не создаётся).

Философия и место в пайплайне — `../methodology.md` §3 «Stage 0».

## 1. Назначение

«Логический регион» — не административное деление, а тематический
кластер мест, связанных географически и логистически, посещаемый в
одной поездке как единая единица.

Stage 0 v2 разбивает направление на **region universe** (обычно 10–15
регионов с 2–3 фактическими предложениями каждый), затем формирует
**longlist 6–8 регионов** для DR с reserve pair-bindings (region X имеет
substitute region Y на случай если основной отпадёт по сезону / логистике).

Stage 0 v2 **не выбирает финальные регионы и не строит variants** —
это работа Stage 4 (после видения POI evidence из Stage 3, при наличии
пользовательских тегов на регионах).

Зачем эта стадия:

- Deep Research (Stage 1) на размытом scope вернёт generic-обзор по
  20 регионам или случайно сфокусируется на одном. Stage 0 задаёт
  longlist для целевого DR.
- 30% reserve в longlist'е страхует от потери региона на этапе DR
  (плохое coverage, неполный POI набор) — есть substitute для замены.
- Stage 0 v2 не закрывает маршрут на «среднем знании» LLM о направлении
  до того как factual evidence собран. Это страховка от canonical
  bias (виден только стандартный туристический скелет страны).

### Формат поездки

Stage 0 v2 детектирует один из трёх форматов по запросу пользователя:

- **Multi-region tour** (по умолчанию): longlist 6–8 регионов, варианты
  в Stage 4 различаются выбором подмножества.
- **Single-base trip** («жить в одном месте, оттуда ездить») — пользователь
  фиксирует базу, longlist = 1 регион + 2–4 day-trip направления.
- **Explicit list** — пользователь сам перечислил ≥3 регионов как
  обязательные; longlist = эти регионы + опц. 1–2 дополнительных.

Конкретные критерии детекции — §4 «Gate-проверки».

## 2. Inputs / Outputs

**Inputs:**

- Запрос пользователя: направление, длительность, сезон, предзафиксированные
  места (опц.), `trip_id` (опц., новый или существующий)
- Профиль группы: `{travel_root}/profiles/{profile_id}.md` ← Read
- Опц.: артефакты предыдущей итерации поездки, если scope пересматривается:
  `{travel_root}/trips/{trip_id}/0_scope.md` (предыдущий) ← Read

**Outputs (в чат + manual save пользователем):**

- `{travel_root}/trips/{trip_id}/0_scope.md`
  — Stage 0 v2 артефакт с YAML-шапкой (schema_version: 2), region universe,
  longlist 6–8 регионов с reserve pairs, excluded regions, non-canonical
  found, tempo + country quota, honest assessment.

**Downstream:** Stage 1 (DR-промт) запускает DR по **всем регионам longlist'а**
(включая reserve) — это и есть смысл 30% reserve.

## 3. Поток

Зависит от полноты входа в первом сообщении.

### Случай A: вход полный (Akt A → user → Akt B, минимум 3 chat-turn'а)

Полный вход = все 4 обязательных параметра в Turn 1: направление,
длительность, сезон, `profile_id` (явный или однозначно подразумеваемый),
плюс `trip_id` (явный или генерируемый по конвенции).

#### Turn 1 — пользователь
Полный запрос с обязательными параметрами.

#### Turn 2 — скилл — **Akt A**

1. Gate-проверки (§4) — все прошли. Включая retrospective gate и
   trip_format detection.
2. Read профиля.
3. Опц. — Read предыдущего `0_scope.md` если `trip_id` уже существует
   (см. §9.1).
4. Подставить параметры в промт (§6) → **Akt A**.
5. Web search для актуальной проверки (визы, политика, транспорт,
   сезонные риски) — §7.
6. **LLM-message (Akt A):**
   - Region universe — 10–15 регионов с 2–3 фактическими предложениями
     каждый + density tag.
   - Universe summary + density warning (если применимо).
   - Tempo math для запрошенной длительности.
   - 3 вопроса в одном batch'е: mood, country quota (если multi-country),
     must-have'ы/skip'ы из universe.

**Стоп.** Ждать ответ пользователя.

#### Turn 3 — пользователь

Отвечает в одном сообщении на 3 вопроса Akt A. Если говорит «выбери сам» —
скилл применяет defaults и переходит к Akt B без задержки.

#### Turn 4 — скилл — **Akt B**

7. Парсит ответ пользователя из Turn 3 (mood, country quota, must/skip).
8. Формирует longlist 6–8 регионов согласно формулу N (см. §6 раздел
   «Akt B: формула размера longlist'а») с учётом тегов из Akt A.
9. Сформировать выход по структуре §8 (YAML + тело markdown).
   **`## Сохранить как` блок НЕ включается в тело файла** — он
   выдаётся отдельным сообщением.
10. **Отдельным сообщением в чате после markdown-артефакта** — блок
    «Сохранить как» с путём `{travel_root}/trips/{trip_id}/0_scope.md`,
    адаптированный под environment.

**Стоп.** Пользователь сохраняет файл, переходит к Stage 1 (DR-промт по
longlist'у).

### Случай B: вход неполный (доп. batch уточнений)

#### Turn 1 — пользователь
Например, только направление: «хочу в [страну]».

#### Turn 2 — скилл — ОДИН batch уточнений

Не задавать вопросы по одному. В одном сообщении:

1. Перечислить, что не хватает из обязательных параметров (§4).
2. Если у пользователя только один профиль или есть очевидный кандидат —
   предложить его дефолтом, иначе перечислить существующие профили
   (Glob → Read frontmatter каждого) и спросить.
3. Если можно сгенерировать `trip_id` по конвенции
   `{назначение}[_{детализация}]_{YYYY-MM}` (см. `../storage-and-naming.md`
   §3.2) — предложить дефолт.
4. Спросить пакет уточнений одним блоком.

**Стоп.** Не делать никакой содержательной работы до получения параметров.

#### Turn 3 — пользователь
Отвечает на batch.

#### Turn 4-6 — скилл — как Turn 2-4 в случае A
Akt A → пользователь отвечает на 3 вопроса → Akt B.

## 4. Gate-проверки на входе

Применяй ДО запуска работы. Если хоть одна не выполнена — переход в
Случай B (Шаг E из profile-management.md style): ОДИН batch уточнений,
стоп.

| Что | Обязательно | Если не задано |
|---|---|---|
| Направление (страна / макрорегион) | да | спросить |
| `duration_nights` | да | спросить |
| Сезон (`YYYY-{descriptor}` или конкретный месяц + год) | да | спросить |
| `profile_id` или `profile_path` | да | предложить из существующих |
| `trip_id` | да (можно сгенерировать) | предложить по конвенции, дать переопределить |
| **`home_city`** | нет (резолвится автоматически) | (1) поле `## Базовый город` профиля; (2) если в профиле пусто — ОДНА строка-вопрос в общем batch'е уточнений |
| **`trip_start_city`** | нет (резолвится автоматически) | (1) явное указание в запросе пользователя («лечу через {город}», «начало в {городе}», «{город} транзит»); (2) дефолт = `home_city` |
| `pre_committed_places` | нет | принять пустой список |
| **`trip_wishes`** | нет (резолвится автоматически) | извлекать вербатим из запроса пользователя — короткие фразы-пожелания, не сводящиеся к топонимам |
| **`retrospective`** (флаг) | нет (резолвится автоматически) | см. блок «Retrospective validation gate» ниже |
| Предыдущая итерация поездки | нет | пропустить |

### Retrospective validation gate

Stage 0 **обязан проверить**, не относится ли указанный сезон к прошлому
(относительно текущей даты). Если относится — это либо retrospective
blind-валидация (поездка уже состоялась, тестируется методология), либо
опечатка пользователя.

**Триггер:** `parsed_season_end_date < current_date - 30 days` (хотя бы один
из месяцев сезона уверенно в прошлом, не граничная неделя).

**Логика:**

1. Если в запросе или в YAML явно `retrospective: true` → принять как
   blind-валидацию, использовать заявленный сезон **как есть** (не
   сдвигать). Зафиксировать в YAML.
2. Если флаг не задан и сезон в прошлом → ОДНА строка-вопрос в batch'е
   уточнений:

   > Сезон `{сезон_год}` — в прошлом относительно сегодняшней даты
   > `{current_date}`. Это:
   > 1. **Retrospective blind-валидация** (поездка уже состоялась, тестирую
   >    методологию) — установлю `retrospective: true`, использую заявленный
   >    сезон как есть.
   > 2. **Опечатка** — имел в виду `{сезон_год_сдвинут_+1_год}`?
   >
   > Без явного выбора — НЕ делать silent shift на +1 год.

3. Stage 0 **никогда** не сдвигает дату молча. Silent shift на +1 год
   («ну прошлый сезон уже закончился, значит следующий») — нарушение
   spec, ломает чистоту blind-валидации накопленных постмортем-кейсов.

**Зачем это нужно:** retrospective режим позволяет пользователю запустить
пайплайн на дате уже состоявшейся поездки (например, чтобы пересмотреть
свой выбор маршрута или сравнить с фактическим). Без этого gate модель
самостоятельно сдвинула бы сезон в будущее, отвечая на запрос про другое
направление и сезон, чем имел в виду пользователь.

### Trip format detection

Stage 0 v2 определяет формат поездки **до** Akt A, по содержанию запроса
пользователя. Это влияет на формулу размера longlist'а (§6).

| Формат | Триггер в запросе | Longlist size |
|---|---|---|
| **multi-region tour** (default) | Запрос не содержит явных single-base маркеров и `pre_committed_places` < 3 регионов | 6–8 регионов с reserve |
| **single-base trip** | Запрос содержит «жить в», «база в», «оттуда ездить», «day-trip из», «провести [N] недель/дней в [один город]» | 1 базовый регион + 2–4 day-trip направления |
| **explicit list** | `pre_committed_places` ≥ 3 регионов | все pre_committed + опц. 1–2 дополнительных |

Если триггеры неоднозначны (например, «2 недели в Турции» — это может
быть и multi-region и single-base) — спросить в Akt A одной строкой:
«Формат поездки — multi-region tour, single-base trip или explicit list?».
Не угадывать.

Результат фиксируется в YAML как `trip_format: multi_region_tour | single_base | explicit_list`.

### Точка старта поездки — `trip_start_city`

Stage 0 обязан зафиксировать, **откуда** начинается и где заканчивается
маршрут. Логика резолва:

- Если в запросе пользователя **явно назван стартовый город** («{город}
  транзит», «начало в {городе}», «лечу через {город} и далее в …») —
  этот город становится `trip_start_city`. Никаких «транзитных хабов» отдельно от
  него скилл не моделирует — даже если у пользователя физически будет
  пересадка с ночёвкой между домом и этим городом, эта пересадка
  описывается пользователем в запросе и оседает в `pre_committed_places`
  или в первой/последней ночи маршрута, без отдельной структуры.
- Если в запросе стартовый город **не назван** — `trip_start_city` =
  `home_city` (старт и конец маршрута в домашнем городе).
- При неоднозначности (запрос намекает на возможный старт-город, но не
  явно) — ОДНА строка-вопрос в batch'е уточнений: «Маршрут стартует из
  {home_city} или ты летишь через {угаданный_город}?»

**Производный флаг `home_eq_start`** = `home_city == trip_start_city`.
Используется Stage 4 для формулировки крайних дней маршрута (День 1 /
последний день).

**Аллокация ночей в `trip_start_city`.** Если `home_eq_start == false`,
аллокация ночей в стартовом городе — **по решению пользователя**: если
пользователь явно сказал «N ночей в [стартовом городе]» — выделить N
ночей; если просто «транзит» без длительности — предложить по умолчанию
2 ночи (одна на въезд, одна перед вылетом) и явно обозначить в Akt B
honest assessment как редактируемое решение (пользователь меняет
длительность через теги или явный комментарий). Если `home_eq_start ==
true` — ночей в стартовом городе как «транзитного хаба» не нужно вовсе;
день 1 — первый содержательный день маршрута.

**Извлечение `trip_wishes`.** Свободно-формулированные пожелания
пользователя из запроса, **не сводящиеся к топонимам** (которые
оседают в `pre_committed_places`) и **не профильные** (постоянные
интересы — в профиле). Это категории активности или конкретные
впечатления для **этой** поездки.

Примеры:

| Из запроса | trip_wish |
|---|---|
| «хочу [конкретное животное]» | `[животное]` |
| «хочу побыть на леднике» | `побыть на леднике` |
| «увидеть северное сияние» | `северное сияние` |
| «попасть на карнавал» | `карнавал` |
| «посидеть в кофейне с видом на океан» | `кофейня с видом на океан` |
| «пейзажная фотография [конкретного региона]» | `пейзажная фотография [региона]` |

Правила извлечения:

- Извлекать **вербатим** (как сказал пользователь), без перевода в
  «канонические» термины.
- Длина одной фразы — 1–6 слов.
- 0–8 пожеланий в списке. Если в запросе одни топонимы — список пустой.
- НЕ дублировать с `pre_committed_places` (если пользователь назвал
  конкретный топоним — это в `pre_committed_places`, не в `trip_wishes`).
- НЕ копировать профильные интересы (если в профиле уже есть «пейзажная
  фотография» как ядро интересов — не добавлять «фото» в `trip_wishes`,
  если пользователь не выделил это **особо для этой поездки**).

**Особые проверки направления:**

- Направление = один город без day-trip ambitions (например «хочу в
  [город] на 7 ночей, ничего за городом») → Stage 0 не нужен. Сообщить:
  «Один город без day-trips — региональное разбиение не имеет смысла.
  Иди сразу к Stage 3 или 4 для аналитики POI внутри этого города,
  либо к стандартной планировке без пайплайна». И стоп.
- Направление = один город с day-trip ambitions («жить в [городе] и
  ездить по окрестностям») → это **single-base trip** формат (см.
  «Trip format detection»). Stage 0 проходит, longlist =
  1 базовый регион + 2–4 day-trip направления.
- Направление = очень крупный регион/континент → предложить сузить
  хотя бы до 2–3 стран.

**Особые проверки длительности:**

- < 5 ночей → Stage 0 обычно overkill (одна локация, не нужно разбивать).
  Предупредить, спросить, продолжать ли.
- > 30 ночей → другая категория (extended slow travel, workation).
  Предупредить, что методология калибрована под 14–25 ночей; продолжить
  если пользователь подтверждает.

## 5. Параметры промта (placeholders)

В тексте промта (§6) используются плейсхолдеры в `{фигурных_скобках}`,
заполняемые из контекста перед отправкой LLM.

| Плейсхолдер | Источник | Пример |
|---|---|---|
| `{назначение}` | из запроса пользователя | название страны / макрорегиона |
| `{сезон_год}` | из запроса пользователя | «март {год}», «весна {год}» |
| `{длительность_ночей}` | из запроса пользователя | `13` |
| `{профиль_путь}` | резолв `profile_id` | `profiles/{profile_id}.md` |
| `{предзафиксированные_места}` | из запроса (опц.) | `[{топоним_1}, {топоним_2}]` |
| `{предыдущий_scope}` | если итерация | `0_scope.md` (предыдущая версия) |
| `{home_city}` | резолв по §4 (профиль → спросить, если пусто) | `Москва`, `Берлин`, `Буэнос-Айрес` |
| `{trip_start_city}` | резолв по §4 (запрос → дефолт `home_city`) | `Буэнос-Айрес`, `Ханой`, `Москва` |
| `{home_eq_start}` | вычисляемое: `home_city == trip_start_city` | `true` / `false` |
| `{trip_wishes}` | вербатим из запроса (§4) — 0–8 коротких фраз | `[северное сияние, кофейня с видом, побыть на леднике]` |
| `{retrospective}` | retrospective gate (§4); `true` для запуска на дате уже состоявшейся поездки, иначе опускается | `true` / опущено |

Если `{предзафиксированные_места}` пуст — заменить блок промта на
«Жёстких предзафиксированных мест нет, регионы выбираются с нуля».

Если `{предыдущий_scope}` отсутствует — соответствующие инструкции в
промте опускаются.

## 6. Промт (Akt A + Akt B)

Промт состоит из двух частей: **Akt A** (диалог + 3 вопроса
пользователю) и **Akt B** (формализация longlist'а после ответа
пользователя). Между ними — ответ пользователя в чате (не промт).

### 6.1 Akt A — общий header (одинаковый для всех trip_format'ов)

Подстановка плейсхолдеров → текст ниже отправляется LLM как user message
(после загрузки профиля и контекста). Профиль читается отдельным
сообщением до промта.

---

Я планирую поездку в **{назначение}** в **{сезон_год}** продолжительностью
**{длительность_ночей} ночей**. Состав группы и профиль интересов — в
прочитанном выше файле `{профиль_путь}`, применяй его при разбиении на
регионы.

**Домашний город:** `{home_city}`. **Стартовый город маршрута:**
`{trip_start_city}`.

{Если `{home_eq_start} == true`:} Маршрут стартует и заканчивается в
домашнем городе — день 1 = первый содержательный день маршрута, никаких
«транзитных ночей» в стартовом городе не выделять.

{Если `{home_eq_start} == false`:} Маршрут стартует в `{trip_start_city}`.
Если пользователь явно задал длительность пребывания — использовать её;
иначе предложить 2 ночи (1 на въезд, 1 перед вылетом) и явно обозначить
в honest assessment как редактируемое решение. `{trip_start_city}` сам по
себе как **регион** содержательно не анализируется — это точка старта,
не дестинация.

**Никаких предположений «после длинного перелёта», «акклиматизация после
дальнего рейса» и т.п. в текст не вставлять.** Дальность перелёта не
входит в scope Stage 0.

{Если `{trip_wishes}` непуст:}
**Пожелания пользователя для этой поездки:** `{trip_wishes}`. Учитывай
при оценке релевантности регионов; если регион — единственный/лучший
способ удовлетворить пожелание, отметь это плюсом в «Релевантность
профилю». Не подгонять scope под пожелания насильно — если пожелание не
ложится на сезон/географию, отметить как обоснованную невозможность,
не выдумывать.

{Если есть {предзафиксированные_места}:}
Уже зафиксированные места: **{предзафиксированные_места}**. Обязательны
к включению; регионы вокруг них выбираются с учётом стыковки.

{Если есть {предыдущий_scope}:}
Это пересмотр предыдущего scope (`{предыдущий_scope}`). При построении —
явно сравни с предыдущей версией и подсвети, что изменилось и почему.

### 6.2 Akt A — задача

**Trip format:** `{trip_format}` (multi_region_tour / single_base / explicit_list).

#### 6.2.1 Внутренний анализ (не показывается пользователю)

LLM mental loop. Сюда **не** показывает в Akt A turn — это traceability
артефакт, пишется в Akt B output md (см. §8).

1. **Сформировать full region universe** — все логические регионы
   направления, обычно:
   - single-country compact (Корея, Италия, Грузия): 6-10 регионов
   - single-country large (Япония, Китай, Индия): 8-12 регионов
   - two-country: 10-15 регионов
   - **Cap: 15.** Если естественно получается больше — **консолидировать
     соседние** в один (например, «Восточные нагорья» = Мондулкири +
     Ратанакири; «Северный Лаос» = Луангнамтха + Phongsavan если оба
     low-density).

   Для каждого региона — внутреннее описание 2-3 фактических предложения
   + density tag + сезонная пометка.

2. **Назначить `role`** для каждого региона:

   | Ключ (YAML) | Ярлык группы в теле | Ярлык региона в теле | Критерий |
   |---|---|---|---|
   | `core` | Ядро поездки | Ядро | HIGH density И сильный fit с профилем — ядро поездки |
   | `supporting` | Поддержка | Поддержка | MED density ИЛИ HIGH density с MED fit ИЛИ LOW density с сильным fit — дополнение к ядру |
   | `niche` | Нишевые | Нишевый | специфический интерес профиля (non-canonical / hidden gem) — для пользователя с этим интересом |
   | `borderline` | Пограничные | Пограничный | конфликт с профилем (исключённая категория) ИЛИ блокирующий сезонный/политический фактор — кандидат на excluded |

   **Язык роли:** в YAML `role:` — английский ключ (`core` …); в теле `.md`
   и в Akt A digest — русский ярлык из таблицы. Ключ и ярлык не смешивать.

3. **Non-canonical pass** — для каждого профильного интереса проверить
   «есть ли регион вне mainstream guidebook?». Найденные → `role: niche`
   + `non_canonical: причина соответствия профилю`.

#### 6.2.2 Akt A user-facing turn (digest)

**Сюда** идёт LLM сообщение к пользователю. Это **не enumeration всех
регионов** — это **digest для решения**, организованный по role-группам.

**Структура turn'а:**

1. **Universe summary** (1 строка): «Нашёл {M} логических регионов в
   {назначение} — {N_core} core / {N_supporting} supporting /
   {N_niche} niche / {N_borderline} borderline».

2. **Density warning** (1-2 строки, если применимо):
   - Country density: «{страна} имеет всего {K} значимых регионов»
   - DR-bandwidth: «если longlist >8 — DR теряет качество, рекомендую
     split-trip».

3. **Расчёт темпа** (1 строка): «для {длительность_ночей} ночей при
   longlist=~{L} → ~{длительность/L} ночей/регион
   ({размеренный|сбалансированный|активный})».

4. **Region universe by role** — НЕ sequential list, а **группированно**
   (заголовки групп — русскими ярлыками ролей, см. §6.2.1 п. 2):

   ```markdown
   ### Ядро поездки ({N} регионов)
   - **{Регион 1}** — {1 предложение differentiator, не enumeration
     характеристик}. (плотность: высокая · февраль: ok)
   - **{Регион 2}** — {differentiator}. (плотность: высокая · февраль: risk)
   - ...

   ### Поддержка ({N})
   - **{Регион 3}** — {differentiator}. (средняя · ok)
   - ...

   ### Нишевые ({N}) — под конкретные интересы
   - **{Регион 4}** — {какому профильному интересу соответствует}. (средняя · ok)
   - ...

   ### Пограничные ({N}) — скорее skip
   - **{Регион 5}** — {почему конфликт / блокер}. (низкая · bad — конфликт)
   - ...
   ```

   **Differentiator** — это **1 предложение про то, что отличает регион
   от других в той же группе**. Не enumeration POI, не маркетинг.
   Пример хорошего: «Тише и менее канонично, чем Луангпрабанг — карст
   плюс лодки». Пример плохого: «Драматичные карстовые пики над рекой
   Нам-Оу, радиальные видовые треки (пик Пха-Даенг), приречные деревни,
   пещеры, каяк» (это enumeration характеристик, не differentiator).

5. **Сезонные блокеры** отдельным абзацем (если есть): «В {сезон_год}
   {региональный блокер}: {описание} — затронуты регионы X, Y, Z».

6. **3 вопроса в одном batch'е к пользователю** (НЕ по одному):

   1. **Темп поездки:** «эта поездка — размеренная (3-4 ночи/регион,
      глубокое погружение) / сбалансированная (2-3) / активная (1-2,
      насыщенный темп)?»
   2. **Country quota** (только если multi-country): «баланс по странам
      или акцент на одну? Пример: `{country1}: proportional`,
      `{country2}: major`, `{country3}: transit`.»
   3. **Must-haves и skip'ы из universe** (опционально): «есть ли в
      списке выше что-то, что точно должно войти в longlist (must-have)
      или точно нет (skip-now)?»

**Стоп.** Ждать ответ пользователя.

#### 6.2.3 Цель и не-цель Akt A digest

**Цель:** дать пользователю **способ сравнить** регионы — не fact-sheet
для каждого. Пользователь, не знающий направления, должен после Akt A
понимать:
- какие регионы — ядро (точно стоит рассматривать)
- какие — пограничные (зависит от его интересов)
- какие — стоит пропустить

**Не цель:** показать всё, что LLM нашёл. Полный universe с 2-3
факт. предложений каждый — в Akt B output md, не в Akt A turn.

**Anti-pattern (КЛТ-обнаружение):**
> «Опус дал 17 регионов с описанием каждого, и без гугления мне эти 17
> вообще ничего не дали».

Перечисление 15+ unfamiliar регионов — **noise**, не signal.

Если пользователь говорит «выбери сам» — применить defaults
(`balanced`, proportional country quota, без must/skip) и сразу
перейти к Akt B.

### 6.3 Akt B — формализация longlist'а (после ответа пользователя)

После получения ответа пользователя:

1. Спарсить mood + country quota + must/skip из ответа.

   **Язык значений** (YAML — ключ, тело — ярлык; ключ и ярлык не смешивать):

   | Что | Ключ (YAML) | Ярлык в теле |
   |---|---|---|
   | `tempo` | `slow` | размеренный |
   | | `balanced` | сбалансированный |
   | | `active` | активный |
   | `trip_format` | `multi_region_tour` | мульти-регион-тур |
   | | `single_base` | одна база |
   | | `explicit_list` | явный список |
   | `density_tag` | `HIGH` / `MED` / `LOW` | высокая / средняя / низкая |
   | `country_quota[].weight` | `proportional` / `major` / `minor` / `transit` | пропорционально / основная / второстепенная / транзит |

   В прозе тела — **только русские ярлыки**. Если формат/темп упоминается
   впервые и ключ важен для трассировки, допустима одна форма
   «явный список (`explicit_list`)»; дальше по тексту — только русским.
   Смешанные формулировки вида «balanced с лёгким slow-уклоном» запрещены —
   пиши «сбалансированный, с лёгким уклоном в размеренный».

2. **Применить формулу размера longlist'а** в зависимости от `trip_format`:

   **Если trip_format == multi_region_tour:**
   - `target_count = ceil(длительность_ночей / 3)` — средние 3 ночи на
     регион (corrected для mood: slow → /4, balanced → /3, active → /2.5).
   - `longlist_count = ceil(target_count * 1.3)` — 30% reserve.
   - **Floor:** `longlist_count = max(longlist_count, ceil(available × 0.7))`
     — если доступно мало регионов, берём ≥70% (`available` =
     `total_regions_analyzed` минус excluded/borderline).
   - **Ceiling (применять ПОСЛЕДНИМ):** `longlist_count =
     min(longlist_count, 8)` — жёсткий DR-bandwidth limit. Ceiling
     **перебивает** floor: даже при большом `available` longlist ≤ 8.

   **Если trip_format == single_base:**
   - longlist = 1 базовый регион (указанный пользователем или выведенный
     из запроса) + 2-4 day-trip направления вокруг базы.
   - day-trip кандидаты — те регионы из universe, которые в радиусе
     1-3 часов транспорта от базы.

   **Если trip_format == explicit_list:**
   - longlist = все `pre_committed_places` + опц. 1-2 дополнительных
     региона (которые подходят профильно и стыкуются логистически).
   - Не превышать `pre_committed_count + 2`.

3. **Сформировать longlist** с reserve pair bindings:
   - Должные регионы (must) — включить первыми.
   - Остальные — заполнить до `longlist_count` по релевантности профилю.
   - Reserve pair: 1-2 региона помечены как `reserve_for: {другой_регион}`
     + `substitute_reason` — substitute, если основной отпадёт (сезон,
     логистика, политика).
   - Skip'ы из ответа пользователя — исключить.

4. **Для каждого региона longlist'а** заполнить 8+2 параметров (см. ниже).

5. **Сформировать excluded regions** — то, что в universe, но не в
   longlist'е. 1-2 строки + причина (логистика / сезон / mood / уже
   покрыто / skip пользователя).

6. **Non-canonical found** — отдельная подсекция: 2-3 hidden-gem региона
   из non-canonical pass'а + их статус (в longlist или excluded).

7. **Темп и распределение по странам** — в YAML + honest assessment.

8. **Honest assessment** — 1 абзац: уверенные кандидаты / пограничные /
   открытые вопросы. Без выбора за пользователя.

### 6.4 Для каждого региона longlist'а укажи (8+3 параметра)

1. **Название региона** (логическое) и состав ключевых мест.
2. **Что в нём принципиально** — 1-2 предложения, фактических, без
   клише.
3. **Минимум и оптимум ночей.** Для оптимума — content-density override
   при необходимости (см. §6.5).
4. **Релевантность профилю** — для каких интересов важен. Явно
   подсвети совпадения и конфликты.
5. **Сезонные особенности именно для {сезон_год}.** Жара оценивается
   по **ощущаемой температуре** (температура + влажность), а не по
   столбику термометра: 34 °C при влажности 80% и 34 °C в сухом климате —
   разные поездки. Если в профиле заполнена секция «Переносимость» —
   сверить сезон с климатическим порогом **самого чувствительного
   участника** и сказать прямо, что регион в это окно за порогом.
   Это фильтр региона и окна дат, а не примечание к дню: перенести
   активность на утро Stage 5 сможет, переставить сезон — уже нет.
6. **Логистическая стоимость включения** — стыковка с
   `{предзафиксированные_места}`, время в пути, нужен ли перелёт.
7. **Уровень туристической нагрузки 0-10.**
8. **Особые ограничения** — визы, политика, недоступность.
9. **Density tag:** строго `HIGH` / `MED` / `LOW` (uppercase canonical).
10. **Role:** `core` / `supporting` / `niche` / `borderline` (см. §6.2.1).
11. **Reserve pair binding** (опц.): `reserve_for: {другой_регион}` +
    `substitute_reason: ...` если регион — substitute.

**Жёсткий лимит:** 8-10 строк на регион в longlist'е. Не enumeration POI,
не часы съёмки, не цены, не время трансферов в минутах (это Stage 5).

### 6.5 Content-density override (mandatory check per HIGH region)

**Обязательная проверка для каждого региона с `density_tag: HIGH`.**
Не opportunistic — каждый HIGH-регион должен получить явный ответ:
override либо отсутствие override с reasoning.

#### Алгоритм

Для каждого региона с `density_tag: HIGH`:

1. Оценить реальный content (по знанию модели + опц. web search):
   «сколько ночей самодостаточного контента в регионе для данного
   профиля?».
2. Прочитать профильный max из `## Частота смены локаций` (например,
   «2-4 ночи на локацию, редко 5» → `profile_max = 4`).
3. Решение:
   - Если `observed_content_nights > profile_max` → **добавить override**
     в YAML `content_density_overrides[]`.
   - Иначе → в reasoning региона явная строка:
     `Content-density check: профильный max {N} достаточен — реальный
     content ~{K} ночей.`

**Это не silent skip.** Каждый HIGH-регион должен оставить trace либо
в YAML overrides, либо в reasoning. Pre-emit checklist (§6.7) проверяет.

Формулировка override в reasoning:

```
**Content-density override:** {регион} содержит ~{N} ночей самодостаточного
контента ({короткое перечисление активностей-типов}). Профиль ограничивает
до {max} ночей, но реально набирается {N} — рекомендую override.
```

YAML:

```yaml
content_density_overrides:
  - region: "{Регион}"
    profile_max_nights: 4
    observed_optimum_nights: 6
    reason: "{1 строка}"
```

### 6.6 Чего НЕ делать на этой стадии

**Из v2 архитектуры:**

- НЕ строй variants — это работа Stage 4 (после Stage 3 evidence).
- НЕ создавай блок `## Решение` или `## Предложенные пакеты` — этого
  в v2 артефакте нет (теги ставятся в Stage 3 md, выбор в Stage 4).
- НЕ выбирать регионы за пользователя — пользователь выбирает в Stage 4
  через теги.

**Из anti-scope-creep (Stage 0 ≠ Stage 5):**

- НЕ предлагай конкретные POI внутри регионов (это работа Stage 3).
- НЕ строй маршрут по дням (Stage 4 / Stage 5).
- НЕ рекомендуй конкретные отели или рестораны (Stage 5).
- НЕ называй **цены** — никакие («~$80», «~5 млн VND», «$80-120 RT»).
  Цены — Stage 5 territory.
- НЕ называй **часы съёмки / часы работы / часы пика** («лучший свет
  06:00-08:00», «пик к 8:00»). Это Stage 5.
- НЕ называй **время трансферов в минутах** («3.5 часа», «~50 мин»).
  Транспортная дистанция — общая («автобус 3-4 ч»), не точные расписания.
- НЕ называй **конкретных операторов** (Klook, GetYourGuide, имена
  турагентов). Это Stage 5.

**Из формат-discipline:**

- НЕ enumerate POI в описании longlist региона — даёшь differentiator,
  не fact-sheet. Список POI — это Stage 3 work.
- НЕ показывать full universe в Akt A turn — только digest по role
  (§6.2.2). Полный universe — в Akt B output md (§8), для traceability.
- НЕ silent-skip HIGH-density override check (§6.5).

**Из data-discipline:**

- НЕ выдумывать факты без основания. Если по региону данные
  неоднозначны — пометить `[требует проверки: что именно]`.
- НЕ маркетинговые штампы («жемчужина», «must-see», «вы почувствуете
  себя», «открой для себя», «магия места»).

### 6.7 Pre-emit checklist — обязательный self-check ДО записи файла

Прогнать каждый пункт ДО финального emit. Любое нарушение — НЕ
сохранять, исправить сначала. Чеклист закрывает типовые failure modes
Stage 0 (выявлены на КЛТ-валидации Opus vs Sonnet).

#### Класс A — YAML формат

- [ ] **Поле `stage:` присутствует** в YAML И **равно `0_scope`**.
      НЕ `0` цифрой, НЕ отсутствует, НЕ что-то другое.
      Это **уже было нарушено дважды** (КЛТ v1: `stage: 0`; Корея Sonnet:
      поле выпущено). Spec требует строкового идентификатора для
      downstream gate-проверок.

      ✓ correct:
      ```yaml
      stage: 0_scope
      ```
      ✗ wrong:
      ```yaml
      stage: 0          # цифра вместо строки
      # или: поле вообще отсутствует
      ```

- [ ] **`schema_version: 2`** присутствует.
- [ ] **`trip_format` валидный:** `multi_region_tour` / `single_base` /
      `explicit_list`.
- [ ] **YAML обрамлён `---`** сверху и снизу (стандартный frontmatter).

#### Класс B — completeness

- [ ] **`density_tag` поле present для КАЖДОГО региона в longlist YAML**
      (НЕ только в markdown body). Строго uppercase:
      `HIGH` / `MED` / `LOW`. НЕ `high` / `medium` / `medium_high` /
      `LOW-MEDIUM`. Если density только в body, не в YAML — нарушение.

      ✓ correct YAML entry:
      ```yaml
      - region: "Сеул и столичный регион"
        density_tag: HIGH
        role: core
        nights_min: 3
        nights_optimum: 5
      ```
      ✗ wrong:
      ```yaml
      - region: "Сеул и столичный регион"
        role: core
        # density_tag поле отсутствует — нарушение
        nights_min: 3
      ```

- [ ] **`excluded_regions[]` = universe MINUS longlist** (все
      проанализированные регионы, которые НЕ вошли в longlist —
      обязательно в YAML с reason). Не только user-excluded, не только
      несколько примеров. Если universe 12 регионов и longlist 7 —
      excluded_regions должно содержать ровно 5.
- [ ] **`non_canonical_regions[]` в YAML** содержит все non-canonical
      regions с `status: in_longlist | excluded`. НЕ только в md.
- [ ] **`longlist[]` имеет `role` для каждого региона** (`core` /
      `supporting` / `niche` / `borderline`).

#### Класс C — content_density_override mandatory check

- [ ] **Каждый HIGH-регион** в longlist'е получил явный ответ про
      override:

## 7. Правила работы

### Web search

Сделать 3–5 целевых поисков ДО анализа регионов:

- **Визы и доступ:** «visa requirements {гражданство из профиля}
  {назначение} {год_от-год_до}»
- **Политическая доступность:** «{назначение} travel advisory current»,
  «restricted regions for foreigners {назначение}»
- **Транспорт:** «{назначение} domestic transport overview», конкретные
  связи между {предзафиксированные_места} и крупными хабами
- **Сезон:** «{назначение} weather {сезон_год}», особенности климата
  для регионов с экстремальными условиями (горный сезон, муссоны,
  тайфуны, экстремальные температуры и т.п.)

Не делать web search по каждому POI — это работа Stage 1 (DR). Stage 0
проверяет только структурную доступность регионов.

### Что подсвечивать

- **Конфликты с профилем** — явные: «регион требует X, в профиле явно нет».
  Не молча отбрасывать.
- **Сезонные блокеры** — регион принципиально закрыт/недоступен в
  {сезон_год} (например, регион закрыт для иностранцев в текущий сезон).
- **Логистическую дороговизну** — если регион требует крюка с 2 перелётами
  для пары ночей, это явный сигнал «не оптимально».
- **Изменения после знакомых источников** — если знаешь, что в стране были
  политические или инфраструктурные изменения за последние 1-2 года —
  упомянуть, что данные могут отличаться от старых отчётов.

### Стиль

- Плотный, без воды, без клише.
- Каждый регион — 6-10 строк по 8 параметрам, не больше.
- Никаких эмодзи в ответе.
- Сезонные риски и ограничения — отдельной строкой, не закопаны в текст.
- **Тело и диалог — по-русски.** Значения enum'ов (темп, формат поездки,
  роль, плотность, вес страны) в прозе — русскими ярлыками (§6.3 п. 1);
  английские ключи живут только в YAML.
- **Группа путешественников — по имени.** В прозе — «Алексей и родители»,
  не `алексей_родители`: машинный `profile_id` идёт только в YAML-поле
  `travelers_profile`.

- YAML `longlist:` — primary contract для downstream скриптов.

### SSOT и роль YAML

- **YAML `longlist:` — single source of truth** для downstream-стадий.
  Stage 1, Stage 3 читают его машинно.
- Markdown body раздел `## Longlist` — дублирующая prose-форма для
  человеческого чтения; должна совпадать по содержанию с YAML.
- Если расходится — приоритет у YAML, скилл при детекте предупреждает
  пользователя.

## 9. Граничные случаи

### 9.1 `trip_id` уже существует с готовым `0_scope.md`

Это итерация: пересмотр scope. Read предыдущий `0_scope.md`, в Turn 2:

- Прочитать в шапку нового файла поле `previous_scope:` со ссылкой на старый.
- В промте указать «это пересмотр» — LLM явно сравнит с предыдущей версией.
- В honest assessment явно подсветить: «по сравнению с предыдущей версией:
  добавлен регион X / убран регион Y / переаллокация ночей …».

Сохранять как новый файл с суффиксом времени или перезаписывать — решает
пользователь. Дефолт — перезапись (старый можно восстановить из истории
git/Synology, если такая есть).

### 9.2 Профиль отсутствует

Gate (§4). Перечислить существующие, предложить выбрать или запустить
Profile mode.

### 9.3 Жёстких предзафиксированных мест больше, чем влезает в длительность

Например: 5 мест pre-committed на 7 ночей. После Stage 0 свободно 2 ночи
на разбиение. В honest assessment подсветить: «scope практически закрыт
жёсткими местами; оставшихся ночей хватит на 1–2 региона. Возможно, стоит
пересмотреть жёсткий список или увеличить длительность».

Не отказывать в анализе — выдать всё как есть и подсветить проблему.

### 9.4 Направление = весь континент

«хочу в Латинскую Америку на 21 ночь» — слишком широко. Предложить сузить
хотя бы до 2–3 стран, прежде чем разбивать на регионы. Это часть gate-проверки
направления (§4).

### 9.5 Web search вернул противоречивые данные о доступности региона

Например: один источник «открыто для иностранцев», другой «закрыто».
В описании региона явно отметить: `[требует проверки: текущая доступность
для гражданства {гражданство}, источники противоречат]`. Не делать
самостоятельный выбор за пользователя.

### 9.6 Пользователь не согласен с longlist'ом

В v2 нет блока `## Решение` — пользователь не выбирает регионы сразу
после Stage 0. Если longlist выглядит явно неправильно (важный регион
пропущен, странный набор) — пользователь может сразу же в чате попросить
переработать («перезапусти Stage 0, добавь регион X / убери Y»), и
Stage 0 пересоздаёт longlist.

Финальный выбор регионов всё равно делается **после Stage 3** через
теги — если регион в longlist'е, но в Stage 3 окажется без хорошего
POI evidence, пользователь поставит ему тег `не интересно` и в финальный
план он не войдёт.

### 9.7 Длительность изменилась после Stage 0

Если пользователь меняет `duration_nights` после Stage 0 завершён:
- Если изменение ≤ 2 ночей → Stage 4 справится при построении вариантов
  (просто другая аллокация ночей в тех же регионах).
- Если изменение > 2 ночей → перезапустить Stage 0 v2 с новой длительностью
  (формула N даст другой `longlist_count`).

## 10. Что НЕ делать

- НЕ предлагать конкретные POI внутри регионов (это работа Stage 3).
- НЕ строить маршрут по дням (Stage 4 / Stage 5).
- НЕ рекомендовать конкретные отели или рестораны (Stage 5).
- НЕ оценивать цены (любые попытки → TODO; на этой стадии не делать совсем).
- НЕ строить variants и НЕ создавать блок `## Решение` — это работа
  Stage 4 (после видения POI evidence из Stage 3).
- НЕ игнорировать профиль группы — если регион требует чего-то, на что
  есть явный конфликт в профиле, это должно быть в строке «релевантность
  профилю».
- НЕ молча отбрасывать регионы из universe. Если регион не в longlist'е —
  он в `## Excluded regions` с явной причиной.
- НЕ задавать вопросы по одному в Akt A — только batch из 3 вопросов.
- НЕ запускать Stage 1 промт после Stage 0 — это отдельная стадия,
  активируется отдельно.
- **НЕ писать `## Сохранить как` в тело файла** — этот блок выдаётся
  отдельным сообщением в чате после markdown-артефакта.
- НЕ использовать маркетинговые штампы в описаниях регионов («жемчужина
  страны», «must-see», «вы почувствуете себя…», «открой для себя»,
  «магия места»). Только фактические описания, профильно-релевантные.
- НЕ писать enum-ключи в прозе и заголовках тела (`Tempo: balanced`,
  `Role: core`, `Density: HIGH`, «формат — explicit_list») — там русские
  ярлыки (§6.3 п. 1). Ключи — только в YAML.
- НЕ переводить заголовки секций тела (`## Region universe`, `## Longlist`,
  `## Excluded regions`, `## Non-canonical found`, `## Honest assessment`) —
  это якоря парсинга для экспорта и downstream-стадий; их русские названия
  печатает рендер.
- НЕ называть группу путешественников машинным id (`алексей_родители`) —
  в прозе имя группы, id только в YAML.

## 11. Следующий шаг

После того как пользователь сохранил `0_scope.md`:

- Активируется Stage 1 (`/travel-planning` → «нужен промт DR» или
  явное «Stage 1 для {trip_id}»).
- Stage 1 читает YAML `longlist:` и формирует промт для Deep Research
  по **всем регионам longlist'а** (включая reserve pairs).
- 30% reserve в longlist'е страхует от потери региона на этапе DR
  (плохой POI coverage, неполный набор — substitute берёт его место).

Скилл не запускает Stage 1 автоматически — пользователь решает, когда
готов перейти к сбору отчётов.

Финальный выбор регионов (которые в плане) делается **после Stage 3**
через тегирование в `3_poi_pool.md`. Stage 0 v2 не выбирает финальные
регионы — это работа Stage 4 с учётом пользовательских тегов.
