# stage5-final.md

Полная спецификация Stage 5 — финальной консолидации. На входе —
выбранный на Stage 4 вариант маршрута с заполненным блоком
`## Решение` (опционально с правками пользователя) и профиль группы.
На выходе — полный детализированный план по дням с конкретным
транспортом, отелями, программой, бюджетом, планом реагирования на риски и
списком TODO для верификации.

Философия и место в пайплайне — `../methodology.md` §3 «Stage 5».

## 1. Назначение

Превратить выбранный shape вариант Stage 4 v2 в финальный
детализированный план уровня дня. **Stage 5 v2 владеет всем
micro-уровнем** (расширение по сравнению с v1):

- **Day-by-day POI selection** из Stage 3 pool (раньше частично было в
  Stage 4 v1 — переехало в Stage 5 v2).
- **Конкретный транспорт** (рейс с номером, операторы автобусов, время
  отправления) — раньше Stage 4 черновик, теперь Stage 5 полностью.
- **Отели** (имя, район, рейтинг + TODO для верификации цены).
- **Конкретный бюджет per day** (теперь Stage 4 v2 даёт только relative
  cost rank, точные цифры — здесь).
- **Day-fill discipline** (Pre-emit Class G): каждый день должен иметь
  POI на morning slot AND afternoon slot, пустой полудень допустим
  только с явной причиной (день отдыха, буфер при переезде, компенсация
  джет-лага).
- **Stop-over рейсы** описываются явно (прямой / технический stop без
  выхода / stop с ночёвкой) — без двусмысленностей.
- **Активный web search** для расписаний / часов работы / стоимости
  входа / отелей (рейтинги).
- **План реагирования на риски** для основных рисков.
- **Чеклист «что проверить за 2 недели до поездки»** со ссылками на
  источники.

Stage 5 — **детализация, не пересмотр**. Решения Stage 0 (longlist),
Stage 3 (POI categorization + теги), Stage 4 (выбор варианта) считаются
финальными и не подвергаются ревизии в Stage 5.

### Iteration loop

Stage 5 versioned: `5_final_plan_v{N}.md`. При новой итерации Stage 4
(`4_variants_v{N+1}.md`) — Stage 5 запускается с тем же `{N+1}`.

Два режима:

- **Surgical** — выбранный вариант структурно совпадает с предыдущей
  итерацией Stage 5 (`5_final_plan_v{N-1}.md`; тот же набор регионов,
  та же аллокация ночей ±0). Скилл берёт предыдущий план как основу и
  применяет точечные изменения POI/активностей внутри дней.
- **Reconstructive** — структура отличается от предыдущей итерации
  (или это первая v1). Скилл строит план с нуля.

Mode детектируется детерминированно и явно объявляется пользователю в
начале Turn 2.

## 2. Inputs / Outputs

**Inputs:**

- Stage 4 артефакт: `{travel_root}/trips/{trip_id}/4_variants_v{N}.md`
  ← Read. Stage 5 берёт **выбранный пользователем variant** из
  заполненного блока `## Решение` Stage 4 md (поле
  `**Выбран вариант:**` + опц. правки). Пользователь заполняет блок
  руками, работая с md напрямую.
- Профиль: `{travel_root}/profiles/{profile_id}.md` ← Read
  (особенно `## Платёжная инфраструктура`, `## Бюджет`, `## Гастрономия`,
  `## Явные исключения`).
- Опц.: предыдущая итерация Stage 5 `5_final_plan_v{N-1}.md` →
  если есть, используется для mode detection (surgical vs
  reconstructive) и diff.
- Опц. quality-enhancing inputs (через Glob + SKILL.md gate):
  `0_scope.md` — для дат / `home_city` / `trip_start_city` / `trip_wishes`;
  `3_poi_pool.md` — для POI pool, теги, кластеры. Если найдены в
  travel_root но не приложены — STOP с одной строкой вопроса.

**Outputs (в чат + manual save пользователем):**

- `{travel_root}/trips/{trip_id}/5_final_plan_v{N}.md` — Stage 5 v2
  артефакт с YAML-шапкой и 9 обязательными секциями по §8.

**Downstream:** Export mode (Partner / Family / Friends / Self) для
адаптации финального плана под аудитории.

## 3. Поток

Один режим работы. 2 turn'а в стандартном случае; 4 turn'а при
неоднозначных правках пользователя (opt-in clarification, §9.4).

### Turn 1 — пользователь

«детализируй план для {trip_id}», «Stage 5 для {trip_id}»,
«консолидируй финальный план», «пятый шаг», «выбрали вариант {X}».

### Turn 2 — скилл

**0. Model self-check (обязательный первый шаг).** Назвать модель
одной строкой: «Я модель: <name>. Stage 5 рассчитан на Sonnet +
adaptive thinking (surgical) или Opus + adaptive thinking
(reconstructive).»

- **Opus** (с adaptive thinking или без) — продолжать. При
  reconstructive — оптимально; при surgical — избыточно, но не вредно.
- **Sonnet + adaptive thinking** — продолжать; если режим окажется
  reconstructive, после mode detection (шаг 1) одной строкой предложить
  переключение: «Mode reconstructive — рекомендую открыть новый чат на
  Opus для интеграции многих переменных под штучные ограничения.
  Продолжить на Sonnet+thinking или переключиться?». Дождаться ответа.
  При surgical — продолжать без предложения.
- **Sonnet без thinking** — одной строкой остановиться: «Stage 5
  на Sonnet без thinking не поддерживается (детализация по дням
  деградирует — пропускаются конкретные часы, операторы, swap-стратегии
  для рисков). Включи adaptive thinking либо открой новый чат на Opus
  4.7». Дождаться решения.
- **Haiku** — **остановиться**: «Stage 5 не поддерживается на
  Haiku. Открой новый чат на Sonnet + adaptive thinking или на
  Opus. Не нажимай «Continue» после safety pause — это переводит
  на Haiku». Логика — `../../SKILL.md` блок про safety filter.

1. **Gate-проверки (§4).** Если хоть одна не выполнена — отказ.

2. **Получить `4_variants.md`** — источник по приоритету
   `../storage-and-naming.md` §8.0 (приложенный файл → Synology mount;
   сниппеты и превью данными не считать).

3. **Парсинг блока `## Решение` Stage 4** (§6.2). Извлечь:
   - `**Выбран вариант:**` — нормализовать к `вариант_а` / `вариант_б`
     / `вариант_в` / `кастомный`; сохранить raw label.
   - `**Состав:**` (опц.) — текст с описанием состава, может содержать
     правки.
   - `**Почему этот выбор:**` (опц.) — обоснование, может содержать
     дополнительные правки или акценты.
   - Семантически интерпретировать правки: замена формата активности,
     добавление, удаление (см. §6.2).

4. **Mode detection (§6.1).** Детерминированно:
   - `previous_plan == null` → **reconstructive**.
   - `previous_plan != null` + Read предыдущего плана + структурное
     совпадение (тот же набор регионов **в том же порядке маршрута** +
     та же аллокация ночей ±0) → **surgical**.
   - Иначе → **reconstructive** с переиспользованием payment-инфры и
     логики реагирования на риски из previous_plan. **В частности, реордер
     регионов** (тот же набор и ночи, но переставленный порядок) — это
     reconstructive: меняются все межрегиональные плечи, финальный город и
     хореография дней, что точечными правками внутри дней не покрыть.

   Объявить пользователю одной строкой: «Mode: {surgical|reconstructive}.
   {Одна фраза-обоснование}». При reconstructive на Sonnet+thinking —
   предложить переключение на Opus (шаг 0).

5. **Read профиля.** Извлечь:
   - `## Платёжная инфраструктура` — для секции «Деньги» в выходе.
   - `## Бюджет` — `budget_target_rub` уже в YAML Stage 4, но
     перепроверить.
   - `## Гастрономия` — диетические ограничения для секции
     «Гастрономическая шпаргалка» и при выборе ресторанов.
   - `## Явные исключения` — что не предлагать.
   - `## Базовый город` — для секции «Шапка» (билеты от home_city, если
     `home_eq_start == false`).

6. **Read Stage 0 (`0_scope.md`) — ОБЯЗАТЕЛЬНО**, если файл существует
   в `{travel_root}/trips/{trip_id}/`. Извлечь из YAML и тела:
   - **Точные даты поездки** (если зафиксированы — поле дат в YAML
     либо вычисляются из месяца `season` + длительности).
     Использовать эти даты как факт; не подставлять «представительные»,
     если реальные доступны.
   - `home_city`, `trip_start_city`, `home_eq_start` —
     наследуются в YAML Stage 5.
   - `pre_committed_places` — должны присутствовать в маршруте.
   - `trip_wishes` — backstop-сигнал; проверить, что каждое пожелание
     либо закрыто в маршруте Stage 4 (через priority pool / правки
     пользователя), либо явно в Warnings YAML как непокрытое.

   **Если `0_scope.md` недоступен** (новая поездка без Stage 0, либо
   файл повреждён) — допустимы представительные даты с **обязательным
   warning в YAML Stage 5**: «`0_scope.md` недоступен / не прочитан —
   используются представительные даты {диапазон}; сверить с
   фактическими билетами». Молчаливая подстановка представительных дат
   при наличии 0_scope.md — нарушение Pre-emit Class A.

7. **Опц. Read Stage 3** (`3_poi_pool.md`) для контекста
   synergy-пар и user_comments по POI — если нужно для детализации
   операторов / комбо-туров.

8. **Опц. Read previous_plan** (если есть). Извлечь:
   - Payment-инфраструктура (карты, обменники, ATM).
   - Логика реагирования на риски (swap-стратегии при отменах и сбоях).
   - Расписания и операторы транспорта (если даты в новом плане
     совпадают).
   - Конкретные отели и адреса (если регионы сохранились).
   - Чеклист «за 2 недели».

9. **Проверка конфликтов правок со структурой варианта (§9.4).** Если
   правка пользователя противоречит структуре (например, «добавить
   день в {регион}» в варианте, где у этого региона нет резервных
   ночей) — выдать ОДИН batch уточнений и остановиться. Дождаться
   ответа Turn 3.

10. **Web search для целевых данных (§6.4).** Активные поиски:
    - Расписания внутренних рейсов/автобусов/поездов/паромов на даты
      поездки.
    - Часы работы и стоимость входа основных достопримечательностей.
    - Конкретные операторы synergy-пар Stage 3 (если есть).
    - Сезонные ограничения (закрытие пещер в дожди, ремонты, фестивали).
    - **Имена/районы/рейтинги отелей** под класс из профиля. Поиск
      рейтинга — **сначала для основного именованного кандидата
      каждой ночёвки**, потом для альтернатив (см. §6.7 Class C).
    - Опц. адреса/специализации ресторанов.

11. **Опц. MCP-расширения для цен отелей (§6.4, §7).** Если доступны
    `Booking.com` / `Expedia` MCP и пользователь не возразил — вытянуть
    диапазоны цен на даты поездки. Подставляются с пометкой «через
    {Booking|Expedia} MCP, YYYY-MM-DD». **Не заменяют TODO** — TODO
    остаётся, поскольку пользователь финально бронирует сам.

12. **Сборка плана (§6.3, §6.5, §6.6, §8).** 9 обязательных секций по
    методологии §9. Применить правки пользователя естественно в маршрут
    без маркеров в днях; ОДНА summary-строка в `## Контекст и ключевые
    параметры` («Применены правки из `## Решение` Stage 4: …»).

13. **Pre-emit checklist (§6.7) — обязательно.** Прогнать все 8 классов (A–F + G + P)
    self-check'а ДО записи финального ответа. При нарушении любого
    пункта — НЕ сохранять, исправить сначала.

14. **Output — environment-aware** (тот же паттерн, что Stage 2 §3 шаг 10):

    - **Write/Bash доступен:** СРАЗУ сохранить файл через `Write` как
      `{travel_root}/trips/{trip_id}/5_final_plan_v{N}.md`. В чат —
      короткий summary + `computer://`-ссылка. Не говорить «спека не
      пишет файл сам».
    - **Write недоступен** (claude.ai chat): environment-aware emit — Message 1 =
      готовый `5_final_plan_v{N}.md` целиком одним блоком; Message 2 =
      save instruction + summary. На больших планах (>50KB) split на
      part_a/part_b в Message 1.

    Имя строго `5_final_plan_v{N}.md` с versioning (v2 — см.
    `../storage-and-naming.md` §4.1).

15. **Карточка `trip.yaml` — вместе с планом.** Финальный план принят →
    выдать обновлённый `{travel_root}/trips/{trip_id}/trip.yaml` (тем же
    способом, что и план: `Write` или блоком в чат): `status: ready`, свежий
    `updated` и **точные даты**, если у дней плана они есть — `start` = дата
    первого дня, `end` = последнего, `YYYY-MM-DD` (год — из `trip_id`,
    переход через январь переносит год; то же правило выполняет
    `scripts/trip_dates.py`). У дней нет дат «(ДД.ММ …)» или год не
    выводится — ключей `start`/`end` нет: поездка остаётся с `season`,
    это штатно. Перед выдачей — `check_format.check_trip_meta` +
    `trip_meta_warnings` (`../storage-and-naming.md` §2.3).

### Turn 3 — пользователь (опционально)

Если на шаге 9 выдан clarification batch — отвечает.

### Turn 4 — скилл (опционально)

Применить решения пользователя из Turn 3, продолжить с шага 10. В
YAML установить `clarification_used: true`.

**Стоп.** Пользователь сохраняет файл, использует план как руководство
к поездке. Опционально — Export mode для адаптации под аудитории.

### Размер выборки и нагрузка

Stage 5 — самый объёмный выход пайплайна. Длинная поездка (≥18 ночей,
≥4 региона) с активным web search'ем может выдать 600–900 строк. Если
выход не вмещается в один ответ — split на `5_final_plan.md` (основной)
+ `5_final_plan_part_b.md` (продолжение), см. §9.10.

«Опущено for brevity» — **запрещено** (§10). Если детализация
выходит за рамки одного ответа — явно split, не сокращение.

## 4. Gate-проверки на входе

Применяй ДО запуска работы. Если хоть одна не выполнена — отказ
ОДНОЙ строкой с конкретным указанием, чего не хватает.

| Что | Обязательно | Если не задано |
|---|---|---|
| `trip_id` | да | спросить или предложить из существующих (Glob) |

| `## Решение` блок Stage 4 с непустым `**Выбран вариант:**` | да | отказать: «заполни блок `## Решение` Stage 4 и сохрани, потом перезапусти» |

| Секция `## Платёжная инфраструктура` в профиле | да | предупредить, продолжить с TODO-меткой; в YAML добавить `incomplete_sections` warning |

**Отказ при отсутствии Stage 4:**

```
Stage 5 требует результат Stage 4.
Не нашёл `{travel_root}/trips/{trip_id}/4_variants.md`.

Запусти Stage 4: «Stage 4 для {trip_id}».

Стоп.
```

**Отказ при незаполненном блоке `## Решение` Stage 4:**

```
Stage 5 требует выбранный вариант. В `4_variants.md` блок
`## Решение` пуст или поле `**Выбран вариант:**` отсутствует.

Открой `4_variants.md`, заполни блок (минимум `**Выбран вариант:**
A | B | C | кастомный`), сохрани, перезапусти Stage 5.

Стоп.
```

ОДНА строка ответа — ничего больше.

**Transport consent gate** для Stage 4 файла, если он не приложен и
Synology недоступен — общий механизм `../storage-and-naming.md` §1.4.

## 6. Промт — методика консолидации

LLM получает Stage 4, профиль, опц. previous_plan (Read) и инструкцию
ниже как системный контекст. Промт состоит из частей:

- §6.1 Mode detection (surgical vs reconstructive)
- §6.2 Парсинг выбора варианта из чата + опц. правок
- §6.3 Уровень детализации дня
- §6.4 Web search policy и опц. MCP-расширения
- §6.5 Бюджетная консолидация и TODO discipline
- §6.6 Опц. сравнение с предыдущей итерацией 5_final_plan_v{N-1}
- §6.7 Pre-emit checklist (обязательный self-check ДО сохранения)

### 6.1 Mode detection

Детерминированный алгоритм. Выполняется один раз на шаге 4 потока.

**Алгоритм:**

```
# Найти предыдущую итерацию Stage 5
prev_iteration = Glob("trips/{trip_id}/5_final_plan_v*.md") - текущая
                 → max version (либо None для первой итерации)

if prev_iteration is None:
    mode = reconstructive
    warning("первая итерация Stage 5 для этой поездки — режим reconstructive")
elif Read(prev_iteration) недоступен:
    mode = reconstructive
    warning("предыдущая итерация {file} не читается — режим reconstructive")
else:
    prev_regions = chosen_regions из YAML prev, В ПОРЯДКЕ МАРШРУТА (sequence)
    prev_nights  = извлечь аллокацию ночей из предыдущей итерации
    new_regions  = chosen_regions из выбранного variant'а Stage 4 v2, в порядке маршрута
    new_nights   = извлечь аллокацию ночей из variant'а

    # ВАЖНО: сравнение УПОРЯДОЧЕННОЕ (list, не set). Реордер регионов
    # (тот же набор + те же ночи, но переставлен порядок) — НЕ surgical:
    # он пересобирает каждое межрегиональное плечо, финальный город и
    # хореографию дней. Это reconstructive.
    if list(prev_regions) == list(new_regions) and
       max(|prev_nights[r] - new_nights[r]|) == 0:
        mode = surgical
    else:
        mode = reconstructive (смена набора / смена ночей / РЕОРДЕР —
                              с переиспользованием payment-инфры и логики
                              реагирования на риски из prev)
```

**Объявление пользователю одной строкой:**

- Surgical: «Mode: surgical — структура совпадает с
  `5_final_plan_v{N-1}.md`, применяю точечные изменения POI/активностей».
- Reconstructive первая итерация: «Mode: reconstructive — это первая
  итерация плана, строю с нуля».
- Reconstructive c prev: «Mode: reconstructive — структура изменилась
  vs `5_final_plan_v{N-1}.md` ({краткое описание различий}); переиспользую
  payment-инфраструктуру и логику реагирования на риски».

**Legacy compat:** если в YAML Stage 4 указан `previous_plan` (старая
схема v1), он используется в дополнение к v2 versioned логике —
fallback при отсутствии Stage 5 итераций.

**В surgical mode:**
- Брать previous_plan как основу.
- Применять только конкретные изменения, продиктованные выбранным
  вариантом Stage 4 + правками пользователя.
- Сохранять без изменений: payment-инфраструктура; логика реагирования на риски;
  расписания транспорта (если даты совпадают); конкретные отели и
  адреса (если регионы и даты сохранились).
- Изменения явно отражать в секции `## Diff с предыдущим планом`.

**В reconstructive mode:**
- Строить план с нуля по выбранному варианту Stage 4 + правкам.
- Если `previous_plan != null` — извлечь и переиспользовать:
  payment-инфраструктура (если домашние карты не изменились);
  логика реагирования на риски (общие принципы — буферы, swap'ы); чеклист
  бронирований (адаптируя под новый scope). Конкретные блоки (отели,
  расписания) — пересчитать заново.
- Заполнить секцию `## Diff с предыдущим планом`.

### 6.2 Парсинг блока `## Решение` Stage 4 (выбор варианта + опц. правки)

Пользователь записал выбор в блок `## Решение` Stage 4 md (поле
`**Выбран вариант:**`, опц. `**Состав:**` / `**Почему этот выбор:**`
с правками). Stage 5 парсит этот блок:

| Содержимое блока `## Решение` | Что извлекается |
|---|---|
| `**Выбран вариант:** A` | chosen_variant = A |
| `**Выбран вариант:** B` | chosen_variant = B |
| `**Выбран вариант:** C` + `**Состав:** … без региона X` | chosen_variant = C + правка «убрать X» |
| `**Выбран вариант:** A` + `**Состав:** … день на хайк в Y` | chosen_variant = A + правка «добавить хайк в Y» |

**Шаг 1 — извлечь chosen_variant.**

Прочитать поле `**Выбран вариант:**` блока `## Решение`. Допустимые
значения (lowercase): `a`, `b`, `c` (+ нормализация регистра).
Нормализованный:
- `A` / `a` / «вариант_а» → `A`
- `B` / `b` / «вариант_б» → `B`
- `C` / `c` / «вариант_в» → `C`

Пустое поле / placeholder ловит gate (§4) — сюда не доходит. Если
пользователь вместо блока назвал вариант в чате — принять и это.

**Шаг 2 — извлечь опциональные правки.**

Если в блоке `## Решение` есть `**Состав:**` / `**Почему этот выбор:**`
с дополнительным текстом — интерпретировать как правки:

| Тип правки | Признаки в блоке `## Решение` | Действие Stage 5 |
|---|---|---|
| **Замена формата активности** | «{POI} не {формат A}, а {B}»; «{POI} без рассвета» | Заменить формат в маршруте |
| **Добавление активности** | «добавить {активность} в {регион}»; «попробовать {X}» | Найти подходящий слот, добавить. Если слот неочевиден — clarification (§9.4). |
| **Удаление активности** | «убрать {X}»; «не делать {X}»; «без {X}» | Не включать; в `## Diff` отметить. |
| **Уточнение** | «отель в {регионе} премиум»; «машина с водителем» | Изменить уровень/способ; зафиксировать в `## Контекст` summary-строкой. |
| **Замена региона** | «вариант A но без {регион} → добавь {другой}» | Это структурное изменение — Stage 5 это не делает. Предложить пользователю перетегировать и запустить Stage 4 v{N+1}. |

**Шаг 2b — комментарии к вариантам.**

Если в Stage 4 md есть секция `## Комментарии к вариантам` (опц.; строки
`**Вариант X:** …` и `**Общий комментарий:** …`, заполняет пользователь):

- комментарий к **выбранному** варианту и общий комментарий — те же правки,
  что в `**Состав:**` (таблица выше);
- комментарии к **невыбранным** вариантам — только контекст: если там названо
  что-то, что пользователь хочет «забрать» в выбранный («из B взять Чеджу»),
  это правка; оценки вида «B слишком тяжёлый» — не действие;
- противоречие с блоком `## Решение` → приоритет у `## Решение`, расхождение —
  в clarification (§9.4).

**Шаг 3 — применение правок естественно в маршрут.**

- Правки встраиваются в маршрут **без специальных маркеров** в днях.
  Пользователь, читающий через месяц, не должен спотыкаться о пометки
  «эту активность я выбрал в `## Решение`».
- ОДНА summary-строка в `## Контекст и ключевые параметры`:

  ```
  **Применены правки пользователя из `## Решение` Stage 4:** {1-2 фразы}.
  ```

- Если правок нет — summary-строку не добавлять.

**Шаг 4 — кастомный вариант.**

Если `chosen_variant_raw == кастомный`:
- В `**Состав:**` должно быть структурное описание состава (что взято,
  что добавлено).
- Если описание непустое — использовать его как скелет.
- Если описание пустое — clarification: «Выбран кастомный вариант, но
  блок `**Состав:**` пуст. Опиши состав структурно (какие регионы,
  сколько ночей, что включать) и перезапусти». Stop.

### 6.3 Уровень детализации дня

Каждый день маршрута — компактный блок с фиксированными подсекциями.
Иконки используются для быстрого визуального сканирования.

**Шаблон дня:**

```markdown
### День N (DD.MM Wd). Краткое название дня

📍 {Локация-откуда → локация-куда; расстояние, способ переезда, время в пути}
🏨 {Опц. маркер брони: [[бронь: план]]} **{Имя отеля}**, {район/адрес}, {рейтинг если найден} — **TODO: верифицировать цену на {даты} на Booking.com**. {Ориентир по архивным/типовым ценам региона: ~X ₽/ночь; реальная — возможно Y–Z ₽}. {Опц. «почему выбран» — 1 фраза-компромисс}. {Опц. альтернативы: «Альтернатива: {имя_2}, {имя_3}»}. {Опц. блок-маркер: «— ночи N, N+1, N+2»}
{Строка 🏨 опускается полностью, если отель тот же, что в предыдущий день — см. правила ниже.}

🎯 **Программа:**
- {Time} — {активность}, {адрес/часы работы}, {цена входа если есть}, {время на посещение}, {опц. оператор для synergy-пар}. {Опц. для якорного POI — атрибуция: *Источник: {тег/автор Stage 3}*}
- ...
- {Опц. вечером — ресторан}: **{имя}** ({адрес}, {специализация/блюдо}, {диапазон цены})

💰 ~{диапазон} ₽/{чел.|на группу}

⚠️ {Короткий указатель риска (1 фраза): что под угрозой + куда смотреть. Полная развёртка «если пошло не так» — в `## План реагирования на риски`.} {Опц. для погодозависимого дня: [[погода: {краткий риск}]]}
```

Элементы, помеченные «опц.», — **backward-compatible**: их отсутствие во
входном/старом плане не ошибка. Маркеры статуса и атрибуции описаны в §6.3.1.

**Правила:**

- **Локация-ночёвки** в блоке `🏨` — конкретное имя отеля, район,
  рейтинг (если найден web search'ем), диапазон-оценка цены, TODO-метка.
  Опц. 1-2 альтернативы в той же ценовой категории. **Цены отелей —
  всегда диапазон с TODO**, даже если найдены через MCP (см. §6.4, §7).
- **Повторные ночи в том же отеле — строка `🏨` ОПУСКАЕТСЯ.** Если
  пользователь ночует в одном отеле подряд (2-3+ ночи), полное описание
  даётся **только в день заселения**; в последующих днях строка `🏨`
  не пишется (никаких «🏨 Та же гостиница» / «🏨 Та же гостиница
  (Ханой)» — это шум). Подразумевается, что отель остаётся прежним до
  следующего блока с явным `🏨 {новый отель}`. Опц. при заселении —
  обозначить блок: «{имя отеля} — ночи N, N+1, N+2». При смене отеля в
  том же городе (например, апгрейд после буфера) — новый `🏨` блок
  даётся явно.
- **Часы программы** — конкретные (не «утром / днём / вечером»), если
  активность чувствительна ко времени (рассвет/закат, время работы);
  иначе «утром», «днём», «вечером» допустимы.
- **Цены входа / часы работы / адреса** — со ссылкой на источник web
  search'а либо `TODO: проверить`. Не выдумывать.
- **Операторы** — если активность из synergy-пары Stage 3, указать
  конкретного оператора (по web search), иначе `TODO: выбрать
  оператора`.
- **Бюджет дня** — диапазон в ₽ (per person или на группу — по
  профилю); сумма из всех платных активностей дня + размещение
  midpoint + еда по типовой норме региона.
- **Swap-стратегии** — для каждого риска из `## Ключевые риски`
  выбранного варианта Stage 4 — конкретный swap; если новый риск
  возникает на детализации (например, операция оператора закрыта в
  выходные) — добавить.

#### 6.3.1 Маркеры статуса и атрибуции (Этап-2)

Шесть **опциональных, backward-compatible** конвенций. Их отсутствие в
старом плане не ошибка; рендер без них работает как раньше. `check_format`
валидирует выход (новый vN+1), не вход.

**(#8) Happy path vs контингенси — разделение.** Дневной `⚠️`-блок — это
**короткий указатель** (1 фраза: что под угрозой + куда смотреть), не
дерево «если пошло не так». Полная развёртка контингенси (сценарий →
вероятность → действие/swap) живёт в `## План реагирования на риски`.
Принцип вовлечённости: основной путь дня не доводить до поминутной
обороны. Пример:
- ❌ в дне: «⚠️ Если поезд KTX отменён — взять автобус 1234 от
  терминала B, ~3 ч, ₩18 000; если и он отменён — такси ~₩90 000; если
  снег закрыл перевал — остаться ещё ночь в Сокчо, перекроить день 6…»
- ✅ в дне: «⚠️ Перевал к Сораксану зависит от снега — план Б в риск-таблице.»
  + строка в `## План реагирования на риски` с полным swap.

**(#12) Тирирование рационала.** Тонкий «почему» (1 фраза) остаётся в точке
использования (`📍`/`🎯`/`🏨`). Глубокий рационал (почему именно этот буфер,
почему такая хореография региона, развёрнутый трейдофф) — НЕ вшивать в текст
дня; он идёт в `## Контекст и ключевые параметры` → под-секцию
**«Логика ключевых решений:»** (рендер выносит её в приложение в конец).
Цель — день читается как операционный план, не как защита решений.

**(#13) Строка-источник для якорных POI.** Для **якорных** POI (MUST/HIGH
из Stage 4 priority pool) — inline-атрибуция источника курсивом (звёздочки,
не подчёркивания — рендер курсивит `*…*`): `*Источник: {тег или автор
Stage 3}*` (например `*Источник: HIGH-автор Алара2009*` или
`*Источник: STRONG CONFIRMED*`). Только POI, **не рестораны**
(ресторанную атрибуцию не доискиваем). Зачем: Stage 5 иначе теряет авторские
атрибуции Stage 3 на детализации — пользователь не видит, откуда взялась
точка. Проходные POI (закатная точка, кофейня) — без атрибуции.

**(#10) Booking-режим отеля «до брони».** Stage 5 — это режим **«до
брони»**: блок `🏨` несёт **логику выбора** (1 фраза «почему выбран» —
компромисс: «ближе к вокзалу ценой шумной улицы»), **дифференцированные
альтернативы** (не клоны: разный трейдофф — «тише, но +15 мин до центра») и
**TODO-цену**. Маркер статуса — `[[бронь: план]]` (опц.; ставится в начале
строки `🏨`). После реального бронирования статус меняется на
`[[бронь: забронировано]]`, а логику выбора заменяет доступ/удобства/завтрак
(это уже пост-бронь, делается отдельно — здесь не эмитим).

**(#14) Тезис «Замысел маршрута».** В начале `## Контекст и ключевые
параметры` — опц. строка `**Замысел маршрута:** {2–3 фразы}` — короткая
формулировка идеи маршрута (не пересказ дней): чем этот маршрут является как
целое, какой компромисс в его основе. Рендер выносит её на обложку. Пример:
«**Замысел маршрута:** север Вьетнама без юга — горы и террасы вместо
пляжей; база-радиалы из Ханоя ради минимума переездов; темп умеренный с
буфером под дожди.»

**(#15) Маркер «погодный риск».** Для погодозависимого дня/активности — опц.
маркер `[[погода: {краткий риск}]]` (например `[[погода: тайфунное окно,
сверить JTWC за неделю]]`). Явный маркер от модели, не keyword-детект.
Рендер показывает его отдельным цветным чипом (синий — отличается от
amber-TODO и green-«забронировано»).

**Длительность переездов и расстояния:**

- Время в пути — диапазон или среднее со ссылкой на источник (Google
  Maps / Rome2Rio / 12Go / OAG / source указать в `## TODO для
  верификации` категории «расписание»).
- Расстояние в км — приблизительное.

**Ясность описания stop-over рейсов.** Рейсы с пересадкой
описываются по одному из трёх форматов **явно**, без двусмысленностей:

1. **Прямой рейс:**
   `Рейс {номер} {откуда-IATA} → {куда-IATA}, {время} (прямой, без пересадок)`

2. **Stop-over без выхода из транзитного аэропорта** (одна tail-number
   или короткая стыковка с тем же бортом):
   `Рейс {номер} {откуда} → {куда} через {транзит-IATA} (тех. остановка
   ~{N} мин в {транзит}, без выхода из аэропорта; багаж транзитом)`

3. **Stop-over с ночёвкой / содержательной пересадкой:**
   `Рейс {номер1} {откуда} → {транзит}, прибытие {время}; ночь в
   {транзит}; следующий день {номер2} {транзит} → {куда}, {время}`

Запреты:
- НЕ писать `{откуда} → {куда} через {X}` без явного пояснения,
  является ли `{X}` технической остановкой или содержательной ночёвкой.
  Без явной семантики пользователь при беглом чтении может прочитать
  `через X` как «маршрут заходит в X как пункт программы» — это
  переинтерпретация формата stop-over.
- НЕ опускать слова «без выхода из аэропорта» / «с ночёвкой» — это
  ключевая информация для пользователя при выборе варианта.

**Arrival/departure day choreography (F-61).** Дни 1 и N — особые,
требуют явной choreography, не «акклиматизация / спокойная прогулка».
Senior travel agent не оставляет первый и последний день без структуры.

**Использовать `international_flight_context` из Stage 4 YAML:**
- `direct_to_entry == false` → транзит ≥ 10ч door-to-door. День 1 = ground
  day с лёгким evening anchor.
- `direct_to_entry == true` + `approx_one_way_hours ≤ 6` → нет существенного
  jet-lag, День 1 может быть полноценным.
- Symmetric для `direct_to_exit` / Day N.

**Шаблон Day 1 (при `direct_to_entry == false`):**

```
### День 1 (DD.MM Wd). Прилёт в {Entry city}

📍 {Home city} → {Entry IATA}; transit ≈ {approx_one_way_hours} ч door-to-door
через {expected_hubs[0]} ({Stage 4 YAML)}. {Время прибытия местного — указать.}
🏨 **{Имя отеля в районе walkable до evening anchor}**, {адрес}, ~₽X-Y/ночь
TODO Booking.

🎯 **Программа:**
- {Время прибытия + 2-3ч} — заселение, душ, лёгкая разминка.
- {Закат / вечер} — **{1 walkable iconic POI в ≤1 км от отеля}**:
  {адрес/часы}, {почему этот POI выбран как evening anchor — visually
  iconic, без heavy кадровой нагрузки}.
- {Время} — **food anchor: {конкретный ресторан}** ({адрес}, {блюдо/
  специализация}, ₽X-Y). Не «найти что-то локальное» — explicit имя.
- Ранний отбой ({время} максимум, не позже 22:00 локального).

💰 ~{диапазон} ₽

⚠️ После {approx_one_way_hours} ч transit — full programme невозможна;
запрет на heavy POI (museum-with-audioguide 3+ часа, sunrise hike,
формальный ужин). Choreography — light evening anchor + ранний сон.
```

**Шаблон Day N (при `direct_to_exit == false`):**

```
### День N (DD.MM Wd). Вылет из {Exit city}

📍 {Exit IATA} → {Home city}; transit ≈ {approx_one_way_hours} ч.
**Вылет {время местного}.** Buffer от check-out до flight: {N} ч
(check-out обычно 11:00; flight {время} → buffer {N}).

🎯 **Программа:**
- Утро — light walkable POI в ≤30 мин от отеля. **НЕ heavy POI** (нет
  возврата за вещами).
- {Время} — check-out, **luggage storage в отеле** (бесплатно при
  бронировании ≥3 ночей) ИЛИ {ближайший камеры хранения адрес}.
- {Время} — **food anchor близ отеля**: {имя ресторана}, ₽X-Y.
- Buffer-окно ({N} ч): light city walk / café / последняя покупка.
  Никаких ticketed activities с risk опоздания на flight.
- {Время} — трансфер в аэропорт (~{N} мин с buffer на пробки). Цена ₽X-Y.

💰 ~{диапазон} ₽

⚠️ **Outbound transit ≈ {approx_one_way_hours} ч** через
{expected_hubs} — рассчитать общую время home из расчёта arrival +
transit. При раннем рейсе (≤10:00 локального) — рассмотри буфер 1 ночь
в exit city (Stage 4 red_flag); проверь сейчас.
```

**Что НЕ писать:**
- «Свободная прогулка по городу» / «акклиматизация» — без конкретного
  evening anchor + food anchor. Это amateur-уровень и нарушение Class G.
- «Найти что-то поесть» / «выбрать ресторан на месте» — explicit имя
  обязательно.
- «По желанию» без альтернативы — давать 1 baseline + 1-2 swap.

**Где LLM находит данные:**

- Время работы / стоимость входа / адреса достопримечательностей —
  активный web search.
- Расписания внутренних рейсов / автобусов / поездов / паромов —
  активный web search; ссылка на конкретное расписание или агрегатор
  (12Go, Skyscanner, Rome2Rio).
- Операторы туров (synergy-пары Stage 3) — активный web search.
- Имена/районы/рейтинги отелей — активный web search (Booking,
  Tripadvisor, Trip.com индексируются Google).
- Цены отелей — **TODO**, ориентир-диапазон по архивным данным
  региона/класса; опц. через Booking/Expedia MCP при доступности.
- Цены ресторанов — **TODO**, ориентир из общих источников по региону.
- Цены такси — **TODO**, ориентир по Grab/Bolt/местным аналогам.

### 6.4 Web search policy и опц. MCP-расширения

**Активный web search** для следующих категорий (выполнять до сборки
маршрута):

1. **Расписания транспорта.** Внутренние рейсы / автобусы / поезда /
   паромы на даты поездки. Цены обычно стабильные диапазоны — указать
   с ссылкой на источник (12Go, Skyscanner, операторские сайты).
2. **Часы работы и стоимость входа достопримечательностей.** Особенно
   тех, что упоминались в Stage 3 как priority pool или в Stage 4 как
   programs of the day.
3. **Конкретные операторы synergy-пар Stage 3.** Если Stage 3 пометил
   пары `commonly_combined_with`, найти конкретного оператора (URL,
   способ бронирования, диапазон цен).
4. **Сезонные ограничения.** Закрытие пещер в дожди, ремонты,
   тайфунные риски, фестивальные даты.
5. **Имена/районы/рейтинги отелей.** По классу размещения из профиля
   (бюджетный / mid-range / премиум) и по району (центр / тихий /
   ближе к достопримечательностям). 1-2 кандидата на каждую ночёвку.
5a. **Пороги самоходного транспорта без прав.** Проверять **по классам**,
   а не по факту наличия прав: велосипед, электровелосипед, электроскутер
   до странового порога (мощность / скорость / объём), бензиновый скутер,
   мотоцикл, машина. «Прав нет» закрывает только те классы, где права
   требуются; электробайк во многих странах легален без прав и меняет
   логистику дня радикально (радиус 15–20 км вместо 3–5 пешком). Если
   профиль содержит класс «электробайк без прав» — искать прокат
   и закладывать в дни, а не писать «аренда не планируется».
5b. **Как в стране платят и где брать наличные.** Три отдельных вопроса:
   (1) можно ли купить местную валюту дома до вылета — для
   не-экзотических валют это снимает весь узел обмена на месте
   и проверяется первым; (2) какие карты группы реально работают
   (профиль → «Платёжная инфраструктура», «оформлена» ≠ «планируем
   оформить»); (3) банкоматы и обменники по маршруту. Не выводить
   «карты не работают» из гражданства — проверять по профилю.
6. **Опц. адреса/специализации ресторанов.** Конкретные адреса и
   блюда — да; цены — нет (TODO).

**НЕ web search** (всегда TODO):

- **Цены отелей.** Динамические, волатильные, систематически
  занижаются LLM на 3-10×. Даже если найден price tag на конкретный
  отель — указывается с пометкой «ориентир, TODO: верифицировать на
  Booking».
- **Цены ресторанов** (кроме общего диапазона по типу заведения).
- **Цены такси** (кроме среднего по городу).
- **Курсы валют** (выносится на чеклист «за 2 недели»).

**Опц. MCP-расширения через Booking/Expedia.**

Если в текущем окружении доступны MCP-коннекторы Booking.com или
Expedia (имена сервисов могут варьироваться — `mcp__claude_ai_Booking_com__*`,
`mcp__claude_ai_Expedia__*` или аналогичные), скилл МОЖЕТ
дополнительно вытащить актуальные диапазоны цен.

**Правила использования MCP:**

- **По умолчанию** — MCP не используется, цены отелей всегда TODO.
- **Активировать MCP-расширение** только если:
  - Пользователь явно попросил («используй Booking», «подключи MCP для
    отелей», «найди реальные цены»);
  - ИЛИ скилл сам видит, что Booking/Expedia MCP активны в среде, и
    разумно их использовать (без явного отказа пользователя).
- **Подстановка MCP-цен в плане:**
  - Указывать с пометкой «**через {Booking|Expedia} MCP, YYYY-MM-DD**».
  - **Не заменяет TODO** — TODO остаётся, потому что (а) пользователь
    финально бронирует сам, (б) цены могут измениться за время до
    поездки.
  - Формат строки: `{имя отеля}, {адрес/район}, рейтинг {N.N} — ~{цена}
    ₽/ночь (через {Booking|Expedia} MCP, {YYYY-MM-DD}). **TODO:
    верифицировать на дату бронирования**`.
- **В YAML фиксировать** `mcp_extensions_used: ["booking"]` (или
  `["booking","expedia"]`), если использовались.

**Если MCP-коннекторы недоступны** — стандартный режим, цены отелей
TODO с диапазоном-ориентиром.

**Лимит web search'ей.** Не делать систематические поиски «на каждый
ресторан». Целевые: ~10-20 поисков на план. Если на конкретный POI
данных нет — TODO с маркером «нужна довыборка на Stage 5 при наличии
интернета». Не выдумывать.

### 6.5 Бюджетная консолидация и TODO discipline

**Расчёт total_budget_rub:**

1. Сложить дневные бюджеты (midpoint диапазонов) по всем дням +
   ночёвки midpoint + внутренний транспорт.
2. Опц. добавить международный перелёт **только если** `home_eq_start
   == false` (международный перелёт — отдельной строкой в `## Шапка`).
3. Сравнить с `budget_target_rub` из YAML Stage 4 → определить
   `budget_status`:
   - `under_target`: total ≤ 0.9 × target
   - `on_target`: 0.9 × target < total < 1.1 × target
   - `over_10_20`: 1.1 × target ≤ total < 1.2 × target
   - `over_20+`: total ≥ 1.2 × target

**TODO discipline:**

Каждая денежная цифра в плане классифицируется на три типа:

1. **Подтверждена web search** — например, цена входа в музей со
   ссылкой на официальный сайт. Идёт как есть без TODO.
2. **Оценочный диапазон** — типовая для региона цена (отель, ресторан,
   такси). Идёт с диапазоном + пометкой «оценочно, TODO:
   верифицировать».
3. **Подтверждена через MCP** (опц.) — через Booking/Expedia. Идёт с
   пометкой «через X MCP, YYYY-MM-DD» + TODO.

**Эвристика для оценочных цен отелей (без web search / MCP).**

При установлении midpoint оценочного диапазона mid-range отеля
**без верификации через web search или MCP** — брать **нижнюю
половину типичных mid-range цен** региона, не середину и не верх.

Обоснование: LLM системно завышает оценочные цены отелей, ставя
midpoint в **верхнюю половину mid-range диапазона** (что де-факто
уже бутик/luxury). Это создаёт ложно высокий `total_budget_rub` и
смещает `budget_status` в сторону `over_*`.

**Правило:**
- Mid-range для региона типично занимает диапазон $X–$Y/ночь
  (на основе общего знания / web search по нескольким источникам).
- Подставляемый в план диапазон-ориентир для отеля **без MCP/web
  search** = `[X, X + (Y-X)/2]`, то есть нижняя половина региона.
- Верх mid-range подставляется только если есть **подтверждающий
  сигнал** (web search конкретного отеля показал реальную цену в
  этом диапазоне; MCP вернул данные; источник цитирует «премиум
  mid-range»).

**Пример:**
Эль-Чальтен типичный mid-range диапазон $90–180/ночь. Без web search
оценочный диапазон отеля = $90–135/ночь (нижняя половина), midpoint
~$112. Не $150–220 (верхняя половина и выше) — это систематическое
завышение.

Это **эвристика, не закон**: если профиль явно указывает «премиум»
или «верх mid-range» (`## Стиль путешествий`) — берётся середина
или верх. Соответственно при `бюджетный` стиле — нижняя треть.

**Категории TODO в финальной секции:**

`## TODO для верификации` имеет три подсекции:

```markdown
### Перед бронированием (за 1-2 месяца до поездки)
- [ ] Booking: {отели} — диапазоны на конкретные даты
- [ ] Расписания: {рейсы/автобусы} — актуальные времена и цены
- [ ] Операторы: {имена} — расписание/наличие/брони
- ...

### За 2 недели до поездки
- [ ] Прогноз погоды / сезонные риски
- [ ] Регистрация на рейсы
- [ ] Финальное подтверждение туров
- ...

### В процессе планирования (опц.)
- [ ] Сравнить альтернативы отелей
- [ ] Курсы валют / payment стратегия
- ...
```

`todo_verification_items` в YAML = общее число TODO во всех трёх
подсекциях.

### 6.6 Сравнение с previous_plan

Если `previous_plan != null` — обязательная секция `## Diff с
предыдущим планом` (5-15 строк summary).

**В surgical mode:**

Структура — таблица или список изменений:

```markdown
## Diff с предыдущим планом

Структура маршрута сохранена. Точечные изменения:

| День | Было (v{N-1}) | Стало (v{N}) | Причина |
|---|---|---|---|
| N | {активность А} | {активность Б} | {обоснование из Stage 3/4 или правок пользователя} |
| ... |
```

**В reconstructive mode (с переиспользованием из previous_plan):**

```markdown
## Diff с предыдущим планом

Структурные изменения:
- {регионы добавлены/убраны}
- {ночи переаллоцированы — что куда}
- {ключевые POI добавлены/убраны}

Что сохранено:
- Payment-инфраструктура (карты, обменники, ATM)
- Логика реагирования на риски по {region X}
- Расписания транспорта по сегментам, где даты совпали
```

**Если `previous_plan == null`** — секция полностью опускается.

### 6.7 Pre-emit checklist — обязательный self-check ДО записи файла

Прогнать каждый пункт ДО финального emit. Любое нарушение — НЕ
сохранять, исправить сначала. 8 классов закрывают типовые failure
modes детализации.

#### Класс A — Stage 4 consistency

- [ ] **Все дни выбранного варианта присутствуют.** Если Stage 4
      вариант имел N ночей — Stage 5 имеет N дней маршрута (плюс опц.
      «День 0 — прилёт» и «День N+1 — вылет», если они в Stage 4 уже
      обозначены).
- [ ] **Правки пользователя применены.** Каждый элемент из
      `**Состав:**` / `**Почему этот выбор:**` блока `## Решение`
      Stage 4 нашёл отражение в маршруте. Summary-строка «Применены
      правки пользователя…» в `## Контекст и ключевые параметры`
      присутствует, если правки были.
- [ ] **Формулировка крайних дней по `home_eq_start`.** Если
      `home_eq_start == true` (старт и конец в home_city) — день 1
      «Старт маршрута в {trip_start_city}», последний день
      «Завершение маршрута в {trip_start_city}». Если `false` —
      «Прилёт в {trip_start_city}», «Вылет из {trip_start_city}».
      Логика наследуется из Stage 4 (`../stage4/stage4-variants.md` §6.3).
- [ ] **Mode объявлен.** В YAML `mode` и в `## Контекст и ключевые
      параметры` явно указан режим (surgical/reconstructive) с
      одной фразой-обоснованием.
- [ ] **Решения Stage 0/3/4 не пересмотрены.** Stage 5 не предлагает
      альтернатив выбранному варианту, не оспаривает выбор пользователя,
      не «оптимизирует» категории POI задним числом.
- [ ] **Stage 0 прочитан если файл существует.** Если
      `trips/{trip_id}/0_scope.md` доступен — он прочитан, и из него
      взяты как **факт**: точные даты поездки (если зафиксированы),
      `home_city`, `trip_start_city`, `home_eq_start`,
      `pre_committed_places`, `trip_wishes`. Молчаливая подстановка
      «представительных дат» при наличии 0_scope.md — нарушение. Если
      файл недоступен (новая поездка без Stage 0) — это явно отмечено
      warning'ом в YAML Stage 5 («0_scope.md недоступен — используются
      представительные даты {диапазон}, сверить с фактическими
      билетами»).

#### Класс B — TODO discipline

- [ ] **Каждая цена отеля → TODO** с указанием района/класса и
      диапазона-ориентира. Без исключений (даже если найдена через
      MCP — TODO остаётся, MCP-цена идёт как дополнение).
- [ ] **Каждая цена ресторана** (кроме общего диапазона по типу) →
      TODO. Конкретные блюда с прайсом без TODO допустимы только при
      явной web search ссылке (например, Michelin Guide,
      официальный сайт).
- [ ] **Цены экскурсий и активностей** — либо подтверждены web
      search (с ссылкой), либо диапазон + TODO.
- [ ] **Цены такси / Grab / Bolt** — диапазон + TODO.
- [ ] **Международный перелёт.** Если `home_eq_start == false` —
      входит в `## Шапка` отдельной строкой (с TODO на верификацию
      на конкретные даты или со ссылкой если уже куплены). Если
      `home_eq_start == true` — НЕ упоминается в плане; маршрут
      стартует в home_city.
- [ ] **`todo_verification_items` в YAML совпадает** с числом TODO в
      секции `## TODO для верификации`.
      → `check_format.py` проверяет автоматически (`todo_count`); если
      разошлось — привести поле к факту, не считать вручную.
- [ ] **Согласованность дневного и сводного бюджета.** Сумма midpoint
      дневных диапазонов из `🎯 💰` блоков маршрута сопоставима с
      подытогом из `## Сводные таблицы → Бюджет` (расхождение ≤15%).
      Если дневные `💰` показывают только часть статей (например,
      «активности + еда + входы дня» без отеля и межгородского
      транспорта) — это **явно оговорено одной строкой** в начале
      `## Маршрут по дням`: «`💰` в днях — только {что включено};
      полная разбивка — в `## Сводные таблицы`». Молчаливое расхождение
      в 2× (дневные ~80k vs сводная ~160k) — нарушение, выглядит как
      внутренняя ошибка бюджета.
- [ ] **Mid-range pricing heuristic (см. §6.5).** Если midpoint
      оценочного диапазона отеля установлен **без web search и без
      MCP** — он лежит в **нижней половине типичного mid-range
      диапазона** региона, не в середине и не в верху. Систематическое
      завышение (midpoint в верхней половине без подтверждающего
      сигнала) — нарушение. Уровень mid-range — из `## Стиль
      путешествий` профиля; «бюджетный» → нижняя треть, «mid-range» →
      нижняя половина, «премиум» → середина-верх.

#### Класс C — данные и факты

- [ ] **Часы работы / стоимость входа** — каждое утверждение либо со
      ссылкой на web search источник (URL в скобках или в `## TODO`
      категории «расписание»), либо помечено TODO для верификации.
- [ ] **Операторы synergy-пар Stage 3.** Каждая пара
      `commonly_combined_with` из Stage 3 либо реализована конкретным
      оператором (имя + способ бронирования из web search), либо
      помечена TODO.
- [ ] **Расписания транспорта** — конкретные времена и операторы со
      ссылкой на источник (12Go, Skyscanner, операторский сайт), либо
      TODO.
- [ ] **MCP-цены — с датой запроса.** Если использовался Booking или
      Expedia MCP, каждая MCP-цена сопровождается «через {Booking|
      Expedia} MCP, YYYY-MM-DD». В YAML `mcp_extensions_used`
      указано.
- [ ] **Если MCP не использовался** — цены отелей всегда TODO без
      исключений.
- [ ] **Рейтинг для каждого отеля, особенно для основного кандидата.**
      В блоке `🏨` каждого отеля (кроме ночей в поезде/автобусе) —
      имя + район + **рейтинг** (по Booking / Tripadvisor через web
      search, формат «X.X/5» или «X.X/10» в зависимости от источника)
      + диапазон-ориентир цены + TODO. Если web search не вернул
      рейтинг для конкретного отеля — явная пометка «рейтинг не найден
      на Booking, проверить вручную» в той же строке (не пропуск).

      **Особое правило для основного кандидата.** Web search для
      рейтингов делается **сначала для основного именованного отеля
      каждой ночёвки**, потом для альтернатив. Лазейка «нашёл рейтинг
      для альтернатив (потому что они короче и проще ищутся), а
      основной — TODO» — нарушение. Если основной кандидат имеет
      `TODO: уточнить рейтинг`, а альтернатива в той же строке имеет
      `рейтинг 9.4/10 Expedia` — это значит, что web search был, но
      непоследовательно применён → перепрогнать поиск для основного.

      Молчаливое отсутствие рейтинга у части отелей — нарушение
      (выдаёт, что web search применялся непоследовательно).
- [ ] **Time-of-day sanity для активностей.** Для каждой time-sensitive
      активности (рассвет/закат/раннее утро/работа рынка в узкое окно
      / прилив-отлив) — старт скорректирован под время в пути и
      достижимое окно. Пример нарушения: «рынок активен на рассвете»
      + «выезд из города X в ~05:30» + «3 ч в пути» = на рынке к ~08:30
      когда он уже сворачивается → невыполнимо без ночёвки накануне.
      Если активность недоступна по времени из выбранной локации —
      либо ночёвка в близкой точке, либо замена активности, либо явная
      пометка «доступна только утренние часы — придётся выезжать в
      03:00, оценить осознанно».
- [ ] **TODO операторов — с платформой поиска.** Каждая строка
      `TODO: выбрать оператора {активности}` дополнена **конкретной
      платформой/сайтом** для поиска: Klook / GetYourGuide / Viator /
      Civitatis / vexere.com / 12go.asia / sapaochau.org /
      bookaway.com / локальная агрегация. Голое `TODO: выбрать
      оператора` без указания, куда смотреть, — нарушение.

#### Класс D — логистика

- [ ] **Каждый переезд имеет:** транспорт (тип/оператор) + время в пути
      + способ бронирования (ссылка или платформа) + диапазон стоимости.
- [ ] **Узкие звенья из Stage 4** (хрупкие транзиты, двойные пересадки)
      сохраняют swap-стратегию в маршруте — конкретный план Б при
      отмене/опоздании.
- [ ] **Happy path vs контингенси разделены (#8, §6.3.1).** Дневной
      `⚠️`-блок — короткий указатель (1 фраза: что под угрозой + куда
      смотреть), полная развёртка swap'ов/контингенси — в `## План
      реагирования на риски`. Дерево «если…то…если…» внутри дня —
      нарушение (хоронит основной путь в обороне).
- [ ] **Synergy-пары Stage 3** оформлены как «комбо у оператора X»
      (если активны в варианте), не как две независимые активности.
- [ ] **План реагирования на риски** содержит сценарий + **числовую
      вероятность в процентах** (`~XX%` или диапазон `~XX–YY%`) +
      действие для каждого из основных рисков, наследованных из
      Stage 4 `## Ключевые риски` + новых, выявленных на детализации.
      Голые категории «low/medium/high» без числового якоря —
      нарушение (читателю нужно решать «брать ли страховку отмены» по
      числу, не по слову).
- [ ] **Понижения вероятностей — в пределах горизонта прогноза (R1).**
      Каждое число, уменьшенное против предыдущей итерации, несёт
      ссылку на прогноз и его горизонт. Дни за горизонтом понижать
      нельзя — там норма сезона.
- [ ] **Зависимые риски помечены общим фактором, есть дождевой блок
      (R2).** На каждую базу — минимум один блок, не зависящий от
      доминирующего фактора, с маркером `[[дождевой блок]]`, и он
      наполняет полный день, а не час.
- [ ] **Митигации честные (R3).** Ни одно понижение не опирается на
      митигацию, которая не убирает причину риска. Ограничения «нужна
      предварительная бронь» проверены на реальность.
- [ ] **Плечи без объезда имеют путь отхода (R4)**, в обе стороны.
- [ ] **Скамейка запасных (R5)** присутствует, если у пользователя есть
      исключённые точки в ≤30 мин от баз маршрута.
- [ ] **Риск стыковки посчитан для обоих международных плеч (R6).**

#### Класс E — формат и YAML

**Auto-check через `scripts/check_format.py`.** Прогон:

```bash
python3 skills/travel-planning/scripts/check_format.py --stage 5 < 5_final_plan.md
```

Exit 0 = OK; exit 1 = список нарушений в stderr. Класс проблем
encoding bash-grep решён — script на pure Python.

- [ ] **Долларовые цены.** Все упоминания цен в долларах — `\$80–100`
      (escape) ИЛИ `USD 80–100` ИЛИ в backtick'ах `` `$80–100` ``.
      Чистый `$80` без escape запрещён (MathJax-ломка визуальных
      просмотрщиков).
      → `check_format.py` проверяет (`dollar_escape`).
- [ ] **YAML-разделители.** Frontmatter строго ровно `---` (три
      дефиса) сверху и снизу. Никакого `-----`.
      → `check_format.py` проверяет (`yaml_delimiters`).
- [ ] **Имя файла.** Строго `5_final_plan.md` через подчёркивания,
      без пробелов. Проверка вручную при save.
- [ ] **«Сохранить как» НЕ в теле файла** — отдельным сообщением в
      чат после файла (см. `../storage-and-naming.md` §9).
      → `check_format.py` проверяет (`no_save_as_body`).
- [ ] **Никаких «опущено for brevity»** в маршруте. Если не
      помещается — split на `5_final_plan_part_b.md` (§9.10).
      → `check_format.py` проверяет (`no_for_brevity`).
- [ ] **Счётчик TODO = факту.** `todo_verification_items` в YAML равен
      числу чекбоксов в `## TODO для верификации` (ведётся вручную и
      легко отстаёт — частый дефект).
      → `check_format.py` проверяет (`todo_count`).
- [ ] **Строка `🏨` опущена при повторе отеля.** В днях с продолжением
      ночёвки в том же отеле строка `🏨` отсутствует полностью —
      никаких «🏨 Та же гостиница» / «🏨 Та же (Ханой)». Полное
      описание отеля — только в день заселения; опц. блок-маркер «—
      ночи N, N+1, N+2» при заселении.
      Проверка вручную при review дня.

#### Класс F — Diff, TODO summary, чеклист

- [ ] **`## Diff с предыдущим планом`** заполнен, если есть
      предыдущая итерация `5_final_plan_v{N-1}.md` (или legacy
      `previous_plan`). Опущен для первой итерации.
- [ ] **`## TODO для верификации`** содержит все TODO из тела файла,
      категоризовано (before-booking / 2-weeks-before / in-trip).
- [ ] **`todo_verification_items` в YAML** = общее число TODO в
      секции `## TODO для верификации` (точное число, не
      приблизительное).
- [ ] **Чеклист «за 2 недели» — со ссылками на источники проверки.**
      Каждый пункт чеклиста снабжён URL или явной платформой проверки
      (JTWC / Windy / cbr.ru / met-service страны / сайт авиакомпании
      / Booking / agribook ...). Голое «проверить прогноз погоды»
      без направления — нарушение.

#### Класс G — Day-fill discipline (v2)

- [ ] **Каждый день имеет POI на morning slot AND afternoon slot.**
      Morning = с утра до обеда (~12:00). Afternoon = после обеда
      (~14:00 — закат). Минимум 1 POI / активность в каждом slot'е.
- [ ] **Пустой slot («полудня свободно», «свободное время») — только
      с явной причиной.** Допустимые причины (должны быть явно
      указаны в описании дня):
      - «день отдыха после активного {вчерашнего региона}»;
      - «компенсация джет-лага» (только в первые 1-2 дня дальних
        перелётов; **подтверждено** через `international_flight_context.approx_one_way_hours` ≥ 10ч в Stage 4 YAML — F-49);
      - «буфер при переезде» (если переезд занимает половину дня);
      - «штормовое окно / погодный буфер» (если регион имеет известный
        weather risk).
      Все остальные «свободно» без причины = нарушение spec, перестроить
      день.
- [ ] **Day 1 / Day N choreography при отсутствии direct flights.** Если
      Stage 4 YAML `international_flight_context.direct_to_entry == false`
      (трансферный перелёт от home_city), Day 1 **обязан** быть лёгким:
      light evening anchor (1 walkable iconic POI в радиусе ≤ 1км от
      отеля) + food anchor (конкретный ресторан, не «найти что-то») +
      ранний отбой. Это не «свободно» — это **explicit choreography
      после 14-18ч transit**. Аналогично если `direct_to_exit == false`,
      Day N имеет **buffer-окно ≥ 4ч** от check-out до отлёта; если рейс
      утренний — light morning anchor walkable.
- [ ] **Не более одного «отдыхового» полудня подряд.** Два пустых
      полудня подряд (без переезда или объективной причины) — нарушение.
- [ ] **Stop-over рейсы описаны явно** (один из трёх форматов из §6.3
      подсекции «Ясность описания stop-over рейсов»). Не «через X»
      без указания типа (тех. остановка / ночёвка / содержательная
      пересадка).

#### Класс H — Profile-fit аудит (финальный проход)

**Назначение.** Перед emit пройти собранный план целиком против профиля
группы — отдельным проходом «подходит ли это им», не только «корректен ли
формат». Это бьёт в калибровку: план может быть формально валиден, но не
лечь на темп / возраст / интересы группы. Читается профиль (`## Темп`,
`## Частота смены локаций`, `## Физическая форма`, `## Ядро интересов`,
`группа_архетип`).

- [ ] **Темп.** Плотность дней не противоречит `## Темп`. Профиль
      «медленный / умеренный» + архетип старшего возраста → не пачка
      перегруженных дней подряд (3+ якорных POI + длинный переезд в одном
      дне). Несоответствие — разрядить день или явный warning.
- [ ] **Ранние подъёмы.** Сосчитать дни с предрассветным / очень ранним
      подъёмом (рассветные точки, ранние трансферы). Их число умеренно для
      темпа/возраста; подряд два «рассветных» дня для медленного/старшего
      профиля — флаг (`warnings`) или перестановка.
- [ ] **Частота смены локаций.** Фактические ночи-на-базу не противоречат
      `## Частота смены локаций` (профиль «3–5 ночей» → не цепочка
      one-night-stand'ов без причины).
- [ ] **Фото-профиль.** Если в `## Ядро интересов` есть фотография — золотой
      час / рассвет-закат у ключевых видовых точек учтён (не «приехали в
      полдень к точке, которая работает на закате»).
- [ ] **Интересы и анти-интересы.** Якорные POI тянутся к `## Ядро
      интересов`; регионы/POI из «не интересно» не просочились (пересекается
      с Классом P, но здесь — на уровне тематики, не только явных
      комментариев).

Нарушение → НЕ молчать: либо поправить план, либо строка в `warnings:`
с сутью несоответствия. Аудит **диагностический** (не блокирует emit сам по
себе, кроме явных нарушений Класса P), но молчаливо пропускать mismatch
нельзя.

#### Класс P — User comment enforcement (F-54)

**Назначение.** Stage 3 даёт пользователю поле `Комментарий пользователя:`
под каждым POI. Stage 4 priority pool учитывает MUST-комментарии и
исключает отрицательные. Stage 5 при детализации дня обязан **не нарушить
пользовательские сигналы** — особенно жёсткие негативы.

**Это критическая проверка.** Включение POI с негативным комментарием = bug,
не оптимизация. Молчаливое игнорирование conditional-комментариев = неуважение
к клиенту. Любое нарушение = НЕ сохранять.

**Алгоритм:**

1. Прочитать `3_poi_pool.md` (или legacy `3_poi_aggregation.md`) и собрать таблицу
   `{POI_name → user_comment_text}` для всех POI с непустым полем
   «Комментарий пользователя».
   Дополнительно собрать пользовательские сигналы уровнем выше:
   - `**Комментарий к региону:**` (шапка региона Stage 3) — негатив по
     названному месту/активности («не хочу X») классифицируется как
     HARD_NEGATIVE для X, пожелание («ещё храм Y») — как MUST для Y, если Y
     в маршруте региона уместен (иначе — строка в Day note / honest-части,
     почему не вошло);
   - комментарий к выбранному варианту и общий из `## Комментарии к
     вариантам` Stage 4 — по той же таблице классов.

2. Для каждого POI, появляющегося в `Маршрут по дням` Stage 5, определить
   класс комментария:

   | Класс | Признаки в тексте | Действие Stage 5 |
   |---|---|---|
   | **HARD_NEGATIVE** | «не интересно», «не хочу», «скип», «нет», «скучно», «пропусти», «не нужно», «не вижу смысла» | **БЛОКИРОВАТЬ включение.** Если POI в маршруте — удалить. Если был запланирован в кластере — кластер можно оставить без этого POI. |
   | **CONDITIONAL** | «если ... то можно», «если есть Х», «можно, но», «надо проверить», «потенциально интересно», «зависит от» | **РАЗРЕШИТЬ только с явным обоснованием в описании дня:** «{POI} включён потому что: {условие из комментария выполнено по такой-то причине}». Без обоснования — БЛОКИРОВАТЬ. |
   | **MUST** | «надо», «обязательно», «must», «да», «хочу», «ради этого» | **ПРИОРИТИЗИРОВАТЬ.** Если POI выпал из дня по соображениям места/времени — явный warning в Day note. |
   | **NEUTRAL** | произвольный freeform без чёткого сигнала, описательный | Без специального действия. |
   | **EMPTY** | поле пустое | Без специального действия. |

3. **Самые опасные** — HARD_NEGATIVE. Любое включение POI с
   HARD_NEGATIVE-комментарием в `Маршрут по дням` = критическая ошибка
   генерации. НЕ сохранять, удалить POI, перепрогнать день.

3a. **HARD_NEGATIVE ≠ стереть из плана.** Блокировка касается `Маршрут по
   дням`: отдельного времени на такую точку не выделяем, в день она не
   попадает. Но если точка лежит **в ≤30 мин от одной из баз маршрута**,
   она идёт в скамейку запасных (R5, блок после риск-таблицы) с цитатой
   пользователя и пометкой, когда годится. Причина — эмпирическая:
   исключения формата «не интересно / слишком попсовое» рядом с базой
   пользователь нарушает сам, когда день срывается по погоде, и тогда
   он выбирает вслепую, без плана. Дальние HARD_NEGATIVE (отдельный
   выезд, полдня дороги) в скамейку **не** идут.
   Сверяться с профилем: секция «Явные исключения» может явно делить
   вето («никогда») и мягкий тир («не как основа, но эпизодически
   допустимо») — мягкий тир скамейку разрешает, вето не разрешает
   никогда, включая скамейку.

4. **CONDITIONAL — особое правило.** Если включаешь — обоснование должно
   ссылаться на **конкретное** условие из комментария. Пример:
   - Комментарий: «Кымчжонсансон ворота скучны, но если виды красивые, то можно».
   - Включение OK: «День 10 — крепость Кымчжонсансон: тропа от Помоса даёт
     панораму Пусана и реки Нактонган с Северных ворот (HIGH-автор Алара2009),
     условие комментария «виды красивые» выполнено».
   - Включение НЕ OK: «День 10 — крепость Кымчжонсансон» без упоминания
     причины почему condition выполнен.

5. **Логирование в YAML.** В `warnings:` блок Stage 5 эмитит строку для
   каждого включённого CONDITIONAL и каждого исключённого HARD_NEGATIVE:
   - `"User comment enforcement: {POI} (HARD_NEGATIVE «{краткая цитата}») — исключён из плана"`
   - `"User comment enforcement: {POI} (CONDITIONAL «{краткая цитата}») — включён, основание: {где обоснование в плане}"`

**Что НЕ делать:**
- Не пытаться интерпретировать ambiguous как permission («не интересно, но
  если совмещается — можно» → это HARD_NEGATIVE + CONDITIONAL пограничный
  случай; в сомнительных кейсах ставить HARD_NEGATIVE и исключать).
- Не молчать о решении. Каждое HARD_NEGATIVE-исключение и каждое
  CONDITIONAL-включение — строка в `warnings`.

Нарушение Класса P (включён HARD_NEGATIVE POI / включён CONDITIONAL без
обоснования) = НЕ сохранять, исправить.

Нарушение любого пункта = НЕ сохранять, исправить и перепрогнать.

## 7. Правила работы

### Граница LLM vs скрипт

Stage 5 — **pure LLM, без скрипта** (как Stage 4). Детализация дня —
семантическая работа, скрипт ничего не добавляет.

**LLM делает:**
- Чтение Stage 4, профиля, опц. previous_plan, опц. Stage 0/3 для
  контекста.
- Парсинг `## Решение` Stage 4 (семантическая интерпретация правок).
- Mode detection (surgical/reconstructive).
- Web search для расписаний / операторов / отелей / часов работы /
  стоимости входа.
- Опц. MCP-запросы для цен отелей.
- Бюджетная консолидация (сумма дневных бюджетов).
- Сборка markdown по §8 (9 секций).
- Pre-emit checklist (8 классов).

### Web search guidelines

- **Целевые поиски (~10-20 на план):** расписания транспорта; часы
  работы и стоимость входа топ-достопримечательностей; операторы
  synergy-пар; имена/районы/рейтинги отелей; сезонные ограничения.
- **НЕ массовые поиски** «на каждый ресторан / на каждую активность».
  Если для конкретного POI данных нет — TODO.
- **Указывать источник** — URL в скобках или в `## TODO для
  верификации` категории «расписание/часы».

### MCP guidelines

См. §6.4. По умолчанию не используется; opt-in для цен отелей.

### Стиль

- **Плотный, без воды, без клише.** «{имя заведения} ({отличительный
  признак — Michelin Bib / адрес / специализация}, {ключевое блюдо
  + диапазон цены}, {часы работы})» — а не «прекрасный ресторан с
  великолепной кухней».
- **Сенсорная проза в описаниях мест** — конкретные детали (материалы,
  запахи, текстуры, время дня для света), не туристические эпитеты.
- **Сенсорная плотность для key POI.** Для **key POI** — главных точек
  региона с архитектурным / историческим / природным значением —
  2–4 предложения культурного контекста (год постройки, материал,
  эпоха, чем уникально, как воспринимается на месте), не только адрес
  + часы + цена. Для проходных POI (вечерняя прогулка, кофейня,
  закатная точка) — короткое перечисление достаточно.

  **Граница «key vs проходной»** определяется приоритетом из Stage 4
  priority pool:
  - **MUST** (положительный user_comment) → плотное описание.
  - **HIGH** (STRONG CONFIRMED / HIDDEN GEM из Stage 3 без negative
    comment) → плотное описание.
  - **MEDIUM** (WEAK CONFIRMED) → среднее: 1–2 предложения контекста.
  - Проходные (LOW SIGNAL без user_comment, заполнение дня по общему
    знанию) → короткое перечисление, без культурной развёртки.

  Цель — не «энциклопедичность» (это работа гида), а **достаточно
  контекста, чтобы пользователь понимал, почему это место в плане**.
  Без культурного веса описаний key POI план читается как сухой
  каталог, теряется обоснование «зачем именно это место выбрано
  Stage 3».

- **Иконки `📍 🏨 🎯 💰 ⚠️`** — для быстрого визуального сканирования
  каждого дня.
- **Никаких эмодзи в заголовках** (исключение — `⚠️` для inline
  warnings и `✅ ❌` в опц. блоках «кому подходит / кому нет», если
  переиспользуется из Stage 4).
- **Часы и цены — конкретные числа**, диапазон при невозможности
  точного.

## План реагирования на риски

| Сценарий | Вероятность | Что делать |
|---|---|---|
| {риск 1} | **~XX%** или диапазон **~XX–YY%** | {конкретное действие/swap} |

**Вероятность — в процентах**, не в категориях «low/medium/high».
Числовая оценка нужна, чтобы пользователь мог осмысленно принимать
решения (брать ли страховку отмены, закладывать ли дополнительный
буфер, докупать ли запасной билет). Источники оценки: статистика
тайфунов/осадков для сезона; среднее время задержек оператора;
эмпирические данные DR-отчётов Stage 1. Если численная оценка
невозможна (нет статистики, разовый редкий риск) — допустимо
качественное «низкая (<10%)» / «средняя (~20–40%)» / «высокая (>50%)»
с явной нижней или верхней границей. Голые «low/medium/high» —
нарушение Class D.
| ... |

**R1. Понижать вероятность — только внутри горизонта цитируемого
прогноза.** Свежий бюллетень («осадки на 20–40% ниже нормы») покрывает
конкретное окно дат. Для дней за этим окном действует климатологическая
норма сезона, и понижать их вероятность нельзя — бюллетень про них
ничего не говорит. Рядом с каждым изменённым числом указывать горизонт:
`~20% (было 30%; бюллетень NCHMF до 10.09 — дни 1–6)`. Для дней вне
горизонта — `норма сезона, прогноза на эти даты нет`.

**R2. Зависимые риски не складываются как независимые.** Если несколько
строк таблицы зависят от одного фактора (один погодный режим, одна
дорога, один оператор) — это **одна ставка**, и «перетасуем блоки между
собой» не является хеджем: плохой режим выносит все блоки сразу.
Правило: в таблице такие строки помечаются общим фактором
(`общий фактор: погодный режим 10–15.09`), а на каждую базу должен
приходиться **минимум один блок, не зависящий от этого фактора**, и
он помечается явно — `[[дождевой блок]]`. Блок-затычка на час (музей
в одну витрину, вечерняя баня) дождевым днём не считается: дождевой
блок обязан наполнять **полный день**, иначе день будет
импровизироваться на месте.

**R3. Митигация, которая не снимает риск, не даёт понижать
вероятность.** «Гид поведёт по плоскому» снижает нагрузку, но не
вероятность поскользнуться на мокром грунте; «возьмём такси» не
разгружает перевал. Понижение допустимо только если митигация убирает
саму причину (перенос на другой день, крытая альтернатива, ранний
выезд из окна пробок). Иначе вероятность остаётся, а митигация
описывает, как с последствиями жить. Отдельно проверять, **настоящее
ли ограничение по брони**: «трек требует предварительного согласования
с оператором» часто оказывается фантомом (гид нанимается в отеле
накануне) — фантомное ограничение зря сужает свободу манёвра, реальное
идёт в чеклист.

**R4. Путь отхода для плеч по единственной дороге.** Для переезда,
у которого нет объезда (горное шоссе, паром, единственный рейс дня),
буфера недостаточно: буфер спасает от задержки, но не от закрытой
дороги. Такая строка обязана содержать **направление отхода** — куда
вернуться, откуда уехать иначе, что делать с ночёвкой. Проверять
обе стороны плеча: отход «обратно в точку старта» и отход «вперёд, в
точку назначения» — это разные сценарии с разной ценой.

**R5. Скамейка запасных — внутри этой секции.** Точки, исключённые
пользователем как «не интересно / слишком попсовое», но лежащие
в ≤30 мин от базы, **не выбрасываются из плана**: они идут отдельным
блоком после таблицы — что это, сколько до неё, почему исключено, когда
годится. Исключение остаётся в силе (отдельный день на неё не тратим),
но при сорванном дне у пользователя должен быть список, а не пустота.
Дальние исключения (полдня дороги, отдельный выезд) в скамейку не
идут — они держатся сами. Формат:

```markdown
**Скамейка запасных (если день сорвался):**

| Точка | От базы | Почему не в плане | Когда годится |
|---|---|---|---|
| {имя} | {время в пути} | исключено: «{цитата пользователя}» | {дождь / жара / нет сил} |
```

**R6. Симметрия плеч.** Риск задержки и срыва стыковки считается для
**обоих** международных плеч, не только для обратного. Туда и обратно —
разные рейсы, разные аэропорты пересадки и разная цена опоздания.

**Запасные деньги:** ~N USD наличными отдельно для медицины/экстренных
расходов.

**Контакты:** посольство РФ в стране, страховая, ключевые операторы.

## 9. Граничные случаи

### 9.1 `## Решение` Stage 4 не заполнен

Gate (§4). Отказать ОДНОЙ строкой: «Stage 5 требует выбранный вариант.
В `4_variants.md` блок `## Решение` пуст или поле `**Выбран вариант:**`
отсутствует. Заполни блок и сохрани, потом перезапусти». Stop.

### 9.2 `## Решение`: вариант указан, но не существует в Stage 4

Например, `**Выбран вариант:** D`, но Stage 4 содержит только A/B/C.
Отказать: «Указан вариант `{X}`, но Stage 4 содержит только
{A, B, C}. Проверь блок `## Решение` и поправь». Stop.

### 9.3 `## Решение`: кастомный вариант без описания

`**Выбран вариант:** кастомный`, но `**Состав:**` пуст. Отказать:
«Выбран кастомный вариант, но блок `**Состав:**` пуст. Опиши состав
структурно (какие регионы, сколько ночей, что включать) и перезапусти».
Stop.

### 9.4 Правка пользователя конфликтует со структурой варианта

Например, выбран вариант с регионом {R} = 2 ночи без резерва, правка
пользователя — «добавить день в {R} на {активность}». Структурно
требует увеличения ночей.

**Opt-in clarification (как §9.12 Stage 2):**

Один batch с тремя вариантами:

```
В блоке `## Решение` Stage 4 указана правка «добавить день в {регион}»,
но в варианте {X} на этот регион выделено {N} ночей без резерва. Чтобы
добавить день, нужно перераспределить ночи. Варианты:

1. **Перераспределить ночи.** Откуда взять день (укажи регион)?
   Например, «убрать ночь из {другой регион в маршруте}» / «убрать
   день из {другой регион}».
2. **Реализовать урезанно без увеличения ночей.** Например, вписать
   {активность} как утреннюю активность в существующий день {регион}
   (до основной программы дня).
3. **Отказаться от правки.** Реализовать вариант {X} как есть, без
   добавления {активность}.

Стоп.
```

Дождаться ответа Turn 3. После ответа — продолжить с шага 10. В YAML
установить `clarification_used: true`.

### 9.5 Surgical mode: previous_plan существует, но даты изменились

Например, поездка перенесена с марта на октябрь. Структура регионов
сохранилась — формально surgical. Но расписания транспорта, отели и
цены могут измениться.

Действия:
- Mode = surgical.
- В `## Diff` явно отметить «Даты изменились с {prev_dates} на
  {new_dates}; расписания и цены пересчитаны».
- Расписания и операторы — заново через web search.
- Отели — заново (доступность и цены могут измениться).
- Payment-инфраструктура, логика реагирования на риски — сохранить.

### 9.6 Profile drift

Профиль обновлён после создания Stage 4 (`updated` профиля > `created`
Stage 4). Одной строкой предупредить в `## Контекст и ключевые
параметры`: «Профиль обновлён {date}, Stage 4 создан {date}; план
строится по текущему профилю, базовые решения Stage 4 — по старому.
При существенных изменениях — перезапусти Stage 4 и Stage 5».

Не блокировать.

### 9.7 Профиль без `## Платёжная инфраструктура`

Не блокирующее. В `## Критические подготовительные пункты` подсекция
«Деньги» помечается TODO с явной строкой: «`## Платёжная инфраструктура`
в профиле не заполнена — здесь общие рекомендации, верифицировать на
актуальность платёжных карт перед поездкой». В YAML добавить
`incomplete_sections: ["payment_infrastructure"]` warning.

### 9.8 Размер выборки и нагрузка на модель

Большая поездка (≥18 ночей, ≥5 регионов) с активным web search'ем
может потребовать поднять модель.

- **Sonnet+thinking** обычно справляется на surgical (детализация по
  существующему скелету).
- **Opus+thinking** рекомендован для reconstructive с >15 ночами +
  множеством регионов.

Если выход на Sonnet начинает деградировать (пропуски часов работы,
обрезанные swap-стратегии, потерянные категории TODO) — рекомендовать
пользователю открыть новый чат на Opus.

### 9.9 Web search не вернул данные по конкретной активности

Например, для уникального оператора synergy-пары Stage 3 в малом
регионе — web search ничего не нашёл.

Действия:
- В маршруте день: «{activity}, оператор — **TODO: найти оператора на
  Stage 5 при наличии интернета** ({пометка из Stage 3 о synergy})».
- В `## TODO для верификации` категории «before booking» добавить
  явную строку.
- Не выдумывать имя оператора.

### 9.10 Большой выход не помещается в один ответ

Если 18+ ночей × детализация не вмещается:

- **Split на два файла:**
  - `5_final_plan.md` — YAML + контекст + шапка + подготовительные +
    маршрут дни 1–N/2 + сводные таблицы + план реагирования на риски +
    чеклист + diff + TODO.
  - `5_final_plan_part_b.md` — YAML (с `details_file` ссылкой) +
    маршрут дни N/2+1–N + остальное.

- В YAML основного файла: `details_file: 5_final_plan_part_b.md`.

- «Опущено for brevity» **запрещено** (§10).

### 9.11 MCP-коннекторы отвалились в середине сессии

Например, начали с Booking MCP, к 5-му отелю rate-limit или
timeout.

- Остальные отели → стандартный TODO (без MCP-цен).
- В YAML `mcp_extensions_used` указать использованные коннекторы.
- В Warnings — строка: «Booking MCP частично использовался (отели 1-4),
  остальные цены требуют ручной верификации».

### 9.12 trip_id со смешанной системой письма

См. `../storage-and-naming.md` §10.8. Одной строкой предупредить,
добавить `trip_id_warning: mixed_script` в YAML, продолжить.

## 10. Что НЕ делать

- НЕ пересматривать решения Stage 0 (scope), Stage 3 (POI categorization),
  Stage 4 (выбор варианта). Stage 5 — детализация, не ревизия.
- НЕ предлагать альтернативы выбранному варианту. Если правки
  пользователя противоречат структуре — opt-in clarification (§9.4),
  не альтернативный план.
- НЕ выкидывать payment-инфраструктуру и логику реагирования на риски из
  previous_plan в surgical / reconstructive с переиспользованием. Они
  остаются как фундамент.
- НЕ выдумывать цены отелей. Всегда TODO с диапазоном-ориентиром.
  Даже если MCP вернул цену — это диапазон + дата запроса, не факт.
- НЕ выдумывать имена ресторанов / операторов / отелей. Если web
  search не нашёл — TODO с указанием, что искать.
- НЕ угадывать неоднозначные правки пользователя — opt-in clarification
  (§9.4), один batch с 3 вариантами, не silent guess.
- НЕ использовать чистый `$NN` для долларовых цен (MathJax-ломка
  визуальных просмотрщиков). Только `\$NN` / `USD NN` / backtick.
- НЕ изобретать имя файла. Строго `5_final_plan.md`.
- НЕ использовать `-----` (пять дефисов) или иное число — YAML
  frontmatter строго `---` (три дефиса).
- НЕ запускать Stage 5 без заполненного `## Решение` Stage 4 — gate
  отказывает (§4).
- НЕ продолжать на Haiku (model self-check, шаг 0).
- НЕ реконструировать данные Stage 4 из сниппетов и превью —
  только полный файл (приложение / Synology,
  см. `../storage-and-naming.md` §8.0).
- НЕ опускать дни «for brevity». Все N ночей — целиком; при нехватке
  места — split (§9.10).
- НЕ маркировать правки пользователя в днях маршрута («**(правка
  пользователя)**» или подобное). Правки естественно встраиваются;
  ОДНА summary-строка в `## Контекст и ключевые параметры` — всё.
- НЕ хранить текст правок в YAML (отдельным полем
  `custom_modifications` или подобным). Информация о правках уже в
  `## Решение` Stage 4 и в самом теле плана.
- НЕ упоминать международный перелёт в плане, если `home_eq_start ==
  true`. Маршрут стартует в home_city.
- НЕ подмешивать стоимость международного перелёта в `total_budget_rub`,
  если `home_eq_start == true`. Если `false` — отдельной строкой в
  `## Шапка` с TODO.
- НЕ делать систематический web search «на каждый ресторан / каждую
  активность». Целевые ~10-20 поисков; остальное — TODO.
- НЕ использовать MCP-коннекторы без явной policy. По умолчанию —
  стандартный TODO режим; opt-in через явный запрос пользователя или
  активность коннекторов в среде (§6.4).
- НЕ задавать дополнительных уточняющих вопросов в Turn 2, если все
  gate-проверки прошли и правки не конфликтуют со структурой. Один
  batch уточнений только в случае §9.4 (конфликт правки).
- НЕ писать «Сохранить как» в тело файла (§8).
- НЕ использовать sandbox-пути (`/home/claude/`, `/tmp/`) для
  файла-результата (см. `../storage-and-naming.md` §9).
- НЕ пропускать Pre-emit checklist (§6.7). Прогон обязателен ДО
  сохранения файла.

## 11. Следующий шаг

После того как пользователь сохранил `5_final_plan.md`:

- Опционально активируется **Export mode** (`/travel-planning` →
  «экспортируй план для X», «pdf для родителей», «презентация для
  партнёра»).
- Export адаптирует тон и уровень детализации финального плана под
  одну из 4 аудиторий (Partner / Family / Friends / Self) и
  делегирует генерацию файла на core-скиллы `pdf` / `docx` / `pptx`
  / `xlsx`.

Скилл не запускает Export автоматически — пользователь решает, нужен
ли экспорт.

Если по результату Stage 5 потребовались правки (нашлись логистические
проблемы при детализации, выяснилось, что отель/оператор недоступен,
бюджет вышел за неприемлемые пределы) — возможные пути:

- **Локальные правки** — пересохранить план руками, не перезапуская
  стадии.
- **Перезапуск Stage 5** — изменить `## Решение` Stage 4 (новые
  правки), перезапустить.
- **Возврат на Stage 4** — пересмотреть выбор варианта.
- **Возврат на Stage 0** — пересмотреть scope (например, сократить
  длительность или убрать регион).

Скилл не запускает возврат на предыдущие стадии автоматически —
пользователь решает.
