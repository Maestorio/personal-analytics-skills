# stage5-polish-prompt.md

Инструкция для модели в **export-mode Stage 5**. Применяется ДО рендера
PDF: модель читает оригинальный `5_final_plan_v{N}.md`, выдаёт
«отполированную» версию для presentation-grade output'а, а уже её
рендерит детерминированный Python-скрипт.

**Принцип:** polish = переформатирование под аудиторию, НЕ переписывание
фактов. Все даты, цены, решения, рекомендации сохраняются дословно.
Удаляется/перефразируется только pipeline-жаргон.

**Когда применять:** при `recipient ∈ {self, parents}`. Для archive /
debugging — пропускать (там pipeline-метаданные полезны).

---

## Что на входе и что на выходе

**Вход:** полный markdown файла стадии 5 — YAML frontmatter + body.
Размер: типично 30–60 KB, до 100 KB на длинных планах.

**Выход:** markdown того же формата (YAML + body), с применёнными
ниже трансформациями. Никаких пояснений, no preamble — только сам
markdown в ответе.

---

## Трансформации

Применять **все** по порядку. Если какая-то не применима к конкретному
файлу (например, нет такого поля) — пропустить, не упоминать.

### T1. Cover title

H1-заголовок документа переписать в человеко-читаемый формат.

**Было:**

```markdown
# Stage 5 — Финальный план: камбоджа_лаос_2026-02
```

**Стало:** извлечь страну/регион из тела `## Контекст и ключевые параметры`
+ длительность из YAML + сезон из текста. Шаблон:

```markdown
# {Страна/регион} · {N} ночей · {сезон/месяц год}
```

Примеры:
- `# Камбоджа и Лаос · 18 ночей · февраль 2026`
- `# Южная Аргентина · 13 ночей · март 2025`
- `# Северный Вьетнам · 20 ночей · октябрь 2026`

Если страна/регион не очевидна из контента — оставить дословно
`{trip_id без подчёркиваний и слаг-даты}`.

### T2. Скрыть pipeline-метаданные из frontmatter

**Этот список — исчерпывающий. НЕ выясняй keep/drop чтением
parser/adapter/рендерера — это лишние чтения и главный вклад в исчерпание
контекста на длинных планах.** Незнакомое YAML-поле, не попавшее ни в один
список ниже → **удалить** (по умолчанию — служебное).

**СОХРАНИТЬ** (нужны рендереру для naming / роутинга / обложки):
`trip_id`, `stage`, `iteration`, `created`, `duration_nights`,
`travelers_profile`, `chosen_variant`, `total_budget_rub`, `budget_target_rub`,
`budget_status`, `todo_verification_items`, `home_eq_start`, `warnings`.
⚠ `iteration` = версия плана; из неё `export.py` берёт номер `_vN` выходного
файла (строгое соответствие версии). Удалишь → выход получит `_v1` и
travel-окно спрячет его как устаревший.

**УДАЛИТЬ** (метаданные построения, не про сам план):
`mode`, `chosen_variant_raw`, `aggregation_mode_inherited`, `schema_version`,
`previous_plan`, `trip_id_warning`, `input_files`,
`web_search_used`, `mcp_extensions_used`, `clarification_used`, и любые
прочие `*_used` / служебные флаги.

### T3. Перефразировать pipeline-фразы в Контексте

В блоке `## Контекст и ключевые параметры`:

| Pipeline-фраза | Заменить на |
|---|---|
| «Применены правки пользователя из `## Решение` Stage 4:» | «Маршрут учитывает следующие уточнения:» |
| «Mode: reconstructive — предыдущего плана нет» | удалить полностью |
| «aggregation_mode_inherited: scarce — узкая STRONG-когорта...» | удалить полностью (это диагностика построения) |
| «независимая пара» / «независимые путешественники» (про группу) | «самостоятельная пара» / «путешествуют самостоятельно» |
| «Логика выбора пользователя (Решение Stage 4):» | «Логика выбора:» |
| «Выбран вариант A (Stage 4) — ...» | «Маршрут: ...» (только описание, без upstream-номера варианта) |

### T4. Day titles — оставить как есть

Заголовки дней `### День N (DD.MM Дн). Описание` **НЕ трогать** — оставить
сырой формат с датой в скобках. Дату форматирует сам builder:

- в PDF-outline → `День N · DD.MM` (ориентир по дате, а не только по номеру);
- подзаголовок дня → `DD месяца (Дн): Описание` (например
  `7 сентября (Пн): Ремесленные улицы → …`).

(Раньше polish разворачивал дату в `### День N · понедельник, 3 марта · …` —
**убрано**: это дублировало работу builder'а и заодно вымывало дату из
outline. Если такой развёрнутый формат встретится во входе — свернуть обратно
к `### День N (DD.MM Дн). Описание`.)

### T5. Section rename

| Было | Стало |
|---|---|
| `## TODO для верификации` | `## Что проверить перед поездкой` |
| `## Чеклист за 2 недели до поездки` | `## Чеклист за 2 недели до выезда` (если уже «выезд» — оставить) |

Остальные H2 (`## Шапка`, `## Маршрут по дням`, `## Сводные таблицы`,
`## План реагирования на риски`, `## Контекст и ключевые параметры`,
`## Критические подготовительные пункты`) — **не трогать**, downstream
renderer и anchor-map знают эти точные имена.

### T6. Скрыть/перефразировать «Контекст для следующих стадий»

Если такая H2 секция есть — она handoff между стадиями пайплайна.
Её надо либо удалить (если содержание дублируется в `## Контекст и
ключевые параметры`), либо переименовать в `## О поездке` и сократить
до 3-4 строк human-prose.

### T7. Пунктуация и микро-полиш

- Замена ASCII-кавычек `"..."` на «русские ёлочки» `«...»` в body
  (frontmatter оставить как есть)
- ASCII-дефис между числами `10-20` → en-dash `10–20`
- `--` (двойной hyphen) → em-dash `—`
- `(c)` → `©`, `(r)` → `®`

**НЕ** менять: URL'ы, code-блоки `` `...` ``, YAML.

### T8. Пустые секции

Если какая-то H2 секция оказалась пустой (только заголовок без body) —
удалить заголовок тоже. Не оставлять «голые» H2.

### T9. Регионы (инференция структуры маршрута)

Stage 5 markdown содержит плоский список дней. Регионы зашиты в текст
дней-переездов («Переезд Сеул → Сораксан»). Polish **выводит** регионы
и размечает их для рендера. Это переформатирование (группировка уже
имеющейся информации), НЕ генерация нового контента.

**T9a. Определить регионы.** Пройти по дням, сгруппировать по
географическим базам. Регион меняется на дне-переезде: фраза «Переезд X
→ Y» означает, что начиная с этого дня и далее — регион Y (день переезда
логически принадлежит НОВОМУ региону — сборы и заселение уже в нём).

**T9b. Маркер региона в каждом дне.** Первой строкой тела каждого дня
(сразу после заголовка `### День N ...`, ПЕРЕД маркерами 📍🏨🎯💰⚠️)
вставить маркер. У ПЕРВОГО дня каждого региона — с доп. полями
(скрипт соберёт из них сводную таблицу + titler-блок); у остальных
дней региона — только название:

```
[[регион: Сораксан | описание: гранитные пики и буддийские тропы национального парка — два дня на главные виды | база: Сокчо | главное: Ульсанбави (день 4) | буфер: день 5 — погодный | бронь: express bus Seoul Bus Terminal → Sokcho | риск: метель → fallback Соннянса]]
```
```
[[регион: Сораксан]]
```

Поля (все, кроме названия, — только у ПЕРВОГО дня региона):
- **Название** — короткое, человекочитаемое (Сеул, Сораксан, Кёнджу...).
  Повторный регион (возврат в Сеул) — уточняй: `Сеул (прилёт)` /
  `Сеул (финал)`. Маркер обязателен в КАЖДОМ дне.
- **описание** (опц.) — establishing-фраза региона: одна короткая строка
  (≤ ~120 символов), что это за регион и зачем он в маршруте. Рендер
  выносит её курсивом под названием в titler-плашку — establishing shot
  перед днями региона. **Не новый контент**: формулируй из уже имеющихся
  дней/полей `главное` (что группа здесь делает), не добавляй фактов.
  Отсутствие — норма (titler рендерится без неё).
- **база** — город-якорь региона (где ночёвки). Идёт в titler.
- **главное** — 2–4 ключевых пункта (колонка «Главное» + titler).
- **буфер** — описание буфер-дня, если есть.
- **бронь** — что бронировать заранее.
- **риск** — главный риск + fallback.
- **бюджет** НЕ указывать — скрипт сам считает диапазон из дневных 💰.

**T9c. Сводную таблицу и titler НЕ писать вручную.** Скрипт строит их
сам из маркеров T9b: группирует дни по регионам, проставляет кликабельные
ссылки `[N](#dayN)`, считает даты/ночи, суммирует бюджет региона
диапазоном, рисует titler-блоки «РЕГИОН N ИЗ M» с bullets из полей выше.
Твоя задача — только корректные маркеры в днях. Раздел `## Регионы
маршрута` создавать НЕ нужно.

### T10. Эмодзи — убрать из заголовков

В заголовках (cover-title, H2, заголовки дней) НЕ оставлять и НЕ
добавлять эмодзи (флаги стран 🇰🇷, 🏔, ✈ и т.п.). Шрифт рендера их не
поддерживает — будут квадраты. В заголовке оставлять только текст.
(Маркеры 📍🏨🎯💰⚠️ внутри тела дня НЕ трогать — скрипт обрабатывает их
сам, превращая в текстовые метки/плашки.)

### T11. Теги пользователя в прозе → человеческий язык

Значения тегов регионов/POI (`обязательно`, `можно`, `не интересно`,
`пропуск`, `can_pool`) иногда попадают в видимый текст сырыми — обычно
в backticks: «регион `можно` не выбран», «тег `не интересно`», «тег
региона `пропуск`». Это машинные ярлыки, в прозе их быть не должно.

Переписать фразу целиком, с грамматическим согласованием, заменив ярлык
человеческой формулировкой. Backticks убрать.

| Тег | Человеческая формулировка |
|---|---|
| `обязательно` | обязательный (must-have) регион |
| `можно` | оставлен опциональным |
| `не интересно` | помечен как неинтересный |
| `пропуск` | слот осознанно пропущен |
| `can_pool` | можно объединить с соседним регионом |

Примеры:
- «Чеджу — регион `можно` не выбран в вариант A» →
  «Чеджу — оставлен опциональным, в маршрут не вошёл»
- «Андон — тег региона `пропуск`» →
  «Андон — слот осознанно пропущен»
- «Чхунчхон — тег `не интересно`» →
  «Чхунчхон — помечен как неинтересный»

**Отдельно — цитата комментария пользователя `user «…»`.** В днях твой
комментарий к POI цитируется как `user «текст»` (например «озеро Хоанкьем
(STRONG, user «надо и днём, и ночью»)»). Слово `user` в прозе не оставлять —
переписать как «по твоей пометке «…»» или «ты отметил «…»», сам комментарий
сохранив **дословно**.

Примеры:
- «(STRONG, user «надо и днём, и ночью»)» →
  «(по твоей пометке «надо и днём, и ночью»)»
- «Train Street — user «не интересно»» →
  «Train Street — ты отметил «не интересно»»

Это **переформулировка ярлыка**, не изменение факта: причина исключения
сохраняется, меняется только формулировка. Новых причин не выдумывать.

### T12. Имена полей и токены стадий в прозе → человеческий язык

В видимый текст (вне YAML-шапки и code-блоков) иногда протекают имена
YAML-полей и внутренние токены. В прозе их быть не должно — заменять
человеческими формулировками:

| Токен в прозе | Заменить на |
|---|---|
| `home_eq_start` / `home_eq_start: true` | «старт и финиш — из дома» |
| `total_budget_rub` | «итоговый бюджет» |
| `retrospective` / `retrospective: true` | «ретроспективный прогон» |
| «cost rank» / `cost_rank` | «по уровню стоимости» |
| «Stage 1 Mode B», «Stage 4», «Stage N» | убрать ссылку на стадию, описать суть («по итогам сбора отчётов» и т.п.) |

**Англицизмы в прозе → русский** (видимый текст, не YAML и не code):

| Англицизм | Заменить на |
|---|---|
| `transit` | транзит / пересадка |
| `per person` / `per-person` | на человека |
| `Old Quarter` | Старый квартал (если в том же файле уже есть рус. форма) |
| `direct_to_entry`, `international_flight_context` и т.п. поля | описать суть по-русски |

Имена полей в YAML-шапке (T2) НЕ трогать — там они нужны. Правило
касается только тела документа. Vietnamese/локальные топонимы (`Hang Múa`,
`Trang An`) не русифицировать насильно, но если в файле уже есть рус. форма
того же места — придерживаться её единообразно.

### T13. Маркеры статуса/атрибуции и тезис — сохранять дословно

Этап-2 ввёл опциональные маркеры, которые **потребляет рендер** (чипы на
плашке дня, тезис на обложке). Polish их **НЕ удаляет и НЕ переписывает**:

| Маркер | Где | Зачем рендеру |
|---|---|---|
| `[[бронь: план]]` / `[[бронь: забронировано]]` | начало строки `🏨` | цветной чип статуса брони |
| `[[погода: {риск}]]` | в дне | синий чип «погода» |
| `*Источник: {тег/автор}*` | в `🎯`-пункте | inline-атрибуция якорного POI (курсив) |
| `**Замысел маршрута:** …` | первая строка `## Контекст…` | тезис на обложке |

Их отсутствие — норма (старый план). Если присутствуют — оставить как есть
(можно поправить пунктуацию внутри значения, но не формат маркера и не
квадратные скобки). Аналогично `[[регион: …]]` (T9).

### T14. Happy path / контингенси / рационал — не смешивать обратно

Этап-2 разводит «основной путь» и «если пошло не так» (#8) и тирирует
рационал (#12). Это **дисциплина авторства** (модель уже пишет так); polish
лишь не ломает разделение:

- НЕ вшивать контингенси-дерево обратно в день. Если дневной `⚠️` —
  короткий указатель, оставить коротким.
- Если день РАЗДУТ контингенси-деревом, **а полная версия уже есть** в
  `## План реагирования на риски`, — свернуть дневной `⚠️` до одной
  фразы-указателя (без потери: детали остаются в таблице). Если в таблице
  дубля НЕТ — **НЕ трогать** (не терять информацию).
- Глубокий рационал в `## Контекст… → «Логика ключевых решений:»` НЕ
  возвращать в текст дней (рендер сам выносит его в приложение).

## Что НЕЛЬЗЯ делать (no-go list)

Эти действия **запрещены** в polish-step:

1. **Менять факты.** Даты, цены, имена городов, отелей, контактов,
   операторов — дословно. Если в источнике написано «USD 150–220/ночь» —
   в polished версии должно быть ровно то же.
2. **Добавлять контент, которого не было.** Никаких «также рекомендую
   посетить...», никаких новых соображений. Polish ≠ writing.
3. **Удалять решения и обоснования.** «Логика ключевых решений»,
   «Чего больше нет в маршруте и почему», «Swap при позднем прилёте» —
   полная сохранность. Только rephrase pipeline-фраз.
4. **Менять структуру дней.** Маркеры 📍/🏨/🎯/💰/⚠️ оставлять как есть
   (downstream parser их извлекает). Контент под каждым маркером — без
   потерь.
5. **Сокращать TODO.** Все checkbox-пункты `- [ ] ...` остаются. Их
   значения может перепроверять только пользователь, не модель.
6. **Менять имена H2 секций кроме T5.** Anchor-map в renderer'е знает
   фиксированный набор имён. Произвольное переименование сломает
   внутренние ссылки и TOC.
7. **Добавлять preamble в ответ.** Не писать «Вот polished версия:» в
   начале. Не писать «Готово, изменения:» в конце. Только сам markdown.

## Стилевой guard

Длина output'а: **не больше +5% и не меньше -25%** от длины input'а в
символах. Если модель видит, что её правки выходят за этот коридор —
скорее всего она над-переписывает. Откатиться к более механическим
правкам.

Tone: нейтрально-фактологический. Профиль пользователя — биостатистик
(см. CLAUDE.md), он любит точность и не любит маркетинг. Никаких
«незабываемые впечатления», «откройте для себя».

Sanity reminder: после polish'а Python-скрипт `polish_check.py`
автоматически сравнит счёт H2/H3 секций и ключевые числа frontmatter.
Если расхождение — abort. Поэтому над-переписывать нет смысла, проще
сразу следовать списку T1-T8.

## Формат ответа

Один markdown-блок начиная с `---` (YAML frontmatter) и до конца файла.
Без обёртки в \`\`\`markdown ... \`\`\`. Без вводных фраз. Без trailing
комментариев. Чистый stage5-формат, готовый к скармливанию в
`export.py --input polished.md --stage 5 --recipient self`.
