# profile-management.md

Полная спецификация Profile mode (P) скилла `travel-planning`.
Описывает пять под-режимов (CREATE / UPDATE / MERGE / SHOW / DELETE),
шаблон профиля и дизайн one-batch interaction.

---

## Главный принцип: ONE-BATCH INTERACTION

Профиль заполняется за **минимальное число обращений к диску и минимальное
число turn'ов**:

- На каждый под-режим — **максимум 1 запрос к диску** на чтение (Glob или Read)
  до начала интерактива. Никаких промежуточных Read во время диалога.
- Вопросы пользователю задаются **одним батчем** — целым шаблоном, а не
  по одному. Пользователь отвечает одним сообщением с заполненными
  значениями.
- Запись на диск — **только в конце**, и она всегда manual (скилл выдаёт
  markdown, пользователь сохраняет руками — см. `storage-and-naming.md` §8.6).

Антипаттерн: «А какой у вас бюджет? ... А состав группы? ... А диета?» —
вереница вопросов в десять turn'ов. Скилл так делать не должен.

## 1. Маршрутизация под-режимов

После того как Маршрутизация SKILL.md определила режим P, определи под-режим
по сути запроса:

| Под-режим | Когда |
|---|---|
| CREATE | пользователь хочет завести новый профиль (новое имя, новая группа) |
| UPDATE | пользователь хочет изменить существующий профиль (бюджет, ограничения, состав) |
| MERGE | объединить два или более существующих профиля в групповой (для совместных поездок) |
| SHOW | пользователь хочет посмотреть, какие профили вообще есть, или прочитать конкретный |
| DELETE | пользователь хочет удалить профиль |
| **EXPORT_FORM** | пользователь хочет получить **DOCX-анкету** для заполнения в Word (пустую для CREATE или предзаполненную для UPDATE существующего профиля) — см. §10 |
| **IMPORT_FORM** | пользователь прислал **заполненный DOCX**, нужно собрать profile.md — см. §10 |
| **MERGE_FORM** | пользователь прислал **2+ DOCX/MD** профилей для объединения — см. §10.5 |

### 1.1 Распознавание под-режима по запросу

| Триггер пользователя | Под-режим |
|---|---|
| «создай профиль», «новый профиль», «заведи профиль X» | CREATE |
| «обнови профиль X», «поменяй … в профиле X» | UPDATE |
| «объедини X и Y», «совместный профиль из X и Y» | MERGE |
| «покажи профили», «какие профили есть», «открой X» | SHOW |
| «удали профиль X» | DELETE |
| **«дай анкету»**, **«пустую форму»**, **«DOCX для нового профиля»** | **EXPORT_FORM** (под-режим A — пустая) |
| **«анкета для правки X»**, **«DOCX для редактирования X»**, **«выгрузи анкету профиля X»** | **EXPORT_FORM** (под-режим B — предзаполнённая) |
| **прикреплён DOCX + «обнови»/«создай»/«импортируй»** | **IMPORT_FORM** |
| **прикреплены 2+ DOCX/MD + «объедини»/«merge»** | **MERGE_FORM** |

Если из запроса под-режим неоднозначен (например, «обнови профиль для
родителей», но `алексей_родители.md` ещё не существует) — задать ОДИН
уточняющий вопрос («профиль для родителей ещё не существует — создать
новый?») и перейти в соответствующий под-режим.

## 2. CREATE — создание профиля

### Поток (4 turn'а: запрос → batch вопросов → ответ → выдача)

#### Turn 1 — пользователь

Например: «создай профиль для родителей».

#### Turn 2 — скилл (preflight + batch)

В одном сообщении сделать ВСЁ нижеперечисленное:

**Шаг A. Резолв `profile_id`.**
Из запроса попытаться извлечь имя профиля. Если из «для родителей» очевидно,
что нужен `алексей_родители` (или контекст указывает на другое) — предложить
конкретное имя в начале ответа. Если неочевидно — попросить уточнить.

**Шаг B. ОДИН `Glob` существующих профилей.**

```
Glob("{travel_root}/profiles/*.md")
```

Получить список. Если есть похожий по имени (`алексей_марина.md`) —
предложить опцию клонирования (см. §8).

**Шаг C. Проверка коллизии.**
Если файл `profiles/{profile_id}.md` уже существует — НЕ создавать. Сразу
сообщить: «профиль `{profile_id}` уже существует, переключаюсь в UPDATE»
или предложить другое имя.

**Шаг D. Один batch с template + [ASK] архетипа.**
Выдать пользователю шаблон профиля (§7) с явно отмеченными:
- `[ОБЯЗАТЕЛЬНО]` — поля, без которых пайплайн работать не сможет
- `[ВАЖНО]` — поля, без которых стадии деградируют по качеству
- `[ОПЦИОНАЛЬНО]` — поля, которые можно пропустить, если для группы
  не релевантно
- `[HELPER]` — секция helper-вопросов, ответы на которые упрощают
  заполнение

**В начало batch включить отдельный блок `### Архетип группы
(обязательно)`** — см. §7.5. Это `[ASK]`-вопрос с 4 опциями и опц.
эвристической подсказкой по введённым в Turn 1 данным. Пользователь
обязан выбрать значение.

Каждое поле — с краткой инструкцией «что писать», без длинных пояснений.

В конце шаблона — инструкция: «Заполни и пришли ответом. Поля
`[ОПЦИОНАЛЬНО]`, которые не релевантны — можешь пометить `—` или просто
оставить пустыми. Архетип группы — обязателен.»

**Стоп.** Не задавать дополнительных вопросов в этом turn'е. Не делать
больше никаких файловых операций.

#### Turn 3 — пользователь

Присылает заполненный шаблон.

#### Turn 4 — скилл (assembly + manual save)

В одном сообщении:

1. Распарсить ответы пользователя.
2. Собрать финальный markdown профиля с YAML-шапкой (§7).
3. Прогнать минимальную валидацию (см. §9.3 — недозаполненные поля).
4. Если чего-то критичного не хватает — сообщить одним списком, что нужно
   досказать. **НЕ задавать вопросов по одному.**
5. Если всё ок — выдать готовый markdown + блок «Сохранить как» по
   `storage-and-naming.md` §9.

### Что НЕ делать

- Не задавать вопросы по одному в формате диалога.
- Не делать промежуточных Read/Write в середине диалога.
- Не «угадывать» поля, которые пользователь не заполнил (кроме
  `created` = сегодняшняя дата). Лучше пустое поле, чем выдуманное.
- Не выдумывать `profile_id` без подтверждения пользователя.

## 3. UPDATE — обновление профиля

### Поток (4 turn'а: запрос → текущий профиль + batch → ответ → выдача)

#### Turn 1 — пользователь

«обнови профиль алексей_марина», «поменяй бюджет в профиле родителей».

#### Turn 2 — скилл (read + summary + batch)

В одном сообщении:

**Шаг A. ОДИН Read.**

```
Read("{travel_root}/profiles/{profile_id}.md")
```

Если файл не найден — переключиться в CREATE flow с уточнением
«профиль не существует, создаём?».

**Шаг B. Краткий summary текущего профиля.**
Вывести в чат 5–8 строк с основными полями (состав, стиль, ядро интересов,
бюджет). Не выводить весь файл — пользователь его уже знает.

**Шаг C. Один batch — «что меняем».**
Один блок вопросов:

```
Что меняем (одним сообщением, в свободной форме):

- какие секции/поля редактируются (укажи новые значения)
- какие поля удаляются
- какие добавляются
- меняется ли состав группы (это пересчитает несколько связанных полей)
- меняется ли `profile_id` (требует переименования файла)
```

**Стоп.** Не запрашивать по полю отдельно.

#### Turn 3 — пользователь

Присылает diff в свободной форме.

#### Turn 4 — скилл (apply + manual save)

В одном сообщении:

1. Применить изменения к копии профиля в памяти (не на диск).
2. Обновить YAML поле `updated: YYYY-MM-DD`.
3. Если меняется `profile_id` — пометить как требующее переименования
   файла на диске (пользователь делает сам).
4. Выдать обновлённый markdown целиком + блок «Сохранить как» с пометкой
   «это перезапись существующего файла».

### Особенности

- Если изменения структурные (новый состав группы, смена пары на семью) —
  возможно, проще создать новый профиль через CREATE, а старый оставить.
  Подсказать это в Turn 2 если видишь, что изменения тянут на новый профиль.
- Не пересчитывать старые поездки. См. SKILL.md «profile drift» —
  только предупреждение, не автоматический пересчёт.

## 4. MERGE — объединение профилей в групповой

### Поток (4 turn'а: запрос → preview + ASK batch → ответ → выдача)

#### Turn 1 — пользователь

«объедини алексей и мария», «создай совместный профиль из X и Y»,
«merge X + Y», «профиль для совместной поездки».

#### Turn 2 — скилл (read + auto-merge preview + ASK batch)

**Шаг A. Резолв `profile_id` объединённого профиля.**

Правило именования:

- Если в группе есть владелец (`алексей`) — он первым:
  `алексей_мария`, `алексей_родители`, `алексей_родители_марина`.
- Если владельца в группе нет (например, родители + кто-то ещё, без
  тебя) — по алфавиту: `мария_родители`.

Это умолчание; в начале ответа показать предложенное имя и оставить
пользователю возможность переопределить (одной строкой в Turn 3).

**Шаг B. Два (или более) Read source-профилей.**

```
Read("{travel_root}/profiles/{profile_id_1}.md")
Read("{travel_root}/profiles/{profile_id_2}.md")
[Read доп. профилей для merge >2]
```

Если хотя бы один source не найден — отказ, перечислить существующие
профили, предложить CREATE для отсутствующего.

**Шаг C. Auto-merge по правилам §4.1.**

Применить per-field правила к каждой секции source-профилей. Получить
full merged профиль в памяти (на диск не пишем).

**Шаг D. Preview — полный merged профиль с маркерами.**

Вывести в чат **весь** объединённый профиль (не сжатую сводку
расхождений). Рядом с заголовком каждой секции — один из 5 маркеров:

- `[MIN]` — взята более ограничительная версия
- `[UNION]` — сложены оба источника
- `[STRICTER]` — объединено по принципу «исключаем если кто-то против»
- `[NO CONFLICT]` — у source-профилей было одинаково (или один пустой)
- `[ASK ↓]` — поле требует уточнения, поставлен placeholder
  `<требует уточнения>`, вопрос задан в Шаге E

Под каждой секцией `[MIN]` / `[STRICTER]` — одна строка с пояснением
источника решения:

```
## Физическая форма                           [MIN]
- треки до 20 тыс. шагов в день
- лестницы и высокогорье до 3000 м — нормально

> алексей: 30 тыс шагов, высокогорье любое
> мария: 20 тыс шагов, высокогорье до 3000 м
> взят минимум по каждой шкале
```

В финальном merged профиле (Turn 4) маркеры и поясняющие строки
удаляются.

**Шаг E. Один batch ASK-вопросов.**

В одном блоке — все вопросы по полям, которые потребовали уточнения.
Пример для пары:

```markdown
## Уточнения для объединённого профиля

### Архетип группы (обязательно при MERGE)
- алексей: самостоятельные
- мария: самостоятельные

Объединение может менять архетип. Подтверди один:
- [ ] самостоятельные (пара взрослых, оба активны, планируют сами)
- [ ] семья_с_детьми (если в группу добавляется ребёнок)
- [ ] взрослые_50_плюс (если основной возраст 50+)
- [ ] люкс (если поднят класс размещения)

### Бюджет
- алексей: ~$1000/нед на одного, единый потолок
- мария: $X/нед на одного, ...

Как считаем для совместной поездки?
- [ ] Сумма (двое → ~$2000/нед на пару)
- [ ] Общий бюджет, новый (укажи число)
- [ ] Per person сохраняется индивидуально, общий = сумма

### Состав группы — подтверди
2 человека, возраст 37 + ?, гражданство РФ + ?

### Фотография
- алексей: Fujifilm X-S10, трэвел/природа, Capture One
- мария: <как указано в её профиле или пусто>

Оставлять секцию для merged профиля или убрать?

### [Другие ASK-поля при наличии расхождений]
```

**Стоп.** В этом turn'е больше ничего. Пользователь видит весь merged
профиль с маркерами + список вопросов.

#### Turn 3 — пользователь

Отвечает на ASK-вопросы. Может также внести ручные правки в любую
секцию auto-merged профиля, если не согласен с решением.

#### Turn 4 — скилл (assembly + save)

1. Применить ответы пользователя к черновику в памяти.
2. Применить ручные правки.
3. Удалить из заголовков маркеры и пояснения — они только для preview.
4. Собрать финальный markdown с обычной YAML-шапкой:

```yaml
---
profile_id: алексей_мария
created: 2026-05-21
updated: 2026-05-21
---
```

Поля `type: merged` / `source_profiles: [...]` в frontmatter
**не добавляются** — merged профиль после сборки = самостоятельный
групповой профиль. Исходные `алексей`, `мария` остаются нетронутыми
и используются независимо для сольных поездок. Если в будущем merged
расходится с обновлёнными source-профилями — это новая отдельная
правка через UPDATE этого merged профиля.

5. Выдать финальный markdown + блок «Сохранить как» (см.
   `storage-and-naming.md` §9).

### 4.1 Per-field правила объединения

Поля разделяются на 4 категории по способу слияния:

| Категория | Правило | Поля |
|---|---|---|
| **MIN** | взять более ограничительную версию | Физическая форма; Темп; Класс размещения (если оба про одну ось); Допустимы ли ночные переезды |
| **UNION** | сложить оба, отметить кто откуда | Опыт поездок; Языки группы; Ядро интересов (с подсветкой overlap); Платёжная инфраструктура (карты обоих); **Переносимость** (см. ниже) |
| **STRICTER** | объединить по принципу «исключаем если хоть один против» | Явные исключения; Гастрономические ограничения; Запреты по транспорту/размещению |
| **ASK** | автомерж невозможен, спросить | Бюджет; Состав группы (подтвердить); Фотография (актуально для пары или нет); Частота смены локаций при расхождении; **Возможность вождения** (см. ниже); любые поля с принципиально разным содержанием |

**Граница MIN vs ASK:**

- Если в обоих профилях поле сопоставимо (оба количественные на той же
  шкале / оба про одну ось) → **MIN**.
  Пример: «алексей: треки 30 тыс шагов, мария: 20 тыс шагов» → MIN: 20 тыс.
- Если содержание принципиально разное (разные оси, не сопоставимо
  напрямую) → переводим в **ASK**.
  Пример: «алексей: древняя архитектура + треккинг; мария: гастрономия
  + дегустации» — это не MIN, это требует явного решения «что включаем
  в общее ядро интересов на эту поездку».

**Особый случай — Переносимость.**

Порог переносимости принадлежит человеку, а не группе, поэтому
MIN здесь теряет информацию, а усреднение прямо вредно: «в среднем
группа терпит 36 °C» — бессмысленная величина, если одному из двоих
плохо уже при 34 °C с влажностью.

- Мерж — **UNION с обязательной атрибуцией по имени**:
  «Мария: ~34 °C при высокой влажности — предел; Алексей: ок».
- Планирование при этом идёт **по самому низкому порогу группы**:
  день строится под того, кому тяжелее. Это правило для Stage 0/5,
  а не операция слияния — в профиле сохраняются обе строки.
- Пустая секция у одного из source-профилей — не «ограничений нет»,
  а «не спрашивали»: переносить как есть, не додумывать.

**Особый случай — Возможность вождения.**

Ни одно из правил MIN/UNION/STRICTER не работает:

- UNION даёт «машина + нет» — нонсенс.
- MIN даёт «нет возможности», но фактически у группы есть один
  водитель — это потеря информации.
- STRICTER даёт «нет машины», что неверно — машина доступна группе
  через водителя из второго профиля.

Наличие одного водителя в группе ≠ его готовность возить всех каждый
день в любой ситуации (long-haul, ночью, в незнакомой стране).
Поэтому всегда **ASK** с конкретным вопросом:

```markdown
### Возможность вождения
- {profile_1}: <значение из профиля 1>
- {profile_2}: <значение из профиля 2>

Кто реально готов водить в этой поездке (и в каких странах)?
- [ ] машина (кто водит)
- [ ] байк/скутер (кто водит)
- [ ] нет возможности — едем без аренды
- [ ] зависит от региона — уточни
```

## 5. SHOW — перечисление профилей

### Поток (2 turn'а)

#### Turn 1 — пользователь

«покажи все профили», «какие у меня есть профили», «покажи профиль
алексей_марина».

#### Turn 2 — скилл

**Если запрошен список:**

```
Glob("{travel_root}/profiles/*.md")
```

Для каждого файла — Read первых 30 строк (YAML + заголовок + первые
2–3 секции). Хватит для краткой сводки.

Выдать таблицу: `profile_id` | состав | ядро интересов одной строкой | даты
created/updated.

**Если запрошен конкретный профиль:**

```
Read("{travel_root}/profiles/{profile_id}.md")
```

Выдать полный markdown в чат. Никакой обработки.

**Стоп.** Это read-only режим, никаких изменений.

## 6. DELETE — удаление профиля

### Поток (2 turn'а: запрос → инструкция)

#### Turn 1 — пользователь

«удали профиль X».

#### Turn 2 — скилл

1. ОДИН Read для проверки существования. Если нет — сообщить и стоп.
2. Если есть — вывести краткий summary (на что пользователь смотрит,
   чтобы убедиться) + предупреждение: «связанные поездки в `trips/`
   будут продолжать ссылаться на этот профиль через

3. Перечислить связанные поездки через

## 7. Шаблон профиля (полная спека)

### 7.1 YAML frontmatter

```yaml
---
profile_id: алексей_родители
created: 2026-05-21
updated: 2026-05-21
группа_архетип: взрослые_50_плюс
---
```

`группа_архетип` — обязательное поле, определяет калибровку Stage 1
(seed source-set DR-выборки) и Stage 2 (веса similarity по 6
компонентам). Допустимые значения и таблицы калибровки — см. §7.5.
При CREATE и MERGE поле обязательно задаётся через `[ASK]` (дефолта
нет). При UPDATE — менять только по явному запросу пользователя.

Опционально для продвинутого пользователя — `similarity_weights_override`
блок, перекрывающий веса архетипа:

```yaml
---
profile_id: ...
created: ...
updated: ...
группа_архетип: ...
similarity_weights_override:
  стиль: 30
  фокус: 25
  темп: 15
  независимость: 5
  non_touristy: 15
  возраст_состав: 10
---
```

Сумма весов должна быть 100. Stage 2 валидирует.

Опционально — `display_name`: человекочитаемое имя группы/человека для
витрин экспорта («Родители», «Петя», «Алексей и Мария»). Это самый
авторитетный источник ответа «Кто едет» на обложках всех стадий экспорта —
надёжнее, чем разбор `profile_id` по подчёркиваниям (даёт «Алексей и
Родители» неточно) или чем текст, который приходится восстанавливать
из `trip.yaml`/маркеров черновика. Отсутствие поля — не ошибка: экспорт
откатывается на `travelers:` из `trip.yaml`, затем на текст в черновике
поездки, затем на разбор `profile_id`. При CREATE/UPDATE поле не входит
в обязательный batch — заполняется по желанию пользователя отдельной
правкой YAML.

```yaml
---
profile_id: алексей_родители
display_name: Родители
created: ...
updated: ...
группа_архетип: ...
---
```

Других полей в шапке не вводить — остальные детали живут в теле
документа.

### 7.2 Структура тела

```markdown
# Профиль: {Имя группы — человекочитаемое}

## Состав группы                              [ОБЯЗАТЕЛЬНО]
- кол-во человек, возрастной диапазон
- гражданство и паспорта (важно для виз)
- знание языков (если значимо для логистики)

## Базовый город                              [ВАЖНО]
- Домашний город пользователя — где группа живёт и куда возвращается
  по умолчанию. Примеры: `Москва`, `Санкт-Петербург`, `Тбилиси`, `Берлин`.
- Используется Stage 0 как **дефолтный стартовый город маршрута**
  (`trip_start_city = home_city`), если в запросе на поездку явно не
  назван другой стартовый город.
- Используется Stage 4 для формулировки Дня 1 и последнего дня
  маршрута (`Прилёт в X` vs `Старт маршрута в X` — в зависимости от
  того, совпадает ли `home_city` со стартовым городом конкретной
  поездки).
- Поле опционально — пустой профиль допустим. При отсутствии Stage 0
  спросит пользователя ОДНОЙ строкой при первом планировании.
- Per-trip переопределение **в профиле не нужно** — оно живёт в Stage 0
  через `trip_start_city`. Если конкретная поездка стартует из другого
  города (например, гость родителей в другом городе перед вылетом) —
  пользователь указывает это **в запросе** к Stage 0, и Stage 0
  фиксирует `trip_start_city` под эту поездку. Профильный `home_city`
  остаётся неизменным.

## Стиль путешествий                          [ОБЯЗАТЕЛЬНО]
- независимое / организованное
- класс размещения (бюджетный / средний / премиум).
  По желанию уточни: «бюджетный — хостелы и общие спальни»,
  «средний — недорогие отели или квартиры с private rooms»,
  «премиум — 4-5* и выше»
- транспорт-предпочтение: с водителем / общественный / аренда /
  байки (что хочется использовать)
- допустимы ли ночные переезды

## Возможность вождения                       [ВАЖНО]
Это про реальную способность и желание водить (не только наличие прав).
Выбрать один или несколько вариантов:
- **машина** — могу и готов водить машину
- **байк/скутер** — могу и готов водить байк/скутер (бензиновый,
  требует прав почти везде)
- **электробайк без прав** — готов брать класс, для которого права
  не нужны (электровелосипед / e-scooter до странового порога
  мощности и скорости)
- **нет возможности** — нет прав, либо есть права но водить не хочу
- (опц.) географические ограничения: «машина в спокойных странах,
  не в Индии/Камбодже/Юго-Восточной Азии»

⚠️ «Нет прав» ≠ «самоходного транспорта нет»: классы без прав
(велосипед, электробайк) — отдельная правовая категория, и Stage 5
обязан проверить страновой порог прежде, чем закрывать
самостоятельную аренду целиком.

Поле читается стадиями для оценки доступности регионов
(некоторые регионы реально достижимы только с арендой машины
или байка — например, Ha Giang Loop, исландские F-roads,
Cordillera Real).

## Темп                                       [ВАЖНО]
- активный / умеренный / медленный

## Частота смены локаций                      [ОПЦИОНАЛЬНО]
- сколько ночей на локацию: 1–2 / 3–5 / 5+
- если нет жёсткого предпочтения — оставить пустым

## Ядро интересов                             [ОБЯЗАТЕЛЬНО]
- 3–7 основных тем, ради которых едут
  (архитектура, этнография, природа, гастрономия,
   треккинг, фотография, исторические места, ...)
- по возможности — конкретно (не «культура», а
  «доколониальная архитектура в живой среде»)

## Физическая форма                           [ОБЯЗАТЕЛЬНО]
- общая (хорошая / средняя / ограниченная)
- треки: сколько часов в день допустимо
- лестницы, подъёмы, высокогорье — что ОК, что нет
- индивидуальные ограничения отдельных членов группы

## Переносимость                              [ВАЖНО]
Не выносливость (она выше), а внешние условия, при которых день
перестаёт работать. Пер-персонально — не усреднять по группе.
- климат: предел по ощущаемой температуре (температура + влажность),
  кому именно тяжело
- экспозиция и скольжение: мокрые тропы с уклоном, броды, обрывы,
  крутые спуски — для кого зона дискомфорта
- укачивание: горные серпантины, морские переходы, ночные автобусы
- мото-пассажиром / easy-rider, особенно в дождь

Читается Stage 0 (выбор сезона и окна дат — климатический предел
работает как фильтр региона, а не примечание к дню) и Stage 5
(окна активностей, класс автобуса, выбор трека).

## Явные исключения                           [ОБЯЗАТЕЛЬНО]
Два тира — смешивать нельзя, иначе стадии трактуют «не интересно»
как вето и выбрасывают точку из артефакта целиком.
- **Никогда** — жёсткое вето, в план не включать ни в каком виде
  (организованные тур-группы, ночные клубы, ...)
- **Не как основа, но эпизодически допустимо** — по прямому
  запросу или как замена сорвавшегося по погоде дня
  (пляж на полдня; популярная точка рядом с базой)
- по составу — что специфичное группе нельзя

## Гастрономия                                [ВАЖНО]
- стиль (уличная еда / рестораны / отели)
- кофе, алкоголь, особое питание
- индивидуальные ограничения (не ест морепродукты,
  аллергии, вегетарианство, что-то ещё)

## Фотография                                 [ОПЦИОНАЛЬНО]
- профессионально / для себя / на телефон / не делает
- жанры (пейзаж / архитектура / ночная / репортаж)
- особенности (съёмка на рассвете да/нет, дроны, оборудование)

## Опыт поездок                               [ВАЖНО]
- список стран/регионов с базовой оценкой опыта
  («Япония — был, азиатская инфраструктура знакома»)
- особенно — похожие по типу к планируемой поездке
- нужно для similarity-калибровки на Stage 2

## Бюджет                                     [ВАЖНО]
- ориентир в RUB/неделю на группу. Бюджет часто зависит
  от типа поездки — указать раздельно если различается:
  - дальние страны (Азия, Латинская Америка и т.п.)
  - Европа / ближние развитые страны
  - постсоветское пространство, по РФ
- что включает (всё / без перелётов)
- готовность переплачивать за конкретные вещи (комфорт,
  гид, частный транспорт)
- на стадиях планирования (Stage 4–5) допустима региональная
  коррекция бюджета ±20% если конкретный регион значимо
  дороже/дешевле среднего

## Платёжная инфраструктура                   [ВАЖНО]
- работающие иностранные карты (есть / нет, какие —
  Visa / MC / UnionPay / Mir), и **оформлены ли фактически**:
  «планируем оформить» ≠ «есть» (карта, которой нет на руках,
  для Stage 5 — TODO, а не платёжный канал)
- бесконтактная оплата (ApplePay / Google Pay) — проходила ли
  реально и где
- готовность осваивать локальные платежи (Alipay,
  WeChat Pay и т.п.) — да / нет / при необходимости
- покупка местной валюты до вылета: если валюта не экзотическая —
  часть суммы дома, остаток менять на месте
- ограничения на оплату иностранных онлайн-сервисов из страны
  проживания (eSIM-агрегаторы, брони) — влияет на план связи

Наличные подразумеваются по умолчанию — отдельно не уточнять.
```

### 7.3 Минимально необходимые поля

Для того чтобы пайплайн стартовал (Stage 0):

- `группа_архетип` (YAML, [ASK] на CREATE/MERGE)
- `Состав группы`
- `Стиль путешествий`
- `Ядро интересов`
- `Физическая форма`
- `Явные исключения`

Остальные секции могут быть пустыми — стадии деградируют по качеству,

`Базовый город` (ВАЖНО, но не блокирующий) — если пустой, Stage 0
ОДНОЙ строкой спросит при первом планировании поездки, без блокировки.

### 7.4 Маркеры в шаблоне на старте

При выдаче template'а в CREATE flow рядом с заголовком каждой секции
ставится маркер: `[ОБЯЗАТЕЛЬНО]` / `[ВАЖНО]` / `[ОПЦИОНАЛЬНО]`.
В финальном профиле эти маркеры **удалить** — это инструкция для
заполнения, не часть данных.

### 7.5 Архетипы группы — лукап калибровки

Поле `группа_архетип` принимает одно из 4 значений. Архетип определяет
**дефолтные веса similarity** (Stage 2) и **seed source-set DR-выборки**
(Stage 1). Это семантическая калибровка под основной стиль группы —
выбирается человеком, не выводится автоматически.

#### Допустимые значения и описания

| Значение | Описание |
|---|---|
| `самостоятельные` | Соло или пары без жёстких ограничений, активный темп, mid-range размещение, самостоятельное планирование без гида |
| `семья_с_детьми` | В группе есть дети до 16, длительные базы, кид-friendly POI, ограничения по интересам и темпу |
| `взрослые_50_плюс` | Основной возраст 50+, комфорт, без ночных переездов, средний темп, лифты обязательны |
| `люкс` | Премиум-класс размещения, $5000+/неделя, resort-based, fewer locations, премиум-сервисы |

**Legacy-алиас.** `независимые_соло_пара` — прежнее имя архетипа `самостоятельные`
(легаси: профили и артефакты поездок до переименования). Оно остаётся валидным
на чтении: скрипты (`similarity_score.py`, импорт/предзаполнение анкеты)
резолвят его в `самостоятельные`, веса и seed-набор те же. Старые файлы
не переписываются; новые профили и анкеты пишут только каноническое имя.
`родители_60_плюс` → `взрослые_50_плюс` — аналогичный алиас.

#### Эвристика для подсказки архетипа (помощь в [ASK])

При CREATE / MERGE скилл может **предложить** конкретный архетип, опираясь
на ранее введённые данные. Эвристика только подсказывает — финальный
выбор за пользователем:

- Возраст основной группы > 50 → подсказать `взрослые_50_плюс`
- В составе есть дети до 16 → подсказать `семья_с_детьми`
- Класс размещения «премиум» или бюджет ≥ $5000/неделя → подсказать `люкс`
- Иначе → подсказать `самостоятельные`

#### Веса similarity (Stage 2) по архетипам

Сумма каждого столбца = 100. Сумма используется Stage 2 как калибровка
similarity-score 0–10 по 6 компонентам автора DR-выборки.

| Компонент | `самостоятельные` | `семья_с_детьми` | `взрослые_50_плюс` | `люкс` |
|---|---|---|---|---|
| стиль (стиль путешествий) | 25 | 20 | 15 | 30 |
| фокус (фокус автора) | 25 | 20 | 15 | 20 |
| темп (темп поездки) | 15 | 25 | 25 | 15 |
| независимость (планирование) | 10 | 5 | 5 | 5 |
| non_touristy (depth) | 15 | 5 | 5 | 10 |
| возраст_состав (демография) | 10 | 25 | 35 | 20 |

Логика:
- Для семьи / родителей вес «возраст_состав» резко растёт — нужны
  авторы похожего демографического состава (с детьми / в возрасте).
- Для них же вес «non_touristy» падает: стандартный маршрут с
  предсказуемой инфраструктурой важнее, чем off-the-beaten-path.
- Для люкса акцент на стиле и demo — премиум-авторы похожего профиля.
- Для самостоятельных текущие 25/25/15/10/15/10 (дефолт алексея).

При наличии `similarity_weights_override` в YAML профиля — он
перекрывает архетипные. Stage 2 валидирует, что сумма перекрытия = 100.

#### Seed source-set DR-выборки (Stage 1)

**Это рекомендация, не жёсткий ограничитель.** DR-агент Stage 1 должен
**начинать** с seed-списка, но может включать любые другие источники, если
найдёт релевантный контент (фуд-блог с разовым подробным trip report'ом,
photo-substack с серией про городскую архитектуру, podcast-транскрипт).
В META-DIAGNOSTICS Stage 1 отмечается доля «вне seed-списка» — со
временем по результатам нескольких поездок seed можно эмпирически
дополнять.

| Архетип | Seed-набор |
|---|---|
| `самостоятельные` | **рус:** tourister.ru, travel.ru, livejournal travel-tags, telegra.ph travel; **англ:** reddit r/travel + страновые subreddit, lonely planet thorn tree, substack travel writers, individual backpacker-блоги; **фото:** landscape photography blogs, photo-essays substack/medium |
| `семья_с_детьми` | **рус:** babyblog.ru travel-tags, instagram мамы-путешественницы; **англ:** reddit r/familytravel, family-with-kids blogs, ciaobambino.com, travelinglight family bloggers |
| `взрослые_50_плюс` | **рус:** tourister.ru, otzyv.ru, tury.ru реальные отчёты; **англ:** tripadvisor forums (обсуждения, не отзывы об отелях), road scholar / smithsonian journeys participant reviews |
| `люкс` | **рус:** tourister.ru luxury-tag, премиум-форумы; **англ:** conde nast traveler long-reads, travel+leisure, NYT travel section, премиум-substack писатели, robb report travel |

**forum.awd.ru (Винский) в seed НЕ входит:** DR не открывает awd.ru
(BPC-challenge), поэтому он покрывается отдельно через Stage 1 под-режим
B1 (`fetch_awd.py`-discovery), а в самом DR-промте awd.ru — в exclusions.

Этот блок — единый источник seed-набора; Stage 1 DR-промт встраивает
его как есть, своей версии списка не держит. В DR-промт встраивается
двойная формулировка:

```
Источники для поиска. Начни с этого набора (откалиброван под
архетип "{группа_архетип}"):

{seed-список по архетипу}

Дополнительно ищи на других платформах, если найдёшь релевантный
контент. Не ограничивайся seed-списком — встретишь полезный отчёт
вне списка, включай при соответствии критериям включения (личный
опыт, ≥1500 слов, конкретные имена/адреса/даты).

В META-DIAGNOSTICS отметь источники "вне seed-списка".
```

#### [ASK]-вопрос для CREATE / MERGE

При создании или объединении профиля скилл задаёт пользователю один
вопрос в составе общего batch (не отдельным turn'ом):

```markdown
### Архетип группы (обязательно)

Выбери один — определяет калибровку поиска DR и фильтрации авторов:

1. `самостоятельные` — соло или пара, планируют сами, без гида; активный
   темп, без жёстких ограничений, mid-range
2. `семья_с_детьми` — длительные базы, кид-friendly POI
3. `взрослые_50_плюс` — комфорт, без ночных переездов, средний темп
4. `люкс` — премиум-класс, resort-based, fewer locations

[опц.] Подсказка по введённым данным: {результат эвристики из §7.5}
```

Дефолта нет — пользователь должен явно выбрать. При попытке сохранить
профиль с `группа_архетип: [ASK]` или пустым — отказ с напоминанием.

**Backward-compat для legacy-профилей.** Profile mode CREATE/MERGE
требует архетип обязательно. Однако downstream-стадии (Stage 1, 2)
толерантны: если legacy-профиль (созданный до v0.22) не содержит
`группа_архетип` — стадия использует fallback `самостоятельные`
+ одна строка-warning пользователю («профиль без `группа_архетип`,
используется дефолт; запусти Profile mode UPDATE для калибровки»).
Это не противоречие политике «дефолта нет» — это разница между
**созданием** профиля (обязательный [ASK]) и **чтением** существующего
(толерантный fallback). При первой возможности пользователь должен
обновить профиль через UPDATE.

## 8. Helper questions (что упрощает задачу)

В Turn 2 CREATE flow в конец template'а добавляется секция:

```markdown
## [HELPER] Что упростит заполнение

Ответы на эти вопросы не обязательны, но если применимо — облегчат работу:

1. **База из существующего профиля.**
   Найдены существующие профили: {список из Glob}.
   Хочешь взять один из них как базу и указать только отличия?
   - если да: укажи `base_profile: {profile_id}` и в каждой секции
     заполни только то, что отличается. Остальное скопируется автоматически.

2. **Пропуск нерелевантных секций.**
   Какие секции для этой группы не важны? (например, `Фотография` для
   родителей, если они на телефон от случая к случаю).
   - перечисли через запятую: `пропустить: фотография, ...`
   - такие секции будут опущены из финального профиля целиком.

3. **Auto-fill раздела «Опыт поездок».**
   Если эта группа = ты сам (а не родители/друзья), список
   посещённых стран можно скопировать из твоих User Preferences
   в Cowork — он там уже есть. Сказать: `опыт_поездок:
   взять_из_user_preferences`.

4. **Бюджет и платёжная инфраструктура от другого профиля.**
   Если бюджет и платёжная стратегия совпадают с другим профилем —
   можно сослаться: `бюджет_и_платежи: from {profile_id}`. Скилл
   скопирует обе секции.
```

В Turn 4 (assembly) скилл применяет:

- `base_profile: X` → читает `profiles/X.md`, копирует все секции,
  замещает теми, что заполнены пользователем
- `пропустить: A, B` → удаляет секции A и B из финального профиля
- `опыт_поездок: взять_из_user_preferences` → берёт список стран
  из User Preferences текущей Cowork-сессии, форматирует в секцию
- `бюджет_и_платежи: from X` → читает `profiles/X.md`, копирует две секции

Каждое применение требует **максимум 1 дополнительный Read** на профиль.
Если `base_profile` + `бюджет_и_платежи` ссылаются на разные профили —
это два Read. Всё ещё минимум.

User Preferences читать НЕ нужно — они уже в контексте сессии (системный
промпт). Просто извлечь раздел про путешествия.

## 9. Edge cases

### 9.1 Коллизия `profile_id` при CREATE

`profiles/{profile_id}.md` уже существует. Не перезаписывать. Варианты:

- предложить UPDATE
- предложить другое имя (например, добавить год: `алексей_марина_2026`,
  если состав или ограничения меняются настолько, что это уже другой
  «контекст путешественников»)

### 9.2 Профиль не найден при UPDATE/DELETE

`Read` возвращает ошибку. Реакция: перечислить существующие профили
(`Glob` + краткие summary) и спросить, что имелось в виду.

### 9.3 Пользователь прислал только часть полей в CREATE

В Turn 4 проверить минимально необходимые поля (§7.3). Если чего-то
не хватает:

- Сообщить ОДНИМ списком: «не заполнены: X, Y, Z. Без них Stage 0 не
  стартует. Допиши и пришли ещё раз».
- Не задавать вопросы по одному.

Если опциональные поля пусты — просто опустить соответствующие секции
из финального markdown (не оставлять пустые заголовки).

### 9.4 Профиль без некоторых [ВАЖНО] полей

Допустимо: пайплайн стартует, но стадии деградируют по качеству.

| Отсутствует | Что деградирует |
|---|---|
| `Темп` | Stage 4 не сможет оценить, не слишком ли плотный/разрежённый маршрут для группы |
| `Возможность вождения` | Stage 0/4/5 могут предлагать регионы с обязательной арендой машины/байка без проверки capability — будет hedging типа «исключено если нет прав» вместо чёткой фильтрации |
| `Гастрономия` | Stage 5 не сможет адаптировать рестораны под ограничения |
| `Опыт поездок` | Stage 2 (similarity) — менее точная калибровка |
| `Бюджет` | Stage 4–5 не смогут проверить варианты на укладывание (особенно если по типу поездки бюджеты разные) |
| `Платёжная инфраструктура` | Stage 5 не сможет дать payment-инструкции |
| `Фотография` | Stage 3 не сможет отметить фото-релевантные POI |
| `Частота смены локаций` | Stage 4 — переходы между вариантами сравниваются грубее |

При выдаче профиля без [ВАЖНО] поля — добавить в YAML-шапку
`incomplete_sections: [имя_секции, ...]` для будущих стадий.

### 9.5 Изменение `profile_id` через UPDATE

Если пользователь хочет поменять имя профиля — это требует:

1. Сохранения нового файла под новым именем (manual).
2. Удаления старого (manual).
3. Обновления `travelers_profile:` в YAML всех артефактов поездок,
   которые ссылались на старый профиль.

Скилл в Turn 4 выдаёт:
- новый markdown
- инструкцию на удаление старого файла
- список поездок (`Glob trips/*/0_scope.md` + проверка `travelers_profile`),
  которые потребуют обновления `travelers_profile` поля — пользователь
  делает руками

Это редкая операция, не оптимизируется.

### 9.6 Латиница в `profile_id`

См. `storage-and-naming.md` §10.7. Допустимо (legacy), но при создании
новых рекомендуется русский — для консистентности с экспортами.

### 9.7 Пользователь хочет добавить нестандартную секцию

Например, «у нас есть собака, добавь раздел про неё». Допустимо.
В Turn 4 добавить новую секцию в финальный markdown. Не блокировать
схемой.

### 9.8 MERGE: один из source-профилей не найден

См. §4 Шаг B. Отказать, перечислить существующие профили, предложить
CREATE для отсутствующего. Не пытаться merge с пустым source.

### 9.9 MERGE: merged профиль уже существует

`profiles/алексей_мария.md` уже есть. Не перезаписывать. Варианты:

- UPDATE этого merged профиля (если изменения точечные)
- удалить и заново merge (если расхождение source-профилей значительное)
- если состав группы расширяется (≥3 человек) — новый merge в файл с
  другим именем

### 9.10 MERGE: один из source-профилей обновился после merge

Merged профиль **не пересчитывается автоматически**. Если `алексей`
обновился, `алексей_мария` продолжает работать со старыми данными
`алексей` на момент merge. Это аналог `profile drift` из SKILL.md —
явное предупреждение пользователю при следующем использовании, не
auto-recompute.

Чтобы синхронизировать — пересоздать merged профиль через MERGE
(старый удалить или перезаписать).

### 9.10.5 MERGE через DOCX-анкеты

Альтернативный сценарий: вместо двух уже существующих
`profiles/X.md` + `profiles/Y.md` пользователь подаёт **DOCX-анкеты**
(заполненные в Word, см. §10). Это удобно когда:
- один из участников ещё не имеет собственного `profile.md` —
  его анкета сразу идёт в merge без промежуточного сохранения;
- анкета пришла от другого человека текстом, без его профиля в
  `profiles/`.

Запуск:
```bash
python3 scripts/profile/anketa.py merge \
    /path/to/анкета_алексей.docx \
    /path/to/анкета_мария.docx \
    --profile-id алексей_мария \
  > /tmp/алексей_мария.md
```

CLI принимает любую комбинацию `.docx` (через `parse_docx`) и `.md`
(через `parse_profile_md`). Внутри тот же `merge_answers()`
по правилам §4.1, тот же ASK-список идёт в stderr (для скилла —
показывает пользователю в чате как batch уточнений).

### 9.11 MERGE ≥3 профилей

Поддерживается. MIN и STRICTER применяются к самой ограничительной
версии из всех. UNION складывает все. ASK-вопросов становится больше
(каждый разнящийся параметр от каждого source).

`profile_id`: владелец первым (если в группе), остальные по алфавиту:
`алексей_мария_дмитрий`. Если имя получается длинным (>40 символов) —
сократить до «инициаторов» с пометкой состава в YAML:
`алексей_друзья_2026.md` + перечисление в первой строке тела профиля.

Но: новые секции не подхватываются автоматически стадиями. Они полезны
для контекста, но если хочется, чтобы стадия учитывала «собаку», нужно
явно упомянуть в `Состав группы` или `Явные исключения`.

## 10. EXPORT_FORM / IMPORT_FORM — анкета через DOCX

Альтернатива one-batch interaction в чате: пользователь получает
анкету в Word, заполняет offline и присылает обратно. Удобно когда:
- профиль большой и заполнение в чате утомительно,
- анкету заполняет другой человек (родители, партнёр, друг),
- хочется сохранить заполненную анкету как артефакт переписки.

### 10.1 EXPORT_FORM — генерация DOCX

#### Под-режим A — пустая анкета (CREATE flow)

Триггеры: «дай анкету для нового профиля», «экспортируй пустую анкету»,
«нужна форма для создания профиля».

Запуск:
```bash
python3 skills/travel-planning/scripts/profile/anketa.py export \
    --output {travel_root}/profiles/анкета_новая_{YYYY-MM-DD}.docx
```

Скилл выдаёт пользователю одной строкой путь к сохранённому файлу.
DOCX содержит 17 секций (все из §7.2 + архетип §7.5 + опц.
«Дополнительно» §9.7), все строки `Ответ:` пустые, чекбоксы `[ ]`.

#### Под-режим B — предзаполненная анкета (UPDATE flow)

Триггеры: «выгрузи анкету для правки профиля X», «дай DOCX для
редактирования алексей», «сделай анкету на базе профиля X».

```bash
python3 skills/travel-planning/scripts/profile/anketa.py export \
    --profile {travel_root}/profiles/{profile_id}.md \
    --output {travel_root}/profiles/анкета_{profile_id}_правка_{YYYY-MM-DD}.docx
```

Скилл читает существующий профиль через
`profile_md_parser.parse_profile_md`, который извлекает значения по
секциям best-effort и возвращает `answers: dict[qid → answer]`.
Builder подставляет ответы в `Ответ:` строки и проставляет `[x]` на
соответствующих опциях. Если в исходной строке профиля есть
clarification (например `Класс размещения: средний (недорогие отели
…)`) — оно попадает в скобки после варианта: `[x] средний (недорогие
отели …)`.

Шапка DOCX содержит маркер источника:
> travel-planning · правка профиля «алексей»
> предзаполнено из текущей версии профиля от 2026-05-25

### 10.2 Структура DOCX (контракт с парсером)

DOCX-builder и DOCX-parser договорены через единую spec
`scripts/profile/anketa_spec.py`. Контракт:

**Для каждого вопроса:**
- параграф, начинающийся с `Вопрос: `, далее текст вопроса (bold);
- опц. параграф-hint italic grey (пример/что подразумевается);
- для choice-вопросов — блок `Пояснения:` + строки `— значение: описание`;
- для choice — строка `Выбери один [или несколько] (поставь «x» в скобках):`;
- для choice — строки `[ ] значение` или `[x] значение (опц. clarification)`;
- для text — параграф `Ответ: <текст пользователя>`.

**Якоря парсера:**
- `_QUESTION_RE = r"^\s*Вопрос:\s*(.+?)\s*$"` — старт нового вопроса;
- `_ANSWER_RE = r"^\s*Ответ:\s*(.*?)\s*$"` — свободный текст;
- `_CHECKBOX_RE = r"^\s*\[\s*([xXхХ✓\s])\s*\]\s+(.+?)\s*$"` —
  чекбокс (поддерживает русское «х», латинскую «x», галочку);
- уточнение в круглых скобках после варианта: `\[(x| )\] значение (clar)`.

Сопоставление вопроса с qid из spec — по нормализованному тексту:
точное совпадение → префикс → жаккардова мера ≥0.5. Это устойчиво к
ручному добавлению/удалению нумерации секций в Word.

### 10.3 IMPORT_FORM — DOCX → profile.md

Триггеры: пользователь прикладывает DOCX в чат и пишет «обнови профиль
из анкеты» / «создай профиль из этой анкеты» / просто «вот заполненная».

Поток:
1. Скилл резолвит `profile_id`:
   - из имени файла (`анкета_алексей_правка_*.docx` → `алексей`),
   - либо спрашивает одной строкой если не очевиден.
2. Если профиль с этим id уже существует — Read его для:
   - сохранения исходной даты `created:`,
   - сравнения diff'а перед перезаписью.
3. Запуск:
   ```bash
   python3 skills/travel-planning/scripts/profile/anketa.py import \
       --input /path/to/filled.docx \
       --profile-id алексей \
       --merge-with {travel_root}/profiles/алексей.md \
       > /tmp/алексей_new.md
   ```
4. `anketa.py import` вызывает в этой последовательности:
   - `anketa_docx_parser.parse_docx(path)` → `answers + warnings`,
   - `profile_assembler.assemble_profile_md(answers, profile_id,
     created, updated=today)` → `(markdown, warnings)`.
5. Скилл выдаёт markdown в чат вместе с блоком «Сохранить как» по
   `storage-and-naming.md` §9 и пометкой «**перезапись** существующего»
   или «**новый файл**».
6. Все warnings парсера и ассемблера показываются пользователю списком
   ДО блока markdown (валидация: отсутствующий обязательный архетип,
   неузнанное значение опции, и т.п.).

### 10.4 Round-trip и его границы

Полный pipeline `profile.md → DOCX → profile.md` валидирован на профиле
`алексей.md` (см. `tests/test_anketa.py`). Гарантия — **семантическая
эквивалентность**, не байт-в-байт:

- все [ОБЯЗАТЕЛЬНО] и [ВАЖНО] поля сохраняются с точностью до выбранного
  варианта и текста уточнения;
- multi-choice опции сохраняются как set (порядок может меняться);
- архетип сохраняется точно;
- свободный текст в `Ядро интересов`, `Явные исключения`, `Опыт поездок`
  может ремется (потеря `**bold**` маркеров, переноса строк, конкретного
  деления на буллеты), но **содержание** не теряется.

**Известные потери при round-trip:**
1. **Markdown форматирование в свободных секциях.** `**Европа:** …`
   становится `Европа: …`. `*курсив*` теряется.
2. **Дробление буллетов.** Длинный буллет с подпунктами через `;` при
   ре-сборке может стать одним пунктом или несколькими — детерминированно,
   но не идентично оригиналу.
3. **Custom-секции вне 17 стандартных** (см. §9.7 «нестандартные
   секции») попадают в свободный текст последней секции
   «Дополнительно» — без разделения на отдельный H2.

Это **сознательная граница**: анкета моделирует «90% полей с
семантической структурой + 10% свободного контекста». Для случаев,
где пользователю важно сохранить уникальное markdown-форматирование —
рекомендуем редактировать `profile.md` напрямую через UPDATE в чате,
а не через DOCX round-trip.

### 10.5 Backward-compat: legacy архетип `родители_60_плюс`

Архетип `родители_60_плюс` был переименован в `взрослые_50_плюс`
(акцент на стиль, не возраст; возраст вынесен в отдельную секцию 2).

При `parse_profile_md` для legacy-профиля скилл:
- автоматически конвертирует `родители_60_плюс` → `взрослые_50_плюс`,
- DOCX рендерится с правильным новым архетипом,
- при IMPORT новый профиль пишется с `группа_архетип: взрослые_50_плюс`
  → старое имя постепенно вымывается из библиотеки.

Stage 1/2 толерантны: если они встречают legacy-архетип в YAML — fallback
работает по правилам §7.5 (deprecated alias).

### 10.6 Edge cases

| Случай | Поведение |
|---|---|
| Пользователь не отметил ни одной опции в `[ОБЯЗАТЕЛЬНО]` choice-вопросе (например, архетип) | Ассемблер пишет warning + fallback `самостоятельные`. Скилл показывает warning пользователю **до** блока markdown — пользователь сам решает: сохранить с дефолтом или исправить анкету и переслать. |
| Пользователь отметил `[x]` сразу на 2+ опциях в single-choice вопросе | DOCX-parser сохраняет первый и warning: «выбрано N опций при типе single — взята первая». |
| Пользователь написал значение опции своими словами (не точно из spec) | Парсер пробует нормализованное совпадение и префикс. Если не нашлось — warning «значение X не из набора». |
| Перепутали `[x]` и `х` (русская/латинская/✓) | Парсер принимает все три варианта. |
| Изменён порядок секций в Word | Не влияет: парсер идёт по тексту вопроса (`Вопрос: …`), а не по позиции. |
| Удалили целую секцию | Соответствующие qid не попадут в answers — секция выпадет из финального profile.md. Если [ОБЯЗАТЕЛЬНО] — ассемблер пишет `- TODO: заполнить (обязательная секция)`. |
| Имя файла не подходит под `анкета_*.docx` | Парсер не падает — он работает с содержимым, не с именем. |

### 10.7 Имена файлов

DOCX-анкета:
- `анкета_новая_{YYYY-MM-DD}.docx` — пустая,
- `анкета_{profile_id}_правка_{YYYY-MM-DD}.docx` — предзаполненная.

Папка по умолчанию — `{travel_root}/profiles/`. Не обязательно: скилл
может сохранить в любую папку по запросу пользователя.

Финальный profile.md (после IMPORT) — обычное имя
`profiles/{profile_id}.md`, как при CREATE/UPDATE в чате.
