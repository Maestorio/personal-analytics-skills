# stage1-dr-prompt.md

Полная спецификация Stage 1 — подготовка DR-базы отчётов. Два режима:

- **Режим A — генерация DR-промта.** Скилл выдаёт готовый промт для
  запуска Deep Research в отдельной сессии. Пользователь запускает DR
  сам и сохраняет результат как `1_dr_reports.md`.
- **Режим B — расширение готовой DR-выборки своими отчётами.** После DR
  пользователь может добавить найденные отдельно отчёты (URLs или
  цитаты). Скилл прогоняет их через ту же 20-field структуру и сливает
  с существующим файлом.

Философия и место в пайплайне — `../methodology.md` §3 «Stage 1».

## 1. Назначение

Подготовить DR-базу отчётов для последующего similarity-фильтра (Stage 2).

**Режим A** — основной: подготовить промт для Deep Research, который
соберёт **20-30 отчётов** независимых путешественников по выбранным
регионам — широкую разнородную выборку без фильтрации. Скилл сам DR не
запускает — пользователь запускает в отдельной DR-сессии.

**Режим B** — дополнительный: пользователь после DR может найти ещё
несколько отчётов (например, в источниках, которые DR не индексирует;
свои bookmark'и; рекомендации друзей). Скилл прогоняет эти отчёты через
ту же 20-field структуру (используя web_fetch для URL и встроенное знание
для текста), сливает с существующим `1_dr_reports.md` и пересчитывает
META-DIAGNOSTICS.

Зачем сохранять выборку широкой и без фильтрации:

- Если DR начнёт сам отбирать «лучшие» отчёты, он применит свой неявный
  критерий (популярность, рейтинг) — и потеряет OUTLIER авторов с
  ценными сигналами (критика переоценённых мест, упоминания редких
  локаций). Это разрушает работу Stage 3 (POI categorization).
- Фильтр по профилю прозрачно применяется на Stage 2, на уже собранной
  выборке. Видно распределение по категориям и можно проверить
  репрезентативность.

## 2. Inputs / Outputs

**Inputs:**

- Запрос пользователя (либо ссылка на готовый Stage 0, либо явные regions)
- Stage 0 артефакт `{travel_root}/trips/{trip_id}/0_scope.md` (если есть)
- Профиль `{travel_root}/profiles/{profile_id}.md`

**Outputs:**

- **В чат** — готовый промт для копирования в отдельную DR-сессию
- **Артефакт в файловой системе** — `1_dr_reports.md`, который пользователь
  сохранит САМ после прогона DR. Скилл выдаёт YAML-шапку и инструкцию
  «приклей DR-output ниже шапки и сохрани».

**Downstream:** Stage 2 (similarity filter) читает `1_dr_reports.md` как
вход.

## 3. Поток

### Режим A — генерация DR-промта

Сначала определи sub-вариант по наличию Stage 0 артефакта.

#### A.со-Stage-0 — 2 turn'а

##### Turn 1 — пользователь
«дай промт Stage 1», «scope готов для {trip_id}», «нужен DR-промт».

##### Turn 2 — скилл

1. Read `{travel_root}/trips/{trip_id}/0_scope.md`.
2. **Определить версию схемы** по YAML `schema_version`:
   - **v2 (Stage 0 v2):** primary поле — `longlist[]` (6-8 регионов с
     reserve pairs). Stage 1 запускает DR **по всему longlist'у**,
     включая reserve. Все регионы получают coverage в выборке.
   - **v1 (legacy):** primary поле — `selected_regions[]` (3-5 финальных
     регионов из ## Решение). Stage 1 запускает DR по selected_regions.
3. Извлечь из YAML (по схеме):
   - **v2:** `longlist[]` → `{regions_list_with_descriptions}`,
     `tempo`, `country_quota`, `trip_format`.
   - **v1:** `selected_regions[]` → `{regions_list_with_descriptions}`.
   - Общие: `season`, `duration_nights`, `travelers_profile`,
     `pre_committed_places`, `trip_wishes`.

**Если v2 YAML невалидный** (нет `longlist[]`, или пустой): отказать —
«Stage 0 v2 не завершён или longlist пустой. Запусти Stage 0 заново».

**Если v1 без `selected_regions`** (legacy): отказать как раньше — «блок
`## Решение` Stage 0 не заполнен или `selected_regions:` null».
4. Read профиля. Извлечь `группа_архетип` из YAML профиля.
   - Если поле есть и валидное (одно из 4 значений; legacy-имя
     `независимые_соло_пара` = `самостоятельные`) — использовать
     каноническое имя.
   - Если поле отсутствует или невалидное — фолбэк
     `самостоятельные` + одна строка-warning пользователю
     («профиль не содержит `группа_архетип`, используется
     `самостоятельные` по умолчанию; обнови профиль для
     других калибровок»).
5. **Резолв `{seed_source_set}`.** По резолвленному `группа_архетип`
   найти соответствующую строку в `references/profile-management.md`
   §7.5 (раздел «Seed source-set DR-выборки (Stage 1)»). Подставить
   в плейсхолдер `{seed_source_set}` шаблона §6 — целым блоком (рус +
   англ + опц. фото для архетипа). Не сокращать, не выдумывать
   источники сверх таблицы (open-ended-расширение — задача DR-агента
   на следующем шаге, не скилла).
6. Подставить остальные плейсхолдеры в шаблон промта (§6) — включая
   `{группа_архетип}`, `{regions_list_with_descriptions}`,
   `{season_year}`, `{duration_nights}`, `{season_specific_features}`,
   `{recency_window}`, `{trip_wishes}`.
7. Выдать промт в чат + инструкцию по запуску DR + шаблон YAML-шапки
   для будущего файла.

#### A.без-Stage-0 — 2 или 4 turn'а

Применим когда:

- Scope очевиден без анализа (небольшая страна целиком: Камбоджа,
  Лаос, Шри Ланка, Бутан, Хоккайдо, Грузия — DR покроет всю страну
  без региональной декомпозиции; либо один город).
- Пользователь явно перечисляет регионы (повторная поездка, жёсткие
  предпочтения).

##### Turn 1 — пользователь
«дай DR-промт для {страна} на {N} ночей в {месяц}, профиль {profile_id}»

##### Turn 2 — скилл

**Если вход полный** (scope + season + duration + profile_id):
- Read профиля → извлечь `группа_архетип` (fallback `самостоятельные`
  с warning при отсутствии; legacy `независимые_соло_пара` резолвится в него же).
- Резолвить `{seed_source_set}` по архетипу из `references/profile-management.md` §7.5.
- Подставить остальные плейсхолдеры → выдать промт.

**Если вход неполный** — ОДИН batch уточнений (см. §4), потом Turn 4
как выше.

#### A.wrap — обработка вернувшегося DR-файла

**Когда применяется:** пользователь после Mode A.Phase 1 (получил
DR-промт, запустил его в отдельной DR-сессии) возвращается в чат с
**готовым DR-output файлом** и просит «заполни YAML шапку» или
«оформи в 1_dr_reports.md». Опционально с дополнительным запросом B1
по awd.ru (см. §7.2 Mode B).

Это **не** новая стадия — это **Phase 2 Mode A** (wrap-up после
внешнего DR-прогона).

##### Turn 1 — пользователь
Прикладывает DR-файл (через upload, paste, либо ссылку на сохранённый
артефакт в travel_root). Опционально: «найди ещё на awd.ru», «сделай
B1».

##### Turn 2 — скилл

1. Read приложенный DR-файл целиком.
2. Read `0_scope.md` (если доступен) или derive контекст из запроса.
3. Read профиля для `группа_архетип` и `travelers_profile` path.
4. Извлечь из META-DIAGNOSTICS DR-файла:
   - `reports_count` (число карточек)
   - регионы и их coverage
   - WARNING-флаги (sample skew, missing local-language, POI-критика
     per region per F-23)
4.5. **Канонизация структуры + валидация (gate перед эмитом).**
   DR-агент размечает карточки по-разному (`**КАРТОЧКА N**` bold vs
   `## КАРТОЧКА N` heading) и разделители (`---` vs `-----`). Без
   приведения к канону Stage 2-парсер и экспорт-парсер спотыкаются
   (региональные заголовки распознаются как карточки, выдержки/авторы
   теряются). Поэтому ПЕРЕД эмитом:
   - **Bash доступен:** канонизировать —
     `python3 scripts/parse_dr_cards.py --normalize < dr_raw.md > dr_canon.md`.
     Маркеры → `## КАРТОЧКА N` (сквозная нумерация по порядку документа),
     разделители `-{3,}` убраны; контент карточек, region-заголовки, META
     и аннотации (`tonality: critical`, `multi-region`, `[B1 awd.ru: …]`)
     сохраняются дословно. **`--normalize` сам себя проверяет:** если он не
     распознал ни одного маркера или часть осталась неканонизированной —
     выходит с кодом 1 и пишет причину в stderr. Это сигнал «формат не тот»:
     разобраться, **почему** (тот ли файл? нестандартные маркеры?), а не
     эмитить странный результат. Затем валидировать (emit-gate):
     `python3 scripts/parse_dr_cards.py --trip-slug {slug} --require-count < dr_canon.md` —
     сверить `total_cards` с `reports_count`. `--require-count` делает
     `reports_count` обязательным: `diagnostic.status=error` при >20% без URL,
     крупном расхождении count, **ИЛИ** отсутствии top-level `reports_count`
     (`count_required_missing` — поле отсутствует / плейсхолдер `N` / съехало
     под список `regions:` и стало вложенным). Любой error → не эмитить молча:
     проставить корректный top-level `reports_count: N` и перепрогнать;
     крупное расхождение count/URL → §9.12 (opt-in LLM-fallback). Дальше
     эмитить **dr_canon.md**.
     - *(Опц. лёгкая доп-сверка:* `python3 scripts/check_format.py --stage 1
       < dr_canon.md` — делиметр + `reports_count` == числу маркеров карточек.
       Комплементарна `--require-count` выше; не замена.*)*
   - **Bash недоступен:** канонизацию пропустить (downstream-парсеры
     терпимы к bold-маркерам и `-----`), но в Message 2 пометить одной
     строкой «структура карточек не канонизирована — нет Bash».
   **Важно:** `--normalize` перенумеровывает карточки по порядку
   документа. Запускать ТОЛЬКО здесь, на Stage 1, ДО Stage 2 — после
   Stage 2/3 номера карточек уже зашиты в similarity/POI, повторная
   канонизация их рассинхронизирует.
5. Опционально — если запрошен B1 (поиск awd.ru):
   - Запустить B1 discovery по §7.2.1 — `scripts/fetch_awd.py`,
     если доступен.
   - **Если scripts/ недоступен** (claude.ai chat без Bash tool): попытать
     `web_search site:forum.awd.ru` + `web_fetch`. **Если BPC-challenge
     блокирует** (типовая ситуация в claude.ai chat — BPC требует
     local execution через fetch_awd.py): per §9.11 — «B1 не найдено»,
     никаких балластных карточек.
6. **Эмитить готовый `1_dr_reports.md` целиком одним markdown-блоком**
   в чат — YAML-шапка склеена с DR-content от пользователя (не отдельным
   YAML-блоком с просьбой «вставь руками»).

##### Структура output (Phase 2 Mode A)

Per Class G output discipline — **раздельные сообщения**:

**Message 1 — готовый артефакт целиком:**

```markdown
---
trip_id: {trip_id}
stage: 1_dr_reports
schema_version: 1
travelers_profile: profiles/{profile_id}.md
regions:
  - "{регион 1 из longlist Stage 0 v2 или из запроса}"
  - "{регион 2}"
  - ...
season: {season_descriptor}
dr_run_date: {YYYY-MM-DD реального прогона DR; если дата неизвестна —
              today's date, а пометку retrospective вынести в коммент
              `# retrospective`, НЕ вторым двоеточием в значении}
reports_count: {N из META-DIAGNOSTICS}
meta_diagnostics_warnings:
  - "WARN-{N}: {one-line описание}"
  - ...
  - "B1-awd.ru: {result}" ← если B1 запрошен
created: YYYY-MM-DD
---

[полный DR-content — карточки и META-DIAGNOSTICS. Канонизированный по
§A.wrap-шагу 4.5 (если был Bash), иначе как есть. Контент не сокращать.]
```

**Message 2 — save instruction + summary:**

```
Сохрани как `{travel_root}/trips/{trip_id}/1_dr_reports.md`.
Папку `trips/{trip_id}/` создай если не существует.

Ключевые сигналы Stage 1:
- {1-3 пункта: WARN-флаги, B1 status, что особо важно для downstream}

Готов к Stage 2: `/travel-planning stage 2 для {trip_id}` —
приложи 1_dr_reports.md и {profile_id}.md.
```

##### Важно

- **НЕ выдавать YAML-блок отдельно с просьбой «вставь руками»** — это
  uesless step для пользователя, и spec §3 §7.1.3 формально допускал
  такое только для Phase 1 (где DR ещё не прогонялся и body будет
  заполнен извне).
- **НЕ сокращать DR-content** даже если он длинный. 37+ карточек = норма.
  Если совсем не помещается в один turn — разбить на 2 turn'а в
  Message 1 («part_a», «part_b»), но **per Class G** save instruction
  идёт отдельным сообщением **после** обеих частей, не вместе.
- **`dr_run_date` обработка:** если в DR-файле явно зафиксирован — взять
  оттуда. Если не зафиксирован — использовать today's date с пояснением
  в Message 2 («`dr_run_date` поставлен как today; если фактический
  прогон был раньше — поправь вручную»).
- **B1 поиск** — опционально, **только если пользователь явно попросил**.
  Не запускать B1 по умолчанию.

### Режим B — расширение готовой DR-выборки

Применим когда у пользователя уже есть DR-файл от Режима A + DR-прогон,
и он хочет добавить отчёты в ту же базу с консистентной 20-field
структурой. Два опциональных под-режима, могут идти вместе или порознь:

- **B1 — discovery на forum.awd.ru** по тематике поездки (DR не открывает
  этот источник из-за BPC-challenge).
- **B2 — пользовательские URL** (любой ресурс, который пользователь
  принёс руками).

Минимум одно из B1/B2 должно быть указано. Детали — в §7.2.

#### Turn 1 — пользователь

Возможные формы запроса:

- **B1 only:** «посмотри ещё на Винском по этой поездке», «добавь
  отчётов с awd.ru», «найди что-нибудь актуальное на форуме Винского».
- **B2 only:** «добавь к Stage 1 эти отчёты: [URL1, URL2, ...]»;
  цитата или приложенный файл с готовым контентом.
- **B1 + B2:** «вот ссылка X, плюс посмотри ещё на awd.ru».

В Turn 1 пользователь также прикладывает / указывает путь к
**main_dr_file** (либо upload через интерфейс, либо явный путь к
`1_dr_reports.md`).

#### Turn 2 — скилл

1. Read main_dr_file, прочитать YAML (regions, season, trip_id) и
   список карточек (для дедупликации по URL в поле 1).
2. Определить, какие под-режимы активны (B1, B2 или оба) по содержимому
   запроса пользователя.
3. Выполнить активные под-режимы (детали в §7.2.1 / §7.2.2):
   - B1: discovery через `scripts/fetch_awd.py --list-subforums` →
     `--list-topics` → отбор 0-3 кандидатов → fetch `--all-posts
     --author-only` → разбор в 20-field.
   - B2: для каждого URL → fetch (awd.ru через `fetch_awd.py`,
     остальное через `web_fetch` / Chrome MCP) → разбор в 20-field.
4. Собрать additions во временный `/tmp/_dr_additions_*.md` (не
   сохраняется в outputs).
5. Прогнать merge: `scripts/merge_dr_additions.py main_dr_file
   /tmp/_dr_additions_*.md -o /tmp/_dr_merged_*.md`, скопировать
   результат в outputs скилла, удалить temp.
5.5. **Записать `mode_b_decisions` в YAML-шапку merged-файла** (провенанс
   довыборки — чтобы база воспроизводилась с диска, а не из памяти чата).
   Скрипт merge пересчитывает `reports_count`, но решения Mode B — зона LLM;
   добавить блок руками в шапку (схема — `../storage-and-naming.md` §6.2):
   `submodes` (какие из b1/b2 запускались), `scope_filter` (принятое решение
   по off-scope отчётам), `added` (карточек по происхождению), `awd_themes`
   (ID тем forum.awd.ru, если был b1), `dropped` (что отброшено и почему).
   Без блока перезапуск Stage 1 с диска не воспроизведёт состав базы.
6. Выдать пользователю краткое тезисное summary (что нашли + сколько)
   + `computer://`-ссылку на финальный merged. Никаких полных YAML или
   META-DIAGNOSTICS в чате — всё в файле.

**Стоп.** B1 не «добирает» отчёты без явного запроса пользователя.
B1 агрессивно фильтрует — лучше ничего не добавить, чем добавить
балласт.

## 4. Gate-проверки на входе

### 4.1 Для Режима A (генерация промта)

| Что | Обязательно | Источник | Если не задано |
|---|---|---|---|
| `scope` (список регионов ИЛИ вся страна) | да | Stage 0 блок `## Решение` (primary) → YAML (fallback) → inline | см. §9.1/§9.2 |
| `season` | да | Stage 0 YAML ИЛИ inline | спросить (формат `YYYY-{descriptor}` или конкретный месяц + год) |
| `duration_nights` | да | Stage 0 YAML ИЛИ inline | спросить |
| `profile_id` / `profile_path` | да | Stage 0 YAML ИЛИ inline | предложить из существующих |
| `trip_id` | да (можно сгенерировать) | Stage 0 или inline | предложить по конвенции `../storage-and-naming.md` §3.2 |
| `pre_committed_places` | нет | Stage 0 YAML | принять пустой список |

**Про `scope`:** primary источник — блок `## Решение` в `0_scope.md` (см. §9.2).
YAML `selected_regions:` — производный кэш, читается только если совпадает
с блоком (быстрый путь). Расхождения и null в YAML — не блокируют, блок
всегда важнее.

**Эвристика для scope = «страна без подразбиения»:**

Не блокирующее правило. Принять как валидный scope, опционально дать
мягкую рекомендацию по Stage 0.

- **Принимать молча** (без рекомендации Stage 0): небольшие или
  географически узкие направления, типично разумно охватываемые в
  одном DR-прогоне — Камбоджа, Лаос, Шри Ланка, Бутан, Хоккайдо
  (как остров), Грузия, Армения, Уругвай, Эстония, Албания, Косово,
  Мальта, Кипр, Сингапур и аналогичные. DR на них вернёт отчёты по
  всей стране без потери на широте scope.
- **Принять с мягкой рекомендацией** (одна строка «scope широкий —
  Stage 0 поможет сузить, но проходим если уверен»): крупные
  multi-region страны — Россия, Китай, Бразилия, США, Австралия,
  Индия, Индонезия (распределённая по островам), Канада, Аргентина
  целиком, Мексика.
- **Один город** (Прага, Стамбул, Куала-Лумпур): валидный scope,
  DR соберёт отчёты по районам и маршрутам внутри города.

Решение пользователя финально — скилл не гейткипер, а помощник.

### 4.2 Для Режима B (добавление отчётов)

| Что | Обязательно | Источник | Если не задано |
|---|---|---|---|
| `main_dr_file` (готовый DR-файл) | да | upload, путь в запросе ИЛИ `{travel_root}/trips/{trip_id}/1_dr_reports.md` | отказать: «нет main_dr_file — запусти сначала Режим A → DR» |
| Триггер B1 ИЛИ B2 (минимум один) | да | формулировка пользователя ИЛИ список URL в запросе | отказать: «нужен либо запрос discovery awd.ru, либо хотя бы одна ссылка» |
| `trip_id` | желательно | YAML main_dr_file ИЛИ запрос | если нет — для discovery (B1) использовать regions/season из main_dr_file напрямую |

**Особый случай: Режим B без существующего DR-файла.**

Если пользователь хочет добавить отчёты, но main_dr_file отсутствует —
это не «расширение», а «создание с нуля». Реакция: предложить два
варианта:
- «Создать `1_dr_reports.md` целиком из твоих отчётов?» (применить
  20-field структуру ко всем) — корректно, но META-DIAGNOSTICS
  деградирует (мало отчётов, выборка не контролируется), отметить
  явно как warning.
- «Запустить полноценный Режим A для широкой выборки сначала?» —
  рекомендуемый путь.

### 5.1 Language targeting — вычисление `{language_targeting}` (F-62 v4)

Mode A (Sonnet base, без thinking) собирает target language set перед
финальной подстановкой плейсхолдеров. Алгоритм:

1. **Target languages set** = `{home_lang, en, dest_country_langs, neighbor_country_langs}`:
   - `home_lang` — из YAML профиля (текущая версия скилла: `ru`).
   - `en` — всегда (default international coverage).
   - `dest_country_langs` — официальные + крупные региональные языки **всех**
     стран из `country_quota` Stage 0. LLM выводит из general knowledge:
     - Корея → `ko`
     - Вьетнам → `vi`
     - Морокко → `ar`, `fr` (берберский — мало online)
     - Индия → `hi`, `en` (en native, не дублирует)
     - Перу/Боливия/Чили → `es`
     - Танзания/Кения → `sw` (мало online), `en` native
     - Парагвай → `es`, `gn` (мало online)
   - `neighbor_country_langs` — если в `country_quota` есть транзитные/
     соседние страны (Бангкок-транзит для Камбоджи → добавить `th`).

2. **Examples в DR-промте — только для широко известных стабильных
   платформ на 4 языках, верифицированных на момент v0.25 spec'а.**
   Mode A LLM включает в промт **закреплённый** список ниже, без
   попыток «обогатить» его dynamic discovery (валидировано: модель
   выдумывает несуществующий «forum.винского.ru» — реальный Vinsky
   forum хостится на `forum.awd.ru` и отдельного домена не имеет).

   **Закреплённый список (Mode A копирует as-is):**

   | Язык | Платформы | Тип контента |
   |---|---|---|
   | **ru** (Russian) | `tourister.ru`, `otzyv.ru` | Travel community + trip reports + photo albums |
   | **en** (English) | `tripadvisor.com` (forums), `reddit.com/r/travel`, `wikivoyage.org` | Forums + crowdsourced guides |
   | **ja** (Japanese) | `4travel.jp`, `jalan.net` | Travelogues 850K+ entries + reviews |

   Mode A включает только секцию для языков в target set. Если language
   не в этой таблице (zh / kh / lo / sw / gn / mn / hi / vi / ko / th / etc.)
   — оставляет discovery DR: «Find current major travel resources на этом
   языке — не выдумывай несуществующие платформы».

   **Notes по конкретным языкам, для которых pinning не сделано:**

   - **zh (Chinese):** существуют major платформы (mafengwo.cn 马蜂窝,
     qyer.com 穷游) но **anti-bot защита непредсказуема**: server-side
     fetches могут проходить, а scaled DR-запросы триггерят CAPTCHA /
     rate-limits. Оставлено в discovery-режиме с caveat — DR пытается,
     accept partial coverage если CAPTCHA.
   - **ko (Korean):** Naver Blog, Daum tistory — существуют, но closed
     ecosystems с ограниченным indexing для non-Korean search engines.
     Discovery.
   - Остальные — pinning неоправдан в данный момент.

3. **Явные exclusions — URL'ы, которые DR НЕ должен fetch'ить:**

   - **`forum.awd.ru`** (форум Винского) — BPC-challenge, DR-tools
     (Gemini/Perplexity/Claude) получают redirect-страницы вместо
     контента. Awd покрывается отдельной стадией через `fetch_awd.py`
     (Mode B B1). LLM явно инструктирует DR игнорировать awd.ru-ссылки
     в индексе.
   - Другие сайты с BPC/CF challenge при обнаружении — добавляются в
     этот список по мере накопления опыта.

4. **При расширении/обновлении закреплённого списка — обязательная
   двойная верификация.** Domain hallucinations (`forum.винского.ru`) и
   тихие anti-bot блоки (`mafengwo.cn` server-fetch проходит, браузер
   получает CAPTCHA) — реальные риски. Перед pinning'ом:

   - **Server-side check:** WebFetch на главную страницу — не должно быть
     403/503/redirects.
   - **Browser-side check:** **попросить пользователя** открыть сайт в
     обычном браузере и подтвердить отсутствие CAPTCHA / login wall.
     WebFetch недостаточно — есть anti-bot защиты, которые селективно
     срабатывают (`mafengwo.cn`).
   - **Stability check:** платформа должна существовать ≥ 5 лет, иметь
     активную user base. Молодые/маргинальные сайты — не pin.

   Если хотя бы одна проверка не пройдена — не pin, оставлять в discovery.

5. **Format `{language_targeting}` блока:**

   Mode A собирает блок из закреплённой таблицы (п.2) для target languages
   + DR-discovery инструкция для языков вне таблицы.

   Пример (target_languages = `[ru, en, ko, th]`; ko/th — не в закреплённой
   таблице, значит DR делает discovery):

   ```
   Source priority — поиск на следующих языках:

   - **Russian (язык пользователя):**
     Major travel resources: tourister.ru (travel community + photo albums),
     otzyv.ru (отзывы туристов).
     ВАЖНО: НЕ пытайся fetch'ить forum.awd.ru — этот форум защищён
     BPC-challenge, DR-tools (Gemini/Perplexity/Claude) получают только
     redirect-страницы вместо контента. Awd покрывается отдельной стадией
     пайплайна через локальный fetch — игнорируй awd-результаты, даже
     если они появляются в индексе.

   - **English (default international):**
     tripadvisor.com (forums), reddit.com/r/travel, wikivoyage.org;
     individual traveler blogs (Medium, Substack), blog aggregators.

   - **Korean (язык страны destination):**
     Найди actual current major travel resources на этом языке — не
     выдумывай несуществующие платформы.

   - **Thai (язык транзитной страны):**
     Найди actual current major travel resources на этом языке — не
     выдумывай несуществующие платформы.

   Если для какого-то target language platforms не находятся (niche destination
   или редкоязычный регион — Камбоджа, Лаос, Бутан, etc.) — accept English
   coverage, **не выдумывай** платформы и не списывай первое попавшееся.
   ```

   Для `target_languages = [ru, en, ja, zh]` (например, поездка в Японию
   + Тайвань-транзит) — японский и китайский блоки берутся из закреплённой
   таблицы аналогично русскому и английскому, с caveat'ом про возможный
   geo-block для китайских.

6. **YAML output Mode A** (transparency):

   ```yaml
   language_targeting:
     home_language: ru
     default: en
     destination_languages: ["ko"]
     neighbor_languages: ["th"]
     pinned_platforms_used:                  # из закреплённой таблицы п.2
       ru: ["tourister.ru", "otzyv.ru"]
       en: ["tripadvisor.com", "reddit.com/r/travel", "wikivoyage.org"]
     dr_discovery_languages: ["ko", "th"]    # не в закреплённой таблице
     exclusions: ["forum.awd.ru"]            # BPC-blocked, отдельный pipeline
   ```

**Sonnet base справится** — это general knowledge mapping (страна → язык),
явный input (country_quota из Stage 0), и format string substitution. Нет
многоступенчатого reasoning. **Без adaptive thinking.**

**Ambiguous cases** (Вьетнам, Индонезия, Турция — между Rich и Moderate
language landscape): default — включать local language как target,
доверять DR делать discovery. Если platforms не находятся — DR fall back
на English без warning.

`{regions_list_with_descriptions}` форматируется как точки с краткими
описаниями ключевых мест в каждом регионе — это помогает DR искать по
правильным ключевым словам.

## 6. Промт (полный шаблон для DR)

Этот текст подставляется в `{промт}` и выдаётся пользователю как готовый
блок для копирования в DR-сессию.

---

```
**Язык вывода:** отвечать на русском языке. Все названия карточек,
поля, META-DIAGNOSTICS и обоснования — на русском. Цитаты из
англоязычных и местноязычных источников оставляй в оригинале, но
снабжай кратким русским пересказом (1-2 предложения) для каждой
цитаты длиннее одной строки. **Топонимы** — в русской транслитерации
с латинским вариантом в скобках при первом упоминании в карточке
(подробнее — в разделе про 20 полей ниже).

Цель задания: собрать сырую структурированную базу из 20–30 подробных
отчётов независимых путешественников по {regions_list_with_descriptions}.
Это первая стадия многоступенчатого пайплайна планирования поездки;
фильтрацию по личному профилю и построение маршрута я делаю на следующих
стадиях вручную. Поэтому критически важно, чтобы выборка была разнообразной
по стилю путешествий и не была предварительно отфильтрована под
предполагаемые предпочтения читателя.

География: {regions_list_with_descriptions}. Обязательно охватить все
перечисленные регионы; для каждого региона минимум 4 отчёта. **Один отчёт,
покрывающий несколько регионов, считается для каждого из них** (например,
если отчёт покрывает регионы A, B и C — он засчитывается в счётчики
всех трёх). Такие multi-region отчёты особенно ценны — отражают
реальную логику путешествий, а не искусственное разделение.

Сезон поездки: {season_year}, длительность {duration_nights} ночей.
Приоритет отчётам с поездками в тот же сезон, но отчёты о других сезонах
тоже принимаются для оценки самих мест.

{Если {trip_wishes} непуст:}
**Особые пожелания пользователя для этой поездки:** {trip_wishes}.
Это конкретные впечатления или категории активности, которые пользователь
хочет увидеть. **Включи в выборку 2–3 отчёта, упоминающих эти пожелания
позитивно** — этого достаточно (если каждый из этих 2–3 отчётов покрывает
большинство пожеланий, **дополнительно искать не нужно**). 

Принципы поиска по пожеланиям:
- **Гибкость, не якорь.** Не подгоняй всю выборку под пожелания —
  основной критерий по-прежнему репрезентативность по регионам и стилям.
  Пожелания — дополнительный сигнал, не доминанта.
- **Физически невозможные пожелания.** Если пожелание не реализуемо в
  выбранных регионах/сезоне (например, «северное сияние» в южном полушарии
  летом, «пингвины» далеко от ареала, «карнавал» вне дат события) — **не
  пытайся найти отчёты под него**. Отметь невозможность в META-DIAGNOSTICS
  одной строкой: «пожелание `{X}` физически не реализуемо в выборке —
  причина {Y}». Не выдумывай отчёты.
- **Покрытие частичное — нормально.** Если пожелание упомянули только 1
  отчёт — этого хватит как сигнала. Если 0 отчётов — отметь в
  META-DIAGNOSTICS, downstream-стадии разберутся.

Источники для поиска.

**Seed source-set (откалиброван под архетип группы `{группа_архетип}`):**

{seed_source_set}

**Open-ended principle.** Seed-список — рекомендация, не жёсткий
ограничитель. Если ты находишь релевантный контент **вне** seed-списка
(фуд-блог с разовым подробным trip report'ом, photo-substack с серией
про городскую архитектуру, podcast-транскрипт с полезными деталями) —
**включай его в выборку**, при условии что отчёт соответствует
критериям включения (личный опыт, ≥1500 слов, конкретные имена/адреса/
даты). В META-DIAGNOSTICS отметь источники «вне seed-списка» отдельной
строкой — это диагностика того, где seed не докрывал.

**Language targeting (F-62 v4):**

{language_targeting}

Указывай язык исходного источника в карточке (`source_language: vi` /
`ja` / `zh` / etc.) — пользователь применит автоперевод.

**Активный поиск критических отзывов (обязательно).**

Стандартная DR-выборка систематически смещена в сторону «поехали —
понравилось» (selection bias: на туристическую ловушку едут люди,
которые её хотели — они её не критикуют). Это блокирует Stage 3
RED FLAG-генератор downstream. Чтобы этого избежать — **по каждому
региону из `{regions_list_with_descriptions}` найти и включить
минимум 1–2 отчёта с обоснованной критикой**. Не «не понравилось без
причины», а с конкретикой: «переполнено», «переоценено», «вылизано
под туриста», «развод на деньги», «прозападная пьянка», etc.

Search-фразы для критики (русский — основной язык поиска):
- `"разочаровался в {region}"`
- `"зря поехал в {region}"`
- `"{region} переоценён"` / `"{region} переоценено"`
- `"{region} туристическая ловушка"`
- `"{region} развод"` / `"развод в {region}"`
- `"{region} не понравилось"` (фильтровать на содержательность —
  отбрасывать пустые жалобы без причин)

Критику конкретных мест проставлять как тональность `критикует` /
`жалеет о посещении` рядом с этими POI в **поле 14** — именно его
читает RED FLAG-генератор Stage 3. Дополнительно весь отчёт можно
пометить `tonality: critical` в поле 18 — это агрегат «Жалобы и
проблемы» для META-диагностики per region, **не** per-POI сигнал.
Это критическая часть задания — без 1–2 критиков на регион (с критикой
именно в поле 14) RED FLAG-генератор Stage 3 не сработает в
scarce-режиме.

**Фотографические** (применимо если фото-фокус в seed-наборе архетипа):
- Блоги landscape-фотографов с привязкой к региону
- Photo-essays на 500px, Behance, индивидуальных сайтах
- Транскрипты подробных YouTube-влогов (без обзоров отелей)

Критерии включения отчёта:
- Реальный личный опыт автора (не компиляция)
- Минимум 1500 слов или эквивалент по детализации
- Конкретные названия мест, ресторанов, отелей, транспорта
- Явно указанная дата поездки
- Желательно описание маршрута по дням

Критерии исключения:
- Маркетинговые посты туроператоров
- Generic-листиклы без личного опыта («10 must-see places in...»)
- AI-generated контент (признаки: общие фразы, отсутствие сенсорной
  конкретики, идеальная структура без живых деталей, отсутствие проблем
  и неудач, повторяющиеся обороты речи)
- Отзывы об одном отеле
- Посты с обилием партнёрских ссылок и affiliate-маркетинга

Временные рамки: приоритет отчётам {recency_window}, допустимы старые
для мест с устойчивой инфраструктурой. Полностью исключи отчёты старше
12 лет — инфраструктура и регуляции меняются.

Для каждого отчёта извлеки структурированные метаданные. Если поле
определить нельзя — явно напиши «не указано». 20 полей.

**Правило для топонимов (применяется к полям 5, 6, 10, 11, 12, 14,
15, 16):** все названия мест (города, регионы, кварталы, кемпинги,
треки, отели, рестораны) — в **русской транслитерации с латинским
вариантом в скобках при первом упоминании в карточке**. Пример:
«Эль-Чальтен (El Chaltén)», «Лагуна-Капри (Laguna Capri)»,
«Рестораны La Tablita и Rústico», «Хойан (Hội An)». Это критично
для downstream-стадий, где пользователь будет искать места в
Google Maps / Booking / агрегаторах — без латиницы поиск ломается
для не-латиничных названий.

**Структура 20 полей — ЖЁСТКАЯ. Имена и порядок полей канонические,
переименовывать или адаптировать под конкретную поездку ЗАПРЕЩЕНО.**
Без жёсткой структуры DR-агент склонен переименовывать поля 14-20 под
trip-specific темы (sезонные явления, региональные топонимы, узкие
интересы) — это ломает downstream parser и не позволяет агрегировать
карточки между разными trip-кейсами. Никаких сезонных/региональных
кастомизаций структуры. Если содержания для поля нет — пиши `не указано`,
не убирай и не переименовывай.

20 полей (канонические имена):

1. URL и название отчёта
2. Платформа публикации (и язык исходника, если не русский / английский —
   `vi` / `ja` / `zh` / `ko` / `es` / etc.)
3. Имя или ник автора
4. Дата публикации
5. Месяц и год поездки, длительность
6. Сезон с особенностями ({season_specific_features})
7. Состав группы (соло / пара / семья / группа друзей / организованный тур)
8. Возрастной диапазон автора (если можно оценить)
9. Стиль путешествия — один тэг **по-русски**, из списка: бэкпэкер /
   миддл-сегмент самостоятельно / бюджетно самостоятельно / мотобайк
   самостоятельно / люкс / организованный тур / диджитал-номад /
   хардкор-адвенчура / семья / фото-фокус / гастро-фокус / культурное
   погружение / стандартный туристический маршрут / микс
10. Темп (количество локаций, среднее число дней на локацию)
11. Транспорт (байк, easy-rider, ночные автобусы, частные водители,
    тур-группы, поезда, аренда машины)
12. Тип размещения — сегмент **по-русски**: отдельные номера / хоумстей /
    отели / люкс / хостелы с общими спальнями / кемпинг. Имена конкретных
    отелей и сетей — как в оригинале, не переводить
13. Главный фокус автора — один тэг **по-русски**: архитектура / природа /
    культура / фото / гастрономия / приключения / отдых / микс
14. POI с тональностью — полный список упомянутых мест с тональностью
    каждого: рекомендует / нейтрально / критикует / жалеет о посещении /
    жалеет что пропустил
15. Hidden gems — отдельно подсвети «нетуристические» или «hidden gems»
    места из отчёта
16. Логистические заметки автора (что сработало, что нет, лайфхаки)
17. Упоминания диетических ограничений и как справлялся
18. Жалобы и проблемы — переоценённые места, опасности, разводы, погодные
    провалы. **Это про POI-туристические-ловушки**, не про сезонную
    дымку или общие условия (для сезонного — поле 6).
19. Главная рекомендация одной фразой прямой цитатой
20. Признаки фотографических интересов (упоминание оборудования,
    рассветной/закатной съёмки, постобработки)

**Запрет на OUTLIER pre-marking.** Поле «OUTLIER» в карточках НЕ
проставлять, даже если автор кажется явным «не как все». OUTLIER —
это категория Stage 2, которая считается на основе similarity-распределения
после агрегации. Stage 1 даёт сырые карточки, Stage 2 решает OUTLIER.
DR-агенту нельзя класть собственный «OUTLIER» тег ни в одно из 20 полей
— это нарушение разделения LLM/script между стадиями.

Формат вывода: последовательность структурированных карточек по 20 полям.
Если общий объём не помещается — раздели на части, но сохрани единый
формат.

Финальная секция META-DIAGNOSTICS:
- Сколько отчётов всего (с учётом, что multi-region отчёт считается
  в каждом своём регионе). **Согласованность счётчиков:** число в YAML
  `reports_count`, в TL;DR («собрано N отчётов»), и в section header
  `## Полная база отчётов ({N})` **должно совпадать**. Используй
  актуальное число уникальных URL.
- Распределение по стилям путешествия в процентах
- Распределение по сезонам
- Распределение по фокусу автора
- Распределение по языку источника (RU / EN / local-language с разбивкой
  по конкретным языкам)
- **POI-критика per region (отдельно от сезонной).** Для каждого
  региона укажи число отчётов с **POI-критикой** (туристические ловушки,
  переоценённые места, развод, прозападная пьянка — то, что лежит в
  поле 18 карточек). Это **не то же самое**, что сезонная критика
  (дымка, муссон, экстремальные температуры — поле 6). Раздели
  явно: «POI-критика per region: {Регион 1}: 2 отчёта, {Регион 2}: 0
  отчётов, …». Сезонные caveat'ы — отдельной строкой «Сезонные
  предупреждения: дымка в марте-мае (упомянуто N раз)».
- **Источники вне seed-списка:** перечисли платформы / блоги / каналы,
  которые попали в выборку, но не входили в `{seed_source_set}` для
  архетипа `{группа_архетип}`. Это диагностика недокрытия seed.
- Если выборка получилась смещённой (>50% одного стиля или одного фокуса,
  либо <10% отчётов на местном языке для не-европейских направлений,
  либо POI-критика = 0 хотя бы для одного региона) — явно укажи
  как `WARNING: sample skew toward X` или `WARNING: no POI critique
  for region Y` (без POI-критики Stage 3 RED FLAG-генератор не сработает
  в scarce-режиме).
- Перечисли источники, которые пробовал, но не смог использовать (нет
  доступа / контента не нашёл / тип источника не подошёл)

Чего НЕ делать:
- НЕ строй маршрут
- НЕ рекомендуй конкретные места
- НЕ синтезируй «лучшие места»
- НЕ оценивай отчёты по полезности для меня (нет моего профиля, эта
  оценка ошибочна по построению)
- НЕ убирай отчёты с критическими взглядами
- НЕ группируй POI по «обязательно посетить»
- НЕ применяй фильтр «mid-range / backpacker / luxury» — оставь все стили

Если на какой-то платформе очень много отчётов, выбирай разнообразных
авторов, а не «лучших по рейтингу», потому что рейтинговые отчёты
отражают стандартный туристический профиль и потеряют OUTLIER-сигналы,
которые нужны на следующих стадиях.
```

## 7. Правила работы

### 7.1 Режим A — три блока в чат

После подстановки плейсхолдеров скилл выдаёт в чат **три блока**:

#### 7.1.1 Промт

В одном code-блоке (```), чтобы пользователь мог легко скопировать.
**Никаких комментариев внутри code-блока** — только сам промт.

#### 7.1.2 Инструкция по запуску DR

Кратко (3-5 строк):

```markdown
1. Открой новую сессию в режиме Deep Research.
2. Скопируй промт выше как первое сообщение.
3. Ожидание: 5-20 минут на сбор и структурирование.
4. Получишь длинный output с 20-30 карточками + META-DIAGNOSTICS.
5. Скопируй всё в файл по шаблону ниже.
```

#### 7.1.3 Шаблон YAML-шапки для сохранения

```yaml
---
trip_id: {trip_id}
stage: 1_dr_reports
travelers_profile: profiles/{profile_id}.md
regions:
  - {region_1}
  - {region_2}
  - ...
season: {season}
dr_run_date: YYYY-MM-DD            # ← заполни датой реального прогона DR
reports_count: N                    # ← заполни числом из META-DIAGNOSTICS
meta_diagnostics_warnings: [...]    # ← вытащи warnings из META-DIAGNOSTICS
created: YYYY-MM-DD                 # ← дата создания файла
---
```

С инструкцией: «Сохрани как
`{travel_root}/trips/{trip_id}/1_dr_reports.md`. После YAML-шапки —
полный output из DR. Если файл слишком большой (> 200 KB) — это норма,
храним как есть».

#### 7.1.4 «Что НЕ делать в DR-сессии»

Кратко предупредить пользователя:

```markdown
В DR-сессии НЕ:
- проси DR применять профиль (это Stage 2);
- проси DR построить маршрут;
- редактируй промт ситуативно (теряется детерминизм при перезапуске).
```

### 7.2 Режим B — добавление отчётов к готовому DR-файлу

Запускается ПОСЛЕ того, как пользователь принёс готовый DR-файл (от
DR-сессии). Имеет два опциональных под-режима, которые могут идти
вместе или по отдельности:

- **B1 — discovery на forum.awd.ru** по тематике поездки (из YAML
  main-файла). DR этот источник не открывает (BPC-challenge); скилл сам
  ищет, фильтрует, разбирает и добавляет.
- **B2 — пользовательские URL** (awd.ru или любой другой ресурс),
  которые пользователь принёс руками.

Минимум одно из B1/B2 должно быть указано. Если пользователь только
принёс main-файл без явного триггера — переспросить одной строкой и
остановиться.

Принцип: всё ручное (выбор, разбор контента) — у LLM; всё детерминируемое
(fetch, merge, recompute META) — через скрипты, чтобы было дешевле и
воспроизводимо.

#### 7.2.0 Gate активации Режима B

**Input gates:**

- `main_dr_file` обязателен, должен содержать ≥ 1 карточку с маркером
  карточки (канон `## КАРТОЧКА N`; парсер также терпит `**КАРТОЧКА N**`
  и `### Карточка N`, см. §6).
- Хотя бы одно из:
  - триггер B1: «найди ещё на awd.ru», «посмотри Винский», «добавь
    отчётов с форума» — любая формулировка пользователя про обогащение;
  - триггер B2: одна или несколько ссылок в запросе пользователя
    (валидируется как URL).
- Если оба отсутствуют — стоп: «Режим B требует либо запрос discovery
  awd.ru, либо хотя бы одну ссылку».

**Environment gate (Bash tool availability) — НОВОЕ:**

Режим B критически зависит от двух скриптов:
- `scripts/fetch_awd.py` — fetch awd.ru через локальное выполнение (без него BPC-challenge блокирует web доступ);
- `scripts/merge_dr_additions.py` — детерминированный merge новых карточек в main_dr_file.

**Проверь доступность Bash tool ДО начала работы.**

- **Bash доступен** (Cowork / Claude Code / Claude Agent SDK с tools): продолжать по §7.2.1 / §7.2.2 / §7.2.4 как описано. Скрипты работают, merge детерминируемый, output — готовый файл.

- **Bash недоступен** (claude.ai chat без MCP tools):
  - **B1 awd.ru невозможен без скрипта.** Web_search `site:forum.awd.ru` и прямой web_fetch на awd.ru блокируются BPC-challenge. **Не падать silent** — эскалировать пользователю **одной строкой**:

    > Bash tool недоступен в текущем чате — `scripts/fetch_awd.py` не выполняется, awd.ru блокирует прямой fetch (BPC-challenge). Чтобы сделать B1:
    > 1. Открой Stage 1 в чате с Bash (Cowork / Claude Code), OR
    > 2. Запусти локально: `python3 scripts/fetch_awd.py --discover-reports {страна} --pages 3 --filter "{регион_паттерн}" --json` → выбери 2-4 топика → `python3 fetch_awd.py --all-posts --author-only --json <URL>` для каждого → приложи результат в B2.
    >
    > Продолжаю **без B1** (или со списком ссылок из B2, если приложены).

  - **B2 частично работает без Bash:** URLs **не** на awd.ru — стандартный `web_fetch` (без скрипта). URLs **на awd.ru** — `web_fetch` упрётся в BPC, эскалировать как в B1 (опц. локальный fetch + повторное B2).

  - **Merge без Bash:** `merge_dr_additions.py` не запускается. LLM **строит merged-файл сама** — это допустимо для случая «нет Bash», но LLM **обязана**:
    1. Прибавить новые карточки к main_dr_file (продолжая нумерацию `## КАРТОЧКА N+1, N+2, …`).
    2. Пересчитать `reports_count` в YAML.
    3. Пересчитать META-DIAGNOSTICS:
       - per-region counts;
       - distribution по style / focus / language / season;
       - WARN-флаги (≥ 50% sample skew по style/focus, < 10% испано-/местных языков, < 4 на регион).
    4. Добавить строки `sample_curation_note` в YAML с номерами добавленных карточек.
    5. Сохранить смысловые блоки «Источники, которые пробовали…», «Технические уточнения», «Что фотографически отсутствует» как есть.

    Если LLM считает что **не справится** с recompute (большой файл, complex META) — эскалировать пользователю «без скрипта merge ненадёжен, рекомендую запустить локально». Не выдавать неполный merge.

#### 7.2.1 B1 — discovery на awd.ru

Активируется когда пользователь явно просит расширить выборку с
Винского. Цель — 0-3 реально релевантных отчёта (потолок 5-10),
которых нет в main_dr_file. Discovery агрессивно фильтровать — лучше
ничего не добавить, чем добавить балласт.

**Жёсткое правило:** discovery идёт ИСКЛЮЧИТЕЛЬНО через
`scripts/fetch_awd.py --discover-reports`. Никаких `WebSearch` с
`site:forum.awd.ru` (Google не индексирует awd.ru, выдаёт мусор),
никаких прямых `web_fetch` страниц форума (BPC-challenge), никаких
обращений к `search.php` форума (JS-rendered, выдаёт пустоту).

Шаги:

1. **Построить query.** Из YAML main_dr_file взять `regions`, `season`,
   `trip_id` → страна, регионы (русскоязычные топонимы), сезон.

2. **Discovery одной командой.**

   ```bash
   python3 scripts/fetch_awd.py --discover-reports <страна> \
     --pages 3 --filter "<регион_паттерн>" --json
   ```

   Скрипт сам:
   - находит country forum по подстроке (например, «вьетнам» → f=134);
   - выбирает дочерний reports-subforum **скорингом названия** (слова
     `отчёт/впечатления/фото/рассказ/дневник` — плюс; `маршрут/планирование/
     советы/вопросы/виза/транспорт/отели/деньги/шопинг/рестораны` — минус;
     `отзыв` — слабый +1), а **не** первым совпавшим. При близких баллах двух
     веток — тай-брейк по доле отчётных заголовков на 1-й странице. В выводе
     виден выбор: `[выбран: score, score=9]`;
   - перечисляет темы первых N страниц с regex-фильтром по заголовкам;
   - возвращает JSON с country_forum, reports_forum, topics.

   **Shared-ветки и маленькие регионы (важно — не падать):**
   - У части стран **одна общая ветка на несколько стран** (Аргентина f=439
     «Аргентина, Парагвай, Уругвай — отзывы и отчёты»; Непал f=341 «Отзывы о
     Непале, Тибете, Бутане»; ЮАР f=673 на 6 стран). Скоринг их находит
     штатно — отдельной страновой ветки может не быть, это норма.
   - Если у страны **нет** травелог-ветки вовсе — скрипт вернёт ValueError
     (см. шаг 3), а не выберет планировочную. Это ожидаемо: B1 завершить без
     добавлений, не пытаться «дотянуть» из планировочной ветки.

   Примеры фильтров:
   - Вьетнам Север: `"Сапа|Хойан|Ханой|самостоятельн"`;
   - Аргентина Юг: `"Чальтен|Чалтен|Калафате|Огненная"`;
   - Япония: `"Хоккайдо|Хонсю|самостоятельн"`.

3. **Fail-handling.** Если `discover-reports` упал с ValueError:
   - subforum по стране не найден → попросить пользователя дать точную
     подстроку (`«Не нашёл subforum 'X' на awd.ru. Попробуй другое
     написание, или дай ссылки через B2»`);
   - дочерний reports-subforum не найден → fallback на сам country
     forum (если у него есть свои темы) или стоп B1 с сообщением
     пользователю.

4. **Отсеять полученный список (LLM):**
   - URL, уже присутствующие в main_dr_file (grep по `viewtopic.php?t=N`);
   - заголовки-вопросы («Помогите...», «Подскажите...», «Вопрос про...»);
   - очень старые темы (по году в заголовке, если есть): год <
     {текущий − 12};
   - очевидно нерелевантные регионы.

5. **Отобрать 0-3 кандидата.** Критерии приоритизации:
   - совпадение сезона / месяца с YAML main_dr_file;
   - стиль автора, дополняющий выборку (если в main 80% mid-range —
     приоритет photo-focused / adventure);
   - содержательный заголовок (с регионами, не «Вьетнам 2024»).

   Если ни один кандидат не проходит — пропустить B1 без добавлений
   и честно сообщить пользователю «B1: ничего релевантного не нашлось».

6. **Получить тексты.** Для каждого выбранного URL —
   `python3 scripts/fetch_awd.py --all-posts --author-only --json
   <URL>`. Это вернёт все посты автора первого поста + блок профиля
   (`author_profile` с возрастом, городом, полом).

7. **Разобрать в 20-field карточки.** LLM применяет структуру из §6
   и §7.2.3 к каждой полученной теме.

**Anti-pattern (что НЕЛЬЗЯ делать):**

- `WebSearch "site:forum.awd.ru Вьетнам отчёт"` — Google awd.ru не
  индексирует, на выходе — Tripadvisor и Skyscanner. Не запускать.
- `web_fetch https://forum.awd.ru/viewforum.php?f=…` — BPC-challenge,
  пустой ответ. Использовать `fetch_awd.py`.
- `fetch_awd.py "https://forum.awd.ru/search.php?…"` — встроенный
  поиск форума JS-rendered, отдаёт страницу «Информация» без данных.
- Прыгать между `--list-subforums` → `--list-topics` руками — это
  то, что должен делать `--discover-reports` одним вызовом.
- **Брать subforum только потому, что в названии есть «отзыв».** У многих
  стран так называется ПЛАНИРОВОЧНАЯ ветка (Китай f=911 «Маршруты… советы,
  планирование и **отзывы**» — ловушка; нужен f=247 «**Отзывы**… впечатления,
  отчёты и фото»). `--discover-reports` уже разводит их скорингом — не
  переопределять его выбор вручную на «первую ветку с отзывами».
- **Триаж по заголовку без проверки первого поста.** Даже в правильной
  travelogue-ветке заголовок врёт («Путешествие по маршруту…: советы» =
  планирование). Финальный фильтр — по первому посту: прошедшее время +
  личный опыт → отчёт; «хочу/прошу/планирую» → балласт.

#### 7.2.2 B2 — пользовательские URL

Активируется когда пользователь приносит конкретные ссылки. Источник
может быть любой (awd.ru, Tourister, Reddit, личный блог, viajeros.com,
jalan.net и т.п.).

Шаги:

1. **Разбить по типам:**
   - URL содержит `forum.awd.ru/viewtopic.php?t=` → fetch через
     `scripts/fetch_awd.py --all-posts --author-only --json <URL>`;
   - всё остальное → стандартный `web_fetch`; если возвращает заглушку
     (client-rendered) → fallback на `mcp__Claude_in_Chrome__navigate`
     + `get_page_text`.

2. **Проверка дублей.** Если URL уже есть в main_dr_file — пропустить
   с уведомлением пользователю в финальном summary.

3. **Если контент не получен** (paywall, удалена, недоступна) —
   пропустить и отметить в summary `«{URL}: не получен — {причина}»`.
   Никаких выдуманных карточек.

4. **Разобрать в 20-field карточки** так же, как в B1.

#### 7.2.3 Применение 20-field структуры

Для каждой собранной темы LLM прогоняет строго те же 20 полей из §6.
Это критично — Stage 2 парсит карточки по фиксированной структуре.

Особенности при работе с awd.ru:

- **Поле 2 (Платформа и язык):** `forum.awd.ru (Форум Винского), ru`.
- **Поле 3 (Имя/ник):** `author` из JSON.
- **Поле 4 (Дата публикации):** `date` из JSON.
- **Поле 8 (Возрастной диапазон):** взять из `author_profile.Возраст`,
  если есть; иначе оставить «не указано». Эвристики по тону — только в
  крайнем случае.
- **Поле 3 → город автора:** если в `author_profile.Город` — добавить
  в скобках (например, `helvhrav (Москва)`).
- Если поле не определить — `не указано`.
- Стиль (поле 9) и фокус (поле 13) — из таксономии, использовавшейся в
  оригинальном DR-output. Посмотри первые 3-5 карточек main-файла,
  чтобы попасть в тот же набор лейблов. Если main-файл на английских
  тэгах (`mid-range independent`) — дописывай **в том же наборе**:
  консистентность внутри файла важнее языка, значения русифицирует
  экспорт (см. `stage1-output-spec.md`, «Формы полей»).

#### 7.2.4 Merge через скрипт

Промежуточные additions-файлы **не сохраняются** в выводы — это
временные файлы в `/tmp/`, удаляются после прогона.

Шаги:

1. Собрать все 20-field карточки (из B1 и/или B2) в один временный
   файл `/tmp/_dr_additions_<random>.md` без YAML и META-DIAGNOSTICS
   (только карточки `## КАРТОЧКА N` + поля).

2. Прогнать merge:

   ```bash
   python3 scripts/merge_dr_additions.py <main_dr_file> \
     /tmp/_dr_additions_<random>.md -o /tmp/_dr_merged_<date>.md
   ```

3. **Канонизировать структуру слитого файла** — merge сохраняет формат
   маркеров источников, а старые/импортированные отчёты часто идут как
   `**КАРТОЧКА N**` + `-----` (downstream-парсеры на них спотыкаются):
   ```bash
   python3 scripts/parse_dr_cards.py --normalize \
     < /tmp/_dr_merged_<date>.md > /tmp/_dr_canon_<date>.md
   ```
   Маркеры → `## КАРТОЧКА N` (сквозная нумерация), `-{3,}` убраны, контент
   и аннотации сохранены. Затем валидировать
   (`parse_dr_cards.py --trip-slug {slug} < …canon.md`): `total_cards`
   против `reports_count`, `status=error` → §9.12. Канонизированный файл —
   финальный.

4. Скопировать результат в outputs скилла под человеко-читаемым именем
   (например, `1_dr_reports_<trip_id>_merged.md`).

5. Удалить временные additions/merged-файлы.

Что merge делает детерминированно:
- `reports_count` в YAML + раздел «Количество отчётов»;
- распределение по языку (поле 2, по суффиксу `, xx`);
- распределение по стилю (поле 9, keyword-таксономия);
- распределение по фокусу (поле 13);
- распределение по сезону (regex по полям 5-6);
- warnings: доля одного стиля < 50%, доля одного фокуса < 50%,
  испаноязычная доля ≥ 10%;
- в YAML добавляется `sample_curation_note` со списком добавленных
  карточек.

Что **не** пересчитывает (помечается TODO-маркером в выходе):
- распределение по регионам (требует NER);
- региональный warning «≥ 4 на регион»;
- унаследованные смысловые блоки («Источники, которые пробовали»,
  «Технические уточнения», «Что фотографически отсутствует») —
  сохраняются как есть в раздел «Унаследованные блоки».

#### 7.2.5 Выдача в чат

**Output структура зависит от environment** (см. §7.2.0 environment gate):

## 9. Граничные случаи

### 9.1 Чтение Stage 0 артефакта: SSOT и приоритеты

Stage 0 артефакт имеет **два места**, где может оказаться решение:

- **Блок `## Решение` в markdown — single source of truth.** Человек
  принимает решение здесь. Файл шарится и редактируется без чата
  (попутчики, другие участники).
- **`selected_regions:` в YAML — производный кэш.** Опционален. Удобен
  для быстрого машинного чтения, но не обязателен.

**Правило приоритета — всегда блок `## Решение` важнее YAML.**

Алгоритм чтения:

1. Распарсить `## Решение` (см. §9.2 — формат и три кейса).
2. Сравнить с YAML `selected_regions:`:
   - Совпадают → быстрый путь, ничего не сообщать.
   - YAML null → молча использовать блок, в финальном summary одна
     строка: «YAML `selected_regions:` был пустой, использую
     `## Решение`. Хочешь обновить YAML — скажи 'обнови'».
   - YAML заполнен и расходится → блок primary, в чате уведомление:
     «YAML расходится с `## Решение` ({краткий diff}). Использую блок.»
3. Никаких блокирующих вопросов «что важнее» — блок всегда важнее.

### 9.2 Парсинг блока `## Решение`: три формата

Stage 0 фиксирует машинно-парсимый формат (см. `../stage0/stage0-scope.md`
«Машинный контракт»). Блок имеет три поля:

```markdown
**Выбран пакет:** <компактный | сбалансированный | расширенный | кастомный>

**Разбивка по дням** (заполни только если меняешь распределение или
выбран «кастомный»):

- {регион} — {N} ночей
- ...

**Почему этот выбор:**
- ...
```

Логика парсинга:

1. **Прочитать `**Выбран пакет:**`** — обязательно. Имя пакета —
   lowercase, без эмодзи. Допустимы: имена из `## Предложенные пакеты`
   Stage 0 + `кастомный`.
2. **Прочитать `**Разбивка по дням:**`**:
   - **Под ней непустой список** — это итоговое распределение.
     Использовать как есть.
   - **Пусто или отсутствует** — взять распределение пакета из
     `## Предложенные пакеты` (найти `### {имя}` и распарсить список
     ниже до следующего `###`/`##`).
3. **Оба указаны** (имя пакета + непустая разбивка) — разбивка
   приоритет, имя пакета используется как label. В summary одна
   строка: «Использую разбивку из блока (пакет '{имя}' — label)».
4. **`Выбран пакет: кастомный` без разбивки** — стоп: «Выбран
   кастомный пакет, но `**Разбивка по дням:**` пуста. Заполни
   разбивку и повтори».
5. **Имя пакета не найдено в `## Предложенные пакеты`** — стоп:
   «Пакет '{имя}' не найден. Доступны: {список_имён}. Поправь блок
   `## Решение` и повтори».
6. **Sanity:** сумма ночей в распределении должна совпасть с
   `duration_nights` из YAML. Расхождение → warning в summary
   (не стоп), спросить пользователя «использовать как есть или
   синхронизировать?».

### 9.2a Stage 0 артефакт есть, но блок `## Решение` отсутствует

Stage 0 завершён, но раздел `## Решение` не заполнен (или удалён).
Отказать: «В `0_scope.md` нет раздела `## Решение`. Открой Stage 0,
заполни блок (выбери пакет минимум одной строкой `**Выбран пакет:**`),
потом повтори».

### 9.3 Пользователь хочет DR по стране целиком

См. §4.1 эвристику. Для небольших / географически узких стран
(Камбоджа, Лаос, Шри Ланка, Грузия, Хоккайдо и т.п.) — принимать молча
как валидный scope. Для крупных multi-region стран — мягко
порекомендовать Stage 0, но не блокировать; проходим если пользователь
подтверждает.

### 9.4 Пользователь хочет DR по одной локации (один город)

OK, прогоняем с `scope: [{один_город}]`. DR соберёт отчёты по разным
районам и трип-форматам в пределах этого города. META-DIAGNOSTICS
покажет распределение.

### 9.5 Пользователь хочет повторно запустить DR с другими regions

Если файл `1_dr_reports.md` уже существует — не перезаписывать. Новый
прогон → `1_dr_reports_v2.md` или `1_dr_reports_{дата}.md`. В YAML
поле `chosen_dr_run` в Stage 2 укажет, какой используется.

### 9.6 DR-выборка получилась маленькой (< 15 отчётов)

При META-DIAGNOSTICS reports_count < 15 — сигнал плохого покрытия.
Возможные причины: редкое направление, узкий timeframe, слабое
проиндексирование на русскоязычных площадках. На Stage 2 это вылезет
как `HIGH < 5` warning. Перезапустить DR с расширенными источниками,
добавить свои отчёты через Режим B, ИЛИ продолжать с тем, что есть,
понимая ограничение.

### 9.7 DR вернул отчёты только одного стиля (>70% одного типа)

META-DIAGNOSTICS должен вызвать `WARNING: sample skew`. Перезапустить
DR с явным указанием «найти контр-стиль» (например, «найди ещё 5
backpacker отчётов, текущая выборка перегружена organized tour»). Или
догнать руками через Режим B.

### 9.8 Пользователь хочет править промт

Допустимо, но осторожно: сильные изменения промта ломают сравнимость
с другими прогонами. Если меняешь — зафиксируй в `meta_diagnostics_warnings`
YAML, что промт был модифицирован.

### 9.9 Режим B (B2): новый отчёт не получается прочитать (paywall, 404)

Пропустить этот URL. В summary явно: «{URL}: не получен — {paywall/
404/client-rendered/etc.}». Не выдумывать содержание.

### 9.10 Режим B (B2): дубль по URL

Если URL уже есть в main_dr_file — не дублировать. В summary отметить:
«{URL} уже в файле под номером {N}, пропущен». Если пользователь
настаивает «перезапиши анализ для этого URL» — допустимо, заменить
старую карточку (требует ручной правки merged-файла, скрипт это
автоматически не делает).

### 9.11 Режим B (B1): discovery не дал результатов

Бывает: в subforum-е нет свежих тем по нужным регионам / сезону, или
все найденные — старше 12 лет, или дубли. В этом случае честно сообщить
в summary: «B1: релевантного не нашлось». Не насиловать выборку
балластом. Если пользователь хочет — может расширить параметры
discovery (другой subforum, другой временной коридор).

### 9.12 Режим B: новые отчёты на местном языке

OK. Fetch возвращает оригинальный текст, скилл применяет 20-field
анализ через своё знание (Sonnet / Opus неплохо понимают основные
азиатские и романские языки). В поле 2 (Платформа и язык) указать
суффикс `, vi` / `, ja` / `, zh` / etc.

### 9.13 Режим B (B1+B2 одновременно): что выдавать в summary

Один общий summary, но в нём явно разделить блоки «B1: найдено N
отчётов на awd.ru: ...» и «B2: добавлено M отчётов из ваших ссылок:
...». Если один из под-режимов ничего не дал — отдельной строкой
«B1: ничего» / «B2: ничего».

## 10. Что НЕ делает скилл

- **НЕ запускает DR (Режим A).** DR работает в отдельной сессии в
  DR-режиме; скилл не имеет к нему доступа.
- **НЕ генерирует сами отчёты в Режиме A.** Выдаёт только промт.
  В Режиме B скилл прогоняет 20-field анализ на отчётах, явно
  поданных пользователем — но это не «генерация», а структурирование
  существующего контента.
- **НЕ сохраняет файлы.** Пользователь сохраняет руками (manual save).
- **НЕ оценивает качество отчётов.** Это работа Stage 2 (similarity).
- **НЕ редактирует промт ситуативно.** Шаблон детерминирован; любые
  правки — явные и зафиксированные в YAML.
- **НЕ применяет профиль для фильтрации.** Применение профиля = Stage 2,
  на уже собранной выборке.
- **В Режиме B не «добирает» собственные отчёты сверх запрошенных.**
  Если пользователь дал 3 URL — анализирует ровно 3, не делает
  дополнительных web_search «на всякий случай».

## 11. Следующий шаг

После того как DR прогнался и файл `1_dr_reports.md` сохранён:

- Активируется Stage 2 (`/travel-planning` → «Stage 2 для
  {trip_id}» или «нужна фильтрация авторов»).
- Stage 2 читает `1_dr_reports.md` и применяет профиль для расчёта
  similarity-score каждому автору.

Скилл не запускает Stage 2 автоматически — пользователь решает, когда
готов перейти к фильтрации (например, может потребоваться несколько
DR-прогонов до того, как выборка устроит).
