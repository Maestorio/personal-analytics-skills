# scenario-builder

Язык вывода — русский. Всегда.

## Принципы метода

1. **Равновероятность.** Ни один сценарий не является «базовым» или «наиболее вероятным». Все четыре равновозможны — это фундамент метода Shell. Никаких вероятностных оценок в нарративах.

2. **Оси — из реальных разногласий.** Хорошая ось строится там, где существуют принципиально несовместимые позиции между реальными агентами. Если по теме нет полярных позиций по какой-то переменной — это не ось, а тренд.

3. **Нарративы — не списки рисков.** Каждый нарратив описывает целостный мир, в котором обе оси приняли конкретные значения. Не перечень факторов, а связная картина.

4. **Leading indicators — наблюдаемые.** Конкретные данные, события или пороговые значения — не «ухудшение ситуации». Пользователь должен понимать, что именно отслеживать прямо сейчас.

5. **Карта лагерей строится через web_search.** Актуальные позиции важнее любых шаблонов. Исключение — темы без публичного дискурса (см. Шаг 1.0).

6. **Доменный жаргон требует пояснений.** Любой специальный термин в карте лагерей, осях или нарративах — раскрыть в скобках (1 предложение).

7. **Машиночитаемый блок Events YAML.** В конце вывода всегда добавляется технический блок `## Events YAML (для save-to-library)` для автоматического сохранения через save-to-library. Содержит scenario_triggers с leading_indicators в машиночитаемом формате.

---

## Inputs / Outputs

**Inputs:**
- Тема, горизонт, домен ← запрос пользователя (inline)
- Позиции лагерей (для корп/закрытых тем) ← от пользователя

**Outputs (как artefact в чат):**
- Матрица 2×2 + 4 нарратива + `## Events YAML (для save-to-library)` →
  пользователь проверяет → save-to-library пишет в `Claude-Memory/scenarios/<slug>-<date>.{md,yaml}`
- Черновик той же пары в `Claude-Memory/_drafts/` (служебная зона, Шаг 5) — источник для save-to-library, чат не
  теряет текст при сжатии контекста

**Upstream скиллы:** —
**Downstream скиллы:** hypothesis-stress-tester (по хрупкому сценарию), save-to-library
**Shared refs:** transport-layer, events-yaml-spec, yaml-schemas, file-naming

## Шаг 0 — Приём входа

Зафиксируй перед запуском:

- **Тема** — о чём сценарии (1–2 предложения)
- **Горизонт** — на какой срок/дату (например: «конец 2026», «3–5 лет»)
- **Домен** — `ru-macro` / `geopolitics` / `global-markets` / `tech` / `corporate` / другое
- **Цель** — для прогнозирования / для stress-test / для стратегического решения

Если тема уже содержит явные оси — зафиксируй их и пропусти Шаг 1.

## Шаг 1 — Карта лагерей и выбор осей

### 1.0 — Определение режима

**Публичный дискурс** (ru-macro, geopolitics, global-markets, tech): web_search.
**Закрытая / корпоративная тема:** запросить у пользователя 2–4 позиции, переход к 1.2.

### 1.1 — Поиск актуальной карты лагерей

2–3 поисковых запроса:

```
"[тема] [горизонт] разногласия эксперты позиции"
"[тема] debate arguments camps [год]"
"[тема] прогноз расхождение мнения аналитики"
```

Таблица лагерей: 2–4 лагеря с принципиально несовместимыми тезисами. Жаргон раскрывать.

### 1.2 — Выбор двух осей

Из разногласий — две переменные: самые неопределённые и самые влиятельные.

**Хорошая ось:** исход неизвестен, оба полюса реалистичны, разные лагеря на полярных позициях.
**Плохая ось:** один полюс маловероятен, переменная зависима от другой, тренд а не развилка.

> **Двусторонность по ключевым downstream-факторам (§15, F1).** Проверь мысленно: даст ли набор
> осей **встречный мир** для ставки и рубля? Систематическая ошибка (self-audit №1) — когда все 4
> мира сдвигают ставку/рубль в одну сторону от текущего факта (нет мира «пауза/hike ЦБ», нет
> «крепкий рубль»). Встречный мир по ставке живёт **не на оси разрядки**, а на оси
> инфляция/фискальное доминирование: эскалация → девальвация → pass-through → ЦБ держит/повышает.
> Если оси этого не порождают — при FCA конкретный фактор получит `one_sided_cone: true` и потребует
> `counter_world_reason`. Учитывай это при выборе осей.

Покажи оси с обоснованием → **жди подтверждения** перед Шагом 2.

```
Предлагаю оси:

— Ось X: [переменная (пояснение)]
  Полюса: [A] vs [B]
  Обоснование: [...]

— Ось Y: [переменная (пояснение)]
  Полюса: [C] vs [D]
  Обоснование: [...]

Подтверди или предложи другие оси.
```

## Шаг 2 — Матрица 2×2

После подтверждения осей — Markdown-таблица. Имя каждому квадранту (2–4 слова).

|  | **[Ось Y: полюс C]** | **[Ось Y: полюс D]** |
|---|---|---|
| **[Ось X: полюс A]** | **Сценарий A: «[Имя]»** | **Сценарий B: «[Имя]»** |
| **[Ось X: полюс B]** | **Сценарий C: «[Имя]»** | **Сценарий D: «[Имя]»** |

> **D1 (default):** все 4 сценария получают `probability: 0.25`.
> `modal_scenario_id: none`. Это методологическое допущение Shell, не оценка вероятности.
> Изменить веса можно через opt-in Шаг 5.5 ниже.

> **Polarity-lock (§17, F4).** Присваивай квадранты по канону: **Sc-A = максимальный стресс**
> (война+санкции), **Sc-D = максимальная разрядка** (мир+снятие санкций). В Events YAML (Шаг 5)
> задекларируй `matrix.polarity: {stress_pole: A, detente_pole: D}`. Если новая матрица темы
> **инвертирует** полярность относительно прежней — это осознанное действие: `axis_polarity_change:
> true` + таблица `axis_polarity_migration` (A↔D). Иначе save-to-library выдаст warning рассинхрона
> (инверсия осей — доминирующая часть process-churn, self-audit №4а).

## Шаг 3 — Нарративы

Для каждого из 4 сценариев нарратив одинаковой глубины:

```
### Сценарий [X]: «[Имя]»

**Мир:** [2–3 предложения — что правда в этом мире на горизонте]

**Ключевые механизмы:** [2–3 причинно-следственных цепочки]

**Для темы это означает:** [1–2 предложения — конкретный вывод]

**Leading indicators** (что наблюдать):
- [конкретный показатель / событие / пороговое значение]
- [...]
- [...]
```

**Требования:**
- Не повторяет формулировку осей
- Не содержит вероятностных слов: «скорее всего», «вероятно», «возможно»
- Leading indicators — наблюдаемые прямо сейчас или в горизонте
- Жаргон раскрывается при первом появлении

## Шаг 4 — Triage по хрупкости (опционально)

Запускается если пользователь планирует stress-test или явно запрашивает.

Для каждого сценария — pre-mortem (1–2 предложения): при каком одном событии этот мир рассыпается?

| Сценарий | Главная точка хрупкости |
|----------|------------------------|
| A «[Имя]» | [...] |
| B «[Имя]» | [...] |
| C «[Имя]» | [...] |
| D «[Имя]» | [...] |

**Рекомендованный сценарий для stress-test** — наиболее хрупкий И значимый.

Формат передачи в `hypothesis-stress-tester`:
```
Прогноз для стресс-теста: «[формулировка сценария как утверждения]»
Горизонт: [дата]
Домен: [домен]
```

## Шаг 4.5 — Downstream sensitivity hints (опционально, V3)

Блок добавляется, если выполнено **хотя бы одно** условие:

- scenario-builder вызван из `macro-forecast-chain` (по контексту вызова);
- пользователь явно написал «downstream», «stress-test» или «сценарии для портфеля»;
- пользователь уже работает с `portfolio-scenario-stress` в текущей сессии.

Блок **не** добавляется при явном «только сценарии» / «не нужен downstream-анализ»
и для темы без финансовых факторов. Содержание блока — как каждая ось сценария
влияет на типовые downstream-факторы.

Это нужно для V3 (per-factor translation): chain читает эти hints и сопоставляет
с таблицей `GEOPOLITICS_TRANSLATION` в `dependency-map.md`, чтобы выбрать
правильный translation для каждого downstream-фактора.

### Что записывать

```yaml
## Downstream sensitivity hints (для macro-forecast-chain V3)

axes_meta:
  axis_x:
    name: "{короткое имя оси X}"
    domain: [low_label, high_label]      # семантические концы
    typical_responders:                   # какие downstream-факторы реагируют
      monotone:                           # отклик линейный по этой оси
        - {sanctions_intensity, brent (через сырьевую премию), urals_discount}
      non_monotone:                       # отклик немонотонный
        - {usdrub: "при умеренном увеличении растёт через risk-off, но при
                     полной эскалации может упасть из-за capital controls"}
      indifferent:
        - {xauusd: "слабый safe-haven эффект, доминирует USD-cycle"}
    quantitative_anchor:                  # если есть числовая привязка оси
      low_value: 0.0
      high_value: 1.0
      modal_expected_value: 0.55          # из распределения сценариев

  axis_y:
    # аналогично

# Cross-axis interactions — где взаимодействие осей создаёт нелинейность
cross_effects:
  - factors_affected: [brent]
    explanation: "При high-X + high-Y нефть может получить и premium, и demand-destruction
                  одновременно — суммарный эффект непредсказуем."
  - factors_affected: [usdrub]
    explanation: "Аналогично: при сильной эскалации курс становится bimodal."
```

### Где брать данные

Эти hints — экспертная разметка от scenario-builder, основанная на:
1. Экономическом анализе осей (что они означают для финансовых рынков).
2. Наличии нелинейных порогов (capital controls, sanctions cliffs, embargo).
3. Известных взаимодействиях осей (cross-effects).

Не выдумывай hints — если для конкретной оси scenario-builder не уверен в классификации,
помечай:
```yaml
typical_responders:
  unclassified: ["fact_X", "factor_Y"]   # требуется ручная разметка пользователем
```

### Когда блок НЕ выводится

- Запрос явно тестовый («просто построй сценарии», «без downstream-анализа»).
- Тема сценариев не имеет известных downstream-факторов в финансовой системе
  (например, сценарии климата, выборов в страну без портфельной экспозиции).

### Связь с macro-forecast-chain

`macro-forecast-chain` (Шаг 5.0) читает этот блок при построении translation map.
Если `axes_meta.axis_x.typical_responders.monotone` содержит фактор → factor
получает `conditional_on_scenarios.marginal.method = linear` (см.
`references/events-yaml-spec.md` §5). Если фактор в `non_monotone`
→ method = nonlinear. Если в `indifferent` → method = indifferent.
`axis_dependent` назначается, если фактор привязан только к одной оси
(сильная monotone-связь с одной осью + indifferent ко второй). Диагностический
тег — `aggregation_formula: weighted_mean` (математически эквивалентен `linear`
вдоль доминантной оси). Опциональная аннотация `dominant_axis: x|y` добавляется
вручную при необходимости. Никакого `_todo` — метод полностью определён (SB-1).

## Шаг 5 — Сборка блока Events YAML

В самом конце вывода (после Шага 4 если был, иначе после Шага 3) — технический блок для save-to-library.

### Шаблон

```markdown
## Events YAML (для save-to-library)

\`\`\`yaml
matrix:
  date: {YYYY-MM-DD = сегодня}
  horizon: {YYYY-MM-DD из Шага 0}
  domain: {domain из Шага 0}
  topic: {topic-slug — kebab-case, ISO 9 транслит, ≤30 симв.}
  axis_x: "{переменная X: полюс A vs полюс B}"
  axis_y: "{переменная Y: полюс C vs полюс D}"

scenario_triggers:
  - scenario_id: A
    label: "{Имя сценария A}"
    probability: 0.25     # default Shell-равновероятность
    enabling_conditions:
      - "{условие 1 из ключевых механизмов}"
      - "{условие 2}"
    leading_indicators:
      - id: {slug}
        description: "{из leading indicators сценария}"
        threshold: "{численный или событийный порог}"   # опционально
        check_date: {YYYY-MM-DD}                        # опционально
        auto_checkable: true|false
        manual_check_method: "{как проверить вручную}"  # обязательно если auto_checkable: false

  - scenario_id: B
    label: "..."
    probability: 0.25
    enabling_conditions: [...]
    leading_indicators: [...]

  - scenario_id: C
    label: "..."
    probability: 0.25
    enabling_conditions: [...]
    leading_indicators: [...]

  - scenario_id: D
    label: "..."
    probability: 0.25
    enabling_conditions: [...]
    leading_indicators: [...]

reviews:
  interval_months: 6      # дефолт для сценариев — 6 мес.
  next_due: {matrix.date + 6 мес.}
\`\`\`
```

### Правила заполнения

**`matrix.topic`:** slug по правилу `events-yaml-spec.md §1.2` (kebab-case, ISO 9 транслит, стоп-слова отсеять, первые 3 значимых слова, ≤30 симв.).

**`scenario_triggers[].probability`:** дефолт `0.25` для всех 4 сценариев (Shell-равновероятность). Если пользователь после Handoff в FCA получил вероятности — он передаст их явно при сохранении.

**`scenario_triggers[].enabling_conditions`:** 2–3 условия из секций «Ключевые механизмы» нарратива. Каждое — короткая формулировка, не вся причинно-следственная цепочка.

**`scenario_triggers[].leading_indicators`:** все индикаторы из соответствующего нарратива, переформатированные:
- `id` — slug по правилу
- `description` — формулировка индикатора как в нарративе
- `threshold` — конкретный численный или событийный порог (если есть в формулировке)
- `check_date` — конкретная дата (если есть в формулировке); для качественных индикаторов опускается
- `auto_checkable`:
  - `true` если есть числовой порог ИЛИ конкретная дата
  - `false` если индикатор требует суждения — тогда **обязательно** поле `manual_check_method`

- `manual_check_method` (обязательно при `auto_checkable: false`): описание источника
  и критерия «сработал». ≤100 симв.
  Пример: `«Протокол заседания ЦБ: риторика "проинфляционные" → "нейтральные"»`

**`reviews.interval_months`:** дефолт 6 мес. Уменьшить до 3 если домен `ru-macro` (быстро меняется) или `geopolitics-active` (война, выборы).

**`reviews.next_due`:** `matrix.date + interval_months`.

### Когда блок НЕ выводится

Только если пользователь явно сказал «не сохраняй». По умолчанию блок присутствует — save-to-library не запускается без отдельной команды.

### Черновик в файл (до вывода в чат)

Собрав вывод с блоком Events YAML, запиши два файла через `Write` на mount (`references/transport-layer.md`); рабочий корень —
`{MEMORY_ROOT}/_drafts`, не всё дерево:
`{MEMORY_ROOT}/_drafts/scenario-<topic>-<date>.md` — весь вывод как в чате и
`{MEMORY_ROOT}/_drafts/scenario-<topic>-<date>.events.yaml` — содержимое блока Events YAML без обёртки;
`<topic>` и `<date>` — `matrix.topic` и `matrix.date` блока (slug по `references/events-yaml-spec.md` §1.2), те же имена
получит пара в `scenarios/`. В чат — как обычно плюс строка «черновик: `_drafts/scenario-<topic>-<date>`»;
save-to-library (Workflow C1.0) берёт пару из черновика, поэтому сжатие контекста между сборкой и сохранением текст
не теряет. Mount недоступен — вывод только в чат и фраза «черновик не записан». «Не сохраняй» — черновик не пишется.

## Шаг 5.5 — Joint weights derivation (opt-in)

Применяется ТОЛЬКО при явном запросе пользователя («взвесь сценарии», «посчитай
вероятности осей») ИЛИ при CLI флаге `--apply-joint-from-axes`.

По умолчанию (D1) — все 4 сценария получают `probability: 0.25`.

**Если opt-in активирован:**

1. Выполнить FCA по каждой оси (3–7 источников × 2 оси):
   - Ось X: `ev_x` = P(axis_x = HIGH) из FCA
   - Ось Y: `ev_y` = P(axis_y = HIGH) из FCA
2. Оценить ρ (корреляция осей) через `references/correlation-rubric.md`
   (default ρ=0 при отсутствии оснований, D6)
3. Применить `weights_from_axes(ev_x, ev_y, rho)` из `scripts/scenario_axis_weights.py`
   (общий канон репозитория, инжектится в скилл при упаковке). **Полярность:**
   маппинг квадрантов на id сценариев — канон §17 F4 (`stress_pole: A` — обе
   оси в HIGH, `detente_pole: D` — обе в LOW). Перепутанная полярность не
   падает, а зеркалит веса: вес войны уезжает на разрядку.
4. Записать результат в `scenario_triggers[*].probability` в Events YAML
5. Установить `modal_scenario_id = argmax(weights)` и `modal_flag: modal`

**ВАЖНО:** веса записываются ТОЛЬКО в scenario YAML. Никогда не дублируются
в forecast YAMLs или macro-input.

**Действующие веса — на сайте.** Если рядом с матрицей есть
`scenarios/stress-weights-<имя матрицы>.json`, стресс и макро-цепочка считают на нём,
а веса в матрице — исходные на её дату. Расхождение двух наборов — норма: владельца о нём
не спрашивай и веса из файла сайта в матрицу не переноси. Пересматриваешь веса — запиши
предложение в матрицу и скажи владельцу задать действующие веса на странице «Стресс» сайта.

**После FCA:** владелец задаёт веса на странице «Стресс» сайта (нет файла сайта — обновляет
`scenario_triggers[*].probability` в YAML и сохраняет через `save-to-library` Workflow C) →
запускает `macro-forecast-chain --mode RECALIBRATE` (пересчёт Layer 2 marginals без LLM-вызовов).
Без этих двух шагов новые веса не дойдут до прогнозов.

## Шаг 6 — Сохранение через save-to-library (опционально)

По завершении предложи:
> «Сохранить матрицу сценариев в Claude-Memory? Запущу save-to-library — создаст пару `Scenarios/scenario-{topic}-{date}.md` + `.yaml`.»

Если пользователь соглашается → передать save-to-library полный вывод (включая блок Events YAML и сами нарративы как `## Сценарии` секцию). save-to-library сам:
- сгенерирует `.md` с frontmatter и контентом
- распарсит блок Events YAML и сгенерирует `.yaml` (тип `scenario-events`)
- проверит дедупликацию по `topic` (если уже есть сценарии с тем же topic — спросит, новая версия / замена / независимый)
- обновит `Scenarios/INDEX.md`

**Не сохраняй сам в `scenarios/`.** Делегирование save-to-library — единая точка валидации схемы; сам скилл пишет
только черновик в `_drafts/` (Шаг 5).

Полная yaml-схема — `save-to-library/references/events-yaml-spec.md` §4.

## Handoff в forecast-confidence-applier

Если пользователь хочет взвесить сценарии по вероятности — объясни:
> Метод Shell намеренно не назначает вероятности: цель в том, чтобы подготовиться к любому из миров. Нет плохих сценариев — есть неотслеживаемые.

Если **настаивает**, передай работу в `forecast-confidence-applier`:

```
Тема: [тема], горизонт [дата].
Я построил 4 сценария по методу Shell:
  A «[Имя]» — [одно предложение]
  B «[Имя]» — [одно предложение]
  C «[Имя]» — [одно предложение]
  D «[Имя]» — [одно предложение]

Собери текущий консенсус экспертов: какой из этих сценариев
они считают наиболее вероятным? Применяй trust weights из INDEX.md.
```

После FCA — пользователь может обновить `probability` в Events YAML вручную перед сохранением; затем `save-to-library` Workflow C и `macro-forecast-chain --mode RECALIBRATE` (см. Шаг 5.5).

## Output rules

- Карта лагерей (из web_search) — всегда, до матрицы
- Подтверждение осей от пользователя — обязательно перед Шагом 2
- Все 4 нарратива — всегда полные, одинаковой глубины
- Вероятности сценариям не назначаются в нарративах **никогда**; в `scenario_triggers.probability` дефолт 0.25 (равновероятность Shell), пользователь может переопределить после FCA
- Матрица — Markdown-таблица, не ASCII-art
- Жаргон — раскрывается при первом использовании
- Triage (Шаг 4) — только по явному запросу или если упомянут stress-test
- **Events YAML (Шаг 5)** — обязателен в самом конце (если пользователь не сказал «не сохраняй»)
- Сохранение (Шаг 6) — предлагать по завершении, делегировать save-to-library
- Handoff в FCA — только если пользователь запросил вероятности
