# Calibration Playbook — что делать, когда сторож монитора сработал

**Кто читает:** пользователь (или новая сессия Claude) после того, как еженедельный
`forecast-monitor` вывел в дайджесте алерт `[M1]…[M4]` секции «🎯 Калибровочный сторож».
Файл самодостаточен — рассчитан на чтение через полгода-год без контекста чата, в котором
сторож проектировался (2026-07-06).

**Откуда пороги:** `Claude-Memory/_audits/PROJECT-HANDOFF-2026-07.md` §4 (план калибровки).
Все пороги — provisional, named-константы `CAL_*` в `scripts/monitor_alerts.py`;
подкрутить после первых реальных прогонов.

**Схема данных:** `references/events-yaml-spec.md` §14 — блоки `fca_stats` (замороженный
машинный слепок прогноза на момент составления) и `outcome_log` (журнал «прогноз vs факт»)
в `Claude-Memory/forecasts/*.yaml`.

## Как сторож устроен (чтобы не искать состояние)

- **Счёт** — по всем forecast-YAML (active + superseded + expired): заполненные записи
  `outcome_log`. **Clean-исход** = `record_type: horizon_resolve` + `shock_flag != exogenous_shock`
  + исход заполнен (`actual` для level / `resolved` для event). `interim_supersession` и
  shock-записи считаются отдельно и в зачёт M1/M3 не входят (анти-паттерн §14.4: interim шумнее).
- **«Сделанность» шага** — файлы-маркеры в `Claude-Memory/calibration/` (никакого скрытого
  состояния между запусками; вся история аудируема как файлы):

  | Маркер (имя жёсткое) | Что означает |
  |---|---|
  | `adhoc-YYYY-MM-DD.md` | ручной ad-hoc прогон калибровки (§M1) |
  | `calibration-YYYY-MM-DD.md` | отчёт будущего calibration-скилла (гасит M2) |
  | `source-rerating-YYYY-MM-DD.md` | пере-рейтинг источников (§M3) |
  | `catalyst-calibration-YYYY-MM-DD.md` | catalyst-калибровка v2-C (§M4) |

- **Повтор:** сработавший шаг перевзводится, когда его последний маркер старше
  `CAL_REPEAT_DAYS = 90` дней.
- Папки `calibration/` может не быть — она создаётся при первом сохранении отчёта.
  Пустой Glob = нулевые счётчики, это нормально.

## §M1 — Ad-hoc калибровка (порог: ≥15 clean-исходов; повтор каждые 90 дней)

Цель: первые честные метрики системы + обкатка порогов перед кодированием скилла.

1. **Собрать выборку.** Прочитать все `Claude-Memory/forecasts/*.yaml` (включая superseded/
   expired), выбрать заполненные записи `outcome_log`. Разложить по bucket'ам:
   - основной зачёт: `horizon_resolve` + `shock_flag: none`;
   - отдельно (справочно, НЕ смешивать с основным зачётом): `interim_supersession`, shock-записи.
   Внутри зачёта — разрезы по `kind` (level/event) и `domain`.
   **Дедуп по событию:** одно событие может резолвить несколько файлов (например, заседание
   ЦБ 24.07 — и квартальный `cbr-rate-2026-2027`, и микропрогноз `cbr-rate-jul24`). В метрики
   точности идут обе записи (это разные прогнозы), но при подсчёте **эффективного n** и
   выводах о значимости группировать по (тема, resolve_date) — 5 записей об одном заседании
   ≠ 5 независимых наблюдений.
2. **Посчитать метрики** (арифметика — скриптом/питоном в сессии, не «на глаз»):
   - **Brier** по `kind: event`: mean((predicted_p − resolved)²);
   - **coverage P10–P90** по `kind: level`: доля записей с `in_p10_p90 == true`
     (если поле не заполнено — сначала прогнать
     `skills/save-to-library/scripts/assemble_artifact.py complete-outcome-log`);
   - **bias**: средний знак и величина `error_pct` по level;
   - **weighted vs unweighted** — главный тест ценности trust-весов: сравнить
     |actual − forecast_l1_weighted| и |actual − forecast_l1_unweighted| по записям,
     где `forecast_l1_unweighted` непустой. Записи с `null # TODO` — пропустить, не фабриковать.
3. **Честность малого n.** При n < 30 писать выводы как «направление», не «вердикт»;
   coverage на n=15 имеет огромную дисперсию — флагать только грубые промахи (например,
   coverage < 50% при номинале 80%).
4. **Отчёт** — markdown: размер выборки по bucket'ам, метрики, что вне зачёта и почему,
   предложения по порогам `CAL_*` и провизорным константам `weighted_consensus.py`
   (`CONF_*`, `ANCHOR_*` — см. events-yaml-spec §16.2).
5. **Сохранить** как `Claude-Memory/calibration/adhoc-<сегодня>.md` — артефакт в чат →
   `save-to-library` (D3: скиллы сами в Claude-Memory не пишут). Если save-to-library ещё
   не знает поддиректорию `calibration/` — добавить её в реестр валидных путей
   (`skills/save-to-library`) первым делом, это маленькая правка.
6. Имя файла — **жёсткое** (`adhoc-<дата>.md`): по нему сторож считает M2 и каденс повторов.

## §M2 — Кодировать calibration-скилл (порог: ≥2 ad-hoc отчёта; гаснет при первом `calibration-*.md`)

После 2–3 ручных прогонов пороги и грабли известны — пора кодировать (handoff §4:
«скилл строить ПОСЛЕ 2–3 ad-hoc прогонов», §6 бэклог).

Архитектура (двухстадийная, как везде в системе):
1. **Скрипт** (детерминированный, stdlib): свип outcome_log → метрики §M1 по bucket'ам +
   вклад источников с флагами значимости (прошёл/не прошёл гейты §M3).
2. **LLM-стадия:** предлагает trust-дельты **только сверх гейтов**; правки — в
   `domains/{domain}/{source}-*.md` профили.
3. Отчёт скилла — `calibration/calibration-<дата>.md` (этим он гасит M2 у сторожа).

Действие при срабатывании: завести задачу в `docs/investment/TODO.md` (префикс согласовать,
например `CAL-`), спроектировать по образцу других скиллов со скриптами + тесты.

## §M3 — Пере-рейтинг источников (порог: ≥30 clean-исходов; повтор каждые 90 дней)

1. **Атрибуция вручную:** `outcome_log` не несёт источников — по каждому resolved-прогнозу
   поднять consensus-таблицу из парного `.md` (или `sources_used` в conditional-блоке) и
   посчитать, сколько clean-резолвов приходится на каждый источник. Нужно **≥5 на источник**,
   иначе источник не пере-рейтингуется в этот заход.
2. **Гейты перед правкой trust** (все четыре, handoff §4):
   - min-n на источник (≥5);
   - материальность: эффект источника на точность консенсуса заметен, не косметика;
   - консистентность: не один выброс, а систематика;
   - **Bayesian-nudge, не binary-flip**: trust — приор, партия исходов его сдвигает
     (HIGH → MEDIUM максимум за заход), а не переписывает. На малом n большинство источников
     гейт НЕ пройдёт — это честный результат, а не неудача.
3. Правки — в `domains/{domain}/`-профили (через ретро-аудит-петлю или напрямую с
   провенансом «calibration source-rerating <дата>»), затем `memory-sync`.
4. Отчёт → `calibration/source-rerating-<дата>.md` (кто прошёл гейты, какие дельты, кто нет и почему).
5. Помнить: `retrospective-forecast-audit` по публичной истории источника — **приор**,
   эта калибровка по твоим исходам — **апостериор**; они дополняют друг друга, не заменяют.

## §M4 — Catalyst-калибровка v2-C (порог: ≥30 resolved catalyst-предсказаний)

Счётчик `catalyst_resolved_count` монитор получает извне (payload) — пока persistent-учёт
catalyst-исходов не построен, в progress-line стоит «н/д», и это честно. Когда появится
учёт (predictions_for_review из weekly-review / coherence-audit накапливают резолвы) —
передавать число в payload.

При срабатывании: выполнить спеку **v2-C** из `docs/investment/TODO.md` (retrospective-audit
на ≥30 resolved predictions → calibration curve P(realized | predicted), Brier/log loss →
multiplicative factor в synthesizer). Отчёт → `calibration/catalyst-calibration-<дата>.md`.

## Как растить n (если счётчик стоит на месте)

Каденс из handoff §3: событие должно резолвиться ДО следующего прогноза (короткие
неперекрывающиеся горизонты):
- **заседания ЦБ** (~8/год) — event → Brier; `predicted_p` замораживать в `fca_stats`
  В МОМЕНТ прогноза, не задним числом;
- **месячная инфляция** (принт Росстата, ~12/год) — level → interval;
- добавлять **ближний горизонт «конец следующего месяца»** в регулярные месячные
  рефреши FCA (usdrub/brent/…) — нулевая маржинальная стоимость, +1 точка на фактор в месяц.

Незаполненные стабы outcome_log (позиция «незаполненных стабов N» в progress-line) — это
резолвы, которые монитор уже должен ловить алертами `[ИСХОД]` (outcome_capture): факт →
`outcome_log_updates` → save-to-library Workflow L.
