# Схема данных MCP ZenMoney (контракт v2)

Ответы инструментов — JSON вида `{data, references, nextCursor}` (у отчёта — `{currency, monthStartDay, months, references}`). Небольшие приходят прямо в контекст; большие (`list_accounts` ≈ 55 тыс. символов, операции за месяц ≈ 60–80 тыс.) среда сохраняет в файл — тогда разбирать кодом (`python3`/`jq`), а в контекст выводить только итоги.

**Названия больше не нужно искать отдельно.** Каждый ответ со ссылками несёт `references`: счета (`name`, `instrument`, `type`, `isInBalance`, `isSavings`, `isArchived`), категории (`name`, `parentId`, флаги), точки (`merchants[id].name`), настройки (`user.currency`, `user.monthStartDay`). `references` — справочник к странице, не дополнительные операции: их суммы не складывать.

Размеры ниже — замеры 2026-10-01 (символы JSON; токенов примерно в 2,5–3 раза меньше).

---

## 1. Инструменты

| Инструмент | Что даёт | Ограничения и стоимость |
|---|---|---|
| `get_monthly_report` | Факт, бюджет и план по категориям и переводам, сумма в RUB по курсам на даты | До 24 месяцев; **≈ 17 тыс. символов на месяц** с `references` |
| `list_transactions` | Фактические операции по датам учёта, с фильтрами | `from`/`to` обязательны; `limit` 1–200; ≈ 400–500 символов на операцию с `references` |
| `list_scheduled_transactions` | Плановые вхождения; `state`: `planned` (по умолчанию, включая просроченные), `processed`, `all` | Только созданные вхождения; те же фильтры |
| `list_accounts` | Все счета, включая архивные и виртуальные долги, с текущими остатками | **≈ 55 тыс. символов → файл**; `nextCursor` всегда `null` |
| `list_categories` | Все категории и теги, плоский список с `parentId` | ≈ 14 тыс. символов |
| `get_account_balances` | Остатки на даты (начало или конец дня) по 1–200 счетам и 1–31 точке | Малый ответ; неизвестный ID ломает весь запрос |
| `get_instrument_rates` | Курсы RUB за единицу на 1–31 дату | Малый ответ; неизвестный код валюты ломает весь запрос |
| `get_user` | Валюта, `monthStartDay`, настройки плана | Обычно не нужен — есть в `references.user` |
| `search_merchants` | Поиск точки или бренда по названию | Публичный бренд в выдаче не значит, что покупки были |
| `upsert_categories`, `create_merchant` | Запись | Только Режим C (`SKILL.md`) |

### Фильтры `list_transactions` и `list_scheduled_transactions`

Фильтры объединяются через И, значения внутри списка — через ИЛИ; списки 1–100 значений; применяются до пагинации.

| Фильтр | Что совпадает | Ловушка |
|---|---|---|
| `accountIds` | Операции, где счёт на любой стороне (включая долги) | Перевод попадёт целиком, с другой стороной |
| `categoryIds` | Только **основная** категория | **Дети не включаются** — перечислить явно; переводы не совпадают |
| `tagIds` | Только теги (не основная категория) | Переводы не совпадают |
| `merchantIds` | Точный `merchantId` | Переводы без точки; долги — через `accountIds` |
| `comments` | Подстрока комментария, без учёта регистра | Ищет только в `comment`, не в `originalPayee` |
| `types` | `income` / `expense` / `transfer` | Для итогов с учётом возвратов брать оба обычных типа |
| `incomeAmount`, `expenseAmount` | `from` (вкл.), `toExclusive`, `equalTo` в валюте счёта | Без пересчёта валют |

Пагинация: первая страница — `from`/`to` + фильтры + `limit`/`order`; дальше только `cursor` (и при желании `limit`); читать до `nextCursor = null`, затем агрегировать. Курсор отклонён — начать заново без него. Страницы живые, не снимок: при долгом чтении данные могут поменяться.

**Область месячного отчёта:** все счета с `isInBalance = true` (независимо от `isOtherUser`), категории и настройки планирования по умолчанию, прогнозы и исключения переводов. Траты по счетам с `isInBalance = false` в отчёт **не попадают**; они видны только в операциях (R8).

Контракт инструментов, ожидаемые поля и порядок проверки актуальности — `mcp-contract.md` и рецепт R9.

## 2. Операция (`list_transactions`)

| Поле | Смысл |
|---|---|
| `id`, `date` (YYYY-MM-DD) | Идентификатор, дата учёта |
| `expense`, `income` | `{accountId, amount}`. Расход — только `expense`, доход — только `income`; **перевод — обе стороны**, без `categoryId` |
| `categoryId` | Основная категория |
| `tagIds` | Дополнительные категории (теги), массив |
| `merchantId` | Точка (`m1_…`), имя — в `references.merchants`; может быть `null` |
| `originalPayee` | Сырое название из банка (латиница, номера филиалов). Пользователь его **не видит** в списке мест и не меняет — в приложении у операции название **места** (`merchantId`). В выгрузке CSV колонка «Кому» — этот же сырой текст |
| `payee` | Может встретиться у ручных операций; у банковских не приходит |
| `comment` | Комментарий (у переводов людям банк пишет туда имя) |
| `source` | `plugin` — из банка; `split` — часть разбитой операции; нет поля — введено вручную |
| `hold` | `true` — ещё в холде; у ручных операций поля нет |

**Пустые поля не приходят.** Отсутствие поля в конкретной операции — норма, не изменение схемы.

Особенности:
- Суммы в **валюте счёта**, без пересчёта. Пересчёт: `amount × rate(валюта, дата) / rate(основная валюта, дата)` по `get_instrument_rates` (при основной валюте RUB делитель = 1).
- Крипто в микро-единицах (`µETH`): 3 774 942 µETH = 1,774942 ETH.
- Долговые счета: ID — непрозрачная строка `a1_…`, копировать целиком; название — в `references.accounts`.
- Удалённые операции и корректировки начального остатка не возвращаются.
- Факты могут включать холды и операции будущей датой.
- Возврат покупки приходит как `income` с расходной `categoryId` (той же, что у покупки).
- Поездка (проект) по замыслу — элемент `tagIds`; тег хранится в списке категорий (тот же ID). Поездка в `categoryId` — не ошибка данных, но проблема учёта (сообщить, предложить перенос в тег; `SKILL.md`, «Аудит»), и в старых данных встречается: искать по обоим.

## 3. Месячный отчёт (`get_monthly_report`)

Ответ: `months → "YYYY-MM" → массив строк` + `references.categories` (названия и родители) + `references.accounts` (для строк переводов). Сумма всегда в валюте пользователя, по курсу на даты операций.

| `rowId.type.type` | Что это |
|---|---|
| `TagTotal` (`isIncome` true/false) | **Итог** расходов или доходов месяца |
| `Tag` без `categoryId` | «Без категории» |
| `Tag` с `categoryId` | Категория. Верхний уровень — `parentRowId.type.type == "TagTotal"`; дети — `parentRowId` с `categoryId` родителя |
| `Transfer` (`accountId`) | Переводы на счёт вне плана и обратно |
| `TransferGroup` (`transferGroupType`) | Группа переводов; `EXCHANGE_DIFF` — курсовая разница, только для сверки остатков |

Поля строки: `fact` («сырой»), `factWithRefund` (использовать его), `factCount`, `budget`, `planned`, `processed`, `residue`, `delta`, `isForecast`, `isHidden`, `isLocked`.

Правила:
- Итог = сумма строк верхнего уровня (проверено). Родитель и дети не суммируются вместе — ни в `Tag`, ни в `Transfer` под `TransferGroup`.
- `isHidden` влияет на отображение, не на итоги.
- Нулевые строки (по факту, бюджету и плану) не возвращаются — родителя может не быть. Строка с `fact = 0`, но с бюджетом приходит.
- Доходная строка родителя может иметь `factCount = 0` и `fact` = сумма доходных детей (возврат в подкатегории).
- Тегов в отчёте нет. Категории-поездки (`#…`) видны как обычные строки.
- **Доход в расходной категории** — строка с `isIncome: true` и `categoryId` расходной категории (возврат покупки). В `TagTotal` доходов она входит; `fact = factWithRefund`. В очищенных итогах — вычитать из обеих сторон (`SKILL.md`, принцип 5).
- **Итоги с переводами** (только по запросу): доход/расход с переводами = `TagTotal` + все строки `TransferGroup` того же `isIncome`, **кроме** `EXCHANGE_DIFF`. Показывать подписанными рядом с обычными, сравнивать периоды в одном и том же охвате.
- Плановые суммы (`planned`, `processed`) к факту не прибавлять.

## 4. Счета, категории, курсы

### Счёт (`list_accounts`)

`id`, `name`, `type` (`cash`, `card`, `checking`, `deposit`, `loan`, `debt`), `instrument` (валюта), `balance` (**текущий**, с холдами и будущими операциями), `isInBalance`, `isOtherUser`, `isSavings`, `isArchived`, `institution {id, name, countryCode}`, `externalIds` (последние цифры карт и счетов — **не выводить**), `startBalance`, `creditLimit`, `balanceCorrectionType`. У вкладов: `interestRate` (%), `openingDate`, `openingAmount`, `term` и `payoffPeriod` (ISO 8601: `P1M` — месяц, `P26915D` — дни; срок в десятки лет = фактически бессрочный), `capitalization`. У долгов — `merchantId` контрагента; `balance` «+» — должны пользователю, «−» — должен он.

Группы, как в приложении: сначала `loan`, затем `debt`, затем `isSavings = true`, затем остальные (вклады — накопления). `references.instrumentRates` в этом ответе — текущие курсы.

### Категория (`list_categories`)

`id`, `name`, `parentId` (`null` у корня), `isIncome`, `isExpense`, `isArchived`. Только два уровня: корни и прямые дети. Теги — те же категории (ID один и тот же). `isIncome`/`isExpense` — умолчания для отчёта, не тип операции; «Корректировка», «Инвестиции», «Другое» могут иметь оба флага. Имена не уникальны («Другое», «Медицина» встречаются несколько раз) — работать по ID.

### Остатки на дату (`get_account_balances`)

`dates: [{date, boundary}]`: `start` — до всех операций дня, `end` — после всех. Ответ: `balance` в валюте счёта и `balanceInMainCurrency` по курсу на эту дату — использовать как есть. Учитывает факты, холды, корректировки начального остатка, долги; не учитывает плановые. Это **реконструкция по текущим записям**, не исторический снимок. Неизвестный или чужой ID ломает весь запрос — ID брать только из `list_accounts`/`references`/полных ID карты.

### Курсы (`get_instrument_rates`)

`rate` — RUB за единицу (RUB = 1). Кросс-курс на дату: `rate(из) / rate(в)`. Если ранней истории нет, может вернуться более поздний курс; `null` — курса нет. Без `instruments` — все валюты счетов (включая архивные). Коды чувствительны к регистру; микро-единицы с префиксом `µ`.

### Роли по правилам (основной способ; карта хранит только исключения)

`isInBalance` не равен роли счёта: брокерские счета и вклады могут стоять с `false`, а мелкие кошельки — с `true`. Роль считается по правилам ниже **в этом порядке** (первое сработавшее), затем перекрывается исключением из карты по полному ID.

| № | Условие | Роль |
|---|---|---|
| 1 | `type` = `debt` или `loan` | `ignore` (долги; показывать только по запросу) |
| 2 | `isArchived` и остаток = 0 | `ignore` |
| 3 | `institution.countryCode` есть и не `RU` | `external` (внешний периметр) |
| 4 | валюта с префиксом `µ` или крипто-код (TON, BTC, ETH, USDT); или в названии «брокерск», «ИИС», «ценные бумаги», «крипт» | `investment` |
| 5 | `type: deposit` | `deferred` (вклад до срока) |
| 6 | валюта RUB | `liquid` (включая накопительные `isSavings`) |
| 7 | валюта USD или EUR | `fx-liquid` |
| 8 | прочие валюты | `trip-wallet` |

Типичные исключения, которые правила не видят (поэтому они в карте): накопительные счета с типом `deposit` (→ `liquid`), общий счёт (→ `shared`), зарубежный банк без страны в данных (→ `external`), брокерские счета без слова «брокерский» в названии (→ `investment`), просроченные или пустые дубли вкладов (→ `ignore`).

**Новые и сомнительные счета.** Не долговой счёт не из реестра известных счетов карты или из раздела «Под вопросом»: роль по правилу, но **в запас и итоги не включать** до подтверждения пользователем; показать блоком и предложить строку для карты. Архивные счета с остатком в запас не входят никогда (только строка «в архивных счетах ещё …»), если в карте нет исключения. Несколько счетов с одним названием — различать по ID; если правило даёт им разные роли или неясно, какой рабочий, — спросить.

**Уровни запаса (R3):** 1 — `liquid`; 2 — `fx-liquid`; 3 — `external`. `shared` в запас не входит (деньги общие), `trip-wallet`, `deferred`, `investment` — только упоминаются.

## 5. Стоимость вызовов (замер 2026-10-01)

| Вызов | Символов |
|---|---|
| `get_monthly_report`, 1 месяц | ≈ 17 000 |
| `list_transactions`, 1 операция | ≈ 400–500 (месяц ≈ 150–200 операций → файл) |
| `list_categories` | ≈ 14 000 |
| `list_accounts` | ≈ 55 000 → файл |
| `get_account_balances`, 2 счёта × 2 даты | ≈ 1 000 |
| `get_instrument_rates`, 2 валюты × 2 даты | ≈ 300 |

Главная экономия v2 — фильтры: выборка по категории, счёту или точке вместо чтения целых месяцев, и `references` вместо справочника.

## 6. Чего нельзя получить

- Теги в месячном отчёте (только через операции).
- Фильтр категории вместе с потомками одним значением.
- Исторический снимок данных: прошлые остатки — реконструкция по текущим записям.
- Будущие плановые платежи за горизонтом генерации.
- Перенос операций между категориями, правку операций и счетов (в этой среде нет инструментов записи для них).
