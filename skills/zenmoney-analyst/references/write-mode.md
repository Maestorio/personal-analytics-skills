# Режим записи в ZenMoney (Режим C)

Читать **до первого вызова любого инструмента записи** в сессии. Ядро правил — в `SKILL.md` (Режим C); здесь протокол, формат плана и ловушки инструментов.

Главный принцип: **каждое изменение или добавление в БД подтверждается пользователем отдельно.** Отката и восстановления удалённого в MCP нет; снимок «как было» — единственный план отката, и откат — тоже запись с подтверждением.

---

## 1. Протокол

1. **Понять просьбу.** Что именно менять и почему. Неясно, какие записи затронуты, — спросить, не угадывать.
2. **Проверить доступность.** Нужный инструмент есть в списке? Если вызов будет отклонён правилом доступа — сказать и остановиться.
3. **Снимок «как было».** Перечитать каждую затрагиваемую запись непосредственно перед планом (§4). Снимок операций при больше 3 пунктах — сохранить JSON-файлом в рабочую папку и отправить пользователю (`SendUserFile`); в `Claude-Memory` не класть.
4. **План.** Пронумерованная таблица (§2): одна строка — один пункт (одна категория, одна операция). Под таблицей: что меняется косвенно, чего сделать нельзя, как откатить.
5. **Согласие на каждый пункт.** Пользователь отвечает по пунктам («1, 2 — да, 3 — нет») или явно подтверждает весь показанный список («да, все 5»). Записываются только подтверждённые номера. Нет явного ответа — ничего не писать.
6. **Пилот.** Первый пункт нового вида в сессии (первая правка операции, первая смена категории у банковской операции, первое создание) — отдельным вызовом из одного элемента, проверка (шаг 8), затем остальные подтверждённые пункты.
7. **Запись.** В вызов — только подтверждённые пункты и только поля из плана. Не больше 10 операций в одном вызове. Создания и изменения — разными вызовами.
8. **Проверка после.** Перечитать каждую изменённую запись тем же способом, что и снимок; сравнить **все** поля со снимком: изменилось ровно то, что в плане, остальное совпадает. Показать «было → стало». Отличие от ожидаемого → стоп, показать пользователю, ничего не исправлять без нового согласия.
9. **Итог записи** (после любого `upsert_transactions`, обязателен; пустой список — «нет»):
   1. **Новые точки** — созданные в сессии (пользователь добавит им сайт в приложении).
   2. **Операции без точки** — дата, сумма в валюте счёта, текст банка, категория, предлагаемое читаемое имя; для импорта список готов в `without_merchant` ответа `stmt_propose.py payload`. Переводы, пополнения, комиссии не входят.
   3. **Сырые точки** — перечитать `merchantId` созданных операций: имя точки = строка банка (код терминала, «IP …», «MSPK 0100…») → предложить снять (`merchantId: null`, Т16) отдельным пунктом; чужой логотип бренда — отметить (Т17).
10. **Журнал.** Предложить строку для раздела «Журнал изменений в ZenMoney» карты (дата, что, сколько пунктов). Не записывать.

**Повторы.** Создание: новый `requestId` (UUID) на пакет; при сбое или таймауте — тот же `requestId`, то же содержимое, тот же порядок. Таймаут ≠ откат: перед любым повтором перечитать данные. Изменения: перед повтором перечитать; если запись уже в целевом состоянии — не повторять. `already_exists` / `already_deleted` в ответе — не ошибка и не повод переписывать: перечитать и показать.

## 2. Формат плана

| № | Действие | Запись (ID) | Поле | Было | Станет |
|---|---|---|---|---|---|
| 1 | изменить | операция `9f1c…` (полный ID), 2026-08-12, 4 500 ₽, «Пятёрочка» | категория | Возврат | Кэшбэк |
| 2 | создать | новая операция | дата / счёт / сумма / категория | — | 2026-10-01 / `<счёт>` / 350 ₽ / Кафе и рестораны |

Правила плана:
- В «Запись» — полный ID и узнаваемые признаки (дата, сумма, точка или комментарий), чтобы пользователь понял, о какой записи речь. Номера карт и `externalIds` не показывать.
- Каждое изменяемое поле — отдельной строкой со своим номером, если у записи меняется больше одного поля.
- Поля, которые **не** меняются, в плане не упоминать и в вызов не передавать.
- Строка «Откат»: какие значения вернуть, если пользователь попросит (из снимка).

## 3. Ловушки инструментов

### `upsert_transactions`

| № | Ловушка | Правило |
|---|---|---|
| Т1 | Передача `income` **или** `expense` заменяет **обе** стороны: пропущенная сторона удаляется | Для правки метаданных (категория, теги, точка, комментарий, дата) — **не передавать ни `income`, ни `expense`**. Менять суммы или счета — только по прямой просьбе и всегда полной парой сторон из снимка + изменение |
| Т2 | `categoryId: null` стирает и категорию, и теги | Никогда не передавать `null`, если пользователь прямо не просил убрать категорию. Смена категории — передать только новый `categoryId`; теги при пропуске сохраняются |
| Т3 | Теги не могут повторять основную категорию и требуют её наличия | При смене категории проверить, что новый `categoryId` не совпадает ни с одним тегом из снимка; совпадает — показать пользователю и спросить |
| Т4 | `merchantId: null` и `comment: null`/пустая строка стирают значение | Пропуск поля = сохранить. `null` — только по прямой просьбе |
| Т5 | `originalAmount`/`originalInstrument` — только парой | Не трогать, если не просили; пропуск обеих сохраняет пару |
| Т6 | Переводы игнорируют `categoryId`/`tagIds`/`merchantId` | Переводу категорию не назначать; если просьба требует — объяснить |
| Т7 | Долг — через `account: {type: "debt", merchantId}` и равные суммы с обычным счётом в его валюте | Создание долговых операций — только по прямой просьбе, с показом обеих сторон |
| Т8 | Суммы — в валюте счёта, без конвертации, не больше 4 знаков после запятой, строго > 0 | Валюту и сумму в плане показывать в валюте счёта |
| Т9 | Холд, источник, банковские метаданные не редактируются; нулевые операции не пишутся | Не пытаться |
| Т10 | Операции банковского плагина (`source: plugin`) | Метаданные (категория, теги, комментарий, точка `merchantId`) — можно; правка точки — пакет `{id, merchantId}` без сторон, после записи перечитать (синхронизация не должна вернуть старую). Суммы, счета и даты таких операций не менять: синхронизация банка может создать дубль. Если просят — предупредить и получить отдельное согласие |
| Т11 | Удаления и восстановления в MCP нет | «Удали операцию» — сказать, что через MCP нельзя, предложить приложение |
| Т12 | **`originalPayee` без `merchantId`**: ZenMoney подставляет точку с тем же нормализованным именем, если она есть, иначе может завести новую точку из этого текста (сырая строка банка → сырая точка; удалить и переименовать нельзя). Читаемый текст сам к существующей точке с другим написанием не привяжется | Есть точка в `search_merchants` → `merchantId` + исходный текст банка в `originalPayee`. Нет → читаемое имя, не строка банка. После создания перечитать `merchantId` каждой операции («Итог записи», п. 2–3) |
| Т13 | У дохода в расходной категории приложение само показывает «Возврат: <категория>» | В комментарий слово «Возврат» не писать |
| Т14 | Превращение записи в перевод (передать обе стороны): категория, контрагент и теги у перевода игнорируются и в приложении не видны; записи плагина — только после отдельного согласия (Т10), дату не менять | Для «Корректировки» источника пополнения — именно так (одна запись, не вторая рядом) |
| Т15 | `comment: null` стирает комментарий; пропуск — сохраняет | Убрать лишний комментарий — отдельный вызов `{id, comment: null}` без сторон |
| Т16 | `merchantId: null` снимает привязку, но точка остаётся в справочнике | Не обещать «чистый» справочник: убрать саму точку пользователь может только в приложении |
| Т17 | Логотип бренда ZenMoney подставляет сам по названию и может ошибиться (чужой бренд у местной точки) | Не исправляется через MCP — отметить в «Итоге записи», правит пользователь |

Создание операции: `date` (дата учёта), хотя бы одна положительная сторона, новый `requestId`. ID не генерировать — сервер присвоит. После создания найти операцию перечитыванием (§4) и показать.

### `upsert_categories`

- Создание требует `name`, `isIncome`, `isExpense` и `requestId`. Имена не уникальны — перед созданием проверить, нет ли уже такой (в том числе архивной); есть — спросить, создавать ли дубль.
- Пропущенные поля при изменении сохраняются; `parentId: null` делает категорию корнем.
- Два уровня: перенос категории с детьми под другой корень — дети в том же пакете (каждый ребёнок — отдельный пункт плана).
- Смена `isIncome`/`isExpense` меняет умолчания отчётов **за прошлые месяцы** — указать это в плане как косвенное последствие.
- Архив ≠ удаление: операции остаются.

### `create_merchant`

- Зачем: чтобы у операции была читаемая точка, а не текст банка. Перед созданием — `search_merchants`, показать совпадения; есть бренд или своя точка — привязать её `merchantId`, дубль не создавать.
- Создание — отдельный пункт плана с названием и согласием. Название — как его знает человек («Hoper's Bar»), не строка банка («IP ABDIRAZAQ»); проверить написание (регистр, апостроф): переименования и удаления нет, другое имя — другой ID.
- После создания — `merchantId` в словарь мест (`stmt_propose.py places-add --merchant-id`), чтобы при следующих импортах точка ставилась сама.
- Инструмента нет в сессии или вызов отклонён → сказать один раз и дать список для создания в приложении (название, дата и сумма операции); после — `search_merchants` и привязка `merchantId` отдельным пунктом. Обходных путей не искать (Режим C, п. 4).

### Запрещённые инструменты: `delete_transactions`, `upsert_accounts`

Есть в MCP с 2026-10-05, но **запрещены пользователем**: не вызывать ни при каких формулировках просьбы, в план не включать. Ответ: «удаление операций / правка счетов в скилле запрещены — это делается в приложении». Снять запрет может только пользователь явным решением; до правки этого раздела запрет действует.

### Будущие инструменты

До первого использования — загрузить схему, выписать её ловушки (что стирает `null`, что заменяется целиком) в план и спросить пользователя, разрешает ли он этот инструмент вообще. Протокол §1 — без изменений.

## 4. Как получить снимок записи

| Запись | Как перечитать |
|---|---|
| Категория | `list_categories` → элемент по ID |
| Операция по известному ID | `list_transactions` с `from = to = дата операции`, `accountIds = [счёт]` и, если нужно, `expenseAmount`/`incomeAmount.equalTo = сумма` → элемент по ID (фильтра по ID нет) |
| Операции группы (например, весь «Возврат» за месяц) | `list_transactions` с `categoryIds` и диапазоном, до `nextCursor = null`; снимок — файлом |
| Новая операция после создания | тот же фильтр по дате, счёту и сумме; ID — из ответа инструмента, сверить |

Снимок хранит **все** поля записи как пришли (включая `tagIds`, `merchantId`, `comment`, обе стороны) — по нему проверяется, что не изменилось лишнее.

## 5. Типовой сценарий: разнести старый «Возврат»

1. `list_transactions` с `categoryIds = [Возврат]` за выбранный месяц (не за все годы сразу).
2. Классифицировать кодом по точке, комментарию и счёту в предложения: «Кэшбэк», «Общак», возврат покупки (в категорию покупки), «оставить». Неясное — «оставить» и спросить.
3. План: одна строка на операцию (дата, сумма, точка/комментарий, Возврат → новая категория). Снимок — файлом.
4. Согласие по пунктам; пилот — одна операция; проверка; остальные подтверждённые — пакетами до 10.
5. В вызове у каждой операции только `id` и `categoryId`. Ни `income`, ни `expense`, ни `tagIds` (Т1, Т2).
6. Перечитать, сверить все поля со снимком, показать итог. После — сравнить месячный отчёт до и после: итоги расходов и доходов не должны измениться (меняется только разбивка по категориям); изменились — стоп и показать.
