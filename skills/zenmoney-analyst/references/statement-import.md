# Режимы E и F: выписка банка → ZenMoney (импорт и сверка)

Читать при просьбе «внеси / сверь по выписке», при PDF/CSV-выписке банка. Запись в ZenMoney — по Режиму C (`write-mode.md` читать **до первого вызова записи**).

**E — импорт:** выписка(и) → операции, которых нет в ZenMoney → добавление по согласию (категория, тег поездки, место).
**F — сверка:** выписка ↔ ZenMoney → расхождения → исправление (добавить, поправить сумму/дату, превратить «Корректировку» в перевод, разделить слитую сумму). Оба режима — один конвейер, разница в том, что предлагается.

## 1. Конвейер и скрипты

```
выписка(и) банка                 stmt_import.py узнаёт банк, тип счёта и валюту по содержимому — пользователь ничего не объясняет
 → parse_<банк>_statement.py     строки + проверки арифметики (blocking)       банк-специфично
 → <банк>_normalize.py           операции в общем формате (§2) + флаги         банк-специфично
 → MCP: list_transactions        только счета выписки, окно = период           общее
 → stmt_compare.py               классы расхождений (§4)                       общее
 → stmt_propose.py plan          пронумерованный план по write-mode.md §2      общее
 → согласие пользователя         по пунктам; пилот; перечитать                 Режим C
 → stmt_propose.py payload       пакеты upsert_transactions (Т1–Т10)           общее
 → get_account_balances          сверка остатков с банком                      общее
```

Реализованы банки: **FF** (Freedom Bank KZ) — `parse_ff_statement.py`, `ff_normalize.py` (§6); **BOG** (Bank of Georgia) — `parse_bog_statement.py`, `bog_normalize.py` (§6а, на живой записи не обкатан); **Т-Банк** — `parse_tbank_statement.py`, `tbank_normalize.py` (§6б); **Райффайзенбанк** — `parse_raif_statement.py`, `raif_normalize.py` (§6в). Банки с синхронизацией (BOG, Т-Банк, Райф) нормализуются построчно — как лежит синхронизация; для них главное — пропуски, «корректировки» вместо операций и точки (§5а). Новый банк = парсер + нормализатор + запись в `BANKS` (`stmt_import.py`: сигнатуры шапки) + строка в `docs/test-registry.md`; `stmt_compare.py`, `stmt_propose.py` менять не нужно, если нормализатор отдаёт формат §2.

Результаты скриптов содержат IBAN, суммы и тексты операций — **только локально** (рабочая папка вне git и вне `Claude-Memory`).

## 2. Общий формат операций (выход нормализатора)

`{"operations": [...], "flags": [...], "reconcile": {...}, "interest": [...]}`; операция:
`id` (стабильный хеш), `type` (`expense` | `refund` | `transfer` | `topup`), `date` (ISO; для покупки — дата транзакции), `booking_date`, `currency` и `amount` (в валюте счёта), `original {amount, currency}` (если покупка в другой валюте), `merchant {name, raw, country, city}`, `refs` (откуда в выписке); `transfer` — `from`/`to` `{currency, amount}`; `topup` — пополнение извне.
Флаги: `unknown-row`, `no-merchant`, `conversion-ambiguous`, `transit-unfunded` и т. п. — **показывать пользователю, не угадывать**.

## 3. Сколько операций читать (предупреждение пользователю)

- Окно выписки × счета выписки — не больше **200** операций ZenMoney: одна страница `list_transactions` (≈ 100 токенов на операцию, ≈ 25 тыс. токенов на страницу). Читать до `nextCursor = null`.
- **Больше 200 — предупредить:** «в окне N операций, чтение через MCP занимает много токенов; рекомендую Claude Code (страницы ответов сохраняются в файл и разбираются скриптом) либо нарезать период». В чате не начинать, пока пользователь не ответил. Больше ~1000 — CSV-выгрузка (`docs/zenmoney/csv-recompute.md`) или нарезка по периодам.
- Фильтр `accountIds` обязателен: другие банки в контекст не попадают. Перевод между счетом выписки и другим банком приходит с названием второго счёта в `references`; его операции не загружаются.
- Источник пополнения ищется окном ±3 дня: `list_transactions` с `comments`/`expenseAmount` по счетам пользователя — там обычно «Корректировка» или расход без пары.

## 4. Классы расхождений (`stmt_compare.py`)

`matched` · `differs` (ZenMoney выше банка на 1–3%: в приложении блокировка по курсу на авторизацию, банк рассчитывает по итоговому; сумма банка — истина) · `date_shift` (сумма до копейки, дата на недели: ≤45 дней, от 50 — ≤120) · `to_other_account` (у банка покупка или перевод, в ZenMoney — перевод на другой счёт; сравнение `transfer_out` включается флагом `--with-transfer-out`) · `merged` (одна сумма ZenMoney = несколько покупок банка одного места) · `partial_transfer` (совпала одна сторона) · `topup_currency` (банк зачислил одну валюту, пользователь внёс в другую) · `expense_vs_transfer` (банк перевёл на свой счёт в другом банке, в ZenMoney — расход: превратить запись в перевод) · `missing_in_zen` · `missing_in_bank` (+ `adjustment` — «Корректировка баланса»). У банков с несколькими счетами одной валюты (Т-Банк, Райф) сравнение — по одному счёту за прогон: `--bank-account <договор|счёт> --accounts RUB=<id>`. В `stmt_propose.py plan`: непарная запись ZenMoney + непарная покупка банка той же категории → **правка** записи (`fix_rework`), а не «создать + удалить».
Что остаётся без пары в банке — список «на удаление/решение» (`delete_transactions` запрещён: удаляет пользователь в приложении).

## 5. Правила записи (решения пользователя 2026-10-10)

1. **Данные из банка — истина.** В операции банка нет категории и часто нет места: категория — из словаря мест, потом пользователь; тег поездки — по датам поездки из карты (покупка и её возврат — одна категория и один тег или оба без).
2. **Словарь мест** `{ZENMONEY_DIR}/stmt-places.json` (подстрока названия → категория/контрагент/`merchantId`) — пишет только `stmt_propose.py places-add` (исключение D3, `CLAUDE.md`). Точка ставится сама, только если в записи есть `merchantId` (`--merchant-id`); одно имя (`--merchant`) — лишь подсказка в плане «точка: найти …». Нашли или создали точку для постоянного места — дописать её `merchantId`.
3. **Названия мест — официальные**; если двойное/сложное — так, чтобы было понятно, что делать. В `originalPayee` — читаемое имя точки, **не сырая строка банка с кодом терминала** (`терминал\СТРАНА\ГОРОД\ТОЧКА` → последний сегмент): сервер создаёт контрагента по тексту `originalPayee`, если `merchantId` не указан, а удалить/переименовать контрагента нельзя. Есть подходящий контрагент в `search_merchants` → `merchantId` + исходный текст; нет → читаемый `originalPayee` (так делает `payload`; сырую строку без `merchantId` он не шлёт) и точка в «Итог записи» — создать (`create_merchant` по согласию, `write-mode.md`) или пользователь заводит в приложении.
4. **Слово «Возврат» не писать:** приложение само показывает «Возврат: <категория>» у дохода в расходной категории. Комментарии не добавлять без просьбы.
5. **Комиссия — отдельная расходная операция**, а не разница сумм перевода: комментарий «Комиссия <банк>», категория «Счета», на счёте-получателе. Промежуточный счёт, которого пользователь не ведёт (деньги пробыли там день), не заводить: перевод прямо источник → итоговый счёт на полную сумму + операция-комиссия.
6. **«Корректировка» источника пополнения** (плагин банка не знает получателя) — превращать в перевод **той же записью** (обе стороны; категория у перевода не нужна), а не создавать второй перевод: иначе исходящая сумма посчитается дважды. Изменение суммы/счёта записи плагина — отдельное согласие (Т10); дату не менять.
7. **Транзитные валюты** (деньги в них не держат): конвертация + покупка = одна покупка в валюте источника с исходной суммой; возврат с обратной конвертацией частями = один возврат. Остаток округления переносится на следующую покупку.
8. **Проценты по депозиту** — по умолчанию не вносить; вносить, если пользователь хочет точный остаток («Поступления по процентам»). Копейки «Прием вклада» — внутреннее движение, не проценты.
9. **Исправление остатка до банка:** остаток на начало периода — корректировкой на дату **до** периода (не влияет на статистику года), остальное — настоящими операциями.
10. **Итог — сверка остатков** `get_account_balances` с банком: разность раскладывается на невнесённые пополнения, проценты, записи без пары. Не сходится — искать, а не подгонять корректировкой.
11. **Идемпотентность:** каждая операция банка имеет стабильный `id`; решения пользователя хранить по `bank_id` (не по номеру пункта — номера сдвигаются); создание — новый `requestId` на пакет, повтор — тот же.
12. **Контрагента не придумывать — спрашивать.** Название места в выписке нет или оно неоднозначно (код вместо названия, «PRO», несколько подходящих в `search_merchants`) → не угадывать по сумме или похожей операции, а спросить пользователя. Случай 2026-10-11: «PRO» 20 USD записан как Anthropic, а это Perplexity.
13. **Скриншоты Apple Pay — дополнительный источник для FF и BOG:** в выписке такого банка Apple Pay не показывает место (банк его не знает), а приложение «Кошелёк» по каждой карте (у FF несколько карт на одни счета — по скриншоту на карту) показывает название места, город, сумму в валюте покупки и дату. Просить скриншоты «Последние операции» по каждой карте, сверять по дате и сумме; сумма в валюте покупки — проверка исходной суммы.

## 5а. Точки и «корректировки» у операций, которые уже есть в ZenMoney

Сверка находит не только пропуски: у пар «банк ↔ ZenMoney» план (`stmt_propose.py plan`, `place_review`) проверяет точку:

- `fix_place` — **нет точки** · **перепутана** (комиссия банка с точкой места или покупка с точкой банка — синхронизация Т-Банка путает их у покупок в валюте) · **по словарю мест другая** · **сырая** (имя = текст банка и похоже на строку банка: без кириллицы либо с номерами, «//», «№»). Предложение точки: словарь → та же точка у других операций этого места → найти (`search_merchants`) или спросить (правило 12). Запись — `{id, merchantId}` (метаданные, у операций плагина можно, Т10); точка верная — решение `keep` и место в словарь.
- `places_suggest` — места, у всех операций которых одна точка и одна категория, а словарь их не знает: таблица «В словарь мест», запись — `places-add --merchant-id` по «да» (сам план словарь не пишет).
- `fix_to_transfer` — класс `expense_vs_transfer`: та же запись → перевод (обе стороны, Т14); счёт-получатель называет пользователь, подсказка — банк получателя из выписки; запись плагина — только с отдельным согласием (`plugin_ok`). `create_transfer_out` — перевода на свой счёт нет в ZenMoney.
- Записи без пары в банке, которые вместе дают 0 (корректировка туда и обратно), помечены «группа даёт 0» — скорее лишние, чем пропущенные; удаляет пользователь в приложении. Перевод из такой группы меняет и второй счёт — показать это до решения.

## 6. FF (Freedom Bank KZ): особенности

- Выписки — PDF с текстовым слоем (OCR не нужен): разбор по координатам слов (`pdftotext -bbox`); три проверки на файл (число строк, суммы колонок, остатки), не сошлось — blocking.
- Мультивалютная карта: **четыре текущих счёта (RUB, USD, KZT, EUR) обязательны вместе** (конвертация и каскадное списание видны в двух файлах); депозитные — необязательны (нужны для остатка и процентов). Счёт FF в ZenMoney = текущий + депозит; «Прием/Выплата вклада» — внутреннее движение.
- Транзитные по умолчанию EUR и KZT; пары конвертаций — по «курсу» из текста либо по согласованности курса; неоднозначное — флаг.
- Банк иногда не пишет место (≈20% покупок): место — из приложения банка (скриншоты) или от пользователя.
- Входящее пополнение в рублях удерживает 500 RUB.
- Сумма VND в тексте выписки — в сотых долях (2440 = ₫244 000); нормализатор умножает на 100 (`TEXT_SCALE`). Сумма в USD верна.
- Пустая выписка (нет операций) — остатки без числа, принимается как 0.00.

## 6а. BOG (Bank of Georgia): особенности

Модуль подготовлен заранее: счета BOG в ZenMoney подключены банковской синхронизацией, импорт нужен для сверки и на случай обрыва синка.

- Выписка — **xlsx** (листы `Details`, `Transactions`), один файл = один IBAN, счёт мультивалютный (колонки GEL/USD/EUR/GBP). Банк узнаётся по IBAN `GExxBG…` (в шапке названия банка нет). Депозитный счёт — отдельный файл; обязательных наборов, как у FF, нет.
- Проверки парсера: после каждой строки `Balance` остаток по каждой валюте; исходящий остаток (строгий); знак и валюта строки против текста. **Причуда банка:** в `Balance` валюта без движения за день иногда показана как ровно 0 при ненулевом остатке (4 из 97 строк на реальной выписке) — это не ошибка, а `checks.zero_quirk`; любое ненулевое расхождение — blocking.
- **Цепочки не склеиваются** (в отличие от FF): операция — по валюте списания, как её показывает банк и как лежит в синхронизированном счёте ZenMoney. Покупка в чужой валюте: сумма списания (GEL/USD) + `original` (JPY, ARS…); комиссия конвертации банка уже внутри суммы.
- Обмен («Automatic conversion, rate: R») — `transfer` с двумя суммами; пара — в пределах даты и курса, в том числе кросс EUR↔USD. Нет пары — флаг `conversion-unmatched`.
- **Комиссия** (обслуживание, защита карты) банк показывает тремя строками: Payment GEL 5 / Income GEL 5 / Payment USD 1.87. Синхронизация ZenMoney кладёт это как расход GEL 5 (категория «Счета») + обмен USD 1.87→GEL 5 — нормализатор делает так же (`kind=fee` + `transfer` how=`fee-conversion`), иначе каждый месяц будет расхождение. Взаимно гасящаяся пара без обмена («Placing funds on deposit») — в `internal`, не операция.
- Переводы между своими счетами — `transfer_out`/`topup` со счётом контрагента; сопоставление сторон — задача сравнения, не нормализатора. Chargeback («გაპროტესტებული თანხა») — `topup` с пометкой.
- Сверка по IBAN × валюте: Δ остатка банка = сумма операций (невязка 0.00, считается по строкам — ловит потерянные и задвоенные).
- **Счета ZenMoney — по названию и валюте, без номера счёта:** `stmt_accounts.py --list <list_accounts> --bank bog --currencies GEL,USD,EUR` (метка банка в названии — `account_patterns` в `stmt_import.BANKS`; не депозитный и не архивный; два подходящих — спросить, нет — `missing`). Выводит готовую строку `--accounts`. Банк определяется и по `institution.name` счёта. С `--iban <IBAN выписки>` сверяются `externalIds` счёта ZenMoney («2USD» = последняя цифра IBAN + валюта, у депозита «0830» = последние 4 цифры): `mismatch` — выписка относится к другому счёту банка, чем найденный в ZenMoney (пример 2026-10-11: депозит `BOG Депозит $` имеет `0830`, а приложенная выписка — `…0831`). Страховка — сверка остатка банка на конец выписки с `get_account_balances` (`check_balances`).
- **Сравнение с ZenMoney (проверено на живых данных 2026-10-11, счета `BOG $`/`Лари`/`€`):** `stmt_compare.py --with-transfer-out --accounts GEL=…,USD=…,EUR=…` (по одному счёту ZenMoney на валюту; депозитный счёт в список не включать — валюта совпадёт с текущим). Окно 2024-10-11…2026-10-10: 202 операции ZenMoney, 2 страницы; **185 пар сошлись**, 4 — `to_other_account` (ZenMoney кладёт покупку «MOBILE ICOCA» и переводы на свой депозит переводом на другой счёт — не ошибка), 2 были настоящими находками учёта (дублирующий ручной расход GEL 33.03 «Такси» от 2025-02-17 при уже внесённых плагином 32.96 и компенсирующая «Корректировка» +33.03 от 2025-04-24) — пользователь удалил обе, после перечитывания ZenMoney: 185 пар, 4 `to_other_account`, расхождений нет, 189 операций банка = 189 операций ZenMoney. Остатки банка на 2026-10-10 = остатки ZenMoney (USD 11.51, GEL 0, EUR 0, депозит 0).
- **Депозит `BOG Депозит $` без выписки (2026-10-11):** выписку по нему найти не удалось (приложенная `…0831` — другой счёт). Согласованность проверена косвенно: в ZenMoney в депозит вошло 505 + проценты 0.86, вышло 505.86 (остаток 0); банк (сторона `BOG $`) видит ровно те же шесть выплат с `…830` на 505.86 и входы 495 + 10 → проценты 0.86 подтверждаются арифметикой, остаток на 2025-04-24 (500) и на 2026-10-10 (0) совпадает. Что НЕ проверено: суммы и даты отдельных процентных начислений (нужна выписка депозита).
- Валидация модуля: настройка на срезе 2026, проверка на 2025 и 2024 — 0 незнакомых строк, 0 флагов, невязка 0 (но перечень видов строк я смотрел по всей выгрузке до разбиения, поэтому 2025 — не слепой тест).
- **Скриншоты Apple Pay (§5 п. 13) BOG почти не нужны:** в выписке BOG место платежа есть всегда (в отличие от FF). Сверено 2026-10-11 по двум скриншотам карты (11 строк с 2025-11-03): все 11 есть в выписке с той же датой транзакции и той же исходной суммой/валютой. Скриншот добавляет только город и русское написание названия — для имени контрагента, не для сумм.
- GBP (пользователь: никогда не будет) в данных не встречался; колонка в выписке остаётся и разбирается, но отдельной логики для неё нет.
- Не реализовано: PDF-выписки BOG.

## 6б. Т-Банк: особенности

- «Справка о движении средств» — PDF с текстовым слоем; **один файл = один договор** (карта, совместный, накопительный), всё в валюте договора. Разбор по координатам слов; описание переносится строками внутри ячейки.
- **Входящего остатка в справке нет** — только «доступный остаток» на дату и итоги «Пополнения/Расходы». Проверки парсера: суммы строк = итоги (до копейки), знак и сумма двух колонок, валюта узнана. Остаток — против ZenMoney: `get_account_balances` на дату остатка = «доступный остаток» (`check_balances`).
- Счёт ZenMoney — по последним 4 цифрам договора в `externalIds`: `stmt_accounts.py --bank tbank --currencies RUB --contract <договор>` (накопительные тоже).
- Строки: «Оплата в <место> <город> <страна>» — покупка (место без города и страны); покупка в чужой валюте — `original` + отдельная строка «Комиссия за операции … в иностранной валюте» с тем же временем списания (`fee_for`); «Внутренний перевод на договор N» — на свой договор из приложенных справок `transfer_out`, на чужой — расход p2p; «Перевод себе» связывается с договором-источником по встречной строке (±5 мин); кэшбэк одного времени — одной суммой (как синхронизация); проценты, СБП, снятие наличных, «Компенсация поездки» — свои виды.
- Синхронизация кладёт комиссию за валюту отдельным расходом с точкой «Т-Банк», но у части покупок в валюте точки комиссии и покупки перепутаны — `fix_place` «перепутана».

## 6в. Райффайзенбанк: особенности

- CSV из интернет-банка (UTF-8 с BOM, «;»); **ни номера счёта, ни периода, ни остатков в файле нет**. Счёт — по текстам операций («Со счета: *N» у списаний, «На счет: *N» у зачислений, «р/с» у зарплаты); не узнан — спросить и передать `--account FILE=N`. Проверки — построчные; сверка остатка — только Δ остатка ZenMoney за окно = сумма операций (`reconcile.sum_operations`). Окно сравнения — период, который пользователь выгружал (в файле — лишь даты первой и последней операции).
- Счёт ZenMoney — по последним 4 цифрам счёта в `externalIds` (`--contract <N>`).
- СБП «Телефон получателя … Банк получателя X»: свой телефон (на который переводили в ≥2 банка, или `--own-phone`) → `transfer_out` с банком получателя (подсказка для счёта-получателя); чужой → расход p2p. «Перевод между счетами Клиента» — свои счета Райфа. Расход и зачисление одного номера документа на одну сумму — отменённая операция (`internal`).
- Задача по Райфу — пропуски и «корректировки» (счета синхронизируются, картой почти не пользуются): `expense_vs_transfer`, группы «даёт 0», точки комиссий.

## 7. Ошибки, которые уже были (не повторять)

- Короткий ID (8 символов) в записи — отклоняется сборщиком (`FULL_ID`); писать только полный ID из MCP.
- Решения по номерам пунктов после пересборки плана попадали не на те операции → решения по `bank_id`.
- Тест на данных, на которых правила подгонялись, не считать проверкой качества: нужна независимая выборка (другой год).
- Название места по умолчанию из соседней операции или по сумме (PRO → Anthropic, Starbucks → Grab из-за городского кода) — нет, правило 12.
- В `originalPayee` при создании — **всегда читаемое имя** (правило 3), даже для места «без контрагента»: сырая строка банка с кодом терминала создаёт контрагента на сервере (2026-10-11 это повторилось на разделении «гостиница + экскурсия»; контрагент остался, привязку сняли).
