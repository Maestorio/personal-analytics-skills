# macro-ru-watcher

Pure signaling panel для российских макроиндикаторов. Собирает данные с первоисточников, считает diff к предыдущему snapshot, флагирует аномалии. **Не интерпретирует, не прогнозирует, не рекомендует.**

---

## Inputs / Outputs

**Inputs:**
- Web/API данные: ЦБ РФ, MOEX ISS, CBR, FRED — через web_search / web_fetch
- Предыдущий snapshot ← `Claude-Memory/macro-snapshots/ru-<date>.md` через Synology mount

**Outputs (как artefact в чат):**
- `ru-<date>.md` → пользователь проверяет → save-to-library кладёт в `Claude-Memory/macro-snapshots/`

**Upstream скиллы:** —
**Downstream скиллы:** macro-forecast-chain (читает snapshot), ru-portfolio-advisor (mode 8)
**Shared refs:** transport-layer, claude-memory-layout

---

## Режим «Обнови инфляцию»

Запрос «обнови инфляцию» — только недельная инфляция, без снимка семи индикаторов: Шаги 1–6 не выполняются. Прочитать `references/inflation-mode.md` и выполнить его: найти последнюю недельную публикацию Росстата/МЭР и записать её скриптом `scripts/save_inflation.py` (файл `macro-snapshots/inflation/model.jsonl`, в чат — одна строка итога). Файла владельца `owner.jsonl` скилл не трогает; режим «без ИИ» скрипт отклоняет кодом 3.

## Глобальные принципы (применяй ВЕЗДЕ)

1. **Pure signaling, never forecasting.** Этот скилл собирает данные. Никаких «это плохо для рубля», «вероятно, ЦБ снизит ставку», «инфляция снижается, что бычий сигнал». Только snapshot → diff → флаги аномалий → ссылки на первоисточники.

2. **Каждое число — со ссылкой на первоисточник из ТЕКУЩЕЙ сессии.** Не из памяти модели, не из training data. Если web_search не вернул свежие данные — индикатор помечается ❓, не подменяется «знанием».

3. **Язык вывода — русский.** Все элементы отчёта (заголовки, таблицы, флаги, источники) на русском. Названия индикаторов и тикеры — на латинице (Brent, IMOEX, RGBI), но описания и комментарии — на русском.

4. **Без интерпретаций.** Если в шаблоне нет места для «комментария аналитика» — значит, его нет. Любая попытка добавить «what does it mean» — методологический брак.

5. **z-score флаг — единственный механизм.** Аномалия определяется через 1σ rolling window по 12М исторических данных. Никаких «выглядит большим движением» по ощущениям.

## Workflow (6 шагов + шаг 0)

### Шаг 0. Транспорт

Прочитать `references/transport-layer.md` (пути, проверка доступности). Транспорт
один — Synology mount; недоступен → остановиться и сообщить пользователю.

Перед первой записью в Claude-Memory прочитать `_hub/settings.json`; `ai_mode: off` → в Claude-Memory не писать, сообщить владельцу, что сайт в режиме без ИИ и правки идут с сайта.

---

### Шаг 1. Определи tier

По умолчанию **Tier 1** — 7 базовых индикаторов (см. `references/sources-ru.md`).

Активация **Tier 2** (+4 индикатора) — по явному запросу пользователя:
- «расширенный макроотчёт»
- «полный snapshot»
- «с tier 2»
- «добавь US 10Y / VIX / ликвидность / резервы»

Tier 3 (квартальные roll-up отчёты) — отдельный режим, см. §«Roll-up».

### Шаг 2. Прочитай предыдущий snapshot

```
files = Glob("ru-*.md", path=MACRO_SNAPSHOTS_ROOT)
```

**Synology conflict rule:** если есть `ru-<date>.md` и `ru-<date> (N).md` —
использовать только `ru-<date>.md` (без суффикса), конфликтные копии игнорировать.
Признак конфликтного файла: имя содержит ` (` перед `.md`.
Конфликтный файл сигнализирует о несинхронизированной правке на другом устройстве.
Если каноничный файл отсутствует (есть только конфликтная копия) — предупредить
пользователя и использовать конфликтную копию с пометкой ⚠️.

Отсортировать по имени (дата в имени файла). Взять: самый свежий (prev), ~недельной давности (weekly diff), ~месячной давности (monthly diff). Читать через `Read`.

Если snapshot'ов нет — первый запуск. Сохранить без diff и без флагов аномалий. Пометка: «Первый запуск, недостаточно данных для аномалий».

Если snapshot'ов меньше 12 — z-score считается на доступной выборке с пометкой «короткое окно (N недель), пороги ориентировочные».

### Шаг 3. Определи торговый контекст и собери current snapshot

#### 3.1. Сначала: запусти `scripts/fetch_macro.py`

Этот скрипт детерминированно собирает 5 из 7 Tier-1 индикаторов через
публичные API (MOEX ISS + CBR DailyInfo) за ~2 секунды:

| Ключ JSON | Индикатор |
|---|---|
| `cbr_key` | Ключевая ставка ЦБ (%) |
| `usd_rub` | USD/RUB закрытие MOEX |
| `cny_rub` | CNY/RUB закрытие MOEX |
| `rgbi` | RGBI (индекс ОФЗ price index, ~120 — совместим с историей snapshots) |
| `imoex` | IMOEX (индекс акций Мосбиржи) |

**Запуск:**
```bash
python3 skills/macro-ru-watcher/scripts/fetch_macro.py
```

Парси JSON: `indicators[<name>].value` / `prev_close` / `change_pct` / `as_of` / `status`.

**Если `status: "error"`** для отдельного индикатора — пометь `❓ не получено`,
продолжай (как и при провале web_search). Скрипт уже сделал 3 ретрая.

**Не запускай скрипт повторно** в рамках одного снапшота.

#### 3.2. Обработка нерабочих дней (для оставшихся индикаторов)

Перед web_search для Brent — определи, является ли сегодня торговым днём:
- Выходные / российские праздники → торгов нет, ищем данные последней торговой сессии
- Скрипт `fetch_macro.py` сам возвращает `as_of` последней доступной сессии — это уже учтено

Для инфляционных данных торговый день не релевантен (публикации Росстата по своему графику).

#### 3.3. Затем: web_search для оставшихся 3 индикаторов Tier 1

| Индикатор | Источник |
|---|---|
| Инфляция г/г | Росстат / ЦБ |
| Инфляция недельная | Росстат |
| Brent | EIA |

Целевой web_search или web_fetch по списку из `references/sources-ru.md`.
Один запрос на индикатор.

**Делегирование субагенту (рекомендуется):** чтобы сырые выдачи не копились в твоём
окне, запусти ОДНОГО субагента (**model: haiku**) на все поисковые индикаторы разом.
Промт самодостаточный (агент не читает SKILL.md и не может спросить):

```
Найди через web_search три индикатора и верни СТРОГО JSON-массив:
{"indicator": "cpi_yoy|cpi_weekly|brent", "value": <число>, "as_of": "YYYY-MM-DD", "url": "..."}
Правила: значение — только со страницы из результатов ЭТОЙ сессии (ничего из своих
знаний); as_of — дата данных, не публикации; предпочтительные источники: Росстат/ЦБ
для инфляции, EIA для Brent; не нашёл/страница не открылась → {"indicator": "...",
"status": "failed"} — честный отказ лучше догадки.
```

Ты валидируешь его JSON (число? дата парсится? URL есть?) и вставляешь в отчёт;
`status: failed` → индикатор `❓ не получено` (тот же fail-fast, что и ниже).
Битый формат ответа → отбросить и выполнить поиски самостоятельно (fallback).
Правило «каждое число — со ссылкой из текущей сессии» распространяется на сессию
субагента: его URL идут в отчёт как первоисточники.

**Tier 2 (если активирован)** — все 4 индикатора через web_search (см. секцию
Tier 2 в `sources-ru.md`); при делегировании — тем же субагентом, добавь их в список.

**Fail-fast при сбое.** Если web_search/web_fetch вернул пустой результат, ошибку,
или явно неподходящую страницу — индикатор помечается `❓ не получено`, остальной
отчёт продолжает собираться. НЕ заполняй знанием из training data.

**Запрещено:** launch_extended_search_task. Скилл собирает 7–11 индикаторов
с известных URL — DR здесь избыточен и лишает контроля над источниками.

### Шаг 4. Посчитай diff и аномалии

Для каждого индикатора:
- **Δ нед** = (current − prev_week) / prev_week × 100% (для уровней) или absolute (для %-ставок)
- **Δ мес** = (current − prev_month) / prev_month × 100%
- **z-score**: расчёт по `references/anomaly-detection.md`

Флаг аномалии = `|z| ≥ 1.0`. Это ровно 1σ — по нормальному распределению ~32% наблюдений за порогом, что соответствует «заметному движению, заслуживающему внимания», без false-positive штормов.

**Не флагуем:**
- Изменения ниже 1σ — это рутинный шум
- Изменения выше 3σ при low-quality history (<8 weeks) — слишком зашумлены, помечай отдельно как «возможная аномалия, требует ручной проверки»

### Шаг 5. Сгенерируй отчёт и передай на сохранение

Шаблон — `references/output-template.md`.

Сгенерировать отчёт как **artefact в чат** (`ru-{YYYY-MM-DD}.md`).

После показа отчёта — вывести короткое подтверждение:
«Snapshot готов: ru-{date}.md, [N] аномалий: [список тикеров с ⚠️].
Для сохранения вызови `save-to-library`.»

save-to-library кладёт файл в `Claude-Memory/macro-snapshots/ru-{date}.md`
(`Write("{MACRO_SNAPSHOTS_ROOT}/ru-{YYYY-MM-DD}.md", content=...)`); прямой
`Write()` из этого скилла не используется.
⚠️ Если папка `macro-snapshots` недоступна — **не писать в корень и никуда ещё**:
остановиться и сообщить пользователю.

### Шаг 6. Обнови Claude Memory

После успешного сохранения — обновить запись в Claude Memory через `memory_user_edits`.

**Формат записи (≤500 символов):**
```
[macro] Снапшот {YYYY-MM-DD}: ставка {X}%, инфл {X}% г/г, USD/RUB {X}, CNY/RUB {X}, Brent ${X}, IMOEX {X} (Δнед {±X}%), RGBI {X} (Δнед {±X}%). Аномалии: {тикеры с ⚠️ или «нет»}. Данные MOEX за {дату сессии если нерабочий день}.
```

**Логика обновления:**
1. Проверить через `memory_user_edits(command="view")` — есть ли уже запись с тегом `[macro]`
2. Если есть → `replace` по номеру строки
3. Если нет → `add`

**Что писать в память:**
- Только цифры и флаги аномалий — никакой интерпретации (те же anti-patterns)
- Если какой-то индикатор `❓ не получено` — писать `❓` в записи, не опускать
- Дату сессии MOEX если отличается от даты снапшота

## Anti-patterns (что НЕЛЬЗЯ делать)

❌ **Интерпретировать динамику.**
Плохо: «Рост USD/RUB на 1.9% — следствие ослабления цен на нефть».
Хорошо: «USD/RUB +1.9% (z=2.0σ ⚠️) · Brent −2.1% (z=−1.3σ)». Корреляция остаётся в голове читателя.

❌ **Делать прогнозы.**
Плохо: «При сохранении тренда USD/RUB достигнет 95 к концу мая».
Хорошо: текущее значение + diff + флаг. Точка.

❌ **Давать рекомендации.**
Плохо: «Рекомендуется зафиксировать прибыль по позициям в RGBI».
Никогда. Это compliance issue, и это не задача скилла.

❌ **Заполнять пробелы памятью.**
Плохо: «USD/RUB = 91.20» (без URL, потому что web_search упал).
Хорошо: «USD/RUB ❓ не получено · попробуй ещё раз через час или укажи альтернативный источник».

❌ **Скрывать data quality issues.**
Если за 4 недели было только 6 наблюдений вместо 12 → явная пометка «короткое окно». Не делай вид, что z-score рассчитан корректно.

❌ **Использовать launch_extended_search_task.**
DR избыточен и медленен. Скилл ходит по 7–11 известным URL — это работа для web_fetch / web_search, не Deep Research.

## Scheduled task в Cowork (рекомендованный режим использования)

В Cowork: `/schedule` → задача «Запусти macro-ru-watcher каждую субботу в 10:00 MSK с tier 1. Сохрани в Claude-Memory/macro-snapshots/. Обнови Claude Memory. В чате выдай только short-form summary (аномалии + ссылка на файл)».

**Почему суббота, а не пятница:**
- Пятница вечером — пиковое время использования ИИ → дороже
- Суббота утром: все торги пятницы закрыты и зафиксированы, данные стабильны
- Скилл автоматически берёт данные последней торговой сессии (пятницы) при запуске в нерабочий день

Cowork требует Desktop app открытый и Mac/PC проснутым в момент запуска. Если ноут спит — задача пропускается; следующее срабатывание в штатное время.

Для extended режима (tier 2) — отдельная scheduled task, например, первая суббота месяца.

## Roll-up отчёты (Tier 3, опционально)

Раз в квартал пользователь может попросить: «макро roll-up за квартал».

Скилл читает все snapshot'ы за период (`Glob("ru-*.md", path=MACRO_SNAPSHOTS_ROOT)` → Read), собирает quarterly aggregate отчёт:
- Средние значения индикаторов за квартал
- Диапазоны (min/max + даты экстремумов)
- Кумулятивные изменения (Δ за квартал)
- Топ-5 weekly аномалий за квартал (наибольший |z|)

**Без интерпретаций.** Те же anti-patterns применяются. Roll-up — компактная сводка фактов, не quarterly review.

- **`references/output-template.md`** — Markdown-шаблон отчёта с примерами заполнения для нормального запуска, первого запуска, и запуска с битыми источниками

Reference читается ОДИН раз в начале сессии, не на каждый индикатор.
