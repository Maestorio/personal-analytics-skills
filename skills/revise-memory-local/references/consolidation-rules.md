# consolidation-rules: правила консолидации локальной памяти

## Когда объединять два файла в один

Объединяй, если:
- Оба файла описывают **одного человека, один проект или одно предпочтение**.
- Один является подмножеством другого (один добавляет детали к тому же факту).
- Оба `type: user` и описывают один аспект рабочего стиля.

Не объединяй, если:
- Разные `type` (например, `user` и `feedback` не объединяются — разные роли).
- Файлы описывают разные проекты, даже если оба `type: project`.
- Объединение приведёт к записи >400 слов — лучше оставить как есть.

При объединении: сохранять путь более содержательного файла; более старый удалять.

## Долгосрочное vs временное

**Долгосрочные** (сохранять и уточнять):
- Предпочтения пользователя: язык, стиль ответов, формат вывода
- Рабочие процессы: как пользователь привык работать с инструментом
- Уровень знаний: где силён, где новичок
- `feedback`-записи с явными Why/How to apply

**Временные** (удалять после завершения):
- Конкретные дедлайны с прошедшей датой
- Статус «в процессе» задачи, которая уже завершена
- Контекст «этой недели» / «этого спринта»

Признаки временности: содержит конкретную дату из прошлого, слова «сейчас», «в процессе», «следующий шаг», ссылку на завершённую задачу.

Если `type: project` и дата прошла → удалить файл или перенести постоянный вывод
(например, «пользователь предпочёл подход X в таких-то случаях») в `user_*.md`.

## Как обрабатывать устаревшие project-записи

1. Прочитать файл — понять, есть ли в нём долгосрочный вывод.
2. Если вывод есть → перенести как одно предложение в подходящий `user_*.md` или
   `feedback_*.md`. Удалить `project_*.md`.
3. Если выводов нет → удалить без переноса.
4. Никогда не обновлять `project_*.md` «под будущее» — для нового проекта создавать
   новый файл в новом разговоре.
5. Если вывод есть, но восстановить `Why:` и `How to apply:` невозможно — не мигрировать
   в `feedback_*.md`: оставить `project_*.md` и добавить во frontmatter строку
   `status: awaiting_context`. То же для `feedback_*.md` без `Why:`/`How to apply:`, чей
   контекст утерян: правило не придумывать, пометить `status: awaiting_context`.

## Чистка reference-записей

Удалять `reference_*.md`, если:
- Ресурс устарел или больше не используется (инструмент заменён, канал закрыт).
- Ссылка дублирует то, что уже есть в CLAUDE.md.
- Ресурс легко найти заново из общедоступных источников (не несёт уникального контекста).

Сохранять, если: ресурс нестандартный (внутренний инструмент, нестандартный путь, кастомный Slack-канал, специфическая команда которую сложно вспомнить).

## Порог уплотнения MEMORY.md

- MEMORY.md ≤150 строк → всё хорошо.
- MEMORY.md 151–180 строк → рекомендуется уплотнение при следующей ревизии.
- MEMORY.md >180 строк → обязательное уплотнение сейчас.

Способы уплотнения:
1. Удалить строки устаревших `project`-записей.
2. Объединить похожие записи одного типа.
3. Укоротить хук (часть после `—`) — детали должны быть в файле, не в индексе.

## Anti-patterns

❌ **Объединять записи разных типов.** `user` и `feedback` выполняют разные роли.

❌ **Удалять `feedback`-запись только потому, что она «мелкая».** Мелкие корректировки часто самые важные.

❌ **Перезаписывать `feedback`-файл без чтения Why.** Why определяет, применимо ли правило в новом контексте.

❌ **Создавать записи с датами в будущем.** Память описывает то, что уже известно.

❌ **Хранить draft-записи без type в frontmatter.** Любой файл без `type` — сигнал незавершённой записи; либо заполнить, либо удалить.

❌ **Трогать файлы вне директории `memory/`.** CLAUDE.md, SKILL.md, настройки Claude — не территория этого скилла.
