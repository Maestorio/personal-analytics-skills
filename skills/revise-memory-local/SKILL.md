# Ревизия локальной памяти

Рефлексивный проход по тому, что известно о пользователе и его работе. Цель: будущая
сессия должна быстро ориентироваться — с кем работает пользователь, на чём сосредоточен,
как предпочитает работать — без повторных вопросов. Структура файлов и типы записей
описаны в `references/memory-structure.md`.

---

- Обновлённые файлы памяти → `~/.claude/projects/*/memory/` (merge дублей, удаление устаревших, исправление фактов)

## Локализация директории памяти

Директория памяти для текущего проекта:
```
~/.claude/projects/<project-slug>/memory/
```

`<project-slug>` — sanitized путь рабочей директории (слэши → дефисы, пробелы → `-`).
Пример: `/Users/you/Documents/personal-analytics-skills` →
`-Users-alexey-Documents-----------claude_skills`.

Если точный slug неизвестен:
```
Glob("*/memory/MEMORY.md", path="~/.claude/projects/")
```
→ найдёт все активные индексы памяти; выбрать тот, что соответствует текущему
`working_directory` из системного промпта.

Единственная точка входа — `MEMORY.md`. Читай его первым.

## Фаза 1 — Инвентаризация

1. Прочитать индекс:
   ```
   Read("~/.claude/projects/<slug>/memory/MEMORY.md")
   ```
2. Получить список всех файлов:
   ```
   Glob("*.md", path="~/.claude/projects/<slug>/memory/")
   ```
3. Бегло прочитать каждый файл. При просмотре отмечать:
   - **Устаревание:** содержит дату из прошлого, упоминает завершённый проект,
     говорит «сейчас»/«на этой неделе».
   - **Перекрытие:** два файла описывают один аспект (стиль, проект, источник).
   - **Неполнота:** файл без `type` в frontmatter; `feedback`-файл без `Why:`/`How to apply:`.
   - **Раздутость MEMORY.md:** строк >180.

4. Составить мысленный список: что объединить, что удалить, что дополнить.
   Не начинать правки до конца инвентаризации.

## Фаза 2 — Консолидация

Детальные правила — в `references/consolidation-rules.md`.

**Разделяй долгосрочное и временное.** Предпочтения, рабочий стиль, ключевые
контакты и повторяющиеся процессы — долгосрочные: сохранять и уточнять.
Конкретные проекты, дедлайны и разовые задачи — временные: если дата прошла или
работа завершена, либо удалить файл, либо перенести полезный вывод
(например, «пользователь предпочитает формат X для документов запуска») в
долгосрочную `user_*.md` запись.

**Объединяй перекрытия.** Если два файла описывают одного человека, проект или
предпочтение — объедини в один, сохранив путь более содержательного файла.
Не объединяй файлы разных типов.

**Проверяй структуру feedback-записей.** Каждый `feedback_*.md` должен содержать
три части: само правило, строку `**Why:**` (причина) и `**How to apply:**` (когда
срабатывает). Если они отсутствуют — дополнить из контекста файла; если контекст утерян — не выдумывать, оставить запись и добавить во frontmatter `status: awaiting_context`.

**Исправляй временны́е ссылки.** «На следующей неделе», «в этом квартале», «к
пятнице» — переводи в абсолютные даты, чтобы записи оставались читаемыми спустя
время. Если восстановить точную дату невозможно — удалить временную ссылку.

**Проверяй frontmatter.** Каждый файл должен иметь `name`, `description` и `type`.
Если `type` отсутствует — восстановить из имени файла (`user_*` → `user`, и т.д.).
Если не ясно — спросить пользователя или удалить.

**Удаляй то, что легко переспросить.** Если запись пересказывает то, что можно
получить из календаря, документов или инструментов по запросу — убирать.
Оставлять то, что сложно восстановить: явные предпочтения, контекст за решением,
к кому обращаться по каким вопросам.

## Фаза 3 — Чистка индекса

Обнови `MEMORY.md` так, чтобы он оставался в пределах 200 строк и ~25 КБ.
Одна строка на запись, не длиннее ~150 символов:
```
- [Название](файл.md) — однострочный хук
```

Проверить при обновлении:
- **Убери** ссылки на удалённые файлы.
- **Укороти** строки, в которых есть детали, которым место в самом файле.
- **Добавь** всё важное, что появилось или изменилось.
- **Уникальность:** каждый файл упоминается ровно один раз.
- **Хук отвечает на вопрос «зачем это помнить»**, а не просто пересказывает название.

При >180 строках → обязательное уплотнение до ≤160 (с запасом на рост).

## Anti-patterns

❌ **Трогать файлы вне директории `memory/`.** CLAUDE.md, SKILL.md, `.claude/settings.json` — не территория этого скилла.

❌ **Создавать дубли типов.** Один аспект рабочего стиля = один файл. Если похожий уже есть — обновить его, не создавать новый.

❌ **Перезаписывать `feedback`-файл без чтения `Why:`.** Why определяет, применимо ли правило в новом контексте — без него коррекция слепая.

❌ **Удалять `feedback`-запись только потому, что она «мелкая».** Мелкие корректировки часто важнее крупных — они ближе к конкретному поведению.

❌ **Молча удалять записи с неясным статусом.** Если непонятно, актуальна ли запись — спросить пользователя, а не удалять по умолчанию.

❌ **Сохранять в память то, что уже есть в CLAUDE.md.** Дублирование только засоряет контекст.
