# travel-stage-builder

Дев-скилл (не пользовательский). Помогает спроектировать и реализовать новую
стадию пайплайна `travel-planning` так, чтобы она вписалась в существующие
паттерны и не сломала уже работающие стадии.

Скилл **сначала планирует и обсуждает, потом реализует**. Реализация
не начинается без явного «да» от пользователя.

Работает только в корне репозитория `claude_skills` — он правит файлы скилла
`skills/travel-planning/` и дев-документацию `docs/travel-planning/`. Если
текущая директория — не этот репозиторий, сказать об этом и остановиться.

## Поток

Шесть фаз строго по порядку. Не перепрыгивать: без чтения документации
(Фаза 1) план будет неверным; без согласования (Фаза 5) — реализация
преждевременна.

### Фаза 1 — Чтение документации (обязательно, целиком)

Прочитать `Read`'ом **все** перечисленное. Это не опционально — план,
построенный без полного контекста, нарушит паттерны.

| Файл | Что даёт |

| `skills/travel-planning/references/storage-and-naming.md` | transport, имена файлов, §6.x — YAML-схемы по стадиям |
| `skills/travel-planning/references/stage0/stage0-scope.md` | образец stage-reference (структура §1–§11) |

### Фаза 2 — Уточнение стадии

Если из запроса пользователя не очевидно, уточнить ОДНИМ компактным
сообщением (можно `AskUserQuestion`):

- какой номер стадии и её рабочее имя (`stageN-{name}`);
- одна атомарная задача стадии (одна — не несколько);
- вход: какие артефакты предыдущих стадий потребляет;
- выход: что за markdown-файл производит, для какой следующей стадии.

Если методология (`travel-planning-methodology.md`) уже описывает эту
стадию — взять задачу/вход/выход оттуда и подтвердить у пользователя,
а не выдумывать заново.

### Фаза 3 — Черновик плана

Перечислить конкретные файлы к созданию/правке. Типовой набор для новой
стадии (брать применимое, не раздувать):

1. **`references/stageN/stageN-{name}.md`** — новый stage-reference.
   Структура строго по образцу: §1 Назначение · §2 Inputs/Outputs ·
   §3 Поток · §4 Gate-проверки · §5 Параметры · §6 Промт/методика ·
   §7 Правила работы · §8 Структура выходного файла · §9 Граничные
   случаи · §10 Что НЕ делать · §11 Следующий шаг.
2. **`scripts/{name}.py` + `tests/test_{name}.py`** — только если Фаза 4
   подтвердила, что есть детерминированная работа. stdlib-only.
3. **`SKILL.md`** — строка в routing-таблице, строка в activation-gate,
   строка в model-routing; mini-spec блок, если стадия склонна к drift'у.
4. **`storage-and-naming.md` §6.x** — YAML-схема выходного файла стадии
   (для Stage 3/4/5 базовые схемы уже зарезервированы — расширить).
5. **`docs/travel-planning/architecture.md`** — обновить §8, при
   нетривиальных решениях добавить раздел.
6. **`docs/travel-planning/changelog.md`** — запись новой версии (v0.X)
   в формате существующих записей.
7. **`docs/test-registry.md`** — блок нового файла тестов (аннотация `# …` + команда
   `python3 …`); запуск — `python3 tools/run_tests.py travel-planning`. В CLAUDE.md тесты не перечисляются.

### Фаза 4 — Оптимизация плана

Прогнать черновик через чек-лист. Каждый пункт — либо «применили», либо
«осознанно не нужно».

- **Граница LLM vs script** (`architecture.md` §2): детерминированное →
  скрипт, семантика → LLM. Чётко, не размыто.
- **Атомарность.** Стадия решает ровно одну задачу и не залезает в работу
  соседних стадий (Stage N не приоритизирует за Stage N+1 и т.п.).
- **Model routing.** Начать с того, что говорит методология, но помнить
  эмпирику: Sonnet без thinking срезает углы на сложных стадиях. Если
  стадия объёмная — заложить Opus и model self-check, как у Stage 2.
- **Anti-drift.** Для стадии с риском срезания углов — mini-spec прямо в
  `SKILL.md` (канонические имена, шкалы, обязательные шаги).
- **Anti-bloat.** Sanity-порог на доминирующую категорию (как
  `OUTLIER > 30%` в Stage 2), если стадия категоризует.
- **Opt-in fallback.** Если есть скрипт — он не падает, а возвращает
  диагностику; при ошибке скилл спрашивает пользователя (3 варианта),
  не парсит молча сам.
- **Manual + environment-aware save.** Стадия выдаёт markdown в чат и не
  пишет автоматически (кроме Cowork+Synology). Цены, не проверенные на
  агрегаторе, — TODO.
- **Чистота скилла.** В `SKILL.md`/`references/` не должно протекать
  дев-материалов: упоминаний других скиллов, `_shared-references`/`pack.sh`,
  фраз «by design», changelog, ссылок на калибровочные кейсы как на тесты
  (см. чек-лист в `CLAUDE.md`). Это всё — в `docs/travel-planning/`.

### Фаза 5 — Презентация плана и обсуждение (СТОП)

Показать пользователю итоговый план: список файлов, ключевые решения
(граница LLM/script, модель, нужен ли скрипт, edge cases), и что осталось
открытым вопросом.

**Остановиться.** Не начинать реализацию. Дождаться явного одобрения или
правок. Если пользователь правит план — внести и показать снова.

### Фаза 6 — Реализация

Только после «да». Реализовать файлы из согласованного плана в порядке:
сначала stage-reference, затем скрипт, затем тесты, затем правки
`SKILL.md`/`storage-and-naming`, в конце `architecture.md`/`changelog.md`.

После реализации:
- прогнать тесты (новые и затронутые регрессионные) и показать результат;
- кратко отчитаться: что создано/изменено, что осталось TODO.

Коммит не делать, если пользователь не попросил.

## Что НЕ делать

- Не реализовывать до одобрения плана (Фаза 5).
- Не строить план, не прочитав документацию из Фазы 1 целиком.
- Не выдумывать задачу стадии, если методология её уже описывает.
- Не объединять две задачи в одну стадию — это нарушает атомарность.
- Не оставлять дев-материалы в файлах скилла `travel-planning`.
- Не коммитить без явной просьбы.
