# Спайк: лабораторный PDF → `PLAN.json` локально на Mac, без Claude

**Статус: отложено решением владельца 2026-11-10 — делать позже в его системе локальных моделей (`../LLM`, mlx-lm); не начат. Исполнитель — локальная сессия Claude Code на Mac (данные и модель только там).**
Спайк — эксперимент, ограниченный одним рабочим днём, с заранее названной метрикой и порогами
решения. По его итогу решается, появляется ли в здоровье путь «PDF → показатели» без Claude, или
остаётся только ручной ввод (задача 3.2 `START.md`) и Claude.

Железо: MacBook Air M4, 16 ГБ. Пределы — `07-autonomy-local-api.md` §3 (модели до 8–14B в 4 бит,
`docs/mlx-lm-guide_4.md` разделы 15 и 19). Документы — почти всегда текстовые PDF, сканы редки.

## 1. Что не меняется

- Запись в `labs.json`/`studies.json` делает только `intake.py apply PLAN.json [--apply]`; спайк
  производит **только `PLAN.json`** (формат — `skills/health-labs/references/intake.md` «Формат PLAN.json»).
- Dry-run и подтверждение каждой строки владельцем остаются обязательными: ошибка «число ↔ название»
  в медицинских данных дороже отсутствия импорта.
- Числа и нормы — только из документа; нормы нет → `ref: null`. Никаких «типичных норм» из модели.
- Данные не покидают Mac. Облачные провайдеры для здоровья запрещены (решение 2026-10-20).

## 2. Материал и эталон

- 5–8 текстовых PDF из «Медицинские анализы», **уже внесённых через Claude**, из ≥ 3 лабораторий
  (Инвитро, Helix, KDL, Гемотест — у кого что есть) + 1–2 скана как контроль.
- Эталон — точки `labs.json`, у которых `src` указывает на этот файл (их выставил Claude и подтвердил
  владелец). Сравнение по строкам: `marker` (id из словаря), `value`, `unit`, `ref`.

## 3. Кандидаты (гонять все три на одном материале)

| Вариант | Конвейер | Зачем |
|---|---|---|
| **А. Детерминированный** | `pdftotext -layout` или `pdfplumber` (таблицы) → строки «показатель · результат · ед. · референс» → словарь синонимов (`intake.md` «Словарь показателей» + имена из `labs.json`) → `PLAN.json` | без модели вообще; если хватает, модель не нужна |
| **Б. Локальная VLM** | страница PDF → изображение (`pdftoppm`) → Qwen3-VL-8B / Qwen2.5-VL-7B 4-бит через `mlx_vlm` → JSON строго по схеме `PLAN.json` → валидатор JSON (≤ 2 повтора) | единственный вариант для сканов и «съехавшей» вёрстки |
| **В. Гибрид** | текст из А → текстовая Qwen3-8B-4bit (`mlx_lm`) только для сопоставления названий с id словаря и разбора нормы «<5,2», «Не обнаружено» | меньше памяти, чем Б; закрывает слабое место А (синонимы и форматы норм) |

Промт для Б/В: «извлеки только то, что есть в документе; нет значения — пропусти; нет нормы — `null`;
ответ — JSON по схеме». Любой «домысел» в выводе — критическая ошибка варианта.

## 4. Метрика и пороги

На каждый документ и вариант: доля строк эталона, найденных верно по всем четырём полям (полнота);
доля выданных строк, верных по всем полям (точность); число **критических** ошибок (значение приписано
другому показателю, выдуманная норма); время на документ; пиковая память.

| Результат на текстовых PDF | Решение |
|---|---|
| полнота и точность ≥ 95 %, критических 0 | строим `skills/health-labs/scripts/pdf_to_plan.py` (M): терминал Mac, выход `PLAN.json`, затем штатный `intake.py` dry-run → подтверждение → `--apply` |
| 80–95 % или критические есть, но редки | только как предзаполнение формы ручного ввода (3.2) с показом строки оригинала рядом с каждым полем |
| < 80 % | путь снимается; остаётся ручной ввод и Claude |

Сканы оцениваются отдельно и решение по ним не блокируют.
