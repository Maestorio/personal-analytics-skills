## 3. Три варианта денежной базы для докупки (и почему выбран один)

Обозначения: `T_full` = L1-план класса × NAV; `F` = сумма в замороженных тикерах (не растёт);
`Open` = открытые тикеры с целевыми весами `w_i` (Σ по открытым = `S`, доля от `T_full`).

| Вариант | target_i (₽ на тикер) | Вердикт |
|---|---|---|
| A. Текущая факт. сумма акций | `w_i × L2_cur` | ❌ база сама занижена → недобор класса маскируется, never closes |
| B. Полная плановая сумма (`T_full`) | `w_i × T_full` | ❌ открытые бумаги превышают свой же cap относительно РЕАЛЬНОЙ книги (доказано численно, см. §7) |
| **C. Неподвижная точка (принято)** | `w_i × T*` | ✅ единственный вариант без нарушения caps и без маскировки разрыва |

**Формула T\*** (условие самосогласованности — открытые бумаги ровно на целевых весах,
замороженная часть неизменна):

```
T* = F + S·T*  →  T* = F / (1 − S)
```

Это gross-up: `F` — фиксированная часть, `(1 − S)` — доля, которую она должна занимать в
итоговой книге. `L2_cur < T* < T_full` всегда, если `F` меньше своей полной целевой доли.

**Почему НЕ вариант B, даже если лишние деньги «просто остаются в кэше/TMON»
(контраргумент, который стоит учитывать при code review):**
Cap — риск-лимит, а не декларация о намерениях. Риск реализуется на **фактически удерживаемой
позиции сейчас**, а не на гипотетической полной книге. При варианте B открытая бумага занимает
долю выше cap в РЕАЛЬНОЙ книге прямо сегодня — на всё время, пока гейт по другим бумагам не
снят (может быть недели, может быть неопределённо долго). Плюс: когда гейт снимется, придётся
подрезать переросшую бумагу, чтобы освободить место — B не приближает к целевой книге, а
создаёт отложенную вынужденную продажу.

### 3.1 Вырожденный случай (деление на ноль)

Формула определена только когда `S < 1`, то есть когда в классе есть хотя бы одна позиция
с ненулевым весом, которая сейчас **не может** быть докуплена до таргета (активный
gate/`no_buy`-constraint). Если таких позиций нет — `F = 0` и `S = 1` одновременно (вся
книга «открыта» в терминах гейтов), и `F / (1 − S)` вырождается в `0/0`.

**Guard перед вызовом формулы:** если среди тикеров класса нет ни одного с одновременно
`(real_weight < target_weight)` И активным блокирующим статусом (`review_needed` /
`reviewed_under_review` / `review_aging` / явный `no_buy`) — `T* = T_full`, деление не
применяется вообще. Отдельно: если `(1 − S) < 0.01` (S близко к 1, но не равно) — тоже
fallback на `T_full` и флаг на ручную проверку, а не досчёт: при знаменателе, стремящемся
к нулю, `T*` численно нестабилен и может давать абсурдно большие числа при малейшей
неточности во входных весах.

### 3.2 Из чего на самом деле состоит `F`

`F` — не только gate-заблокированные тикеры. За цикл в классе реально пять категорий
(правка `docs/investment/spec-gate-aware-sizing-trim-fix.md`, задача A, 2026-08-21 — вводит
пятую, `Rebalancing`, дискриминируя её от `Selling`):

| Категория | Определение | В `F`? | В `S`? |
|---|---|---|---|
| **Blocked** | таргет не достигнут, активный gate/`no_buy` — купить нельзя | да | нет |
| **Dormant** | таргет достигнут (в пределах hysteresis, Rule 3 — `\|real − target\| < 1 п.п.`) либо нет триггера на пересмотр — купить можно, сигнала нет | да | нет |
| **Open** | есть разрыв к таргету, гейта нет — можно двигать | нет | да (`w_i`) |
| **Rebalancing** | **срез до определённой плановой доли**; после исполнения позиция стоит на `w_i` | нет | **да (`w_i`)** |
| **Selling** | полный выход либо выход траншами без определённой целевой доли | нет | нет — см. 3.3 |

Формула устойчива к смешению Blocked и Dormant в одном `F`: если Dormant-тикер уже стоит
на целевой доле (`F_i ≈ w_i × T_full`), он не создаёт разрыв `T_full − T*` — разрыв
формируется только Blocked-компонентой, недосчитанной относительно своего веса. Различать
их для самого расчёта не нужно, но нужно **для отчёта пользователю** — иначе фраза «X%
книги недостижимо» вводит в заблуждение, если на деле большая часть `F` — просто позиции
без сигнала, а не позиции под блокировкой.

**Связь с эмпирикой (макс. 3–4 бумаги с рекомендацией «купить» за 3–5 месяцев):** не
случайность, а прямое следствие уже существующего правила `rebalance-framework.md:20` —
Rule 2, «Cap per cycle — ≤4 позиции за один rebalance». `Open` по построению не может быть
больше 4 тикеров за цикл → `S`, как правило, мало → `(1 − S)` близко к 1 → `T*` в норме
близко к `F`, а не к `T_full`. Резкий разрыв `T_full − T*` — сигнал, что среди недостигших
таргета много именно Blocked, а не штатная картина цикла. `Rebalancing` добавляет к `S` тот
же тип вклада, что и `Open` (целевой вес тикера этого цикла) — вывод не меняется, просто
`S` теперь считается по объединённому множеству «тикеры, двигающиеся к таргету в этом
цикле», а не только по докупаемым.

### 3.3 Тикеры на продажу/сокращение — дискриминатор Rebalancing vs Selling

Тикер с активным сигналом «продать»/«сократить» (Шаг 3, `rebalance-framework.md:116-135`)
делится на два разных случая, только один из которых заморожен в смысле формулы:

**Дискриминатор** — один вопрос: *определён ли для позиции целевой вес после сокращения,
и равен ли он её плановой доле?*

- **да → `Rebalancing`.** Остаток после среза — неподвижная величина, стоящая ровно на
  `w_i`: по определению `Dormant` из §3.2, только известная заранее (потому что сокращение
  уже решено, а не гипотетическое). Позиция входит в `S` со своим `w_i`, `target_i = w_i ×
  T*`, докупка выходит отрицательной и равна сумме среза. Обоснование исключения из `F`
  целиком (как раньше делала неразличавшая случаи категория `Selling`) — распространение
  довода «он уменьшается, а не остаётся неподвижным» на всю позицию, хотя он верен только
  для продаваемой части. Исключать остаток из `F` — занижать `T*` и удерживать открытые
  бумаги ниже их относительных весов, то есть получать тот же дисбаланс корзины, ради
  предотвращения которого механизм и введён (численный пример — задача A, §2 её спеки:
  занижение `T*` на 4 017 366 ₽, докупка занижена в 1,8 раза).
- **нет (цель 0, «выходим траншами», либо цель не задана) → `Selling`.** Как и раньше:

  1. Исключается и из `F`, и из `S` — не участвует в fixed-point расчёте.
  2. Его `w_i` пересматривается (частичное сокращение без известной цели → меньший `w_i`;
     полный выход → `w_i = 0`). Высвобождающийся вес **не перераспределяется автоматически**
     между оставшимися тикерами — это отдельное инвестиционное решение, не побочный эффект
     арифметики. Дефолт — unallocated до явного решения.
  3. Ожидаемая выручка от продажи (если тайминг по Шагу 3 уже решён) добавляется в пул
     доступного кэша для докупки `Open`/`Rebalancing`-тикеров — отдельно от свежих
     пополнений. Саму формулу `T*` это не меняет (она по-прежнему от `F` и `S` без учёта
     продаваемого) — меняется только сумма, реально доступная на закрытие разрывов.

Реализация дискриминатора — ручной флаг, не автоклассификация: `--trim` (Rebalancing) и
`--selling` (Selling) в `scripts/gate_aware_sizing.py` задаются аналитиком явно. Выводить
«это трим, а не продажа» из вердикта (`advisor_verdict: TRIM`) автоматически — отдельная,
пока не реализованная задача (вердикт TRIM не несёт целевой доли, а дискриминатор требует
именно её).

## 4. Второй knob: денежная база не единственная переменная

Строго корректная модель — risk-contribution-weighted (вклад в дисперсию портфеля, не в
капитал), но она требует инфраструктуры волатильностей/корреляций, которой у частного
инвестора нет. Поэтому используется двухуровневый прокси:

| Метрика | Знаменатель | Роль |
|---|---|---|
| Операционный cap (сайзинг покупок) | `T*` (§3, вариант C) | Реагирует только на изменения внутри акционной книги |
| Tail-risk / correlation-breakdown проверка | `NAV − кэш` | Периодическая (не при каждой покупке), ловит сценарий схлопывания корреляций акции↔рискованные облигации в системном шоке |

`NAV` (с кэшем) как знаменатель — отклонить: строго доминируется вариантом «NAV − кэш»
(отличается только домножением на константу, кэш не несёт риска и не разбавляет ничего
содержательного).

## 5. Разрыв, который нужно закрыть отдельно: куда идёт `T_full − T*`

Часть L1-плана класса, недостижимая из-за гейтов (`T_full − T*` в пересчёте на NAV), должна

## 7. Тестовый кейс (для валидации после правки)

Вход: `F = 2 782 500`, открытые тикеры с весами RENI 11%, MBNK 4%, X5 5,5% (`S = 0,205`),
`T_full = 4 000 000`.

Ожидаемый результат после правки:
- `T* = 2 782 500 / (1 − 0,205) = 3 500 000`
- target(RENI) = `0,11 × 3 500 000 = 385 000`
- target(MBNK) = `0,04 × 3 500 000 = 140 000`
- target(X5) = `0,055 × 3 500 000 = 192 500`
- Сумма докупки = разница между target и текущим holding по каждому (при факте RENI 350 000 /
  MBNK 120 000 / X5 180 000 → 35 000 + 20 000 + 12 500 = **67 500 ₽**, с точностью до
  округления лотов ≈ 66 700 ₽).

> С 28.10.2026 ручной режим применяет правило «замороженная перевешенная бумага — на плане»: при плановой доле BLK 20% (11 000 000 ₽ против 20% × книга 4 500 000 = 900 000 ₽) она ушла бы в `S`, база стала бы планом класса. Эталон §7 сохранён тестом с подправленной фикстурой (у заморозки нет плановой доли — рубли остаются в `F`); поведение оригинальной фикстуры при новом правиле — `TestFrozenOnPlanManualDefault.test_spec7_original_fixture_under_new_rule`.
>
> **11.11.2026 правило отменено** (spec-gate-aware-sizing-trim-fix.md §10.7): заморозка выше плана — в `F` своими рублями, оригинальная фикстура снова даёт эталон 42 859 890 ₽ / 221 295 ₽ (`TestFrozenAbovePlanInF.test_spec7_original_fixture`).

Если новый прогон скилла даёт число, отличное от диапазона 72–222 тыс. ₽ для этого набора
входов без изменения фактов — правка не заработала, искать регрессию.

**Второй кейс (guard на вырожденность):** вход без заблокированных тикеров (`blocked_sum = 0`,
только Open и Dormant). Ожидаемо: `degenerate = true`, `T_star = T_full`, никакого деления,
таргеты по Open считаются напрямую как `w_i × T_full`. Если вместо этого функция вернёт
ошибку или попытается посчитать `F / (1 − S)` — регрессия по §3.1.

## 8. L1-таргет класса: потолок/якорь, не квота с дедлайном

Тот же вопрос, что решён на уровне тикера в §3 (cap — риск-лимит, не декларация о
намерениях), встаёт и на уровне класса (акции 40% NAV). Требует отдельной рамки, потому что
интуитивный вывод «раз за 3–5 месяцев одновременно открыто максимум 3–4 бумаги, значит 40%
недостижимы» — неверен в общем виде и должен разбираться на составляющие.

### 8.1 Throughput (Rule 2, ≤4/цикл) сам по себе цель не блокирует

Rule 2 — лимит на один цикл, а циклы повторяются. Более того, Rule 1 (per-position cap за
цикл, 0,5–1,5 п.п. по статусу) и так растягивает набор любой отдельной позиции до таргета на
несколько циклов — throughput-лимит не добавляет нового ограничения поверх уже заложенного,
он просто описывает, сколько *разных* тикеров обрабатывается параллельно. Пока состав
Blocked меняется во времени (гейты снимаются по календарю, новые открываются под новые
триггеры) — 40% достижимы за счёт последовательного прохождения разных тикеров через Open,
просто не одномоментно.

### 8.2 Что реально блокирует — состав, не скорость

Недостижимость возникает, если сумма весов у тикеров, застрявших в Blocked, **не убывает со
временем** — то есть гейт не временный (есть дата/триггер пересмотра), а фактически
бессрочный. Для такого тикера есть ровно два выхода: гейт снимается (возврат в Open) или
принимается явное решение сократить/заменить его вес (§3.3 — по определению не
автоматически). Если ни то ни другое не происходит — 40% недостижимы, но это проблема
конкретного поимённого тикера, а не системное свойство лимита в 4 позиции.

### 8.3 Асимметрия: та же, что у L2-cap, на уровень выше

Недовес класса обратим и стоит упущенной доходности. Перевес — risk realized сразу. Отсюда:
**40% — потолок/якорь, к которому идут по мере появления обоснованных возможностей, не
квота, обязательная к выборке к сроку.** Докупка бумаги без пройденного фундаментального
ревью только ради «добрать план» — вариант B из §3, применённый уже к целому классу:
подмена дисциплины косметикой на уровень выше.

### 8.4 Критерий: нормальный недобор vs проблема

| Причина недобора | Оценка |
|---|---|
| Гейты по конкретным именам не резолвятся, но есть дата/триггер пересмотра | норма — цена дисциплины |
| Throughput (4/цикл) технически не успевает разобрать очередь | зафиксировать отдельно, кандидат на временное расширение cap per cycle |
| Гейт бессрочный, без даты, без решения — «просто висит» | это и есть проблема, но она про конкретный тикер, не про недостижимость 40% в принципе |
| Никто явно не проверял, почему факт ниже плана | тот дрейф, который вся эта спецификация призвана убрать |

Правило для скилла: при выводе L1 gap («акции X% вместо 40%») классифицировать причину по
этой таблице, а не давать голую цифру расхождения — голое число неотличимо для читателя от
проблемы, даже когда оно норма.

> того же документа (направленное правило — запрещён разворот, не движение; более ранняя
> редакция §8.2 B3, замораживающая бумагу независимо от направления, отменена решением
> владельца 26.08.2026). Постановка, доказательство сходимости итерации и все эталонные
> числа — там же. Формулировка правила и три уровня защиты для методологии — в
> `references/stocks-methodology.md` §«Правило неразворота» (это дублирующий её конспект,
> не самостоятельный источник).

Проблема — та же, что решена для `T*` уровнем выше (§3), только во времени: `T*` растёт при
снятии каждого гейта, и бумага, срезанная в раннем цикле, в позднем формально может
оказаться недобранной — механический расчёт предписывает выкупить только что проданное.
На горизонте плана такой разворот — чистые потери (комиссии, НДФЛ с реализованной прибыли,
обнуление ЛДВ) без изменения экспозиции.

Три уровня защиты: гистерезис Rule 3 (не реагировать на шум внутри цикла) → фиксация
направления на горизонт (`--acted TICKER=buy|trim`, снимается только человеком по
существенному основанию) → обязательная проверка диапазона цели по обозримым состояниям
цикла (`--cycles`) перед сделкой. Реализация в `scripts/gate_aware_sizing.py` — итеративная:
подавление развернувшегося тикера меняет `T*`, что может развернуть следующий; сходимость
доказана (перевод «покупаемого» тикера из `S` в `F` строго уменьшает базу, множество
подвижных тикеров каждый проход строго сжимается) и ограничена `|sized|` итерациями.
`--selling` (полный выход) правилу не подчиняется — приоритет старше всех.

именованное исключение SBER+SBERP — 20%; сектор — 35% (принят, но не активирован — поле
`sector` в снапшоте смешивает машинный словарь и русские display-ярлыки и на 45,57% пусто,
починка — задача `portfolio-data-loader`, не этого скилла). Группировка эмитента (обычка +
привилегированные одной компании) — из конфига `issuer_groups`, не эвристикой по суффиксу
`P`. Именованное исключение — запись (эмитент, значение, обоснование, дата пересмотра), а
не голое число; истёкшее исключение деградирует к лимиту по умолчанию с warning'ом, а не
игнорируется молча; исключение без даты пересмотра конфиг не принимает вовсе.

Нарушение лимита блокирует ДОКУПКУ (тикер не может попасть в `Open`, `Rebalancing` не может
развернуться в докупку той же бумаги), но не блокирует срез — им нарушение и лечится.
Нарушение также снимает признак «сделка уже была в горизонте» (`--acted`, §10 выше) для
среза: риск-лимит — существенное основание, старше правила неразворота. Отказ загрузки
конфига лимитов (файл/PyYAML/данные) внутри `gate_aware_sizing.py` не прерывает сайзинг —
деградация с warning'ом `concentration_check_unavailable:<причина>`, это риск-надстройка
над уже рабочим расчётом базы докупки, а не его предпосылка.

## 12. Правило кэша: сколько его нормально держать под гейтами

Зеркало `stocks-methodology.md` §«Сколько кэша считать нормальным, пока часть класса под
гейтами». Спека и методология не должны разойтись (§4.2 имплементационного задания).

Когда база докупки ниже полного плана класса, деньги на разницу никуда не деваются — они
ждут снятия гейтов. Меряя кэш обычным целевым буфером, эту разницу каждый раз принимают за
«перебор кэша» и предлагают пристроить, хотя пристраивать нечего: место под эти деньги уже
забронировано конкретными бумагами.

```
ожидаемый_кэш = buffer_pct% × NAV + (T_full − T*)
```

**Сравнивать с `cash.liquid_rub`, а НЕ с `cash.total_rub`.** Заблокированные гейтами деньги
стоят не на брокерском остатке, а в money-market фондах (TMON/TPAY/LQDT/SBMM); снапшот уже
складывает их в `liquid_rub` (`total_rub` + `cash_equiv_rub`). На 21.08.2026: ожидаемый
12 859 281 ₽ против `liquid_rub` 11 871 702 ₽ — расхождение −329 193 ₽, осмысленная величина;
против `total_rub` 171 246 ₽ вышла бы «нехватка» 96%, то есть правило, которое при
односторонней тревоге молчит всегда и потому бесполезно. Фолбэка на `total_rub` нет
намеренно — это подмена похожего поля (`rpa-17-field-paths-audit.md`).

**Тревога односторонняя — только на превышение.** Кэш выше ожидаемого — повод разобраться:
деньги не работают, и гейтами это уже не объясняется. Кэш ниже — не тревога, а рабочее
состояние: буфер частично израсходован. Симметричная тревога давала бы ложное срабатывание
на каждом цикле, где что-то докупалось.

**Арифметику считает скрипт, не рассуждение.** `gate_aware_sizing.py` отдаёт блок
`cash_buffer` (ожидаемый кэш, обе составляющие, фактический `liquid_rub`, расхождение со
знаком) и warning `cash_above_expected`; буфер задаётся `--cash-buffer-pct` (default 4).
Вынесено из чистого текста намеренно: 19.08.2026 методика сайзинга уже была записана в
референсы — и в тот же день не сработала (ошибка ×14 на `goals_matrix.Изменение`). Правило,
живущее только в тексте, применяется через раз. За владельцем — решение, что делать с
превышением, а не пересчёт формулы.
