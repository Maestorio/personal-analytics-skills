## 2. Правила для всех этапов

1. **Только чтение.** В `Claude-Memory/` и репозитории ничего не пишется, кроме артефакта этапа.
   Python — с `-B` (без `__pycache__`), скрипты с `--out` — только в scratchpad, `--dry-run` где есть.
   Не запускать `build_snapshot.py --commit`, `apply_*.py` без `--dry-run`, `deploy.zsh`, запросы к
   `/api/*/set|save|import`. Интерпретатор — `~/.pyenv/versions/3.12.9/bin/python3`.
2. **Зеркало Synology на Маке может отставать** от NAS для файлов, которые пишет `hub-api`/`hub-notify`
   (`plan.json`, `plan-journal.jsonl`, `conditions.yaml`, `snapshots/auto/`). Для них фиксировать
   и mtime зеркала, и (если доступен) ответ `GET` с NAS; расхождение — отдельная находка.
3. **Доступ к `~/Documents` может пропасть посреди сессии (macOS TCC).** Промежуточный результат
   сохранять в scratchpad по мере работы, артефакт — в конце одним файлом.
4. **Каждое утверждение — с опорой:** путь + строка кода, путь файла данных + ключ, или «со слов
   владельца (дата)». Без опоры — пометка «не проверено».
5. **Жёсткие правила, которые этап 2 обязан соблюсти** (этап 1 их фиксирует, не оценивает):
   D3 и перечень исключений (`CLAUDE.md`, `claude-memory-layout.md`); совместимость схем (миграция
   данных или backward-compat в коде, перед правкой — grep по реальным артефактам); сценарная
   независимость скиллов (поля — факторные, без имён сценариев); справка вьюера в двух зеркалах
   (`portfolio-workflow-guide.md` + `tools/assets/help/viewer/NN-slug.md`) и справки страниц;
   защита от model drift (Pre-emit checklist в SKILL.md + Python-валидатор в save-to-library);
   аккуратность с размером SKILL.md (детали — в `references/`); приоритеты владельца:
   корректность > читаемость > стоимость > скорость.
6. Субагенты: допустимы на этапе 1 для механического сбора по группам источников (≤3, sonnet/haiku,
   с заранее выданными разрешениями на чтение); сводку и проверку делает основной исполнитель.

## 3. Этап 1 — инвентарь по циклу (факты + выводы, один артефакт)

**Пересмотрен 30.10.2026** (решения владельца — §6a): прежние этапы 1 «инвентаризация» и 2 «анализ» слиты в один —
носитель уже выбран (R2), нейтральность инвентаря защищать не от чего, а полный каталог баз дублировал бы
`claude-memory-layout.md` и `scripts-map.md`. Этап даёт факты и выводы в одном документе, двумя явно разделёнными частями.

**Цель.** Показать, на каких шагах цикла владельца и цепочки прогноза значение рождается структурно, где оно
извлекается парсером или человеком, где теряется или устаревает — с опорой на код и данные; оценить каждый пробел так,
чтобы этап 2 мог расставить приоритеты.

### 3.0 Принципы этапа

- **Дельта, не каталог.** Матрица «кто пишет / кто читает» (`claude-memory-layout.md` §«Кто пишет / кто читает») и карта
  скриптов (`scripts-map.md`) принимаются за основу и **проверяются по коду**; расхождения — списком. Карточка базы
  пишется только там, где есть что добавить к раскладке: фактическая схема, смысл полей-дат и наличие времени, поля
  вывода (машинно / прозой), копии, задержки, несколько писателей.
- **Потолок длины.** Основной текст `inventory.md` — до 300 строк; таблицы схем, частоты ключей, полные хронологии
  трассировок — приложениями отдельными файлами в `docs/investment/_cross-cutting/data-structures/`. Владелец читает
  основной текст; приложения — для этапа 2 и исполнителей.
- **Стержень — цикл владельца, не список файлов.** Целевой цикл (ответы владельца 30.10, §3.5): разбор делает система →
  за текстом отчёта лежит структурный вывод → сайт обновляет «Доли и цели» и «Действия» → владелец ставит статус →
  заявка. Вторая цепочка — прогноз: файл прогноза → макровход → стресс → обзор недели → строка бумаги на сайте;
  параллельно монитор → «Действия».
- Остальные правила — §2 (только чтение, опоры, scratchpad, жёсткие правила для решения).

### 3.1 Шаг 1 — трассировки (делаются первыми)

Трассировка — хронология за 60 дней по всем базам с датой·временем, в колонках: «что записано (база, ключ)» ·
«кто записал (скрипт/маршрут/скилл)» · «что показывал сайт в этот момент (вкладка, по коду вьюера)» · «как значение
дошло до следующего шага: поле / парсер / человек / не дошло». Результат трассировок определяет, какие карточки §3.3
нужны вообще.

- **GMKN** — разбор Mode 4 от 29.10 (§0): почему строка «Действий» осталась от обзора 28.10.
- **MDMG** — условие среза сработало, обзор TRIM, сайт «держать, выше плана» (26.10).
- **Одна облигация** (ключ ISIN) — выбрать ту, у которой за 60 дней были событие гейта/условия или смена корзины.
- **Один прогноз** — выбрать тот, что входит в действующий стресс-тест и по которому монитор давал предупреждение
  за 60 дней (кандидаты: ставка ЦБ, Brent, USD/RUB); провести по обеим ветвям цепочки прогноза.

### 3.2 Шаг 2 — таблица цикла

Для каждого шага цикла владельца и цепочки прогноза — строка: шаг → носитель (файл, ключ) → писатель (скрипт · скилл ·
маршрут) → читатель(и) с файл:строка → как значение доходит до следующего шага (поле / парсер по тексту / человек /
не доходит) → класс дефекта (§3.6) → пример из трассировки. Отдельные строки свежести: реестр гейтов (блокирует и
разрешает докупку — устаревший гейт = решения по устаревшей оценке), условия, прогнозы в стрессе (дата прогноза против
даты стресса против даты обзора).

Для прогнозов дополнительно — **карта зависимостей**: скилл по акциям (советник Mode 1/2/4/8, стресс, integrated-view,
монитор) → какое поле какого прогноза/сценария читает → откуда берёт (файл напрямую / через стресс / через обзор) →
как проверяется свежесть (`stale_flags.yaml`, `horizon`, дата файла, никак).

### 3.4 Замеры (только чтение)

- Схема фактическая: однократный скрипт в scratchpad (`python3 -B -I`) — объединение ключей до глубины 3 с частотой и
  примером; для `reports/*.md` — частоты `kind`, `mode`, `tickers`, наличие машинных блоков и `created_at`.
- Писатели и читатели: `grep -rn` по `skills/`, `tools/`, `_shared-references/`; вьюер — пути `Portfolio/` и
  манифест `api/pv/sync`; `server.py` — маршруты.
- **Задержки — по снимку с NAS**, не по зеркалу Мака (§2 п.2; факт 30.10: `plan-journal.jsonl` на Маке заканчивается
  27.10 при 30.10 на NAS). Снимок файлов `hub-api` и листинг с датами снимает владелец по ssh в scratchpad исполнителя
  (`…/scratchpad/nas/`), пароль зоны `/api/pv/*` в сессию не передаётся. Для производных — `generated_at` против самого
  свежего источника; история — `.versions/`, `_jobs/log-*.jsonl`, `plan-journal.jsonl`, git-лог скриптов.
- Копии: `conditions.yaml` → `user_constraints`, `gate-reviews.yaml` → `gate_status_snapshot`, снапшот → `securities/`
  — сверка на 3 датах.
- Случаи ошибок (ответ владельца 2, §3.5): `decision-journal/incidents.yaml`, `_jobs/log-*.jsonl`, `TODO.md`,
  `TODO_design.md`, `html-comments.md`, git-лог за 60 дней по словам «парс», «устарев», «не обновил», «расхожд».

выставлять заявку. А если что — выставлял заявку. Это ставил в столце со статусом. Или выделял шрифтом, что сделал,
что в процессе.» Целевой цикл сегодня (30.10): «Сейчас я бы хотел часть задач делигировать системе. В частности,

### 3.6 Часть «Выводы»: каталог вопросов, классы дефектов, оценка

**Каталог вопросов** (из ответов владельца; дополнять найденным). Владелец: держать или балансировать бумагу X и

### 4.2 Критерии выбора

1. Корректность: исключает ли K1 по построению (один ответ, сравнимый по времени).

3. Защита от model drift: поле проверяется Python-валидатором до записи; LLM не пишет файл в обход.
4. Совместимость: старые артефакты читаются без правки или мигрируются скриптом; grep по реальным артефактам перед
   правкой схемы.
5. Обнаружимость расхождения и причины (K12): если источники спорят или предложение заблокировано, это видно на

6. Стоимость: число затронутых инструментов и тестов; рост SKILL.md и токенов на старте скиллов.
7. Совместимость с уходом от `portfolio-data-loader` (до конца 2026) — пересборки только в скилле не планировать.
8. Сценарная независимость: в схеме нет имён сценариев; триггеры — факторные.
9. Обратимость и офлайн-проверка: экспорт/восстановление (требование `TODO-numbers-exit.md` п.5).
10. Минимум парсеров (K10): поле вывода пишется структурно в точке записи — сайтом/API, валидатором save-to-library
    или скриптом из структурного входа; извлечение из прозы допустимо только как разовый бэкфилл с провенансом,
    не как постоянный путь чтения.
11. Предсказуемость: одно и то же состояние баз даёт один и тот же показ и одно и то же предложение (владелец 30.10:

## 5. Приёмка

Цель задачи («на любой вопрос один машиночитаемый ответ с датой и источником; расхождение видно») проверяется не
прочтением документа, а повтором реальных случаев. Решение этапа 2 обязано включить приёмочный тест, реализация —
выполнить его:

1. **Повтор GMKN:** разбор Mode 4 с вердиктом и план-долей сохранён → строка «Действий» и карточка показывают его
   вывод с датой·временем и источником, а не обзор предыдущего дня; без ручной пересборки.
2. **Повтор MDMG:** условие среза сработало, обзор TRIM → «Доли и цели» показывают расхождение со статусом владельца
   плашкой, а не «держать, выше плана» без пометки.
3. **Причина блокировки (K12):** бумага с позитивным разбором и без предложения о покупке → в «Сейчас» видна причина

4. **Свежесть прогноза (R15):** строка бумаги показывает, на каком прогнозе и стрессе основан вывод; стресс старее
   прогноза — предупреждение.
5. **Детерминизм:** повторный прогон на тех же базах даёт тот же показ и те же предложения.
6. Тест по реальному пути сайта и блок в `docs/test-registry.md`; сверка выложенного с HEAD.

  и «производный индекс парсерами как постоянный путь» для «последнего слова» сняты. Открыто на этап 2 (R3): механизм
  попадания вывода Claude в такой файл — структурный блок через валидатор save-to-library или `POST` в `hub-api`
  (как уведомитель с условиями).
- **Опрос §3.5 пересмотрен** (три вопроса вместо семи), пройден 30.10; случаи ошибок собирает исполнитель по журналам
  и истории (ответ 2).
- **Прогнозный контур — через зависимости, не через схемы** («для меня прогнозы — это база… важно, чтобы я понимал, что
  меняется, что на сайте я правильно вижу, что и как зависит друг от друга, и что скиллы по работе с акциями правильно
  берут прогнозы»): трассировка одного прогноза по цепочке и карта зависимостей (§3.1–3.2); внутренние схемы матриц и
  весов — вне рамок; «детерминированность прогнозных скиллов» (ответ В3 от 29.10) — отдельная задача после цикла.
- **Этапы слиты:** инвентарь и анализ — один артефакт (владелец: «этап 1 почти полностью закрыт уже существующей
  документацией»); R9–R11 закрыты уходом от Numbers; добавлены R14 (`securities/`), R15 (прогнозы на сайте), K11, K12,
  приёмка §5.
- **Мета-правило владельца (30.10):** если его ответы противоречат ранее принятым решениям, выглядят странно с точки
  зрения исполнителя или с инвестиционной точки зрения (цель — сохранить и приумножить в режиме умеренной агрессии при
  заданном балансе акций и облигаций) — обсуждать, не исполнять молча. Система не должна быть ни хаотичной, ни
  выдающей всегда одно и то же; «всё должно просто легко работать». Оценки — без лести.
- **R2/R3 уточнены вечером 30.10 («разделение по писателю»).** Скиллы исполняются в Claude.ai Cowork (нет переменных
  окружения и Bash, файлы через Read/Write на mount), поэтому «носитель — сайт» уточнён: **сайт владеет состоянием и
  вводом владельца, скилл владеет своими выводами; у каждого файла один писатель, читатели объединяют по id.**
  Скилл (save-to-library) пишет напрямую на mount: отчёты, обзоры, гейты, определения условий (без удаления, замена
  версией) и «последнее слово» разбора. Сайт (hub-api) пишет план и новый файл состояния условий (касание, срабатывание,
  найденное событие, отметки владельца), события — от уведомителя, из отчётов монитора и с кнопок сайта. Лоток
  (outbox: скилл кладёт запрос файлом, NAS применяет) — запасной путь на случай, когда скиллу нужно изменить состояние
  сайта; POST с секретом и MCP отклонены (секретов и сети у скилла нет, NAS слабый). Формулировка владельца: «тогда
  выбор один: conditions.yaml пишется только save-to-library. А то, что событие сработало, должно быть отображено в
  отдельном файле».
- **Сверка с NAS (§2 п.2):** зеркало на Маке подтверждённо отстаёт — `plan-journal.jsonl` пишется сервером напрямую,
  минуя File Station, и на Маке заканчивается 27.10 при `plan.json` от 30.10. Снимки файлов `hub-api` для замеров
  задержек владелец снимает по ssh в scratchpad исполнителя; пароль зоны `/api/pv/*` в сессию не передаётся.

## 7. Риски

- **Объём и дрейф во время работы:** вьюер, справка и обзоры меняются параллельно — инвентаризация
  фиксирует срез на дату; карточки несут дату замера.
- **Зеркало Synology врёт** для файлов `hub-api`: без сверки с NAS задержки будут неверны (§2 п.2).
- **Ложная полнота:** знания вне файлов легко пропустить — опрос §3.5 пройден 30.10; данные сайта вне `Claude-Memory/`
  (том `notify_data`) — в группе A.
- **Подмена анализа решением:** часть Б этапа 1 формулирует требования и пробелы, но не схемы полей; иначе этап 2
  обсуждает уже выбранное. (Носитель R2 решён владельцем заранее — это данность, не подмена.)
- **Расширение D3 без нужды:** каждое новое исключение — с обоснованием «детерминированно, без LLM»
  или «единственный писатель с журналом»; иначе — через save-to-library.
- **Миграция ломает читателей:** старые отчёты и обзоры читаются вьюером, coherence-audit и журналом
  решений; без backward-compat или скрипта миграции — регресс.
- **Лимиты модели:** Opus на этапе 2; fan-out только на sonnet/haiku.
