## 1. Правила схемы

1. **Один писатель на файл, буквально.** Скилл (через `save-to-library` и его скрипты) пишет выводы: отчёты, обзоры,
   решения, определения условий. Сайт (`hub-api`) пишет состояние и ввод владельца: план, журнал плана,
   состояние условий, снапшоты, типы бумаг, журнал решений. Разработчик пишет кодлисты (в репозитории, выкладка
   деплоем). Mac-пути записи снапшота и журнала решений (`build_snapshot.py --commit`) и CLI плана `numbers_to_plan.py`
   **выводятся** из писателей (ограничение C3; уход от Numbers закрыт) — остаются как инструменты разработчика с
   выводом вне `Claude-Memory`. **Скрипт скилла пишет на mount сам** (проверено 31.10 в Cowork на Sonnet и Haiku: путь
   в сессии `$HOME/mnt/Claude-Memory`, файл доходит до NAS с обычными правами, `os.replace` работает, удаление в
   подключённых папках выключено) — поэтому модель не переписывает файлы инструментом Write, а скрипты скилла никогда не
   удаляют: снятие = `withdrawn`, замена = временный файл + `os.replace`, корень mount — всегда аргументом.
2. **Факт хранится один раз.** Копия факта в другом файле допускается только как *срез на момент* с явным `as_of` и не
   читается кодом как источник истины. Производные не хранятся или помечены как сборка сайта. Выводимое из ключа или
   времени (`key_kind`, предыдущее решение) считается при чтении, не хранится.
3. **Читатели объединяют по идентификатору**, не разбором текста. Разрешённые модули объединения — ровно три, у каждого
   Python- и JS-близнецы с тестом паритета: (а) условия «определение + состояние»; (б) «последнее слово» по бумаге;
   (в) загрузчик кодлистов. Остальное читает файлы напрямую. Слой «старое → новое» в читателе запрещён; поэтому
   **миграция ставит время записи всем старым документам** (оценка с флагом), чтобы у читателей не было ветки «нет
   времени» (`decision.md` §1).
4. **Время** — везде `YYYY-MM-DDTHH:MM:SS+03:00` (МСК с явным поясом), ставит скрипт или сервер, не модель. Оценённое
   время миграции — `T00:00:00` того дня с флагом `*_estimated: true`: оно всегда раньше любой живой записи того же дня.
   Дата без времени — только там, где это дата события по смыслу (срок, дата отчётности). «Что новее» — только по
   полю времени, никогда по имени файла или mtime.
5. **Кодлисты закрыты и расширяемы**: все коды полей-перечислений — из одного `codelists.json`; у каждого кода есть
   русское слово; новый код без слова роняет тест-сторож. Ключ версии у всех новых файлов — `schema_version: "<имя>@<N>"`.

### 1а. Критерии владельца (30.10 вечером) и честная оценка схемы по ним

| Критерий | Как выполняется | Где схема НЕ дотягивает (после рецензии) |
|---|---|---|
| **Связность** | решение → `source.doc`, `source.stress_id`, `conditions_created[]`, `conditions_resolved[]`; условие → `source.decision_id`; событие состояния → `condition_id`; строка журнала плана → поле `decision_id`, когда правка сделана с карточки; стресс → `macro_input` → `forecast_files{}` → файлы прогнозов → `superseded_by` | **сделки не имеют идентификатора** (выводятся из разницы количеств между снапшотами); строка обзора не ссылается на решение — связь по ключу и времени |
| **Единственность** | один писатель на файл без исключений; производные не хранятся; **гейт-файл упразднён** — статус гейта считается модулем (б) из новейшего решения; удаляются `securities/`, `stale_flags`, `set_status`, `conditions_state[]` обзора, `gate-reviews.yaml`, `last_checked_at`; класс бумаги — один раз в справочнике бумаг | **копии в обзорах остаются как срез** с `as_of`, их писатель правится следующим циклом |
| **Представимость во вьюере** | решение — JSON из 12 полей, одно вложенное (`source`); «последнее слово» определено **по полям** (§3.5); модуль условий отдаёт плоские строки; кодлисты дают слова; время парсится `Date` | sync не ограничивает число файлов, но первая загрузка уже сегодня тянет обзоры (8,5 МБ) — решения (сотни файлов по 1 КБ) этот груз не меняют; офлайн-кэш `sw-offline.js` должен узнать новые пути (шаг 12) |
| **Дёшево для скиллов** | модель заполняет **4 поля** решения (вердикт, доля, срок, заметка) и при желании уверенность; один блок вместо двух директив; шапка отчёта — 3 новых поля; **запись решений и условий целиком в скрипте** (проверено 31.10: скрипт в Cowork пишет на mount), модель файлы носителей не видит | ветки «если → то» остаются прозой и всегда ведут в разбор |

Вывод оркестратора: связность, представимость и дешевизна закрыты; единственность — с одной сознательной отсрочкой
(копии в обзорах) на следующий цикл.

## 3. Новые и переработанные сущности

### 3.1 Решение по бумаге — `decision@1`

Один файл на запись, пишет **скрипт** `save-to-library` после разбора (режимы 3/4/5a/8) или по слову владельца. Модель
заполняет четыре поля (и при желании уверенность), остальное ставит скрипт. Гейт в решении **не хранится** (вопрос
владельца 31.10): статус гейта — проекция вердикта по таблице `verdict_to_gate`, срок — `review_by`, считаются при чтении.

| Поле | Тип | Кто ставит | Смысл |
|---|---|---|---|
| `schema_version` | `"decision@1"` | скрипт | — |
| `id` | `2026-10-29T1740-GMKN` | скрипт | = имя файла; время — МСК записи |
| `key` | строка | скрипт из блока | тикер или ISIN (класс и вид ключа — по реестру типов при чтении, не хранятся) |
| `verdict` | кодлист `verdict` | **модель** | единый словарь для всех классов (§3.4) |
| `target_pct` | число или null | **модель** | целевая доля плана, % портфеля; null = «как в плане» |
| `review_by` | дата или null | **модель** | срок пересмотра; **он же срок гейта**: null → `recorded_at` + `defaults.review_days` (60); валидатор: 7–180 дней от записи |
| `note` | строка ≤ 200 | **модель** | одна фраза «почему» |
| `confidence` | 0..1 или null | модель, не обязательно | — |
| `conditions_created` | список id | скрипт | условия, созданные командами в том же сохранении |
| `conditions_resolved` | список id | скрипт | условия этого ключа, ждущие владельца (`waits_owner`: сработали и не отложены им), на момент сохранения; модель может исключить через `keep_open: [id]` в блоке — тогда условие остаётся «ждёт владельца» |
| `source` | `{kind, doc, mode_codes[], stress_id}` | скрипт | `kind` ∈ `decision_source` (report / owner / backfill / backfill_llm); `doc` — путь отчёта; `stress_id` — действующий стресс на момент разбора (R15) |
| `author` | `model` / `owner` | скрипт | — |
| `recorded_at` | время с поясом | скрипт | единственное поле для сравнения «что новее» |

Удалено после рецензии: `key_kind`, `asset_class`, `supersedes` (выводимы при чтении), `valid_days`/`cooldown_weeks`
(дубль `review_by`), `triggers` (расщеплён на «создано» и «закрыто», оба ставит скрипт — так требовал R1). Удалено после
ответов владельца 31.10: `gate{ticker_class}`. **Класс бумаги** (`bluechip` 10, `mid_cap` 11, `ipo` 5, `fund_zpif` 1 в
сегодняшних гейтах) в решении не хранится: он почти не меняется, поэтому живёт в **справочнике бумаг** (§4.8) — один
раз заведён, правится точечно. По данным гейтов класс срок не задаёт (внутри `bluechip` 45–75 дней, `mid_cap` 14–75,
`ipo` 35–120 — срок ставит модель от ближайшего катализатора); несущая роль класса — IPO-пауза: `ticker_class: ipo` и
`listed_at` + 8 кварталов > сегодня → докупка заблокирована при любом вердикте (решение 28.10). Формализовать «гуляние»
сроков по классам не нужно — это закрепило бы шум; формализуется то, что в данных постоянно: пауза между докупками 21 день
(`defaults.add_cooldown_days`, с 11.11 — от первой покупки после решения BUY/ADD, правило 7 модуля (б)) и срок по умолчанию 60 дней.
Что НЕ хранится: причины блокировки движка, доля по факту, цена, текст отчёта. Обзор недели файлы решений **не пишет**.
**Запись (шаг 8):** модель кладёт поля в блок `decisions:` YAML-шапки отчёта (`report@1`, по записи на бумагу: `key, verdict, target_pct, review_by, note`, `confidence?`, `keep_open?`); `save-to-library` `decision_write.py from-report --doc … [--stress …]` пишет файлы (`owner` — по слову владельца, `digest` — чтение); после записи блок кодом не читается.

### 3.2 Определение условия — `conditions@2`

Записи-определения; правка = новая запись с тем же `id` и `version+1`, прежняя получает `superseded_by`. Удаления
нет: снятие = `withdrawn`. Носитель — **один YAML с версиями, пишет скрипт** (`apply_condition.py`: читает, валидирует,
дописывает, заменяет через временный файл и `os.replace`; модель видит только вывод скрипта) — решено проверкой Cowork
31.10 (§8 в.4). Годовой архив — тем же скриптом при обслуживании.
Команды скрипта (шаг 6): `add`, `edit` (новая версия), `withdraw`, `list`/`digest` (выборка модулем (а)), `crosscheck`,
`validate`; вход — JSON в stdin, корень — `--root`, автор — `--by`; валидаторы — `_shared-references/ds_schemas.py`;
`edit` закрытого (done, dismissed, expired) — ошибка, нужно `add`; дата в `id` — из `created_at`.

| Поле | Тип | Кто ставит | Смысл |
|---|---|---|---|
| `id` | старые как есть (`nvtk-sellgate`); новые `c-ГГГГ-ММ-ДД-<ключ>-<n>` | скрипт | стабильный через версии |
| `version` | целое от 1 | скрипт | — |
| `key` | строка | модель | тикер или ISIN |
| `kind` | кодлист `condition_kind` | модель | review / trade / watch |
| `trigger` | `{type, value, window_end?}` | модель | `type` ∈ `condition_trigger_type`: `date`, `price_below`, `price_above`, `report_published`, `gate_expired`, `forecast_breach`, `event`; у `report_published` `value` — что ждём словами, `window_end` обязателен: к этой дате событие считается наступившим даже без находки (решение владельца). **Правило окна (31.10): `window_end` = ожидаемая дата + 3 дня** — монитору даётся три дня поймать отчёт; при недельном прогоне монитора большинство окон закроется «по сроку, не найдено» (пометка `fired_by_deadline`), срабатывание от этого не зависит — его делает ежедневная задача NAS |
| `event_text` | строка | модель | что ждём словами (для поиска монитором) |
| `while_pending` | `{verdict, target_pct?, text?}` | модель | что делать, пока ждём |
| `on_trigger` | `{action, verdict?, target_pct?, target?, amount_source?, text, branches?[], otherwise?}` | модель | `action` ∈ `condition_action`: `run_analysis`, `set_verdict`, `set_target_pct`, `notify_only`, `reinvest` (с 03.11, R30); ветки `[{if_text, then:{verdict, action, target_pct?, text}}]` и `otherwise{}` — внутри `on_trigger`. У `reinvest` обязательны `target` (корзина облигаций — кодлист `bond_bucket`, или ключ бумаги) и `text`, `verdict` и `target_pct` запрещены, `amount_source` ∈ `reinvest_source` (`redemption`, `offer`, `coupon`, `sale`) необязателен |
| `on_expiry` | `{action, verdict?, target_pct?, text}` или null | модель | что делать, если `valid_until` прошёл без срабатывания |
| `not_before`, `valid_until` | дата | модель | окно действия |
| `note` | строка ≤ 200 или нет поля | модель | почему создано или изменено (вместо `reason` прежнего `edit`); модуль (а) несёт его в плоской строке |
| `context` | `{plan_pct, snapshot_id, as_of}` | скрипт | срез на момент создания |
| `source` | `{kind, doc, decision_id?}` | скрипт | `kind` ∈ `condition_source` = `decision_source` + `migration` |
| `created_at`, `created_by` | время с поясом; кодлист `actor` | скрипт | `created_by`: `mode_1`…`mode_9`, `mode_5a/5b`, `owner`, `notifier`, `monitor`, `site`, `script` |
| `withdrawn` | `{at, by, reason}` или null | скрипт | снятие; состояние (§3.3) не трогается |
| `superseded_by` | `id@version` или null | скрипт | — |

**Реинвест и погашение (R30, 03.11).** «Погашение → деньги в другую корзину» — исход `reinvest`, не вердикт: после
погашения бумаги нет. У облигации с датным триггером в день погашения или позже `set_verdict` с вердиктом направления
up/flat — ошибка (`ds_schemas.maturity_errors`, правило 19 валидатора; даты погашения — снапшоты корня через
`decisions_read.maturities`; `apply_condition.py add|edit` проверяет записываемое определение, `validate` — действующие;
без даты погашения — пропуск, `maturity: null` в выводе). Модуль (а) несёт `target` и `amount_source` строкой (действие —
`action_code`), ничего не считает. Корзина-цель сверяется с живым планом: при известном корне `target` из кодлиста `bond_bucket`
обязан быть ключом `bond_buckets[].key` в `Portfolio/plan.json`, иначе ошибка «корзины <код> нет в плане (есть: …)»
(`ds_schemas.plan_bucket_errors`, правило 20; `apply_condition.py add|edit|validate`); без плана — только кодлист.

Удалено из `conditions@1.2`: `state`, `fired_date`, `touched`, `history[]` (состояние и журнал → §3.3; строки
`created/edited` остаются в архиве), `on_trigger.set_status` (его смысл «после срабатывания — разбор» переходит в
`action: run_analysis`; статус гейта ставит только решение после разбора).

### 3.3 Состояние условия — `conditions-state@1`

JSON `conditions-state.json`, пишет только `hub-api` (маршрут для сайта и внутренний для hub-notify). Только
дописывание событий; записи не правятся и не удаляются; годовой срез при обслуживании. Служебных полей, меняющихся при
каждой проверке, в файле нет (`last_checked_at` живёт в состоянии hub-notify) — иначе версии `.versions/` съедались бы
за сутки.

```
{ "schema_version": "conditions-state@1",
  "events": [ { "condition_id": "c-…", "event": "fired", "at": "…+03:00", "by": "notifier",
                 "data": { "price": …, "doc": "…", "note": "…", "decision_id": "…", "until": "…" } } ] }
```

`event` ∈ `condition_event`: `fired` (сработало: порог пересечён, дата наступила, монитор нашёл, окно вышло),
`expired` (`valid_until` вышел), `event_found` (находка монитора — информация, задача на NAS пишет его **вместе** с
`fired` и `data.doc`; **R32, 03.11:** от владельца — кнопка «вышел» у ждущего `report_published`/`event`, сам переводит
условие в `fired`, hub-api принимает его только у такого ждущего условия), `owner_mark` (`data.mark` ∈ `owner_mark` = `dismissed` «не актуально» — закрывает; `deferred`
«отложить до» с обязательным `data.until` — снимает «ждёт владельца» до даты), `reopened` (владелец открыл заново;
статус считается по событиям после него), `done` (закрыто; `by: owner` — кнопка «сделал», `data` может быть пустым — опора сама отметка; `by: decision` — уведомитель по
новому решению с `conditions_resolved[]` → `data.decision_id`, только для условий, ждущих владельца (отложенные им не закрываются); `by: site` — по сделке → `data.trade_date`). Одного «касания
порога» нет: порог пересечён — `fired`. «Снятие определения» в состоянии не дублируется.

**Правило согласованности (модуль (а), правила в докстринге `_shared-references/conditions_merge.py`):**
действующее = определение не снято **и** состояние не терминально. `fired` без закрытия — активно и «ждёт владельца»;
`deferred` снимает «ждёт владельца» до `until`; `done`, `dismissed`, `expired` — закрыто; `reopened` обнуляет.
**Дедлайны считаются при чтении** как страховка (решение владельца): триггер `date` при `value ≤ сегодня` или окно
при `window_end < сегодня` без события → `fired` с пометкой `fired_by_deadline`; `valid_until` в прошлом → `expired` и
показ `on_expiry`. Событие уведомителя первично, вычисление при чтении покрывает промежуток до его прохода. Снятое
определение с живым состоянием — норма. Движок «Сейчас» показывает «ждёт владельца» как блок с причиной.

**Правило 14 (шаг 6):** новая версия определения начинает состояние заново — для статуса и отметок учитываются только события с `at` ≥ `created_at` последней версии (раньше — история прежних версий); поэтому `edit` снимает fired без участия сайта, а `reopened` остаётся кнопкой владельца для того же без правки определения.

Модуль (а): `_shared-references/conditions_merge.py` + `tools/assets/conditions-merge.js`, паритет — `test_conditions_merge_parity.py`.
