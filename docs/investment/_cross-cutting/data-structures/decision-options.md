### Условия: два файла

**Определение (`conditions.yaml`, `conditions@2`, пишет скилл):**
```yaml
schema_version: conditions@2
conditions:
  - id: tick-trim-after-1910            # id версии; первая версия без суффикса
    rev: 1
    supersedes: null                     # у новой версии — id прежней; superseded_by читатели выводят сами (прежняя запись не правится)
    key: TICK
    trigger: {type: date, value: "2026-10-19"}          # кодлист C4: date | price_below | price_above | report_published | event
    window: {not_before: null, valid_until: "2026-11-30"}
    while_pending: {verdict: HOLD}
    on_trigger: {verdict: TRIM, action: {type: trim, target_pct: 3.5}, set_status: null, kind: trade}
    source: {kind: report, doc: "Portfolio/reports/2026-10-01-weekly-review-stock.md", decision: null}
    created: {at: "2026-10-01T12:08:00+03:00", by: mode_1}
    withdrawn: null                      # {at, reason, doc} — снято разбором/обзором/владельцем словами; запись не удаляется
```
Замена условия: прежняя запись получает `withdrawn {at, reason: superseded, doc}`, новая версия — **свой `id`** и `supersedes: <прежний id>`.
**Состояние (`conditions-state.json`, пишет hub-api; только события, append-only):**
```json
{"schema_version": "conditions-state@1",
 "by_id": {"tick-trim-after-1910": {"events": [
   {"seq": 1, "at": "2026-10-19T08:30:04+03:00", "type": "fired", "by": "hub-notify", "data": {"trigger": "date"}},
   {"seq": 2, "at": "2026-10-26T15:02:11+03:00", "type": "owner_mark", "by": "owner", "data": {"after_fired": "done", "note": "сделал"}},
   {"seq": 3, "at": "2026-10-28T12:20:00+03:00", "type": "definition_withdrawn", "by": "hub-notify",
    "data": {"doc": "Portfolio/weekly-reviews/weekly-review-stock-2026-10-28.yaml"}}]}}}
```
Кодлисты (C4): `events[].type ∈ {touched, fired, expired, event_found, checked, owner_mark, definition_withdrawn}`; `owner_mark.after_fired ∈ {waiting_owner,
deferred{until}, resolved_other, done}`; `by ∈ {hub-notify, monitor, owner}`. Сводное состояние (`pending/fired/terminal`, текущий `after_fired`) **не хранится** —
его выводит модуль объединения из событий. Нет записи по `id` — условие `pending`. `checked` пишется только от монитора (раз в неделю) и не чаще раза в сутки
от hub-notify; ежечасные проверки цен в файл не попадают.

**Правило согласованности (принято владельцем 30.10):**
1. **Определение отвечает за существование** условия: снятие разбором/обзором/словами владельца не удаляет запись, а ставит `withdrawn {at, reason ∈ {superseded,
   resolved_by_review, owner, error}, doc}`; новая версия — новый `id` с `supersedes`. Определение **не хранит событий** (`touched`, `fired`, `fired_date`, `history`
   переезжают в состояние).
2. **Состояние — только события**: дописываются, никогда не правятся и не удаляются; состояние **не говорит о существовании** условия.
3. **Активно** = определение не снято **и** по событиям состояние не терминальное (терминальное: `owner_mark` с `done`/`resolved_other`, `expired` без
   продолжения). **Снятое определение с живым состоянием — норма** (история остаётся видна, движок его не учитывает).
4. Задача на NAS может дописать событие `definition_withdrawn` (удобство для «Истории»), источник истины о снятии — всё равно определение.
5. Валидаторы: `validate-conditions@2` (скилл) — число записей не убывает, `withdrawn` не снимается, `supersedes` ссылается на существующий `id`;
   hub-api — `id` события существует в определениях, `seq` строго растёт, переписывание прежних событий → 400.
Последний `checked` в файл **не пишется** (иначе запись каждый час) — держится в `state.json` уведомителя (`/data`), как `price_hits` (`N:902-910`).
