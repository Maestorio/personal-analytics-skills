## 0. Характер фазы и диспозиция всех 6 задач

В отличие от Фаз 3/4/6 (каждая — связная спека с чётким расширением архитектуры),
**Фаза 7 — не фаза, а зафиксированный набор из 6 разнородных «possible future directions».**
Все помечены *Низкая критичность · нет срока*; `plan.md` прямо пишет «Нет конкретного плана».
Этот документ — не указание реализовать всё, а **roadmap с эскизом по каждой задаче**, чтобы
можно было выбрать пункт и сразу уйти в работу.

Главное наблюдение: **две задачи (v4-B, и ML-варианты v4-C/W2/W3) конфликтуют с осознанными
инвариантами системы**, а одна (v4-D) — это отдельный класс инструментов. Аккуратно вписывается
без оговорок только **v4-A**.

**Сквозной принцип всей фазы.** Система — **LLM-first + детерминированный Python для математики**;
ML-training/labeled-data/serving в репо **нет** и его появление поменяло бы деплой-модель всего
проекта (скиллы = markdown + stdlib/numpy-скрипты). Поэтому каждая «ML»-задача здесь либо
**переосмысляется в LLM-native форму** (которая даёт ту же ценность без новой инфры), либо
честно признаётся несоразмерной *Низкой* критичности. Рекомендованная последовательность — §8.

## 1. Инварианты, которые нельзя ломать (общий контекст)

- **Offline / privacy-first вьюер** (спека `06-…HTML-spec.md` §2.3, переподтверждён в Фазе 6):
  ни одного сетевого вызова, всё из локально загруженных файлов. I-1 (Фаза 2) **специально удалил**
  браузерный fetch к MOEX ISS (`moexBondCache`/`fetchMoexBond`/`showBondModalFromMoex`). Прямой
  удар по этому инварианту — v4-B (§3).
- **Правило D3** (CLAUDE.md): кроме loader (исключение D3) и maintenance-скиллов, никто не пишет
  в `Claude-Memory/` напрямую — скилл генерирует артефакт, пользователь вызывает `save-to-library`.
  Касается нового `portfolio-optimizer` (§5) и sentinel (§7): они **генерируют артефакт**, не пишут.
- **integrated-view — read-only синтезатор, без рекомендаций** (CLAUDE.md, роли скиллов). Оптимизатор
  по природе выдаёт рекомендации (целевые веса) → его место **вне** integrated-view, отдельным
  скиллом (§5).
- **Frozen US-stocks** (память `feedback_frozen_us_stocks`): позиции с `current_price_source ==
  "cost_basis"` зафиксированы на 21.02.2022 и не анализируются. Оптимизатор и любые скоры обязаны
  их **исключать**.
- **Phantom precision** (принцип №1 из `05-…TODO.md`): оценки expected return шумные (широкие CI) —
  не выдавать ложную точность. Особенно критично для оптимизатора (§5) и ML-скоров (§6).
- **Два зеркала вьюера** (CLAUDE.md «Синхронизация справки вьюера»): правки HTML — в обоих
  (`tools/…` репо + Synology `…/Claude-Memory/tools/…`); при смене вкладок/UI синхронизировать
  `docs/investment/portfolio-workflow-guide.md` и `Claude-Memory/tools/viewer-help.md`.

## 2. v4-A — Multi-portfolio support

**Цель.** Агрегировать **несколько отдельных портфелей** (второй брокер, ИИС супруги и т.д.):
синтезатор работает с каждым и/или с консолидацией.

> **Важно не спутать оси.** Снапшот **уже** содержит split «один владелец, два счёта»
> (`iis_positions`, `bonds_iis`, `goals.matrix_iis` в `parse_portfolio.py`) — это main vs ИИС-3
> внутри **одной** выгрузки. v4-A — **другая ось**: несколько владельцев/брокеров, у каждого своя
> выгрузка IntelInvest и свой `trades_portfolio_*.xlsx`.

**Соответствие архитектуре.** ✅ Чистое аддитивное расширение data-layer + aggregation. Инвариантов
не ломает, D3 соблюдён (пишет loader).

**Блокер.** Данные: нужна отдельная выгрузка IntelInvest на каждый портфель (по сути тот же блокер,
что [D-1](../TODO.md#d-1) per-account XIRR). Решается **организационно** — есть ли у пользователя
доступ к выгрузкам всех счетов.

**Эскиз реализации.**
1. **Loader — измерение `portfolio_id` (pid).** Имя снапшота получает slug владельца/счёта:
   `Portfolio/snapshots/portfolio-<pid>-<date>.json` (либо подпапка `snapshots/<pid>/`). Каждый
   портфель — свой прогон `parse_portfolio.py` → `portfolio_returns.py` → `per_security_xirr.py` на
   своих файлах. XIRR считается **per-portfolio**. В JSON добавить `portfolio_id`, `portfolio_label`.
2. **Aggregation — два режима в `aggregate_positions.py`:**
   - **per-portfolio** (как сейчас, на один pid) — без изменений в логике;
   - **consolidated** — объединение holdings нескольких снапшотов с **пере-нормировкой весов** по
     суммарной стоимости. Конфликт «одна бумага в двух портфелях» → суммировать qty,
     weighted-average cost-basis, `weight_pct` от общей стоимости. ИИС-3-ограничения (R10) и frozen
     US-stocks — per-portfolio, сохраняются.
3. **Viewer — измерение «портфель».** Селектор портфеля по аналогии с селектором горизонта C1
   (Блок C, 2026-06-11). Folder-picker уже читает все файлы — нужно **группировать** snapshot/iv
   по pid (парсить pid из имени) и хранить активный pid + псевдо-pid «Консолидировано» в `state`.
   Инвариант offline **сохраняется** (по-прежнему только локальные файлы).
4. **Stress / weekly-review.** Макро-прогнозы и факторные беты **общие** (свойство фактора, не
   портфеля) → stress можно гонять на консолидированных holdings. Решение «per-portfolio vs
   consolidated обзор» оставить пользователю (флаг).
5. **Зеркала + докуменация** (§1): viewer ×2, `viewer-help.md` + `portfolio-workflow-guide.md`
   (новый селектор портфеля).

**Сложность:** L. **Этапы:** (0) бэкап; (1) loader pid; (2) consolidated aggregation + тесты; (3)
viewer portfolio dimension; (4) зеркала/доки.

**Acceptance.**
- [ ] ≥2 снапшота с разными `pid` грузятся; viewer переключает портфели.
- [ ] Consolidated: Σ `weight_pct` = 100 ± 0.5; дубль-бумага суммирует qty и усредняет cost.
- [ ] Per-portfolio XIRR в каждом снапшоте; frozen US-stocks исключены per-portfolio.
- [ ] **Регрессия:** один pid → числа бит-в-бит как сейчас (никакой консолидации не навязано).
- [ ] Зеркала идентичны; обе справки синхронизированы.

**Рекомендация.** Главный кандидат Фазы 7 — делать первым, как только появятся данные по второму
портфелю.

## 3. v4-B — Real-time prices (переосмыслить)

**Цель (как в TODO).** Live-котировки MOEX ISS в integrated-view вместо цены на момент snapshot.

**Конфликт.** ❌ Прямо ломает инвариант **offline/no-network** вьюера (§1) и **реверсит I-1**: в
Фазе 2 браузерный fetch к ISS был осознанно удалён ради офлайна. Реализовать «как задумано» — значит
откатить свежее архитектурное решение.

**Рекомендуемая альтернатива — «refresh snapshot», не live-fetch.**
- Не котировки в браузере, а **лёгкий re-run loader**: `moex_quotes.py` (уже есть) обновляет цены →
  новый снапшот `portfolio-<date>.json`. Вьюер остаётся офлайн-читателем; «свежесть» цен = свежесть
  снапшота. Дельта цен **уже видна** через панель «Реализованная XIRR по снапшотам» / историю
  (вкладка «Динамика», viewer 2.2.0).
- Это даёт суть цели («не застревать на старом снапшоте») **без** нарушения инварианта.

**Если всё же нужен live-режим в браузере** (не рекомендую): изолировать за **явный opt-in тоггл
«🌐 Онлайн-цены»**, по умолчанию **off**, с предупреждением о сетевом вызове; дефолтный офлайн-путь
не трогать; запрашивать только `marketdata` по SECID из снапшота (как в удалённом `fetchMoexBond`).

**Сложность:** M (но конфликт делает реализацию нежелательной). **Рекомендация:** не реализовывать
как задумано; при необходимости — поток «refresh snapshot».

## 4. v4-C — ML-augmented catalyst generation (переосмыслить)

**Цель (как в TODO).** Train на исторических sell-side reports → автогенерация дерева катализаторов.

**Конфликт.** ⚠️ Дублирует то, что **уже делает LLM-advisor** (Mode 1/8 строит catalyst tree в
формат `weekly-review` `catalyst:`). Отдельный ML-стек (training, labeled dataset, feature pipeline,
serving) в репо отсутствует и несоразмерен *Низкой* критичности.

**Рекомендуемая альтернатива — LLM-native «catalyst extraction», без обучения модели.**
- Под-режим `ru-portfolio-advisor` (или расширение `forecast-collector`): подать корпус sell-side
  (через прочитанные отчёты / web_search) → Claude извлекает структурированные катализаторы строго в
  schema `weekly-review` `catalyst[]` (id `{event_type}_{fiscal_year}`, `source` required,
  опц. `macro_dependency`). Это «augment advisor», как и просит v4-C, но в духе LLM-first.
- **Калибровка качества** этих катализаторов уже запланирована: [V2-C](../TODO.md#v2-c) (Brier score
  на resolved `predictions_for_review`). То есть «обучающий сигнал» приходит через ретро-аудит, а не
  через отдельный ML-train.

**Если всё же ML:** нужен labeled dataset (катализатор → realized?), что упирается в тот же горизонт
накопления данных, что и V2-C. XL, отдельный слой инфры. **Рекомендация:** отложить ML-вариант;
рассмотреть LLM-native catalyst-extraction под-режим как дешёвую реализацию цели.

## 5. v4-D — Portfolio optimization layer (отдельный скилл)

**Цель.** Mean-variance / robust optimization поверх выходов системы.

**Архитектура.** ⚠️ «another class of tools», explicitly decoupled (`05-…TODO.md` §v4-D). Реалистично —
**новый самостоятельный скилл** `skills/portfolio-optimizer/`, НЕ часть integrated-view: тот —
read-only синтезатор без рекомендаций (§1), а оптимизатор по природе **рекомендует** целевые веса.
Разделение concerns = соблюдение D3-духа.

**Эскиз реализации.**
- `skills/portfolio-optimizer/scripts/optimize.py` (numpy + **scipy** — новая зависимость, opt-in):
  - **Вход (JSON):** `expected_returns` per position (из integrated-view `by_horizon.expected_pct`),
    `covariance` (из stress `factor_betas` × факторная ковариация, либо напрямую MC-сэмплы из V2-B
    Monte Carlo), `constraints` (ИИС-3 lock R10, frozen US-stocks исключены, min/max веса, лимит
    отклонения от текущих весов).
  - **Метод:** mean-variance frontier (`scipy.optimize`), плюс **robust-обвязка** — Black-Litterman-lite
    или явный кэп на |Δweight| от текущих, т.к. mean-variance — «error maximizer» на шумных
    expected-return оценках (широкие CI системы прямо это провоцируют).
  - **Выход:** целевые веса + сравнение с текущими (Δ return, Δ vol, Δ концентрация по секторам),
    с **честным CI** на ожидаемое улучшение (phantom-precision-guard, §1).
- **Связь с [V3-C](../TODO.md#v2-d)** (hypothetical re-allocation, отложена в Фазе 6): оптимизатор —
  «движок», V3-C — UI поверх него. Логично делать **вместе**.
- Артефакт → `save-to-library` (новый Workflow), D3 соблюдён.

**Сложность:** XL (новый скилл + scipy + тесты + честная подача неопределённости). **Acceptance:**
frontier считается; constraints (ИИС-3 / frozen / кэп Δ) соблюдены; вывод не лучше, чем позволяет CI;
тесты на синтетике. **Рекомендация:** самостоятельный скилл, после стабилизации v2-методологии
(✅ готова, Фаза 4); кандидат №2 после v4-A.

## 9. Риски и заметки

- **v4-B и инвариант offline** — главный риск фазы: реализация «в лоб» откатывает I-1. Любой live —
  только за явным opt-in тогглом, дефолт off.
- **D3** — `portfolio-optimizer` и sentinel **генерируют артефакт**, не пишут в `Claude-Memory/`
  напрямую (save-to-library).
- **Frozen US-stocks** — оптимизатор/скоры обязаны исключать `current_price_source == "cost_basis"`.
- **Phantom precision** — оптимизатор на широких CI = error maximizer; обязателен robust-обвяз и
  честная подача Δ с CI.
- **Новая зависимость scipy** (только v4-D) — opt-in, как numpy в SS-1; не тащить в stdlib-скрипты.
- **ML-инфра меняет деплой-модель** всего репо (skills = markdown + Python). Появление training/
