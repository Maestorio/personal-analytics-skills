## Что такое база (basis) в этом скилле

Скилл считает два слоя:

- **Layer 1 — ценовой (`price`).** Mark-to-market: переоценка позиций по факторной чувствительности. Это то, что лежит в `per_position.*.by_horizon.*`.
- **Layer 2 — купонный (`bond_carry`).** Купоны по фактическому графику, pull-to-par, реинвест, FX на купоны. Считается `compute_bond_carry.py` только по держимым облигациям.

**Дивидендов по акциям в стрессе нет.** Слой 3 (`dividend_forward`) живёт в weekly-review, и полную доходность из трёх слоёв собирает `portfolio-integrated-view`. Не добавлять дивидендный слой в стресс — это сломает downstream, который складывает слои сам.

Отсюда ровно две базы:

| basis | Состав | Где применяется |
|---|---|---|
| `price` | Layer 1 | `per_position`, секторальная сводка, ценовые агрегаты |
| `total_return` | Layer 1 + Layer 2 | портфельные агрегаты полной доходности |

**Инвариант, который нельзя нарушать:** `per_position` всегда `price`. `portfolio-integrated-view` считает `total_return[hNN][scenario] = price_delta + bond_carry + dividend_income` сам; если положить в `per_position` полную доходность, купон удвоится.

## Задача 1. Контракт имён

Ввести в схему выхода фиксированный набор имён. Правило: **имя поля само называет базу, и обе базы эмитятся рядом.** Поле `basis` дублирует это машиночитаемо. Голых имён, не называющих базу, в новой схеме не остаётся.

### 1.1. Новые top-level поля

```yaml
schema_version: 2
basis_contract: 1                 # версия контракта баз; при смене имён — инкремент
layers_included:                  # что входит в total_return этого прогона
  price: true
  bond_carry: true
  dividends: false                # в стрессе дивидендов нет — всегда false
per_position_basis: price         # инвариант, всегда price
base_value_rub: <int>             # знаменатель ВСЕХ pct-полей
base_value_note: "<из чего состоит: holdings unblocked + кэш; что исключено>"
```

`base_value_rub` вынести явно и считать один раз. Сейчас база фигурирует только в тексте `.md` («База расчёта: 45 060 969 ₽»), а все проценты считаются от неё неявно — это следующий кандидат на такой же дрейф.

### 1.2. Портфельный уровень по сценариям

Заменить `scenarios.<X>.portfolio_level_by_horizon.<hNN>` на:

```yaml
scenarios:
  A:
    portfolio_level_by_horizon:
      h12:
        price_delta_rub: <int>
        price_delta_pct: <float>
        carry_rub: <int>
        carry_pct: <float>
        total_return_rub: <int>
        total_return_pct: <float>
```

Инвариант: `total_return_rub == price_delta_rub + carry_rub` (допуск ±1 ₽ на округление).

**Запрещённые имена в новых файлах** (валидатор из задачи 3 отклоняет файл при их наличии):
`delta_rub`, `expected_pct_pweighted` на портфельном уровне (внутри `per_position` оно легитимно и остаётся), `l1_price_only_delta_rub`, `l1_price_only_pct`.

### 1.3. Портфельные агрегаты

Заменить скаляры `expected_pl_rub` и `portfolio_pl_range_rub` на блок с обеими базами и разбивкой по всем горизонтам:

```yaml
portfolio_aggregates:
  price:
    basis: price
    expected_pl_rub_by_horizon: {h6: <int>, h12: <int>, h24: <int>}
    expected_pl_pct_by_horizon: {h6: <float>, h12: <float>, h24: <float>}
    pl_range_rub_by_horizon:
      h6: {min: <int>, max: <int>, min_scenario: "<id>", max_scenario: "<id>"}
      h12: {...}
      h24: {...}
  total_return:
    basis: total_return
    expected_pl_rub_by_horizon: {...}
    expected_pl_pct_by_horizon: {...}
    pl_range_rub_by_horizon: {...}
```

**Запрещённые имена:** `expected_pl_rub` (скаляр), `portfolio_pl_range_rub` (скаляр), `total_return_by_horizon_rub` (появился в прогоне 09-18, заменяется на `portfolio_aggregates.total_return`).

### 1.4. Robustness — две базы

Это поле меняло смысл чаще всех: в прогоне 03.09 считалось на полной доходности и по горизонтам, в прогоне 18.09 — на ценовом слое и плоско, **под тем же именем**. Именно отсюда вывод «3 из 4 сценариев положительны» вместо «4 из 4».

```yaml
robustness:
  price:
    basis: price
    by_horizon:
      h6:
        positive_or_neutral_scenarios: <int>
        worst_case: {id: "<sid>", pl_pct: <float>}
        best_case:  {id: "<sid>", pl_pct: <float>}
        spread_pct: <float>
      h12: {...}
      h24: {...}
  total_return:
    basis: total_return
    by_horizon: {...}
  modal_scenario: "<id|none>"
  hedge_target: "<текст>"
```

`modal_scenario` и `hedge_target` от базы не зависят и остаются на верхнем уровне блока.

### 1.5. Секторальная сводка

`sector_breakdown_pct` и любые секторальные ΔRUB — добавить рядом `sector_breakdown_basis: price`. Секторальные числа собираются из `per_position`, то есть всегда ценовые. Явно это записать.

### 1.6. Скаляр `p`

`scenarios.<X>.p` в прогоне 09-03 был значением на primary horizon (A = 0.15), в прогоне 18-09 стал средним по горизонтам (A = 0.2233). `p_by_horizon` при этом не менялся. Добавить рядом:

```yaml
p_basis: primary_horizon | mean_across_horizons
```

Выбрать `primary_horizon` как значение по умолчанию (совпадает с тем, как поле читается интуитивно), но не менять существующую логику расчёта — только подписать, что именно посчитано, и дать возможность задать второе значение явно.

## Задача 3. Валидатор — главный результат работы

Создать `scripts/validate_stress_output.py`. Он должен быть единственным механизмом, который не даёт схеме уехать снова. Вызов:

```
python3 scripts/validate_stress_output.py --input <stress.yaml> [--snapshot <portfolio.json>] [--json]
```

Exit 0 — чисто. Exit 1 — есть блокеры. Блокеры печатаются с указанием поля и ожидаемого/фактического значения.

Проверки. Разделить на `STRUCTURE` (присутствие и имена) и `RECONCILE` (сходимость чисел). Обе группы блокирующие.

### STRUCTURE

- **3.1.** Все поля из 1.1 присутствуют и непусты. `layers_included.dividends` строго `false`.
- **3.2.** Ни одного запрещённого имени из 1.2 и 1.3 на портфельном уровне.
- **3.3.** У каждого блока `portfolio_aggregates.*` и `robustness.*` поле `basis` совпадает с ключом блока.
- **3.4.** `portfolio_aggregates` и `robustness` покрывают **все** горизонты из `horizons`, обе базы.
- **3.5.** `per_position_basis == "price"`; ни в одной записи `per_position.*.by_horizon.*` нет ключей, намекающих на карри или полную доходность (`carry`, `total_return`, `coupon`).

### RECONCILE

Допуски: денежные — ±1 ₽; процентные — ±0,01 пп; агрегатные сверки снизу вверх — ±0,5% от `base_value_rub`.

- **3.6. Тождество слоёв.** Для каждого сценария × горизонта: `total_return_rub == price_delta_rub + carry_rub`. Это ловит именно тот класс ошибки, ради которого задача делается.
- **3.7. Снизу вверх.** `price_delta_rub[X][h]` должен сходиться с суммой по позициям: `Σ_i (weight_pct_i / 100 × base_value_rub × delta_pct_by_scenario_i[X][h] / 100)`. Расхождение больше допуска — блокер. В прогоне 2026-09-03 портфельный уровень был в полной доходности, а `per_position` — в ценовой, и эта проверка бы его отклонила.
- **3.8. Вероятностное взвешивание.** Для каждой базы и горизонта: `expected_pl_rub_by_horizon[h] == Σ_X p_by_horizon[h][X] × pl_rub[X][h]`. Отдельно: `Σ_X p_by_horizon[h][X] == 1.0` (±1e-6) для каждого h.
- **3.9. Коллизия горизонтов (детектор, ничего не чинит).** Если для какого-либо сценария набор значений `factors_by_horizon` полностью совпадает между двумя разными горизонтами — вывести блокер с текстом, что горизонты численно неразличимы, и назвать оба ключа. Причина такого совпадения — выбор фактора по ближайшему **году** в `compute_horizon_factors.py`, когда два горизонта попадают в один календарный год. Логику выбора НЕ менять; задача детектора — не дать такому файлу уйти в библиотеку молча.
- **3.10. Диапазон.** `pl_range_rub_by_horizon[h].min` равен минимуму по сценариям на этой базе, `.max` — максимуму; `min_scenario` / `max_scenario` совпадают с argmin / argmax.
- **3.11. Robustness.** `positive_or_neutral_scenarios` равен числу сценариев с `pl_pct >= 0` **на своей базе**; `worst_case.id` / `best_case.id` совпадают с argmin / argmax; `spread_pct == best.pl_pct - worst.pl_pct`.
- **3.12. Проценты.** Каждое `*_pct` равно соответствующему `*_rub / base_value_rub × 100`.
- **3.13. Покрытие (при переданном `--snapshot`).** `unmapped_tickers` пуст; каждый тикер/ISIN из `per_position` есть в снапшоте среди unblocked; сумма `weight_pct` по `per_position` равна 100 ± 0,5.
- **3.14. Carry-провенанс (при переданном `--snapshot`).** Каждый ISIN в `bond_carry.per_position` есть в снапшоте; записи с `credit_review_required: true` имеют `expected_carry_pct == 0` на всех горизонтах.

### 4.1. Определение базы старого `delta_rub` — по сверке, не по дате

В архиве `delta_rub` означает разное. Определять надо арифметически, а не по эвристике «до такой-то даты»:

1. Посчитать ценовую сумму снизу вверх (как в 3.7).
2. Если `delta_rub` сходится с ней в пределах допуска → `basis: price`.
3. Если расходится, а `delta_rub − ценовая сумма` совпадает с суммой `bond_carry` по этому сценарию и горизонту → `basis: total_return`.
4. Если не подошло ни то ни другое → `basis: unknown` и запись в отчёт. **Не угадывать.**

Известные алиасы для маппинга: `l1_price_only_delta_rub` → `price_delta_rub`; `l1_price_only_pct` → `price_delta_pct`; `total_return_by_horizon_rub[h][X]` → `portfolio_aggregates`-эквивалент; плоский `robustness` → `robustness.<определённая база>.by_horizon`.
