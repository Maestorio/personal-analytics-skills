## Пакет A · PSS-6 — перевзвешивание и чувствительность

**Новый файл:** `skills/portfolio-scenario-stress/scripts/reweight_stress.py`
**Новые тесты:** `skills/portfolio-scenario-stress/tests/test_reweight_stress.py`

### A.0. Граница инструмента (решение 2026-08-04)

Инструмент **только читает и печатает**. Не пишет и не изменяет stress-YAML, ничего не
сохраняет в Claude-Memory.

Причина: D2 сознательно убрало `expected_pl_*` из вывода стресса — равные веса Pure
Shell не вероятности, среднее по ним вводит в заблуждение. Инструмент, дописывающий EV
в артефакт, вернул бы это через заднюю дверь.

Следствие: вопросы «в какие поля писать», `weight_type`, `modal_flag`,
`expected_pl_rub` не возникают. Ничего из этого не трогать.

### A.1. Что считается и на какой базе

Вход: `per_position[t].by_horizon[h].delta_pct_by_scenario[s].value` и
`per_position[t].weight_pct`. Пересчёта бет, факторов и сети нет.

**Величина — ценовая переоценка портфеля (Слой 1).** Это должно быть написано в каждом
выводе. Она **не** сопоставима с `expected_pct_pweighted` (там total-return с carry и
дивидендами) и не с `portfolio_summary.pct_by_scenario_h12`.

**Базы (проверено до рубля):**

| величина | знаменатель | значение на 08-04 |
|---|---|---|
| `weight_pct` | незаблокированные holdings, **без кэша** | 40 262 371.80 ₽ |
| `l1_price_only_pct` | **полная** база с кэшем | 41 480 997.00 ₽ |
| `cash_rub_pct`, `blocked_pct` | полная база | — |

Отношение баз **1.03027**. Складывать `Σ weight_pct + cash_rub_pct + blocked_pct`
нельзя — на живом файле 102.61.

Инструмент **печатает `Σ weight_pct` и обе базы в каждом выводе**, предупреждает при
`|Σ − 100| > 0.5`. На артефакте 08-04 сумма 99.6701 (до-фиксный вес `RU000A1038V6`),
на свежих прогонах 99.9999.

### A.2. API

```python
def load_stress(path: Path) -> dict
    """schema_version != 2 -> SystemExit(2)."""

def portfolio_by_scenario(stress: dict) -> dict[str, dict[str, float]]
    """
    {hk: {sid: dPct ценовой переоценки от ПОЗИЦИОННОЙ базы}}.
    dPct(h,s) = sum_t weight_pct[t]/100 * delta_pct_by_scenario[t][h][s].value
    Ячейки с price_delta_zeroed участвуют как есть (value = 0.0).
    """

def portfolio_rub_by_scenario(stress: dict, positions_value_rub: float
                              ) -> dict[str, dict[str, float]]
    """{hk: {sid: dRub}} — то же в рублях. Нужно для сверки с артефактом (A.4 #1)."""

def weighted_expectation(pbs: dict, weights: dict[str, float]) -> dict[str, float]
    """{hk: dPct}. Валидации суммы здесь НЕТ — она в CLI."""

def sensitivity(pbs, axis_sid, horizon, baseline, *, steps: int = 11) -> dict
    """
    Модель: вес axis_sid едет 0->1, остальные сохраняют ВЗАИМНЫЕ пропорции baseline
    и делят остаток (1 - w).

    Сетка: концы ВКЛЮЧЕНЫ, w_i = i/(steps-1), i = 0..steps-1.
    steps < 2 -> SystemExit(2) (при steps=1 деление на ноль).
    slope — АНАЛИТИЧЕСКИЙ (V_axis - M), не снятый с таблицы.

    sum b_s по s != axis == 0 -> SystemExit(2): пропорции остальных неопределены.
    Случай b_axis == 0 законен: ось из M исключена, w едет 0->1 независимо от baseline.

    Возвращает {"axis","horizon","baseline_w","baseline_source",
                "table":[{"w","value"},...], "slope","M","V_axis"}
    """

def solve_for(pbs, axis_sid, horizon, baseline, target: float) -> float | None
    """
    E(w) = w*V_axis + (1-w)*M,  M = sum_{s != axis} (b_s/sum b_{s != axis}) * V_s
    E линейна по w => w* = (target - M)/(V_axis - M)  — ЗАМКНУТАЯ ФОРМА, не бисекция.
    |V_axis - M| < 1e-12 -> None. w* вне [0,1] -> None.
    """
```

**Чего в API нет.** `monotonic` и бисекция сняты: `E(w)` линейна по построению модели.
`leader_flip` снят: лучший сценарий это `argmax_s V_s`, от весов не зависит.

### A.3. CLI

```
reweight_stress.py --stress FILE [--weights JSON] [--sensitivity SID]
                   [--target FLOAT] [--horizon hNN] [--steps N]
```

- `--weights` — JSON-строка или путь: `{"A":0.4,...}` либо `{"h6":{...},...}`.
- Сумма != 1 +- 1e-6 -> **SystemExit(2)** с горизонтом и суммой. Молча нормировать
  нельзя. Проверка **в CLI**.
- Набор sid != набору артефакта -> SystemExit(2) с обеими разностями.
- Набор ключей горизонта в `--weights` != набору `by_horizon` -> SystemExit(2).
- `--horizon` default — `primary_horizon` артефакта. Это **int** (12), ключи —
  `"h12"`: конвертация `f"h{primary_horizon}"` обязательна и покрыта тестом. В репо
  уже есть шрам ровно от этого (`f"h{h}"` на строке давал `"hh6"`).
- `--sensitivity` не требует `--weights`. Baseline: `scenarios[sid].p_by_horizon[hk]`
  при наличии, иначе `scenarios[sid].p`. **Источник печатается** и возвращается в
  `baseline_source`.
- Baseline с `sum b != 1` -> предупреждение: кривая в точке `baseline_w` перестанет
  совпадать с `weighted_expectation(pbs, baseline)`.
- `--target` только вместе с `--sensitivity`.
- Вывод — текст в stdout. **Шапка каждого вывода:** величина = ценовая переоценка
  (Слой 1), `Σ weight_pct`, обе базы, источник baseline.

### B.1. Проблема

`half_width = max(|delta|*0.4, 5.0)` зависит только от величины движения. У SBER в D из
+45.86% движения **+31.5 п.п. — санкционный канал**, откалиброванный на одном эпизоде.
У `RU000A106E90` ценовые +17.60% на **97.5%** из `cbr_rate` — дюрация и арифметика.
Обе получают одинаковую относительную ширину.

### B.2. Формула и порядок

```
1. свёртка:   raw = sqrt( sum_f ( |beta_f * f_value_eff| * u_f )^2 )
2. пол:       hw  = max(raw, CI_MIN_HALF_WIDTH_PP)
3. r2:        только в легаси-ветке (contributions=None) — как сейчас, после пола
4. инфляция:  _inflate_ci в _build_by_horizon — не трогается
```

`f_value_eff` — движение фактора **после** клампа `sanctions_position`
(`compute_delta_pct:314–316`, кламп до умножения на бету).

Квадратичная свёртка, не сумма: вклады разных факторов не обязаны ошибаться в одну
сторону.

**Потолка нет.** В v1 стоял `CI_MAX_HALF_WIDTH_PP = 60.0` с обоснованием «иначе SBER
уедет за ±40». Измерено: максимум по всем **632 ячейкам** — **21.82 п.п.** (SBER h24/D),
с CI-инфляцией 22.79. Потолок не связывал бы нигде. Обоснование было выдумано.

### B.3. Пол 5.0 — решение и честное обоснование

`CI_MIN_HALF_WIDTH_PP = 5.0` **сохраняется** (решение пользователя 2026-08-04).

> **Формулировка v2 была неверна в обеих половинах — не повторять её.**
>
> Говорилось: «кредитного качества в семи факторах нет вовсе» и «для акций —
> идиосинкратика». Оба опровергнуты:
>
> 1. **Кредитный канал в модели ЕСТЬ.** `references/bonds-sensitivity.md` §4 называется
>    «Кредитный риск (Credit Spread)», политические беты облигаций выводятся именно из
>    него: `beta_sanctions = -duration_years * dSpread_bps / 100`. Нет **независимого**
>    кредитного фактора, и магнитуда таблицы помечена как заниженная (строка 120, PSS-5).
> 2. **Идиосинкратика — не «вне контура», а отдельный слой.**
>    `aggregate_positions.py:1035–1040`: `total.ci = macro_ci + div_ci + idio_ci`,

   Весов на h18 нет, интерполяция запрещена сознательно (`weights_by_horizon`:

   > marginal остаётся посчитанным на ПРЕЖНИХ весах, и внешне он неотличим от

   > реализации шага 2 пропуск по несопоставимому горизонту обязан идти туда же,
   > а не тихо.

4. **`save-to-library`** — менять нечего, проверено прогоном:
   `validate_scenario_events` принимает сценарный файл с `p_by_horizon`
   (`valid ✓`), `validate_forecast_events` принимает forecast-YAML и до, и после
   пересчёта Layer 2 по горизонтным весам — структура `marginal.values` не
   меняется, только числа.

   *Наблюдение, не задача: валидатор поэтому и не заметит, если пересчёт сделан
   НЕВЕРНЫМИ весами. Проверять арифметику весов — новое требование, которого в
   контракте нет; Layer 2 по архитектуре диагностический.*

**Итого: шаг 2 разблокирован — осталась работа, решений не требуется.**
Приоритет низкий по факту: `portfolio-integrated-view` Layer 2 marginal
