# Режим готовки — исследование UX кухонных интерфейсов

**Что это:** веб-исследование, а НЕ архитектурный план. Собрано 2026-07-20 для
проектирования экрана «Рецепт — готовка» в разделе «Еда» Personal Hub.

**Архитектура раздела (модель данных, хранилище, сайдкар, роутинг) — не здесь.**
Она в утверждённом плане контура; промт для Claude Design и решения по экранам —
в `tools/design-reference/food-plan.md`. Этот файл отвечает только на вопрос
«как должен быть устроен пошаговый режим на кухне и почему».

> Происхождение: файл собран исследовательским агентом и содержал ещё разделы с
> архитектурой (рецепт-на-файл, скан папки, хеш-роутинг) — они противоречили
> утверждённому контуру и удалены. Остались проверяемые находки со ссылками.

---

## 1. Главное: «cook mode» — перегруженный термин

| Что называют cook mode | Кто | Что это на самом деле |
|---|---|---|
| Только Wake Lock | NYT Cooking, BBC Good Food, EatingWell, Simply Recipes, весь WordPress-эко | Тумблер «экран не гаснет». Навигации по шагам нет вообще |
| Настоящий пошаговый режим | Crouton, Mela, Paprika, AnyList, Mealie, Google Nest Hub, Alexa Show | Полноэкранный фокус на одном шаге, крупный кегль, ингредиенты рядом |

Крупные веб-издания сделали только дешёвую часть: их страница — рекламный носитель,
и ломать её ради UX они не станут. **Вывод: копировать «cook mode» крупных сайтов не
надо, это ухудшенный образец.** Ориентир — приложения без рекламной модели и
смарт-дисплеи, где готовка была основным сценарием продажи железа.

Русский сегмент: режима готовки нет ни у Гастроном.ру, ни у Еда.ру, ни у Повар.ру.
Локального образца для сверки не существует.

## 2. Решения и обоснования

### 2.1. Количества ингредиентов прямо в тексте шага — самый доказанный пункт

Два независимых разбора приходят к одному через эвристику Нильсена «minimize the
user's memory load»: стандартный формат рецепта требует «superhuman short term memory
for ingredient quantities», и люди бесконечно скроллят между таблицей и шагами.
Решение — гибрид: список сверху для закупки + количества в тексте шага для готовки.
Реализовано у Crouton, Mealie, RecipeStripper.

- https://mike-eng.com/the-ux-of-recipe-formats/
- https://medium.com/usabilitygeek/the-user-experience-on-recipe-sites-is-broken-4584973a1fbe

**Проверка на реальных данных (`Pasta_Bolognese.pdf`):** количества проставлены
непоследовательно. Есть «Разогреть 15 мл оливкового масла», «фарш порциями по
150–200 г», «зарезервировать 150 мл крахмальной воды». Нет — «Добавить томатную пасту»
(80 г), «Влить белое вино» (150 мл), «Добавить бульон и молоко» (300 мл / 200 мл),
то есть на шагах 4 и 5, где ошибка дороже всего.

**Следствие для проекта:** это чинится строкой в `docs/food/instruction.md`, а не кодом:

> В пошаговой инструкции указывать количество каждого ингредиента прямо в тексте шага
> при первом его использовании («добавить томатную пасту 80 г»), даже если оно уже есть
> в таблице ингредиентов. Таблица — для закупки и проверки наличия, текст шага — для
> готовки.

Вдобавок это то, что делает работающим пересчёт порций: страница подставляет
пересчитанные числа в текст шага, но подставлять их некуда, если чисел там нет.

### 2.2. Один шаг на экран

**Контролируемых исследований именно для готовки не существует** — ни у NN/g, ни у
Baymard. Опора на три вещи:

1. **Сходимость практики.** Crouton, Mela, Paprika, AnyList, Mealie, Nest Hub, Echo Show
   независимо пришли к «один шаг за раз».
2. **NN/g про визарды:** один шаг на экран «reduces cognitive overload», «better screen
   real estate for larger, less-crowded controls», «decreased error rates».
3. **Архитектурный довод:** страница перерисовывается целиком по состоянию — это
   убивает позицию скролла, но точно восстанавливает дискретный `stepIndex`.

Скролл-простыня с подсветкой по позиции скролла отвергнута: платим сложностью
(IntersectionObserver / scroll-timeline), не получаем фокуса, конфликтуем с перерисовкой.

**Важная поправка:** правило NN/g «не давать выбрать шаг до завершения предыдущих»
к готовке **не переносится**. В визардах следующий шаг зависит от введённых данных,
в рецепте — нет, а потребность прыгнуть назад («сколько там соли?») возникает постоянно.
Переносить сюда запрет — карго-культ.

- https://www.nngroup.com/articles/wizards/
- https://developers.googleblog.com/tasty-a-recipe-for-success-on-the-google-home-hub/

**Проверка применимости к нашим данным:** шаги в «Болоньезе» атомарны — 7 штук по
40–55 слов (≈4–5 строк при кегле 24px). Резать данные не надо. Бонус: у каждого шага
уже есть короткое имя («Обжарка фарша») — это ровно то, что NN/g требует для списка
шагов, — и длительность в заголовке («8 мин»).

### 2.3. Типографика и тап-цели

- Исследование MIT AgeLab в разборе NN/g: крупнее — значимо быстрее (p<0.01);
  **condensed-начертания на 11.2% медленнее**. Оговорка самих авторов: тестировались
  изолированные слова, поэтому находка «прописные быстрее строчных на 26%»
  **не переносится** на связный текст — капсом шаги не писать.
- WCAG 2.2 SC 2.5.8 (AA) — 24×24px это **пол**, не рекомендация; SC 2.5.5 (AAA) — 44×44;
  Apple HIG 44pt; Material 48dp.
- Hoober: 49% держат телефон одной рукой, 75% взаимодействий большим пальцем; низ по
  центру — «green zone», верхние углы — «red zone».

Цифры под сценарий «дистанция 50–70 см, руки грязные» (*экстраполяция, не источник*):
текст шага 22–28px, line-height 1.5–1.6, ширина ≤65 знаков, контраст целить в 7:1,
кнопки навигации ≥56×56px с зазором ≥12px, количества выделять весом 600–700, не цветом.

- https://www.nngroup.com/articles/glanceable-fonts/
- https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
- https://www.smashingmagazine.com/2016/09/the-thumb-zone-designing-for-mobile-users/

### 2.4. Wake Lock

- Требует **secure context (HTTPS)** — обходов нет. По `http://` в локальной сети
  не работает в принципе.
- Поддержка ~93–94%: Chrome 85+, Safari 16.4+, Firefox 126+.
- Снимается автоматически при скрытии вкладки, потере фокуса, низком заряде →
  обязателен `visibilitychange` + повторный `request()`; sentinel не переиспользуется.
- Может отказать с `NotAllowedError`.
- **Историческая мина:** в приложениях с домашнего экрана iOS не работал с 16.4 по
  18.3.1, починено только в iOS 18.4 (31.03.2025).
- Рекомендации Chrome/MDN: видимый индикатор активности, лёгкое выключение, только по
  инициативе пользователя, progressive enhancement, `try/catch`.

Отсюда: **тумблер, привязанный ко входу в режим готовки**, а не автозахват при загрузке
страницы — иначе воруем батарею у того, кто просто читает рецепт.

- https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API
- https://caniuse.com/wake-lock
- https://bugs.webkit.org/show_bug.cgi?id=254545

### 2.5. Таймеры — почему их нет

Веб-таймер структурно хуже системного таймера телефона:

- Chrome с 88-й версии душит фоновые таймеры до одной проверки в минуту (вкладка
  скрыта >5 мин); Safari аналогично плюс Tab Purging.
- `navigator.vibrate` **Safari не поддерживает ни на одной платформе**, Firefox убрал
  в 129.
- Web Push на iOS работает только для PWA с домашнего экрана, не из вкладки Safari;
  звук веб-уведомлений не настраивается; Background Sync на iOS нет вовсе.

То есть даже полностью реализованный веб-таймер не звучал бы на заблокированном экране
и не пережил бы закрытие браузера — бледная копия того, что у человека уже в руке.

**Замена за ноль логики:** длительность уже лежит в заголовке шага — показывать её
заметным бейджем «⏱ 8 мин».

**Следствие:** без таймеров человек будет выходить из страницы к системному таймеру.
Значит сохранение прогресса из «желательно» становится обязательным, а перезапрос
Wake Lock по `visibilitychange` — основным сценарием, а не страховкой.

- https://developer.chrome.com/blog/timer-throttling-in-chrome-88

### 2.6. Отметки: асимметрия ингредиентов и шагов

Ингредиенты — **чекбоксы**: снимают реальную неопределённость («сыпал соль или нет?»),
единодушно у Paprika, Mela, AnyList, Mealie.

Шаги — **подсветка, не чекбокс**: в режиме «один шаг на экран» текущий шаг уже отмечен
самим фактом отображения, а «Шаг 3 из 7» и есть прогресс; чекбокс дублирует состояние и
стоит лишний тап мокрой рукой. AnyList не случайно выбрал «tap on your current step to
**highlight** it».

Возврат после отвлечения: сохранять индекс шага (не позицию скролла — она ломается при
повороте и смене кегля), при возврате не продолжать молча, а показать «Вы остановились
на шаге 4 — [Продолжить] [Начать заново]». Если прошло больше ~6–8 часов, первым
предлагать «Начать заново».

- https://help.anylist.com/articles/recipe-cooking-view/
- https://www.nngroup.com/articles/designing-for-waits-and-interruptions/

## 3. Антипаттерны

**Подтверждено источниками:**

1. Реклама между шагами; страница фуд-блога >4000 слов с автоплеем и попапами.
2. Прокрутка вверх-вниз за количествами — нарушение эвристики «minimize memory load».
3. Жест как единственный способ действия: «content that only appears via gesture is
   invisible to many users». Свайп допустим **только поверх видимых кнопок**.
4. Аккордеон с автоскроллом к верху — ломает ожидания кнопки «Назад» (NN/g).
5. Кнопки в верхней зоне экрана — «red zone» по Hoober.
6. Condensed-шрифты — +11.2% времени распознавания.
7. Точки-индикаторы и деления полосы прогресса как тап-цели: при 8–15 шагах цель
   выходит 8–12px, ниже минимума WCAG 24×24.

**Вывод из анализа, без прямого источника:**

8. Автопереход на следующий шаг по срабатыванию таймера — таймер сработал ≠ вы готовы.
9. Модальный режим готовки без явного выхода.
10. Один шаг = пять предложений: «шаг на экран» помогает, только если шаг атомарен;
    иначе резать надо данные, а не интерфейс.
11. Скрытие ингредиентов «ради минимализма» — прямой конфликт с §2.1.
12. Голосовое управление в вебе на русском: Web Speech API + шум кухни + офлайн не
    сложатся; у Google и Amazon за этим годы работы и облако.
13. Молчаливый фолбэк Wake Lock — пользователь решит, что сломано у нас.

## 4. Оговорки о качестве доказательств

1. **Сильная база:** технические ограничения (Wake Lock, троттлинг таймеров, Vibration,
   тап-цели) — спецификации, caniuse, баг-трекеры, офдоки. Типографика — настоящий
   психофизический эксперимент MIT AgeLab.
2. **Средняя база:** inline-количества (два аналитических разбора + реализации в
   продуктах), один шаг на экран (сходимость 6+ продуктов).
3. **Вывод из анализа, не источник:** конкретные кегли и 56px под дистанцию 50–70 см;
   асимметрия чекбоксов; авто-сброс прогресса по давности; довод «полная перерисовка ⇒
   дискретное состояние»; неприменимость запрета NN/g на прыжки между шагами.
4. **Отброшено как непригодное:** кейс-стади рецептурных приложений на Medium — это не
   данные. Цифра «Betty Crocker +300% purchase intent» из документации Chrome —
   вендорский маркетинг без методологии, нигде не использована.
