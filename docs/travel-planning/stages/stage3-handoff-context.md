## Что в Stage 3 сейчас

### Назначение

Извлечь POI из reading list Stage 2, нормализовать имена, посчитать
упоминания по тональности, категоризировать в 6 категорий (STRONG /
WEAK CONFIRMED / HIDDEN GEM / CONTESTED / RED FLAG / LOW SIGNAL).
Дополнительно — пометить кандидатов на **synergy** (POI, типично
комбинируемые местными операторами в одну экскурсию) и **iconic
exceptions** (топ-1 эталон категории, формально исключённой профилем).

### Входные файлы

- `1_dr_reports.md` (Stage 1).
- `2_similarity.md` (Stage 2) с непустым `reading_list`.
- Профиль `profiles/{profile_id}.md`.

### Выход

`{trip_id}/3_poi_aggregation.md`:

- YAML-шапка с счётчиками 6 категорий, `aggregation_mode`,
  `iconic_exceptions`, `synergy_pairs`.
- Per-POI блок с полями 1–6, опц. строки `**Iconic exception:**` и
  `**Combined with:**`, поле «Комментарий пользователя:» (пустое —
  заполняется человеком перед Stage 4).
- Non-mainstream highlights.
- Опц. сравнение с предыдущим планом.

### Граница LLM vs скрипт

Один скрипт `aggregate_pois.py` (vs два у Stage 2 — там был ещё
парсер). У Stage 3 детерминированной первичной обработки нет:
извлечение POI из прозы — чистая семантика.

| Что делает LLM | Что делает скрипт |
|---|---|
| Извлечение POI из полей 14/15 карточек | Счёт упоминаний по тональности и категории автора |
| Нормализация имён POI (одно место под разными написаниями) | 6 правил категоризации (приоритет CONTESTED → RED FLAG → STRONG → WEAK → HIDDEN GEM → LOW) |
| Тональность каждого упоминания | `resolve_mode` (abundant / scarce по доле HIGH) |
| Извлечение цитат и characteristics | Анти-bloat warnings |
| Проставление `iconic_exception` | Passthrough флага + подсчёт `iconic_exceptions` |
| Проставление `commonly_combined_with` (v0.17+) | Passthrough поля + подсчёт `synergy_pairs` |

### Модель

**Sonnet 4.6 + adaptive thinking** (приоритет); **Opus 4.7 без
thinking** — fallback.

Калибровочно установлено: Sonnet+thinking лучше **нормализует POI**
(не раздаёт «Cerro Fitz Roy view» в отдельный POI от трека к
Лагуна-де-лос-Трес — консолидирует в одну запись), Opus —
**over-decomposes** (раздувает число POI, обнуляет STRONG CONFIRMED
счёт). Менять дефолт — нет оснований.

### Два режима категоризации

| Режим | Условие | WEAK CONFIRMED порог |
|---|---|---|
| `abundant` | доля HIGH ≥ 30% | `high_recommend ≥ 2` |
| `scarce` | доля HIGH < 30% | `high_recommend ≥ 1` + non-HIGH подтверждение |

Скрипт выбирает автоматически; форс — флаг `--mode`. STRONG CONFIRMED
от режима не зависит — всегда `high_recommend ≥ 3` от **разных**
HIGH-авторов.

## v0.17 — POI synergy detection (hybrid A+B)

### Корневая проблема

Stage 4 в первой v0.13–v0.16 итерации не умел сам обнаруживать пары
POI, которые типично комбинируются местными операторами в одну
экскурсию (катерный комбо-тур Бигль + Мартильо в Ушуае; мостки +
мини-трек на одном леднике Перито-Морено). §6.1 prose-правила в
Stage 4 ловили это нестабильно — модель формально проходила
Pre-emit checklist Класс B, но в реальности пары не объединяла.

### Решение

Перенос **обнаружения** в Stage 3 (data-anchor в payload), **применение**
оставлено в Stage 4. Это вариант **гибрид A+B** из обсуждения:

| Слой | Стадия | Что делает |
|---|---|---|
| Обнаружение | Stage 3 (LLM при экстракции POI) | Помечает кандидатов синергии в поле `commonly_combined_with` |
| Passthrough | `aggregate_pois.py` | Пробрасывает поле без изменений + считает `synergy_pairs` |
| Применение | Stage 4 §6.1 (priority pool) | Читает помеченные пары как **единые юниты**, формулирует день как «X + Y единой экскурсией» |
| Контроль | Stage 4 Pre-emit Класс B | Каждая пара отработана: в одном дне или явно расцеплена в «осознанно отбрасывает» |

### Формат поля

```json
"commonly_combined_with": [
  {
    "poi_name": "Имя второго POI",
    "why": "Краткое обоснование на основе характеристик / упоминаний"
  }
]
```

Симметрично: если POI #X помечен с #Y, то #Y тоже помечается с #X
(модель делает руками; скрипт автоматически не достраивает).

### Изменения в файлах (v0.17)

- `stage3-poi.md`: §6.6 (payload), §6.7 (output), §6.9 (новая
  секция — спека synergy с признаками), §8 (markdown-строка

- `aggregate_pois.py`: passthrough поля + `aggregates.synergy_pairs`.
- `test_aggregate_pois.py`: проверки passthrough + подсчёта + валидации

## v0.18 — расщепление признаков synergy

### Корневая проблема (по результату калибровки v0.17)

Sonnet+thinking при первом прогоне после v0.17 выдал `synergy_pairs: 0`
на Argentina. В логе видно, что модель **рассмотрела** кандидата
Бигль+Мартильо и **отвергла**:

> «Since the authors don't explicitly describe them as a combined
> package, I won't mark this as synergy.»

Признак 3 («явное упоминание совместности автором») применён слишком
буквально. Признак 2 («общая локация / транспорт») сформулирован как
жёсткое AND: одна стартовая точка **И** общий транспорт **И**
пересекающийся маршрут. Бигль+Мартильо удовлетворял первой части (один
порт), но не маршрут целиком — отвергалось.

Opus той же v0.17 нашёл цепочку троп Фитц-Роя (Лос-Трес ↔ Капри ↔
Сусия), но тоже пропустил Бигль+Мартильо и Перито-Морено+мини-трек.

### Решение

Расщепить признак 2 на два независимых:

| Признак | Что означает |
|---|---|
| **1. Общий оператор** | В characteristics обоих POI назван один и тот же оператор / провайдер (явная строка, не догадка). |
| **2a. Общая стартовая локация ИЛИ общий природный объект** | Стартуют из одной точки **ИЛИ** ссылаются на один и тот же физический объект (один ледник, одна гора, одна тропа, один залив, один пляж, одна река). Маршрут и операторы могут различаться. |
| **2b. Общий тип транспорта** | Оба POI — катерные выходы из одного порта; автобусные туры по одной дороге; выезды одного шаттла; хайки от одного trailhead. Полное совпадение маршрута не требуется. |
| **3. Явное упоминание совместности автором** | Дополнительное подтверждение, не самостоятельное условие. Усиливает кандидата, найденного по 1/2a/2b. |

Плюс новый блок «**Один объект, разные грани**» как паттерн особого
внимания: мостки + прогулка на одном леднике, катерный осмотр +
высадка на острове в одном заливе, хайк к точке + боковая лагуна с
той же тропы.

### Изменения в файлах (v0.18)

- `stage4-variants.md` §6.1 fallback-блок: синхронизирован под новые

## Текущие ограничения и known failure modes

### 1. POI consolidation на Opus

Opus раздаёт POI тоньше: «Cerro Fitz Roy view» отделяет от трека
«Лагуна-де-лос-Трес», в результате счётчики `high_recommend` дробятся
по двум POI и **STRONG CONFIRMED становится недостижимым**. Это
методологически валидно (физически разные точки наблюдения), но
ломает downstream Stage 4, который использует STRONG как опорные точки
маршрута.

**Митигация:** Sonnet+thinking как дефолт (он консолидирует
правильно). Opus оставлен fallback'ом — приемлемо для разовых
прогонов, не для основной работы.

### 2. Синергия по признаку 3 без 1/2a/2b — не самостоятельная

Признак 3 («явное упоминание совместности автором») в v0.18
переквалифицирован как **дополнительное подтверждение**. Это значит:
если модель находит **только** упоминание автором без operator / общей
локации — это **не** synergy кандидат. Пользователь принял этот
trade-off: лучше пропустить редкий случай «автор делал в один тур, но
объективно это разные туры», чем выдумывать синергию.

### 3. Symметризация пар руками

Спека требует от LLM проставить `commonly_combined_with` симметрично:
если POI #X помечен с #Y, то и #Y с #X. Скрипт автоматически не
достраивает (это семантика — скрипт не знает, какой `why`-текст
писать с другой стороны). Если LLM забыл симметрию — Stage 4 при
fallback-проверке всё равно найдёт пару, но при отсутствии данных
может ошибиться в формулировке.

**Митигация:** Pre-emit Класс B в Stage 4 проверяет любую сторону пары.
