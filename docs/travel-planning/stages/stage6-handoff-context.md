## 1. Назначение и атомарная задача

**Одна задача:** довести **устаканенный** маршрут (5_vX) до trip-ready идеала,
добавив то, что **не влияет на выбор маршрута**, но нужно в финале. Stage 6 не
переисследует POI, не строит варианты, не меняет логику дней — он **финиширует**.

Граница (правило): *нужно, чтобы ВЫБРАТЬ маршрут или ЗАБРОНИРОВАТЬ → Stage 5;
пост-решение финиш раз → Stage 6.* Stage 5 = прочный каркас (с ним уже можно
ехать). Stage 6 = идеал.

**Stage 6 ≠ Export.** Export (режим E) только конвертирует формат + адаптирует
тон, новых фактов не создаёт. Stage 6 — полноценная контент-стадия пайплайна
(генерит новые факты: координаты, визы, прививки, этикет), её выход `6_*.md`
рендерит Export, как выход любой стадии.

**Состав (компоненты одной задачи «финиш»):**
- **Ядро (детерминированно/всегда):**
  - **Координаты маршрута** — резолвятся двухтиерно и **персистятся в `6_*.md`**
    (см. §6). Карту рисует Export-рендерер из этих координат, не контент-стадия.
  - **Дорожное досье** — визы/транзит, медицина/прививки/денге/высота, страховка,
    этикет (съёмка/хоумстей), сводная упаковка, экстренные номера/больницы, связь.
  - **Инкорпорация косметической брони** — реальные билеты/номера/подтверждённые
    отели (статус, ref). *Структурная* бронь (отель далеко, переезд ломает план)
    идёт НАЗАД в Stage 5 (новый 5_vX), не сюда — см. §5.
- **Enrichment (ТОЛЬКО по явному запросу):** история региона/города, конкретные
  точки/рестораны/онсэны/кофейни. Не делается само — иначе Stage 6 безграничен.

## 2. Inputs / Outputs

**Inputs:**
- `5_final_plan_v{max}.md` — **устаканенный** план (latest версия). REQUIRED.
- `profiles/{profile_id}.md` — для досье (медицина/диета/платёжная инфра).
  REQUIRED (резолвится из YAML 5_vX, поле `travelers_profile`).
- `0_scope.md` — OPTIONAL quality input (направление, сезон, country quota →
  визы/сезон в досье). Если есть в travel_root, но не приложен → STOP/спросить
  (правило optional-quality-inputs из SKILL.md).
- **Факты брони** — OPTIONAL, от пользователя (билеты/отели/переезды + ref).
- **Запросы enrichment** — OPTIONAL, явные.

**Output (artefact в чат, manual save):** `6_final_v{N}.md` (versioned). YAML:
`trip_id`, `stage: 6_final`, `travelers_profile`, `created`,
`source_plan: 5_final_plan_v{max}.md` (на чём построен), `coords_source_summary`
(сколько gazetteer / model), опц. `booking_incorporated: true`,
`enrichment_requested: [...]`. **PDF — отдельно, через Export** (§7).

**Backward-compat (жёстко):** старый/менее подробный 5_vX на входе НЕ должен
вызывать ошибку. Новые поля/маркеры опциональны на входе; отсутствие ≠ ошибка.

## 3. Mode-detection (детерминированно)
- Нет предыдущего `6_*.md` → **fresh** (строим досье/координаты/enrichment с нуля).
- Есть предыдущий `6_*.md` → **update** (мёрж новых фактов брони / новых
  enrichment-запросов; ранее собранное досье/координаты переиспользуются).
Объявляется одной строкой в начале Turn 2 (как Stage 5 mode).

## 4. Модель
**Sonnet 4.6 + adaptive thinking** (retrieval/компиляция/web-search +
синтез досье; не интеграция, как Opus-Stage-5). Model self-check первой строкой
(паттерн Stage 2/3/4/5): Haiku → стоп; Sonnet без thinking → предложить thinking;
Opus → допустимо (overkill, не требуется). Та же ловушка safety-filter→Haiku.

## 5. Бронь — в ОБЕ стадии (важно)
Бронь = новый входной факт-ограничение.
- **Структурная** (отель на окраине ломает логистику дня; переезд фиксирует
  плечо/время несовместимо с планом) → подаётся в **Stage 5** → новый 5_vX
  перепланирует. Stage 6 потом увидит уже устаканенный план.
- **Косметическая** (номер брони, подтверждение, цена — маршрут не меняется) →
  **Stage 6**, секция «Бронирования» + статус-оверлей.
Решает пользователь по структурности. Stage 6 НЕ перепланирует — если бронь
структурная, направляет назад в Stage 5 (gate/подсказка).

## 6. Координаты — двухтиерный резолв + персист

**Tier 1 (детерминированный, скрипт).** Новый `scripts/geocode.py` (stdlib-only):
вход — список имён точек (регионы/базы/ключевые POI из 5_vX); читает забандленный
газетир `scripts/data/gazetteer.json` (D4: геокодер — контент-стадия, не экспорт;
переносится из `scripts/export/data/` где собран; 7342 города); матчинг
Russian↔English через транслит + alias + fuzzy в пределах bbox страны; выход —
JSON `{name → {lat, lon, source: "gazetteer"}}` для найденных + список ненайденных.
Хит-рейт: крупные города высоко (Ханой/Сеул/Пусан/Буэнос-Айрес ✓ проверено),
деревни низко (Sa Pa/Mu Cang Chai/El Chaltén ✗ → Tier 2).

**Tier 2 (модель, для ненайденных).** Stage 6-модель доопределяет координаты
ненайденных точек (знание городов; пометка «ориентир, не навигация»),
`source: "model"`.

**Персист в `6_*.md`** — секция `## Координаты маршрута`: ревьюабельная таблица
`точка | lat | lon | source(gazetteer/model)` + порядок маршрута + подписи рёбер
(вид транспорта/время/тип: обычное/узкое-звено/перелёт — извлекаются из 5_vX:
дневные `📍`-переезды + сводная таблица транспорта). Это **полная спека карты**,
persisted один раз → Export-рендерер её читает, не пересобирая из дней.

## 7. Export-рендерер Stage 6 (отдельно, PDF)

`scripts/export/stages/stage6.py` + `references/stage6/stage6-polish-prompt.md`
(паттерн как stage5.py). Регистрируется в `renderer`/`export.py`
(`DEFAULT_FORMAT["6"]="pdf"`, ветка `args.stage=="6"`, `file_naming`
`6_{trip_id}_досье_v{N}[_получатель].pdf` — описание ОТКРЫТО).

**Сборка финального PDF (D1 = A, УТВЕРЖДЕНО).** Принцип: весь LLM/контент — на
Stage 6; на экспорте только лёгкая полировка + МЕХАНИЧЕСКИЙ рендер.

**ИНВАРИАНТ (анти-дрейф).** Stage 6 **НЕ редактирует `5_final_plan.md`** — файл
immutable, остаётся SSOT маршрута. Stage 6 только ЧИТАЕТ его и пишет ОТДЕЛЬНЫЙ
`6_final.md` с добавками. Слияние (5_vX + карта + добавки 6) — **механическое на
рендере**, не правка плана. Маршрут/дни ни разу повторно не прогоняются через LLM
→ дрейф плана и накопление ошибок через шаги исключены; ошибки LLM Stage 6 заперты
в добавках (худший случай — неверная карта, не испорченный план; таблица
координат ревьюабельна по `source`). Бронь аддитивна (косметическая — секция в
`6_final.md`; структурная — ре-план в Stage 5, не правка Stage 6).
- `6_final.md` хранит ТОЛЬКО добавки Stage 6 (координаты/route-spec + досье +
  бронь-дельты + enrichment) — НЕ переносит день-за-днём контент Stage 5.
- Финальный ideal-PDF собирает stage6-рендерер **механически** = рендер 5_vX
  (переиспускает `stage5.py`-билдеры; контент Stage 5 НЕ прогоняется повторно
  через LLM → ноль дрейфа) + **карта после обложки** (универсальный
  `render_route_map` из прототипа, кормится координатами из `6_final.md`) +
  досье/бронь/enrichment секциями/приложениями.
- Косметическая бронь = аддитивная секция + лёгкий статус-оверлей (не глубокое
  переписывание строк отелей Stage 5). Структурная — назад в Stage 5 (§5).
- **Почему A, не standalone-B:** B заставил бы Stage 6-LLM переносить весь Stage 5
  verbatim (больше LLM + риск дрейфа на Sonnet). A держит LLM Stage 6 только на
  НОВОМ контенте, Stage 5 собирается механически — это и есть «LLM в Stage 6,
  механика на экспорте».

**Карта.** Движок — `render_route_map` (auto bbox/fill/aspect, point-in-polygon
заливка) из `docs/travel-planning/export/map-prototype/overview_map_prototype.py`,
переносится в `scripts/export/stages/stage6.py`. База контура —
`scripts/export/data/ne_countries.geojson` (забандлен). matplotlib → PNG →
`Image` в reportlab (**доимпорт `Image` в `pdf_lib`** — сейчас не импортирован).
Координаты — из `## Координаты маршрута` блока `6_*.md` (НЕ из газетира на
рендере — резолв уже сделан на контент-стадии).

### 7.1 Состав и порядок финального PDF (что именно рендерить)
Ассемблер строит один документ в порядке:
1. Обложка 5_vX (`stage5.py`) + тезис маршрута, если есть.
2. TOC «Содержание» (Этап-1; добавить строку карты).
3. **Обзорная карта маршрута** (Уровень 1 по `travel-plan-maps-spec.md` §1.3):
   контур страны + нумерованные пины по порядку + маршрутная линия + подписи
   рёбер (транспорт/время; «узкое звено» красным; перелёт пунктиром). Без
   тайлов/QR. Координаты — из `## Координаты маршрута` блока `6_final.md`.
4. «Чего нет» → дни → сводные → план рисков → чеклист — **механический рендер
   5_vX как есть** (через `stage5.py`).
5. **Дорожное досье** (новая H2-приложение из `6_final.md`): под-секции
   Визы/транзит · Медицина и прививки · Страховка · Этикет · Упаковка ·
   Экстренные контакты/больницы · Связь и деньги. Рендер по `pdf-visual-language`:
   `info_box` для ключевых предупреждений, `data_table` для контактов/упаковки,
   `bullet_list` для перечней (добавить «§Применение к Stage 6»).
6. **Бронирования** (если есть факты брони): аддитивная секция — подтверждённые
   билеты/отели/переезды + ref; статус-оверлей «забронировано» (не переписывая 5_vX).
7. **Углубления** (enrichment, если запрошены): под-разделы по запросам.
8. Приложение «Обоснование» + Diff (Этап-1) — в самый конец.

**Scope карт v1 (D6):** только **обзорная** (Уровень 1). Региональные инсеты
(Уровень 2, `maps-spec` §1.3 / §2.3–2.4) — ОТЛОЖЕНЫ: нужны POI/деревенские
координаты (газетир не даёт → только Tier-2 модель, риск точности на зуме);
делать отдельной итерацией Stage 6 v2. Опц. контекст-слой обзорной карты
(река/хребет, вручную) — `maps-spec` §2.2; в v1 не обязателен.

## 10. Решения (УТВЕРЖДЕНО 2026-06-05)
- **D1 = A.** Сборка финального PDF — additions-only + механический ассемблер
  (§7). Весь LLM/контент на Stage 6; на экспорте лёгкая полировка + механический
  рендер. Stage 5-контент собирается механически (ноль дрейфа).

  описание `финал` → `6_{trip_id}_финал_v{N}[_получатель].pdf`.
- **D3 = versioned `_v{N}`** (как 4/5; перегон после новой брони/enrichment).
- **D4:** геокодер — контент Stage 6 → газетир в **`scripts/data/gazetteer.json`**
  (перенести из `scripts/export/data/`). Контур страны — только рендер → остаётся
  в **`scripts/export/data/ne_countries.geojson`**.
- **D5 = да:** enrichment — отдельная секция `## Углубления` с под-разделами по
  явным запросам; границы (не разрастаться, opt-in).
- **D6 = карты scope v1: только обзорная** (Уровень 1). Региональные инсеты
  (Уровень 2) отложены в Stage 6 v2 — нужны деревенские координаты (риск Tier-2).
  Полный состав/порядок финального PDF — §7.1.
