## 1. Точка вылета пользователя не должна додумываться

**Случай (Sonnet+thinking, Argentina).** Модель вписала в маршрут:

```
Day 1: Прилёт из Москвы (обычно поздно)
Day 14: ночной рейс BA→Москва
Warnings: Международные перелёты MOW↔EZE (~60,000–92,000 ₽ RT)
Бюджет: midpoint вариантов учитывает MOW-EZE перелёт
```

Москва **не упоминалась** ни в Stage 0 (`0_scope.md`), ни в профиле
(`profiles/алексей.md`). `0_scope.md` прямо говорит:
«Transit: Буэнос-Айрес фиксирован как точка въезда/выезда».

**Корневая причина.** RF-паспорт в профиле → модель применила
дефолт «вылет из Москвы». Стандартный failure mode «срезает угол к
правдоподобному дефолту вместо явного gap'а».

**Правило для Stage 4 (явное).** Если Stage 0 фиксирует транзитный хаб
({transit_hub}), Stage 4 обязан:

1. Трактовать {transit_hub} как фактический старт и конец маршрута.
2. День 1 = «Прилёт в {transit_hub}» (без указания, откуда).
3. День N (отъезд) = «Вылет из {transit_hub}» (без указания, куда).
4. Стоимость международного перелёта в дом — **не подмешивается** в
   midpoint бюджета вариантов и не приплюсовывается к `budget_target_rub`.
   Это отдельный параметр **за пределами scope Stage 4**.
5. Если стоимость международного перелёта релевантна как контекст —
   она появляется **только как TODO** с явной пометкой «уточни точку
   вылета и стоимость RT» в Warnings.

**Принцип шире:** «нет в Stage 0 / профиле → не додумывать». Любой
факт, не зафиксированный во входных артефактах, должен либо
отсутствовать, либо появиться как TODO. Default-факты на основе общего
знания (RF паспорт → Москва; mid-range → X тыс/ночь; и т.п.) запрещены.

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] Точка вылета из дома пользователя НЕ упоминается в плане, если
      Stage 0 её не зафиксировал.
- [ ] Стоимость международного перелёта НЕ участвует в midpoint
      бюджета вариантов; появляется только как TODO в Warnings.
- [ ] Прошёлся по тексту: ни в одной строке нет фактов, источник
      которых нельзя указать в Stage 0 / профиле / Stage 3.
```

## 2. Парные `$` ломают визуальные markdown-просмотрщики

**Случай (Sonnet+thinking, Argentina).** Текст файла `4_variants.md`
в визуальном просмотрщике (например, Obsidian preview) обрывается
сразу после строки:

```
⚠️ Бюджет: 170–248 тыс ₽ — midpoint 209 тыс, на +13% к лимиту 185,700 ₽.
```

Следующая строка (151) содержала **два знака `$` подряд**:

```
Isla Martillo (~$80–100/чел ≈ 7,500–9,200 ₽) +
круиз Спегаццини (~$100–150/чел ≈ 9,200–13,800 ₽)
```

**Корневая причина.** Markdown-рендеры с MathJax (Obsidian preview по
умолчанию; статические рендеры на Pandoc/Hugo с math extension; Quartz,
mdBook с math; часть просмотрщиков GitHub-flavored Markdown с включённым
math-extension) трактуют парные `$` как inline LaTeX. Между долларами
оказывается **невалидный для LaTeX контент** (кириллица, ₽, `≈`,
скобки), рендер либо падает с ошибкой, либо незаметно «жрёт» всё до
следующего `$` / конца документа. Текстовые просмотрщики (vim, cat, Read)
этой проблемы не имеют — они `$` не парсят.

**Правило для Stage 4.** В markdown-артефактах не использовать чистый
`$` для долларовых цен. Безопасные альтернативы (любая):

```
\$80–100/чел           — escape (минимально инвазивный)
`$80–100/чел`          — code span
80–100 USD/чел         — без `$` вообще
USD 80–100/чел         — без `$`, ISO-форма
```

**Симметрично:** одиночные `$` в текстовом контексте безопасны
(парсер ищет пару), но если в одном файле появилось ≥2 `$`, любая
пара становится потенциальной math-mode зоной.

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] Все долларовые цены в файле — либо `\$NN`, либо `USD NN`,
      либо в backtick'ах. Чистый `$NN` запрещён.
```

**Уже сохранённые файлы:** заменять `$N` → `\$N` (минимальная
инвазивность, сохраняет числовое представление).

## 3. HIGH-сигнал по формату активности приоритетнее OUTLIER

**Случай (Sonnet+thinking, Argentina).** POI #16 «Национальный парк
Огненная Земля» в Stage 3:

```
HIGH (Maria Dol): рекомендует как ключевую природную точку Ушуаи
                  — без привязки к Cerro Guanaco
OUTLIER (Кукуха): хайк Cerro Guanaco 14 км / +1000 м

Характеристики:
- прибрежные и лесные тропы (HIGH-сигнал)
- Cerro Guanaco 360° (OUTLIER-сигнал)
- самое южное почтовое отделение
```

Stage 4 во всех **трёх** вариантах схлопнул парк в «Guanaco 14 км
+1000 м». HIGH-сигнал на прибрежные тропы + почту проигнорирован.
Пользователь самостоятельно догадался: «Я бы перенёс 1 день с Калафате
на Ушуаю, чтобы прогуляться по берегу в парке от самой южной почты».

**Корневая причина.** Модель взяла самый «броский» формат (длинный
хайк с цифрами) и применила его универсально. Иерархия HIGH > OUTLIER
не сработала.

**Правило для Stage 4.** Если POI имеет несколько форматов активности:

1. Прочитать характеристики Stage 3 и выделить **все** указанные
   форматы (мягкий vs нагруженный, разные подпункты внутри POI).
2. Если HIGH-сигнал поддерживает **более мягкий** формат, а OUTLIER
   — более жёсткий, **разнести форматы между вариантами**. Не выбирать
   один формат для всех вариантов.
3. По умолчанию — HIGH-формат, OUTLIER в качестве альтернативы.
4. При дефолтном выборе учитывать профиль («умеренный темп»,
   «несложный треккинг») как weight.

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] Для POI с несколькими форматами активности (мягкий/жёсткий,
      хайк/прогулка, etc.) форматы разнесены между вариантами,
      не схлопнуты в один.
- [ ] HIGH-формат присутствует хотя бы в одном варианте, даже
      если OUTLIER-формат «эффектнее».
```

## 4. Внутрирегиональный баланс активностей

**Случай (Sonnet+thinking, Argentina).** Эль-Калафате — 4 ночи в
скоупе. Stage 4 заполнил их 3 ледниковыми/лагунными активностями
(Перито-Морено + мини-трек на льду + круиз Спегаццини или буфер) во
всех вариантах. Glaciarium (музей льда, есть в Stage 0), Lago Argentino
закат (фото), Lago Roca grass-степь (не-ледник) — не предложены ни в
одном варианте.

Симметрично Ушуая — 3 ночи в скоупе с тремя POI типа «активность»
(Бигль + парк + Мартиаль), но HIGH-формат парка (прибрежная прогулка
+ южная почта) отсутствует.

**Правило для Stage 4.** Если в одном регионе ≥3 POI одного типа
(все ледники, все храмы, все хайки), Stage 4 обязан:

1. Разнести их **между вариантами** (один — все три, другой — два,
   третий — один с заменой на другой тип активности).
2. Активно искать в Stage 3 + Stage 0 альтернативные форматы для
   разнообразия.
3. Отметить это явно в оси «культурное наполнение» сравнительной
   таблицы.

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] В каждом регионе с ≥3 ночами проверено: есть ли разнообразие
      типов активности (хайк / прогулка / еда / культура / фото)
      или регион загружен однотонно. При однотонности — разнести
      между вариантами.
```

## 5. Цены без проверки на агрегаторе — TODO, не факт

**Случай (Sonnet+thinking, Argentina).** Подача:

```
Isla Martillo (~$80–100/чел ≈ 7,500–9,200 ₽)
круиз Спегаццини (~$100–150/чел ≈ 9,200–13,800 ₽)
Вариант A: ~155–230 тыс ₽ (midpoint ~192 тыс → on_target)
Вариант B: ~170–248 тыс ₽ (midpoint ~209 тыс → over_10_20)
Вариант C: ~155–232 тыс ₽ (midpoint ~193 тыс → on_target)
```

Ни одной TODO-метки. Бюджетный вердикт «B = over_10_20 (+13%)»
рассчитан на этих цифрах.

`CLAUDE.md` явно:

> «ИИ имеет систематический bias занижения цен отелей в 3–10×.
> Любая цифра, не проверенная на агрегаторе, помечается как TODO.
> Не маскировать TODO под уверенные данные.»

Stage 4 здесь маскирует.

**Правило для Stage 4.** Каждая денежная цифра — диапазон + явная
пометка статуса:

- `≈ TODO/проверить на Booking/Trip.com на Stage 5` — для размещения;
- `≈ TODO/проверить на сайте оператора` — для экскурсий, билетов,
  трансферов;
- `midpoint вариантов — предварительная оценка для сравнения, не
  окончательный бюджет` — для итогового бюджета вариантов.

**Бюджетные ярлыки `under_target` / `on_target` / `over_10_20` /
`over_20+` — допустимы**, но в Warnings обязательна строка: «Все
ярлыки построены на предварительных оценках; Stage 5 пересчитывает».

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] Все денежные цифры в файле — диапазон + источник или TODO.
- [ ] В Warnings есть строка: «бюджетные ярлыки — предварительные,
      Stage 5 пересчитывает».
```

## 6. Физическая нагрузка против профиля «умеренный темп»

**Случай (Sonnet+thinking, Argentina).** Вариант A суммарно за 13 дней:

```
Cerro Guanaco (14 км +1000 м, Ушуая)
Лагуна-де-лос-Трес (22 км +800 м, Чальтен)
Лагуна-Торре (~20 км, Чальтен)
Pliegue Tumbado (~22 км +1200 м, Чальтен)
Ледник Мартиаль (6 км, Ушуая)
мини-трек на льду (полдня)
```

= 4 серьёзных хайка + ледник. Профиль явно: «несложный треккинг,
умеренный темп, 2–4 ночи на локацию». Стандартный соло-фотограф 37 лет
без подготовки на такой суммарной нагрузке к концу поездки не доходит.

Stage 4 ось «физическая нагрузка» в сравнительной таблице отметила
для A как «3 хайка Чальтен + Guanaco + Мартиаль», но **не связала**
это с профильной нормой и не подняла warning.

**Правило для Stage 4.** Ось «физическая нагрузка» в сравнительной
таблице должна:

1. Перечислить суммарные показатели варианта (число серьёзных хайков,
   суммарный км, суммарный набор высоты).
2. Сравнить с профильной нормой («умеренный темп», «несложный
   треккинг» = ~1 серьёзный хайк / 2–3 дня).
3. При превышении — обязательная строка warning внутри варианта
   («физнагрузка выше профильной нормы — учти возможность урезать»).

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] Для каждого варианта подсчитано: число серьёзных хайков
      (>10 км или +>500 м), суммарный набор высоты.
- [ ] Сравнено с профильной нормой; при превышении — warning в
      варианте.
```

## 7. Структурное различие вариантов

**Случай (Sonnet+thinking, Argentina).** Все три варианта имели
**идентичную геометрию**: 2н BA + 3н Ушуая + 4н Калафате + 4н Чальтен.
Различия — только во **внутренних активностях**:

- A: Pliegue Tumbado + Guanaco + 3 хайка Чальтен
- B: Isla Martillo + круиз Спегаццини + 2 хайка Чальтен
- C: Lago del Desierto + буферы

Это **граничит** с §10-запретом «варианты косметически разные = провал».

**Сравнение с Vietnam (Opus).** Три варианта структурно различны:
- A: 4 региона (Ханой/Sa Pa/центр/юг), 6 ночей центр
- B: 5 регионов (+Phong Nha), 5 ночей центр
- C: 5 регионов (+Май Чау), 4 ночи центр

Регионный состав и распределение ночей меняются — это **структурное**
различие, не косметическое.

**Правило для Stage 4.** Структурным считается различие, затрагивающее
**хотя бы один** параметр:

1. Состав регионов (один из вариантов добавляет / убирает регион).
2. Распределение ночей по регионам (≥2 ночи переходят между регионами).
3. Тип активностей региона (один регион в одном варианте — culture,
   в другом — landscape).

Различия типа «POI A vs POI B в одном регионе» **сами по себе**
структурными **не являются**. Если ни одно из 1–3 не выполнено для
всех пар вариантов — перестроить.

**Что добавить в Pre-emit checklist `stage4-variants.md`:**

```
- [ ] Между каждой парой вариантов выполнено хотя бы одно из:
      разный состав регионов, разное распределение ночей (≥2
      ночи переходят), разный тип активностей региона. Иначе
      варианты косметические — перестроить.
```

## 8. Точка отправления пользователя — `home_city`

**Случай (Opus 4.7, Argentina, второй прогон).** Даже после устранения
Москва-галлюцинации в Класс A (#1), скилл по-прежнему по умолчанию
формулировал крайние дни как:

```
День 1: Прилёт в Буэнос-Айрес. Трансфер из аэропорта, акклиматизация.
День 13: вылет домой из BA.
```

Эти формулировки **embedded assume**, что пользователь прилетает в
`transit_hub` из другого места. Stage 0 при этом унаследовал то же
предположение — выделял 2 транзитные ночи «1 на въезд после длинного
перелёта, 1 перед вылетом». Для пользователя, живущего в `transit_hub`
(или вообще не использующего международный перелёт в рамках поездки),
обе формулировки и 2 транзитные ночи — ложные.

**Корневая причина.** Skill methodology не моделировала случай
«пользователь живёт в transit_hub». Дефолт = «приезжает из дома в
направление». Не было поля home_city ни в профиле, ни в Stage 0.

**Правило (v0.15, после упрощения модели).**

Упрощённая модель: храним только `home_city` в профиле, концепт
«транзитный хаб» убран. Per-trip стартовый город — параметр Stage 0,
не профильное поле.

- Профиль получает опциональное поле `## Базовый город` — только
  домашний город пользователя (`references/profile-management.md` §7.2).
- Stage 0 в Gate'е §4 резолвит:
  - `home_city` по приоритету: профиль → если пусто, ОДНА строка-вопрос
    в batch'е уточнений.
  - `trip_start_city` по приоритету: явное указание в запросе
    пользователя («BA транзит», «начало в Стамбуле») → дефолт =
    `home_city`.
- Stage 0 YAML фиксирует `home_city`, `trip_start_city`, `home_eq_start`
  (вычисляемое `home_city == trip_start_city`).
- Stage 4 Pre-emit checklist Класс A проверяет формулировки крайних
  дней: при `home_eq_start == true` — «Старт маршрута в {trip_start_city}»
  / «Завершение маршрута в {trip_start_city}» (без «Прилёт», «Трансфер
  из аэропорта», «Вылет домой»); при `home_eq_start == false` —
  «Прилёт» / «Вылет» допустимы.

Транзитные пересадки с ночёвками между домом и стартовым городом
(если они есть — например, Москва → Стамбул overnight → Буэнос-Айрес)
описываются пользователем **в запросе** к Stage 0 и оседают как часть
`pre_committed_places` или первой/последней ночи; отдельной модельной
структуры под них нет.

## 9. POI synergy — типичные комбо местных операторов

**Случай (Opus 4.7, Argentina, второй прогон).** Вариант B День 5:

```
Утро — пролив Бигль (#17, малый катер);
день — выезд на остров Мартильо к пингвинам (#19)
```

Оба POI с положительным комментарием пользователя, оба в Ушуае, оба
— катерный выход. Stage 4 поставил их на один день, но как **две
независимые активности** с двумя операторами и двумя билетами.
Локальная реальность: в Ушуае это стандартное **комбо-предложение**
одного оператора (Pira Tour и аналоги) — пролив Бигль + высадка на
Мартильо в рамках одного отплыва, один билет.

**Корневая причина.** Скилл моделирует POI как **атомарные**: каждый
со своим reading list, тональностями, рисками. Логика «два POI типично
комбинируются местным оператором в единую экскурсию» нигде в пайплайне
не появляется — ни в Stage 3 characteristics, ни в Stage 4 priority pool.

**История подхода.**

- **v0.14: вариант B — Stage 4 only.** Pre-emit checklist + текстовые
  правила синергии в §6.1 Stage 4. Стартовая гипотеза: достаточно
  чеклиста.
- **Эмпирика на повторном Argentina прогоне (Opus 4.7).** Stage 4 на
  pure-LLM шаге не вытянул синергию даже с явным примером Бигль+Мартильо
  в §6.1. Пользователь нашёл две пропущенные пары руками: Бигль +
  Мартильо и Перито-Морено + мини-трек по леднику. §6.1 prose-описание
  → недостаточный structural force для надёжного попарного чека.
- **v0.17: гибрид A+B.** Перенос обнаружения в Stage 3 (data-anchor),
  применение в Stage 4 (логика).

**Правило (v0.17).**

Слоёная архитектура:

| Слой | Стадия | Что делает |
|---|---|---|
| Обнаружение | Stage 3 | LLM при экстракции POI помечает кандидатов синергии в поле `commonly_combined_with: [{poi_name, why}]` (`stage3-poi.md` §6.9). Признаки: общий оператор в characteristics / общая стартовая локация ИЛИ общий природный объект / общий тип транспорта от одной точки (v0.18 — расщеплены из единого AND). Доп. подтверждение — явное упоминание совместности автором. Паттерн особого внимания: «один объект, разные грани». |
| Passthrough | `aggregate_pois.py` | Скрипт пробрасывает поле без изменений + считает `aggregates.synergy_pairs`. |
| Применение | Stage 4 | §6.1 priority pool читает помеченные пары как **единые юниты** (не два независимых POI). День формулируется «**{X} + {Y} единой экскурсией — {why}**». Negative user_comment на одном POI пары расцепляет её с обоснованием. |
| Контроль | Stage 4 Pre-emit Класс B | Каждая пара из `commonly_combined_with` отработана: в одном дне или явно расцеплена в «осознанно отбрасывает». |
| Fallback | Stage 4 §6.1 fallback-блок | Legacy Stage 3 без поля — попарная проверка по characteristics общими признаками. |

**Принципы, не справочник.** Спецификация скилла **не содержит
реестр конкретных комбо-туров**. Конкретные пары приходят из
`commonly_combined_with` поля Stage 3, наполненного LLM из characteristics
и упоминаний reading list. Скилл не нужно править при обнаружении новых
комбинируемых пар в новой поездке.

## 10. Покрытие свободно-формулированных пожеланий пользователя

**Случай (методологический разбор).** Запрос пользователя
«я хочу поехать на юг Страна В, посмотреть **озеро Эсмеральда**,
**пингвинов** и **кладбище в Реколете**, из БА» содержит:

- топонимы (`озеро Эсмеральда`, `Реколета`) — оседают в Stage 0
  YAML `pre_committed_places`;
- стартовый город (`БА`) — оседает в `trip_start_city`;
- категория активности (`пингвинов`) — **не топоним и не профильный
  интерес** → в исходной модели **нигде не сохранялась явно**.

Цепочка от пожелания «пингвинов» к POI в Stage 4:

```
запрос → Stage 0 LLM может упомянуть в Контекст-абзаце (не гарантировано)
       → Stage 1 DR ищет по регионам (Огненная Земля — выбрана) и
         случайно может вернуть отчёт с Isla Martillo
       → Stage 2/3 включают POI #19 в reading list
       → Пользователь добавляет user_comment на #19
       → Stage 4 видит MUST через user_comment
```

В любой звене может сорваться: Stage 0 не упомянет, DR не вернёт,
пользователь забудет прокомментировать. Тогда пожелание молча
потеряется.

**Правило (v0.16).**

- Stage 0 извлекает `trip_wishes: [...]` — список 0–8 вербатим-фраз
  пожеланий из запроса (категории активности или конкретные
  впечатления, не топонимы, не профильные интересы). Сохраняет в YAML.
- Stage 1 DR-промт получает `{trip_wishes}` и добавляет блок «Особые
  пожелания пользователя»: 2–3 отчётов с positive mention достаточно,
  **гибкость, не якорь**, физически невозможные пожелания (`пингвины
  в северном полушарии летом`) не выдумывать — отметить невозможность
  в META-DIAGNOSTICS.
- Stage 4 §6.1 — `trip_wishes` как backstop-сигнал: POI, совпадающий
  с пожеланием по `name_ru`/`name_local`/`characteristics`, получает
  MUST-вес даже без user_comment'а. Перекрывается негативным
  user_comment'ом, если пользователь явно отказался.
- Stage 4 §6.9 Класс B — пункт чеклиста: каждое пожелание из
  `trip_wishes` покрыто POI хотя бы в одном варианте; непокрытые
  пожелания — TODO в Warnings (либо невозможно, либо нужна довыборка
  через Stage 1 Mode B).
