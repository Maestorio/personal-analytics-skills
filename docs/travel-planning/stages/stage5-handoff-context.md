## Что в Stage 5 сейчас

### Назначение

Превратить выбранный на Stage 4 структурный вариант (с заполненным
блоком `## Решение`) в полный детализированный план уровня дня:
конкретный транспорт, имена отелей, программа с часами/ценами входов,
бюджет, план реагирования на риски, чеклист «за 2 недели» с источниками.

### Входные файлы

- `4_variants.md` (Stage 4) с непустым блоком `## Решение`
  (`**Выбран вариант:**` обязателен).
- Профиль `profiles/{profile_id}.md`.
- **Обязательно (v0.21):** `0_scope.md` если файл существует.
- Опц.: `previous_plan` для surgical-режима.
- Опц.: `3_poi_aggregation.md` для контекста synergy-пар.

### Выход

`{trip_id}/5_final_plan.md`:

- YAML-шапка с 16+ полями (mode, chosen_variant_raw,
  budget_status, mcp_extensions_used, clarification_used, …).
- 9 обязательных секций по §9 методологии:
  1. Контекст и ключевые параметры
  2. Шапка (билеты, визы, валютные курсы)
  3. Критические подготовительные пункты
  4. Маршрут по дням (компактные блоки с иконками 📍🏨🎯💰⚠️)
  5. Сводные таблицы (транспорт / бюджет / гастрономия)
  6. План реагирования на риски (числовые вероятности!)
  7. Чеклист за 2 недели (со ссылками на источники)
  8. Diff с предыдущим планом (только если previous_plan ≠ null)
  9. TODO для верификации (3 категории: before-booking,
     2-weeks-before, in-trip)

### Граница LLM vs скрипт

**Pure LLM, без скрипта** (как Stage 4). Детализация дня —
семантическая работа, любой скрипт-валидатор был бы дублированием
Pre-emit checklist'а. Кандидаты отвергнуты:

- `consolidate_plan.py` (бюджетная арифметика + mode detection) —
  закрыто §6.1 detection и Pre-emit Class B.
- `validate_final.py` (sanity-check после генерации) — закрыто
  Pre-emit checklist'ом 6 классов.

### Модель — два режима с автодетектом

| Режим | Модель | Когда |
|---|---|---|
| **surgical** | Sonnet 4.6 + adaptive thinking (Opus — fallback) | previous_plan ≠ null + структура совпадает (тот же набор регионов + ±0 ночей) |
| **reconstructive** | Opus 4.7 + adaptive thinking (Sonnet — fallback) | previous_plan = null ИЛИ структура отличается |

Mode детектируется детерминированно (§6.1), не вводится пользователем.
При reconstructive на Sonnet+thinking — скилл предлагает переключение
на Opus одной строкой.

### Custom variant interpretation

Stage 4 блок `## Решение` парсится семантически:

- `**Выбран вариант:**` → `chosen_variant_raw` (raw) +
  `chosen_variant` (нормализованный).
- `**Состав:**` / `**Почему этот выбор:**` → опц. правки.

4 типа правок: замена формата активности / добавление активности /
удаление / уточнение (отель, транспорт).

**Правки встраиваются в маршрут естественно, без маркеров в днях.**
ОДНА summary-строка в `## Контекст и ключевые параметры` фиксирует
факт правок. Текст правок НЕ хранится в YAML отдельным полем
(достаточно `chosen_variant_raw`).

### Web search policy — гибрид

**Активно (~10–20 поисков):**
- Расписания транспорта.
- Часы работы и стоимость входа достопримечательностей.
- Конкретные операторы synergy-пар Stage 3.
- Имена / районы / **рейтинги** отелей (по Booking/Tripadvisor).
  Порядок (v0.21): сначала основной кандидат, потом альтернативы.
- Сезонные ограничения.

**Всегда TODO (без web search):**
- Цены отелей (даже найденные — диапазон с TODO; LLM системно
  занижает на 3–10×, цены волатильны).
- Цены ресторанов / такси.
- Курсы валют (выносится в чеклист).

### Опц. MCP-расширения (Booking / Expedia)

По умолчанию НЕ используется (переносимость скилла). Активируется при
явном запросе пользователя или при активных MCP-коннекторах в среде.
MCP-цены подставляются с пометкой «через {Booking|Expedia} MCP,
YYYY-MM-DD» и **не заменяют TODO**.

### Mid-range pricing heuristic (v0.21)

При оценочном диапазоне отеля **без** web search/MCP — midpoint в
**нижней половине** типичного mid-range диапазона региона. Уровень
mid-range берётся из `## Стиль путешествий` профиля:

- `бюджетный` → нижняя треть;
- `mid-range` → нижняя половина;
- `премиум` → середина-верх.

Систематическое завышение (midpoint в верхней половине без
подтверждающего сигнала) — нарушение Pre-emit Class B.

### Pre-emit checklist — 6 классов

| Класс | Что закрывает |
|---|---|
| **A** | Stage 4 consistency + Stage 0 чтение (v0.21): все дни на месте, правки применены, home_eq_start правильно, mode объявлен, 0_scope.md прочитан если есть |
| **B** | TODO discipline + budget heuristic: цены отелей всегда TODO, дневной≈сводный бюджет (±15%), mid-range heuristic (v0.21) |
| **C** | Данные и факты: часы со ссылкой/TODO, операторы synergy-пар, рейтинг для каждого отеля (особенно основного — v0.21), time-of-day sanity (v0.20), TODO операторов с платформой (v0.20) |
| **D** | Логистика и риски: каждый переезд (транспорт+время+бронирование+цена), узкие звенья сохраняют swap, synergy-пары как «комбо», числовые вероятности рисков (v0.20) |
| **E** | Формат и YAML: `\$NN` escape, YAML ровно `---`, имя файла, нет «for brevity», `🏨` опускается при повторе отеля |
| **F** | Diff, TODO summary, чеклист: Diff если previous_plan ≠ null, секция TODO содержит все TODO, чеклист со ссылками на источники (v0.20) |

### §9.4 Opt-in clarification

Если правка пользователя структурно противоречит варианту — ОДИН batch
с 3 вариантами (перераспределить ночи / реализовать урезанно /
отказаться). Stop, дождаться Turn 3. В YAML
`clarification_used: true`. Аналог §9.12 Stage 2.

## Текущие ограничения и known failure modes

### 1. Surgical-режим не валидирован

Оба калибровочных кейса (Argentina, Vietnam) — **reconstructive** (нет
`previous_plan`). Surgical-логика реализована и описана (§6.1, §6.6),
но фактически не прогонялась. Станет тестируемым только при
**второй итерации** одной из поездок: например, перепрогон Vietnam
под v0.21 с использованием первого Vietnam plan как previous_plan.

### 2. C1+C10: рейтинги для основных кандидатов отелей

После v0.21 ожидается фикс, но это zero-shot эвристика для модели:
«сначала основной, потом альтернативы». Может всё равно проскочить
при срезании углов на больших планах (≥18 ночей). Регрессионный знак:
если в каком-либо городе основной кандидат с голым TODO рейтинга при
наличии рейтинга у альтернативы — Pre-emit Class C нарушен.

### 3. C9: эвристика «нижняя половина mid-range» — может над-корректировать

Если регион реально дорогой (Чальтен в пик сезона, Sa Pa в золотое
окно), нижняя половина типичного диапазона может **не покрыть** аренду.
Эвристика — не закон; модель может игнорировать при явном сигнале
региональной премии. Регрессионный знак: при перепрогоне Argentina
v0.21 жильё midpoint снизится с ~$152 до ~$96; но реалистично в
Чальтене может потребоваться ~$110–120 → 10–20% надкоррекции.
Терпимо.

### 4. Бюджетная категория under_target vs Stage 4 категория

Vietnam v0.20: `total_budget_rub: 198000` `under_target` (без
международного перелёта), но Stage 4 оценивал тот же вариант B как
`on_target` (235–255k включая перелёт). Расхождение **методологическое**:
Stage 5 выносит международный перелёт отдельно (если `home_eq_start ==
false`), Stage 4 включал его в общий midpoint. Модель Vietnam-прогона
**правильно объяснила** это в пояснении строкой 381 — это OK.

Регрессионный знак для будущих прогонов: если `budget_status`
расходится со Stage 4 — обязательная строка-пояснение «методологическое
расхождение, не противоречие».

### 5. Стиль профиля и mid-range уровень

C9 опирается на `## Стиль путешествий` профиля. Если стиль не
зафиксирован явно (`бюджетный`/`mid-range`/`премиум`) — fallback к
mid-range. У профилей пользователя сейчас явно `mid-range` (см.
`profiles/алексей.md`), но при появлении новых профилей без явного
стиля — это потенциальная неопределённость.

### 6. Чеклист «за 2 недели» — стандартный набор источников

Список ссылок (JTWC / Windy / cbr.ru / met-service страны) хорошо
работает для типичных случаев. Для нетипичных направлений (полярные
экспедиции, малоизученные страны) источники могут не подойти —
модель должна адаптировать самостоятельно. Регрессионный знак не
заложен.
