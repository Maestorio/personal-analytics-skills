## Stage 3 → Stage 4: что Stage 4 читает

Stage 3 артефакт — `{travel_root}/trips/{trip_id}/3_poi_aggregation.md`.

### YAML-шапка (ключевые поля для Stage 4)

```yaml
trip_id: ...
stage: 3_poi_aggregation
travelers_profile: profiles/{profile_id}.md
input_files: [1_dr_reports.md, 2_similarity.md]
created: YYYY-MM-DD
total_pois: N
strong_confirmed: N
weak_confirmed: N
hidden_gems: N
contested: N
red_flags: N
low_signal: N
iconic_exceptions: N            # v0.10: число POI с iconic_exception (см. ниже)
aggregation_mode: abundant      # v0.10: abundant | scarce — режим
chosen_similarity_run: 2_similarity.md
previous_plan: null             # путь к предыдущему плану, если есть
```

### Тело файла (по секциям)

1. **`## Контекст для следующих стадий`** — 5–8 строк: профиль, scope,
   режим категоризации (`abundant`/`scarce`) и почему, ключевые findings.
2. **`## Распределение по категориям`** — таблица 6 категорий.
3. **`## Warnings`** — info про режим, anti-bloat (STRONG > 50%, RED > 30%),
   узкая HIGH-когорта.
4. **`## Полная агрегация POI`** — **сгруппировано по регионам**
   (регионы в порядке убывания числа POI). Каждый POI:
   - `#{N} **{name_ru}** ({name_local}) — {КАТЕГОРИЯ}`
   - `1. Регион: {region}`
   - `2. HIGH упомянули: ...` (с разбивкой по тональности)
   - `3. OUTLIER / MEDIUM / LOW упомянули: ...`
   - `4. Выдержки: ...` (1–3 цитаты с указанием similarity-категории)
   - `5. Характеристики: ...` (сезон, время, логистика, толпы, риски)
   - `**Iconic exception:** {reason}` ← **только если LLM выставил флаг** (v0.10)
   - `6. Комментарий пользователя: {текст или пусто}` ← **юзер заполняет
     руками** = явный приоритетный сигнал для Stage 4
5. **`## Non-mainstream highlights`** — выжимка hidden gems + сильных
   OUTLIER-сигналов.
6. **`## Сравнение с предыдущим планом`** — если `previous_plan != null`.

Полная спецификация Stage 3 — в `skills/travel-planning/references/stages/stage3-poi.md`.

## Stage 4 — что от него ждёт methodology

Методология §8 (`travel-planning-methodology.md`):

> Построить 2–3 структурно различных варианта маршрута, явно показав
> тредофы каждого. Различие не косметическое (день А или день Б), а
> структурное (глубина против покрытия, городское против горного,
> стандартное против нетипичного).

### 7 полей на каждый вариант

1. Название + фраза-суть.
2. Маршрут по дням (без часов — это Stage 5).
3. Что включает из STRONG CONFIRMED и HIDDEN GEM.
4. Что осознанно отбрасывает и почему.
5. Логистическая структура между точками.
6. Ключевые риски (погода, оползни, отмены автобусов).
7. Кому подойдёт лучше / хуже.

### Дополнительные секции

- **Сравнительная таблица** по осям: культурное наполнение, физическая
  нагрузка, погодные риски, логистическая сложность, соответствие
  профилю, соответствие сезону.
- **Honest assessment** — какой вариант наиболее сбалансирован под
  профиль и почему. Без давления, аналитически.
- **`## Решение`** — заполняется человеком после обсуждения. Аналогично
  Stage 0.

### Методологический priority rule (§8 промт)

| Категория | Приоритет |
|---|---|
| STRONG CONFIRMED | высокий, включай по умолчанию |
| HIDDEN GEM | высокий к рассмотрению |
| WEAK CONFIRMED | средний |
| CONTESTED | низкий, только при явном сигнале в профиле |
| RED FLAG | НЕ включай по умолчанию |

### Модель из методологии

Sonnet 4.6 + adaptive thinking («тредофф-анализ требует явного перебора
альтернатив»). Эмпирически проверить — при Stage 3 пришлось пересмотреть
аналогичную методологическую прескрипцию (см. `architecture.md` §8).

## Ключевые решения, унаследованные из Stage 2/3 (v0.10)

Эти принципы должны быть учтены в Stage 4. Подробности — `architecture.md`.

### 1. User comment = явный приоритетный сигнал ⭐ ключевое для Stage 4

В Stage 3 у каждого POI есть пустое поле «**Комментарий пользователя**».
Пользователь заполняет руками то, что ему интересно (или не интересно).

**Stage 4 ДОЛЖЕН читать комментарии явно и приоритизировать POI с
непустым комментарием поверх методологического priority rule.**

Это лечит две проблемы:

- **Iconic exception** (см. ниже) — пользователь подтверждает интерес к
  «исключению из профиля» через комментарий.
- **Категория недооценивает место** (особенно в scarce-режиме, где
  WEAK = «1 HIGH-рекомендация») — пользователь может поднять LOW SIGNAL /
  WEAK место в приоритет руками.

**Это ключевое отступление от методологии §8** — она не предусматривала
поле комментариев (это решение v0.10). Stage 4 промт нужно
скорректировать: «прежде всего — POI с непустым комментарием
пользователя; затем — по методологическому правилу категорий».

### 2. Iconic exception flag — читать для контекста, действовать только по комментарию

В Stage 3 LLM может пометить POI флагом `iconic_exception` (топ-1
эталон категории, которую профиль исключает: пингвины Isla Martillo при
«не люблю зоонаблюдение», Angkor Wat при «не люблю архитектуру»). Флаг
**не меняет категорию** — он только сигнал пользователю для решения.

**Stage 4:**
- ЧИТАТЬ флаг для понимания, почему место в файле, несмотря на
  исключение профиля.
- **НЕ включать автоматически в варианты только по флагу.**
- Включать **только если пользователь подтвердил комментарием**.

Страховка от silent over-promote: модель не пропихивает профильное
исключение в маршрут без согласия пользователя.

### 3. Mode-aware категоризация (abundant / scarce)

`aggregation_mode` в YAML Stage 3 — режим, выбранный по доле HIGH:

- **abundant** (HIGH-доля ≥ 30%) — строгие правила, WEAK = 2 HIGH-рекомендации.
- **scarce** (HIGH-доля < 30%) — мягче, WEAK = 1 HIGH-рекомендация +
  подтверждение от OUTLIER/MEDIUM/LOW.

**Stage 4 должна понимать:** WEAK CONFIRMED в scarce — **слабее**, чем в
abundant. Не сравнивать категории напрямую через режимы. В `## Контекст`
Stage 4 явно зафиксировать режим, пришедший из Stage 3, и калибровать
ожидания.

При обоих калибровочных кейсах (Argentina, Vietnam) режим был **scarce** —
типичный кейс для минимальной DR-выборки.

### 4. Региональная группировка в input

Stage 3 уже отдаёт POI сгруппированными по регионам. Stage 4 строит
маршрут — география важна. Использовать порядок POI в файле / YAML
поле как естественную географическую группировку. Не ломать
региональную структуру без необходимости.

### 5. Граница LLM vs script

Базовый принцип `architecture.md` §2: детерминированное — в скрипт,
семантика — в LLM.

Для Stage 4:
- **Семантика (LLM):** генерация структурно-различных вариантов,
  тредофф-анализ, сборка сравнительной таблицы, honest assessment,
  прозы.
- **Детерминированное (?):** Открытый вопрос. Stage 4 выглядит как
  «чистая семантика», скрипт может не понадобиться. Кандидаты, если
  нужен:
  - Валидация YAML-шапки (формат `aggregation_mode`, `chosen_variant`).
  - Проверка покрытия: какие STRONG CONFIRMED / user_commented POI **не
    вошли** ни в один вариант (sanity check).
  - Парсинг сравнительной таблицы из markdown (вряд ли нужен).
  - Подсчёт длительности по дням (если variant имеет формат «день N:
    {locality}» — script может валидировать сумму ночей).
- Обсудить с пользователем при дизайне.

### 6. Environment-aware save

См. `skills/travel-planning/references/storage-and-naming.md` §9.
Имя файла строго `4_variants.md` — без пробелов, через подчёркивания.
В Cowork + Synology → `Write` + `present_files`; в Claude.ai чате →
markdown в чат.

### 7. Model self-check + safety filter awareness

Если модель — Sonnet (любая), первая операция стадии — назвать модель
пользователю (см. `SKILL.md` block «Stage 3: model self-check»). Та же
ловушка safety-filter → Haiku, что и в Stage 2/3 (нажатие «Continue»
после паузы тихо переключает на Haiku, сохраняя лейбл «Sonnet»).

### 8. Format-запреты

YAML строго `---` (три дефиса), не `-----`. Имя файла без пробелов
(`4 variants.md` — баг, замечен на Stage 3). Эти запреты обязательно
повторить в §10 reference Stage 4.

### 9. Opt-in fallback при ошибках

Скилл не падает. При любой проблеме (странный формат Stage 3 файла,
отсутствие категорий, нечитаемые комментарии и т.п.) — диагностика
пользователю + 2–3 варианта действий, не silent fix.

## Калибровочные кейсы (доступны для прогона Stage 4)

### Argentina (`страна_в_юг_2025-03`)

- **Stage 3 файл готов** (см. `examples/3 poi aggregation_а.md` для
  справки структуры, хотя в реальном прогоне у пользователя файл лежит
  в `{travel_root}/trips/страна_в_юг_2025-03/3_poi_aggregation.md`).
- **26 POI:** 2 STRONG CONFIRMED (Фицрой, Перито-Морено), 7 WEAK, 2
  HIDDEN GEM, **1 RED FLAG** (пингвины Isla Martillo — с
  `iconic_exception`, отличный тест чейна), 14 LOW SIGNAL.
- **Режим:** `scarce` (HIGH-доля 19%).
- **Регионы:** Tierra del Fuego (Ушуая) · Лос-Гласьярес юг (Калафате) ·
  Лос-Гласьярес север (Чальтен — 15 из 26 POI, сильный skew) ·
  Буэнос-Айрес транзит.
- **Профиль:** соло 37, mid-range independent, ландшафтная фотография,
  без прав.

**Хороший тест Stage 4:** маленькая выборка с явным региональным skew
(Чальтен доминирует — варианты должны структурно по-разному это
обрабатывать), 1 iconic_exception для проверки чейна
(комментарий пользователя → приоритет), 4 региона разной плотности,
2 STRONG CONFIRMED как «обязательные» опоры.

### Vietnam (`страна_б_2026-09`)

- **Stage 3 файл готов** (`examples/3 poi aggregation_в.md`).
- **47 POI:** 0 STRONG CONFIRMED, 6 WEAK, 6 HIDDEN GEM, 0 RED FLAG, 35 LOW SIGNAL.
- **Режим:** `scarce` (HIGH-доля 10.3%).
- **Регионы:** Ханой/Нинь Бинь · Северные горы (Са Па + Май Чау) ·
  Хюэ/Хойан/Мишон · Хошимин/Меконг.
- **Профиль:** соло 37, без прав (структурный конфликт с мото-выборкой).

**Хороший тест Stage 4:** **0 STRONG CONFIRMED** — методологический
priority rule буксует, Stage 4 вынуждена полагаться на HIDDEN GEM +
WEAK + user comments + characteristics. Линейная структура север→юг
(логистика очевидна). 18 ночей × 4 региона — длинная поездка, реальная
комбинаторика тредофов.
