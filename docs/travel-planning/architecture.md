## 1. Общая структура и Stage flow

Скилл — 6-стадийный пайплайн (Stage 0–5) плюс Profile mode и Export.
Каждая стадия живёт в отдельной сессии Claude, контекст передаётся через
markdown-файлы с YAML-шапками в `{travel_root}/trips/{trip_id}/`.

```
Profile mode → 0_scope.md → 1_dr_reports.md → 2_similarity.md
                                                ↓
                             3_poi_aggregation.md → 4_variants.md
                                                       ↓
                             ← user choice ←  5_final_plan.md → Export
```

**Принципиально для Stage 2 и далее:** скилл **не сохраняет файлы
автоматически**, кроме случая Cowork + Synology mount (где разрешён
`Write` + `present_files`). Во всех остальных средах — markdown в чат,
пользователь сохраняет руками. Это сознательное решение для экономии
токенов и контроля пользователя.

## 2. Граница LLM vs script

**Базовый принцип:** всё детерминированное — в скрипт; всё семантическое —
в LLM. Граница чёткая, не размытая.

| Что | Где | Почему |
|---|---|---|
| Парсинг markdown-карточек 20-field | `parse_dr_cards.py` | Структурная работа, regex-friendly. LLM на этом тратит токены и иногда теряет URL/имена. |
| Извлечение метаданных (URL, имя, user_added) | скрипт | Детерминированно, есть якоря (`1. URL:`, `(user_added)`). |
| Извлечение `reports_count` из YAML frontmatter | скрипт | Простой regex. |
| Семантическая оценка автора по 6 компонентам 0–10 | LLM | Требует понимания контекста, профиля, тональности. |
| Определение `outlier_signal.present` | LLM | Семантическая релевантность профилю. |
| Применение весов 25/25/15/10/15/10 | `similarity_score.py` | Арифметика. |
| Нормализация весов при null-компонентах | скрипт | Арифметика. |
| Категоризация HIGH/MEDIUM/LOW/OUTLIER/UNSCORED | скрипт | Сравнение с порогами. |
| Расчёт weighted_contributions per author per component | скрипт | Арифметика. |
| Сборка markdown по §8 reference | LLM | Форматирование с прозой. |
| Reasoning «Тянет вверх / Тянет вниз» | LLM | Семантика. |

**Защитный паттерн:** скрипт жёстко валидирует input (json schema, типы,
диапазоны). Если LLM что-то посчитала руками — это видно сразу, либо
не пройдёт через скрипт, либо вернётся неправильный результат.

## 3. Stage 2 — самый сложный pipeline

Stage 2 — единственная стадия с **двумя скриптами** в цепочке. Это
требование сложности задачи (фильтр 28–60 авторов по 6 компонентам).

### Pipeline

```
1_dr_reports.md
    ↓ Read (по полному файлу, не построчно)
parse_dr_cards.py
    ↓ JSON-template со всеми авторами:
    ↓   id, url, name, user_added, raw_card_text,
    ↓   parse_method, components=null, outlier_signal=null,
    ↓   diagnostic={status, issues, ...}
LLM заполняет components 0–10 + outlier_signal по rubric'ам
    ↓ Filled JSON-payload
similarity_score.py
    ↓ Output JSON:
    ↓   scored_authors[] с total_score, weighted_contributions,
    ↓     category, confidence, in_reading_list, in_extended_reading_list
    ↓   distribution, reading_list, reading_list_extended,
    ↓   warnings (включая anti-bloat OUTLIER warning)
LLM собирает markdown по §8 reference
    ↓ 2_similarity.md
```

### Защита от срезания углов

Stage 2 — место, где модели исторически срезали углы (особенно
Sonnet без thinking, Haiku-fallback). Защитные слои:

1. **Mini-spec в SKILL.md** — 6 компонентов с каноническими именами,
   5 категорий, шкала 0–10. Если модель не прочитает reference,
   она хотя бы возьмёт правильные имена и пороги.
2. **Model self-check** — первая операция Stage 2 объявить модель.
   Haiku → стоп. Sonnet+thinking → продолжать с warning. Opus → ok.
3. **Два скрипта обязательны** — без них Stage 2 не принимается.
4. **Anti-bloat warning** — скрипт ругается если OUTLIER > 30%.
   Защита от Vietnam-кейса (51% OUTLIER).
5. **Diagnostic у parse_dr_cards** — модель не может тихо проигнорировать
   проблемы парсинга; либо ok/warning → продолжать, либо error → диалог.

## 4. Model routing — почему именно Opus 4.7

В скилле модели названы тиром (Opus / Sonnet / Haiku); таблица ниже — на каких версиях шла калибровка.

Routing для Stage 2 переделан после прямых калибровочных прогонов:

| Модель | Результат | Решение |
|---|---|---|
| Sonnet 4.6 без thinking | **fail** — выдумывает Tier-1/2/3 категории, шкала 0-100 вместо 0-10, переименовывает компоненты (`season` вместо `pace`), не запускает скрипт | Из routing убран. |
| Haiku 4.5 (fallback после safety pause) | **fail** — то же что выше, плюс категоричное игнорирование reference | Stop с инструкцией открыть новый чат на Opus. |
| Sonnet 4.6 + adaptive thinking (Cowork) | OK на Argentina (28 авторов), долго (~5 мин) | Fallback, не дефолт. |
| Opus 4.7 без thinking (Claude.ai) | OK на Vietnam (39 авторов), быстрее, стабильно по spec | **Дефолт.** |

**Почему не Opus + adaptive thinking как дефолт:** добавляет токены и
время без видимого выигрыша в качестве — Opus без thinking уже
справляется со spec. Adaptive thinking — для Stage 4/5 (структурные
тредофы), где она реально помогает.

**Почему Sonnet + adaptive thinking как fallback, а не Opus + adaptive:**
дешевле и в Cowork работает. Используется только если по какой-то
причине Opus недоступен.

## 5. Safety filter и Haiku-fallback

**Известный баг платформы Claude.ai:** Sonnet 4.6 в обычном чате
иногда выдаёт «Chat paused» с кнопкой «Continue». Триггер
**не воспроизводим** — паузы случались на безобидных запросах
Stage 2 (профильное упоминание стран, большие DR-выборки).

**Критично:** кнопка «Continue» **не возвращает Sonnet** — она запускает
**Haiku 4.5**, оставляя визуальный лейбл «Sonnet 4.6» в шапке. Качество
вывода резко падает (см. провал v0.6 Argentina с Tier-1/2/3).

**Подтверждено эмпирически:**
- Sonnet 4.6 в Claude.ai → safety filter (Argentina и Vietnam прогоны).
- «Continue» → Haiku → провал.
- Opus 4.7 в Claude.ai → ок, safety filter не сработал.
- Cowork (Sonnet + adaptive thinking, не уверен 100%) → ок.

**Workaround (зафиксирован в SKILL.md):**
- При safety pause не нажимать Continue.
- Открыть новый чат, явно выбрать Opus 4.7.
- Запустить Stage 2 заново.

**Защита model self-check (v0.8+):** первая операция Stage 2 объявляет
модель. Если Haiku — отказ. Это спасает от случаев когда пользователь
не заметил, что после Continue модель сменилась.

## 6. Opt-in LLM-fallback при ошибках парсера

**Контекст:** `parse_dr_cards.py` — терпимый regex-парсер, но может
не справиться с нестандартным форматом DR-файла. Поведение в этом
случае было ключевой развилкой дизайна (v0.9).

**Три варианта, которые рассматривались:**

1. **Жёсткий:** при ошибке парсинга — стоп, пользователь правит Stage 1.
2. **Мягкий:** скрипт делает что может, LLM продолжает silent.
3. **Жёсткий + opt-in fallback:** скрипт всегда возвращает диагностику,
   при `status=error` скилл спрашивает пользователя и предлагает 3 пути.

**Выбран вариант 3.** Обоснование (со слов пользователя): «я не хочу
заставлять пользователю править Stage 1 документ. Все шаги скилла
должны предполагать гибкость со стороны пользователя. И скилл не
должен падать.»

**Реализация:**

- `parse_dr_cards.py` всегда возвращает exit 0 если есть ≥1 карточка.
- В output поле `diagnostic.status` ∈ {`ok`, `warning`, `error`}.
- При `error` скилл выдаёт ОДНО сообщение с диагностикой и 3 вариантами:
  1. LLM-fallback парсинг проблемных карточек (с маркировкой).
  2. Пропустить проблемные.
  3. Стоп — пользователь правит Stage 1 и перезапускает.
- В YAML итогового Stage 2 появляются опциональные поля:
  - `partial_parse: true` + `llm_fallback_authors: [...]`.
  - Либо `skipped_authors_count: N` + `skipped_authors: [...]`.
  - `parse_diagnostic_at_run.{status, issues_summary}`.

**Принцип «прозрачность над автоматизмом»:** LLM-fallback **никогда**
не выбирается автоматически. Только после явного «1» от пользователя.
Это защита от silent выдумывания полей (LLM может «придумать» URL из
`raw_card_text`).

## 7. Калибровочные кейсы

Используются для эмпирической валидации скилла. Конкретные цифры
**не в reference** (там методология general), а здесь — для будущих
правок.

### Argentina (`страна_в_юг_2025-03`)

- **DR-выборка:** 28 карточек (26 основных + 2 user_added: helvhrav, Кукуха).
- **Регионы:** Tierra del Fuego (Ушуая), Лос-Гласьярес юг (Калафате),
  Лос-Гласьярес север (Чальтен), Буэнос-Айрес транзит.
- **Профиль:** соло 37, mid-range independent, ландшафтная фотография,
  без прав.

| Прогон | Модель | Результат |
|---|---|---|
| v0.5 (первый, до правок) | Sonnet без thinking (или Haiku-fallback) | **fail** — Tier-1/2/3, шкала 0-100, переименованные компоненты |
| v0.7+ (после правок) | Opus + adaptive thinking (или Sonnet+thinking в Cowork) | **ok** — 5 HIGH, 4 OUTLIER, 4 MEDIUM extended, формат по spec |

**Что делает Argentina хорошим тестом:** маленькая выборка (28),
не-мото-страна (помогает понять чистый scoring), есть user_added
карточки для проверки независимого scoring.

### Vietnam (`страна_б_2026-09`)

- **DR-выборка:** 39 карточек.
- **Регионы:** Ханой/Нинь Бинь, Северные горы, Хюэ/Хойан/Мишон,
  Хошимин/Меконг.
- **Профиль:** соло 37, mid-range independent, **без прав** (критично —
  Vietnam Coracle и большинство top-авторов мотоцикл-ориентированы).

| Прогон | Модель | Результат |
|---|---|---|
| v0.7+ | Opus в Claude.ai | **частично ok** — формат по spec, но 51% OUTLIER (bloat) |

**Что делает Vietnam сложным тестом:** структурный конфликт профиля с
выборкой (мотоцикл vs «прав нет»). Это **законный** результат — большинство
авторов реально не похожи на профиль, но в reading list нужны как
источники POI. Модель честно отметила это в `outlier_signal=true`, но
для **51%** авторов — это разрушает методику OUTLIER.

**Урок:** v0.8 anti-bloat warning (порог 30%) появился именно после
этого кейса. Если на каком-то trip снова 50%+ OUTLIER — это сигнал,
что либо профиль конфликтует с регионом структурно (надо менять scope),
либо LLM либеральна с маркировкой.

## 8. Stage 3 — реализация (v0.10)

Stage 3 (POI aggregation) реализован в v0.10. Дизайн зафиксирован
обсуждением с пользователем; ниже — решения и их обоснования.

### Граница LLM vs script

Один скрипт `aggregate_pois.py` — в отличие от двух у Stage 2. У Stage 3
нет детерминированного парсер-шага: извлечение POI из прозы карточек —
чистая семантика, regex тут не помогает. Скрипт делает только вторую
половину пайплайна — счёт и категоризацию.

| Что | Где |
|---|---|
| Извлечение POI из полей 14/15 карточек | LLM |
| Нормализация имён POI (дедуп «горы Аватар» = «Чжанцзяцзе») | LLM |
| Тональность каждого упоминания | LLM |
| Цитаты, характеристики места | LLM |
| Счёт упоминаний по тональности и категории автора | скрипт |
| 6 правил категоризации | скрипт |
| Агрегаты, anti-bloat warnings, diagnostic | скрипт |

### Модель — Sonnet 4.6 + adaptive thinking

Методология §7 предписывала «Sonnet без thinking». Решение пересмотрено:
Sonnet без thinking доказанно проваливает задачи Stage-2-класса (§4), а
кросс-авторская нормализация POI не легче per-author scoring Stage 2.
Дефолт Stage 3 — **Sonnet 4.6 + adaptive thinking**, fallback —
**Opus 4.7 без thinking**. Это мягкий шаг вверх от методологии, а не
полный override к Opus: скрипт страхует категоризацию, thinking помогает
дедупликации имён, а Sonnet+thinking в 4–5× дешевле Opus (стадия
read-heavy, input доминирует над output).

### RED FLAG — вариант B (извлечение LOW-авторов)

RED FLAG по определению — место, которое хвалят LOW-similarity авторы,
но критикуют HIGH. Чтобы скрипт мог это вычислить, LLM извлекает из
карточек LOW-авторов их recommend-упоминания (только positive). Это
вариант **B** из обсуждения. Рассматривался и вариант A — targeted-флаг
`mainstream_praise` (ленивая проверка LOW-карточек только для
HIGH-критикуемых POI). Пользователь выбрал B как более точный по букве
методологии.

### Known risk: B + Sonnet

Вариант B (извлечение LOW) на Sonnet+thinking — самая тяжёлая нагрузка
на не-Opus модель в пайплайне. Митигировано: от LOW-авторов извлекаются
**только** recommend-упоминания, не полный набор (это не ×2 объём).
Если на калибровке (Vietnam, 39 авторов, ~15 LOW) Stage 3 начнёт срезать
углы при извлечении — первый кандидат на пересмотр: поднять модель до
Opus либо вернуться к targeted-варианту A.

### Шесть категорий

Правила — `references/stage3/stage3-poi.md` §6.5. Приоритет (скрипт
проверяет сверху вниз): CONTESTED → RED FLAG → STRONG CONFIRMED →
WEAK CONFIRMED → HIDDEN GEM → LOW SIGNAL. `high_neg` =
`high_criticize` + `high_regret_visited`; `regret_missed` в правила не
входит — это контекст. Anti-bloat: STRONG CONFIRMED > 50% или
RED FLAG > 30% от всех POI → warning.

### Два режима категоризации (abundant / scarce)

Калибровочный прогон Vietnam (HIGH=4 из 43 авторов) показал: при узкой
HIGH-когорте строгие правила схлопывают ~85% POI в LOW SIGNAL — место
с 1 HIGH-рекомендацией + OUTLIER-подтверждением (Святилище Мишон) падает
ниже «hidden gem» с 1 HIGH и без подтверждения. Категория недооценивает
место.

Решение — два режима, авто-выбор по **доле HIGH**
(`high_authors_total / total_authors`, порог 30%):
- **abundant** (доля ≥ порога) — строгие правила, WEAK требует hr=2;
- **scarce** (доля < порога) — WEAK допускает hr=1 (при non_high_total>0).

Доля, а не абсолют — чтобы редкий регион с маленькой, но профильной
выборкой не штрафовался за размер. Отличие режимов — **ровно одно
правило** (WEAK_CONFIRMED); STRONG не трогается (всегда hr≥3). Режим
выбирает скрипт (`resolve_mode`), форс — `--mode`.

Stage 2 двухрежимность не нужна: там авторы категоризируются по
абсолютному порогу score (≥7 → HIGH) — устойчиво к размеру выборки.
Схлопывается именно Stage 3, где категория POI реляционна (зависит от
числа сошедшихся HIGH).

**Вывод §8 — по регионам.** «Полная агрегация POI» группируется по
регионам (регионы по убыванию числа POI), не по категориям; категория
видна в заголовке каждого POI. Скрипт сортирует `pois[]` region-first,
отдаёт `region_order`. Под каждым POI — пустое поле «Комментарий
пользователя» для ручной калибровки.

**Iconic exception flag.** Опциональный per-POI флаг для случаев, когда
место явно конфликтует с исключением профиля, но является топ-1
эталоном своей категории в регионе (пингвины Isla Martillo при «не
люблю зоонаблюдение»; Angkor Wat при «не люблю архитектуру»). LLM
ставит флаг с reason (высокий порог), скрипт пробрасывает и считает
агрегат `iconic_exceptions`. **Категорию не меняет** — это
ортогональная аннотация. Чейн: LLM флаг → пользователь видит в §8 и
сам отмечает в «Комментарии» (поле 6) → Stage 4 приоритизирует
по комментарию, не по флагу (страховка от silent over-promote).

### POI synergy — `commonly_combined_with` (v0.17 + v0.18)

Опциональный per-POI флаг для случаев, когда два или более POI в
одном регионе **типично комбинируются местными операторами в одну
экскурсию** (один билет, один отплыв, общий маршрут). Решает проблему:
Stage 4 на pure-LLM шаге без data-якоря пропускает попарную проверку
synergy даже с явными примерами в prose-спецификации.

**Слоёная архитектура (гибрид A+B):**

| Слой | Стадия | Что делает |
|---|---|---|
| Обнаружение | Stage 3 (LLM при экстракции POI) | Помечает кандидатов в поле `commonly_combined_with: [{poi_name, why}]` |
| Passthrough | `aggregate_pois.py` | Пробрасывает поле + считает `aggregates.synergy_pairs` |
| Применение | Stage 4 §6.1 | Читает помеченные пары как **единые юниты** priority pool |
| Контроль | Stage 4 Pre-emit Класс B | Каждая пара отработана или явно расцеплена |

**Признаки synergy для LLM Stage 3 (v0.18):**

1. **Общий оператор** в characteristics обоих POI (явная строка).
2a. **Общая стартовая локация ИЛИ общий природный объект** (один
    ледник, одна гора, одна тропа, один залив, один пляж, одна река).
    Маршрут и операторы могут различаться.
2b. **Общий тип транспорта от одной точки** (катера из одного порта;
    автобусные туры по одной дороге; выезды одного шаттла).
3. **Явное упоминание совместности автором** — дополнительное
   подтверждение, не самостоятельное условие.

Плюс паттерн «**один объект, разные грани**» (мостки + прогулка на
одном леднике; катерный осмотр + высадка на острове в одном заливе) —
сильный сигнал synergy.

Хотя бы один из 1 / 2a / 2b явно выполнен → кандидат. Высокий порог:
если все слабы — поле остаётся пустым (лучше пропустить, чем
выдумать).

**История эволюции:**

- **v0.17 (исходная):** признак 2 как жёсткое AND («общая стартовая
  локация И общий транспорт И пересекающийся маршрут»). Sonnet+thinking
  отвергал Бигль+Мартильо («авторы не описывают совместный пакет»);
  Opus находил часть пар, но тоже пропускал.
- **v0.18 (расщепление):** признак 2 → 2a (локация ИЛИ объект)
  + 2b (транспорт). Признак 3 переквалифицирован в «дополнительное
  подтверждение». Добавлен паттерн «один объект, разные грани».

После v0.18 Sonnet+thinking стабильно ловит пары Бигль+Мартильо,
Перито-Морено мостки+мини-трек, цепочку троп Чальтена. Opus — частично
пропускает (на калибровочном Argentina пропустил Бигль+Мартильо).

**Принципы, не справочник.** Спека НЕ хранит реестр конкретных
комбо-туров по регионам. Все пары выявляются LLM Stage 3 из
characteristics и упоминаний. Скилл не нужно править при появлении
новых синергий в новых поездках.

Тесты: `test_aggregate_pois.py` — 160 проверок (v0.17 расширил
с 152 на 160: passthrough поля + подсчёт + валидация структуры),
stdlib-only, без внешних файлов.

Полная спека POI synergy — `references/stage3/stage3-poi.md` §6.9.
Детальный handoff Stage 3 с эволюцией — `stage3-handoff-context.md`.

### Edit-слой HTML-экспорта (v0.63)

HTML-экспорт Stage 3 умеет операционные правки (тег региона + комментарий
POI) через generic write-API хостинга (`/api/health`·`/api/file`·`/api/save`;
в среде пользователя это сайдкар hub-api Personal Hub). Ключевые решения:

- **md — SSOT, API — generic.** Вся семантика формата живёт в экспортёре
  (рядом с парсером `stages/stage3.py`), API знает только path+content+hash.
  Эволюция формата md не требует передеплоя API.
- **Ноль дрейфа регэкспов.** JS не дублирует паттерны: Python-паттерны
  (`_REGION_HEADER_RE` и др.) уезжают в JS вербатим через JSON-конфиг;
  контракт закреплён тестом (`test_html_export.py [15]`).
- **Хирургия зеркалит `import_docx`** — единая семантика с DOCX-round-trip
  (тег выставить/сменить, комментарий — только существующая строка поля 6,
  однострочный v1). Кросс-языковая эквивалентность проверена JXA-прогоном.
- **Прогрессивное улучшение.** Без API / file:// / вне whitelist / расхождение
  экспорта с md → статичная витрина, никаких ошибок пользователю.
- **Имя md резолвится по директории ВЫВОДА, а не по имени входа (v0.74).**
  Страница просит файл у API по имени, зашитому при сборке; whitelist сайдкара
  пускает только `trips/{id}/3_*.md`. Каноничный flow рендерит из
  `polished_stage_3.md`, поэтому «имя входа» и «имя, которое примет API» —
  разные вещи: `stages_html._stage3_md_name` берёт имя входа, только если оно
  само каноничное, иначе ищет `3_*.md` рядом с выводом (приоритет
  `3_poi_pool.md`, затем max `_vN`); нет кандидата → слой не включается вовсе
  (лучше честная витрина, чем ссылка в никуда). Ось «продюсер имени ↔
  whitelist» закреплена тестом `tools/tests/test_pages_contracts.py`.
- **Stage 4 и комментарии к регионам (v0.79).** Тот же протокол и принципы
  (md — SSOT, регэкспы из Python вербатим, прогрессивное улучшение) расширены:
  Stage 3 — поле «Комментарий к региону» (`**Комментарий к региону:**` в шапке
  региона; нет строки → создаётся под заголовком, в отличие от поля 6 POI,
  которое только правится), Stage 4 — комментарии к вариантам + общий в секции
  `## Комментарии к вариантам` перед `## Решение` (`stages_html._stage4_md_name`,
  whitelist `4_*.md` уже был). Метки обеих строк намеренно без «Комментарий
  пользователя»: `check_format.check_poi_count` сверяет `total_pois` по числу
  таких строк. DOCX-round-trip комментарий к региону не несёт (HTML — основной
  путь заполнения). Сквозная проверка — `tests/test_edit_layers.py` (chromium +
  фейковый write-API).
- **Молчание — только для гостя (v0.74).** Прогрессивное улучшение выше
  означало полное молчание при ЛЮБОМ отказе, и операционная ошибка (не тот md)
  была неотличима от read-only-витрины: диагноз занял часы. Теперь, если API
  жив и пишет, а файл не отдался, страница печатает причину в углу («вне
  whitelist» / «нет файла»); гостю без доступа к API по-прежнему молчит.

## 9. Stage 4 — реализация (v0.11)

Stage 4 (Route variants) реализован в v0.11. Дизайн зафиксирован
обсуждением с пользователем; ниже — решения и их обоснования.

### Граница LLM vs script — pure LLM

Stage 4 — **единственная стадия пайплайна без скрипта**. Это сознательное
решение, согласованное с пользователем: построение вариантов,
тредофф-анализ, бюджетная оценка, сравнительная таблица, honest
assessment — всё семантика, скрипт ничего не добавляет.

Кандидаты, которые были рассмотрены и отвергнуты:
- `coverage_check.py` — проверка, какие user_commented + STRONG/HIDDEN
  GEM POI не вошли ни в один вариант. Отказано: silent-drop ловится
  обязательным блоком «Чего я бы не делал ни в одном из вариантов» в
  honest assessment (§6.8 reference).
- `budget_check.py` — парсинг диапазона рублей и сравнение с лимитом.
  Отказано: грубая оценка по midpoint полностью укладывается в
  LLM-эвристику; точная верификация цен — задача Stage 5.
- `validate_yaml.py` — формат YAML-шапки. Отказано: format-запреты
  фиксируются в §10 reference, mini-spec в SKILL.md закрывает риск
  drift'а.

### Модель — Sonnet 4.6 + adaptive thinking

Дефолт — **Sonnet 4.6 + adaptive thinking**, fallback — **Opus 4.7**.
Методология §8 предписывала Sonnet+thinking, и это решение
поддерживается. Эскалация к Opus — по результату калибровки. Stage 4
рекомендуется на Opus для **reconstructive Stage 5** прогона следующей
стадии, но сам Stage 4 — типичная тредофф-задача, Sonnet+thinking
справляется.

Аналогично Stage 3 — без thinking модель срезает углы (косметические
варианты вместо структурных), поэтому в SKILL.md model self-check
блокирует Haiku и предупреждает при Sonnet без thinking.

### User comments как явный приоритетный сигнал

Самое значимое отступление от методологии §8. Чейн:

1. **Stage 3** — каждое POI имеет пустое поле «Комментарий
   пользователя» в §8 выходного файла. Пользователь заполняет руками
   между сохранением Stage 3 и запуском Stage 4.
2. **Stage 4** — читает комментарии семантически (не boolean): сильное
   положительное → MUST (включить во все варианты); положительное с
   условием → включить с учётом условия; нейтральное → контекст;
   негативное → EXCLUDE.
3. **Приоритет:** user_comments **перекрывают любую категорию Stage 3**,
   включая RED FLAG. Логика: RED FLAG = ловушка для среднего туриста
   из выборки, но осознанный выбор пользователя имеет приоритет.

Это лечит две проблемы (унаследованные из Stage 3 v0.10):
- **Iconic exception** — пользователь подтверждает интерес к
  «исключению из профиля» через комментарий, а не через автоматическое
  включение.
- **Категория недооценивает место** (особенно в `scarce`-режиме, где
  WEAK = «1 HIGH-рекомендация») — пользователь может поднять LOW SIGNAL
  / WEAK место в приоритет руками.

### Iconic_exception — только через user comment

Унаследовано из Stage 3 чейна. Stage 4 ЧИТАЕТ `iconic_exception.reason`
для контекста (объясняет, почему место в файле, несмотря на исключение
профиля), но **включает только при наличии положительного user
comment**. Без коммента — место упоминается в honest assessment с
строкой «не включён, обнови комментарий в Stage 3».

Страховка от silent over-promote: модель не пропихивает профильное
исключение в маршрут без согласия пользователя.

### RED FLAG исключение

Стандартное правило (методология §8): RED FLAG **не включать**.

**Исключение v0.11:** положительный user comment перекрывает RED FLAG
(как любую другую категорию). При включении — обязательная строка
«⚠ RED FLAG-предупреждение: {что говорят HIGH-критики}. Включён по
явному выбору пользователя (комментарий: "{цитата}")». Прозрачность
важнее автомата.

Пример: Argentina Isla Martillo (RED FLAG + iconic_exception + «На
попасть туда» от пользователя). Включается в один вариант с warning.

### Mode-awareness (`abundant` / `scarce`)

`aggregation_mode_inherited` в YAML Stage 4 — режим, унаследованный из
Stage 3 (выбран по доле HIGH = `high_authors_total / total_authors`,
порог 30%):

- **abundant** (≥ 30%) — строгие правила Stage 3, WEAK = 2
  HIGH-рекомендации.
- **scarce** (< 30%) — мягкие правила, WEAK = 1 HIGH-рекомендация +
  подтверждение.

Stage 4 интерпретирует это в priority pool: в `scarce` категория WEAK
получает приоритет MEDIUM (слабее), чем была бы в `abundant`. В
`## Контекст` явно отметить режим — пользователь видит калибровку.

### Inline бюджет-warning (по запросу пользователя)

Защита от silent over-budget. Чейн:

1. `budget_target_rub` извлекается из секции `## Бюджет` профиля
   (RUB/неделю × `duration_nights / 7`). Без этой секции — gate
   отказывает.
2. Каждый вариант получает грубый диапазон «~XXX–YYY тыс ₽ на группу»
   (LLM-оценка на основе транспортных сегментов + типового размещения
   по классу из профиля + питания).
3. Midpoint сравнивается с лимитом:
   - `under_target` (≤-10%) — info-строка «бюджет ниже на XX%, запас на N».
   - `on_target` (±10%) — без warning.
   - `over_10_20` (10-20%) / `over_20+` (>20%) — ⚠️ warning ОБЯЗАТЕЛЕН
     в начале варианта с источниками превышения и альтернативами.

Пороги — ±10-20% от лимита, как запросил пользователь. Если профиль
предусматривает вилку ±N% — `on_target` ширится до ±N%, остальные
пороги сдвигаются (§9.12 reference).

Почему не pre-check turn (до построения вариантов): пользователь явно
выбрал inline warning. Pre-check добавил бы +1 turn без явного выигрыша
— inline в каждом варианте даёт ту же информацию сразу с контекстом
конкретного варианта.

### Previous_plan — опц. секция ДО вариантов

Если в YAML Stage 3 `previous_plan` != null — **обязательная отдельная
секция** `## Сравнение с предыдущим планом` ПЕРЕД блоком вариантов.
Структура — 3 подсекции:

1. **Сильные совпадения с консенсусом Stage 3** — точки предыдущего
   плана, попавшие в STRONG/HIDDEN GEM или MUST через user_comment.
2. **Точки со слабым / противоречивым сигналом** — конкретный разбор
   каждой проблемной точки + действие («исключаем» / «перекомпонуем»
   / «заменяем»).
3. **Чего нет в плане, но Stage 3 выделил с сильным сигналом** —
   кандидаты на включение.

В каждом варианте — **1-строчная связка** «**Что меняется vs предыдущий
план:** …» (без дублирования общего анализа).

Если `previous_plan` == null — секция и строки опускаются. Калибровочные
кейсы (Argentina + Vietnam) на момент v0.11 — без previous_plan,
поэтому секция теоретическая. Дизайн взят из пользовательского
`Stage-4-example.md`, который как раз содержал сравнение с планом v3.

### Структурное различие вариантов

Sanity-check: между любыми двумя вариантами различается **минимум один**
из тредофов:

- Глубина против покрытия.
- Городская против природной плотности.
- Стандартный набор регионов против нетипичного.
- Сжатый маршрут с одним мощным буфером против распределённых буферов.
- Высокий темп vs низкий темп.
- Включение vs исключение iconic_exception (через user comment).

Если все 3 варианта косметически разные (одни регионы, разный порядок
дней) — это **провал mini-spec**. В honest assessment не маскировать
косметические варианты под структурные.

### Сравнительная таблица — гибкий формат

6 обязательных осей методологии §8 + 2 фиксированных (бюджет + уникальный
риск) + до 2 опц. релевантных конкретной поездке (например, «архитектурная
глубина» для Vietnam, где профиль фокусируется на архитектуре, или
«число локаций» для длинной поездки с большим скоупом). Лимит — 10
осей всего (anti-bloat).

Фиксированные оси гарантируют сравнимость между поездками; опц. оси —
гибкость под специфику. Это компромисс между жёстким форматом (Stage 0
3 пакета, Stage 3 6 категорий — где имена строго) и LLM-свободой.

### Тесты

Stage 4 не имеет автотестов (скрипта нет). Валидация — через
калибровочные прогоны:

- **Argentina** (`страна_в_юг_2025-03`): 2 STRONG, 1 RED FLAG +
  iconic + user comment (Isla Martillo — отличный тест чейна),
  региональный skew Чальтена 15/26 → варианты должны структурно
  по-разному обрабатывать. Бюджет — из профиля `алексей`.
- **Vietnam** (`страна_б_2026-09`): 0 STRONG, 6 WEAK, 6 HIDDEN GEM,
  35 LOW SIGNAL. Методологический priority rule буксует — варианты
  опираются на HIDDEN GEM + WEAK + user_comments. 18 ночей × 4 региона
  — реальная комбинаторика тредофов.

### Эволюция Stage 4 после v0.11

Стадия прошла через несколько калибровочных циклов с регрессиями
методологии. Подробности — `stage4-comments.md` (журнал failure modes)
и `changelog.md` (записи v0.12–v0.18). Ключевые вехи:

- **v0.12 — Transport consent gate** (`storage-and-naming.md` §1.4).
  Silent fallback на Google Drive MCP отключён для всех режимов кроме
  Profile management — после ловушек на Sonnet (base64-декод и
  search_files сниппеты).
- **v0.13 — Opus 4.7 primary + Pre-emit checklist §6.9**. Stage 4 на
  Sonnet+thinking систематически пропускал failure modes (Москва-
  галлюцинация, HIGH/OUTLIER путаница в форматах POI, однотонная
  загрузка региона, физнагрузка против профиля, парные `$` ломали
  визуальные viewers). 6 классов чеклиста (A — факты, B — Stage 3
  сигнал, C — структура, D — логистика, E — формат, F — Warnings)

- **v0.14 + v0.15 — `home_city` / `trip_start_city`**. Stage 0 теперь
  резолвит точку отправления из профиля (`Базовый город`) или запроса
  пользователя. Stage 4 формулирует крайние дни маршрута по
  `home_eq_start` («Старт маршрута в X» vs «Прилёт в X»). Транзитный
  хаб как отдельная сущность убран — `trip_start_city` это просто
  город старта/конца поездки.
- **v0.16 — `trip_wishes`**. Свободно-формулированные пожелания
  пользователя из запроса («хочу пингвинов», «увидеть карнавал»)

  Stage 4 (поднимает POI в MUST даже без user_comment'а на нём).
  Закрыта дыра «trip-specific пожелания, не сводящиеся к топонимам,
  терялись в structured extraction».
- **v0.17 + v0.18 — POI synergy hybrid** (см. §8 выше). Stage 4
  читает `commonly_combined_with` из Stage 3 как data-anchor priority
  pool. Pre-emit Класс B проверяет, что каждая пара отработана.

## 10. Stage 5 — реализация (v0.19)

Stage 5 (Final consolidation) реализован в v0.19. Дизайн зафиксирован
обсуждением с пользователем; ниже — решения и их обоснования.

### Граница LLM vs script — pure LLM

Stage 5 — **pure LLM, без скрипта** (как Stage 4). Детализация дня —
семантическая работа: интерпретация правок пользователя, поиск
конкретных отелей/операторов/часов работы, сборка swap-стратегий,
бюджетная оценка. Скрипт-валидатор для post-emit проверки рассмотрен
и отвергнут — Pre-emit checklist 6 классов в reference закрывает риск
drift.

Кандидаты, которые были рассмотрены и отвергнуты:

- `consolidate_plan.py` — детерминированный сбор бюджета дня→неделя→
  total из markdown, валидация покрытия дней vs duration_nights,
  surgical/reconstructive detection. Отказано: LLM сама считает midpoint
  через арифметику в проекте, mode detection укладывается в детерм.
  алгоритм §6.1 reference, валидация покрытия — Pre-emit Класс A.
- `validate_final.py` — sanity-check после генерации (число дней
  совпадает с duration_nights, YAML-схема, обязательные секции на
  месте, todo_verification_items совпадает с реальным числом TODO).
  Отказано: всё закрыто Pre-emit checklist'ом; внешний валидатор
  ловит то, что модель должна была проверить сама.

### Модель — два режима

| Режим | Модель | Когда |
|---|---|---|
| **surgical** | Sonnet 4.6 + adaptive thinking (Opus — fallback) | Структура совпадает с previous_plan; меняются POI/активности внутри дней |
| **reconstructive** | Opus 4.7 + adaptive thinking (Sonnet — fallback) | Нет previous_plan ИЛИ структура отличается |

**Mode detection** — детерминированно на шаге 4 потока, БЕЗ участия
пользователя:

- `previous_plan == null` → reconstructive (нет с чем сравнивать).
- `previous_plan != null` + структурное совпадение (тот же набор
  регионов + ±0 ночей) → surgical.
- Иначе → reconstructive с переиспользованием payment-инфры и
  логики реагирования на риски.

Mode объявляется одной строкой пользователю в начале Turn 2.

**Эскалация Sonnet → Opus при reconstructive:** после mode detection,
если модель Sonnet+thinking и режим оказался reconstructive — скилл
предлагает переключение на Opus одной строкой (см. SKILL.md «Stage 5:
model self-check»). Дождаться ответа.

### Custom variant interpretation — variant + правки

Stage 4 блок `## Решение` содержит:

- `**Выбран вариант:**` — `A` / `B` / `C` / `кастомный`.
- Опц. `**Состав:**` — структурное описание (для кастомного) или
  правки к variant.
- Опц. `**Почему этот выбор:**` — обоснование, может содержать
  дополнительные правки.

Stage 5 семантически интерпретирует правки в 4 типа:

1. **Замена формата активности** («Мартильо не с высадкой, а с
   катамарана»).
2. **Добавление активности** («подъём на ледник Мартиаль», «велосипед в
   Хюэ день 15»).
3. **Удаление активности** («убрать X», «без Y»).
4. **Уточнение** («поменять отель на премиум», «брать машину с
   водителем»).

**Правки встраиваются в маршрут естественно**, без маркеров в днях.
ОДНА summary-строка в `## Контекст и ключевые параметры` фиксирует
факт правок («Применены правки из `## Решение` Stage 4: …»). Финальный
план читается как единое целое — пользователь, открывающий файл через
месяц, не должен спотыкаться о пометки «вот эту активность ты сам
выбрал».

**Custom modifications не хранятся в YAML отдельным полем.** Информация
уже в `## Решение` Stage 4 и в самом теле финального плана.
`chosen_variant_raw` + `chosen_variant` в YAML — достаточно для
traceability.

**Opt-in clarification при конфликте.** Если правка пользователя
структурно противоречит варианту (например, «добавить день в Хюэ» при
Хюэ 2 ночи без резерва) — Stage 5 в Turn 2 выдаёт ОДИН batch с 3
вариантами (перераспределить ночи / реализовать урезанно / отказаться
от правки) и останавливается. Дождаться Turn 3. Аналог §9.12 Stage 2.
В YAML фиксируется `clarification_used: true`.

### Web search policy — гибрид

Stage 5 — единственная стадия с **активным web search** (Stage 0
делает целевые поиски на актуальность, Stage 4 не делает вообще,
остальные читают артефакты предыдущих стадий).

**Активные поиски (~10-20 на план):**
- Расписания внутренних рейсов / автобусов / поездов / паромов.
- Часы работы и стоимость входа достопримечательностей.
- Конкретные операторы synergy-пар Stage 3 (если есть).
- Сезонные ограничения.
- **Имена / районы / рейтинги отелей** под класс из профиля.
- Опц. адреса / специализации ресторанов.

**НЕ web search (всегда TODO):**
- Цены отелей (волатильны, систематически занижаются LLM на 3-10×).
- Цены ресторанов (кроме общих диапазонов).
- Цены такси.
- Курсы валют (на чеклист «за 2 недели»).

**Принципиальное решение по отелям.** Первоначальный дизайн «отели
всегда полностью TODO» был слишком строгим. Vietnam_v4_calibrated.md
показал правильный гибрид: имена/районы/рейтинги отелей — структурные
данные, LLM находит активно (Booking/Tripadvisor/Trip.com индексируются
Google); **только цены** идут как TODO с диапазоном-ориентиром. Это
позволяет финальному плану быть полезным сразу — пользователь видит
конкретный отель, не TODO-плейсхолдер.

### Опц. MCP-расширения (Booking / Expedia)

Stage 5 может опционально использовать MCP-коннекторы для цен отелей.

**Policy:**
- **По умолчанию** — не используется (переносимость скилла; не
  привязываем к окружению Claude.ai).
- **Активировать** при явном запросе пользователя ИЛИ при активных
  MCP-коннекторах в среде без явного отказа.
- MCP-цены подставляются с пометкой «**через {Booking|Expedia} MCP,
  YYYY-MM-DD**» и **не заменяют TODO** — TODO остаётся, потому что
  (а) пользователь финально бронирует сам, (б) цены могут измениться
  до даты поездки.
- В YAML фиксируется `mcp_extensions_used: ["booking"]` (или
  `["booking","expedia"]`).

**Зачем не убирать TODO при MCP-ценах:** MCP-цены — мгновенный
снимок, не контракт. Пользователь должен сам зайти на Booking перед
бронированием.

### Уровень детализации дня — иконки

Каждый день — компактный блок с фиксированными иконками-секциями (по
образцу vietnam_north_v4_calibrated.md):

- 📍 переезд (откуда → куда, расстояние, способ, время в пути)
- 🏨 отель (имя + район + рейтинг + диапазон-ориентир + TODO)
- 🎯 программа (часовая разбивка с часами работы, ценами входов,
  временем на посещение, опц. операторами synergy-пар)
- 💰 бюджет дня (диапазон в ₽)
- ⚠️ риски / нюансы / swap-стратегии при отмене

Это компактный визуальный формат для быстрого сканирования. Иконки
**только в блоках дней**; в заголовках секций и в прозе — без эмодзи
(исключения — `⚠️` для inline warnings и `✅`/`❌` в опц. блоках «кому
подходит», если переиспользуется из Stage 4).

### 9 обязательных секций output

Структура наследуется из методологии §9:

1. `## Контекст и ключевые параметры` (опц. подсекции: «Логика ключевых
   решений», «Чего больше нет в маршруте и почему» — включаются по
   релевантности)
2. `## Шапка` (билеты, визы, валютные курсы)
3. `## Критические подготовительные пункты` (деньги, SIM, транспорт,
   сезонные риски)
4. `## Маршрут по дням`
5. `## Сводные таблицы` (транспорт, бюджет, гастрономия)
6. `## План реагирования на риски`
7. `## Чеклист за 2 недели до поездки`
8. `## Diff с предыдущим планом` *(только если `previous_plan != null`)*
9. `## TODO для верификации` (3 категории: before-booking,
   2-weeks-before, in-trip)

Адаптивное сжатие (например, surgical → только diff + изменённые дни)
**не делается** — потеря контекста при изолированном чтении через год.
9 секций всегда. При размере, не вмещающемся в один ответ — split на
`5_final_plan_part_b.md` (см. §9.10 reference), не «опущено for
brevity».

### Pre-emit checklist — 6 классов

Аналог Stage 4 checklist'а, но с фокусом на детализацию:

- **Класс A — Stage 4 consistency.** Все дни выбранного варианта
  присутствуют; правки применены; формулировка крайних дней по
  `home_eq_start`; mode объявлен; решения Stage 0/3/4 не пересмотрены.
- **Класс B — TODO discipline.** Каждая цена отеля → TODO (даже с MCP);
  цены ресторанов TODO; цены экскурсий — диапазон или web search ссылка;
  международный перелёт только при `home_eq_start == false`;
  `todo_verification_items` в YAML совпадает с реальным числом TODO.
- **Класс C — данные и факты.** Часы работы / стоимость входа со
  ссылкой или TODO; операторы synergy-пар — конкретные или TODO;
  расписания транспорта со ссылкой или TODO; MCP-цены с датой запроса.
- **Класс D — логистика.** Каждый переезд имеет транспорт + время +
  способ бронирования + диапазон стоимости; узкие звенья из Stage 4
  сохраняют swap-стратегию; synergy-пары как «комбо у оператора X».
- **Класс E — формат и YAML.** Долларовые цены escape'нуты (`\$NN` /
  `USD NN` / backtick); YAML три дефиса; имя файла `5_final_plan.md`;
  нет «опущено for brevity»; нет «Сохранить как» в теле файла.
- **Класс F — Diff и TODO summary.** Diff заполнен если `previous_plan
  != null`; секция TODO содержит все TODO из тела; счётчик в YAML
  точный.

## 13. Stage 6 — реализация (v0.43)

Финишная контент-стадия: доводит **устаканенный** план 5_vX до trip-ready
идеала добавками, не влияющими на выбор маршрута. Граница 5/6 и решения D1–D6
— `stage6-handoff-context.md`.

### Инвариант: 5_vX immutable, слияние механическое

Главное архитектурное решение (D1=A). Stage 6 НЕ редактирует
`5_final_plan.md` — он immutable SSOT маршрута. Stage 6 пишет ОТДЕЛЬНЫЙ
`6_final.md` только с добавками (координаты + досье + дельты брони +
углубления); день-за-днём контент 5_vX в нём не дублируется. Финальный PDF
собирается **механически на экспорте**:

```
рендер 5_vX (билдеры stage5.py)  ←  immutable, читается по YAML source_plan
  + обзорная карта (из координат 6_final.md)
  + приложения досье / бронь / углубления (из 6_final.md)
```

Почему так (а не standalone-стадия, переносящая весь Stage 5 verbatim):
держит LLM Stage 6 только на НОВОМ контенте, Stage 5 собирается механически →
маршрут/дни ни разу повторно не прогоняются через модель → дрейф плана и
накопление ошибок через шаги исключены. Худший случай ошибки Stage 6 —
неверная карта, не испорченный план; таблица координат ревьюабельна по столбцу
«Источник» (gazetteer / model).

Технически — opt-in `inject`-пакет в `stage5.build_pdf(..., inject=None)`:
при `None` поведение Stage 5 неизменно (golden сохранён); при `{…}` сплайсит
`map_flowables` (после обложки → ложится после TOC) и `appendix_flowables`
(после чеклиста, перед приложением «Обоснование»). Single orchestration path,
ноль дублирования логики между stage5 и stage6.

### Координаты — двухтиерный резолв + персист (граница LLM/скрипт)

| Tier | Где | Что |
|---|---|---|
| **1** | `scripts/geocode.py` (детерминированный, stdlib) | имена точек → координаты из газетира `scripts/data/gazetteer.json` (транслит / alias / fuzzy / bbox страны). Авторитет координаты — газетир, не модель |
| **2** | модель | ненайденные Tier-1 точки (деревни, мелкие POI) — знание модели, `source: model` |

Резолв делается на КОНТЕНТ-стадии и персистится в `6_final.md` (таблица
`№ | Точка | lat | lon | Источник | Дни` + порядок маршрута + рёбра). Это
полная спека карты: Export-рендерер её ЧИТАЕТ, не геокодит. По D4 газетир —
ассет контент-стадии (`scripts/data/`), контур стран `ne_countries.geojson` —
ассет рендера (`scripts/export/data/`).

Хит-рейт Tier-1: крупные города высоко (Ханой / Сеул / Пусан / Буэнос-Айрес),
деревни низко (Сапа / Мукангчай / Эль-Чальтен → Tier 2) — это и есть штатное
разделение труда, не дефект.

### Карта — универсальный рендерер (Уровень 1)

`render_route_map(spec, countries, out_base)` в `stage6.py` (перенесён из
dev-прототипа): авто bbox, point-in-polygon заливка страны маршрута, поправка
широты, кривые рёбра, типы рёбер (обычное / узкое звено = красный / перелёт =
пунктир). matplotlib → PNG → `pdf_lib.map_image` (вписать в контент-бокс).
Spec строится из `## Координаты маршрута` (`build_route_spec`), fallback —
`гео:`-маркеры дней 5_vX (`extract_route_spec`).

Scope v1 (D6): только обзорная карта. Региональные инсеты (Уровень 2) нужны
деревенские координаты (Tier-2, риск точности на зуме) — отложены в v2.

### Модель — Sonnet+thinking

Stage 6 = retrieval / компиляция / web-search + синтез досье + мёрж брони —
НЕ Opus-интеграция (как reconstructive Stage 5). Координаты резолвятся
детерминированно (Tier-1) + модель добивает Tier-2; карту рисует рендерер.
Opus допустим, но избыточен. Sonnet без thinking — стоп (досье деградирует).

## 12. Архетипы группы (v0.22)

Калибровка скилла под разные демографии — введена в v0.22 после
ретроспективной валидации на двух кейсах (Vietnam mediocre 6.75/10,
Argentina-юг successful 5.25/10) показавшей, что текущие умолчания
arseniioцентричны.

### Дизайн: 4 архетипа, [ASK] на CREATE/MERGE

Поле `группа_архетип` в YAML профиля принимает одно из 4 значений:
- `самостоятельные` (дефолт-эквивалент текущих весов алексея; прежнее имя
  `независимые_соло_пара` — legacy-алиас, резолвится в него, v0.81)
- `семья_с_детьми`
- `взрослые_50_плюс` (прежнее `родители_60_плюс` — legacy-алиас)
- `люкс`

Дефолта **нет** — при создании или объединении профиля поле требуется
обязательно через `[ASK]`-вопрос. Это решение пользователя, не выводимое
автоматически. Эвристическая подсказка (возраст > 55 → `родители`; есть
дети → `семья`; премиум → `люкс`) выдаётся в Profile management mode
вместе с вопросом, но финальный выбор — за человеком.

При UPDATE менять архетип можно только по явному запросу пользователя —
автоматическая миграция запрещена (изменение архетипа существенно
меняет калибровку весов и DR-выборки, не должно быть silent).

### Веса similarity (Stage 2)

Лукап-таблица в `references/profile-management.md` §7.5. Логика:

- Для семьи / родителей вес `demo` резко растёт (нужны авторы похожего
  состава) — 25 / 35 соответственно vs 10 у алексея.
- Для них же `depth` падает с 15 до 5 — стандартный маршрут с
  предсказуемой инфраструктурой важнее off-the-beaten-path.
- Для люкса акцент на `style` (30) и `demo` (20) — премиум-авторы
  похожего профиля.

Сумма весов = 100 для каждого архетипа. Скрипт `similarity_score.py`
валидирует.

### Override механизм

Опциональный блок `similarity_weights_override` в YAML профиля
перекрывает архетипные веса при необходимости индивидуальной калибровки.
6 русских ключей: `стиль`, `фокус`, `темп`, `независимость`,
`non_touristy`, `возраст_состав`. Сумма обязана быть 100.

В выход скрипта добавлены поля `archetype_used` и `weights_source` для
traceability (`default` / `archetype` / `override` / `cli_weights` /
`cli_archetype` / `payload_weights`).

### Seed source-set DR-выборки (Stage 1)

Лукап в `references/profile-management.md` §7.5. Принцип **seed +
open-ended**:
- seed-список — стартовая рекомендация по архетипу;
- DR-агент может включать другие источники, в META-DIAGNOSTICS отмечает
  «вне seed».

Это решает проблему «закрытого списка» (фуд-блог с разовым подробным
trip report'ом нельзя упустить) при сохранении калибровки (для родителей
60+ Reddit r/travel даёт мусор, нужен tripadvisor forums + road
scholar reviews).

### Принципиально: что НЕ зависит от архетипа

- Поля профиля (Состав группы / Ядро интересов / Темп и т.п.) — их
  скилл и так читает через профильные секции.
- Местные языки DR-источников (vi / es / ja / etc.) — применяются для
  всех архетипов одинаково.
- Структура output Stage 0–5 — 9 секций, шаблон одинаковый.
- Текстуальные шаблоны reasoning Stage 0 и Stage 5 гастро/риск-таблица
  — пока **зашиты под алексея**. Профиль-зависимые шаблоны — Tier 3
  TODO, не входит в v0.22.

### Бэклог для архетипов

Что мог бы дополнительно зависеть от архетипа (откладываем):
- Шаблон гастро-шпаргалки Stage 5 (для семьи — кид-friendly места;
  для родителей — без острого / без street food; для люкса — fine
  dining).
- Шаблон риск-таблицы Stage 5 (для родителей — давление /
  языковой барьер; для семьи — детские медицинские риски).
- Reasoning Stage 0 (текстуальная подача релевантности региона —
  сейчас алексеевская).
- Тонкая настройка темпа: `nights_per_locale.{min,max}` per-архетип
  в профиле (сейчас всё через `## Частота смены локаций` в теле).

## 14. Локализация таксономии (Фаза 1, v0.55)

Решает «смешанный регистр» видимого вывода (английские таксоны
`HIGH/OUTLIER/…`, `STRONG CONFIRMED/…` рядом с русским текстом). Реализована
**двухфазно** (план — `russification-plan.md`); ниже — Фаза 1.

**Словарь-SSOT.** `scripts/data/taxonomy.json` — единственный источник переводов
(7 групп: `author_category`, `poi_category`, `poi_category_badge`, `region_role`,
`warning_severity`, `tonality`, `similarity_component`) + алиасы приёма.
`scripts/taxonomy.py` даёт `label/canon/pattern/keys/groups/legend` (stdlib).

**Инвариант: EN в `.md`/YAML — RU на рендере.**
- Модель эмитит `.md`/YAML с **английскими** таксонами (как раньше) — контракты
  не тронуты, выход модели не меняется → golden-прогон не требуется.
- Канонический ключ группы = текущий машинный EN-ключ (underscore-форма
  `STRONG_CONFIRMED` для poi_category — как `aggregate_pois.CATEGORY_RANK`;
  space-форма `STRONG CONFIRMED` — отображаемый EN-ярлык, ключ `style.CATEGORY_*`).

**Слои.**
- *Скрипты-счётные* (`similarity_score`, `aggregate_pois`): на входе принимают
  EN и RU (`canon`), на выходе добавляют display-поля (`category_label`,
  `severity_label`) **аддитивно** — EN-контракт неизменен.
- *Парсеры экспорта*: регулярки расширены на оба языка через `pattern()`, сразу
  после матча — `canon()`, дальше внутри кода живут **только EN-ключи**.
- *Рендер*: каждая подпись — `label()`; бейджи PDF/DOCX русифицированы через
  `style.CATEGORY_SHORT` (строится из taxonomy) без правок самих pdf/docx-библиотек.
- *Легенда* (Р2): сноска RU↔EN один раз на документ (Stage 2/3 PDF/HTML/DOCX),
  т.к. `.md` остаётся с EN-таксонами.

**Drift-защита.** `test_format_contract` получил ось taxonomy: ключи групп ↔
константам скриптов 1:1, `pattern()` матчит EN+RU.

**Остаток на Фазу 2** (эмит `.md`, под golden-прогон): перевод output-spec'ов,
references §6.x, polish-промтов `stage{0..4}-polish-prompt.md`, `SKILL.md`,
`STAGES.md`; русификация прозы warning-сообщений скриптов (сейчас мост — легенда).
Карта — `russification-plan.md` §7.
