# Экспорт по типам получателей (recipient modes)

Один и тот же артефакт стадии рендерится под **разных получателей**: что
включить, что вырезать, какая тональность. Этот документ — про **отличия**
между тем, что реально получается сейчас (`self`), и тем, как это выглядело
бы для остальных типов.

Связанные источники правды:
- `export-design.md` §3 (recipient modes), §4 (per-stage adaptation),
  §7 (critical preserve/strip) — дизайн;
- `skills/travel-planning/scripts/export/adapter.py` — **реализация**
  (`RECIPIENT_RULES`, `adapt_for_recipient`, `register_recipient`).

---

## 0. Статус реализации (что есть, чего нет)

| Тип | Статус | Где |
|---|---|---|
| **`self`** (для себя) | ✅ реализован, основной | `RECIPIENT_RULES["self"]` |
| **`parents`** (родители) | ✅ реализован (engine + S5-расширение) | `RECIPIENT_RULES["parents"]` |
| **`partner`** (попутчик) | ⛔ спланирован, не зарегистрирован | — |
| **`guide`** (гид) | ⛔ спланирован, не зарегистрирован | — |
| **`archive`** (архив) | ⛔ спланирован, не зарегистрирован | — |

`adapt_for_recipient` при неизвестном получателе **бросает KeyError**
(fail-fast, а не «отрендерить как-нибудь»). Новый тип добавляется через
`register_recipient(name, RecipientRules(...))` + при необходимости
`register_stage_extension(recipient, stage, fn)` для стадийных правил.

**Принцип** (из методологии скилла): типы добавляются **не превентивно**,
а под реальный кейс. `self` + `parents` покрывают v1/v2; остальное —
когда появится конкретная потребность.

---

## 1. Базовая линия — `self` (то, что получилось)

Полный **операционный документ** для самого путешественника. Видит всё,
кроме сугубо машинных метаданных.

**Включено:** маршрут по дням с адресами/часами/выходными; транспорт
(номера, цены, длительность, терминалы); бюджеты по дням и регионам (₩+₽);
TODO-маркеры (подсвечены жёлтым — непроверенные цены); все warnings;
«План реагирования на риски» с вероятностями; чеклисты с живыми ссылками;
аварийные контакты; K-ETA / курсы; honest assessment и тредофы;
пользовательские комментарии (Stage 3).

**Вырезано даже для self:** raw YAML frontmatter, `_log` / `_diagnostic`
блоки (внутренняя диагностика пайплайна).

Это уровень хорошего агентского day-by-day — «реально можно ехать по
документу».

## 3. Отличия по типам

### `parents` — родители (реализован)

**Зачем:** родители волнуются; им нужен «вот план, всё под контролем», а
не черновик в работе.

**Главные отличия от `self`** (всё закодировано в `RECIPIENT_RULES["parents"]`):
- **Убрано целиком:** «План реагирования на риски», «TODO для верификации»,
  «Honest assessment», «Контекст для следующих стадий», «Diff с предыдущим
  планом».
- **Убраны подсекции:** TODO, Warnings, Tag parse warnings, Risk-таблица,
  Swap-стратегии; inline-блоки `⚠️ Риски` внутри дней.
- **Убраны inline TODO-маркеры** (`strip_todo_markers`) — чтобы план не
  читался как «не финальный».
- **YAML ужат** до `trip_id / stage / duration_nights / created /
  chosen_variant / total_budget_rub`.
- **Оставлено:** day-by-day, адреса/телефоны отелей, транспорт с часами,
  аварийные контакты, бюджет — но как **summary**, без alarmist-разбора.
- **Тональность:** финальная, успокаивающая.

Почему именно так: родителю TODO и warnings читаются как «ещё не готово» и
пугают; risk-таблица с вероятностями — тревожит без пользы. Оставляем
безопасностный минимум (контакты) без alarmist-тона.

### `partner` — попутчик (спланирован)

**Зачем:** со-путешественник планирует вместе — ему нужен **полный** план
и возможность **вносить правки/выбирать**.

**Главные отличия от `self`:**
- По содержанию ≈ `self` (видит тредофы, warnings, риски, TODO — со-планирует
  на равных).
- **Формат — DOCX, не PDF:** партнёр оставляет комментарии / отмечает выбор
  (как round-trip Stage 3/4). PDF read-only здесь мешает.
- **Вырезаются только сугубо-приватные заметки** владельца (личные
  пометки Stage 3, помеченные как приватные) — не общий контент.
- **Тональность:** совместная («наш план»), не «мой план для согласования».

По сути `partner` = `self` в editable-формате минус приватные заметки.

### `guide` — гид / водитель (спланирован)

**Зачем:** местный гид или водитель получает план для **координации на
месте** — где быть, когда, что забронировано, где встреча.

**Главные отличия от `self`:**
- **Фокус на логистике:** маршрут по дням, тайминги, адреса, точки встречи,
  транспортные сегменты, что и на какие даты забронировано.
- **Убрано:** бюджет (особенно ₽-конвертация — гиду не нужна), личные
  заметки, honest assessment, методология, TODO про цены, тредофы. Из
  рисков — **только safety-релевантное** (а не «вариант B дороже на 30%»).
- **Хангыль в скобках** к топонимам (경복궁, 울산바위) — для гида особенно
  ценно: указатели, навигация, поиск в Naver/Kakao.
- **Тональность:** операционно-координационная, без планировочной «кухни».
- Возможен акцент на местный язык в адресах/названиях.

### `archive` — архив (спланирован)

**Зачем:** поездка закончилась — нужна **постоянная запись** (не для
действия, а для памяти и будущих поездок).

**Главные отличия от `self`:**
- **Максимально verbose:** включает всё, что `self`, **плюс** опционально
  фактические отклонения «план vs как получилось» и постмортем-заметки.
- **Контекст для стадий и diff'ы — сохраняются** (для archive это ценная
  история решений, а не handoff-мусор).
- **Тональность:** ретроспективная, полная.
- **Создаётся ПОСЛЕ поездки** — единственный тип, который дополняется
  фактическими данными, а не только планом.

## 4. Как добавить новый тип (когда появится кейс)

1. В отдельном модуле (не в `adapter.py` напрямую):
   `register_recipient("partner", RecipientRules(strip_sections=…,
   strip_subsections=…, strip_warnings_block=…, keep_only_yaml_fields=…))`.
2. Стадийные тонкости — `register_stage_extension(recipient, stage_id, fn)`
   (например, «для guide в Stage 5 убрать бюджетные плашки в днях»).
3. Если формат отличается (DOCX для partner) — учесть в `DEFAULT_FORMAT`
   и stage-builder.
4. Тест на `adapt_for_recipient(parsed, recipient)` — нужные секции
   вырезаны, нужные сохранены.
5. Запись в `export-design.md` §3 и обновление матрицы в этом файле.

Адаптер не модифицирует вход (возвращает новый dict через deepcopy) —
правила декларативны (`RecipientRules`), не императивный код per получатель.
