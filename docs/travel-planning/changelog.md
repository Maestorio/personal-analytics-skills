**v0.77 (2026-09-20): профиль — секция «Переносимость», два тира исключений,
классы транспорта без прав**

Источник — постмортем реальной поездки (Северный Страна Б, 09.2026, кейс 3
калибровки): семь из десяти находок разбора оказались профильными, и ни одно
из полей, которых не хватило, в шаблоне не существовало.

Что вскрыл разбор:

- «Физическая форма» описывает выносливость (шаги, перепад, лестницы) и
  ничего не говорит об условиях, при которых день перестаёт работать:
  жара с влажностью, мокрая тропа с уклоном, укачивание на серпантине,
  езда пассажиром на байке в дождь. План строил дни, опираясь на

### 2. Stage 3 RED FLAG-генератор: вторая ветка для scarce-режима

**Проблема:** RED FLAG требовал `high_neg ≥ 1` + `low_recommend ≥ 1`.
При узкой HIGH-когорте (Vietnam: 4 HIGH из 43, доля 9%) шанс что 2 HIGH-
автора независимо сойдутся на критике одного места близок к нулю →
RED FLAG-генератор не срабатывает. Далат не получил RED FLAG, хотя
из общего знания — классическая туристическая ловушка.

**Решение:** добавлена **ветка 2** в `categorize()`:
- scarce-режим И `high_recommend = 0` И `non_high_negative ≥ 3` →
  RED_FLAG.
- scarce-режим И `high_recommend = 0` И `non_high_negative ≥ 2` →
  CONTESTED.

`non_high_negative` — обоснованная критика (criticize / regret_visited)
от OUTLIER/MEDIUM/LOW. «Обоснованная» — с указанием причины в карточке
(«переполнено», «развод», «вылизано»). LLM при экстракции проставляет
тональность `criticize` только при наличии причины.

**Реализация:**
- `scripts/aggregate_pois.py`: `count_mentions()` теперь трекает
  `non_high_negative` (раньше OUTLIER/MEDIUM критика молча
  игнорировалась, LOW критика создавала `low_non_recommend` warning).
  `categorize()` дополнен веткой 2 после ветки 1, перед STRONG.
- `references/stages/stage3-poi.md` §6.4: переписан под двух-ветковую
  модель. Из не-HIGH авторов теперь извлекаются criticize/regret_visited
  упоминания (раньше только recommend от LOW).
- `tests/test_aggregate_pois.py`: +8 проверок ветки 2 (173 всего),
  обновлены LOW non-recommend проверки (criticize больше не warning,
  neutral остался).
- SKILL.md: новый mini-spec блок «Stage 3: scarce-ветка RED FLAG».

### 3. Stage 1 DR-промт: активный поиск критических отзывов

**Проблема:** DR-выборка систематически смещена в сторону «поехали —
понравилось» (selection bias: на туристическую ловушку едут люди,
которые её хотели — они её не критикуют). Это блокировало
RED FLAG-генератор downstream даже без проблемы scarce-режима.

**Решение:** обязательный блок в Stage 1 DR-промте:

- META-DIAGNOSTICS обязан отметить число critical-отчётов **по
  каждому региону** + WARNING если critical=0 хотя бы для одного.

Local-language расширение critic-фраз отложено — пока только русский.

**Реализация:**
- `references/stages/stage1-dr-prompt.md` §5: добавлены плейсхолдеры
  `{группа_архетип}` и `{seed_source_set}`.

  и «critical по регионам».
- SKILL.md: новый mini-spec блок «Stage 1: critic-фразы + seed
  source-set».

### 4. Stage 0 content_density_override

**Проблема:** профильное окно `## Частота смены локаций` («2–4 ночи на
локацию») применялось как жёсткий потолок. Argentina: Ушуая имеет
~7 ночей самодостаточного контента (парк × 2 + Бигль + Мартиаль +
город), но скилл сужал до 3 ночей — в обратную сторону даже от
скорректированного user-оптимума (~6).

**Решение:** для каждого региона Stage 0 **обязательно** проверяет,
не противоречит ли content-density профильному окну. Если регион
содержит ≥5 ночей самодостаточного контента, а профиль сужает до 4 —
подсветить override в reasoning региона с конкретной формулировкой
(«N ночей реального контента: {перечисление}, профильный max = M»).
Решение — за пользователем в `## Решение`.

**Реализация:**
- `references/stages/stage0-scope.md` §6: новый блок «Content-density
  override» с триггерами и формулировкой.
- YAML-шапка §8: новое поле `content_density_overrides[]` с регионом,
  observed/profile-max и reason для каждого override.
- SKILL.md: новый mini-spec блок «Stage 0: content_density_override».

- **Модель — два режима с автодетектом.** Sonnet+thinking для
  surgical (структура совпадает с previous_plan), Opus+thinking для
  reconstructive (нет previous_plan ИЛИ структура отличается). Mode
  детектируется детерминированно на шаге 4 потока, не вводится
  пользователем. Эскалация Sonnet→Opus при reconstructive
  предлагается одной строкой.
- **Custom variant = variant + правки.** Stage 5 семантически парсит
  блок `## Решение` Stage 4: `**Выбран вариант:**` (нормализация
  A/B/C/кастомный) + опц. `**Состав:**`/`**Почему этот выбор:**`
  (правки). Правки **встраиваются естественно в маршрут без маркеров
  в днях**; ОДНА summary-строка в `## Контекст и ключевые параметры`
  фиксирует факт правок. Текст правок **не хранится в YAML**
  отдельным полем — информация уже в `## Решение` Stage 4 и в самом
  теле финального плана.
- **Web search policy — гибрид.** Активно: расписания транспорта,
  часы работы достопримечательностей, конкретные операторы synergy-пар
  Stage 3, **имена/районы/рейтинги отелей**, сезонные ограничения.
  НЕ web search (всегда TODO): **цены отелей** (даже найденные —
  диапазон с TODO; LLM систематически занижает на 3-10×), цены
  ресторанов, цены такси, курсы валют. Лимит ~10-20 поисков на план,
  никаких систематических «на каждый ресторан».
- **Опц. MCP-расширения (Booking / Expedia).** По умолчанию не
  используется (переносимость скилла). Активируется при явном запросе
  пользователя или при активных коннекторах в среде. MCP-цены
  подставляются с пометкой «через {Booking|Expedia} MCP, YYYY-MM-DD»
  и **не заменяют TODO** — пользователь финально бронирует сам, цены
  могут измениться. В YAML фиксируется `mcp_extensions_used`.
- **9 обязательных секций output** (по методологии §9): Контекст и
  ключевые параметры (опц. подсекции «Логика ключевых решений», «Чего
  больше нет в маршруте и почему») → Шапка → Критические
  подготовительные пункты → Маршрут по дням → Сводные таблицы
  (транспорт/бюджет/гастрономия) → План реагирования на риски → Чеклист за 2
  недели → Diff с предыдущим планом (только если `previous_plan !=
  null`) → TODO для верификации (3 категории: before-booking /
  2-weeks-before / in-trip). Адаптивное сжатие не делается; при
  размере, не вмещающемся в один ответ — split на
  `5_final_plan_part_b.md`.
- **Уровень детализации дня — иконки** (по образцу
  `vietnam_north_v4_calibrated.md`): 📍 переезд → 🏨 отель → 🎯
  программа с часами → 💰 бюджет дня → ⚠️ риски/swap. Иконки только
