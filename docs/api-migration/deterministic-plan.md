## A. Загрузка портфеля без LLM

### Что сейчас делает LLM в скилле

Вычисления уже детерминированные (`parse_portfolio.py` → `portfolio_returns.py` → `per_security_xirr.py`
→ `moex_quotes.py` → опц. `iis_returns.py` → `assemble_snapshot.py` → `decision_journal_update.py`).
Модель только оркестрирует:

1. Определяет, какие файлы приложены (полный, returns-only или holdings-only снапшот).
2. Гоняет команды и выбирает фолбэки (`--no-moex`, `--cbr-offline`) при сбоях сети.
3. Копирует в `/tmp` предыдущий снапшот и `sector-overrides.yaml`; ищет выгрузку ИИС-3.
4. Реагирует на флаги, требующие решения владельца: `cash_drift_changed` (перегнать с
   `--rebaseline-cash`?), `iis_returns_mismatch` / `iis_composition_changed` (нужна свежая выгрузка).
5. Спрашивает «сохранить?», пишет снапшот, запускает журнал решений.

Всё это — правила, а не суждение. Значит, переносится в код целиком.

### Этапы

| Этап | Что | Входы | Выход этапа | Оценка |
|---|---|---|---|---|
| 0 | Инвентаризация полей снапшота и образцы выгрузок | — | таблица «поле → источник» | S |
| 1 | Оркестратор + проверки качества | как сейчас (с Numbers) | `build_snapshot.py`, `checks.py`, тесты | M |
| 2 | Теневой период: скилл против скрипта | как сейчас | 2–4 зелёные сверки | 2–4 недели календаря, работы S |
| 3 | Уход от Numbers | IntelInvest + `Portfolio/plan.yaml` | 2–4 зелёные сверки «с Numbers / без» | M–L |
| 4 | Веб: загрузка через вьюер, редактор плана | только xlsx | `/api/pf/*`, UI | M |
| 5 | Переключение скилла, вывод Numbers | — | SKILL.md на скрипте, справки | S |

Этапы 2 и 3 — ожидание реальных прогонов; в это время делается **B** (eShop).

### A.0. Инвентаризация (до кода)

- Таблица «каждое поле `portfolio-*.json` → откуда сейчас (Numbers / trades / MOEX / ЦБ / overrides /
  ручной реестр) → откуда будет → кто читает ниже по цепочке». Поля, завязанные на Numbers, читают
  многие файлы вне загрузчика: `ie_model`/`ie_actual`/`ie_summary`, `goals_matrix`, `balance_summary`,
  `plan_bucket_key`, `user_plan` — от 6 до 15 файлов каждое.
- Образцы выгрузок IntelInvest: сделки, сделки ИИС-3, **«текущий портфель» (`common_portfolio_*.xlsx`)**.
  Проверить, есть ли в ней остаток денег по счетам. От этого зависит, как считать кэш без Numbers (§A.3).

### A.1. Оркестратор `scripts/build_snapshot.py`

- Один CLI: `--trades`, `--iis-trades` (опц.), `--balance` (опц., до этапа 3), `--memory <Claude-Memory>`,
  `--out <staging>`, `--replay <bundle>` (§A.2).
- Сам находит предыдущий снапшот, `sector-overrides.yaml`, последнюю выгрузку ИИС-3; выбирает режим
  по набору файлов; при сбое сети повторяет и уходит в фолбэк с флагом.
- Выход: снапшот в staging + `build-summary.json`: позиции, XIRR, флаги на русском, **решения владельца**
  (`cash_drift_changed` → перебазировать?; ИИС-3 → нужна выгрузка) и результат проверок (§A.5).
- `--commit`: перенос на место + `decision_journal_update.py`; без флага — сухой прогон.
- **Архив входов:** каждый прогон кладёт входные xlsx и ответы сети в `Portfolio/inputs/<дата>/`. Это нужно
  для повтора (§A.2), разбора инцидентов и замены `docs/investment/source/` на Mac, откуда сейчас
  берётся последняя выгрузка ИИС-3.
- Заодно: убрать устаревший `scipy` из `pip install` в Шаге 3 SKILL.md (в скриптах не импортируется).

### A.2. Сверка «скилл против скрипта» (этапы 2 и 3)

**Принцип — повтор на тех же входах.** Если скрипт отдельно сходит в MOEX через 10 минут после скилла,
цены разойдутся и сверка утонет в шуме. Поэтому скрипт берёт ответы сети, записанные прогоном скилла.

1. **Пакет прогона.** На теневой период в Шаг 6 SKILL.md временно добавляется: «сохрани входные файлы,
   `/tmp/quotes.json`, `/tmp/returns.json`, курсы ЦБ, `prev_snapshot`, overrides и итоговый снапшот
   в `Portfolio/parity/<дата>/`». Прогон скилла не меняется, только сохраняет пакет.
2. **Повтор.** `build_snapshot.py --replay Portfolio/parity/<дата>/` строит снапшот без сети.
3. **Сравнение** — `scripts/parity_check.py A.json B.json`:
   - канонизация: ключи по алфавиту, списки — по ticker/ISIN/account, служебные поля (`generated_at`
     и т. п.) исключаются по явному списку;
   - точное совпадение: количества, статусы, флаги, счета, даты, сектора;
   - допуск для денег и долей: 0,01 ₽ и 1e-9 относительный (порядок операций с плавающей точкой);
   - отчёт: «совпало / в допуске / расходится» с путём поля и значениями; код выхода ≠ 0 при
     «расходится»;
   - **список известных расхождений** с причиной: правило, а не исключение по факту. Пример для
     этапа 3 — кэш (§A.3).
4. **Критерий переключения:** 2 подряд прогона без «расходится», всего не меньше 2–4. Среди них хотя бы
   один со сделками за период, по возможности один с фолбэком сети или с ИИС-3.
5. Пакеты и отчёты сверки остаются в `parity/` — это доказательство, на котором держится переключение.

**Этап 3 тем же инструментом:** на одних входах строятся снапшот «с Numbers» и снапшот «без Numbers»
(IntelInvest + `plan.yaml`), сверка с отдельным списком известных расхождений.

**Ретро-проверка (по желанию):** если на Mac сохранились старые выгрузки из `docs/investment/source/`,
можно пересобрать 1–2 прошлых снапшота с ценами из самих этих снапшотов. Это приблизительно
(облигационные поля MOEX не восстановить), только как дымовой тест до теневого периода.

### A.3. Уход от `Общий баланс.numbers` (этап 3)

Что Numbers даёт сейчас и чем заменяется:

| Данные из Numbers | Замена | Риск |
|---|---|---|
| Количества и стоимость позиций | уже из сделок (`returns.json`) + MOEX — Numbers и сейчас запасной | нет |
| **Кэш**: строка «Имеется (RUB)» − стоимость позиций | восстановление из сделок (`cash_reconciliation.reconstructed_cash_rub` уже считается) **или** остаток денег из `common_portfolio_*.xlsx`, если он там есть (A.0) | **главный**: исторический разрыв ≈340 тыс. ₽ (пополнения прошлых лет вне выгрузки). Закрыть один раз записью «начальный остаток» в `plan.yaml` с датой и обоснованием; дальше проверка дрейфа |
| Разбивка ИИС-3 / основные счета | отдельная выгрузка ИИС-3 (уже используется): позиции ИИС = из неё, основные = всё − ИИС | средний: выгрузка ИИС-3 приходит только после операций по счёту — переносится из архива `inputs/` |
| Плановые доли, веса Invest Era (`IE New/Old`), заметки «План/Статус/IE/AI» | `Portfolio/plan.yaml`, правка на странице | средний: много потребителей — поля снапшота сохраняются **с теми же именами**, меняется только источник |
| Облигации: `Тип`, `Подтип`, `Рейтинг`; «План по облигациям» по корзинам | `plan.yaml` (MOEX рейтингов не даёт) | низкий |
| Сектора (у баланса приоритет над overrides) | `sector-overrides.yaml` на все бумаги, разово дополнить из Numbers | низкий |
| FINAMAR — ручная оценка | `plan.yaml` → `manual_valuations` с датой | низкий |
| `errors_check` («Есть в IntelInvest, нет в Акция») | новая проверка: бумага в сделках без записи в `plan.yaml` | нет |
| «Пополнение» и «Итого» (план на горизонт) | `plan.yaml` | нет |

Шаги этапа 3:

1. Схема `plan.yaml` + валидатор (Python и зеркало в JS для страницы — как у рецептов в «Еде»).
2. Разовый перенос: скрипт `migrate_numbers_to_plan.py` читает последний `Общий баланс.numbers` и пишет
   `plan.yaml`, расхождения показывает списком.
3. Загрузчик: без `--balance` берёт `plan.yaml`; **контракт снапшота не меняется** (те же поля
   `ie_model`, `goals_matrix`, `balance_summary`, …), downstream не трогается.
4. Теневой период «с Numbers / без» (§A.2), 2–4 прогона.
5. После зелёной сверки: `numbers-parser` уходит из зависимостей, `parse_portfolio.py` — в легаси-режим
   (только для ретро-пересборки старых снапшотов).

### A.4. Тот же контейнер `hub-api` — в чём разница и почему получится

| | Тот же `hub-api` | Отдельный контейнер |
|---|---|---|
| Запись на место | своим клиентом File Station напрямую | через внутренний вызов `hub-api` |
| Зависимости | том с `openpyxl` (как у `hub-notify`) | свой образ или том |
| Сбой загрузчика | не должен ронять единственного писателя → **запуск подпроцессом** с таймаутом и лимитом памяти | изолирован сам по себе |
| Обновление загрузчика | перезапуск `hub-api`: на секунды недоступна запись «Еды» и «Здоровья» | `hub-api` не трогается |
| Деталей в compose и deploy | меньше | больше |

Почему получится: после отказа от Numbers из зависимостей остаётся только `openpyxl`. Это чистый Python,
на alpine ставится без сборки. `numbers-parser` (protobuf, snappy) был бы главной проблемой
alpine-образа. `hub-api` уже многопоточный (`ThreadingHTTPServer`), долгую сборку держит фоновая задача.

Значит: этапы 1–3 работают локально и в скилле; веб (этап 4) — в `hub-api` подпроцессом. Если до
этапа 4 Numbers ещё нужен, веб принимает только xlsx-экспорт баланса из Numbers.

### A.5. Проверки целостности и качества (`scripts/checks.py`, этап 1)

Три уровня: **блок** — не сохранять; **предупреждение** — сохранить с флагом и показать;
**инфо** — в сводке. Каждая проверка — отдельная функция с тестом и строкой в `docs/test-registry.md`.

**Входные файлы**
- Тип и размер, наличие листов и колонок выгрузки IntelInvest (схема выгрузки), понятные сообщения
  при смене формата. — блок
- Неизвестный тип операции, неизвестная валюта, сделка в будущем, дубликаты сделок
  (дата + бумага + количество + сумма). — блок / предупреждение
- Свежесть: последняя сделка и дата в имени файла против сегодня; файл тот же, что в прошлый раз
  (хеш) → «ничего нового». — предупреждение / инфо
- Выгрузка ИИС-3: номер счёта тот, бумаги ИИС есть в общей выгрузке. — блок

**Позиции**
- Отрицательное количество после восстановления позиций. — блок
- Сверка с прошлым снапшотом: количество = прошлое ± сделки между датами; бумага исчезла без
  продажи; новая бумага без сектора или записи в плане. — предупреждение
- Скачок стоимости позиции сверх движения цены и сделок. — предупреждение
- Сплит: изменение количества без сделки при цене ×N → «похоже на сплит, нет в `KNOWN_SPLITS`». —
  предупреждение (связь с PDL-A)
- Уже есть, переносятся в общий отчёт: `avg_cost_fallback_value_over_qty`, сверка
  `balance_vs_trades`, статусы blocked/distressed.

**Кэш**
- Кэш не отрицательный ни по одному счёту. — блок
- Дрейф восстановленного кэша против базы > 10 тыс. ₽ (существующий `cash_drift_changed`) →
  решение владельца. — предупреждение
- Без Numbers: восстановленный кэш против остатка из `common_portfolio_*.xlsx` (если он там есть,
  A.0). — предупреждение
- Валютные конвертации сходятся (рубли ушли — валюта пришла); фонды ликвидности (LQDT/TMON/TPAY)
  в `liquid_rub`, FINAMAR — нет. — предупреждение

**Сеть и котировки**
- Доля позиций с котировкой MOEX; котировка старше последней торговой сессии; облигации без НКД
  или купона. — предупреждение
- Дата курсов ЦБ; офлайн-кэш курсов → флаг. — предупреждение

**Итоговый снапшот**
- Валидатор схемы v2 по `references/output-schema.md`. — блок
- Инварианты: позиции + кэш = итог; доли в сумме 1 (допуск); нет NaN и бесконечностей;
  XIRR в разумных границах. — блок / предупреждение
- Идемпотентность: повтор на тех же входах даёт тот же хеш (тест, не проверка прогона).

### A.6. Веб (этап 4)

- **Загрузка через вьюер:** файл отправляется сырым телом запроса, имя — заголовком (без multipart:
  модуль `cgi` в stdlib устарел). Лимит размера, проверка, что это xlsx (zip-сигнатура).
  Файлы ложатся в `Portfolio/inputs/<дата>/`.
- `POST /api/pf/upload` → `POST /api/pf/build` (асинхронно, блокировка от параллельного запуска,
  таймаут) → `GET /api/pf/status` (ход сборки, `build-summary.json`) → `POST /api/pf/commit`
  (подтверждение + ответы на решения, например перебазирование кэша).
- Caddy: `/api/pf/*` — под паролем с любого IP, как `/api/hd/*`.
- Окно во вьюере: выбор файлов → ход сборки → сводка, проверки по уровням, вопросы-решения →
  «Сохранить». Блок-проверка выключает кнопку.
- Редактор `plan.yaml` (этап 3) на странице с валидатором и `base_hash`.
- `tools/deploy.zsh`: выкладка скриптов загрузчика на NAS (сейчас скрипты скиллов не выкладываются).
- Справки: `tools/viewer-help.md` **и** `docs/investment/portfolio-workflow-guide.md` (правило двух
  зеркал), строка в `tools/assets/help/hub.md`.

**Что остаётся ручным:** `KNOWN_SPLITS` и `KNOWN_POSITION_STATUS` (автоопределение сплитов — PDL-A
в `docs/investment/TODO.md`).

## M. Макросрезы: та же сверка (задача API-1c)

`macro-ru-watcher` уже на 5/7 скрипт (`fetch_macro.py`); через поиск идут инфляция и Brent.

1. Скрипт `build_macro.py`: `fetch_macro.py` + Brent + инфляция из **тех же первоисточников, что

   JSON и тот же markdown `ru-<дата>.md`.
2. Сверка на 2–4 еженедельных срезах. Скрипт запускается в тот же день, что и скилл; сравнение по
   значениям, разобранным из таблицы markdown:
   - MOEX и ЦБ: совпадение при одинаковом `as_of`;

   - diff и z-score: точно при одинаковой истории;
   - разный `as_of` из-за выходных — отдельная категория, не ошибка.
3. Шаг 6 скилла (строка `[macro]` в памяти Claude) скрипт сделать не может. Решить: отказаться или
   оставить обновление памяти за `memory-sync`.
4. После переключения: запуск по расписанию в `hub-notify`, запись через `hub-api`.

## B. Цены US eShop без LLM

### B.0. Что нужно решить по правилу

В `docs/game-advisor/CLAUDE.md` два правила, которые скрипт формально нарушает:

- «исполняемых скриптов и тестов нет» — снимается, это описание, а не запрет;
- «цены — только из fetched-страниц» — по смыслу это «цена только из первоисточника, прочитанного
  сейчас, не из памяти модели». Скрипт читает цену раньше (по расписанию), а скилл берёт её из файла.

Решение (2026-10-20): **скилл доверяет `eshop-prices.json` не старше 24 ч.** Старше — скилл сам идёт
в веб, как сейчас. В выдаче скилла рядом с ценой — источник и время чтения.

### Источник

- Недокументированный эндпоинт цен Nintendo `api.ec.nintendo.com/v1/price`
  (параметры `country=US`, `lang=en`, `ids=<nsuid,…>`). Отдаёт обычную цену и скидку с датами
  начала и конца. Им пользуются сторонние библиотеки (nintendeals) и агрегаторы; гарантий
  стабильности нет.
- Нужен **nsuid** игры для американского региона: nsuid другого региона даёт цены другого региона.
- Из облачного контейнера 2026-10-20 эндпоинт проверить не удалось (прокси 403) → **шаг B1**.

### Шаги

**B1. Проверка с NAS или Mac** (XS): один `curl` на известный nsuid; зафиксировать формат ответа,
лимит id в запросе, поведение на неизвестном id. Не работает → план B откладывается, скилл как есть.

**B2. Поля в `Gaming/watchlist.yaml`** (S, риск 2 — схема)
- `nsuid_us` — заполняет скилл один раз при добавлении в watchlist.
- `price_target_usd` — числовой порог вместо свободного текста `condition` («ждёт скидку ≤ $24.99»);
  разовая миграция скиллом; `condition` остаётся для нечисловых условий (формат, порт).
- Нет `nsuid_us` → запись пропускается с флагом, цена не выдумывается.

**B3. Загрузчик `tools/hosting/notify/eshop.py`** (S–M, риск 1; ред. 3: инфраструктура сайта в `hub-notify`, скилл только читает файл)
- Вход: `watchlist.yaml` (статусы `хочу`, `на-карандаш`); выход: `Gaming/eshop-prices.json` —
  `fetched_at`, по каждой игре обычная цена, цена со скидкой, % скидки, конец скидки, источник, `target_met`.
- Ошибка сети или формата → `status: unavailable`; старые цены не выдаются за свежие.
- Тесты без сети: разбор записанного ответа, порог, неизвестный nsuid, сменившийся формат → громкий флаг.

**B4. Расписание и кнопка** (S): раз в сутки в 08:30 МСК в дневном тике `hub-notify` (повтор в 09:00 при
неудаче), запись через `hub-api` (`/api/save`); кнопка «Обновить цены» → `POST /api/games/eshop-refresh`
(не чаще раза в 10 мин); push, когда `target_met` впервые стал true: «X: $19.99 до 03.11».

**B5. Страница и скилл** (S): `games.html` — цена, бейдж скидки, «до DD.MM», «порог выполнен»;
SKILL.md режимы 4/4a — свежий файл первым источником US-цены; справка `tools/assets/help/games.md`;
правка правила в `docs/game-advisor/CLAUDE.md` (B.0).

**Вне плана:** московские магазины (JS-каталоги, Авито — дешевле оставить скиллу); DekuDeals
(агрегатор, не первоисточник).
