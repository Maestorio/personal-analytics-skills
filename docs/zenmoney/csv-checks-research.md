# Исследование: выгрузка CSV на сайт — политика записи и проверки до сохранения

**Статус: ТЗ, не начато. Исполнитель — локальная сессия на Mac (нужны выгрузки `docs/zenmoney/source/`
и `Claude-Memory/ZenMoney/audit/`).** Результат — таблица проверок с бэктестом (§4) и уточнённые задачи
3.6/3.7 `docs/no-ai-mode/START.md`. Код не пишется до решения владельца по таблице.

Два сценария владельца, которые должны работать с сайта без Claude:

1. **Ретроспективный пересчёт.** Категории и места исправлены в ZenMoney → новая выгрузка → итоги
   записанных месяцев, поездок и разбивка категорий приводятся к выгрузке.
2. **Закрытие нового месяца.** Выгрузка за новый месяц → проверки до записи → запись итогов.

## 2. Политика записи (предложение; утверждает владелец)

Источник правды — ZenMoney, CSV — его слепок, руками не правится. Отсюда:

| Правило | Следствие |
|---|---|
| CSV главнее записанных итогов | месяц, где итог или разбивка отличаются, перезаписывается — но только после показа diff и явного «да» |
| Diff обязателен | по месяцу: итог расход/доход, разбивка категорий, поездки; по операциям: добавлено / изменено / **удалено** (ключ операции без id — хеш `дата+сумма+счёт+категория+комментарий`, сравнение множеств с прошлой выгрузкой) |
| Расхождение классифицируется | «объяснимое» (есть изменённые или новые операции после записи, перекладка категорий) / «необъяснимое» (итог изменился без изменённых операций) → второе — стоп до разбора |
| Полнота выгрузки проверяется до всего | первая и последняя дата, число строк против прошлой выгрузки, нет «дыр» по месяцам: неполный экспорт (фильтр по датам) иначе выглядит как массовые удаления |
| Запись с копией и пометкой | `.versions/` (сайт) или `*.before-*` (терминал), поля `source: csv`, `recomputed_at`, хеш выгрузки |
| Жёсткие стопы | потеря тега поездки; необъяснимое расхождение; удаления в записанном месяце без подтверждения; неполная выгрузка |

## 4. Метод бэктеста и порог приёма

1. Прогнать каждую проверку по всем месяцам, доступным в прошлых выгрузках `docs/zenmoney/source/`
   (минимум 12 месяцев), на том состоянии данных, какое было на дату выгрузки.
2. Эталон ошибок: аудиты `ZenMoney/audit/history.json` (реестр замечаний «проверка:ID»), `accepted.json`
   («это норма»), записи README «что вошло» по датам выгрузок (найденные и исправленные ошибки), память
   владельца о правках.
3. На каждую проверку: срабатываний на месяц, из них подтверждённых ошибок, точность.
4. Порог: точность ≥ 50 % → предупреждение (показывать до записи); ≥ 80 % и ошибка искажает итог месяца →
   стоп; ниже 50 % → подсказка или снять. Класс из §3 — исходное предположение, бэктест его меняет.

Результат — таблица §3 с колонками «срабатываний / подтверждено / класс после бэктеста», затем правки
задач 3.6 (политика записи, diff, «да») и 3.7 (набор проверок «Качества учёта» из CSV).

## 4а. Результаты бэктеста 2026-11-10

Цепочка из 15 выгрузок `docs/zenmoney/source/` (2026-10-07 … 2026-11-01), на каждую — проверка трёх последних
закрытых месяцев на состоянии данных этой выгрузки; суррогат эталона — «то же измерение операции изменено в
какой-либо следующей выгрузке» (категория, место, дата, удалена/изменена сумма или счёт; для N2/N9/B6' — сдвиг
итога месяца, категории или счёта). Срабатывания, впервые замеченные в последней выгрузке, не оцениваются.
Подробная таблица — в таблице §3 выше.

- Подтверждение выше 50 % ни у одной проверки при заметной выборке нет; стопа (≥ 80 %) не заслужила ни одна:
  у A4 и P4 одно срабатывание и одно подтверждение — выборка не годится для вывода. Класс «предупреждение» —
  только у A3 и A4 (реестр `history.json`: по одному исправленному замечанию). Остальное — подсказки.
- A5: 11 срабатываний, подтверждено 1; в реестре аудита 38 замечаний A5 приняты как «норма» и ни одно не
  исправлено — проверка шумит на законных повторных покупках; N1 (15 / 0) и N5 (14 / 0) — тоже. Снять или сузить.
- N2: сетка k = 2 / 3 / 4 / 5 даёт 18 / 15 / 12 / 5 срабатываний и 6 / 6 / 4 / 1 подтверждённых — выбрано k = 3
  (максимум подтверждений при минимуме шума, точность 40 %).
- P3 — 63 срабатывания, 31 подтверждено (49 %): место с сырым текстом банка владелец обычно переименовывает.
  Самая полезная новая проверка, но под порогом 50 % и не искажает итог — подсказка.
- Не сработали вообще (A1, N2i, N3, N6, N7, N9): либо данные чисты (владелец исправляет по ходу), либо нечего
  ловить (нет категории-перевода, две стабильные категории дохода). Эталона нет → по §4 «подсказка».

Оговорки (честно): (1) суррогат — не истина: владелец правит не всё и не сразу, неисправленное не значит «не
ошибка», а правка мимо проверки — не подтверждение; (2) выгрузки покрывают четыре недели, три закрытых месяца на
выгрузку и ~12 дней правок — для N2, N9 и B6' (нужен целый новый месяц с ошибкой) эталон слабый; (3) часть
цепочки — девять выгрузок за один день 2026-10-07, это почти одно состояние; (4) совпадение с реестром `history.json`
возможно только для A2–A5 (по ним в реестре 1 / 1 / 38 замечаний); (5) подтверждение «операция удалена или
сумма/счёт изменены» для A5, N1, P2, N7 не различает удаление и правку; (6) N6, N7, N9, N3 проверены только
тестами на синтетике. Повторить бэктест после первых реальных закрытий месяца через сайт: тогда у каждого
срабатывания будет настоящий ответ владельца.
