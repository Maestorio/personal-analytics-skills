## 1. Модель данных

### 1.1 `labs.json` — контракт `health-labs@1` (сборка)

```json
{
  "schema": "health-labs@1",
  "generated": "2026-07-16",
  "person": { "sex": "m", "birth_year": 1988 },
  "biomarkers": [
    {
      "id": "glucose_fasting",            // slug, ключ справочника
      "name": "Глюкоза натощак",           // канон (дубли имён слиты)
      "category": "biochem",               // enum категорий, см. 1.2
      "unit": "ммоль/л",
      "series": [
        { "date": "2025-10-14", "value": 4.94,
          "ref": {"low": 4.1, "high": 6.0},   // либо {"op":"<","v":21}
          "status": "norm",                    // norm | high | low | na
          "lab": "Гемотест", "source": "ornament" }
      ]
    }
  ]
}
```

Конвертер — `Health/программы/build_health_json.py` (stdlib):
- разовая аккуратная конвертация `master_labs.csv` → `labs.json`
  (даты DD.MM.YYYY → ISO; референсы «35 − 50» → числа, «< 21» → односторонний;
  статусы → enum; пол/возраст → `person`, из строк убрать);
- **канонизация имён**: словарь синонимов (один маркер из разных лабораторий /
  выгрузок называется по-разному) — дубли сливаются в один id;
- **разметка категорий**: словарь id → категория (собрать при реализации);
- дальше — режим merge: новая выгрузка Ornament подмешивается по ключу
  (id, date), существующее не перетирается; валидация схемы, отчёт о новых
  строках. Никаких LLM-чисел — детерминированный data layer
  (по образцу portfolio-data-loader).

CSV остаётся мастером и историческим сырцом. Аналитические скрипты
`Health/программы/*.py`, читающие `master_labs.csv`, переводятся на
`labs.json` через общий мини-loader-модуль — отдельный пункт фазы
реализации, страницу не блокирует.

### 1.5 `meds.json` — контракт `health-meds@1` (живое, ДВА писателя)

> **ПЕРЕСМОТРЕНО 2026-07-17 (§6-фаза).** Схема ниже — **фактическая**.
> Прежняя редакция §1.5 описывала вложенные `user`/`ref`, которые **никогда не
> были отгружены**: победил плоский набор полей дизайна (решение §0 —
> «поля аптечки `inn`/`class`/`prescribedBy`/`timing`/`regimen` … их в плане не
> было, они полезны»). §1.5 за этим решением не обновили, и §6 унаследовал
> несуществующую модель. Историческая редакция — в git.

**Схема плоская.** Ни `user`, ни `ref` в файле нет:

```json
{
  "schema": "health-meds@1",
  "updated": "2026-07-17",
  "meds": [
    {
      "id": "atorvastatin",
      "name": "Аторвастатин",      // ┐
      "dose": "20 мг",             // │
      "regimen": "", "timing": "", // │ поля ЧЕЛОВЕКА — пишет страница,
      "form": "", "taking": true,  // │ скилл не трогает никогда
      "prescribedBy": "",          // │
      "expiry": "", "notes": "",   // ┘
      "inn": "",                   // ┐
      "class": "", "for": "",      // │ поля СПРАВКИ — пишет скилл health-meds
      "indications": "",           // │ (форма страницы их тоже показывает!)
      "interactions": "",          // │
      "affects": [],               // ┘ id биомаркеров из labs.json
      "ref_meta": {                // ПРОВЕНАНС — аддитивно, только скилл
        "filled_at": "2026-07-17",
        "confidence": "high|medium|low",
        "fields_filled": ["inn", "class"],
        "sources": [{"title": "…", "url": "…", "fetched": "2026-07-17"}]
      }
    }
  ]
}
```

**Разделение пространств имён не работает — и не работало бы.** Форма правки
страницы включает поля справки (`Показания`/`Взаимодействия` с подписью
«заполняет скилл» — но редактируемые), а сохранение шлёт **файл целиком**.
Поэтому безопасность держится не на структуре, а на правилах в
`skills/health-meds/scripts/validate_meds.py`:

1. `merge_ref` пишет только в поля справки; попытка тронуть поле человека
   отклоняется и попадает в отчёт;
2. непустое поле справки **без `ref_meta`** = заполнено рукой → не
   перетирается (нужен явный `--overwrite-manual`);
3. заявленное в `fields_filled` ⇒ непустые `sources`. Факт без источника —
   blocking.

`ref_meta` аддитивен и переживает правку со страницы: `med-save` делает
`Object.assign({}, S.medEdit, {…})`, то есть мержит поверх записи, а не
пересобирает её из полей формы (зафиксировано тестом в
`test_pages_contracts.py` — замена на пересборку молча съедала бы провенанс).

- Бейдж «справка не заполнена» страница считает сама:
  `enriched = !!(inn || class || indications || interactions)`. Никакого
  `ref: null` не существует.
- `affects` (не `affects_biomarkers`) связывает вкладки: в карточке маркера —
  «Препараты, влияющие на показатель».
- `interactions` — **строка прозой**, не список объектов: страница рисует её
  одним блоком warn-стилем.
- **Полей `atc` / `standard_dose` / `storage` / `shelf_after_open` нет** — их
  негде показать. Нужны → сначала поля на странице + в валидаторе сайдкара.
- Страница НЕ создаёт файлы: `meds.json` и `vaccinations.json` заводятся

### 2.2 Caddy + compose

- **compose**: `caddy` получает третий volume
  `/volume1/homes/hubuser/Claude-Memory/Health:/srv-health:ro`;
  **`hub-api` — тот же каталог на запись**:
  `/volume1/homes/hubuser/Claude-Memory/Health:/srv-health`.
- **Чтение**: в `route` (после `basic_auth @private`) —
  `handle /health-data/*` → `root * /srv-health` + `uri strip_prefix
  /health-data` + `file_server`. Путь не в публичных списках → под
  `@private`/`@private_fetch*` автоматически: пароль всегда, фоновый fetch без
  креда → тихий 403 (попапов на хабе нет).
- **Запись — новый префикс `/api/hd/*`** (health-data). Почему не текущие
  `/api/file|save`: (а) `GET /api/health` уже занят healthcheck'ом сайдкара —
  коллизия имени; (б) главное — зону нельзя выбрать по телу запроса: у
  `POST /api/save` ресурс лежит в JSON-body, Caddy его не видит, значит
  «здоровье = пароль всегда» не навесить. Отдельный URL-префикс решает обе.
- **Зона `/api/hd/*` — пароль с ЛЮБОГО IP** (в отличие от travel-правок,
  свободных с доверенных IP): здоровье приватно и на чтение, и на запись.
  Правки: `@api_trusted` получает `not path /api/hd/*` (иначе LAN проглотит
  health-запросы мимо пароля); новый `@api_health { path /api/hd/* }` →
  `basic_auth` → `reverse_proxy hub-api:8000`. Существующее правило тихого
  403 на fetch без креда (`@api_fetch_noauth`, path `/api/*`) покрывает и его.
- **Дыра, которую это закрывает**: без правки `@api_trusted` любое устройство
  в LAN могло бы ПИСАТЬ аптечку, не имея права её ПРОЧИТАТЬ.
- **`server.py`**: второй корень `HEALTH_ROOT=/srv-health`, эндпоинты
  `GET /api/hd/file?path=` + `POST /api/hd/save` (та же механика: base_hash →
  409 при гонке, бэкап в `.versions/`, атомарная запись, лимит), whitelist
  `meds.json` + `vaccinations.json`, только существующие файлы. Плюс:
  **валидация схемы перед записью** — сайдкар отклоняет структурно битый JSON
  (`400`), чтобы кривая правка не сломала страницу.
- **Страница** `tools/health.html` — публичная ОБОЛОЧКА (добавить в
  исключения обоих матчеров `@private*`), данные тянет с явным
  `Authorization` из `localStorage["hub-auth"]` + `credentials:'omit'`
  (паттерн вьюера v2.9.0); без токена — форма входа, как во вьюере.

**Вкладка «Анализы»**:
1. Сводка: всего маркеров / измерений / свежесть / N вне нормы.
2. «Требует внимания» — маркеры, у которых ПОСЛЕДНЕЕ значение вне нормы,

   отклонений из справочника, связанные лекарства (`affects_biomarkers`),
   дисклеймер.

**Вкладка «Прививки»**: таблица (дата · вакцина · от чего · доза ·
следующая), кнопки «Добавить» / «Редактировать» / удалить, статус-чип
«через N дней» / «просрочено».

**Вкладка «Аптечка»**:
- фильтры-чипы: «принимаю» / «все» / «истекает срок»;
- строка/карточка: галочка **«принимаю»** (мгновенное сохранение), название +
  бренд, форма, доза/режим, срок годности с чипом, бейдж «справка не
  заполнена» при `ref: null`;
- кнопка **«Добавить лекарство»** → форма полей `user` (название обязательно,
  остальное опционально);
- **«Редактировать»** → та же форма;
- раскрытие карточки: справочная часть `ref` **только для чтения** —
  действующее вещество, назначение, стандартная дозировка, хранение,
  предупреждения, взаимодействия (подсветить те, что с другими `taking:true`),
  связанные биомаркеры, источники + «заполнено скиллом <дата>»;
- сохранение: весь файл + `base_hash` → `POST /api/hd/save`; **409** →
  «данные изменились, обновите страницу» (гонка со скиллом/другим устройством);
  без токена/прав → read-only витрина (та же деградация, что в travel Stage 3).
- Футер с версией (health v1.0; правило версий страниц).

Отличия от Ornament (сознательные): «требует внимания» первым экраном;
нормированная позиция в референсе (сравнима между маркерами); спарклайны
прямо в списке; связка «лекарство ↔ биомаркер»; всё офлайн/приватно,
без подписок.

своя лестница источников.

**Вход/выход**: Transport B (Synology) —
`SynologyDrive-home/Claude-Memory/Health/meds.json`. Никакого web-API: скилл работает
с файлом напрямую через Read/Write.

⚠ `transport-layer` описывает пути внутри `Ext_gDrive` — **к health они не
относятся** (§0.2: два разных `Claude-Memory`). Запись аптечки по путям
transport-layer утечёт медданные в Google-синк; в `SKILL.md` это вынесено в
шапку и в pre-emit checklist.

**Процедура** (реализована в `SKILL.md`):
1. Читает `meds.json` + `labs.json`, гоняет `validate_meds.py validate`. Очередь:
   записи без справки (`pending_ids`); `--refresh` → справка старше года
   (`stale_ids`). Ручные записи (справка есть, `ref_meta` нет) — вне очереди,
   упомянуть и спросить.
2. Для каждого лекарства ищет справочные данные (WebSearch/WebFetch;
   приоритет — ГРЛС, DailyMed, SmPC, инструкция производителя; лестница
   источников — `references/sources.md`, по образцу game-advisor).
   **Не выдумывать**: неподтверждённое поле не заполняется и не заявляется
   в `fields_filled` (в `enrich` передаётся `null`). `confidence` по качеству
   источника; каждый заявленный факт → `ref_meta.sources`.
3. Перепроверка (требование «внимательно и аккуратно»): второй проход —
   сверка заполненного с источником заново, не по памяти; расхождение →
   первичка выигрывает, `confidence` вниз на ступень, упомянуть в отчёте.
4. Взаимодействия считаются парами среди `taking: true` — на странице
   подсвечиваются только активные. Пара с непринимаемым — в отчёт, не в файл
   (`taking` изменится, текст останется врать).
5. `affects` — только id, реально существующие в `labs.json` (иначе битая
   ссылка между вкладками; валидатор проверяет — blocking).
6. **Запись**: `validate_meds.py merge` перечитывает файл (страница могла его
   изменить), сливает ТОЛЬКО поля справки, валидирует результат и пишет
   атомарно — и то лишь при `--apply` и зелёной валидации. По умолчанию
   dry-run. Валидация — в скрипте, не в прозе (правило репозитория: защита
   контрактов от model drift; здесь оно же не даёт модели уговорить себя
   записать догадку).
7. Дисклеймер в выводе: справочно, не медицинская рекомендация; дозировки —
   из инструкции, а не рекомендация к приёму.

## 12. Давление и пульс: два входа, один вид (2026-11-02)

**Решение владельца — «файл вносит скилл, остальное — руками»:**
- **Ручной замер** (тонометр дома, «померил у врача без бумаги») — форма на
  странице → `vitals.json`, массив `bp[]`. Писатель — только страница
  (write-API, `base_hash`), как у веса. Через чат с Claude ручные замеры НЕ
  вносятся (иначе у `vitals.json` второй писатель).
- **Файл** — документ клиники (как сейчас, `intake.py`) и **экспорт Apple
  Health** (`export.zip`/`export.xml`, новый режим `health-labs`) →
  `labs.json`, ряды `exam_bp_sys`, `exam_bp_dia`, `exam_pulse`. Писатель —
  только скилл.

**Контракт `vitals.json` (`health-vitals@1`, поле добавляется, версия схемы не
меняется — старые читатели игнорируют):**
`bp: [{ "id": "bp_YYYYMMDD_HHMM", "date": "YYYY-MM-DD", "time": "HH:MM"|null,
"sys": int, "dia": int, "pulse": int|null, "note": "" }]`. Валидатор
server.py: `sys` 60–260, `dia` 30–160, `sys > dia`, `pulse` null или 25–250,
`id` уникален. Поле `bp` необязательно (файл без него валиден).

**Импорт Apple Health:** давление — корреляции `HKCorrelationTypeIdentifierBloodPressure`
(систолическое/диастолическое внутри); пульс — `HKQuantityTypeIdentifierHeartRate`
с тем же `sourceName` и временем в пределах 2 минут от замера давления
(пульс часов в покое НЕ берётся). Точка = среднее за день, `lab`:
«Самоизмерение (Apple Health)» / «…, среднее из N замеров за день» (как у
существующих 47 точек). Дни, уже имеющиеся в ряду с тем же источником, не
дублируются; дни, на которые есть ручной замер в `vitals.bp`, пропускаются
с пометкой в плане. Поток — тот же, что у intake: план → dry-run → показать →
`--apply`, резервная копия перед записью. Парсинг потоковый (`iterparse`) —
экспорт бывает в сотни МБ.

**Вид:** карточка «Артериальное давление» (пара `exam_bp_sys`+`exam_bp_dia`) и
«Пульс» (`exam_pulse`, имя ряда — «Пульс») показывают объединение рядов
`labs.json` и `vitals.bp`; у ручных точек источник «Вручную». Нормы/статусы —
от рядов `labs.json`. Ручную точку можно поправить и удалить, точку из
`labs.json` — нет (её источник — файл).

## 13. Личный анамнез «Я» и связь с замерами (2026-11-02)

**Решение владельца:** в `anamnesis.json` добавляется раздел `self` — аллергии,
хронические болезни, перенесённые болезни (в т.ч. ковид), операции, травмы,
госпитализации. Писатель — страница (как `family`); Claude один раз заполнил
`self` по документам из `studies.json` (диагнозы с `study`), дальше не пишет.

**Контракт** (`health-anamnesis@1`, поле необязательное):
`self: { allergies_checked: bool, allergies: [], history: [] }`.
- `allergies_checked` — `true` и пустой список = «аллергий нет»; `false` =
  «не заполнено» (как `unknown` у родственника — «нет» ≠ «не знаю»).
- Аллергия: `id`, `substance`, `kind` (`drug|food|insect|other`), `reaction`,
  `severity` (`mild|moderate|severe|anaphylaxis`), `certainty`
  (`known|hearsay|guess`), `since` (год или null), `note`.
- Событие `history[]`: `id`, `name`, `kind` (`chronic|illness|surgery|injury|
  hospitalization`), `group` (как у `family`), `start` (`YYYY` | `YYYY-MM` |
  `YYYY-MM-DD`), `end` (то же или null), `status` (`active|resolved|remission|
  unknown`), `treatment`, `certainty`, `study` (id из `studies.json` или null),
  `note`. Обычные простуды не записываются; ковид, пневмония, курсы
  антибиотиков, всё с госпитализацией — записываются.

**Связь «замер ↔ болел ли тогда» — вычисляется страницей, не хранится.**
Точка биомаркера (и ручной замер) с датой `d` получает пометку, если есть
событие `kind ∈ {illness, injury, surgery, hospitalization}` с
`start ≤ d ≤ (end или start) + 28 дн.`: «во время: <name>» или «через N дн.
после: <name>». Точность `YYYY-MM` — пометка «в тот же месяц: <name>», `YYYY` —
не ставится. `chronic` не помечает (длится всегда). Это факт о дате, а не
интерпретация: вывод «значение искажено болезнью» делает разбор, не страница.

**Скилл `health-labs`:** `anamnesis.json` не пишет. При разборе документа с
диагнозом (МКБ-код, выписка, больничный, консультация) кладёт в план блок
«Предложение для анамнеза» — что добавить в «Я» на странице; при разборе
показателей читает `self.history` и учитывает болезни около дат замеров.

**Вид:** третий вид «Я» во вкладке «Анамнез» (первым: «Я · По людям · По
болезням»): аллергии вверху (или «не заполнено» / «аллергий нет»), затем
хронические, затем остальное по дате (новые сверху). Формы добавления и правки
— как у родственника. «Текст для врача» начинается с личного: аллергии,
хронические, операции, значимые болезни, потом семейный.

**Дополнение §13 (2026-11-02, владелец): окно события и панель события.**
- У события `history[]` — необязательные `window_before` и `window_after` (целые
  дни, 0–365). Нет поля — по умолчанию: `surgery`/`hospitalization` — до 14,
  после 28; `illness`/`injury` — до 0, после 28; `chronic` — окна нет. Окно
  задаётся в форме события и в панели события (выбор сохраняется сразу).
- Пометка у точки биомаркера — по окну события: «за N дн. до: …» (только при
  `window_before > 0`), «во время: …», «через N дн. после: …».
- **Панель события** (`uiPaneHTML`, стопкой; открывается нажатием на событие
  в «Я», в списке — только счётчик «N показателей рядом»): таблица показатель →
  «До» (последнее значение в окне до; нет — последнее раньше, но не старше
  180 дн., приглушённо с датой) → «Во время / после» (значения в окне после,
  с «+N дн.»). Сначала строки со сменой статуса норма ↔ вне нормы, остальные —
  под «ещё N». Нажатие на строку — карточка биомаркера поверх. Новых чисел и
  выводов панель не считает.
- **Аллергии:** блок выводится, только если список не пуст. «Аллергий нет»
  (`allergies_checked`) на экране не показывается — только в «Тексте для врача».
- **Уточнение владельца (2026-11-02, вечер), заменяет умолчания и правило точности выше:**
  окно по умолчанию для ВСЕХ событий (кроме `chronic`) — 0 дн. до, 28 дн. после.
  Для `illness` в форме обязательна дата окончания. Дата события вводится с
  выбором точности: полная дата / месяц и год / год. Границы события при
  неполной дате — по периоду: `start` = первый день месяца/года, `end` (или
  `start`, если `end` нет) = последний день месяца/года; «до» отсчитывается от
  первого дня, «после» — от последнего, «во время» — весь период. Пометка
  «в тот же месяц» и запрет пометок для точности «год» отменены.

**Дополнение §13 (2026-11-02, вечер): хронические, длинные болезни, «Требует внимания».**
- `chronic` — без окон: в форме событий этого вида полей «Окно анализов» нет (смена
  вида в форме переключает блоки, введённое не теряется); при сохранении
  `window_before`/`window_after` удаляются.
- У хронической — необязательное `markers`: массив уникальных id показателей (непустые
  строки ≤ 80 символов, не более 30; пусто — поле не пишется). Каталог выбора —
  `bioList()` плюс псевдопоказатели «Вес» (`vitals_weight`) и «ИМТ» (`vitals_bmi`,
  если есть рост) из `vitals.json`. Строка в «Я» с `markers` открывается и подписана
  «N показателей →». Панель (стопкой, как у события): по каждому показателю

  только она; нет в данных — «нет данных». Нажатие — карточка показателя поверх.
- **Вид панели хронической (v1.51).** Строка показателя — как «Показатели» в окне исследования

  дата · разница со знаком и единицей» (нет точки раньше начала — «первый замер после начала: …»);
  у веса, ИМТ и состава тела (`AN_PCT_IDS`) — ещё «(−7%)». Разница не окрашивается (без оценки).
  Справа «сейчас» (вне нормы — цветом статуса), под ним дата, после неё «больше года назад», если
  последняя точка старше 365 дн.; затем мини-график (точка отсчёта и всё после неё, крупная —
  последняя) и «→». Смена «норма ↔ вне нормы» между отсчётом и последней точкой дописывается
  в подпись («стал выше/ниже нормы», «вернулся в норму») и ставит строку выше остальных (дальше —
  порядок `markers`). Одна точка после начала — «единственный замер», без графика. Показатели без
  замеров после начала — не строками, а одной строкой внизу «Нет замеров после начала болезни: …».
  Смена статуса пишется, только когда норма известна у обеих точек («без референса» не сравнивается).

  и в чипе формы, и в нижней строке панели (v1.52). Подпись поля окончания («обязательно для
  болезни») следует за видом и при его смене в открытой форме (`anEveLabel`).
- «Во время: …» у точки биомаркера ставится только при длительности события

  «во время» остаются.

  365 дней; давние (вне нормы) — одна свёрнутая строка «Давние отклонения: N» под
  сеткой, по нажатию список. Тот же порог — в плитке здоровья `hub.html`.

  сняты; формат хранения прежний. «С какого года» у аллергии — то же поле `{ only: "y" }` (в
  `since` по-прежнему целое число). «＋ Добавить запись» у родственника — залитая кнопка.
- **Биомаркер из отчёта (v1.53).** Кнопка биомаркера в шапке отчёта открывает панель поверх окна

  панелями (`openDoc` снимает `panesOverDoc`).

## 14. Ручная точка анализа — только в режиме «без ИИ» (health v3.2)

`labs.json` читается через `apiGet` с хэшем (`NEED_FILES`; старый сайдкар → прежний путь `health-data/labs.json`,
только чтение). Кнопки «＋ Добавить точку» (карточка показателя, кроме пары давления и пульса — их вводит `bpModal`
в `vitals.bp`) и «Новый показатель» (каталог) — только при `uiAiMode() === "off"` и признаке `health_labs_manual`.
Запись — `POST /api/hd/save` с `base_hash`; сервер (`labs_rules.check_manual_edit`) пускает лишь точки
`source: manual` и новый показатель, статус (`auto_status`) и производные поля (`recompute_marker`) считает сам;
при `on` — 403. Точка помечена «вручную» (история, подсказка точки графика), правится и удаляется только своя.
Скилл `intake.py` ручные точки не трогает; совпадение даты и показателя — конфликт в dry-run.
