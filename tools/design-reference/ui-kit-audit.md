# Аудит стандартных UI-элементов Personal Hub → `ui-kit`

Составлен 2026-07-21 на ветке `ui-kit-unification`. Источник — три параллельных
read-only аудита пяти страниц (`tools/{hub,travel,games,food,health}.html`).
Цель — понять, что из общего UI можно вынести в `tools/assets/ui-kit.{css,js}`,
и с какой стоимостью. Это карта для многофазной унификации, не план правок.

## Уже вынесено (Фазы 1–2, закоммичено)

- **Датапикер** (`.dp-*`, `maskDMY/parseDMY/dateField/monthField/openMonthPicker/openCalendar/closeCalendars`) — из health в ui-kit.js/css. Единственный потребитель — health. Живёт с контрактом host-глобалов (`esc/fmtDay/MSHORT/todayISO`).
- **`esc()`/`attr()`** — единый полный replace в ui-kit.js (фикс реального дефекта: travel/games не экранировали кавычки в `data-*`). `ui-kit.js` подключён на всех 5 страницах, `ui-kit.css` — пока только health.

## Сквозная находка (определяет всю стоимость)

**food.html строит весь свой «хром» — топбар, крошку, заголовки, кнопки, модалки —
инлайновыми `style=""` в JS-шаблонах, а не классами.** Поэтому у food в CSS
буквально нет правил `.h-sec/.h-dot/.h-div/.crumb/.hub-masthead/.chip-btn(база)/.act-btn`,
а есть их дословные копии внутри строк рендера. Половина «дрейфа» в аудите — это
не «пять разных реализаций», а «food делает inline то, что у других класс».

**Следствие:** любой вынос CSS-хрома в ui-kit требует сперва переписать билдеры
food (`topBar()`, заголовки, `modal()`) с inline-стилей на классы — иначе вынос
фиктивен (ровно тот класс риска «старая копия молча живёт дальше», что уже
ловили на esc()). health, будучи такой же SPA, наоборот использует общие
классы — то есть SPA-архитектура шарингу CSS не мешает, food просто выбрал inline.

## Ярусы по стоимости выноса

### Ярус 1 — чистый вынос (риск низкий, окупаемость высокая)

Идентично или почти идентично на большинстве страниц; вынос механический.

| Элемент | Состояние | Действие |
|---|---|---|
| `@font-face` × 28 (Golos Text + Spectral) | **побайтово идентичны на всех 5** | вынести в ui-kit.css как есть; подключить `ui-kit.css` на остальные 4 страницы. ~−280 строк дублирования. Самый крупный LOC-выигрыш при нулевом риске |
| База `:root`/`[data-theme=dark]` токенов (bg/text/border/accent/warn/err/success/shadow/radius, c-1..c-6) | hub=health побайтово; у games/food осознанный трим | вынести общий набор; решить судьбу «сирот» `--accent-bg` (мёртв в hub/travel) и `--c-6` (жив только в games) — не баг, но мусор |
| Анти-мигание темы `<script>` в `<head>` | идентично 4/5; travel — легитимный share-кейс `?trip=`→светлая | оставить дублированным ПО ДИЗАЙНУ (внешний `<script>` вернёт вспышку) ИЛИ вынести с флагом share; зафиксировать тестом-инвариантом |
| `@keyframes spin` + `.spin` | тело идентично 3/5; food/health — то же тело под другим именем/inline | вынести; переименовать вызовы food (`food-spin`→общий) |
| `plural(n,one,few,many)` | идентичен 4/5, health не использует | вынести в ui-kit.js; health не пострадает |

### Ярус 2 — вынос после сведения (риск средний)

Тела/имена разошлись; сначала выбрать эталон, потом переносить, часть страниц переписать.

| Элемент | Расхождение | Что требуется |
|---|---|---|
| Топбар-идентити `.h-div/.h-sec/.h-dot` | travel=health канон; **games переименовал** в `.h-sep/.h-ident/.h-diamond`; **food — inline** | выбрать канон + переписать food `topBar()` на классы + переименовать games |
| `.chip-btn` (база) | hub/travel/games идентичны (999px-пилюля); health — сразу 8px-шапка; food — только `:hover`, база inline | выбрать канон + механизм модификатора (сейчас 4 разных пути к «топбар-кнопке»); games-шапка визуально отличается (weight 500 vs 600) |
| Кнопка-CTA `.act-btn.primary`/`.plan-btn`/`.rep-btn` | один смысл, три имени, три радиуса (9/8/999∨8); health внутренне несогласован (inline на каждом вызове) | свести к одному классу+модификатору |
| Чипы `.fchip`/`.vchip`/`.ap-chip`/`.st-chip` | padding/min-height нигде не совпадают 1:1; **активное состояние тремя механизмами**: CSS `.on` (travel) / зеркалирование атрибута (food) / JS-inline `chipStyle()` (health) | согласовать механизм selected перед выносом CSS — иначе часть страниц не подключит общий класс |
| Заголовки `.sc-head/.sec-eyebrow/.hub-masthead` | `.hub-masthead` — 3 адаптивные стратегии (hub clamp 34–58, travel фикс 58+media, games/health clamp 42–58); **food без класса, 4 inline-профиля в одном файле** | самый трудоёмкий узел яруса; food — переписать заголовки на класс |
| `cacheGet/cacheSet/bust` | тело одинаковое; TTL из `CONFIG.cacheTtlMin` vs `CACHE_TTL_MIN`; **есть только на hub/travel/games** | параметризовать; food/health кеш НЕ добавлять (у них write-API, TTL замаскировал бы свежесть) |
| `fmtDate` | 3 сигнатуры: hub ждёт `Date`, games — ISO-или-Date, health — ISO | выбрать один контракт (ISO), проверить все call-site hub |

### Ярус 3 — архитектурный пересмотр (риск высокий)

Не «вынос», а сведение двух разных архитектур; обязателен ручной браузер-тест.

| Элемент | Почему дорого |
|---|---|
| Поля формы `fld()` | food 6 арг. vs health 8; параметр `span` **семантически несовместим** (число колонок у food vs булев full-width у health) — механическое слияние ломает ~15+ call-site |
| `area()` / тумблер `.tgl` | существуют только у health; тумблер — не CSS-класс, а JS-функции, генерящие inline-стиль по состоянию → сперва перевести в классы `.tgl.is-on` |
| Система модалок `modal()` | food (5 арг., `sub`/`extraFoot`, nested-DOM + noop-guard) vs health (3 арг., delete вынесен из модалки, sibling-overlay) — **две разные архитектуры закрытия-по-клику-вне**; выбрать одну, переписать другую сторону |
| `.savebar` | у health — зрелый класс; у food класса нет вовсе (inline-копия) → «перевести food на health-компонент», не слияние |
| `nav-rail`/`.mnav`/`.h-mnav` | разные имена (health `.h-mnav`), **три z-index (60/70/80)**, **три breakpoint (760/820/860)** — перед объединением сверить стек-контекст слайд-оверов каждой страницы |
| Переключатель темы | id-listener (hub/travel/games) vs data-act/`ACTS` (food/health) — принципиально разный из-за модели рендера; унифицируемо только на уровне «применить data-theme», не общей функции |

### Ярус X — обязано остаться per-page (НЕ трогать)

- Доменный акцент `--c-N` в разметке — это идентичность раздела, не дублирование.
- food `--paper`/`--c2-bg`, `@media print`/`.sc-print`/`.print-sheet` — уникальный визуальный язык + единственный потребитель печати.
- health `sparkPath()` (привязан к `tms()/r1()` и форме данных), `trim(v)` (**НЕ строковый — числовой форматтер; не путать/не переименовывать наивно**).
- travel share-исключение анти-мигания (`?trip=`→светлая).
- hub пара `#btn-login`/`#btn-logout` — уникальная роль корневой страницы (обрабатывается в Фазе 3 плана auth/refresh).

## Рекомендованный порядок (окупаемость ↓ / риск ↑)

1. **Ярус 1 «чистая метла»** — `@font-face` + база токенов + `plural` + `spin` + анти-мигание. Один низкорисковый проход, ~−300 строк дублирования, и именно здесь `ui-kit.css` становится общим для всех 5 (сейчас его линкует только health). Фундамент для всего остального.
2. **Фаза 3 плана (auth/refresh)** — уже разобрана, низкий/средний риск, явно запрошена пользователем (hub-баг, food-логаут, единый «Обновить»).
3. **Ярус 2: кнопки + чипы + топбар** (с переписыванием food-хрома на классы) — видимый выигрыш «одинаковые стандартные элементы».
4. **Ярус 3: поля + модалки** — самое дорогое; только после сведения сигнатур и с полным ручным тестом всех модалок обеих страниц.

## Честная оценка

- Исходная мотивация («датапикеры реализованы по-разному») на поверку не подтвердилась: датапикер был только у health. Настоящий разнобой — в кнопках/чипах/топбаре/полях, и он реальный.
- Самый большой выигрыш при нулевом риске — Ярус 1 (одни шрифты это ~280 строк × дублирование). Его стоит сделать вне зависимости от остального.
- Самое дорогое и рискованное (поля/модалки, Ярус 3) даёт наименьший видимый эффект на строку кода и требует ручного тестирования — кандидат делать последним или не делать вовсе, если food/health редактируются редко.
- Ключевой скрытый множитель стоимости для Ярусов 2–3 — **переписывание inline-хрома food на классы**. Без него унификация food фиктивна.
